Use offline learning packs

A learning pack is a directory containing reading material, practice examples and a small catalogue called a manifest. The manifest describes what each file is for. A reader can use that description to show a title, find a topic or link a lesson to its example. Keeping these details together lets the same pack serve a desktop application, a documentation website or a mobile reader.

This guide uses the real C example in main.c beside this page. It loads the manifest through Umicom Framework, prints its resources and can verify one resource's contents. The example uses an installed Framework SDK containing the developer component. The current Studio foundations-library chooser remains available; it does not automatically discover these manifests.

1. Understand the four pieces

PieceResponsibility
Pack directoryOwns the manifest and its declared files. The reader receives its absolute location explicitly.
ManifestNames the product, locale, content revision, compatible product versions and resources.
Framework pack serviceChecks the catalogue, bounds allocations and reads declared files through rooted storage.
Application readerChooses what to display, how to render it and whether a learner may copy an example into a practice project.

A resource is one declared file. Its identifier is a stable name such as guide; its path is a location such as guide.html. Using an identifier in navigation allows a publisher to reorganise a directory without changing every lesson link that refers to that identifier.

2. Build the real inspection example

Install a current Framework SDK with the developer component first, using the same compiler and target platform as the consumer. The example checks the chosen SDK's origin, environment metadata and installed headers. A core-only SDK does not supply the learning service.

Run each stage separately. Stop if a command fails and keep its log. PowerShell does not automatically stop after a native program returns an error.

New-Item -ItemType Directory -Force "C:\umicom\_local\logs\learning-pack"

cmake --build "C:\umicom\_local\learning\pack-inspector" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\learning-pack\build.log"

The three example checks list the pack, verify its guide and verify its C example. Successful configuration also creates a pack directory inside the chosen build directory. It copies this guide and main.c, calculates their hashes and fills learning-pack.json.in to produce a complete manifest. Hashing the staged bytes avoids assuming that every checkout has identical line endings.

& "C:\umicom\_local\learning\pack-inspector\umicom-learning-pack-inspect.exe" "C:\umicom\_local\learning\pack-inspector\pack" "learning-pack.json"

Expect the title, product, locale and two resources. The second command also prints Verified guide: followed by its byte count. The inspector reports verification; an application document renderer is responsible for displaying the HTML and its illustration.

3. Read the manifest

JSON represents an object with braces, named fields and values. A quoted value is text. An array uses square brackets and keeps its values in order. In this format, [0, 9, 0] is a major, minor and patch version.

{
  "schema": "umicom.learning.pack",
  "version": 1,
  "id": "framework.learning-packs",
  "title": "Learning offline documentation packs",
  "product": "framework",
  "locale": "en",
  "revision": 1,
  "compatibility": {
    "minimum": [0, 9, 0],
    "maximum": [0, 9, 0]
  },
  "resources": [
    {
      "id": "guide",
      "title": "Use offline learning packs",
      "topic": "learning-packs",
      "kind": "guide",
      "path": "guide.html",
      "sha256": "THE_64_HEXADECIMAL_CHARACTERS_FOR_THE_ACTUAL_FILE",
      "example": "inspector"
    }
  ]
}

This shortened illustration omits the second resource and uses a hash placeholder. Use the generated complete manifest for a working input. The example field must name another resource whose kind is example. A missing reference is rejected. Valid kinds are lesson, guide, example and image.

The schema version describes the manifest format. The content revision describes this pack's edition. Compatibility bounds describe the embedding product version and include both endpoints. The example uses the Framework version because it reads a Framework guide. A Trader or Studio adapter must supply its own product version for product-specific packs.

Version one rejects unknown fields and duplicate field names, including names spelled with JSON escapes. It accepts at most 256 resources and a 256 KiB manifest. Pack and resource identifiers use letters, digits, dots, hyphens and underscores, starting with a letter or digit. Locale names use alphanumeric segments separated by hyphens; this checks spelling, not the existence of a translation. Labels must contain visible text and no ASCII control characters.

4. Follow the C ownership

UmiLearningPack *pack = NULL;
UmiVersion host = {0, 9, 0};
UmiStatus status = UmiLearningPackLoad(root, "learning-pack.json", host, &pack);
if (status == UMI_STATUS_OK) {
    UmiLearningPackInfo info;
    status = UmiLearningPackCopyInfo(pack, &info);
    /* Use info only after checking status. */
}
UmiLearningPackDestroy(pack);

A pointer such as pack names an object owned by the application. The ampersand in &pack passes the address of that pointer so the loader can publish the new owner. A failed load leaves it null. Destroying a null pack is safe. Release an existing owner before reusing its output variable.

Metadata snapshots contain their own character arrays. They can outlive the pack. Resource bytes have separate ownership: call UmiLearningPackFreeBytes after the reader finishes using them. Keep the pack alive during a read. Immutable metadata supports concurrent reads while the owner prevents destruction.

UmiLearningShelfAdopt transfers a pack into a shelf. On success it clears the caller's pack pointer. On failure the caller still owns the pack. A shelf can own up to 32 packs and requires unique pack IDs. Resource identifiers are qualified by a pack ID, so two products can both have a resource called guide. Serialize shelf changes against reads and removal.

5. Understand integrity and trust

SHA-256 calculates a fixed-size digest from file bytes. A changed byte normally produces a different digest. The reader checks the digest of the exact buffer it returns. It therefore avoids checking one file read and then displaying a later, potentially different read.

A hash does not establish who published the pack. Someone able to replace both a file and its manifest can recalculate it. Review the source of a pack before adopting it. The rooted-files service rejects traversal, reserved device names and links or reparse points beneath the chosen root. Ancestors above that root remain trusted. This service does not establish a content-revision lock against other writers.

Each resource read has a caller-chosen maximum byte count. Images and examples may be binary; an embedded zero byte is retained. The renderer must apply its own content-type, script and link policy. Reading an example never grants workspace trust or permission to execute it. Copying examples into a practice project is a separate operation with its own destination and overwrite rules.

6. Investigate an error

  • Unavailable: check the reader's product version against both compatibility endpoints.
  • Already exists: look for duplicate manifest keys, resource IDs or an adopted pack ID.
  • Not found: check a required field, referenced example, pack ID or the physical file named in the manifest.
  • Invalid state while reading: the selected file no longer matches its declared hash. Inspect the change and regenerate the pack intentionally.
  • Capacity exceeded: check field lengths, resource count, manifest limits and the chosen resource byte limit.
  • Invalid argument or permission denied: inspect the absolute root and relative path. Moving a pack requires selecting its new root explicitly.

After editing either example file, reconfigure to regenerate the staged pack and its hashes. Keep the configure, build and test logs together with the source revision used. The Framework tests under framework.learning_pack cover schema refusal, copied ownership, compatibility boundaries, changed bytes and two independent pack directories. Their result applies to the source and environment actually tested.

Follow links within the same pack

A resource identifier names an entry in the manifest. A filename says where its bytes are stored. These are different things: the identifier inspector names the file main.c in this example. A lesson reader should resolve a link through the pack before opening it, so an arbitrary filename cannot silently become part of the learning library.

  1. Keep the identifier of the resource currently displayed. For this guide it is guide.
  2. Pass that identifier and the lesson's local link to UmiLearningPackResolveLink. A link such as main.c is relative to the current resource's containing folder.
  3. Check the returned status. On success, the result contains copied resource metadata and an optional anchor. On failure, your previous selection stays unchanged.
  4. Read the selected resource using UmiLearningPackReadResource. This checks the actual bytes against the manifest before your reader displays them. Resolving a name alone does not check the file.
#include "umicom/teacher/learning_navigation.h"

UmiLearningPackLink next = {0};
UmiStatus status = UmiLearningPackResolveLink(
    pack, "guide", "main.c", &next);
if (status == UMI_STATUS_OK) {
    unsigned char *bytes = NULL;
    size_t size = 0;
    status = UmiLearningPackReadResource(
        pack, next.resource.id, 4U * 1024U * 1024U, &bytes, &size);
    if (status == UMI_STATUS_OK) {
        /* Render these checked bytes as source text.
         * Opening a source example does not grant permission to run it. */
    }
    UmiLearningPackFreeBytes(bytes);
}

The #navigation suffix is an anchor: a named place inside a document. The resolver returns that name; the renderer must still find the matching heading. An empty link or a link starting with # stays in the current resource. An image link such as images/diagram.svg is permitted only when the manifest declares that relative path.

This first offline link profile accepts literal filenames and forward slashes. It refuses parent traversal (..), dot segments, absolute paths, network addresses, query strings, percent escapes and backslashes in links. It does not download external pages. Use portable filenames and keep related lessons and assets beneath an appropriate common folder. A future broader URL policy must be explicit; a frontend must not bypass a refusal by sending the same text to a browser or shell.

UmiLearningPackFindPath is available when an adapter already has a pack-relative filename. It compares the manifest's slash spelling consistently. If two resource identifiers declare the same path, path lookup reports ALREADY_EXISTS rather than selecting one by array order. Direct identifier lookup remains unambiguous.

Keep a reading session with Back and Forward

A single verified read gives an application some bytes. A reading session also needs to remember which lesson is open and how the learner arrived there. UmiLearningReader owns that session. It holds one pack, the current verified content and up to 64 history entries. A history entry records a resource identifier and its anchor. It does not retain a second copy of every document.

Ownership means one place is responsible for cleanup

Load a pack as before, then pass its pointer by address to UmiLearningReaderCreate. On success, the reader takes ownership and clears your pack pointer. Destroying the reader later also destroys its pack and frees its current content. If creation fails, your original pack remains yours. This rule lets the same cleanup code handle both outcomes.

#include "umicom/teacher/learning_reader.h"

UmiLearningPack *pack = NULL;
UmiLearningReader *reader = NULL;
UmiStatus status = UmiLearningPackLoad(
    selected_directory, "learning-pack.json", host_version, &pack);
if (status == UMI_STATUS_OK) {
    status = UmiLearningReaderCreate(
        &pack, 4U * 1024U * 1024U, &reader);
}
if (status == UMI_STATUS_OK) {
    status = UmiLearningReaderOpen(reader, "guide");
}
/* Use reader here while it remains alive. */
UmiLearningReaderDestroy(reader);
UmiLearningPackDestroy(pack);

The address operator & gives the function access to your pointer variable. It can set that variable to NULL after a successful transfer. The size limit is four mebibytes: four groups of 1,024 × 1,024 bytes. This bounds each content allocation. The API accepts limits from one byte up to 16 mebibytes; a file larger than your chosen limit is refused.

A failed navigation is not a new page

Open selects an explicit resource identifier. Follow resolves a local link relative to the current document. Both read and verify the candidate before changing the session. A missing file, invalid path, changed hash or allocation failure leaves the old content and history in place. A UI can show an error beside the existing page instead of displaying a blank panel or a mismatched title.

Back and Forward also verify the requested document again. If a file changed on disk after an earlier visit, the operation fails and the history cursor stays where it was. Reload rechecks the current page without creating another history entry. Reopening the same resource and anchor has that same history behaviour.

ActionHistory result after success
Open A, then follow BA and B are recorded; B is current.
Back from BA becomes current; Forward can return to B.
Open C while at AC replaces the forward branch. The new path is A → C.
Try to open an invalid link from AA stays current and the forward branch remains available.
Visit a 65th distinct entryThe oldest entry is evicted; the most recent 64 remain.

Use UmiLearningReaderCopySnapshot to obtain the current title, identifier, anchor, byte count and Back/Forward availability. The snapshot is a copy. A successful content commit increments its revision, so a frontend can distinguish a newly loaded document from an earlier display update.

Transfer content to the display safely

Disk access can take time. Run reader operations on a worker owned by your application. Serialize access to that reader: one operation must finish before another changes or destroys it. The reader does not add its own background thread or call a UI callback.

  1. Query the content size with UmiLearningReaderCopyContent(reader, NULL, 0, &size).
  2. Allocate size + 1 bytes and check the allocation. The extra byte holds a terminating zero.
  3. Copy the content while the same owner still controls the reader. If an application changes the reader between the query and copy, it must handle a capacity error and repeat the operation.
  4. Transfer that independent allocation and its metadata to the UI using your application's existing message or event mechanism.
  5. Let the UI release its copy when it no longer needs it. Do not share mutable reader state across threads.

Use the explicit byte count even though a terminating zero is supplied: examples and images may contain binary zero bytes. A renderer must choose how to handle each resource kind, validate text encoding and refuse implicit script or source execution. This session service does not render images, execute HTML, open external websites or compile practice code.

Read and run the complete example

The file history.c beside this guide is a complete C application. It opens a lesson, follows another resource, goes Back and Forward, then copies the selected bytes into an independent allocation. It demonstrates cleanup after both success and failure.

& ".\umicom-learning-pack-history.exe" "$PWD\pack" learning-pack.json guide main.c

Expected output describes Open on guide, Follow on inspector, Back on guide, and Forward on inspector. The final line reports the independent copy's byte count. Copy an example into your own practice file

A lesson is easier to understand when you can change its example. Keep the learning pack as a reference and make a separate practice copy. A copy contains the same bytes at the time of copying, but later edits to that file do not change the original. The Framework operation here creates one new file. It does not assemble a multi-file project or decide that the code is safe to run.

The complete application in practice.c uses UmiLearningPracticeResolveExample to find the example linked to a lesson. A manifest's example field contains a resource identifier, not a command. Selecting an example directly also works. A guide without an example link returns NOT_FOUND; the reader should explain that no practice file is provided.

Choose a destination and preview it

  1. Build the inspection example using the earlier SDK instructions. It also builds umicom-learning-pack-practice.
  2. Create an empty practice directory that you control. This directory is separate from the pack. A root is the directory below which this operation is allowed to select a file.
  3. Run the preview command below from the example's build directory. Replace the practice directory with your chosen absolute path.
  4. Check the example title, destination root and new filename. Preview checks manifest metadata and path syntax. It does not open the destination or promise that the directory is writable.
New-Item -ItemType Directory -Force "C:\umicom\practice\learning-packs"
& ".\umicom-learning-pack-practice.exe" "$PWD\pack" learning-pack.json guide "C:\umicom\practice\learning-packs" my-inspector.c

The output includes “Preview only.” No file named my-inspector.c should appear. The root is an absolute path. The filename is relative to that root, so my-inspector.c means a file inside the chosen directory. Nested relative names are allowed only when their parent directories already exist. Dot segments, device names, links beneath the root and .git paths are refused by the rooted storage service.

Request the copy explicitly

& ".\umicom-learning-pack-practice.exe" "$PWD\pack" learning-pack.json guide "C:\umicom\practice\learning-packs" my-inspector.c --copy

The additional --copy argument requests creation. Framework reads the example under a caller-selected size limit, checks the manifest digest and passes those exact bytes to an exclusive file writer. Exclusive means that an existing destination is refused as part of opening the new file. An earlier “does this file exist?” check alone would be unsafe: another writer could create the name between that check and the write.

Expected output reports the number of copied verified bytes. Open the new file in your editor and compare it with pack/main.c. Edit only your practice copy. Running the copy command again should report ALREADY_EXISTS on an ordinary existing destination. Choose another new filename if you want a fresh copy; the service does not overwrite your edits.

Understand failure without losing work

ResultMeaningNext step
Source hash mismatchThe source bytes differ from the manifest. No destination creation was attempted.Obtain or rebuild the intended pack and investigate why it changed.
Destination already existsThe existing file was not opened for replacement.Keep it and choose a different name.
Missing destination parentThe operation does not create directories for you.Create the intended directory yourself, then retry.
Failure after new-file creationA new, possibly partial file remains. Its accepted byte count is reported.Inspect that file before choosing a new destination. File existence alone does not establish success.

The C result separates source_verified, destination_attempted and destination.created. The writer sets destination.complete only after all bytes, the flush and the close succeed. Flushing asks the operating system to commit its buffered output; it is not a guarantee against every power failure or storage fault. The writer retains a partial file on failure and never removes it by pathname. This avoids deleting a file that another process might have replaced.

For an application interface, perform copying on a worker, then send the copied result to the UI. Display the error and the chosen destination. Do not automatically compile or run an example after copying: use the application's separate project-opening and execution-trust workflow. Framework's built-in project generators remain available when a lesson needs a complete buildable project rather than one source file.

The installed example's sdk.learning_pack.practice.copy test checks preview, copying, preserved source bytes and refusal of an existing destination. Framework's focused creation tests also cover native I/O failures and competing writers. These command-line checks do not replace testing the actual Studio learning interface.

Search titles and topics offline

A catalogue search helps a reader find a guide without opening every document. The Framework service searches the metadata already admitted to a UmiLearningShelf. It does not scan the disk, download content or read resource bodies. This distinction makes the work bounded and keeps a search separate from later content verification.

The complete search.c example loads one pack, transfers it to a shelf, makes a query and prints copied results. A product can adopt several packs into the same shelf. Each pack must have a distinct identifier and must already have passed its host-version compatibility check.

& ".\umicom-learning-pack-search.exe" "$PWD\pack" learning-pack.json
& ".\umicom-learning-pack-search.exe" "$PWD\pack" learning-pack.json history framework en
& ".\umicom-learning-pack-search.exe" "$PWD\pack" learning-pack.json no-such-topic

The first command browses the resources because it supplies no query text. The second finds the reader-history example, restricting results to product framework and locale en. The third should report zero matches and exit successfully: finding no matching resource is a valid search result, not a process failure.

Choose explicit matching rules

UmiLearningSearchQuery starts with all fields zeroed. Put text in its bounded text array, or leave it empty to browse. Words separated by ASCII spaces form up to eight terms. Every term must occur in a resource ID, resource title, topic or pack title. Different terms may match different fields. The characters * and ? have no special meaning.

ASCII letters match without regard to case. Other bytes match exactly. For example, a UTF-8 query containing café can match that spelling, but this service does not normalize different Unicode representations or fold every language's uppercase letters. A frontend validates its query's encoding and should explain these matching limits. Control characters and unterminated input arrays are refused.

Product filtering uses the exact stable identifier. Locale filtering ignores ASCII letter case but does not fall back from a region-specific locale to a language-only locale. The optional kind selects lessons, guides, examples or images. A zero kind accepts all of them. Empty product and locale arrays leave those filters disabled.

Keep result ownership separate from the shelf

#include "umicom/teacher/learning_search.h"

UmiLearningSearchQuery query = {0};
UmiLearningSearch *search = NULL;
/* Fill query using checked bounded copies if filters are needed. */
UmiStatus status = UmiLearningSearchCreate(shelf, &query, 64U, &search);
if (status == UMI_STATUS_OK) {
    UmiLearningSearchInfo info;
    status = UmiLearningSearchCopyInfo(search, &info);
    /* Read complete copied hits with UmiLearningSearchResultAt. */
}
UmiLearningSearchDestroy(search);

A result contains the pack description, the resource description and flags showing which metadata fields matched. It owns copies, so removing or destroying the shelf cannot leave dangling text pointers in the result. The application must still serialize the shelf while a search is being created. Once created, the immutable search can be read while its owner keeps it alive.

A search can retain between one and 256 hits. The summary reports how many resources matched and whether results were truncated. Results follow shelf order and manifest order; there is no relevance score. For example, a request limited to one hit can report five matches, one retained result and truncated = true. Do not show that result as the entire catalogue.

Each new search reads the current admitted metadata, so a removed pack no longer appears in a new query. An older result remains a historical snapshot. Discard or relabel it when the catalogue changes. Before opening a hit, resolve its current pack and resource identity again, then verify the resource bytes. A search match is not permission to open an external link, copy a file or run code.

This metadata service is the first part of catalogue search. It does not index body text, extract glossary entries, produce exact paragraph anchors or supply a Studio search panel. Those require additional indexing and interface work; the current console example demonstrates only the contracts described here.
