Planning boards with Umicom Framework

A Kanban board groups work into columns. Umicom's native C library shares card rules between application hosts. The library provides planning data, checked changes, filtered pages and portable archives. A graphical board, collaboration server and automatic tool execution are separate application integrations.

1. Add the library to a native application

Use a C23 compiler and a Framework SDK containing the Kanban library. In your CMake project, load the package and link its target:

find_package(UmicomFramework CONFIG REQUIRED)
target_link_libraries(my_application PRIVATE Umicom::kanban)
set_target_properties(my_application PROPERTIES C_STANDARD 23 C_STANDARD_REQUIRED YES)

Source-tree hosts can link the same target after adding Framework. Include umicom/kanban/board.h for edits, view.h for pages and summaries, and archive.h for import/export.

2. Create a board and propose a card

Each successful batch produces a new revision. A revision is a number used to reject an edit based on an outdated view. Keep all board calls on one owner thread, or serialize them in your host. Check every returned status.

#include <stdlib.h>
#include <string.h>
#include "umicom/kanban/board.h"

UmiKanbanBoard *board = NULL;
UmiStatus status = umi_kanban_board_create_development(
    "application", "Application development", &board);
if (status != UMI_STATUS_OK) return status;
UmiKanbanEdit *edit = calloc(1, sizeof(*edit));
if (edit == NULL) {
    umi_kanban_board_destroy(board);
    return UMI_STATUS_OUT_OF_MEMORY;
}
edit->kind = UMI_KANBAN_CREATE_CARD;
strcpy(edit->card.id, "build-dialog");
strcpy(edit->card.title, "Show build diagnostics");
strcpy(edit->column_id, "todo");
edit->card.priority = UMI_KANBAN_HIGH;
UmiKanbanProblem problem;
status = umi_kanban_board_apply(board,
    umi_kanban_board_revision(board), "contributor", edit, 1, &problem);
free(edit);
/* Read or save the board while this owner remains alive. */
umi_kanban_board_destroy(board);
return status;

The example uses short literals that fit the fixed fields. Validate user input length and encoding before copying it. Display card text as plain text. Actor and assignee identifiers are local labels, not authenticated identities.

3. Move work through the development workflow

ColumnAllowed destinations
tododoing
doingtodo, testing
testingdoing, done
donetodo

Use a MOVE_CARD edit with the card ID and destination column ID. A before-card ID inserts before an active card; an empty value appends. UPDATE_CARD replaces card details without moving it. Custom boards can define different columns and transition edges when created.

A card entering Doing or Testing must have no explicit blocker and all prerequisites in Done. Done also requires every checklist item complete. A planning checklist is a person's assertion; it does not certify build or test results. A blocked card already in progress stays visible.

A work-in-progress limit caps active cards in a column; zero means unlimited. Limits are checked against the complete batch, allowing one card to leave while another enters. A rejected batch changes no cards, activity or revision. Reopening a prerequisite of completed work requires reopening its completed dependents in the same batch.

4. Read pages and summarize work

Read the revision, then call umi_kanban_board_page with that revision for every page. Filters combine column, assignee, label, case-sensitive text, minimum priority, blocked state and overdue state. Supply the current UTC time in seconds for deadline comparisons. If an edit changes the revision, restart pagination rather than combining pages from different states.

Archives keep card IDs reserved. They do not count against active work limits. Restoring a card checks the current board rules again. An active card cannot reference an archived prerequisite. Summary counts distinguish active, archived, done, blocked and overdue work.

5. Save and restore a portable board

  1. Call umi_kanban_board_encode with a null buffer and zero capacity to measure the byte count.
  2. Allocate that many bytes and encode at the same revision. A short buffer is refused without partially overwriting it.
  3. Use your application's reviewed storage service and a user-selected location to save the bytes. The Kanban library itself does not access files or networks.
  4. Read the file with a bounded input service and call umi_kanban_board_decode. Keep the current board until decoding succeeds.
  5. Publish the new owner in the host and destroy the old owner only after readers have released it.

Decoding checks the envelope, lengths, identifiers, dependency graph, limits and completion rules. Its checksum detects accidental damage; it is not encryption or proof of authenticity. A restored board starts at revision 1 with empty local activity. The saved revision is historical information. Archives may contain private planning text; their storage and sharing remain the host's responsibility.

6. Qualify the module independently

From a Framework checkout, use a separate, short build directory. These commands compile the production board and base codec, and register only Kanban tests:

cmake -S tests/kanban -B build/kanban -G Ninja -DBUILD_TESTING=ON
cmake --build build/kanban --parallel 2
ctest --test-dir build/kanban --output-on-failure --no-tests=error

A successful run reports all registered Kanban cases passing. It does not qualify the full SDK, GTK host or other products. In a configured full Framework build, build umi-kanban-board-test, umi-kanban-view-test and umi-kanban-archive-test, then select ^framework[.]kanban[.] with CTest's -R option.

Troubleshooting and limits

  • Stale: reread the board and ask the host to review the proposed edit again. Do not silently retry against a newer revision.
  • WIP or dependency refusal: display the returned card/column identifiers and preserve the draft for correction.
  • Invalid archive: preserve the original file and current board. Never replace good state after a failed import.
  • Capacity: a board supports up to 1,024 cards, including archived cards, 16 columns and 128 edits per batch. Choose a smaller capacity for small boards.
  • Activity: only the latest 256 events are retained. This is local activity, not a durable audit trail.

7. Keep an editable board in a chosen folder

For native file storage, link Umicom::kanban_storage and include umicom/kanban/document.h. This separate adapter adds a document owner around the pure planning library. Ask the user to choose an existing folder and a filename ending in .umikb. It never chooses AppData or a home folder, creates parents, or uploads a board.

target_link_libraries(my_application PRIVATE Umicom::kanban_storage)
  1. Use umi_kanban_document_create(directory, filename, config, &document) for a new board, or umi_kanban_document_open for a saved board. Initialize the document pointer to null. Creation refuses an existing destination; opening refuses a damaged or unsupported archive.
  2. Borrow the board with umi_kanban_document_board, then use the same checked card editing API. The document owns this board. Do not destroy the borrowed board separately.
  3. Read umi_kanban_document_state to display the chosen location, revision and unsaved state. This call reads memory; it does not check for external file changes.
  4. Call umi_kanban_document_save with the reviewed live revision. The service compares the entire file with the last saved bytes and then writes a complete replacement. It keeps edits if the file changed, disappeared, became unreadable, or cannot be replaced.
  5. Call umi_kanban_document_close(&document, false) when finished. Dirty documents refuse closure. Save successfully first, or obtain the user's decision to discard edits and pass true. Closing never saves implicitly.

Run storage operations on a worker when used by an interactive application, and serialize all access to the document and borrowed board. No operation automatically merges, reloads or overwrites conflicting external content.

Recover from a refused save

UMI_KANBAN_SAVE_STALE_REVISION means the host presented an older board view. Read the current state before asking the user to review again. UMI_KANBAN_SAVE_EXTERNAL_CHANGE means the observed file no longer matches the baseline. Preserve both versions. Use umi_kanban_document_save_copy with a different unused filename to keep the current edits. This leaves the original binding and unsaved flag unchanged. After reviewing the copy, close the original with an explicit discard decision and open the chosen file.

A clean save checks disk but does not rewrite the archive. When reopening, the editable board starts at revision 1. The recorded archive revision describes an earlier session and must not be used as the current edit token.

Understand storage ownership and recovery limits

A session holds a native lease on the sibling file named filename.umikb.lock. A second cooperating editor receives BUSY. The guard remains after closing or crashing; its existence alone does not mean it is locked. Do not delete or replace guard files. They contain no board text. Keep the selected folder and its ancestors stable while a session is open.

New files use exclusive creation. Failed initial writes can leave an incomplete new file; retain it for diagnosis and use a new filename. Existing saves use the native complete-replacement service. An unrelated program that ignores the guard can still race between the comparison and replacement. This is local cooperative ownership, not a distributed transaction or a power-loss guarantee. Archives are plaintext. Choose suitable folder permissions and sharing rules for private planning data.

Qualify the storage adapter

This focused project includes the existing board tests and native storage tests. It does not build the application suite:

cmake -S tests/kanban_storage -B build/kanban-storage -G Ninja -DBUILD_TESTING=ON
cmake --build build/kanban-storage --parallel 2
ctest --test-dir build/kanban-storage --output-on-failure --no-tests=error

For an already configured full Framework build, build both umi-kanban-document-test and umi-kanban-storage-limits-test and select ^framework[.]kanban[.]storage[.] with CTest. Storage fixtures are created beneath the test build directory and retained for diagnosis. Windows symbolic-link cases report a skip when the native capability is unavailable; skips are not passes. These tests do not verify an application GUI, network collaboration or installed SDK relocation.
