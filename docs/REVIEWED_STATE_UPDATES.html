Review and publish state safely

A background refresh can finish after a user has made another edit. If the refresh blindly replaces the displayed collection, the newer work disappears. Framework's value registries provide a capture and a checked replacement so an owner can detect that conflict before publishing anything.

Understand the three pieces

  • The registry owns the current ordered collection.
  • A capture is your own copy of its records, accompanied by a count and a revision. The revision is an observation token for that particular registry.
  • A proposal is the complete collection you want to publish after reviewing that capture. Publication succeeds only if the registry is still at the captured revision.

The APIs ending in _registry_capture and _registry_replace_if_current apply to the value registries whose public headers declare them. They do not automatically make other stores thread-safe.

Capture, review and publish

  1. On the thread that owns the registry, call its capture operation with NULL records and zero capacity to discover the required count.
  2. Allocate your record array and call capture again. Use the revision returned by this second call: the collection may have changed since the size query. If capacity is insufficient, the array is untouched and the returned count tells you how much space is required. Bound retries if another producer is busy.
  3. Prepare the proposed records in your own storage. Every record needs a unique, terminated ID. Existing field and domain checks still apply. Keep the registry's identity together with its revision when handing work to another component.
  4. Return to the owning thread and call checked replacement using the captured revision. On success the whole collection is replaced in the proposed order.
  5. If the result is UMI_STATUS_INVALID_STATE, stop and obtain a fresh capture. Show the conflict or review it again. An automatic retry using a newer revision would bypass the very protection this API provides.
UmiSnapshotCapture capture;
UmiBookmarkSnapshot proposal[1];
UmiStatus status = umi_platform_bookmarks_registry_capture(
    bookmarks, proposal, 1U, &capture);
if (status == UMI_STATUS_OK) {
    /* Review and change the owned proposal before publishing it. */
    status = umi_platform_bookmarks_registry_replace_if_current(
        bookmarks, capture.revision, proposal, capture.count, NULL);
}
/* Handle a refusal explicitly; the registry still contains its previous data. */

This small example has room for one bookmark. A real collection should follow the size-query steps above. See the complete reviewed bookmarks example for a competing edit, a refused stale proposal and a deliberate second review. Its companion CMake project consumes a separately installed Framework SDK.

Know what replacement means

Replacement removes records that are not in the proposal. It is different from the existing multi-record upsert, which retains records you did not mention. An empty proposal clears a populated collection. Replacing an already-empty collection with another empty one makes no change.

A successful replacement advances the registry once and gives all published rows that same revision. Old metadata supplied in the proposal is normalised by the existing owner. Duplicate IDs, invalid fields, insufficient capacity and allocation failure leave the complete previous collection intact. The optional result identifies a rejected row when the failure concerns one record.

Revision exhaustion is a refusal, not a reason to reset the counter and continue with outstanding captures. Resolve that owner's lifetime explicitly. A revision from another object or an earlier destroyed registry cannot authorise an edit.

Keep text edits consistent

For fixed text fields that belong to a revisioned record, use umi_text_update. It checks the new text and remaining revision space before changing either the field or the revision. An oversized or invalid edit therefore preserves the earlier field. Text from the field itself, including a suffix, is supported. The revision must occupy separate storage.

Existing presentation-copy helpers keep their documented behaviour, including helpers that clear a destination when text does not fit. Choose the record-edit helper when failure must leave an existing record unchanged.

Extend an owner carefully

  • Keep shared behaviour in Framework. Application code should prepare user intent and display a refusal instead of duplicating registry internals.
  • When adding a text member, extend its validator and field-aware regression checks. A copied pointer is not an owned value: records containing handles, callbacks or owned pointers need an appropriate ownership design.
  • Capture and replacement require serialized owner access. A revision check is not a mutex and cannot repair a data race. Workers may prepare independent arrays; the owner remains responsible for reading and publishing the live collection.
  • Keep input records, output arrays and result metadata in separate storage as documented by the public functions. Do not alias them with private registry memory.
  • These operations publish memory only. Durable saving, schema migration and restart recovery still belong to the persistence service.

Chart documents use a complete registry capture and then retain only the chosen pane's drawings. This keeps neighbouring charts unchanged while preserving the observation needed for later review.

Review insertions and removals together

Use _registry_edit_if_current when a review changes only some records. Each typed edit contains a kind and an item. An upsert inserts a new ID or replaces an existing one; a removal reads only the item's ID. Records you do not mention retain their payload and position relative to other survivors.

  1. Capture the registry and keep its revision with your review.
  2. Create an array of the typed edits declared in that registry's header. Give each ID one operation. To change an existing row, supply its complete replacement using UMI_SNAPSHOT_EDIT_UPSERT. To remove it, use UMI_SNAPSHOT_EDIT_REMOVE and set item.id.
  3. Put removals before insertions when the registry is full. Operations run in the listed order on a private copy. A transaction can contain up to twice the registry's stored capacity, allowing a full set to be removed and replaced.
  4. Publish on the owner with the revision you reviewed. Check the returned status before updating the display or requesting a durable save.
  5. On failure, keep the review and explain the refusal. A missing removal gives UMI_STATUS_NOT_FOUND; repeated IDs give UMI_STATUS_ALREADY_EXISTS. The optional result identifies the edit that failed, when one applies. Nothing from the proposal has been published.

Success advances the owner once and gives every remaining row that publication revision. A current empty list makes no change; a stale empty list is still a conflict. Input edits are not changed. These rules let a properties panel keep its draft while the owner continues to hold a complete, usable collection.

The mixed bookmark lesson deliberately tries a missing removal. Its preceding insertion does not leak into the registry. The lesson then makes a new, valid decision and shows that repeating the old review is refused.

Review a complete SDK or test record

For SDK and test-state models that declare _replace_if_current, several related fields can be prepared together. Copy the live value and remember its original revision. Apply ordinary setters to the copy, checking each result. Then pass that copy and the original revision to the live owner's checked replacement. The live record receives one new revision, regardless of how many setters were used while preparing the proposal.

Both records must validate and retain the same ID. A proposal cannot rename another record, select the owner's revision or overwrite a newer value. Invalid fields and revision exhaustion leave the live value unchanged. This is a value operation: publishing a description of a package or test result does not inspect a package, execute a test or authenticate the supplied evidence.

The package description lesson shows related fields arriving together, followed by a stale description being refused. Its values explicitly remain awaiting inspection.

Try the public lessons

  1. Install the Framework SDK using the project's supported SDK installation workflow. Keep the install directory separate from your source checkout.
  2. Copy examples/snapshot_contracts to a separate working directory. Configure it with your C23 toolchain and the SDK's install prefix. For example: 
    cmake -S . -B build -DCMAKE_PREFIX_PATH="C:/UmicomSDK" -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure
    Replace C:/UmicomSDK with your actual SDK installation.
  3. The mixed-change lesson prints that a missing removal left the original draft intact, that a reviewed change succeeded, and that an old review was refused. The package lesson reports one publication followed by a stale refusal. A nonzero exit status means the observed behaviour did not match the lesson.
  4. If CMake cannot find UmicomFramework, check the installation prefix and the SDK's dependency setup. If the new symbols are unavailable, install matching headers and libraries together. Do not combine new headers with an older library. If a review is stale, obtain current state and review again rather than replacing the expected revision automatically.
