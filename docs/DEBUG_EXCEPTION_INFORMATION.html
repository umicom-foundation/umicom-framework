Inspect a stopped exception

An exception is a condition the debugger reports as interrupting normal execution. The exception viewer shows the description and nested causes supplied by the selected adapter. Availability depends on the language, target and adapter.

Use the viewer

  1. Open and trust your project. Start its native debugger or attach to a process you are authorised to inspect.
  2. If appropriate, use Exception filters to ask the adapter which exceptions should stop execution. Filter support and exception-detail support are separate capabilities.
  3. When the program stops because of an exception, open the Debug surface and expand Stopped exception.
  4. Choose Refresh exception. The request uses the observed stopped thread and current inspection revision.
  5. Read the exception identifier, description and break mode. Expand nested details to inspect messages, type names, inner causes and stack traces.
  6. After another stop, refresh again. The label describes a captured result; it does not claim the program is still at that stop.

What the viewer does

All text is descriptive. An adapter may supply an expression naming an exception object, but the viewer does not evaluate it. Stack traces are plain read-only text, and their paths and links are not opened automatically. Refreshing never resumes the program or changes a breakpoint.

The Framework checks the connection, stopped thread and inspection revision both before and after waiting. If a continued, stopped or exited event arrives during the request, the result is withheld until the host processes that event and you request current details.

When details are unavailable

  1. A normal breakpoint or manual pause is not necessarily an exception stop. Wait for an exception event before requesting details.
  2. The adapter must advertise exception-information support. Missing support is reported rather than replaced with invented information.
  3. A rejected response or timeout clears the previous displayed capture. Review the adapter output and the current program state before refreshing again.
  4. Replies allow 32 detail records and eight nesting levels. Each stack trace allows 8,191 UTF-8 bytes and each message 2,047. Larger or malformed replies fail explicitly; they are not silently shortened.

Reuse from Framework

Capture UmiDebugRuntimeExceptionTargetRead on the owner thread, then pass that target to UmiDebugRuntimeExceptionInformationRead. Recheck your application's workspace authority before requesting data. Allocate the large information result on the heap. Failed reads leave it unchanged.

UmiGtk4DebugExceptionInformationCreate hosts the same plain-text presentation for other development tools. Its callback must obtain a fresh authorised target; the widget owns its callback context until finalization.

Requests are synchronous and bounded, so the current window may pause briefly while the adapter replies. No retry is automatic.
