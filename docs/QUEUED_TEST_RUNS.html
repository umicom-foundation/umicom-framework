Running tests on the Framework task queue

Build a small Notes test project, run it without blocking an application window, and inspect completed results through the C API.

1. From a test catalogue to a test run

CTest is the test runner supplied with CMake. A configured project contains a catalogue of named tests. Discovery reads that catalogue; execution starts a selected test and checks its outcome.

A long test should not occupy the thread that handles clicks, typing and repainting. A task queue assigns that work to a worker thread. The application continues handling input and periodically copies a progress snapshot. It applies completed results to its own models on the application thread.

Choose tests→Copy requests→Submit a task→Poll results

Umicom uses UmiCtestJob for this workflow. The job uses the existing task queue, process service and verified CTest adapter. A worker owns its private request and result storage; it does not borrow a GTK widget or mutate an application's live catalogue.

2. Prepare the Notes test project

On Windows, install the UCRT64 C compiler, CMake and Ninja in the same MSYS2 prefix. Open PowerShell in your Applications checkout. Run one command at a time and stop when it reports an error.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$Cmake = "C:\msys64\ucrt64\bin\cmake.exe"
$CTest = "C:\msys64\ucrt64\bin\ctest.exe"

The example is in framework/examples/testing/notes_project. Its Save test writes a note to a temporary file and checks the saved bytes. The Unicode test checks non-ASCII text. The Index test is deliberately slow enough to practise cancellation and finishes on its own after a few seconds.

& $Cmake -S ".\framework\examples\testing\notes_project" `
    -B ".\build\notes-tests" -G Ninja `
    -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe `
    -DCMAKE_MAKE_PROGRAM=C:/msys64/ucrt64/bin/ninja.exe `
    -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw "Notes configuration failed." }

& $Cmake --build ".\build\notes-tests" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Notes tests build failed." }

& $CTest --test-dir ".\build\notes-tests" --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Notes tests failed." }

-S selects the source folder and -B selects a separate build folder. Configuration creates CTest's catalogue; the build creates the test executable. --output-on-failure prints diagnostics for a failing test. The three named tests should pass before you practise Stop.

3. Build and use the queued runner

The focused test project also builds umicom-ctest-job-example, a small application using the public job API. The project exercises result publication with real Framework tasks, CTest execution and record storage.

& $Cmake -S ".\applications\studio\tests\test_execution_bridge" `
    -B ".\build\test-run-checks" -G Ninja `
    -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe `
    -DCMAKE_MAKE_PROGRAM=C:/msys64/ucrt64/bin/ninja.exe `
    -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw "Test-run configuration failed." }

& $Cmake --build ".\build\test-run-checks" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Test-run build failed." }

& $CTest --test-dir ".\build\test-run-checks" `
    --parallel 2 --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Test-run checks failed." }

Run the Save test first. Then give the Index test a 100-millisecond Stop deadline:

$NotesBuild = (Resolve-Path -LiteralPath ".\build\notes-tests").Path
$Runner = ".\build\test-run-checks\framework-checks\umicom-ctest-job-example.exe"

& $Runner $NotesBuild "notes.save"
if ($LASTEXITCODE -ne 0) { throw "The selected Notes test failed." }

& $Runner $NotesBuild "notes.index" 100
if ($LASTEXITCODE -ne 2) { throw "The example did not report the expected cancellation." }

The first invocation should show one completed, passing test and return exit code 0. The second requests cancellation and returns 2. That exit code is expected for this exercise; it is not a passing test. Other failures return 1.

The supplied runner uses a monotonic clock, which measures elapsed time independently of wall-clock adjustments. Its polling loop sleeps briefly between reads so it does not continually occupy a CPU core.

4. Select the correct build directory

A test has two different locations: the build directory containing the CTest catalogue and the working directory selected for the test executable. Pass the build directory to the CTest adapter. CTest applies the executable's working-directory property itself.

When selecting an imported Test Platform item, call UmiTestPlatformCtestMakeRunRequest. It finds the item's own discovery record, checks the provider and build-root identity, and copies the test name, configuration and enabled state. This avoids using a different project's last-active configuration.

A build directory contains executable CMake test scripts. Use projects you trust. Creating a job does not grant permission to execute a project; the application must authorise the selected locations before submission.

5. Use the C API

Include umicom/testing/ctest_job.h and link your application target to Umicom::testing. The existing target brings in Framework's platform dependency. Use the Test Platform header as well when converting discovered metadata into a run request.

FunctionPurpose
UmiCtestJobCreateValidate every request and allocate the planned result storage before any test starts.
UmiCtestJobSubmitSubmit the created job once to an existing task queue.
UmiCtestJobGetSnapshotCopy current task state, active-test identity and completed outcome counts.
UmiCtestJobResultAtCopy a fully recorded attempt. An unfinished index returns UMI_STATUS_NOT_FOUND.
UmiCtestJobCancelRequest cancellation of the active CTest invocation and prevent later attempts.
UmiCtestJobDestroyRelease a created or terminal job. UMI_STATUS_BUSY leaves an active job intact.

A request contains an identifier, literal CTest name, build directory, configuration, optional invocation deadline and enabled flag. Names are matched literally, so punctuation such as notes.save[1]+ is not treated as a regular-expression instruction.

repeat_count sets the number of passes through the selection; zero means one pass. stop_on_failure stops after a failed, timed-out or not-run attempt or a process/report error. A legitimate skipped result does not stop the selection.

Complete runner source

This is the source of the executable used above:

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/testing/queued_ctest.c
 * PURPOSE: Run one chosen CTest test on the shared Framework task queue.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/
#include "umicom/testing/ctest_job.h"
#include "umicom/platform/threading.h"
#include "umicom/platform/clock.h"
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(int argc, char **argv)
{
    if (argc < 3 || argc > 4) {
        (void)fprintf(stderr, "Usage: umicom-ctest-job-example BUILD_DIRECTORY TEST_NAME [STOP_AFTER_MS]\n");
        return 1;
    }
    uint32_t stopAfter = 0U;
    if (argc == 4) {
        char *end = NULL; errno = 0;
        unsigned long value = strtoul(argv[3], &end, 10);
        if (errno != 0 || (argv[3][0] == '\0' || argv[3][0] == '-') || *end != '\0' || value > UINT32_MAX)
            return 1;
        stopAfter = (uint32_t)value;
    }
    UmiCtestJobRequest request = {0};
    if (strlen(argv[1]) >= sizeof(request.build_directory) || strlen(argv[2]) >= sizeof(request.name))
        return 1;
    (void)snprintf(request.build_directory, sizeof(request.build_directory), "%s", argv[1]);
    (void)snprintf(request.name, sizeof(request.name), "%s", argv[2]);
    (void)snprintf(request.test_id, sizeof(request.test_id), "notes.selected");
    (void)snprintf(request.configuration, sizeof(request.configuration), "Debug");
    request.enabled = 1;
    UmiCtestJob *job = NULL;
    UmiTaskQueue *queue = NULL;
    UmiTaskQueueConfig config = {0}; config.worker_count = 1U; config.capacity = 4U;
    UmiStatus status = UmiCtestJobCreate(&request, 1U, NULL, &job);
    if (status == UMI_STATUS_OK) status = umi_task_queue_create(&config, &queue);
    if (status == UMI_STATUS_OK) status = UmiCtestJobSubmit(job, queue);
    UmiClock clock = umi_clock_system();
    uint64_t started = clock.monotonic_nanoseconds(&clock);
    int stopRequested = 0;
    UmiCtestJobSnapshot snapshot = {0};
    while (status == UMI_STATUS_OK) {
        status = UmiCtestJobGetSnapshot(job, &snapshot);
        if (status != UMI_STATUS_OK || snapshot.state >= UMI_TASK_SUCCEEDED) break;
        if (stopAfter != 0U && !stopRequested &&
            (clock.monotonic_nanoseconds(&clock) - started) / UINT64_C(1000000) >= stopAfter) {
            status = UmiCtestJobCancel(job); stopRequested = 1;
        }
        umi_thread_sleep_ms(10U);
    }
    int exitCode = 1;
    if (status == UMI_STATUS_OK) {
        (void)printf("Completed %zu/%zu: %zu passed, %zu failed, %zu skipped, %zu cancelled.\n",
            snapshot.completed, snapshot.planned, snapshot.passed, snapshot.failed,
            snapshot.skipped, snapshot.cancelled);
        UmiTestResult result;
        if (UmiCtestJobResultAt(job, 0U, &result, NULL) == UMI_STATUS_OK)
            (void)printf("%s\n", result.output);
        exitCode = snapshot.status == UMI_STATUS_OK ? 0 : snapshot.status == UMI_STATUS_CANCELLED ? 2 : 1;
    } else (void)fprintf(stderr, "Test run error: %d\n", (int)status);
    if (job != NULL) {
        (void)UmiCtestJobCancel(job);
        while (UmiCtestJobDestroy(job) == UMI_STATUS_BUSY) umi_thread_sleep_ms(1U);
    }
    umi_task_queue_destroy(queue);
    umi_clock_dispose(&clock);
    return exitCode;
}

6. Interpret results and Stop

planned is the number of requested attempts. completed is the number with recorded outcomes, including skipped, cancelled or not-run attempts. While an attempt is running, its identity appears separately. Once the job is terminal, planned - completed is the number of attempts that never started.

A passed result requires the existing adapter's process and fresh JUnit-report checks to succeed. Skipped and disabled tests are not passes. Completed results remain readable after cancellation, and Stop cannot rewrite an already terminal success as a cancellation.

Stop requests cancellation; it does not join the worker from the UI thread. Continue polling until the job reaches a terminal state, then destroy it. A test that starts independent services or child processes remains responsible for their cleanup; cancelling CTest is not a general system-wide process cleanup operation.

Adapter output is bounded and marks truncation. An application may show a smaller labelled tail while retaining the copied adapter result for inspection. Do not interpret a short display snippet as the complete original process log.

7. Ownership and capacity

Create, submit and destroy a job on its owning thread. Keep the job alive while another thread reads a snapshot or result. The queue must remain valid until its owner drains or shuts it down. A queue-full rejection leaves a created job available for a later submission attempt.

Requests are copied during creation, so the caller may release its original arrays immediately afterwards. Results remain in the job until destruction. The hard limit is 4,096 attempts, calculated as selected requests multiplied by repeat count. Storage is allocated before submission, and allocation failure does not start a partial selection.

Studio adds its own limits: selections contain up to 1,024 test identifiers, and result/output registries hold 4,096 records each. New runs must fit the available history space. Reduce the selection or repeat count, or use the clear-results and clear-output commands after reviewing the existing records.

8. Run the examples on Linux

Use a C23-capable compiler, CMake, Ninja and pthread support. From the Applications checkout:

cmake -S framework/examples/testing/notes_project -B build/notes-tests -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/notes-tests --parallel 2
ctest --test-dir build/notes-tests --no-tests=error --output-on-failure
cmake -S applications/studio/tests/test_execution_bridge -B build/test-run-checks -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/test-run-checks --parallel 2
ctest --test-dir build/test-run-checks --no-tests=error --output-on-failure
./build/test-run-checks/framework-checks/umicom-ctest-job-example "$(pwd)/build/notes-tests" notes.save

To inspect memory and concurrency separately, configure new build folders using UMICOM_CTEST_JOBS_SANITIZERS=ON for AddressSanitizer/UndefinedBehaviorSanitizer or UMICOM_CTEST_JOBS_THREAD_SANITIZER=ON for ThreadSanitizer. Do not combine the two modes in one build folder.
