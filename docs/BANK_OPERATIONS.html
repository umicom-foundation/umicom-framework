1. What this batch delivers

The shared operations engine is implemented in C23 inside Framework. Bank selects the capability and adds a launcher to its existing workstation. The existing manual funds review, product body, command handlers, layout services and startup code remain available; the new operations window is an additional consumer, not a replacement.

Operating boundary. This is a bounded, local banking simulation profile, not a live banking service. It supports up to 64 records per business catalogue and 256 accepted command events per book. Capacity exhaustion returns an error; history is never discarded automatically. It has no real funding, payment network, card processor or authenticated user session.
CapabilityDelivered behaviour
Customers and accountsCreate customers; open currency-specific accounts; active, blocked and closed states; ownership and closure restrictions.
Balances and reservationsChecked integer minor-unit money, explicit currency scale, journal-derived booked balance, reservations and available balance. Different currencies use separate accounts; internal transfers require matching currency and scale.
Beneficiaries and transfersStored internal beneficiaries, submission-time reservation, distinct maker/checker approval, rejection, cancellation, approved execution and compensating reversal.
Cards and holdsExplicitly simulated cards, per-transaction limits, blocking, manual reservations, authorisation, one final capture, void and full captured refund.
EvidenceCanonical balanced journals, revision-range statements, copied audit records and reconciliation match/break evidence. Reconciliation never alters a balance to force a match.
PersistenceEvent and revision updates through one Data Server transaction; strict replay, idempotent retries, failure-atomic reload and stale-writer detection.
PresentationFramework GTK4 command form and seven read-only projection tabs, selected through a new Bank launcher. The adapter source is delivered but has not been compiled or exercised in the delivery environment.

The command-line example runs entirely in memory. The graphical operations window deliberately selects SQLite, shows its database path and reports failure rather than silently switching to volatile storage.

3. Ownership, persistence and financial controls

Composition and authority

Bank’s composition entry points delegate to Umicom::bank_operations. This optional Framework library links the existing Umicom::finance and Umicom::data targets; it does not build private copies of them inside Bank. Bank selects the capability through the Framework CMake helper. Framework-only consumers can select the same helper after creating the canonical targets, or link the exported capability when it has been installed.

The GTK Slave Controller owns widgets, input conversion and copied projections. The operations service owns customer/account records and workflow state. Its private Data Server owns persistence. The public API exposes an opaque handle and copy-out queries; neither Bank nor GTK receives raw SQL access or mutable pointers into the operations book.

One accepted command, one durable event

Execution checks the caller’s capabilities and the command, copies current state to a private candidate, validates the requested state transition and builds any resulting journal. The service begins a Data Server transaction, verifies the persisted revision, writes the encoded event and next revision, and commits. Only a successful commit publishes the candidate as current memory state. Failed writes or commits trigger rollback. A failed rollback poisons the handle so subsequent queries and commands cannot pretend it is healthy; close and reopen after investigating the store.

Each handle must be called through one serial queue. This is not an unrestricted concurrent handle. Separate SQLite handles detect a stale revision inside the transaction and return UMI_STATUS_BUSY; the caller must reload, review and deliberately retry. The GTK adapter uses the main thread and bounded synchronous operations.

Representation and restart

Money uses UmiMoney with integer minor units, currency and scale. The Bank journal adds a currency/scale wrapper to the existing canonical UmiAccountingJournalEntry, whose lines carry debit and credit minor units. Accepted events use an explicit byte encoding rendered as hexadecimal text, rather than dumping C structures or their padding. Restart validates schema, sequence, fields, identities and every replayed transition. Missing, malformed and orphan events are rejected.

Retry, approval and reversal

A repeated request ID with the same actor identity and canonical payload returns its original receipt without repeating the financial effect. The expected revision is excluded from payload equality; business time and other command values are not. Conflicting reuse returns ALREADY_EXISTS. Capabilities are checked before returning an idempotent receipt. Submission reserves funds before approval, and a maker cannot approve or reject their own transfer. Reversal and refund append compensating journals and keep the originals.

Audit records are retained through this API, but are not cryptographically tamper-proof. A trusted administrator can still modify the SQLite database outside the service. Capabilities are supplied by trusted calling code, not by an authentication implementation in this batch. The three graphical test identities demonstrate policy separation; they are not a security boundary against someone controlling the local process.

4. Command field map

Every command needs an action, request ID, entity ID, business date, timestamp and expected revision. The GUI supplies request/time/revision values and lets the operator review the business date. Names are bounded; identifiers accept letters, digits, dot, hyphen and underscore and reserve the sys. prefix for internal accounts. Unused payload fields are rejected at the service boundary. Disabled GUI fields are not sent.

Additional failure and card checks

Prepare a new transfer exceeding available funds: it must fail without reserving anything. Attempt approval under Test maker: it must fail. Record a reconciliation with a different external balance: a break must appear while the ledger stays unchanged. The API regression suite separately tests an actor with both maker and approval capabilities to prove that identity separation is enforced independently of the GUI’s role split.

Issue a simulated card on bank12-current with a 10000-minor limit, authorise 5000 minor under Test operator, then capture 4000 minor using the same authorisation entity ID and a new request. The unused 1000 reservation is released. A full refund restores the captured 4000. Use new entity IDs for independent authorisations; a second capture of an already-captured authorisation is rejected. Nothing is submitted to a processor.

The database is under g_get_user_data_dir()/Umicom/Bank/bank-operations-simulation.sqlite; the window displays the resolved absolute path. The memory-only example never opens this file. Do not place simulation databases in the repository or commit them. This book is separate from the older manual review’s caller-supplied values; the batch does not invent or migrate financial records from those values.

9. Remaining engineering work

Batch 12 is not marked complete in the roadmap by this delivery. Further work includes full Windows/GTK qualification, operational reconciliation ingestion and break-resolution workflows, scalable repositories, larger event histories with governed retention, authenticated identity and revocation, production permissions, external beneficiary validation, payment-provider acknowledgement/repair/retry, real card-provider integration, multi-capture and partial-refund policies, governed FX conversions, migration and security controls, and deployment/backup/recovery qualification.

This batch provides API revision-range statements and a GTK statement grid, not a finished print/PDF/CSV statement publishing service. It provides internal transfers and simulated card clearing, not outbound payment rails. Its account model is deliberately bounded and separate from any pre-existing demonstration books; migration must be explicit. The event store is not encrypted or cryptographically signed by this module. Test-funding capability must not become production funding authority.

The tested result is the delivered C23 local operations capability and its focused integration closure. The pending result is the complete application’s behaviour on your Windows machine. Keep these two forms of evidence separate when recording acceptance.
