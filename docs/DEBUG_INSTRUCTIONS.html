Inspecting paused machine instructions

A debugger translates source code into a view of a running program. Disassembly shows the machine instructions that the processor executes. Framework provides bounded, read-only instruction pages for a selected paused stack frame. A stack frame represents one active function call.

Capture a frame, then request a page

  1. Connect a native debug adapter, pause the program and refresh its threads, stack and scopes with UmiDebugRuntimePlatformInspectStopped. The selected Framework workspace must belong to the same debug service.
  2. Call UmiDebugInstructionTargetCapture with that workspace. Framework requests the selected frame's instruction reference using its stack position. The adapter must advertise supportsDisassembleRequest and return an instructionPointerReference.
  3. Allocate a UmiDebugInstructionPage on the heap. Call UmiDebugInstructionPageRead with the captured target, independent byte and instruction offsets, and a count from 1 to 64.
  4. Display the copied rows as text. A row marked invalid represents an unavailable instruction. Keep that row visible so the requested page retains its positions.
  5. Destroy the target with UmiDebugInstructionTargetDestroy when replacing the capture or closing the view. Free the page separately.

Offsets and locations

The byte offset moves relative to the captured reference; the instruction offset then moves by instructions. Instruction sizes vary between architectures, so do not multiply an instruction offset by a guessed size. Signed offsets are bounded to the exact integer range used by the Debug Adapter Protocol. UmiDebugInstructionOffsetRead accepts decimal text and an optional leading minus sign.

Addresses remain decimal or hexadecimal strings, including addresses wider than the host pointer size. Source locations are descriptive metadata. A location omitted on a later row inherits the previous row's location within that page; line and column fields remain independently optional. Source paths are not opened, and symbols and instruction text are not evaluated.

Lifetime and error handling

ResultWhat to do
NOT_IMPLEMENTEDThe adapter did not advertise disassembly. Use its supported source-level tools.
NOT_FOUNDThe connection or selected frame has no usable reference. Pause and refresh the stack before capturing again.
BUSYPublish pending debugger events through the normal event pump, then explicitly refresh the capture. Events are left queued for the owner.
INVALID_STATEThe connection, paused revision, selected frame or workspace changed. Capture the current frame again.
PARSE_ERROR or CAPACITY_EXCEEDEDThe adapter reply is malformed, incomplete or too large. The previous output value remains unchanged; show the failure instead of labelling it as a fresh result.
TIMEOUT or UNAVAILABLEThe adapter did not reply in time or rejected the request. Inspection does not retry automatically.

Calls run on the native debugger owner's thread. Supply a finite timeout and serialize access to that owner. A successful response must contain exactly the requested number of rows, with unavailable rows represented by the adapter's filler entries. Captures stay readable after closure, but they cannot authorize a new request against a later connection.

Adding a frontend

UmiGtk4DebugInstructionsCreate accepts capture and page callbacks. A frontend binds those callbacks to its existing workspace and permission checks. The GTK panel clears old rows when request settings change and rejects callback results if settings change again or the panel closes. It owns the callback context only after successful creation. No source files, breakpoints, registers, memory or execution state are changed by the view.

The legacy umi_debug_runtime_decode_disassembly entry point shares field validation and preserves its existing bounded result type. Line or column values outside that type's range are rejected instead of truncated. Invalid presentation hints are retained so an unavailable row cannot be offered as a breakpoint location.

Protocol reference: Debug Adapter Protocol specification.

Continue, step and pause

Continuing or stepping retires the previous frame, scope and variable captures before the request is sent. A lost reply cannot make old instruction references current again. Wait for a fresh stop, select its frame and refresh the instruction view. If a control request fails and no new stop arrives, end the debugging session and reconnect before inspecting again.

A Pause acknowledgement means the adapter accepted the request; Studio waits for the stop event before offering paused inspection. Retained text describes an earlier capture until you refresh it.
