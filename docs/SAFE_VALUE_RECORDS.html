Constructing and reading values safely

A value record stores a small description, such as a component identity or a language-service observation. It does not own a window, file handle or background task. This distinction lets Framework prepare a complete replacement before publishing it, without accidentally giving two objects ownership of one resource.

Construct a record and handle refusal

  1. Include the public header for your record. Use its _init_checked function when the identity comes from input that may be empty or too long. These functions are available for SDK runtime, test runtime, desktop control and the supported language-intelligence value records.
  2. Check the returned status. INVALID_ARGUMENT rejects a missing or empty identity. CAPACITY_EXCEEDED rejects an identity that does not fit, including its terminating zero byte.
  3. Use the record only after UMI_STATUS_OK. On refusal, the destination retains its previous bytes. On success, it receives the existing initializer's defaults, including its initial revision.
UmiSdkRuntimeComponent component;
UmiStatus status = umi_sdk_runtime_component_init_checked(&component, "notes.application");
if (status != UMI_STATUS_OK) {
    /* Report the input problem; do not use an uninitialized component. */
    return status;
}

Construction starts a new value. It is not a way to edit an identity that other observers are using: initialization resets the fields and revision. Use setters or an available reviewed-replacement API for live edits. The original void initializers remain available for compatibility; they cannot report identity errors.

Edit without losing an accepted field

The covered text setters publish the complete text and its revision together. An oversized replacement does not clear the previous field. Text can come from the field itself, including a suffix. A full revision counter causes refusal before mutation; it never wraps around to make an old observation look current. Scalar setters with a status result follow the same refusal rule. Callers still serialize access on the owning thread.

Fixed text arrays in a record need a terminator inside that member. A zero byte in the next field is not a valid terminator for the first field. Validators reject malformed arrays before domain helpers inspect them. Identity comparison also refuses unterminated identities. These checks do not establish UTF-8 validity, filesystem access, permissions or evidence that a described operation really happened.

Read a registry in small pages

A registry owns an ordered collection of accepted snapshots. A revision is its change counter. Keep one revision while reading every page so that rows from different collection states cannot silently mix.

  1. Read the owner's revision and start with offset zero.
  2. Provide an output array and call the typed _registry_read_page function with that revision.
  3. On success, consume exactly page.copied entries. Continue at page.next_offset while page.has_more is true.
  4. If the function returns INVALID_STATE, discard the partial collection and obtain a new revision. Do not resume halfway through using the newer token. For an atomic user-facing result, stage all accepted pages in your own buffer before publishing the completed collection.
uint64_t revision = umi_platform_bookmarks_registry_revision(registry);
UmiBookmarkSnapshot items[16];
UmiSnapshotPage page;
UmiStatus status = umi_platform_bookmarks_registry_read_page(
    registry, revision, 0, items, 16, &page);

Offset equal to the row count returns an empty final page. Offset beyond the count is invalid. Capacity zero allows a null item array and returns metadata without advancing; do not use that query in a loop expecting progress. On any refusal, both outputs retain their previous bytes, so check status before reading them. Output storage must not overlap the registry or the page report. Pagination allocates nothing and performs no I/O.

Build the installed SDK lesson

The complete C23 example constructs SDK and test records, refuses an invalid identity, reads three bookmarks in two pages, and detects a stale observation.

  1. Install Framework into a prefix such as C:/umicom-sdk, including the platform, SDK runtime and test runtime libraries.
  2. Copy the installed share/umicom-framework/examples/snapshot_contracts directory to your own working folder.
  3. From that folder, configure, build and run the lesson with your installed toolchain:
cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH=C:/umicom-sdk -DBUILD_TESTING=ON
cmake --build build --target umicom-safe-values-lesson
ctest --test-dir build -R "^safe-values-lesson$" --output-on-failure

A successful run prints three bookmark identities and Checked construction and consistent page reads completed. If CMake cannot find UmicomFramework, check the installation prefix. A missing symbol usually means the linked library and public headers were installed from different source states: rebuild and reinstall the same Framework checkout together. A failed status check prints a failing test or nonzero process exit; do not treat it as success.

Extend a record or registry

Keep reusable ownership rules in Framework. When adding a field, extend its validator and its member-level regression comparison. Add fixed text members to bounded validation. Do not apply the value-copy helpers to structs that own pointers, resources or callbacks. A registry's page function preserves its existing insertion order and normalization; it does not sort, persist, lock, or refresh external data.

See reviewed state updates for publishing a prepared edit after checking that the live revision still matches.
