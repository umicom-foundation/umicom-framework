Report native application failures

A failed constructor should tell you which operation failed. Framework provides a small logging helper that records a public operation name and the original status. It uses the existing diagnostic sink: the callback that receives a message for a console, a log or the Problems view.

1. Connect a diagnostic sink

The following sink writes messages to standard error. A host with a diagnostic pipeline can use umi_diagnostic_pipeline_sink and pass its pipeline as the logger's user data instead. The callback must copy text if it needs to retain it after returning.

#include "umicom/diagnostics/log.h"
#include <stdio.h>

static void report(const UmiDiagnostic *event, void *data)
{
    (void)data;
    fprintf(stderr, "[%s] %s\n", event->source, event->message);
}

UmiLogger logger = {report, NULL, "application-startup"};

2. Report the failed operation

Call the helper with the status returned by the operation. Successful operations produce no message. Continue to return the original failure and release partially created resources through their normal owners.

umi_log_status(&logger, "adapter.prepare", status, correlation_id);

For UMI_STATUS_INVALID_STATE, the message is:

Operation adapter.prepare failed: Invalid state (2).

Use fixed names from your source code. An operation name accepts up to 96 ASCII letters, digits, dots, hyphens or underscores. Invalid names become unspecified-operation. Do not supply paths, account names, credentials or document content. This validation is not a general secret detector. The helper formats its message without heap allocation; the receiving sink can have its own allocation and retention policies.

3. Keep native toolkit messages visible

The built-in runtime parser recognizes warning and critical markers from Gtk, Gdk, Gsk, GLib, GLib-GObject and GLib-GIO. Applications that feed process output into the default diagnostic pipeline receive these messages in its diagnostic model.

  • A warning marker becomes a warning with code native-toolkit-warning.
  • A critical marker becomes an error with code native-toolkit-critical. It does not prove that the process terminated.
  • The original source, message and correlation identifier remain available for the host to display.

Keep collecting the process exit status separately. Recognizing a message does not fix its cause, suppress it or change whether a test succeeds.

4. Investigate a Studio startup failure

  1. Launch Studio from a terminal and retain standard error with the rest of the process log.
  2. Find the first [Studio startup] message. It identifies the failed operation, such as window.titlebar or bootstrap.create.
  3. Read the following higher-level messages as context for that same failure. For example, a bootstrap failure can also prevent runtime attachment and workbench creation.
  4. Inspect the named operation and its status before changing unrelated application settings. Rebuild the changed libraries and the application before repeating the same workflow.

These diagnostics describe initialization failures. They do not certify a completed build, successful tests, working broker connections or a release-ready application.
