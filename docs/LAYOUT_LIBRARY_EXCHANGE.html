Portable layout libraries

A layout library contains your named panel arrangements, their order and the active selection. Export it to keep a separate copy or move it between compatible workspaces in the same product.

Export your layouts

  1. Finish or cancel any layout editing, then open Layout Library.
  2. Choose Export layouts… and select a destination. The suggested file name is workspace-layouts.umicom-layouts.
  3. Wait for the export confirmation. Export leaves your current workspace and its saved library unchanged.

Review and import

  1. Open Layout Library and choose Review layout file….
  2. Select the file. Read the proposed names, panel counts, active layout and change totals. Nothing changes during review.
  3. If the list is correct, select Replace my named layouts with this reviewed library, then choose Apply reviewed layouts.
  4. Check the restored arrangement. Use Save library separately if you want the imported list to survive restart. The library notice states whether persistent storage is available.
The import replaces the complete named list. Export your current library first if you want to keep it. Layout files do not contain document drafts, account state, orders or general application settings.

What the review guarantees

The review owns a copy of the selected file's content. Changing that file afterwards cannot change what Apply uses. If the workspace changes after review, Apply refuses the old review; select the file again and review it against the current workspace.

The summary compares names, order, panel counts, locking and active selection. Panel geometry is included in the file but is not displayed as a visual difference. Imported tools and context links must already be available in the receiving workspace.

When an import is refused

  • Layout editing is active: finish or cancel editing and try again.
  • The workspace changed: review the file again before applying it.
  • The file is incompatible or damaged: keep the original and export a fresh copy from the same product. Do not manually remove validation fields.
  • The file is too large: the archive must be smaller than 450 KiB plus its internal terminating byte. Ordinary exports enforce this limit.
  • Saving is unavailable: the imported list can be used in the current session. Check the existing library storage notice before relying on restart recovery.

Undo an import or library edit

Layout Library keeps the last eight successful library changes in memory. This includes renaming, copying, removing, ordering and opening named layouts, applying an imported library, and using Restore library. Each entry keeps the arrangements before and after that change.

  1. Open Layout Library after making a change.
  2. Choose Undo layout change. The previous named list and active arrangement return.
  3. Choose Redo layout change if you want the arrangement you just undid.
  4. Check the result, then choose Save library if it should survive restart. Undo and Redo do not write the saved library.

Making a new library change after Undo replaces the redo branch. For example, undoing an import and then renaming a layout starts a new path from the restored list. The discarded branch is no longer available through Redo.

Understand history limits

  • Session lifetime: history is cleared when the workstation closes. Keep an exported file for a separate copy that survives restart.
  • Eight changes: accepting a ninth change drops the oldest entry. The remaining entries can still be undone in order.
  • Changes outside Layout Library: panel editing and other workspace commands may invalidate the history. The controls then disable instead of overwriting newer work. A successful new library action begins a fresh history from the current arrangement.
  • Active layout editing: finish or cancel editing before using history.
  • A refused restoration: the owner validates the archived tools and layout again. If it cannot accept the arrangement, the history position stays unchanged. Review the reported error; do not assume that the layout changed.

Layout history does not undo typing, restore document drafts, place or cancel orders, post bank transactions, or save account state. Use each product's existing document or business workflow for those operations.

Extend a native workspace safely

The shared workspace_library_history.h interface owns the recovery archives. A product keeps its current workspace model and supplies a publication callback; this callback accepts native widgets before changing that model.

  1. Create one history object for each workspace owner. Keep all its calls on the same thread.
  2. Build a proposed model using the existing library commands. Pass the current and proposed models to umi_ui_workspace_library_history_record. The service validates and allocates both archives before calling the publisher.
  3. In the publisher, keep the current model if native layout creation fails. Return the actual failure. On success publish the candidate without retaining its borrowed pointer.
  4. Read the copied history state for controls. Pass the revision shown to the user when calling umi_ui_workspace_library_history_navigate. A newer model causes refusal rather than an automatic retry.
  5. Destroy the history after callbacks finish and before releasing its workspace owner. Do not destroy it from the publication callback.

The shared GTK layout-library controller accepts history read and apply callbacks. It copies the request before idle dispatch, cancels queued work on destruction, and disconnects retained widgets. The Studio, trading-suite and generic product workstations provide examples of this integration.
