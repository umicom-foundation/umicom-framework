Qualify an installed Umicom Framework SDK

An SDK is the headers, libraries and build configuration that another application consumes. A successful build inside the Framework repository does not by itself show that an installed SDK is complete. This exercise builds existing Notes and workspace-import examples against a single installation, with no source-library fallback.

Prepare a complete installation

  1. Configure and build Framework or its Applications host using the supported preset for your compiler. Keep the compiler, architecture and configuration consistent between the SDK and its consumer.
  2. Install the completed build to a new, explicitly selected prefix. Use a full installation for this exercise. The current Framework install component alone does not include every archive, header and package file registered by the broader build.
  3. Keep logs outside the source repository. For example, after a successful Applications build, PowerShell can record installation with:
    cmake --install "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug" --config Debug --prefix "C:\umicom\installed\sdk-qualification" 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-install.log"
    Choose a fresh prefix and ensure the private log folder already exists. Stop if installation reports an error.

Build the independent consumers

The installed qualification project uses only its selected SDK. It checks imported component paths and the complete public-header fingerprint recorded when the SDK was configured. It then compiles the installed public examples; no implementation source is taken from the Framework checkout.

  1. Configure in a separate build folder. Keep your compiler tools and any external SDK dependencies available in the shell:
    cmake -S "C:\umicom\installed\sdk-qualification\share\umicom-framework\examples\sdk_qualification" -B "C:\umicom\_local\sdk-consumer-build" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DUMICOM_SDK_ROOT="C:\umicom\installed\sdk-qualification" -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_PREFIX_PATH="C:/msys64/ucrt64" -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-consumer-configure.log"
  2. Build the consumer:
    cmake --build "C:\umicom\_local\sdk-consumer-build" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-consumer-build.log"
  3. Run its two registered exercises:
    ctest --test-dir "C:\umicom\_local\sdk-consumer-build" --output-on-failure --no-tests=error 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-consumer-tests.log"

Run each step separately and stop at an error: PowerShell continues after a failed native command unless you stop it. For a multi-configuration generator, also pass --config Debug to the build and -C Debug to CTest. On Linux, choose Linux paths and your C23 compiler instead of the Windows compiler path.

What the exercises check

  • sdk.notes.edit_history_save edits the intended document while another draft remains active, checks Undo and Redo, explicitly saves, then reads back the saved content. The established Framework services own the documents and history. The exercise creates its own temporary directory and removes only its own fixture afterwards.
  • sdk.workspace.scratch_ownership decodes a bookmark using caller-owned temporary storage, reuses that storage and refuses damaged input without replacing the accepted result.

You can launch either executable directly from the consumer build folder to see its messages. These are headless acceptance exercises. They do not demonstrate that a graphical editor, installer upgrade, broker connection or every product feature has passed.

Diagnose a rejected SDK

  • Wrong prefix: use a fresh consumer build directory. An older CMake cache can still refer to another installation through UmicomFramework_DIR.
  • Missing component or archive: finish the owner build and install its complete matching configuration. A partial install is not a complete SDK.
  • Header identity mismatch: install the matching headers and libraries together into a fresh prefix. Extra headers left from an older SDK also change the identity. Do not copy individual headers into an older installation.
  • Missing external dependency: provide the dependencies used by this SDK build through their supported package paths. The strict check covers the selected Framework components; it does not bundle or authenticate third-party packages.
  • Compiler or linker error: retain the log. Do not substitute source-tree libraries or disable diagnostics to make the acceptance result appear successful.

Use the same check in another application

find_package(UmicomFramework CONFIG REQUIRED COMPONENTS platform document)
umicom_require_installed_sdk("C:/UmicomSDK" Umicom::platform Umicom::document)
target_link_libraries(my_notes PRIVATE Umicom::document)

This opt-in configure-time check validates the requested component targets and public-header identity. It is not a cryptographic signature, a whole-installation binary digest or a runtime test. Run the consumer after a successful configure and build.

Framework's assertion-based legacy fixtures also include a test-only policy that keeps their setup and checks active in Release builds. Production libraries retain their chosen build flags. New tests should use explicit setup and cleanup so failure handling remains clear.
