Publish retained diagnostic pages

A native list can run application callbacks while it removes or inserts a row. Those callbacks may close the window, replace its filters or change the diagnostic model. Use an owned page to keep displayed records stable while checking whether they still belong to the current view.

  1. Link Umicom::diagnostic_ui and include umicom/diagnostic_ui/page.h. Keep the model alive during capture and validation.
  2. Initialize a UmiDiagnosticQuery. Set its filters, order and offset. A page accepts up to 300 rows; a zero limit requests 300. The normal query initializer requests 64 until you change it.
  3. Call UmiDiagnosticPageCreate. On success, read the summary and borrowed immutable rows. On failure, the output pointer is unchanged. Free the page exactly once when its last consumer finishes.
  4. Before and after a native callback, resolve the window's lifetime and compare the captured page with the current model and query. A non-OK validation result means the page cannot authorize actions. Schedule a fresh capture instead of continuing a partial publication.
  5. Track a separate host generation for filter edits. An edit away from and back to the same text still cancels work associated with the previous user intent. A page validates current values, not the history of edits.
UmiDiagnosticPage *page = NULL;
UmiDiagnosticQuery query;
umi_diagnostic_query_init(&query);
query.sort = UMI_DIAGNOSTIC_SORT_SEQUENCE_DESCENDING;
query.limit = UMI_DIAGNOSTIC_PAGE_LIMIT;
UmiStatus status = UmiDiagnosticPageCreate(model, &query, &page);
if (status == UMI_STATUS_OK) {
    UmiDiagnosticPageSummary summary;
    (void)UmiDiagnosticPageReadSummary(page, &summary);
    /* Prepare owned native rows before publishing them. */
    for (size_t i = 0; i < summary.count; ++i) {
        const UmiDiagnosticSnapshot *item = UmiDiagnosticPageItem(page, i);
        /* Copy the fields required by your presentation. */
        (void)item;
    }
}
UmiDiagnosticPageDestroy(page);

Counts and recovery

The matching count follows the query. Active, resolved and severity totals describe the whole model; severity totals exclude resolved records. has_more reports additional matches after the captured rows. To read the next page, increase the offset by the number of returned rows and capture again. A changing model can change page boundaries.

Malformed bounded filter strings and unknown sort values return INVALID_ARGUMENT. A limit above 300 returns CAPACITY_EXCEEDED. Allocation failure returns OUT_OF_MEMORY. Model changes during capture can cancel the read; do not treat a partial read as a completed page. No retry loop is performed internally.

For GTK4, UmiGtk4ListBoxPublish checks a caller-supplied current-state callback around row changes. Retain its input widgets and invalidate old row actions first. Cancellation may leave a partial list, so only enable actions after the whole page and its host checks succeed. This is not a thread lock, a source-file permission check or proof that the underlying build passed.

Previous and next page controls

For a paged user interface, include umicom/diagnostic_ui/page_navigation.h and use UmiDiagnosticPageCreateWindow. This wrapper aligns the requested offset to a page boundary and moves an obsolete offset to the last available page after results shrink. It uses at most two captures. The original UmiDiagnosticPageCreate still accepts arbitrary offsets.

  1. Set the page size in query.limit, then pass the model and query to the window capture service. A zero limit requests 300 rows. Neither output changes on failure.
  2. Display navigation.page_index + 1 and navigation.page_count only when the count is nonzero. An empty result has zero pages and offset zero.
  3. Enable Previous and Next using has_previous and has_next. Copy the corresponding offset into the next query. Reset the offset to zero when the user changes a filter or sort.
  4. Use the returned navigation.query for validation: the caller's original offset may have been rounded or clamped. Keep checking the host lifetime and query generation around native notifications.
  5. If a click refers to stale evidence, refresh first and require a new click. A page number is a view position, not a persistent diagnostic identity.
UmiDiagnosticPage *page = NULL;
UmiDiagnosticPageNavigation navigation;
UmiStatus status = UmiDiagnosticPageCreateWindow(model, &query, &page, &navigation);

Producer text and display text

Every inline diagnostic text field must contain a NUL character within its declared capacity. The model rejects records that fail this contract before storing them. Text encoding is a separate concern: a native presenter may replace invalid display bytes with a visible replacement character, while retaining the original message, identifier and source path in the diagnostic snapshot. Repaired display text must not become a source-file identity.
