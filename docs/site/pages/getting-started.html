Umicom Framework & Applications

Start developing with Umicom

From a clean checkout to your first Framework example.

Choose a starting point

To use an application, begin with its user guide. To build with Framework, keep the complete Applications checkout available: its submodules contain Framework and the product repositories. A GitHub source archive for the parent alone does not include the contents of those separate repositories.

1. Get the source

Git is the version-control tool. GitHub hosts a remote copy. Open a terminal in the directory that should contain your checkout and use a new, empty destination.

Windows PowerShell

Set-Location "C:\umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
Set-Location ".\Umicom-Applications"
git status

Linux shell

mkdir -p "$HOME/umicom"
cd "$HOME/umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
cd Umicom-Applications
git status

Run one line at a time and stop on an error. If the destination already contains your work, update that checkout instead of cloning over it. Use GitHub's supported authentication; never place a token in these URLs or in a public guide.

2. Select the development branches before editing

Submodules may initially be detached at the exact commits recorded by the parent. For a reproducible build of that snapshot, leave those commits selected. For the project's main-only development workflow, first inspect each clean repository and check that its current work is included in its remote main branch.

git status
git fetch origin
git --no-pager log --oneline origin/main..HEAD
git submodule foreach --recursive 'git status --short --branch'
git submodule foreach --recursive 'git fetch origin'
git submodule foreach --recursive 'git --no-pager log --oneline origin/main..HEAD'

Continue only when there are no uncommitted changes and the log commands print no commits (the submodule headings are normal). Output containing commits needs review before switching. Then:

git switch main
git submodule foreach --recursive 'git switch main'
git merge --ff-only origin/main
git submodule foreach --recursive 'git merge --ff-only origin/main'
git branch --show-current
git submodule foreach --recursive 'git branch --show-current'

Each branch check should print main. Stop if a branch is missing or a fast-forward fails; do not force a switch or reset. Selecting newer child branches changes the parent's recorded source combination. Build and review that combination before updating its lock. A Git setting cannot prevent a later command from detaching HEAD, so repeat this check before each development session.

3. Build the development environment

The maintained build and publication guide explains dependencies, Windows and Linux presets, tests, installation into a separate directory and Git publication. Follow that guide before compiling the examples. Installing a Framework SDK gives an independent project headers, libraries and CMake package information.

4. Read and run one example

Start with the compiler-message reader. It is small enough to inspect in one file but solves a real IDE task. Then use working copies to understand text ownership and Undo. Finally, follow the Notes window to connect the same document operations to buttons, menus and panels.

For each example, predict its output, run it, make one controlled change and check the result. A successful compilation proves the compiler accepted the program; its test and actual behaviour tell you whether it does what you intended.

5. Find the next component

Search the source map for a feature name such as document, build or component. Open the public header first, identify its types and ownership rules, then follow the implementation and tests. Do not include a private source file directly in an application to avoid learning its library boundary.
