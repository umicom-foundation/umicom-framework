Build an application using shared services

An SDK, or software development kit, is the set of files another program needs to use a library. A library is reusable compiled code. A header tells the C compiler which names and types the library exposes. CMake package files tell the build tools where those files are and which other libraries they require.

A source archive is not an installed SDK. An empty installation folder, or a failed installation, cannot satisfy find_package. A selected-component installation only includes the components selected for that build.

1. Prepare a compatible installation

Use a completed Framework or Applications build made with the same compiler family, architecture and runtime as the program you are about to compile. The example below uses the Windows UCRT64 toolchain. Keep its compiler and libraries together. If you already have a working SDK, use its actual prefix and continue to step 2.

First follow the build guide. After its configure, build and tests succeed, install that build into a dedicated directory. These commands assume the Applications build named below exists and completed successfully.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --install ".\build\windows-ucrt64-all-debug" --prefix "C:\umicom\installed\applications"

Expected result: CMake reports installed or up-to-date headers, libraries and package configuration. Stop if it reports a missing executable, access failure or another error. A partial installation does not establish that the package is usable. Never install over source directories.

2. Start with the real diagnostic reader

A consumer is a program that uses the installed SDK. This example takes a compiler message and extracts the file, line and column, the same kind of information Studio needs for its Problems view. It is a command-line program, so no native window is required.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S ".\framework\examples\build_diagnostics" -B ".\build\sdk-diagnostics" -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_PREFIX_PATH=C:/umicom/installed/applications
cmake --build ".\build\sdk-diagnostics" --parallel 2
ctest --test-dir ".\build\sdk-diagnostics" --output-on-failure --no-tests=error
& ".\build\sdk-diagnostics\umicom-notes-diagnostics.exe"

Run one command at a time. Stop on failure before moving to the next stage. The separate build directory keeps generated files away from source. The program should print:

Source: C:/Umicom Notes/src/main.c
Line: 8
Column: 5
Message: expected ';' before return

The compiler message is sample input. It is not evidence that the example itself failed to compile. The test checks that the parser extracted the intended location.

3. Understand the connection

The example's CMakeLists.txt requests find_package(UmicomFramework CONFIG REQUIRED) and links Umicom::build. An imported target carries the include paths and dependency relationships. Avoid manually collecting individual library files: that loses those relationships and makes installation changes harder to follow.

Read the complete source walkthrough, then Introduction to CMake. For an interface found in another guide, use the source map and that component's own installed example. Target names and package components are related but not interchangeable names.

Recover from common setup errors

Could not find UmicomFrameworkConfig.cmake
The prefix must identify a successful installation. Check the installation log and the lib/cmake/UmicomFramework directory. Changing the compiler does not create a missing SDK.
Imported target or library is missing
Confirm the installation contains the example's required component and its dependencies. Complete the selected component build and installation; do not edit generated package files to hide the error.
The executable cannot load a DLL
Use the matching toolchain runtime and the documented installed runtime arrangement. A successful link does not prove every runtime library is available. Keep the failing filename in your report.
Compiler changed in an existing build directory
Configure a new build directory. Do not reuse one made for a different compiler, architecture or workspace.
A security product quarantined an executable
Keep the detection name, exact file hash and build identity. Investigate the detected file and report a suspected false positive to the security vendor. Do not disable protection or exclude the whole source tree merely to make tests appear successful.

Installation success, example tests and native application testing are separate evidence. This guide describes how to check them; it does not certify every component or product for production use.
