Umicom Framework & Applications

Build and publish the documentation

Use one shared site build while keeping product content beside its source.

Build the website without building the applications

The documentation project uses CMake to assemble the shared pages, the selected application pages and a public-header catalogue. It does not start an application, create a payment or execute a project build. Run these commands from the complete Applications checkout after merging the documentation sources.

Windows PowerShell

Set-Location "C:\umicom\Umicom-Applications"
& "C:\msys64\ucrt64\bin\cmake.exe" -S framework/docs/site -B build/documentation -G Ninja -DCMAKE_MAKE_PROGRAM="C:/msys64/ucrt64/bin/ninja.exe"
& "C:\msys64\ucrt64\bin\cmake.exe" --build build/documentation --target umicom-website
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir build/documentation --no-tests=error --output-on-failure
Start-Process ".\build\documentation\site\index.html"

Linux shell

cd "$HOME/umicom/Umicom-Applications"
cmake -S framework/docs/site -B build/documentation -G Ninja
cmake --build build/documentation --target umicom-website
ctest --test-dir build/documentation --no-tests=error --output-on-failure
xdg-open build/documentation/site/index.html

Use one line at a time and stop on an error. The site can be opened from disk; its small search filter reads only the page and sends no search text to a server.

Add the full API reference

The existing project uses Doxygen. Install it through the supported package manager. On Windows, open the MSYS2 UCRT64 terminal and run:

pacman -S --needed mingw-w64-ucrt-x86_64-doxygen

Return to PowerShell, add C:\msys64\ucrt64\bin to the session PATH as in the build guide, and repeat the documentation configure command. On Debian or Ubuntu, the package is installed with sudo apt install doxygen; other Linux distributions have their own package commands. Check doxygen --version, reconfigure the documentation project, then run:

cmake --build build/documentation --target umicom-website-api

This processes the public headers and implementation roots selected by the site project, including the real build-service source. It does not publish all repository documents automatically. The generated pages appear at build/documentation/site/reference/html/index.html. Review its warnings and coverage; extraction does not prove that each function has adequate ownership or usage documentation.

Package a local copy

cmake --build build/documentation --target umicom-website-package

The resulting build/documentation/umicom-website.zip contains a site folder. Extract it elsewhere and open its index.html. Build the API target first when the archive should contain the generated reference. Check the packaged result, not just the source pages.

Publish deliberately

Upload the contents of the generated site folder to a selected static web host. The relative links support a repository subpath as well as a domain root. A custom domain, DNS changes, GitHub Pages configuration and public deployment are separate decisions; creating this folder does not make a website live.

The existing Foundation website repository is separate. Do not overwrite its PHP application or charity content with this generated site. It can later link to a chosen product-documentation URL. A GitHub Pages deployment can use a reviewed workflow and a selected environment rather than a new publication branch.

Keep development on main

Follow the pre-edit branch checks. In each changed repository, review git status, switch to the intended main, then stage, inspect, commit and push. Publish changed children before their parent. The full build and Git guide contains the existing submodule commands and native repository-lock step. An unchanged repository does not need an empty commit.

What is not automated here

This target is a local website builder. It does not update GitHub Wikis, grant public access, upload release binaries, invent a stable release channel or replace Studio's Help routing. Those integrations require separately reviewed changes. Documentation sources stay in their owning repositories; generated pages and validation logs stay in the build output.
