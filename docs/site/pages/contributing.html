Umicom Framework & Applications

Write documentation people can use

Contribute examples, source references and clear application guides.

Explain a task that another person can complete

Begin with a practical question: how do I save a note, add a menu command, inspect a build error or validate a training-account instruction? Explain the prerequisites and one new idea at a time. Use professional, direct English. A beginner needs clear steps, not childish examples or unexplained shorthand.

Keep the source authoritative

Framework owns shared explanations, examples and documentation build support. Each application owns its product introduction and user tasks. The website assembles those sources for publication. Do not maintain separately editable copies in a website, GitHub Wiki and IDE help window.

The first site keeps Wiki content in ordinary repository files. A future GitHub Wiki can link to these pages, or receive a generated mirror; it must not become a competing source of API facts. There is no Wiki remote published by this source package.

Document a function completely

Record its public header, exact signature, purpose, parameters, return values, error handling, ownership, thread rules, limits, build target, implementation location, tests and one complete use example. Some public contracts currently have brief comments; generated indexes do not turn those into fully explained APIs automatically.

Use real examples

Prefer existing executable examples and include their source during documentation generation. Do not simplify an API by inventing helper functions without providing them. Clearly separate a whole program from a fragment. Compile tests against the real exported Framework libraries. Demonstration errors must be deliberate and clearly marked.

Review the public page

Read it without private project context. Check links, keyboard navigation and a narrow browser window. Do not include private conversations, personal reports, credentials, internal databases or claims that a feature was tested on a platform where it was not run.

Implementation and documentation together

Each completed feature needs its tests, Wiki/source-map entry, application task guide and example. Native Studio usability remains the first product milestone. Websites do not replace the work required to create, edit, build, fix, run and install a project.

The target coverage is all shared modules, components and public functions, followed by all product journeys. Work first on the components used by Studio, Trader, Desk and Bank. Keep stable names and URLs; cosmetic renaming is not a substitute for filling a missing explanation.
