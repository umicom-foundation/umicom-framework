Introduction to GTK4

Follow native widgets, signals and lifetime rules through Umicom Framework examples.

GTK4 is a toolkit for native graphical interfaces. A toolkit provides reusable visible controls and the machinery that dispatches input to them. A widget is one of those controls: a button, label, text view or a container holding other widgets.

Umicom Framework supplies GTK4 adapters and reusable application services. The application chooses its identity and workflow. The shared service owns operations such as editing a document; the toolkit widget displays or requests those operations.

1. Start with the existing Notes window

Read Windows and components. Its code comes from examples/learning/projects/notes_window.c. Keep that file open beside the guide. You are looking at real source used by the Framework learning examples, not a screenshot of an invented application.

  1. Locate the application and window setup described in that guide.
  2. Find how the central document and surrounding panels are described.
  3. Follow one action from its visible control to the shared operation it requests.
  4. Use the example's documented target and prerequisites. Do not compile one C file alone and assume GTK4 and Framework libraries will be linked automatically.

On Windows, keep the GTK4 development packages in the same UCRT64 environment as your compiler. The build guide lists the maintained setup. An installed runtime alone does not supply the headers needed to compile a GTK4 application.

2. Understand signals

A signal is a notification that something happened. A button can emit a clicked signal. A callback is a function connected to receive such a notification. Connecting a callback does not run it immediately; a later event or explicit signal emission may do so.

A callback can trigger other notifications before it returns. That is called reentrancy. For example, setting a control's disabled state can notify another observer, which may close its window. Code must keep the objects it still needs alive across those calls and must recheck whether the operation remains permitted.

Why is a disabled button not the whole safety check?

A disabled widget normally refuses user input, but other code can still emit a signal or keep a reference to the control. The callback must check whether its operation is still valid. Retiring a report must also disconnect or refuse further captures.

3. Keep native UI work on its owning thread

A thread is one path of execution inside a process. GTK4 widget operations belong on the GTK main thread. A background worker can perform suitable slow work using copied data; it must not reach into widget state.

The shared text-export service is a concrete example. The main thread captures a bounded copy of the displayed text and destination. A worker writes that copy. Completion returns to the main thread to show a result if the view still exists. Later edits to the visible text do not silently change the already accepted write.

Read include/umicom/ui/gtk4/text_export.h and adapters/gtk4/text_export_gtk4.c through the source map. Notice the size limit, refusal to overwrite an existing file and explicit retirement operation. These are part of the workflow, not decorative UI details.

4. Distinguish state from appearance

Visible
A widget can be shown or hidden. Hiding it does not necessarily destroy its object or cancel an accepted job.
Sensitive
A widget has its own sensitivity setting and an effective sensitivity inherited from its ancestors. A child can have its own setting enabled while its disabled parent makes it effectively disabled.
Retired
An application service has ended the control's authority to start further work. This is an application lifetime rule, which must still hold if another caller retains or moves the control.
Destroyed
Native-window removal and final object release need not happen at the same moment. Retained objects must not keep working through expired owners.

5. Try a documented workflow

  1. Build and open the Notes example following its owning guide.
  2. Change some practice text and use the described save action.
  3. Observe whether the UI identifies the requested destination and reports success or a refusal.
  4. Try an existing destination only where the guide explicitly documents a safe refusal. Do not use personal files as test data.
  5. Record the result and source revision. A real screenshot can help explain the workflow, but it is not evidence that hidden error paths passed.

Continue with control maps and checks and repeatable GUI check sessions. The examples describe which actions they exercise; they do not imply that every native application interaction is automated.
