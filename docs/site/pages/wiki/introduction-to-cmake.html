Introduction to CMake

Understand configure, build, test and install using a small Framework SDK example.

CMake reads a description of how a program is built and prepares instructions for a build tool. It does not replace the C compiler. In this guide, CMake describes the project, Ninja coordinates the work, the compiler translates C files and the linker connects their references to library implementations.

1. Separate the source and build directories

The source directory contains files you maintain, including CMakeLists.txt. The build directory contains generated instructions, object files and executable files. An object file is the compiler's output for a source file before the final program is linked.

In a command, -S selects the source directory and -B selects the build directory. A generator such as -G Ninja selects the build tool format. A cache entry such as -DCMAKE_PREFIX_PATH=... supplies a configuration value. CMake saves configuration choices in the build directory, which is why a cache from another computer or compiler should not be copied into your own build.

2. Read the actual example's build description

Open examples/build_diagnostics/CMakeLists.txt. Its important instructions are:

InstructionMeaning
cmake_minimum_required(VERSION 3.24)State the minimum CMake version expected by this project.
project(UmicomNotesDiagnostics LANGUAGES C)Name this project and enable the C compiler.
set(CMAKE_C_STANDARD 23)Request the C23 language standard. The adjacent settings require it and disable compiler-specific language extensions.
find_package(UmicomFramework CONFIG REQUIRED)Read package information from a Framework installation. Stop if it cannot be found.
add_executable(umicom-notes-diagnostics main.c)Declare a build target: the program to produce from this source file.
target_link_libraries(... PRIVATE Umicom::build)Give that program the Framework build-service dependency. PRIVATE means this target uses it internally.
include(CTest) and add_testEnable test registration and tell CTest which program to execute.

3. Run the stages

Use the exact commands in the SDK guide. Configuration should finish with “Build files have been written to” your chosen build directory. Building should produce umicom-notes-diagnostics.exe on Windows. CTest should run notes.build_diagnostics.preview.

cmake --build normally rebuilds outputs affected by changed inputs. That does not mean CTest automatically knows every test affected by a source change. A test selection must account for shared dependencies, generated files and fixtures as well as the file you edited.

Run a named check

ctest --test-dir ".\build\sdk-diagnostics" -R "^notes\.build_diagnostics\.preview$" --output-on-failure --no-tests=error

-R selects test names matching a regular expression. The start and end markers above request exactly one name. --no-tests=error prevents an empty selection being mistaken for successful coverage. A skipped test is not a passing test.

4. Understand presets

A preset is a named set of configuration choices stored in CMakePresets.json. Presets belong to the repository where you run CMake. List them there with cmake --list-presets. A name that exists in Applications may not exist in OS or Kernel.

RepositoryExample configure presetPurpose
Umicom Applicationswindows-ucrt64-all-debugIntegrated Windows application build
Umicom Frameworkwindows-ucrt64-debugStandalone Framework build
Umicom OSgtk4-debugHosted native OS application
Umicom Kernelriscv64-clang-debugFreestanding RISC-V images, not a Windows application

Check your revision's presets before using a name. A hosted OS application, a bootable Linux image and the independent Umicom Kernel are distinct build paths.

5. Keep useful failure evidence

  1. Record the repository, source revision, compiler and exact command.
  2. Keep configure, build and test output in separate local log files.
  3. Find the first compiler or linker error. A later missing executable may be a consequence of that earlier failure.
  4. After a repair, rebuild the required target before rerunning its tests. An old executable is not evidence about new source.
  5. Keep skipped tests and unfinished runs visible. A partial log is a snapshot, not a completed result.

If configuration failed, do not try to fix “missing build.ninja” by creating that file yourself. Resolve configuration and let CMake generate it. If linking fails, inspect the missing symbol and its owning target before adding unrelated libraries.
