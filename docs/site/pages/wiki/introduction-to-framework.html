Umicom Framework

Introduction to Umicom Framework

Learn how an application uses shared services, public interfaces and clear ownership.

What are we building?

An application is a program someone uses to do a task. Studio helps a person edit and build source code. Bank organises financial workflows. Media works with media-related content. These tasks differ, but each application still needs common facilities: opening files, showing errors, keeping editable work and responding to commands.

A framework supplies reusable facilities and agreed ways to connect them. Umicom Framework is primarily written in C23, a version of the C programming language. Native window adapters use GTK4. An application chooses services and connects them to its own purpose. It should not need its own copy of every common implementation.

Read one real example

  1. Open examples/build_diagnostics/main.c in the Framework source, using a text editor. A source file contains instructions written for a compiler.
  2. Find #include "umicom/build/parser.h". This header declares the public parsing function and the information it uses.
  3. Find UmiBuildDiagnostic problem. The program reserves a result value that it owns.
  4. Find umi_build_parse_diagnostic_line(line, &problem). The program supplies the message and a place for the result.
  5. Find the check against UMI_STATUS_OK. The result must be accepted before the program reads its fields.
  6. Follow the complete diagnostic walkthrough to see the source and expected output. Follow the SDK guide when you are ready to compile it.

You do not need to guess what punctuation means. Introduction to C programming explains this exact example.

Four boundaries to understand

Public interface
A documented set of names other code may use. Framework public headers live beneath include/umicom. Read the parameter and lifetime rules before calling a function.
Implementation
The instructions that do the work. They usually live beneath src or an adapter directory. Applications should use the public interface instead of including a private implementation file.
Ownership
The responsibility for keeping a value alive and eventually releasing it. A borrowed input remains someone else's responsibility; an owned result belongs to the receiver. A pointer alone does not tell you which rule applies.
Adapter
Code connecting a shared service to a particular environment. A GTK4 adapter connects a service to widgets. A platform adapter connects to facilities such as files or processes.

Explore without losing your place

  1. Choose a single workflow from the learning route.
  2. Locate its public header using the source map.
  3. Read its example and tests. A test is a program or check that compares an observed result with an expected result.
  4. Keep a separate build directory. Generated files are the tool's output, not the source you edit.
  5. Make a small practice change and explain what changed. Keep your private notes outside material intended for publication.

The Framework contains services at different stages of development. A header or a visible menu entry does not establish that every complete application workflow has been qualified. Read the owning guide's limits and keep results tied to the exact source and environment you used.

Check your understanding

Why should Studio and another application share the same parser?

Both need the same input rules and location handling. A common service allows a correction and its regression checks to live in one place. Each application still decides how to show the result.

Does successfully parsing an error mean a build succeeded?

No. Parsing succeeded: it understood a message. The message can describe a compiler failure. The program running the build must also inspect that process's result.

Should a page copy an implementation into a tutorial project?

Use a complete small application example that calls the public interface. Link the existing Framework library, so the application and guide exercise the same service.
