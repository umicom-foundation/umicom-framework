What each reference topic should tell you

QuestionReference content
What problem does this solve?A plain-language purpose and an application example.
Where is it?Repository, public header, implementation, tests and CMake target.
How is it called?Real signatures, parameters, result values, preconditions and a complete example.
Who owns the data?Allocation, borrowing, transfer, destruction and thread-affinity rules.
What can fail?Invalid inputs, capacity limits, unavailable providers and recovery behaviour.
What has been checked?Which example and test cover the topic; which platform or provider still needs verification.

How coverage grows

The searchable header catalogue covers the public-header files present in this checkout. A header directory is a source grouping, not necessarily a separately loadable module. Doxygen can generate function, structure, enumeration and source-file indexes from the code. Those indexes are a reference, not a substitute for an explanation.

The first worked Wiki topics cover documents, compiler diagnostics and GUI component composition. More topics will follow the development order: command and event routing, workspaces and layouts, tasks and processes, Data Server persistence, source control, testing and debugging, then the financial and desktop services used by Trader, Bank and Desk.

A listing without a worked explanation is not counted as a finished tutorial. Contributors should add examples beside their owning Framework module and link to them rather than copying an implementation into another application.

Version and access

Check the source reference printed on the source-map page. Browser bookmarks are stable page names; a source link refers to a file at the configured branch or commit. The optional generated reference is built locally from the same checkout. Internal implementation details may appear in source listings, but only the documented public headers are intended as application contracts.
