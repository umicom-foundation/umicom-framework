Inspecting C and Assembly with Umicom Framework

Understand CPU registers and machine instructions through the same debugger models used by Umicom Studio.

1. From C source to machine instructions

A C compiler turns source code into machine instructions for the selected processor. Assembly source describes those instructions more directly, but both C and Assembly eventually execute using registers, memory and an instruction pointer.

C sourceCompilerObject codeLinkerExecutableDebugger

Umicom Framework keeps the reusable debugger models independent of GTK4 or any other frontend. A debugger adapter supplies protocol data, Framework stores it in typed C models, and an application such as Studio presents those models.

2. Registers

A register is a small storage location inside the processor. Register names depend on the architecture. On x86-64, RAX is a general-purpose register, RSP is the stack pointer and RIP is the instruction pointer. ARM and RISC-V use different names.

Conceptx86-64 examplePurpose
Program counterRIPAddress of the instruction being executed.
Stack pointerRSPTracks the current stack position.
General registerRAXHolds values used by calculations and function calls.

The Framework register bank is architecture-neutral. Adapters keep responsibility for architecture-specific parsing; frontends receive bounded register records with names, values, groups and changed-value metadata.

3. Disassembly

Disassembly converts machine-code bytes into readable instruction mnemonics such as mov, add and ret. The Framework disassembly model stores the address, bytes, mnemonic, operands, optional source location and current-instruction marker.

0x401020  48 83 c0 01   add $0x1, %rax
0x401024  c3            ret

The current instruction is normally obtained from the program-counter register. Framework recognises common program-counter names such as PC, RIP and EIP, then asks the active debugger adapter for instructions beginning at that address.

4. Refresh low-level inspection

Low-level inspection is meaningful while a debug session is paused. The Framework workbench service requests register scopes through the existing Debug Adapter Protocol runtime. A complete register snapshot is staged before it replaces the previous one. If the adapter also supports disassembly, Framework obtains the current program counter and refreshes a bounded instruction window.

Paused frameRegister scopesProgram counterDisassemble requestToolkit-neutral view models

The public C functions are declared in umicom/debug/workbench/debug_workbench_service.h. Applications do not need to parse debugger JSON or understand adapter-specific register layouts.

5. Use the views in Umicom Studio

Start a native C or Assembly debug session and stop at a breakpoint. Open the Run and Debug activity and select Registers or Disassembly. Choose Refresh after selecting a different stopped frame.

Changed register values are marked so that you can compare one stop with the preceding refresh. The Disassembly pane begins at the program counter when the debugger adapter exposes a suitable register and supports the DAP disassemble request.

Source-level variables and CPU registers answer different questions. Use Variables to understand C values and Registers/Disassembly when following calling conventions, Assembly routines, compiler output or instruction-level behaviour.

6. Practise with Umicom Notes

Use framework/examples/development/c_assembly_notes. Place a breakpoint before or inside UmiNotesCountByte. When execution stops, inspect the C arguments, continue into the Assembly function, refresh the register view and compare the instruction pointer with the first disassembled instruction.

On x86-64, watch how the calling convention places function arguments in registers. Compare the register values with the declaration in notes.h and the instructions in count_byte.S. Continue until the function returns and inspect the result.
