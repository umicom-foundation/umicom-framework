Run a program that asks for input

The program console connects a selected executable to input and output pipes. You can send text lines, finish the input stream and stop the program while its output remains visible. It is useful for console lessons that use functions such as fgets. A pipe carries bytes; it does not provide a full terminal screen.

Use it in Studio

  1. Open your project folder and review its trust setting. Only run programs that you trust.
  2. Save your source and build the program. In Project Settings, select its executable, arguments, working folder and any required tools folder or non-secret environment values.
  3. Open Studio's Terminal panel and choose Open project program console. Opening the window starts nothing.
  4. Choose Run existing program. This uses the current project launch settings. It does not save files, configure or compile the project.
  5. Type a line in the input field and choose Send line, or press Enter. The console adds one newline. “Input queued” means the bytes were accepted by the console, not that the program has read them.
  6. Choose End input when the program needs to read until end-of-file. Previously accepted input is sent first. You cannot send more input to that run after ending it.
  7. Read Output and Errors separately. A finished run shows its process exit code; zero is the usual success convention. Use Stop for a program that will not finish.

Closing or hiding the console stops its program. Changing or closing the project, or revoking project trust, also requests Stop. Keep the window open while working with the program. Stop the program before rebuilding or starting the debugger; Studio blocks competing build and debug commands while console cleanup is pending.

Write an input prompt

#include <stdio.h>
int main(void)
{
    char name[80];
    /* A pipe may buffer output. Flush the prompt before waiting for input. */
    fputs("What is your name? ", stdout);
    fflush(stdout);
    if (fgets(name, sizeof name, stdin) == NULL)
        return 1;
    printf("Hello, %s", name);
    return 0;
}

The console sends UTF-8 text with an LF newline. A child that expects a different encoding must perform its own conversion. Windows programs may choose binary mode when they need exact byte handling instead of the C runtime's text translations.

Limits and troubleshooting

  • A single input frame is at most 4,096 bytes, including the newline. At most sixteen frames can wait. A full queue keeps your input draft; wait for the program to read before trying again.
  • The Output view retains the last 65,535 bytes and Errors retains the last 4,095 bytes. Omitted earlier text is reported. These views are not saved logs.
  • Input is not copied into command history. A program may itself print input, so do not assume the output view is a secret store.
  • Run uses the existing executable on disk. Check the selected path and rebuild if it is out of date. A missing runtime library may require the project's tools folder or an explicit PATH setting.
  • The project profile timeout also applies to this run. Allow enough time for human input; a timeout stops the program.
  • If the program never reads input, a bounded write can time out after sending only part of a frame. The console stops that run instead of replaying uncertain input.
  • Windows and Linux have native support. Linux accepts native little-endian 64-bit ELF executables and rejects a symlink at the executable or working-directory leaf. Other hosts report unavailable.
  • This is not a PTY or terminal emulator. Programs requiring screen control, raw terminal input, password prompts tied to a terminal device or persistent shell state need an external terminal.
  • Process ownership is not a sandbox. Trusted programs inherit the host environment plus the reviewed overrides. Linux processes can deliberately leave their process group.

Extend the Framework service

UmiBuildProgramConsoleCreate prepares saved project settings. UmiProgramConsoleCreate accepts a directly specified native program. Run the console on one dedicated worker and keep that worker alive until UmiProgramConsoleRun returns. Other threads may send input, request EOF, stop or read snapshots. Join the worker before destruction.

The GTK panel accepts host callbacks that prepare a console and recheck authority. Keep project identity and trust checks in that host callback; input queues, environment preparation, native process lifetime and output ownership remain in Framework. The existing restricted process-channel entry point remains available for protocol clients such as VM tools.
