Build a reusable Test Explorer

The Framework model turns discovered tests and retained results into an ordered tree. Applications supply registries and presentation choices; they do not need another copy of the sorting or hierarchy logic.

  1. Create a model and initialise a UmiTestPlatformFilter with umi_test_platform_filter_init.
  2. Set the filter, sort and grouping mode. These calls change the model revision; rebuild before presenting the new query.
  3. Call umi_test_explorer_model_rebuild on the thread that owns both registries. A successful call copies all admitted metadata. Failure leaves the previous projection intact.
  4. Read the summary, then use immutable pages to display a bounded range. Validate the page and source revisions before granting actions.
  5. Keep selection separate from execution. A row ID identifies a test; it does not approve its command or workspace.

What stays stable

Names, source locations, labels, commands, numeric fields and record revisions are reconstructed in ordinary public snapshots. The model owns its text and retained results, so it does not borrow registry storage. Results use the highest sequence, then highest record revision; exact ties retain the first record. Missing parents become roots. Cyclic components are shown once and never recurse.

When a request fails

An unknown selection or expansion ID returns NOT_FOUND without changing existing state. Unterminated filter text returns INVALID_ARGUMENT. Exhausted memory returns OUT_OF_MEMORY. Rebuild allocates privately before swapping the model, so a refusal cannot expose a partially rebuilt tree. Keep old displayed rows inactive if their source registry revisions no longer match.

Filter and select without partial results

  1. Use UmiTestPlatformFilterValidate when accepting a fixed-size query from another component. Unterminated text, suite or label fields are refused.
  2. Set failed_only to include the latest failed and timed-out results. Skipped, cancelled and never-run tests are excluded. An explicit outcome filter further narrows that set.
  3. Use umi_test_platform_filter_select to capture matching IDs in registry order. When more than 1,024 match, it returns CAPACITY_EXCEEDED and leaves the previous output unchanged. Narrow the filter or plan bounded execution batches; do not treat the old output as a newly accepted selection.
  4. Missing result history is allowed. Text-only selection does not need results; a failed-only selection without history is empty.

Inspect a large workspace

UmiTestPlatformFilterInspect counts the complete matching catalogue and checks one selected identity without building an execution selection. It keeps passed, failed, skipped, cancelled, timed-out and never-run counts separate. UmiTestPlatformFilterItemAt copies a matching record in registry order and its exact latest result. Both leave outputs unchanged on failure.

The testing workspace uses these contracts for refresh, status, visible rows and selecting one test. A catalogue with more than 1,024 matches remains browsable, and a selected test can still produce a one-item plan. Run All stays bounded; configure a smaller execution scope or use CTest for a complete large-suite run. Execution never follows automatically from inspection.

Workspace Rerun Failed uses the same text, suite, label, disabled and outcome filters as the visible list, then narrows to failed and timed-out tests. Clear the query first if you intend to rerun failures across the entire catalogue. The lower-level operation service also retains its global rerun entry point. An empty plan contains no IDs and does not indicate that a test ran.

Bounds

The catalogue accepts 65,536 records. Compact storage reduces unused fixed-buffer space, but long metadata still needs memory and the source registry has its own storage. Selection, retained results, history, discovery transport and execution have separate limits. See the page guide before building a large-suite execution workflow.
