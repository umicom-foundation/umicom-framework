Read source supplied by a debugger

A debugger can describe source that is generated at runtime or stored on another machine. A positive source reference is a temporary handle that lets the adapter supply that text. It is not a local filename and is valid only for the connection that supplied it.

Browse in Studio

  1. Open a project, review its location and trust it. Start its native debugger or attach to an authorised process.
  2. In the Debug surface, expand Debugger sources and choose Refresh sources. The adapter must support listing loaded sources.
  3. Filter by name, path or origin. Use Next and Previous for the locally paged catalogue. Filtering does not contact the debugger.
  4. Choose View source beside an entry with a positive reference. The text appears in the read-only viewer below the catalogue. You can select and copy it; it does not replace an editor draft or save a file.
  5. After reconnecting or changing projects, refresh the catalogue. Old references cannot fetch text from the replacement connection.

Understand the boundary

A row with No adapter source reference may describe an ordinary file. Open that file through the project editor after reviewing its path. This browser never opens a reported path automatically. A path may belong to another machine or describe a generated file that has no disk counterpart.

The response is shown as plain text even when its reported MIME type is HTML. The source content is an observation at request time, not proof that it matches the executable or a local file. The catalogue remains captured until you refresh; changes reported by later adapter events do not automatically replace its rows.

Limits and troubleshooting

  1. The complete catalogue allows up to 128 top-level sources, presented 16 per page. The protocol has no catalogue pagination request. A larger reply is rejected with a capacity error rather than shown as a complete partial list.
  2. Related source descriptors are counted but are not expanded into additional rows. Their adapter-specific data is not saved. Text retrieval uses the positive reference alone.
  3. Source content allows 59,999 UTF-8 bytes plus its terminator. The existing debugger transport also bounds the encoded JSON frame, so heavily escaped text may reach that transport limit sooner. Embedded NUL characters, invalid Unicode and oversized fields are refused.
  4. If the adapter does not support source listing, use its normal stack/source facilities or the local editor. A session may support reading a known reference without supporting the complete list.
  5. On a timeout or rejected response, inspect the adapter's diagnostic output and request again only when appropriate. The browser does not retry automatically. Pending lifecycle events also block publication until the host processes them.

Requests are synchronous and bounded, so Studio may pause briefly while waiting. Browsing does not resume, pause, evaluate or modify the debugged program.

Reuse from Framework

UmiDebugRuntimeSourceCatalogRead returns copied descriptors and a UmiDebugConnectionIdentity. Keep that identity with the selected reference when calling UmiDebugRuntimeSourceContentRead. Both calls belong on the runtime owner thread after a host checks its current workspace authority. Allocate the large output values on the heap; failures leave them unchanged.

UmiGtk4DebugSourcesCreate accepts host callbacks and owns their context after successful construction. Other applications can reuse the browser while enforcing their own workspace policy. Its local document editor remains independent.
