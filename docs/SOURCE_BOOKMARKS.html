Integrating source bookmarks

The document coordinator owns session bookmarks because it already owns open-document identity and source navigation. Applications ask this owner to mark or visit locations instead of keeping a second list keyed by file name. This also supports unsaved drafts whose display names are not unique paths.

Use the shared owner

  1. Include umicom/document/bookmarks.h and use the same coordinator that owns the editor's working copies.
  2. Call UmiDocumentCoordinatorToggleBookmark to add or remove the active line. The optional output reports whether a bookmark was added. It is unchanged on failure.
  3. Read UmiDocumentCoordinatorBookmarks. Its count includes closed-document locations; open_count counts locations whose original documents remain open. A line in an open document may still have been deleted.
  4. Pass the snapshot's revision to UmiDocumentCoordinatorTravelBookmark, using +1 for next and -1 for previous. The revision is a freshness token: it prevents an action based on an older bookmark set from silently applying to a changed set.
  5. Enumerate copied rows with UmiDocumentCoordinatorBookmarkAt if your host needs a list. Use UmiDocumentCoordinatorClearBookmarks to clear metadata after checking the displayed revision.
UmiDocumentBookmarksSnapshot bookmarks;
UmiStatus status = UmiDocumentCoordinatorBookmarks(documents, &bookmarks);
if (status == UMI_STATUS_OK) {
    status = UmiDocumentCoordinatorTravelBookmark(documents, 1, bookmarks.revision);
}
/* Show status through the host's existing notification path. */

Keep ownership and navigation together

Calls run on the coordinator's owning thread. The coordinator retains a bounded array of 64 copied locations, without borrowing source text or allocating a second document store. Each row keeps the original document and view identities, a display name captured when marked, and a one-based line and UTF-8 byte column. A byte column counts encoded bytes, not screen cells.

Travel resolves the current full draft before selecting its tab. Closed identities and missing lines are skipped; columns clamp to a valid text boundary. A successful visit enters the existing Back/Forward timeline. Failed resolution leaves the active tab unchanged. Text, pins, read-only state, dirty markers and text Undo history are not edited.

Save As retains a live identity. Closing and reopening a path does not reconnect old bookmarks. Positions are fixed coordinates, not moving text markers. The array is session memory, not a persisted bookmark database. Existing generic path bookmark APIs remain separate.

Connect a GTK host

  1. Bind document editing through the existing UmiGtk4AdapterBindDocumentEditing ownership contract.
  2. Query UmiGtk4AdapterBookmarkEnabled when presenting commands. The action is zero for Toggle, +1 for Next, -1 for Previous, and 2 for Clear.
  3. Dispatch with UmiGtk4AdapterBookmarkCommand. It rechecks availability and rejects overlapping save, close, replacement-review and clipboard work.
  4. Use the existing editing completion callback for feedback. That callback can release the host, so do not dereference the host after dispatch.
  5. Unbind before destroying the coordinator. A retained control must resolve a live binding before dispatching.

Extend the feature safely

A future persistent bookmark list needs explicit file identity and reopen policy; saving a session view identifier would not provide either. A future moving marker needs a defined response to insertions, deletions and Undo. Add those policies to the shared document owner and cover the transition cases before exposing them in application controls.

Regression sources in tests/document/test_bookmarks.c and tests/document/test_bookmarks_gtk4.c cover identity, capacity, navigation, stale requests and native binding lifetime. Their registration supplies coverage to run; it does not establish qualification by itself.
