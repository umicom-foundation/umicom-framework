Finding a running process

A process is a running program. Its process ID, or PID, is a number assigned by the operating system. Numbers can be reused after a program exits, so a remembered PID alone does not identify the same program forever.

Choose a process in Studio

  1. Open a trusted workspace and select your configured native debug adapter in the Debug surface.
  2. Expand Attach to a running application, then Find a running process.
  3. Choose Refresh processes. Discovery runs in the background. Stop discovery cancels between native reads; it cannot interrupt an operating-system call already in progress.
  4. Filter by program name or PID. Names are matched without regard to letter case. Use pid:123 for an exact PID. Previous processes and Next processes move through the captured matches.
  5. Choose Use process to fill the PID field. This does not attach a debugger. The optional executable or symbols path remains your choice.
  6. Review the PID and choose Attach to process. Studio checks the workspace and observed creation time again before requesting attachment. An exited, inaccessible or changed process requires a fresh selection.
  7. Use Stop in the debugger to request detachment. The debugger may have paused the application; a failed or interrupted detach cannot prove that it resumed.

Understand the list

The list is a capture, not a continuously updated view. It reads process names, parent PIDs and available creation identities. It does not read process command lines, environments, credentials or memory. Native enumeration is available on Windows and Linux, with a scan limit of 4,096 records and 20 displayed rows per page. A limit notice means the list is incomplete.

Protected processes can have unknown creation times. They remain visible but cannot be selected. Linux zombie or exited processes and PIDs outside the debugger's positive signed-integer range cannot be selected. Process names use the existing desktop monitor's printable display form; unsupported name bytes appear as question marks.

A process can exit or change between enumeration, the identity recheck and the debugger's request. The recheck reduces mistakes caused by PID reuse; it does not make attachment atomic. The selected adapter and operating system still decide whether attachment is permitted.

Manual PID entry

You can still type a decimal PID directly. Editing the field discards any earlier captured creation identity. Manual entry has no process-capture recheck, so verify the target yourself before choosing Attach. Studio never automatically attaches on startup or when a workspace is reopened.

Use the shared Framework component

  1. Use UmiDesktopProcessCatalogCapture on a worker thread for native observations. A catalogue owns its copied rows; release it with UmiDesktopProcessCatalogDestroy.
  2. Inspect the capture report as well as the rows. Unreadable observations and incomplete scans are part of the result, not evidence that those processes do not exist.
  3. Use UmiGtk4ProcessPickerCreate when a native application needs filtering and explicit selection. The host callback must enforce its own workspace and action permissions. Choosing a row never grants authority to attach or terminate.
  4. A controlled provider can supply copied rows with UmiDesktopProcessCatalogCreate. Mark fixture observations explicitly. The picker displays those rows but disables selection. A supplied provider must honour cancellation and keep GTK calls on the main thread.

When something goes wrong

If a program is missing, refresh after starting it and check whether the scan was limited. If a creation time is unavailable, verify the program and operating-system permissions rather than treating the row as an authenticated identity. Changing workspace invalidates an earlier selected process. If discovery is still stopping, wait for its current operating-system read to finish before starting another capture.
