Synthetic access requests

Umicom Healthcare uses Framework services to demonstrate how an item request moves from registration to a provider reply, acceptance, simulated funding, a timed reservation and collection. The same C23 service is used by the native window and the verification console.

Demonstration records only. Use fictional identifiers. This workspace does not contact providers, reserve real stock, transfer money, authenticate patients or provide clinical decisions. Records are held in memory. When archive controls are available, save a snapshot before closing to reopen it later. Unsaved changes are discarded. It is not a clinical record system.

Open Healthcare from Desk

  1. Use an installation containing both umicom-desk and the native umicom-healthcare executable in its trusted bin directory. Windows adds .exe to both names.
  2. Open Desk and find Umicom Healthcare in its application selection.
  3. Select it and use the normal launch action. The native Healthcare window presents the synthetic access workspace.

Desk checks for the executable; registration alone does not make the application installed. The console named umicom-healthcare-console is a separate verification tool and is never used as a desktop fallback.

If the entry is unavailable, check that Healthcare was selected in the application build, that Framework GTK support was enabled and that the native executable is beside Desk. Setting UMICOM_HEALTHCARE_BUILD_GTK4=OFF deliberately disables the native host; the suite respects this choice rather than generating a preview under the same name.

Try a full request

  1. Keep the patient ID SYN-000001 and select Register patient.
  2. Keep item ITM-000001, enter a requested quantity of 10, then select Create request. The generated request ID appears in the selector.
  3. Keep provider PRV-000001, enter offered quantity 10 and choose Full offer. The detail view still shows no acceptance or reservation.
  4. Review the item and offer, then choose Accept offer.
  5. Select Simulate funding, then Reserve for 5 minutes. The explicit deadline is shown in UTC epoch seconds, a numeric count of seconds since the start of 1970.
  6. Before that deadline, keep the matching patient ID and choose Record collection. Collected quantity becomes 10 and the remaining requested quantity becomes zero.

Repeating collection is rejected. These buttons exercise workflow rules; they are not an authorization system.

Partial supply and follow-up

  1. Create another request for quantity 10.
  2. Enter offered quantity 6 and choose Partial offer. A partial offer must be positive and smaller than the requested quantity.
  3. Accept, simulate funding, reserve and record collection. The detail view keeps the original request of 10, collection of 6 and remaining need of 4.
  4. Enter fictional coordinator STF-000001 and select Assign follow-up. This records responsibility for the remaining need; it does not declare the need resolved.

The item cannot be substituted silently. A different item requires a new request. Provider replies may be revised before acceptance; after acceptance the offer is fixed. Cancellation, refunds, split collections, terminology lookup and linked follow-up completion are not implemented in this exercise.

Unanswered requests and expiry

Clarification leaves a request pending. A later reply may supply a full or partial offer. Unavailable and No response record distinct provider outcomes; use Close unmet and then assign a follow-up coordinator. Decline offer explicitly closes an unaccepted request.

A collection at or after the reservation deadline is rejected. Select Expire reservation after the deadline to record the unmet outcome, then assign follow-up. Expiry is explicit: this in-memory exercise has no background scheduler and does not claim automatic provider cancellation.

Extend the shared service

The public contract is umicom/healthcare/synthetic_access.h, owned by Umicom::healthcare_core. The native widget is UmiHealthcareAccessWorkspaceNew in umicom/healthcare/access_gtk4.h, owned by Umicom::healthcare_access_gtk4. Thin applications should consume these targets instead of copying their state transitions.

Each accepted transition advances a revision. Failed operations leave stored records and caller outputs unchanged. The book is owned by one thread. The GTK root closes its controller before releasing child widgets, and retained controls become inert after that closure.

Future persistent, authenticated workflows need separate reviewed contracts for storage, provider evidence, consent, access control, retries, event history and recovery. Do not turn this synthetic API into a real patient-data service simply by relaxing its identifier checks.

Find requests needing attention

  1. Choose a Worklist: All requests, Outstanding quantity, Needs follow-up, Unassigned follow-up, Reserved, Overdue reservations or Collected.
  2. Optionally enter a fictional STF-000001 style ID in Filter by follow-up owner, then select Refresh worklist. Leave it empty to see all owners. A name or malformed ID is refused; the previous worklist stays visible.
  3. Select the request ID and review its quantities, outcome and revision before taking an action. Counts above the selector describe the entire session; the number shown describes the filtered view.
  4. For an unmet request or partial collection, enter the fictional coordinator in Synthetic follow-up owner and choose Assign follow-up.
  5. In the Unassigned view, the assigned request disappears. Selection becomes empty so the next click cannot accidentally assign another request. Select another request explicitly to continue.

Outstanding means some requested quantity has not been collected, including an unmet outcome. Needs follow-up means an explicit unmet outcome or a partial collection. A provider reply alone does not create a follow-up assignment.

Overdue reservations compares deadlines with the clock when the worklist is refreshed. There is no background refresh. Reading a deadline does not expire the reservation: select the request and use Expire reservation before assigning its unmet follow-up.

Changing filters does not alter requests. If an action is refused after a record changes, refresh and review the current record rather than automatically repeating the decision. Assignment records a fictional coordinator only; it does not authenticate a user or grant access.

Use the worklist in C23

#include "umicom/healthcare/access_worklist.h"

/* book belongs to this thread; now contains positive UTC epoch seconds. */
UmiHealthcareAccessWorklist view;
UmiStatus status = UmiHealthcareAccessWorklistBuild(
    book, UMI_HEALTHCARE_ACCESS_UNASSIGNED, NULL, now, &view);
if (status == UMI_STATUS_OK) {
    /* Each row owns a record copy. Use record.requestId and record.revision
       when requesting a checked transition through synthetic_access.h. */
}

Link Umicom::healthcare_core. The value snapshot holds at most 32 rows and remains readable after the book is destroyed. Build it again after accepted edits; the service performs no storage or network operations.

Save an exercise and reopen it

An archive is a JSON file containing the session's fictional patient IDs, requests, revisions, quantities, provider replies and follow-up assignments. It has no names, clinical notes, passwords or payment details. The full Framework build supplies these controls; a minimal Healthcare core build can remain memory-only.

  1. Finish the request changes you want to keep. Use Choose new location... beside the archive path to choose a new filename, such as synthetic-access.json, in a folder you control. Choosing a path does not write anything.
  2. Select Save new archive. Wait for the message beginning Saved captured session. The file contains the session captured when you clicked Save, even if you subsequently edit the path entry.
  3. Close the application, reopen Healthcare, and use Browse existing... to choose that file. Select Open archive.
  4. If there are already registered patients in the current session, save that session first. Then tick Replace current session when opening and select Open again. The checkbox grants replacement for one attempt only.
  5. After the successful open message, select a request explicitly. The worklist resets to all requests and retains no selection from the previous session. IDs, quantities, revisions and owners should match the saved exercise.
  6. Continue the exercise and save to a new filename. This workflow never overwrites an existing archive.

The interface rejects domain actions while an archive operation is pending. It reads and writes files on a worker so disk access does not block the GTK thread. Closing during an accepted save can leave a completed or partial file; check the result before relying on it. Closing during Open discards a late result instead of changing a closed workspace.

Archives support at most 32 patients and 32 requests and are limited to 64 KiB. They are readable snapshots, not encrypted storage, authenticated provider evidence, an event history or a multiuser database. Opening an older snapshot deliberately restores its older state. Keep only synthetic exercises in these files.

Use the archive service in C23

Link Umicom::healthcare_archive and include umicom/healthcare/access_archive.h. Capture on the thread that owns the registry and book. The resulting bytes are independent of those handles and can be passed to a file worker.

char *bytes = NULL;
size_t length = 0;
UmiStatus status = UmiHealthcareAccessArchiveEncode(registry, book, &bytes, &length);
if (status == UMI_STATUS_OK) {
    /* Write exactly length bytes using the Framework output-file service.
       Keep bytes alive until the worker finishes. */
}
UmiHealthcareAccessArchiveFree(bytes);

UmiHealthcareAccessArchiveDecode returns a new registry and book together only after the entire archive passes validation. Destroy both when no longer needed. Replace existing handles only after success and invalidate every view or queued command belonging to the old session. Stored revisions remain exact unsigned integers, including values above the exact-integer range of a floating-point number.

Restoration checks whether the saved state is reachable through the existing domain transitions. It does not reconstruct or authenticate historical actions. When a host implements automatic storage, event history or shared editing later, those capabilities need their own contracts; this manual archive must not silently assume those responsibilities.
