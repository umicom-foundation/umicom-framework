Synthetic access requests

Umicom Healthcare uses Framework services to demonstrate how an item request moves from registration to a provider reply, acceptance, simulated funding, a timed reservation and collection. The same C23 service is used by the native window and the verification console.

Demonstration records only. Use fictional identifiers. This workspace does not contact providers, reserve real stock, transfer money, authenticate patients or provide clinical decisions. Records stay in memory and are discarded when the window closes. It is not a clinical record system.

Open Healthcare from Desk

  1. Use an installation containing both umicom-desk and the native umicom-healthcare executable in its trusted bin directory. Windows adds .exe to both names.
  2. Open Desk and find Umicom Healthcare in its application selection.
  3. Select it and use the normal launch action. The native Healthcare window presents the synthetic access workspace.

Desk checks for the executable; registration alone does not make the application installed. The console named umicom-healthcare-console is a separate verification tool and is never used as a desktop fallback.

If the entry is unavailable, check that Healthcare was selected in the application build, that Framework GTK support was enabled and that the native executable is beside Desk. Setting UMICOM_HEALTHCARE_BUILD_GTK4=OFF deliberately disables the native host; the suite respects this choice rather than generating a preview under the same name.

Try a full request

  1. Keep the patient ID SYN-000001 and select Register patient.
  2. Keep item ITM-000001, enter a requested quantity of 10, then select Create request. The generated request ID appears in the selector.
  3. Keep provider PRV-000001, enter offered quantity 10 and choose Full offer. The detail view still shows no acceptance or reservation.
  4. Review the item and offer, then choose Accept offer.
  5. Select Simulate funding, then Reserve for 5 minutes. The explicit deadline is shown in UTC epoch seconds, a numeric count of seconds since the start of 1970.
  6. Before that deadline, keep the matching patient ID and choose Record collection. Collected quantity becomes 10 and the remaining requested quantity becomes zero.

Repeating collection is rejected. These buttons exercise workflow rules; they are not an authorization system.

Partial supply and follow-up

  1. Create another request for quantity 10.
  2. Enter offered quantity 6 and choose Partial offer. A partial offer must be positive and smaller than the requested quantity.
  3. Accept, simulate funding, reserve and record collection. The detail view keeps the original request of 10, collection of 6 and remaining need of 4.
  4. Enter fictional coordinator STF-000001 and select Assign follow-up. This records responsibility for the remaining need; it does not declare the need resolved.

The item cannot be substituted silently. A different item requires a new request. Provider replies may be revised before acceptance; after acceptance the offer is fixed. Cancellation, refunds, split collections, terminology lookup and linked follow-up completion are not implemented in this exercise.

Unanswered requests and expiry

Clarification leaves a request pending. A later reply may supply a full or partial offer. Unavailable and No response record distinct provider outcomes; use Close unmet and then assign a follow-up coordinator. Decline offer explicitly closes an unaccepted request.

A collection at or after the reservation deadline is rejected. Select Expire reservation after the deadline to record the unmet outcome, then assign follow-up. Expiry is explicit: this in-memory exercise has no background scheduler and does not claim automatic provider cancellation.

Understanding rejected actions

Message or conditionWhat to check
Patient not foundRegister the synthetic patient before creating a request.
Invalid inputIDs contain the shown prefix and six ASCII digits. Quantities range from 1 to 1,000,000.
Action unavailable in current stateReview the current request. Acceptance precedes funding; funding precedes reservation. Closed requests cannot be reopened.
Collection patient mismatchThe entered synthetic patient must match the request. ID matching does not prove identity.
Capacity exceededA session holds at most 32 patients and 32 requests. Existing records remain intact.
Stale revision in a C23 consumerRead the current record and let the user review it before submitting a new command. Do not automatically repeat a changed decision.

Extend the shared service

The public contract is umicom/healthcare/synthetic_access.h, owned by Umicom::healthcare_core. The native widget is UmiHealthcareAccessWorkspaceNew in umicom/healthcare/access_gtk4.h, owned by Umicom::healthcare_access_gtk4. Thin applications should consume these targets instead of copying their state transitions.

Each accepted transition advances a revision. Failed operations leave stored records and caller outputs unchanged. The book is owned by one thread. The GTK root closes its controller before releasing child widgets, and retained controls become inert after that closure.

Future persistent, authenticated workflows need separate reviewed contracts for storage, provider evidence, consent, access control, retries, event history and recovery. Do not turn this synthetic API into a real patient-data service simply by relaxing its identifier checks.
