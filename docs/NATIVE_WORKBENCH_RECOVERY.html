Native Testing Contributor Guide

1. Learn the native testing workflow

This guide introduces the tools used to check Umicom’s native application windows, editor behaviour and runtime resources. Follow it to prepare a development build, run focused tests, read their results and contribute changes that other developers can reproduce.

Begin with the small test project in framework/tests/native_recovery. Then build the application workspace and use the native acceptance utility to check a selected set of application tests. The focused project and the application workspace have separate build directories: each contains tests for a different purpose.

What the main terms mean

TermMeaning in this guide
FrameworkThe shared implementation used by Umicom applications. Reusable editor, window and testing behaviour is developed here.
Native testA test that exercises compiled application or toolkit behaviour. A GTK test may need an available display even when it keeps its windows hidden.
CMakeThe tool that configures a build directory from the source project and its selected options.
NinjaThe build tool that compiles the targets described by the generated build configuration.
CTestThe test runner used by the configured project. It finds the registered tests and runs their commands.
Acceptance planA JSON file listing the exact tests to check. The native acceptance utility reads this plan and uses CTest to run its entries.
JUnit reportA structured XML test-result file. The acceptance utility checks it and produces a readable HTML summary.

For example, a contributor changing the editor used by an Umicom Notes application needs to check more than whether text appears. The same editing operation should preserve the intended selection, update the document model and remain consistent with Undo. Focused tests make these expectations explicit.

2. Prepare the development environment

The Windows examples use PowerShell and an MSYS2 UCRT64 toolchain. The paths below are example installation locations. Change the two root variables to match the existing source checkout and toolchain on the development machine.

Use Python 3.10 or newer and CMake 3.24 or newer for the focused project. Its GTK test also requires a C23-capable compiler, Ninja, pkg-config, GTK4 development files for version 4.10 or newer, and an available display. The application workspace has additional dependencies defined by its build configuration.

$RepositoryRoot = "C:\umicom\Umicom-Applications"
$ToolchainRoot = "C:\msys64\ucrt64"

Set-Location $RepositoryRoot
$env:Path = "$ToolchainRoot\bin;$env:Path"
$Cmake = Join-Path $ToolchainRoot "bin\cmake.exe"
$CTest = Join-Path $ToolchainRoot "bin\ctest.exe"

& $Cmake --version
& $CTest --version
python --version

Run each command separately. Resolve a missing executable or dependency before continuing. Keep the compiler, GTK libraries and runtime data in the same toolchain installation.

3. Build and run the focused tests

A focused build is a small project used to test a particular group of behaviours without first building the complete application workspace. The commands below enable the real GTK buffer test as well as the resource and report-checking tests.

Configure

& $Cmake -S ".\framework\tests\native_recovery" `
    -B ".\build\native-recovery-checks" -G Ninja `
    "-DCMAKE_C_COMPILER=$ToolchainRoot/bin/gcc.exe" `
    "-DCMAKE_MAKE_PROGRAM=$ToolchainRoot/bin/ninja.exe" `
    -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON `
    "-DCMAKE_PREFIX_PATH=$ToolchainRoot" `
    "-DPKG_CONFIG_EXECUTABLE=$ToolchainRoot/bin/pkg-config.exe" `
    -DUMICOM_NATIVE_RECOVERY_BUILD_GTK_TESTS=ON

if ($LASTEXITCODE -ne 0) { throw "Focused test configuration failed." }

-S selects the source project and -B selects its build directory. Debug is the build configuration. UMICOM_NATIVE_RECOVERY_BUILD_GTK_TESTS=ON requests the GTK test; missing GTK development files then produce a configuration error.

Build

& $Cmake --build ".\build\native-recovery-checks" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Focused test build failed." }

The build command prepares the executable targets. Limiting parallel compilation to two jobs provides a straightforward starting point for development machines.

Run

& $CTest --test-dir ".\build\native-recovery-checks" `
    --parallel 1 --no-tests=error --output-on-failure

if ($LASTEXITCODE -ne 0) { throw "Focused tests failed." }

--test-dir identifies the configured build to test. --no-tests=error treats an empty selection as an error. --output-on-failure displays the diagnostic output of a failed test.

Linux development

From the Applications root, with the required development packages installed, configure and run the same project:

cmake -S framework/tests/native_recovery -B build/native-recovery-checks -G Ninja \
  -DUMICOM_NATIVE_RECOVERY_BUILD_GTK_TESTS=ON
cmake --build build/native-recovery-checks --parallel 2
ctest --test-dir build/native-recovery-checks --parallel 1 --no-tests=error --output-on-failure

Run these commands one at a time and stop on an error. On a headless Linux machine with Xvfb installed, run the final command through xvfb-run -a to provide a display for GTK.

For the resource and report-checking tests alone, configure a separate build directory with UMICOM_NATIVE_RECOVERY_BUILD_GTK_TESTS=OFF. This builds the portable tooling tests without compiling the GTK buffer helper.

4. Prepare the application test build

The application acceptance plan uses test executables from the complete Applications workspace, not from the small focused project. Return to the Applications root before using its presets. Close running Umicom applications before replacing their build outputs or staged runtime files.

Configure the workspace

Set-Location $RepositoryRoot
& $Cmake --preset windows-ucrt64-all-debug `
    -DBUILD_TESTING=ON `
    -DUMICOM_BUILD_NATIVE_TOOL=ON `
    -DUMICOM_BUILD_LEARNING_EXAMPLES=ON `
    -DUMICOM_LEARNING_BUILD_GUI=ON `
    -DUMICOM_WINDOWS_DEPLOY_RUNTIME=ON `
    "-DUMICOM_WINDOWS_RUNTIME_PREFIX=$ToolchainRoot"

if ($LASTEXITCODE -ne 0) { throw "Workspace configuration failed." }

Build the workspace

& $Cmake --build --preset windows-ucrt64-all-debug --parallel 2 -- -k 0
if ($LASTEXITCODE -ne 0) { throw "Workspace build failed." }

The arguments after -- are passed to Ninja. -k 0 lets it continue independent build work after an error so the output can show more than one compilation problem. A nonzero exit still means that the build needs attention.

Stage the native runtime

& $Cmake --build --preset windows-ucrt64-all-debug `
    --target umicom-windows-runtime --parallel 2

if ($LASTEXITCODE -ne 0) { throw "Runtime staging failed." }

Runtime staging prepares the libraries and data used by the built applications. GtkSourceView needs language data as well as its DLL. In a build that uses GtkSourceView 5, check the schema in both the selected toolchain and the staged runtime:

Get-Item -LiteralPath `
    "$ToolchainRoot\share\gtksourceview-5\language-specs\language2.rng", `
    ".\build\windows-ucrt64-all-debug\share\gtksourceview-5\language-specs\language2.rng"

A missing schema should be repaired in the selected GtkSourceView installation before staging again. An empty replacement file cannot provide the language definitions the editor needs.

5. Run the native acceptance utility

The utility runs each test named in the acceptance plan separately through CTest. It records the command, captures the output, reads the JUnit result and updates a summary. Each invocation creates a new result folder.

Only use a trusted build directory: running its CTest configuration executes the commands registered by that project.

$EvidenceRoot = Join-Path $env:TEMP "Umicom-Native-Acceptance"

python ".\framework\tools\testing\native_acceptance.py" `
    --ctest $CTest `
    --build-dir ".\build\windows-ucrt64-all-debug" `
    --evidence-dir $EvidenceRoot `
    --tests-file ".\framework\tests\native_recovery\required-tests.json" `
    --configuration Debug

if ($LASTEXITCODE -ne 0) {
    throw "Read the acceptance output and resolve any test or setup failures."
}
ArgumentHow to choose it
--ctestThe CTest executable associated with the selected development toolchain.
--build-dirThe configured and built project containing the required test registrations and executables.
--evidence-dirThe parent folder for generated run results. The utility creates a separate child folder for each run.
--tests-fileThe JSON acceptance plan to read.
--configurationThe build configuration, such as Debug. The default is Debug.

The final Evidence: line gives the result-folder path. Open summary.html in that folder. Save any results needed for later investigation outside the temporary directory before it is cleaned.

6. Read the results

Start with the HTML summary. For each selected test, it shows an outcome and the reason for that outcome. When a test needs investigation, open its numbered log and XML report.

FilePurpose
summary.htmlA readable overview of the selected tests and their outcomes.
summary.jsonStructured run details, commands, exit codes, completion state and SHA-256 values for available logs and reports.
required-tests.jsonA copy of the test selection used for this run.
001.log, 002.log, …The captured CTest output for each plan entry.
001.xml, 002.xml, …The corresponding JUnit result files, when CTest produces them.

ACCEPTED and NOT ACCEPTED

ACCEPTED means that the CTest invocation succeeded, its report contains exactly the expected test, and the report contains no failure, error, skip or configured diagnostic refusal. The result applies to the selected case in that run.

NOT ACCEPTED means that one of those conditions was not met. Read the reason first: it distinguishes a test failure from issues such as a missing report, an unexpected test identity or a diagnostic message that the plan requires the contributor to investigate.

The utility returns exit code 0 when the complete plan is accepted, 1 when the run is not accepted, and 2 for setup or input errors reported by its command-line entry point.

Run the full suite as well

A focused plan helps during development, while the complete test suite checks a broader set of interactions. Run it from the Applications root:

& $CTest --preset windows-ucrt64-all-debug `
    --parallel 2 --no-tests=error --output-on-failure

if ($LASTEXITCODE -ne 0) { throw "Workspace tests failed." }

7. Understand and extend a test plan

The standard plan groups checks for startup lifetime, workspace tools, package command arguments, Desk window content, the Studio canvas and the Trader workstation. Read the names in framework/tests/native_recovery/required-tests.json and match them to the registrations in the configured workspace.

To see registered test names without executing them, use:

& $CTest --test-dir ".\build\windows-ucrt64-all-debug" -C Debug -N
if ($LASTEXITCODE -ne 0) { throw "Test listing failed." }

The following smaller plan uses the existing package-command test. It is a useful way to learn the file format before maintaining a wider selection:

{
  "purpose": "Check package command construction for native applications.",
  "tests": [
    {
      "name": "framework.development_workflow.contract.provider-argv",
      "reject_output": ["SKIP:", "smoke test skipped"]
    }
  ]
}

Save this example as NotesTests.json and pass its path to the utility with --tests-file. The utility will run the package-command test listed in the file.

name is an exact registered CTest name, not a regular expression. The utility escapes it and anchors the selection. reject_output contains optional literal messages matched without regard to letter case in the test’s JUnit output. Choose messages that identify a condition the test must not silently accept.

Plans contain between 1 and 128 uniquely named tests. Each entry must be independently runnable and produce one expected test result. When CTest fixture dependencies add extra cases, use an appropriate separate workflow rather than treating the resulting group as one test.

After registering a new test with its CMake project, reconfigure the build and run ctest -N in that build directory to check its name. Run the test directly through CTest before adding its exact name to an acceptance plan.

8. Learn from the workbench tests

Window lifetime and ownership

A window can be closed while another part of a program still holds a reference to its object. Read framework/tests/ui_workstation/test_product_startup_lifetime_gtk4.c alongside framework/adapters/gtk4/application_product_application_gtk4.c to study how the application cancels pending startup work and releases its window observations.

The important contributor question is: which object owns each callback, and how does that callback become inactive when the window is no longer usable? Trace the creation, registration, cancellation and release paths together.

Grouped editor operations

A text replacement may delete the current selection before inserting the new text. If the insertion is rejected, the complete operation needs to restore the accepted draft and selection. Read framework/tests/native_recovery/test_editor_buffer_replace.c beside the shared buffer-replacement helper to follow the grouped editing operation.

Then read the Studio canvas test to see how editor content and selection are checked while the surrounding workspace changes. This connects the small helper test to the application-level editing experience.

Portable layout identity

The Trader workstation test illustrates the difference between an experience selector and the identifier stored in an exported layout. Follow the export, decode and import steps in applications/trader/tests/test_gtk_workstation.c. Comparing the decoded record with the import report tests the portable data contract.

Practical exercise: an Umicom Notes workspace

Use a disposable notes document to practise typing, selecting text, replacing a selection and using Undo. Change the surrounding panel arrangement and confirm that the draft remains intact. Write down the expected behaviour as the basis for a test, rather than recording only the sequence of buttons clicked.

When investigating a failure, reduce it to a small, repeatable operation. Add the reusable behaviour to Framework and test the application’s integration through its own public interfaces.

9. Troubleshoot the first run

SymptomNext step
The build directory has no CTestTestfile.cmake.Confirm the selected build path and configure the intended project with testing enabled. Build its test targets before running them.
CTest cannot find a selected test or its executable.List the registered tests, check the exact name and configuration, and inspect the preceding build output.
The GTK development package is missing.Check pkg-config and the selected toolchain prefix. Install the matching development package before configuring the GTK test again.
A GTK test cannot obtain a display.Use an available desktop session or a configured virtual display on Linux. The environment must permit GTK initialisation.
The editor reports a missing language schema.Check share/gtksourceview-5/language-specs/language2.rng in the selected prefix and staged runtime, then repeat runtime staging.
The report has extra test cases.Inspect fixture dependencies and use a test selection suited to the utility’s single-case report contract.
A test times out.Read its numbered log and the last completed phase. Investigate the operation that stalled; distinguish a genuine timing requirement from a blocked operation before changing the test configuration.
A configured diagnostic message prevents acceptance.Read the surrounding test output and investigate the condition it describes. Re-run with a fresh result directory after correcting the cause.

10. Review your changes

Before preparing a commit, check which files have changed in Framework and in the Applications repository. Open PowerShell at the Applications root and run:

Set-Location $RepositoryRoot
git -C framework diff --check
git -C framework status --short
git diff --check
git status --short

git status --short lists changed files. An M marks a modified file; ?? marks a file that Git does not yet track. git diff --check checks the changes for whitespace errors. No output means that this check found no errors; it does not mean the application tests have passed.

-C framework runs a Git command inside the Framework repository. The commands without -C run in the Applications repository. These are separate repositories: Framework stores its source files, while Applications records which Framework commit it uses.

To read the actual edits, run git -C framework diff. Use git diff --submodule=log from the Applications root to inspect changes to the recorded submodule revisions.
