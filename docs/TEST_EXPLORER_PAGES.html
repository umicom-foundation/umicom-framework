Capture a Test Explorer page

UmiTestExplorerPage copies a bounded range from an existing UmiTestExplorerModel. Frontends use the same Framework filtering, hierarchy, sorting and retained-result rules instead of calculating a second test list.

  1. Build the model from the canonical item and result registries and set its filter and ordering.
  2. Call UmiTestExplorerPageCreate(model, offset, page_size, &page) with a page size from 1 to 300. The requested offset is rounded down to a page boundary and clamped to the last available page.
  3. Read the summary and then each page-relative row. Use the returned previous and next offsets only when their availability flags are set.
  4. Before publishing native controls, verify the source registry revisions and UmiTestExplorerPageValidate(page, model). Check again after callbacks that could change the model.
  5. Destroy the page when it is no longer used. Its copied rows remain readable after model destruction, but validation requires the original model to remain alive.
#include "umicom/test_platform/explorer_page.h"

UmiTestExplorerPage *page = NULL;
UmiStatus status = UmiTestExplorerPageCreate(model, 300U, 300U, &page);
if (status == UMI_STATUS_OK) {
    UmiTestExplorerPageSummary summary;
    status = UmiTestExplorerPageRead(page, &summary);
    /* Read summary.count rows with UmiTestExplorerPageRowAt. */
}
UmiTestExplorerPageDestroy(page);

Catalogue and execution limits

The model accepts up to UMI_TEST_EXPLORER_MODEL_MAX_CAPACITY records (65,536), including hierarchy parents. It stores compact owned text, joins results through an ID index and traverses the hierarchy without recursion. A model rebuild either publishes the whole new projection or preserves the previous rows and revision.

The older UMI_TEST_EXPLORER_MODEL_CAPACITY constant remains a compatibility sizing hint. It is no longer the model admission limit. A page still contains at most 300 rows. Selection still carries at most 1,024 IDs and the result registry still retains at most 4,096 records. Browsing a large catalogue does not expand execution, result history or coverage limits.

Expansion and selection survive a rebuild for IDs still present. The model also keeps a bounded history for temporarily absent IDs; when that history reaches the catalogue limit, present IDs take precedence. Rootless cycles are displayed once using a deterministic root, and matching descendants keep their ancestors visible.

Ownership and failure

Page creation allocates only the returned rows on the heap and leaves the source model unchanged. A failed creation clears the output page pointer. Invalid reads leave their output structures unchanged. An empty projection has zero pages, offset zero and no previous or next page.

The owner must serialize model and registry access on its owning thread. Validation detects a different model or a changed model revision; it is not a lock. It does not rebuild a stale model from changed registries. The caller must compare item and result registry identities and revisions separately. Reusing an address after destroying a model is outside this ownership contract.

Native integration

Prepare native rows from copied page records before changing the displayed list. In GTK4, UmiGtk4ListBoxPublish checks the current host and query around native notifications. Invalidate old actions before publication and enable the new page only after the whole list and status controls still match the captured model and query.

No process, file operation, callback, discovery or test execution is performed by this page API. Existing model capacity and outcome semantics are unchanged.
