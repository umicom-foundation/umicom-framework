Install an Umicom Framework SDK without product executables

An SDK contains the headers, libraries and package description needed to build another application. Use the umicom-sdk-libraries build target and FrameworkSDK installation component to produce that set without first building every product executable or test program. This is a development SDK; it does not install the Studio or Trader application.

The selected component follows your build configuration. It includes every Framework library registered in the package export set, including configured optional adapters. It is not a choice of individual find_package components and it does not bundle external libraries. A GTK4 SDK still requires its GTK4 development dependencies; a Qt SDK requires Qt and a suitable C++ toolchain.

Choose a build and installation folder

  1. Open PowerShell in the Framework source folder. The example uses MSYS2 UCRT64 and its C23 compiler. Create a log directory outside the repository: 
    Set-Location "C:\umicom\Umicom-Applications\framework"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\sdk-component"
  2. Configure the normal Framework preset: 
    cmake --preset windows-ucrt64-debug -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\configure.log"
    If you are qualifying a GTK4 application SDK, add -DUMICOM_BUILD_GTK4_ADAPTER=ON and provide the matching development packages. Existing build options continue to control which capabilities are compiled.
  3. Build the SDK's libraries: 
    cmake --build --preset windows-ucrt64-debug --target umicom-sdk-libraries --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\libraries.log"
    This target has dependencies on the registered libraries. A successful library build does not establish that all application executables or tests build.
  4. Choose a fresh prefix, then install the selected component: 
    cmake --install ".\build\windows-ucrt64-debug" --config Debug --component FrameworkSDK --prefix "C:\umicom\installed\framework-sdk" 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\install.log"
    The prefix in this example must be new for this SDK configuration. Do not overlay a different SDK: old headers and optional dependency fragments could remain. Installation is not transactional; if it fails, keep its log, fix the cause and repeat into a new prefix.

Run each command separately and stop on errors. PowerShell does not automatically stop after a failed native command. For a multi-configuration generator, also pass --config Debug to the build. On Linux, use Linux paths and your native C23 compiler.

Qualify the installed result

  1. Run the component fixtures, which build their own small libraries and record per-stage logs under the build tree: 
    ctest --test-dir ".\build\windows-ucrt64-debug" -C Debug -R "^framework[.]sdk[.]component[.]" --output-on-failure --no-tests=error 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\fixtures.log"
    They check selective and full installation, shared and transitive dependencies, repeated and deferred registration, relocation, Release configuration, spaces in paths and invalid or missing libraries. They run on native hosts; cross-compiled SDKs need qualification on an appropriate target environment.
  2. Build the independent Notes and workspace examples against the real installed Framework: 
    cmake -S "C:\umicom\installed\framework-sdk\share\umicom-framework\examples\sdk_qualification" -B "C:\umicom\_local\sdk-component-consumer" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DUMICOM_SDK_ROOT="C:\umicom\installed\framework-sdk" -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_PREFIX_PATH="C:/msys64/ucrt64" -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\consumer-configure.log"
cmake --build "C:\umicom\_local\sdk-component-consumer" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\consumer-build.log"
ctest --test-dir "C:\umicom\_local\sdk-component-consumer" --output-on-failure --no-tests=error 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-component\consumer-tests.log"
    Follow installed SDK qualification for the expected Notes and workspace behavior. These exercises use the installed headers and archives and do not substitute Framework implementation sources.

The existing full installation and older Framework component remain available. The older component alone is not a complete SDK. SDK companion rules are excluded from a full installation to avoid changing its original library registration rules. Windows deployment support is also available to full installations built without product executables.

Extend the library catalogue

When a Framework composition module exports a new library, retain its normal install(TARGETS ... EXPORT UmicomFrameworkTargets ...) rule, then call umicom_register_sdk_libraries(my_library). This helper is internal to Framework's build composition. It adds the library to the SDK build target and registers SDK-only artifact installation without registering the target in the export set twice.

Use real local static, shared, module or interface library targets. Imported libraries, aliases, object libraries, executables and Apple framework bundles are refused. Repeated registration is harmless. Optional modules must also install their dependency-discovery files with COMPONENT FrameworkSDK EXCLUDE_FROM_ALL, so an independent consumer can reconstruct the same external target names.

Troubleshoot installation

  • Missing executable during install: check that the command selects --component FrameworkSDK. A full install still requires its product executables to have been built.
  • Missing archive: build umicom-sdk-libraries for the matching configuration, then install again to a fresh prefix. Missing artifacts are errors, not optional omissions.
  • Missing GTK, GtkSourceView, Qt, HTTP or playback dependency: install the external development packages used by the producer build. Do not remove exported link dependencies to suppress the diagnostic.
  • Imported target points outside the selected prefix: use a fresh consumer build directory and select the intended SDK explicitly. A previous cache can retain another package location.
  • Relocation fails: use relative GNU installation directories such as include, lib and share. Custom absolute installation paths and external runtime dependencies need separate deployment qualification.

The small component fixtures qualify the packaging mechanism. The independent examples qualify only their exercised Framework behavior. Run the full build, tests and application workflows before making broader release claims.
