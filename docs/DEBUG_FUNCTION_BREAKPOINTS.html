Break at a function name

A function breakpoint asks the debugger to pause when execution reaches a named function. It is useful when you know the function you want to inspect but do not yet know its source line. The adapter must advertise support and have enough symbols to resolve the name.

Edit the current session

  1. Open a trusted project and start its native debugger or attach to an authorised running application. The function editor works with an active session.
  2. In the Debug surface, expand Function breakpoints and choose Refresh function breakpoints.
  3. Choose Add function and enter a name such as main. Keep Enabled checked for a breakpoint you want installed.
  4. If the adapter supports them, enter an optional condition or hit condition. Conditions are debugger expressions; their syntax and effect depend on the debugger. They may evaluate code in the target, so use expressions you understand.
  5. Choose Apply function breakpoints. Studio sends the complete enabled set. Adding, editing, disabling or removing a row alone does not change the debugger.
  6. Read each row's Last Apply result. An accepted response can still contain an unverified breakpoint, for example when symbols are unavailable. The adapter's message helps explain that result.

Clear all rows and Apply to remove the session's function breakpoints. Disabling a row retains it in the local draft while omitting it from the next request. Refresh discards unapplied edits and rereads the Framework-owned draft; it does not ask the adapter to enumerate breakpoints.

Session and failure behaviour

Function choices belong to the active connection. A new session starts with an empty, unacknowledged draft and does not automatically replay the preceding process's names or conditions. Reading that initial draft sends no clearing request.

Applying an old session or revision is refused before a request is sent. After a timeout or malformed response, the last requested draft remains visible with acknowledgement unavailable. The target may have received the change; retry only after reviewing its state. No automatic retry, resume or termination is performed by this editor.

The verification shown is evidence from the most recent Apply response, not a live guarantee about later module loading or breakpoint events. Editing a field retires its previous visible verification so that an old reply cannot appear to confirm a new name.

Use from another application

UmiDebugRuntimeFunctionBreakpointsRead copies the current snapshot. Edit its draft and call UmiDebugRuntimeFunctionBreakpointsApply on the platform's owner thread. The owner checks the session ID, revision, capability flags, complete field bounds and exact reply count. The GTK editor accepts Read and Apply callbacks so another frontend can supply its own workspace authority.

A draft holds at most 32 unique names. Text fields are bounded UTF-8 without embedded NUL or control characters. Only enabled entries are sent. Unsupported conditions are refused before transmission. Choices are kept in memory, and this editor does not provide cross-session storage or configuration before a session starts.

The request follows the Debug Adapter Protocol: setFunctionBreakpoints replaces the complete function set, while capability flags determine support for functions and their optional conditions.
