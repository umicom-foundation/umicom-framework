Attach to a running application

Attachment lets a debugger inspect an application that is already running. It does not compile the project or start a second copy. The selected debugger may pause the application while it connects.

Before you begin

Use a local GDB installation with DAP support or lldb-dap. DAP, the Debug Adapter Protocol, carries requests between Studio and the debugger. Debug only a process you are authorised to inspect. This workflow does not request administrator privileges or change operating-system debugging permissions.

Connect from Studio

  1. Open the project's actual folder and mark it trusted only if you trust its tools and source. Select the build profile for that same folder.
  2. Open the Debug surface. Choose GDB or LLDB, enter the absolute adapter executable path if needed, and choose Use adapter.
  3. Find the running application's process ID using your operating system's process viewer. Recheck its name and owner before proceeding: process IDs can be reused after a process exits.
  4. Expand Attach to a running application. Enter the decimal process ID. Optionally enter the absolute path to the matching executable containing debugging information.
  5. Choose Attach to process. Studio sends an explicit attach request, configures the enabled breakpoints, and completes the adapter's configuration sequence. It does not save editor drafts, run a build, apply launch arguments, or change the target's environment.
  6. Use the existing Debug controls to inspect stopped threads, frames and variables when the adapter provides them. Choose Stop to request detachment. Closing the debugger owner also requests detachment rather than termination.

Understand the result

The connection sequence waits synchronously for bounded adapter replies; the interface can pause briefly during negotiation. Each phase has its own wait budget. A timeout or disconnected adapter is not evidence that the target resumed. Inspect the target before deciding whether to make another explicit attachment request. Studio does not automatically retry an uncertain attachment.

This workflow accepts a local numeric process ID, not a process name, remote debug endpoint, debugger command script, or request to wait for a future process. It refuses the current Studio process to avoid stopping the thread needed to communicate with the adapter. A successful request still depends on the installed debugger, matching symbols, target architecture and operating-system permissions.

Use the shared Framework operation

UmiDebugNativeAttachPlanCreate validates and copies the options before any process starts. UmiDebugRuntimePlatformAttachNative performs the native connection. Keep the platform on its owning thread and authorise both the adapter executable and target before calling it. For an attached session, pass 0 as terminate_debuggee to the explicit stop operation. Destroying the platform selects detachment for an attached session.

The options borrow their strings for the duration of the call. The prepared plan owns its copies. A failed plan leaves the caller's output unchanged. The selected working directory must exist and be absolute; optional executable and symbols paths must also be absolute existing files. No working-directory search is used for an explicitly supplied adapter.

If attachment fails

  1. Check that the process is still running and that its ID has not changed.
  2. Check the selected adapter path and support for DAP. GDB and LLDB are separate tools; choosing one does not install it.
  3. Check that the operating system permits your account to debug the target. Studio does not bypass a permission refusal.
  4. If symbols are missing, select the executable built for that exact running application, with debugging information enabled.
  5. After a timeout, check the application's current state before retrying. A detach request without an acknowledgement cannot establish whether the application is running.

The adapter option mapping follows the GDB DAP documentation and LLDB DAP documentation. The shared layer sends a numeric pid and an optional program; it does not claim support for every adapter-specific attachment option.
