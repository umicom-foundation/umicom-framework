Validate a reviewed patch before editing files

A coding assistant can propose a change without being allowed to write it. Framework represents the proposal as a UmiAiCodingPatch: bounded paths, exact before and after text, hashes, line counts, approval metadata and a revision. A host application supplies the file adapter only when it intends to apply the reviewed proposal. This lesson uses the native patch API.

1. Separate storage limits from policy limits

The patch contains sixteen physical file slots. A policy can allow fewer files; setting its limit to a million cannot create more storage. UmiAiCodingPatchPolicyValidate accepts one through sixteen files and a positive changed-line budget. Existing flag fields treat every nonzero value as true.

UmiAiCodingPatchCheckIntegrity checks the physical count independently. It also checks terminated text, required fields, known operations and states, a nonzero revision, content lengths, hashes, line counts and duplicate paths. An initialized empty draft is valid metadata. The policy-aware umi_ai_coding_patch_validate requires at least one file before it accepts a proposal for application.

2. Build a proposal with the real C API

Allocate large inline records on the heap. The patch owns copies of text, so the source strings need not survive the call. Check every status before using the next result.

#include <stdlib.h>
#include "umicom/ai/coding_patch.h"

UmiStatus describe_change(void)
{
    UmiAiCodingPatch *patch = malloc(sizeof *patch);
    if (patch == NULL) return UMI_STATUS_OUT_OF_MEMORY;
    UmiAiCodingPatchPolicy policy = umi_ai_coding_patch_policy_default();
    UmiStatus status = umi_ai_coding_patch_init(
        patch, "change.1", "request.1", "Correct calculation",
        "Use the calculation accepted during review");
    if (status == UMI_STATUS_OK)
        status = umi_ai_coding_patch_add_file(patch, "src/calculate.c",
            UMI_AI_CODING_PATCH_MODIFY, "return 1;\n", "return 2;\n");
    if (status == UMI_STATUS_OK)
        status = umi_ai_coding_patch_validate(patch, &policy);
    /* Present the actual before/after proposal to the user here.
       Approval must follow that review; validation is not user consent. */
    free(patch);
    return status;
}

This example constructs metadata only. It neither edits a repository nor calls a model. In a real product, keep the accepted proposal alive for the review and application steps. Call umi_ai_coding_patch_approve only after the host has obtained the required approval. An approver string is an audit label, not a verified identity or digital signature.

3. Keep refusal separate from publication

File addition uses temporary storage and publishes the entire candidate only after admission succeeds. A long path, oversized text or duplicate path leaves all bytes of the previous patch unchanged, including unused slots. Inputs may refer to existing patch fields. Approval checks its complete label before copying it, and permits overlapping borrowed text.

A revision is an unsigned counter identifying changes to this live value. At UINT64_MAX, inspection remains possible but another mutation is refused with UMI_STATUS_CAPACITY_EXCEEDED. Wrapping to zero would make stale and newer values difficult to distinguish. Do not reset the counter to make a failed edit appear valid; the host needs an explicit new proposal and review lifecycle.

4. Validate adapter results as well as inputs

A read callback returning UMI_STATUS_OK must initialize exactly the reported bytes, and its length must be smaller than the supplied capacity. A terminator is not required for these bytes because hashing uses the explicit length. Returning success with a length equal to or larger than capacity is refused before any write. Both forward application and reversion apply this rule.

Framework checks all expected file contents before it starts writes. A changed before-hash refuses application; a changed after-hash refuses reversion. The current hash detects ordinary content conflicts; it is not a cryptographic signature. The host must enforce the approved workspace, handle filesystem links and prevent changes between reads and writes when stronger atomicity is required.

5. Understand the remaining transaction boundary

Calls require serialized access. Adapter callbacks must not mutate or reenter the same patch, free it, or invalidate the adapter. Admission is not a mutex. If a write fails, the existing implementation attempts to restore affected files. Its returned failure does not certify that every restoration callback succeeded. Inspect the actual files before retrying and preserve evidence of uncertain recovery.

These limits matter when designing a Studio review dialog or an application-specific file adapter. A correct metadata preview alone does not establish filesystem containment, atomic multi-file writes, authenticated approval or successful recovery after an I/O failure.

6. Qualify the boundary deliberately

  1. Configure and build Framework with testing enabled using the platform's documented preset.
  2. Run ctest --test-dir <framework-build> -R "^framework[.]ai[.]coding-patch[.]" --output-on-failure. The admission cases use memory callbacks and do not edit real files.
  3. Check malformed counts, missing terminators, unknown operations, policy limits, duplicate paths and unchanged rejected mutations.
  4. Check apply/revert read lengths at capacity and SIZE_MAX, exhausted revisions before callbacks, content conflicts and ordinary valid round trips.
  5. Run the installed SDK consumer to verify the exported admission symbols. Then qualify the host's real workspace adapter separately, including rollback failures and filesystem races.

Expected results are an explicit refusal without writes for inadmissible input, and the documented state transition for a valid fixture. If a case fails, preserve its command, source revision and output; compare the reported status and callback counts before changing policy. Authored cases and successful configuration do not establish native test or GUI success.
