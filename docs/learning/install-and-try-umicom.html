Umicom Setup Centre • A practical guide

Install Umicom, then try its operating system

Choose the applications you need, review where their files will go, and try an existing Umicom OS image without replacing Windows.

There are two different things you can install. An application, such as Umicom Notes or Studio, runs under your current operating system. An operating system starts a whole computer. To try an operating system inside Windows, we give it a virtual computer instead of changing the computer you are using.

Setup Centre keeps those jobs separate. Its Applications tab installs an offline application release. Umicom OS in QEMU opens an existing kernel and root filesystem in a virtual machine. Boot media prepares files for a later bootable-image build.

What you need to begin

This source update is for building Setup Centre. It is not a ready-made Windows download, and it does not contain QEMU or a prebuilt Umicom OS image. A prepared Windows release contains Umicom-Setup.exe, suite.umi and a payload folder together. Keep those three items together.

1. Choose a release you trust

An offline release is a folder of already-built programs and their supporting files. It does not download missing applications while you install. For a first practice, use a release prepared by someone whose source and build you trust. Do not select a folder of unknown executables just because it contains an Umicom-looking filename.

My Umicom release/
    Umicom-Setup.exe
    suite.umi
    payload/
        bin/
        share/
        ...

The suite.umi catalogue names the applications and records the size and SHA-256 digest of each file. A digest is a compact description of bytes. Changing those bytes changes the digest. That helps find a damaged or changed file; it does not tell you who published it. A person who can replace both the files and their catalogue can also replace their digests.

Double-click Umicom-Setup.exe. The window uses native Windows controls. It does not need the GTK libraries that it is going to install. Building and release testing must still establish that the finished executable has all its own dependencies.

Choose Applications. The Offline release folder initially names the folder beside the setup program. Use Browse… to choose a different release, then select Load applications. Loading a catalogue does not install or run anything.

The application list comes from that release. Select all means all applications actually present in it, not every future Umicom product. A developer who built only Studio and Trader will have a smaller release than someone who built the complete suite.

2. Install a useful pair of applications

Choose what to install

For a small practice, select two applications present in your release, for example Studio and Bank. Use Select none first, then tick those two names. Their shared runtime is included automatically. You do not need to choose DLLs, icon themes or schema files yourself.

Choose a new folder

Enter an absolute path in New install folder, such as C:\Users\YourName\AppData\Local\Umicom Practice, using your own Windows user folder. The default already uses your local application-data location. Browsing chooses a parent and proposes a new child folder.

The final folder must not exist—not even as an empty folder. This version deliberately makes fresh installations rather than merging into an older installation. To try another release, choose another new folder. Never use your source checkout as an installation destination.

The Desktop shortcut group and Start menu shortcut group checkboxes are optional. Each creates a new current-user group containing links to the selected applications. They do not create autostart entries. An existing shortcut group is not replaced.

Review before copying

Select Review selection. Setup reads every selected file, compares its size and digest with the catalogue, and shows the destination, selected applications, file count, byte count and plan fingerprint in the lower panel. Review does not reserve the destination or copy files.

Read that panel. Are the application names right? Is the destination the new folder you intended? A change to the selection or destination makes another review necessary. Only after a successful review does Install reviewed selection become available.

Install and check the result

Select Install reviewed selection. The installer checks the reviewed inputs again, creates the new destination, and checks each file while copying it. The completion receipt, umicom-install.umi, is written last. No application is started automatically.

Wait for Selected applications installed. A separate shortcut warning means the program files were installed but some shortcut work did not finish. Do not mistake that warning for an incomplete application copy; inspect the named shortcut group separately.

Choose Verify installation with the destination still in the form. This reads the receipt and checks the installed files. Extra files you created are left alone. Verification is not an application smoke test: open each installed program afterwards and check a harmless action, then close it.

Try a cancellation

Use a different new destination for this exercise. Begin another installation and choose Stop while copying is active. The incomplete new folder is retained for inspection, without a completion receipt. Do not launch programs from it. A retry needs another new destination; this tool does not silently delete the partial folder.

This native installation path does not yet provide in-place upgrades, repair, removal or Windows “Installed apps” registration. The earlier NSIS installer remains an alternative with its own installation and removal workflow. Do not mix the two installers into the same folder.

3. Try Umicom OS inside Windows

Windows is the host. It continues running your applications. Umicom OS is the guest. QEMU provides the guest with a virtual processor, memory and devices. Setup Centre supplies a reviewed launch request to QEMU; it is not a new hypervisor.

Windows hostYour current computer
→
Setup CentreReview and start
→
QEMU guestUmicom kernel + root filesystem

The supplied launch profile uses QEMU’s TCG emulation. It does not enable Hyper-V features or WHPX. QEMU also supports Windows Hypervisor Platform acceleration for suitable Windows hosts and guest architectures, but that is a separate capability to qualify before adding an accelerated profile.

Prepare three matching inputs

You need a trusted Windows QEMU installation, an Umicom Linux kernel, and the corresponding umicom-rootfs.cpio.gz. Keep QEMU’s DLLs and firmware files with its installation. Copying only its executable may leave required runtime files behind.

GuestWindows QEMU programKernel from the OS build
x86-64qemu-system-x86_64.exebzImage
RISC-V 64qemu-system-riscv64.exeImage

Use the kernel and root filesystem from the same reviewed OS-image build. The existing OS-image build process records an image manifest and has a separate verification step. Keep that evidence with the image. Setup Centre checks headers and fingerprints the two selected files; it does not decompress and validate every root-filesystem entry or replace the image builder’s verification.

Fill in the QEMU tab

Choose Umicom OS in QEMU. Browse to the QEMU program, kernel and root filesystem. Select the guest architecture. Start with 512 MiB of memory and 1 processor. The accepted ranges are 256–8192 MiB and one to eight processors; choosing a larger value does not make memory appear on the host.

Leave Open QEMU serial-console window selected for an interactive session. Select Start in recovery for the recovery exercise. QEMU must include a graphical display backend that supports its virtual serial console.

Read the launch review

Select Review VM inputs. The lower panel shows the chosen program, input digests, plan fingerprint and individual arguments. This profile supplies no host disk, shared folder, network card or monitor port. It also disables QEMU user configuration for this launch. These settings reduce accidental host integration; they do not turn an unknown QEMU binary or malicious guest into something safe.

Select Start reviewed VM only after checking the paths and architecture. QEMU owns its console window; Setup Centre remains the owner of the launched process. A successful process exit is reported as a QEMU result, not as proof that every guest service started correctly.

Use and leave the foundation console

The current diskless foundation offers a text console, not the completed graphical Umicom OS desktop. In recovery, begin with help, then status and packages. Use poweroff to leave normally. The guest runs in memory and this profile attaches no persistent disk.

Stop forcibly terminates the owned QEMU process. Unsaved guest work is lost. Closing Setup Centre during a run asks whether to stop and waits for the native operation to return.

For a bounded non-interactive check, clear the serial-console checkbox. The profile captures serial output and requests automatic guest power-off. Read the returned diagnostics. The original OS boot-acceptance checks still need to establish the expected service sequence and final boot report; this window does not infer those results from an exit code.

4. Prepare boot media without touching a drive

A folder containing a Linux kernel is not automatically bootable. Firmware needs a boot loader and a suitable disk or optical-image layout. The preparation step therefore has a different name from “Write USB”. It writes only ordinary files into a new directory.

Choose Boot media, select an x86-64 kernel and its matching gzip root filesystem, and choose a New preparation folder. Select Prepare boot-media source. The result is:

Umicom Media Preparation/
    media.umi
    tree/
        boot/
            kernel
            initrd
            grub/
                grub.cfg

The GRUB menu contains normal and recovery entries for the diskless foundation. media.umi records the copied inputs. This directory is still not a bootable USB or CD.

Ask the native Linux GRUB tool to make an ISO

A developer can use the native umicom-setup media-iso command in Linux or WSL with an installed, trusted grub-mkrescue and its native dependencies. The selected GRUB installation determines which BIOS or UEFI boot support is available. This step copies only the known, verified source files into another new tree, then invokes GRUB without constructing a shell command.

umicom-setup media-iso \
    --prepared /absolute/path/to/Umicom-Media-Preparation \
    --grub /usr/bin/grub-mkrescue \
    --output /absolute/path/to/a-new-iso-build

The command checks the produced ISO’s ISO9660 and El Torito structures. That is a structural check, not a real boot test. Test the ISO in a virtual machine using the intended firmware before treating it as a release.

USB writing and optical burning are not enabled here.

No command in Setup Centre opens a physical drive, formats a disk or burns a disc. A later device-writing stage needs clear device identity, removable-media checks, explicit erasure confirmation, locking, write verification and recovery handling. The present kernel is a serial-console QEMU foundation, not a hardware-qualified desktop image.

A future USB or CD release also needs firmware coverage, appropriate hardware drivers and a tested user interface after boot. Do not copy this source-preparation folder to a USB stick and call it a bootable operating system.

5. Build a release for other people

This section is for someone working in the Umicom source checkout. Begin with a successful full build and test run. The ordinary application build already prepares private Windows runtime files and records exactly which files each target owns.

The new native packer reads those generated reports as data. It does not execute them as CMake, scan every executable in build/bin, or include test programs just because they happen to be nearby. It combines the selected applications with their shared runtime and verifies the reported digests.

From the configured Windows Applications checkout, run:

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build --preset windows-ucrt64-all-debug `
    --target umicom-native-installer --parallel 2

For the Debug configuration, the default result is build\windows-ucrt64-all-debug\packages\Debug\native-suite. The destination must be new. To prepare another release, configure UMICOM_SETUP_OUTPUT_DIRECTORY to another absolute directory rather than overwriting the previous one.

Distribute the whole prepared folder, not just Umicom-Setup.exe. This is an uncompressed offline folder release, not yet a signed single-file self-extracting package. The older umicom-windows-installer target remains available for the separate NSIS package.

QEMU bundling is a release decision

This source delivery does not redistribute a QEMU binary. For now, the user selects an existing QEMU installation. An eventual bundled release must include the selected QEMU runtime, firmware and dependencies, preserve their notices, and meet the applicable redistribution and corresponding-source requirements. QEMU’s licensing is separate from Umicom’s MIT licence.

The native payload format can include explicitly listed supporting files, but it does not automatically discover a complete QEMU dependency set. Do not label a release “QEMU included” until it has been assembled and run on a clean Windows machine without your development PATH.

Before publishing

Try a fresh installation on a clean Windows test machine. Test two applications, then all configured applications. Check shortcuts, an existing destination, cancellation and a changed payload file. Launch the installed applications by double-click. Test both normal and recovery guest runs using the selected QEMU build. Keep Windows, guest-boot and BIOS/UEFI results separate: success in one does not establish success in the others.

6. Find a problem without guessing

What you seeWhat to check next
No applications loadChoose the directory containing suite.umi, not its payload subfolder or an arbitrary build directory.
A payload digest changedStop. Obtain a complete release again, or rebuild and repackage it. Do not edit the catalogue to hide the mismatch.
The destination existsChoose a genuinely new folder. Neither an empty folder nor an old installation is accepted for merging.
Installation is incompleteKeep the partial new tree and read the status. It is not a completed installation. A new attempt uses another new destination.
Applications installed, shortcuts failedInspect the shortcut group. The installed files can be verified independently; an existing group is deliberately not replaced.
QEMU exits quicklyRead diagnostics; check the correct system emulator, its firmware/DLLs, selected guest architecture, kernel and root filesystem.
No graphical Umicom desktop appearsThe current image is a diskless text-console foundation. Starting QEMU does not add the later desktop stack.
The media source will not bootSource preparation is not ISO construction, device writing or firmware qualification. Complete those separate stages first.

For a developer report, record the exact operation, input paths without secrets, selected applications or guest architecture, status text and whether any new output directory was created. Do not upload personal project files merely to demonstrate that the installer ran.
