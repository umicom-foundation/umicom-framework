Keep learning checkpoints with their source revision

A checkpoint records a deliberate learning action, such as reviewing an exercise. A lesson can change after that action. The Framework progress journal therefore keeps the lesson identity, its pack revision and its content hash with every checkpoint. An older record stays available without becoming completion for a different lesson.

This service is available through Umicom::learning_progress and umicom/teacher/learning_progress.h. It supplements the existing education workspace, which keeps progress for its own curriculum. The native learning catalogue does not yet provide controls for this journal; use the C API or the SDK example. It does not automatically mark a document complete when a reader opens it.

Understand the record

FieldMeaning
Learner IDA local identifier selected by the application. It is not an authenticated account.
Pack and resource IDsThe exact document in the admitted learning pack.
Pack revisionThe publisher's positive revision number, captured when the reader opened the pack.
SHA-256The content digest verified by the reader. A digest detects changed bytes; it does not prove the publisher is trustworthy.
CheckpointAn application-defined action such as read or exercise-reviewed.
Evidence referenceAn opaque local identifier for supporting evidence. The service does not open or grade that evidence.
SequenceThe record's position in this learner's journal, beginning at one. It is not a timestamp.

Identifiers use letters and digits, with a dot, dash or underscore after the first character. Each is at most 95 bytes. Keep names, conversations, passwords and filesystem paths out of them. The database is plaintext local storage. Choose a separate private location outside course source and public repositories.

Use the service in an application

  1. Open a verified reader. Load an explicit pack and call UmiLearningReaderOpen. Only a guide or lesson can receive a checkpoint. Example source files and images are refused.
  2. Select storage explicitly. A memory Data Server is useful for a temporary demonstration. A SQLite Data Server uses a database path chosen by the learner. There is no silent fallback from SQLite to memory.
  3. Open one journal owner. Pass the Data Server and learner ID to UmiLearningProgressOpen. The journal borrows the server; it does not take ownership of it.
  4. Record an explicit action. After the learner chooses to record a checkpoint, pass the reader, checkpoint and evidence ID to UmiLearningProgressRecord. Check the returned status before displaying success.
  5. Query the current document. UmiLearningProgressFindCurrent compares pack ID, revision, resource ID and digest. A change to any of them prevents an older event satisfying the query.
  6. Close in ownership order. Close the journal before destroying its Data Server. Serialize calls on both the journal and reader. Interactive applications should perform storage work on their worker thread.
UmiLearningProgress *progress = NULL;
UmiLearningProgressEvent event;
UmiStatus status = UmiLearningProgressOpen(server, "local-learner", &progress);
if (status == UMI_STATUS_OK) {
    status = UmiLearningProgressRecord(
        progress, reader, "exercise-reviewed", "review-001", &event);
}
/* Report status; event is published only after a successful commit. */
UmiLearningProgressClose(progress);
/* The application still owns server and reader. */

The application defines what a checkpoint means. This API does not award a qualification, grade an exercise, run source code or verify the evidence reference. For example, a self-recorded reading checkpoint must not be displayed as a teacher-approved assessment.

Try the SDK example

The installed learning_pack_inspector example includes progress.c. Its build creates umicom-learning-pack-progress when the selected SDK exports the progress component. Use the configuration steps in the installed example's guide.html to select the SDK prefix. From that example's build directory, this temporary demonstration records and reopens a checkpoint:

.\umicom-learning-pack-progress.exe memory "$PWD\pack" learning-pack.json guide

Expected output:

Current checkpoint: read
Document: framework.learning-packs::guide revision 1
Event: 1
Storage: temporary

This memory demonstration loses its Data Server when the process exits. For persistent storage, first create a private folder and select its absolute database path. Replace the example learner and evidence identifiers with your local identifiers:

New-Item -ItemType Directory -Force "C:\umicom\_local\learning"
.\umicom-learning-pack-progress.exe record "$PWD\pack" learning-pack.json guide "C:\umicom\_local\learning\practice.sqlite3" learner read review-001
.\umicom-learning-pack-progress.exe show "$PWD\pack" learning-pack.json guide "C:\umicom\_local\learning\practice.sqlite3" learner read

show opens an existing database read-only. A missing database is an error, not an empty new journal. record may create the selected database. An exact duplicate returns ALREADY_EXISTS with exit code 3; a missing current checkpoint returns NOT_FOUND with exit code 4. Other failures return a nonzero code. SQLite must be enabled in the SDK.

Export and restore private records

UmiLearningProgressExport copies the current projection into a bounded text archive. It does not save a file, refresh another writer's records or upload data. UmiLearningProgressImportEmpty accepts an archive only for the same learner ID and only when both the current projection and stored journal are empty. It does not merge, replace or relabel history.

The SDK example archive.c supplies explicit file operations. Its exporter opens the database read-only and creates a new archive with Framework's exclusive file-creation service. An existing destination is refused. Its importer reads a bounded archive and may create the selected destination database; a refused import can leave that empty database in place.

.\umicom-learning-pack-archive.exe export "C:\umicom\_local\learning\practice.sqlite3" learner "C:\umicom\_local\learning" "checkpoints.txt"
.\umicom-learning-pack-archive.exe import "C:\umicom\_local\learning\restored.sqlite3" learner "C:\umicom\_local\learning" "checkpoints.txt"

For one recorded event, the expected messages are Exported 1 checkpoint events. Keep the archive private. and Imported 1 checkpoint events. Keep the archive private. Stop if either command returns an error. Choose a new archive name when the export file already exists. Inspect a partial file or uncertain database result before retrying.

The archive begins with ULP1, the learner ID and event count, followed by the canonical event lines. Export uses LF line endings; import also accepts CRLF. Unknown versions, embedded NUL bytes, extra data, incomplete lines, duplicate events and invalid fields are refused before a transaction starts. Imported events are stored in one transaction. A zero-event archive creates no journal records.

This archive contains local learning history and evidence identifiers. Keep it in a private folder and share it only by an explicit user decision. It is not signed, encrypted or proof of an assessment. Importing a journal does not make its claims more trustworthy. The initial service does not rotate a full journal or provide a multi-device account system.

Handle a conflict or storage failure

ResultWhat to do
BUSYAnother owner changed the journal, or the server already belongs to a transaction. Finish the existing transaction. For a stale journal, refresh, inspect the new history and let the learner decide whether to submit again.
ALREADY_EXISTSThe identical document/checkpoint/evidence event is already recorded. No second event is added.
PARSE_ERRORThe saved journal is incomplete or unsupported. Preserve it for inspection. Do not replace it with an empty journal.
CAPACITY_EXCEEDEDThe journal has reached its 256-event limit or storage cannot accept the record. Existing history is preserved. Export preserves a private copy, but journal rotation is not implemented.
Commit or rollback errorThe result may be uncertain. Inspect recovery_required; close the journal and establish a new storage connection before reopening. Do not blindly retry an event or treat the old projection as current.
PERMISSION_DENIEDThe selected server is read-only. Viewing history does not grant permission to write.

The service stores one header and numbered events under a learner-specific Data Server key prefix. It validates the complete history inside a transaction, including orphaned events and unexpected keys. Before appending, it compares the canonical saved records with its last projection. Checking only the event count would miss a same-length edit to old evidence.

Records are append-only through this API, but an external database editor can change them. This is not an authenticated ledger, encrypted store or protection against a malicious local administrator. It also does not coordinate learner accounts between devices.

Source and regression coverage

Read src/teacher/learning_progress.c for transaction ownership and src/teacher/learning_progress_storage.c for format validation. tests/learning_pack/test_progress.c covers revision changes, duplicate records, separate learners, stale writers, damaged histories and SQLite reopen. test_progress_archive.c covers private transfers and import refusals. test_progress_faults.c injects write, commit and rollback failures, including a commit that succeeds internally but reports an error. Running those checks on a particular SDK and platform is still necessary before relying on that build.
