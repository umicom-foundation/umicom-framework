Review a payment before committing it

Follow one fictional transfer from prediction to reservation, approval and a recorded local posting.

Begin with a prediction, not a payment

You are about to send £250 from a workshop account to its supplier. Before making a change, you should be able to answer three questions: which account is affected, how much will remain available, and whether the operation reserves funds or actually posts a journal.

The Review command button answers those questions using the same Framework banking code that will execute the command. It works on a temporary copy. Reading or discarding the review does not change a balance, create a hold or grant approval.

Use fictional practice data. This workspace is an existing local banking simulation. The identities named Test maker, Test checker and Test operator teach separation of duties; they are not authenticated people. It has no bank or card-network connection and cannot transfer real money.

This guide has two routes. Start with the memory-only C example to learn the complete sequence without creating a database. Then use the graphical exercise in a compatible GTK-enabled Bank build. The native implementation was tested in the delivery environment; the Windows and GTK steps are local acceptance exercises, not a claim that their interfaces have already been tested.

WordMeaning in this exercise
BookedThe balance produced by committed ledger postings.
ReservedFunds held by a pending instruction or another active reservation.
AvailableBooked minus reserved, under this simulation's no-overdraft rules.
ReviewA prediction made from the service's currently loaded history.
ReceiptThe result of an accepted command, with its committed revision and request ID.
RevisionThe number of accepted events in this bounded local history.

1. Run the memory-only lesson

Merge the source files into the matching repositories and complete the build instructions supplied with the delivery. Open PowerShell at the Applications root and run:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom-bank-review.exe" --self-test
if ($LASTEXITCODE -ne 0) { throw "The banking review lesson failed." }

The result should be:

Before applying: GBP 1000.00 is still available.
Review predicts: GBP 250.00 reserved; GBP 750.00 available.
Approval changes the transfer state, not the booked balances.
Local posting: Workshop GBP 750.00; Supplier GBP 250.00.
Practice complete. Memory only; no bank network or real payment was used.

The example uses the actual memory Data Server and banking service. It creates fictional customers and accounts, funds one account with test money, reviews a transfer, approves it under a different identity, and executes its local posting. There is no file, network or real funding operation.

Run demo instead of --self-test to print the complete transfer review. Notice the words source revision and predicted revision. The prediction is not a receipt.

2. Open a practice banking workspace

Open Umicom Bank from your built or installed application. Choose its existing Banking operations control. The window is titled Umicom Bank - Local Banking Operations.

The path printed at the bottom identifies the existing per-user database, normally beneath the user-data directory in Umicom/Bank/bank-operations-simulation.sqlite. This batch does not choose a fresh database automatically or migrate an old one. Use a disposable local test account or an established practice database. Close the application before backing up its database, including any required journal files. Never delete a history to bypass an error.

The form now contains Review command, alongside New request, Submit command, Reload committed data and Show statement. The new Command review page follows the existing Customers, Accounts, Transfers / beneficiaries, Cards / holds, Ledger / statement, Reconciliation and Audit pages.

Submit command starts disabled. It becomes available only after a valid review of the current form. Changing a field, action, identity or lifecycle selection discards that review. Reloading and preparing a new request also require another review.

Read the current state first. If another instance may have changed this database, choose Reload committed data before reviewing. A review is made from cached state; it does not silently refresh the underlying database.

3. Prepare the workshop and supplier

Use the following setup only in a fresh practice history where these IDs do not already exist. For each row, choose the action and simulation identity, choose New request, fill the enabled fields, choose Review command, inspect the prediction and then choose Submit command. Keep a valid business date. A new request supplies a fresh identifier and timestamp.

The table abbreviates the form labels: Entity means Entity ID; Owner means Owner / beneficiary / card ID. Fill only fields enabled for the selected action.

Open account / Test makerEntity workshop-gbp; Owner workshop; Name Workshop current account; Integer minor units 0; Currency GBP; Currency scale 2.
Create customer / Test makerEntity supplier; Name Supplier.
Open account / Test makerEntity supplier-gbp; Owner supplier; Name Supplier current account; minor units 0, currency GBP, scale 2.

At scale 2, 100000 minor units means GBP 1000.00. Enter an integer without a decimal point in the minor-units field. A test credit is simulated funding, not a cash deposit from an external institution.

Check the Accounts page. The workshop should have GBP 1000.00 booked and available, with zero reserved. The supplier should have zero. In a fresh history these six accepted commands produce revision 6.

4. Review a transfer and deliberately change it

Choose Submit transfer and Test maker. Prepare a new request. Enter Entity ID invoice-001, Owner / beneficiary / card ID supplier-payee, Source account workshop-gbp, Destination account supplier-gbp, minor units 25000, currency GBP and scale 2.

Choose Review command. The Command review page should show the complete request and the affected workshop account. It predicts:

MeasureBeforeAfter submitting
BookedGBP 1000.00GBP 1000.00
ReservedGBP 0.00GBP 250.00
AvailableGBP 1000.00GBP 750.00

At this point the actual Accounts page is unchanged. The review has not reserved the GBP 250.00.

Now change the amount to 26000. The review disappears and Submit command becomes unavailable. This prevents a GBP 260.00 command from using the review of GBP 250.00. Change it back to 25000, review again and submit.

The status should say Committed locally with a revision. The actual workshop account now has GBP 250.00 reserved. Check the Transfers / beneficiaries page: the transfer is pending approval. There is no supplier credit yet.

5. Approve, then post, then check the statement

Choose Approve transfer, Entity ID invoice-001 and Test checker. Use a new request, review it and submit it. Attempting approval as Test maker is refused because the creator cannot approve their own transfer.

The approval review has no new journal and normally no changed balance row. That is intentional: it predicts a workflow change, not movement of money. Its resolved transfer details still show the amount, source and destination accounts, beneficiary, maker, checker and state transition. Check those before approving.

Next choose Execute transfer, Entity ID invoice-001 and Test operator. Prepare a new request and review it. This time the prediction shows two affected accounts and a balanced proposed journal. Submit it only after checking the source, destination and amount.

The workshop now has GBP 750.00 booked, zero reserved and GBP 750.00 available. The supplier has GBP 250.00 booked and available. Enter workshop-gbp in the statement account field and choose Show statement. The ledger view explains the corresponding movements.

A later Reverse transfer is a separate controlled command and produces a compensating journal. It does not erase the original payment or guarantee an external reversal; this entire exercise remains local.

A repeated request is not a second payment. The existing service recognises an identical accepted request ID and payload. A fresh review can display its historical receipt without another posting. Reusing the ID with different fields is rejected. The same already-applied review cannot be used after the state has advanced; obtain a new review.

6. Apply the same approach to holds and reconciliation

Use Place hold as Test operator to examine a reservation without changing booked money. Review Release hold before releasing it. The same service also reviews the existing simulated card authorisation, capture, void and refund commands. A capture can post cash and release the unused part of a reservation; its review shows both effects.

For reconciliation, choose Reconcile account, a new entity ID, the source account and an externally observed practice balance. The review tells you whether that amount agrees with the local booked balance. Applying a mismatch records a break; it does not adjust the ledger to make the figures match.

Blocking a customer can change debit eligibility for several accounts without changing a monetary amount. Those accounts appear in the review with their before/after active status. Actions that change a name or another nonmonetary record are described by the command and catalogue counts rather than invented money movements.

7. Read the C ownership and commit path

The public interface is in umicom/bank_operations/review.h. The existing Umicom::bank_operations library owns it; there is no second financial engine.

UmiBankOperationsReview asks the canonical transition to prepare a candidate. Framework copies its description and the relevant event history, frees the candidate and returns an owned immutable review. UmiBankReviewSnapshotRead gives the caller a copy. Destroy the review when the user edits the form, cancels or finishes.

UmiBankOperationsExecuteReviewed checks the current actor and exact loaded history, then calls the same canonical execution path again. For a new command the repository validates the stored history and appends the event and revision within one Data Server transaction. Only a successful commit replaces the in-memory state and produces a receipt.

The review may outlive the handle that created it. It is bound to history, not a path: another handle with equivalent canonical history can use it. The API deliberately does not call this a cryptographically authenticated approval.

The complete lesson below is the source built by the native tool. Its actor capabilities are explicit test inputs, not a login mechanism.

/*-----------------------------------------------------------------------------
 * Umicom Framework | Sammy Hegab, Umicom Foundation | MIT
 * Complete lesson: inspect the reservation, approval and local posting separately.
 * All setup actors are trusted fictional test identities, not authenticated users.
 *---------------------------------------------------------------------------*/
#include "lesson.h"
#include "umicom/bank_operations/review.h"
#include "umicom/finance/money_text.h"
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static UmiStatus Command(UmiBankOperations *bank, UmiBankCommand *command,
    UmiBankAction action, const char *id)
{
    UmiBankCounts counts;
    UmiStatus status = UmiBankOperationsCounts(bank, &counts);
    if (status != UMI_STATUS_OK) return status;
    UmiBankCommandInit(command, action);
    command->expectedRevision = counts.revision;
    command->businessDate = (UmiFinancialDate){2026, 9U, 28U};
    command->timestampMillis = (int64_t)counts.revision;
    (void)snprintf(command->requestId.value, sizeof command->requestId.value,
        "lesson-request-%" PRIu64, counts.revision + 1U);
    return umi_financial_id_assign(&command->id, id);
}
static void Money(UmiMoney *out, int64_t minor)
{
    memset(out, 0, sizeof *out);
    memcpy(out->currency.code, "GBP", 4U); out->scale = 2U; out->minor_units = minor;
}
#define TRY(call) do { status = (call); if (status != UMI_STATUS_OK) goto done; } while (0)
int UmiBankReviewLesson(bool verbose)
{
    UmiBankOperations *bank = NULL;
    UmiBankReview *review = NULL;
    UmiBankReviewSnapshot *snapshot = NULL;
    UmiBankCommand command;
    UmiBankReceipt receipt;
    UmiBankActor maker = {0}, checker = {0};
    UmiBankBalance balance;
    char *text = NULL;
    UmiStatus status;
    maker.capabilities = checker.capabilities = UMI_BANK_CAP_ALL;
    TRY(umi_financial_id_assign(&maker.id, "workshop-maker"));
    TRY(umi_financial_id_assign(&checker.id, "workshop-checker"));
    TRY(UmiBankOperationsOpenMemory(&bank));
    for (unsigned i = 0U; i < 2U; ++i) {
        TRY(Command(bank, &command, UMI_BANK_CUSTOMER_CREATE, i == 0U ? "workshop" : "supplier"));
        strcpy(command.name, i == 0U ? "Workshop" : "Supplier");
        TRY(UmiBankOperationsExecute(bank, &maker, &command, &receipt));
        TRY(Command(bank, &command, UMI_BANK_ACCOUNT_OPEN, i == 0U ? "workshop-gbp" : "supplier-gbp"));
        strcpy(command.ownerId.value, i == 0U ? "workshop" : "supplier");
        strcpy(command.name, "GBP current account"); Money(&command.amount, 0);
        TRY(UmiBankOperationsExecute(bank, &maker, &command, &receipt));
    }
    TRY(Command(bank, &command, UMI_BANK_BENEFICIARY_CREATE, "supplier-beneficiary"));
    strcpy(command.ownerId.value, "workshop"); strcpy(command.destinationAccountId.value, "supplier-gbp");
    strcpy(command.name, "Workshop supplier");
    TRY(UmiBankOperationsExecute(bank, &maker, &command, &receipt));
    TRY(Command(bank, &command, UMI_BANK_TEST_CREDIT, "practice-funding"));
    strcpy(command.sourceAccountId.value, "workshop-gbp"); Money(&command.amount, 100000);
    TRY(UmiBankOperationsExecute(bank, &maker, &command, &receipt));

    TRY(Command(bank, &command, UMI_BANK_TRANSFER_SUBMIT, "invoice-payment"));
    strcpy(command.sourceAccountId.value, "workshop-gbp"); strcpy(command.ownerId.value, "supplier-beneficiary");
    Money(&command.amount, 25000);
    TRY(UmiBankOperationsReview(bank, &maker, &command, &review));
    snapshot = malloc(sizeof *snapshot);
    if (snapshot == NULL) { status = UMI_STATUS_OUT_OF_MEMORY; goto done; }
    TRY(UmiBankReviewSnapshotRead(review, snapshot));
    TRY(UmiBankOperationsBalance(bank, "workshop-gbp", &balance));
    if (balance.available.minor_units != 100000 || snapshot->accountCount != 1U ||
        snapshot->accounts[0].after.available.minor_units != 75000) { status = UMI_STATUS_INTERNAL_ERROR; goto done; }
    puts("Before applying: GBP 1000.00 is still available.");
    puts("Review predicts: GBP 250.00 reserved; GBP 750.00 available.");
    if (verbose) {
        text = malloc(UMI_BANK_REVIEW_TEXT_CAPACITY);
        if (text == NULL) { status = UMI_STATUS_OUT_OF_MEMORY; goto done; }
        TRY(UmiBankReviewDescribe(review, text, UMI_BANK_REVIEW_TEXT_CAPACITY, NULL));
        puts(text);
    }
    TRY(UmiBankOperationsExecuteReviewed(bank, &maker, review, &receipt));
    UmiBankReviewDestroy(review); review = NULL;
    TRY(Command(bank, &command, UMI_BANK_TRANSFER_APPROVE, "invoice-payment"));
    TRY(UmiBankOperationsReview(bank, &checker, &command, &review));
    TRY(UmiBankReviewSnapshotRead(review, snapshot));
    if (snapshot->hasJournal || snapshot->accountCount != 0U) { status = UMI_STATUS_INTERNAL_ERROR; goto done; }
    TRY(UmiBankOperationsExecuteReviewed(bank, &checker, review, &receipt));
    puts("Approval changes the transfer state, not the booked balances.");
    UmiBankReviewDestroy(review); review = NULL;
    TRY(Command(bank, &command, UMI_BANK_TRANSFER_EXECUTE, "invoice-payment"));
    TRY(UmiBankOperationsReview(bank, &maker, &command, &review));
    TRY(UmiBankOperationsExecuteReviewed(bank, &maker, review, &receipt));
    TRY(UmiBankOperationsBalance(bank, "supplier-gbp", &balance));
    if (balance.booked.minor_units != 25000) { status = UMI_STATUS_INTERNAL_ERROR; goto done; }
    puts("Local posting: Workshop GBP 750.00; Supplier GBP 250.00.");
    puts("Practice complete. Memory only; no bank network or real payment was used.");
done:
    if (status != UMI_STATUS_OK) fprintf(stderr, "Lesson failed: status %d\n", (int)status);
    free(text); free(snapshot); UmiBankReviewDestroy(review); UmiBankOperationsDestroy(bank);
    return status == UMI_STATUS_OK ? 0 : 1;
}
#undef TRY

8. Understand a refusal before retrying

What you seeNext step
No current reviewReview the current form. Merely returning to the old amount does not restore the discarded review.
State changed / busyReload committed data, inspect the new state, prepare another review and decide again. Do not loop automatically on the old command.
Permission deniedCheck the practice role and maker/checker separation. Changing the role invalidates the review.
Invalid state / insufficient fundsInspect booked, reserved and available amounts and the current transfer state. Do not assume approval is execution.
Stored data failed validationStop, close the workspace and preserve the database for investigation. Do not edit its event rows, revision or schema to force acceptance.
Record limit reachedThis evaluation profile retains at most 64 records per catalogue and 256 accepted events. Keep it as evidence and begin a separate practice history using the appropriate test environment; do not delete old events.
SQLite unavailableUse a build with the SQLite backend for the persistent GUI. The service does not silently substitute memory storage.

The history check catches changed, missing or extra stored event records before a new append. It does not restore corrupted data or prove that a database is authentic. A historical idempotent receipt can still be returned from the loaded cache. All banking calls on one handle must be serialised, and every user must stop before its owner destroys it.

This update adds review and integrity checks, not authenticated banking, payment-network connectivity, product pricing, fees or interest. Those remain separate roadmap work. Existing Paper/Live broker inspection is unchanged and does not become a payment channel.

Exercises and answers

Exercise 1. Review GBP 250.00 and close the window before submitting. What should happen to the available balance? Answer: nothing; a review does not create a reservation.

Exercise 2. A transfer has been submitted and approved. Why is the supplier balance still zero? Answer: the local execution command has not yet posted its journal.

Exercise 3. Another handle accepts a hold after your review. Should your old prediction be applied automatically? Answer: no. Its history is stale; reload and review again.

Exercise 4. Change the memory lesson amount, build and rerun it. Adjust the independent expected values deliberately, rather than weakening the checks. Explain the distinction between a passing assertion and proof that a real bank accepted a payment. Answer: assertions test this local model only; there is no bank connection in the lesson.

Exercise 5. Why compare canonical event text rather than the bytes of a C structure? Answer: structures can contain padding. The established encoding identifies the fields that belong to the event contract.

Keep the example, its source revision and your test output together. Never put personal customer data, credentials or real account output into a public learning project.
