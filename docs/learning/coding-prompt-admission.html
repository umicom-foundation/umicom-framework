Build a provider request without publishing a partial prompt

A coding task, its selected files, and its owned file contents describe different stages of a workflow. Prompt construction joins them into the provider-neutral UmiAiRequest. Treat this join as a public data boundary: a ready flag alone cannot establish that the records agree.

1. Validate each input using its owning service

  1. Check selected-file metadata through UmiAiCodingMaterializationPlanValidate.
  2. Check the complete coding request through umi_ai_coding_request_validate. This covers fields that materialization does not use, such as the instruction and request ID.
  3. Validate the runtime configuration, including its finite temperature and provider kind.
  4. Validate the materialized context, including lengths, text hashes and token totals.

These checks reuse Framework services. Studio and other applications should not create separate versions of the same path, capacity or numeric rules. See owned repository context and configuration domains for the underlying contracts.

2. Check that the records belong together

The context revision must match the plan revision. Every included path must occur in the selected plan, with the same language and token estimate. Its active-file marker must match the request's active path. Included and skipped counts must account for the selected files.

For example, a valid context containing src/unselected.c is still unsuitable for a plan that selected only src/main.c. Prompt construction returns INVALID_STATE instead of silently sending the unrelated text. A skipped file is allowed when the context records the omission.

A matching revision and path are provenance checks. They are not signatures, a new privacy decision, proof of a filesystem boundary, or permission to invoke a remote provider. The execution service still applies its own current policy.

3. Use a byte span for feedback from another component

A byte span is a pointer plus an explicit length. It does not require a trailing zero byte. The new entry point accepts feedback in that form:

const char feedback[] = {'r', 'e', 't', 'r', 'y'};
UmiStatus status = UmiAiCodingBuildProviderRequestWithFeedback(
    plan, context, config, feedback, sizeof feedback, request);
if (status != UMI_STATUS_OK) {
    /* request still contains its previous complete value. */
    return status;
}

Include umicom/ai_coding_runtime/prompt.h. In this fragment, the plan, context and config point to live records prepared by their Framework services; request points to a writable existing UmiAiRequest. Use the focused regression fixture for a complete memory-only example.

Zero-length feedback may use a null pointer. Nonempty feedback must provide exactly the declared readable bytes and contain no embedded zero. Framework copies the bytes and supplies its own terminator. A length above the total possible message storage is refused before reading that span.

The existing umi_ai_coding_build_provider_request remains available for a null pointer or a valid terminated C string. Its scan stops once the feedback cannot possibly fit a request. Use the length-aware form for input buffers whose size is already known.

4. Keep construction separate from publication

A request owns up to 64 messages, with 2,048 bytes of storage per message text and 128 bytes per message name. These are byte capacities, including terminators, rather than model token limits. A long selected path can fit the context representation but fail the smaller message-name capacity.

Framework allocates a candidate request on the heap, constructs every message, and copies it to the caller only on success. A late message-capacity failure therefore preserves the previous request. Feedback may even borrow text from that previous request because publication occurs after all input reads.

The established order remains: coding policy, modification protocol when applicable, instruction, optional active selection, selected file text, then validation feedback. Source and feedback text now split at complete UTF-8 scalar boundaries. See Unicode prompt text for validation and exact byte preservation. Normalization, grapheme segmentation and model token accounting remain separate concerns.

5. Inspect a failure before retrying

ResultWhat to inspect
INVALID_ARGUMENTRequired pointers, terminated inline fields, request domain rules, configuration and the supplied feedback span.
INVALID_STATEMaterialized content integrity and agreement between context and selected plan.
CAPACITY_EXCEEDEDToken-estimate overflow, message count, feedback size or message-name capacity.
OUT_OF_MEMORYThe candidate request or owned feedback could not be allocated; retain the prior request and retry according to application policy.

Do not resolve a provenance failure by changing only a revision number. Rebuild context from the intended selected plan. Do not hide capacity failures by truncating paths or silently discarding source text; let the caller choose a smaller, explicit selection.

6. Qualify the contract without invoking a model

# From the Framework source root after configuration with testing enabled:
cmake --build build/windows-ucrt64-debug --target umicom-ai-coding-prompt-admission-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework\.ai\.coding-prompt-admission\.' --output-on-failure

The 39 scenarios cover malformed inputs, selection provenance, byte feedback without a terminator, feedback borrowed from the previous output, embedded zero refusal, message and path limits, active selection, empty files, skipped files and existing message order. They allocate only memory and do not execute a provider. Expected result: all selected cases pass. Authored and registered cases still require native execution before a pass can be claimed.
