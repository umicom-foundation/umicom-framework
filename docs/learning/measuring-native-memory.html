Measure memory in your native application

Before changing a program to make it smaller or faster, record what it actually uses. This lesson builds a small C program that observes its own memory before an allocation, while using it, and after releasing it. The program uses Umicom Framework's shared service and retains no growing sample history.

Read bits and bytes, your first C program and allocation ownership first. You need an installed Framework SDK containing desktop_system, a compatible C23 compiler and CMake. The lesson uses the existing approved Umicom branding helper for its executable icon.

1. Name the quantity before comparing it

QuantityMeaningDo not assume
Resident memory / Windows working setMemory currently resident in physical RAM for the process, including applicable shared pages.It is not identical to your live malloc requests or exclusively owned memory.
Peak resident memoryThe process's reported resident high-water mark.It does not reset when you start a new application operation.
Private committed memoryWindows memory-manager commitment for private process memory.Committed memory need not all be resident in RAM at that instant.
Requested buffer bytesThe amount your program asks an allocator to provide.It excludes allocator overhead, other libraries, mapped files and devices.

Umicom stores all these reported sizes in bytes. A KiB is 1,024 bytes; a MiB is 1,048,576 bytes. Linux getrusage reports maximum RSS in KiB, so the adapter checks the conversion to bytes. See the Linux resource-usage contract. Windows fields are already measured in bytes; Microsoft's memory-counter documentation distinguishes working set from private commit.

2. Ask only about the current process

UmiDesktopSelfMemoryCapture observes the program calling it. It does not scan another application, inspect credentials, query model contents or require a background monitoring loop. Windows uses its current-process pseudo-handle; that borrowed handle is not closed. Linux reuses the Framework's existing bounded process-stat reader and obtains its peak through getrusage.

On Windows, resident, peak resident and private committed metrics are supplied together if the native query succeeds. On Linux, resident memory is required, peak is optional, and private committed remains unknown. Unsupported hosts return NOT_IMPLEMENTED. A failure leaves the caller's previous output untouched.

Each sample has known_metrics bits. A bit is a numbered yes/no flag. Check the relevant bit before reading a metric: zero storage with a missing bit means unknown, not a measured zero. Linux snapshots are not atomic, so separate fields may reflect slightly different instants.

If an application starts a separate model server, sampling the application does not measure that server. Keep each process's identity and measurements separate. Device memory also requires its own backend-specific observation.

3. Understand the complete example

The complete source is examples/self_memory/main.c. It performs these steps:

  1. Capture and print a starting sample.
  2. Allocate exactly one MiB and check whether allocation succeeded.
  3. Write to the allocation, so the program actually uses it.
  4. Capture a second sample while the allocation is owned.
  5. Release the allocation even if the second capture failed.
  6. Capture a final sample and compare it with the first.
  7. Check output delivery and return a nonzero exit status if an operation failed.

The writes use a volatile view so an optimizing compiler keeps the demonstration's accesses. This is a teaching workload, not a recommendation to use volatile for ordinary buffers or thread synchronization. The allocation owner remains the original pointer and is released once.

before sample → allocate → touch bytes → during sample
                                      → release → after sample
                                                 → compare identity and metrics

The Framework does not promise that the after-release number returns to the first number. Allocators may retain free pages for reuse; libraries and printing may allocate; the operating system may change page residency. The lifetime peak normally stays high even after the allocation is released.

4. Build using an installed SDK

  1. Open PowerShell and create a folder for your learning project. Copy the example's main.c and CMakeLists.txt into it.
  2. Locate the installed SDK that contains the new header and library. Replace C:/umicom-sdk below with that exact existing directory. A source checkout is not an installed SDK.
  3. Use a fresh build folder when changing SDKs or compilers. The example rejects a cached package outside the requested SDK prefix.
  4. Run each command separately and stop on errors. These commands are instructions for your machine; the guide itself is not execution evidence.
Set-Location "C:\learning\memory-observation"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B build -G Ninja -DUMICOM_EXPECTED_SDK_PREFIX=C:/umicom-sdk -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --no-tests=error --output-on-failure
& ".\build\umicom-memory-observation.exe"
$LASTEXITCODE

The example requests the installed desktop_system component and links Umicom::desktop_system. It also checks the SDK environment and layout and applies the approved Windows icon. If a required runtime DLL is missing, use the SDK's documented runtime deployment workflow; do not copy unrelated DLLs into Windows system directories.

Expect headings for Before allocation, During allocation and After release. Actual byte counts vary. unknown is an intentional result for an unavailable metric. The final direction is -1 for a decrease, 0 for no change and 1 for an increase; its magnitude is an unsigned byte count.

5. Add a sample to an existing C application

#include "umicom/desktop_system/self_memory.h"

UmiSelfMemorySample sample = {0};
UmiStatus status = UmiDesktopSelfMemoryCapture(&sample);
if (status == UMI_STATUS_OK &&
    (sample.known_metrics & UMI_SELF_MEMORY_RESIDENT) != 0U) {
    /* Copy sample.resident_bytes into a bounded diagnostic record. */
}

This fragment belongs inside a checked application operation. Do not poll continuously on a UI thread: native queries can block. Use the application's existing worker and a deliberate bounded interval. The service creates no recurring job and retains no sample list for you.

Use UmiDesktopSelfMemoryCompare on two samples from the same host and process lifetime. It checks provider, PID, creation marker and timestamp ordering. A PID is a process identifier, but operating systems reuse it after a process exits; the creation marker prevents a new process from being treated as the old one. The caller still owns host and operation-stage provenance.

Only metrics known in both samples are compared. If there are none, the comparison returns UNAVAILABLE. A decreasing lifetime peak is refused as inconsistent evidence. Magnitudes are calculated with ordered unsigned subtraction, so values larger than a signed 64-bit range do not overflow a signed delta.

6. Diagnose a suspected leak carefully

  1. Record the application revision, compiler, OS, backend and model digest, along with context size and concurrency.
  2. Capture a baseline after ordinary startup has settled.
  3. Run one controlled load/request/cancel/unload cycle and wait for owned work to finish.
  4. Capture another sample at the same lifecycle point. Repeat a bounded number of times using the same workload.
  5. Track retained objects, tasks, threads and handles alongside memory. A working-set number alone cannot show which owner failed to release something.
  6. Use the existing sanitizer/debugger qualification workflow to investigate suspicious retention. Do not treat a successful smoke test as leak freedom.

When comparing a Python application with a C implementation, keep the model and inference backend equivalent. For example, llama-cpp-python wraps the native llama.cpp API. Replacing the orchestration language may change overhead, copying and lifetimes, while the numerical backend and model's intrinsic memory needs remain similar. Measure the result.

7. Practice and verify

The Framework checks cover publication failures, missing metrics, PID reuse, timestamp reversal, unsigned extremes, native unit conversion and real self-process sampling. From the Framework checkout, after configuration:

cmake --build .\build\windows-ucrt64-debug --target umicom-self-memory-test umicom-self-memory-native-test umicom-self-memory-host-test umicom-self-memory-example-test
ctest --test-dir .\build\windows-ucrt64-debug --no-tests=error --output-on-failure -R "^framework[.]desktop_system[.]self_memory"

The Windows selection contains 32 cases; Linux contains 33 because its optional-peak behavior has an additional case. Other hosts have explicit unsupported behavior and a different selection. Record actual results and skipped coverage separately.
