Close input handles without losing the original failure

1. Two operations can fail in one request

A file operation includes opening a handle, checking metadata, reading bytes, processing them and closing the handle. If processing reports cancellation and closing also fails, there are two failures. Replacing the cancellation status with a generic close error hides the reason work stopped.

Framework's bounded input services always attempt to close their owned native handle. They retain an earlier failure status. If everything succeeded until close, a close failure changes the final result to UMI_STATUS_IO_ERROR.

The single status value reports the first failure; it is not a complete list of every cleanup diagnostic. This policy does not turn failed cleanup into success.

2. Keep cleanup outside the success condition

/* Windows */
if (!CloseHandle(file) && status == UMI_STATUS_OK)
    status = UMI_STATUS_IO_ERROR;

/* POSIX */
if (close(file) != 0 && status == UMI_STATUS_OK)
    status = UMI_STATUS_IO_ERROR;

The close operation is the left operand, so it always runs when control reaches cleanup. Reversing the operands would short-circuit the expression when status already holds a failure and could skip closing the handle. The ordering protects both resource ownership and error attribution.

3. Choose the right bounded input contract

UmiInputFileRead allocates a complete owned buffer under the caller's byte limit. The buffer includes one trailing NUL byte, but embedded NUL bytes remain valid binary data. Failure clears the output pointer and size. Release a successful buffer with UmiInputFileFree.

UmiInputFileVisit reads through a 64 KiB stack buffer and calls a synchronous visitor for each borrowed chunk. This suits large model files, hashing and other incremental consumers. The visitor must not close the reader's handle or retain a chunk pointer after returning. Its failure status stops further reading.

static UmiStatus Consume(const unsigned char *bytes, size_t count, void *context)
{
    Candidate *candidate = context;
    return ProcessCandidateBytes(candidate, bytes, count);
}
/* Candidate and ProcessCandidateBytes are application-specific here. */
uint64_t observed = 0U;
UmiStatus status = UmiInputFileVisit(path, byte_limit, Consume,
    &candidate, &observed);
if (status == UMI_STATUS_OK) {
    PublishCandidate(&candidate);
} else {
    DiscardCandidate(&candidate);
}

The example shows ownership flow rather than a complete program: Candidate and the three processing functions belong to the consuming service. A visitor may receive bytes before a later I/O or metadata-change failure. Publish the candidate only after the entire visit returns OK. A failed visit clears outSize; it cannot undo effects a callback already made elsewhere.

4. Understand what the native reader checks

Both services require an ordinary absolute path and a regular final file, refusing final links or reparse points. Parent aliases may still be followed. Windows paths are converted from UTF-8 for native file access. Keep parents trusted; these functions do not provide a filesystem sandbox.

The reader checks size before consuming the observed file and compares metadata through the same handle afterward. A changed size or timestamp can reject the observation as BUSY. That is useful evidence, not a guarantee against every concurrent writer or an immutable snapshot.

Reading is synchronous and can block. Use an application's existing worker service when integrating it into an interactive product. A streaming callback may return CANCELLED, but it cannot interrupt an operating-system read already in progress.

5. Exercise paired failures deliberately

  1. Read a small known file successfully and verify its exact bytes.
  2. Report a close failure after successful reading. Expect IO_ERROR and no successful output publication.
  3. Set the limit below the file size and also report a close failure. Expect CAPACITY_EXCEEDED.
  4. Refuse allocation in the whole-file reader, then fail close. Expect OUT_OF_MEMORY with a NULL output buffer and zero size.
  5. Return CANCELLED or another failure from the streaming visitor, then fail close. Expect the original visitor status and no further callbacks.
  6. Simulate changed final metadata and a close failure. Expect BUSY.
  7. Check that the real native handle was closed exactly once in every case.

The regression fixture closes the actual handle before simulating a close error. Its metadata hook changes only the returned observation, leaving the fixture bytes untouched. These controlled failures make otherwise rare paths repeatable without leaving handles open or corrupting files.

cmake --build build --target umicom-input-cleanup-status-tests
ctest --test-dir build -R "^framework[.]input_cleanup_status[.]" --output-on-failure --no-tests=error

Replace build with your configured directory. The suite registers twenty-seven cases for whole-file and streaming reads. The Windows and POSIX implementations need qualification on their respective hosts. Successful configuration and authored tests alone are not compiler or runtime evidence.

Exercises

  1. Explain why checking status before calling close can leak a handle.
  2. Design a candidate object for streaming model validation that has no externally visible effects before publication.
  3. Explain why a byte limit and a metadata comparison do not create a filesystem sandbox.
  4. Separate three questions when diagnosing a failed read: what stopped the work, whether cleanup ran, and whether any partial result was published.
