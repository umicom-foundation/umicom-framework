Run source analysis through an owned background job

1. Move the work, preserve its owner

Source scanning can spend time traversing directories and reading files. Running that work inside a button callback blocks the event loop. Framework's UmiCodeGuardJob uses the existing task queue so applications can schedule scanning without implementing another thread system or copying scanner rules.

A job is a one-shot owner. Creation copies the profile and resolves the workspace root to an absolute lexical path. Submission lends the job's copied input to a queue worker. The worker creates private findings. A successful terminal job can transfer that result exactly once to its creating thread.

The synchronous service remains available and unchanged in purpose. The job does not automatically update a Studio panel, install a menu command or change an application's retained report. Those are host responsibilities after a checked transfer.

2. Create and submit on the owner thread

UmiCodeGuardJob *job = NULL;
UmiCodeGuardProfile profile = umi_codeguard_profile_security();
UmiStatus status = UmiCodeGuardJobCreate(workspace, &profile, &job);
if (status == UMI_STATUS_OK)
    status = UmiCodeGuardJobSubmit(job, application_queue);

This fragment assumes workspace and application_queue already belong to the host. NULL profile selects defaults. The job rejects empty or unrepresentable roots, never silently truncates them. It freezes lexical path identity at creation; it does not resolve every link, check that the directory exists, or create a content snapshot.

A full or stopping queue refuses submission without cancelling a newly created task. The host can retain that created job for another suitable queue or destroy it. Once accepted, keep the job alive while it is queued or running. The queue retains a task reference; it does not separately own the job's payload.

3. Poll values rather than borrowing worker storage

UmiCodeGuardJobSnapshot snapshot;
UmiStatus status = UmiCodeGuardJobRead(job, &snapshot);
if (status == UMI_STATUS_OK && snapshot.status == UMI_STATUS_BUSY) {
    /* Keep the prior report visible and let the event loop continue. */
}

The snapshot contains plain values: task state, effective status, original worker status, whether the operation returned, availability of an owned result and a completed summary. It contains no finding pointer that another thread may still mutate. Reading does not wait for analysis to finish, although mutex acquisition and scheduling are not real-time guarantees.

Create, submit, take and destroy belong to the creating thread. Another thread may request cancellation or read a snapshot only while it holds a live job borrow and destruction is excluded. The job itself is not a reference-counted lifetime object.

4. Distinguish an operation failure from task cancellation

The task service classifies a task as cancelled if its token was requested before completion. The scanner can also report a concrete failure at the same time, such as an I/O error. A single cancellation label must not hide that cause.

Cancelled before dispatchCANCELLEDCANCELLED; operation_completed is false

UmiCodeGuardJobCancel is cooperative and does not wait. It cannot interrupt an operating-system read. Do not free a running job immediately after requesting cancellation: continue observing its terminal state first.

5. Transfer and publish a complete result

UmiCodeGuardResult *candidate = NULL;
UmiStatus status = UmiCodeGuardJobTake(job, &candidate);
if (status == UMI_STATUS_OK) {
    status = umi_codeguard_result_swap(retained_result, candidate);
    umi_codeguard_result_destroy(candidate);
}
/* On failure, retain the previous complete report and show attempt status. */

The host must own retained_result and serialize access to it. Take leaves its output untouched on failure or BUSY. A successful empty result is valid and replaces old findings with an empty report. After transfer, the result belongs to the host and survives job destruction. A second take returns NOT_FOUND.

Swapping transfers owned finding arrays without allocation. Finding borrows from the old report now belong to the candidate being destroyed; update the UI's borrows only at this publication boundary. Failure never promotes a partial candidate into the current report.

6. Destroy only after work has released its borrow

UmiStatus status = UmiCodeGuardJobDestroy(&job);
if (status == UMI_STATUS_BUSY) {
    /* Keep job alive, request cancellation if appropriate, then poll again. */
}

Successful destruction clears the owned pointer. Queued or running work returns BUSY without releasing its payload. Exclude other snapshot readers and cancellers before destroying a terminal job. The operation does not join or shut down the application's shared queue.

The independent SDK example includes a console background client. A console can drain and join its private queue before taking the result. An interactive host should use its existing event-loop and queue-shutdown services rather than blocking the GUI thread.

7. Qualify ownership and actual analysis separately

  1. Change caller input after Create and verify the job still uses the copied profile and original absolute root.
  2. Hold a real worker behind a condition gate. Verify Take and Destroy report BUSY while the callback is running.
  3. Fill a queue, refuse a job, then submit the same created job successfully after space becomes available.
  4. Request cancellation before dispatch, during scanning and after private result storage but before task completion. No cancelled candidate may transfer.
  5. Combine a worker failure with cancellation and verify the original failure remains visible.
  6. Transfer once, destroy the job and continue using the independently owned result.
  7. Run a real directory scan through a queue and compare findings with the synchronous scanner. Check a missing root, an oversized file and successful empty input.
