A research program should be able to explain not just its final result, but the sequence that produced it. This lesson uses eight fictional quotes and a short C strategy. You will see a decision, the later quote that can fill it, the fee, the resulting position and the final result.

Nothing in this exercise connects to a broker, sends a real order or writes an account balance. The calculations are an inspectable research model, not a forecast of investment returns. You do not need a market-data subscription to complete the lesson.

1. Meet the three parts of the exercise

An observation is a quote at a recorded time. The bid is the price used here when selling; the ask is the price used here when buying. Their difference is the spread. Each observation also carries a sequence number and available sizes.

A strategy is a C function that examines the current observation and asks for a target position: long, short, flat, or hold the existing instruction. A long position benefits from a price rise; a short position benefits from a fall. This example uses only long and flat.

The replay owner holds a copied dataset, steps through it in order and applies the selected fill model. It does not accept a decision and fill it using the quote the strategy has already examined. The earliest possible fill is the next observation, and only after the configured delay and size check.

The flow is previous instruction → possible fill → current view → new strategy decision. Keeping those stages separate makes it possible to ask whether a result depended on information that was not yet available.

2. Build the practice program

Merge the source delivery into the matching Framework directory first. The complete suite commands are in Build-and-Git.md. For an isolated practice build, open PowerShell and run:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\examples\research_replay" `
    -B ".\build\research-replay" `
    -G Ninja `
    -DCMAKE_BUILD_TYPE=Debug `
    -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe"
if ($LASTEXITCODE -ne 0) { throw "Configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\research-replay" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\research-replay" `
    --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "A test failed." }

This builds the real canonical quote and backtest sources needed by the exercise, not the entire installed product family. A successful result here does not replace a full Windows application build. The new workflow is a native command-line tool and a reusable library; this delivery does not add a new Trader or Studio window.

3. Run the eight-quote example

$Replay = ".\build\research-replay\bin\umicom-research-replay.exe"
& $Replay demo
if ($LASTEXITCODE -ne 0) { throw "The demonstration failed." }

The program prints a trace followed by a summary. Its default settings are 10,000 units of initial simulated equity, one unit per position, a 0.10 fee per executed side, zero extra slippage and zero additional latency. Even at zero latency, an instruction cannot fill on the observation that created it.

The rule in strategy.c asks for a long position when the midpoint is below 100 and asks to become flat when it is above 102. Those numbers are chosen to make the lesson easy to inspect. They are not a suggested trading strategy.

Observation What the example does
1 Midpoint 99.50 produces a request to become long. No fill occurs yet.
2 The request buys at ask 101.00 and pays 0.10.
3 Midpoint 103.50 produces a request to become flat.
4 The request sells at bid 104.00 and pays another 0.10.
5–8 A second cycle buys at 100.00 and sells at 102.00.

For the first completed trade, (104 − 101) × 1 − 0.10 − 0.10 = 2.80. The second contributes 1.80. The completed example therefore reports 4.60 closed net P&L, 0.40 total fees and 10,004.60 marked equity, with no open position or pending instruction.

P&L means profit and loss. These are the outcomes of this particular fictional input and fill model. They do not measure the quality of a live strategy.

4. Understand the trace rather than just the total

fill_units is signed: positive means buying and negative means selling. A zero means no execution occurred on that observation. position is −1, 0 or +1; the configured units determine its size.

pending tells you whether there is still a request awaiting execution. target matters only when pending is true. An instruction can remain pending because its latency has not elapsed or the displayed size is insufficient. This model makes no partial fill: the whole required quantity must be available. Reversing directly from long to short requires two units of sell-side capacity when the position size is one.

equity includes the open position marked at bid for a long or ask for a short, less fees already paid. It is not a cash-account ledger. The model has no margin, borrowing costs, tax, corporate actions or multi-currency conversion.

After buying at 101 on observation 2, the bid is only 100. The immediate marked result therefore includes the spread and the entry fee. It is normal for equity to fall at entry even when no completed trade has yet been recorded.

5. Compare the delay assumptions

& $Replay sweep
if ($LASTEXITCODE -ne 0) { throw "The comparison failed." }

The command runs three independent instances with delays of 0, 100 and 200 milliseconds. It uses the same observations and the same C rule in each instance. There is no ranking or automatic selection of a winning strategy.

Delay Completed trades Closed net P&L Final marked equity Final state
0 ms 2 4.60 10,004.60 Flat, no pending request
100 ms 2 4.60 10,004.60 Flat, no pending request
200 ms 1 −6.20 9,991.70 Long, with a pending request

The longer delay changes which quote can fill an instruction. Notice that the 200 ms run has processed every input but still holds an open position. Completed replay means all selected observations were processed, not that all positions were liquidated. The program does not invent a final sale to make the report look complete.

A useful comparison therefore includes costs, open positions and unfilled requests, not only closed profit.

6. Read a quote file

The included quotes.csv contains the same eight observations. The exact header is:

sequence,time_ms,bid,ask,bid_size,ask_size
1,0,99,100,10,10
2,100,100,101,10,10

Run it explicitly:

& $Replay csv ".\framework\examples\research_replay\quotes.csv"
if ($LASTEXITCODE -ne 0) { throw "The input or research run was rejected." }

The command reads the selected ordinary file and writes results to the terminal. It does not overwrite an output file. Use a copy of the CSV for exercises, outside the source repository.

Rows must contain exactly six unquoted fields. Decimal numbers, decimal exponents, LF and CRLF line endings are supported. Comments, blank rows, byte-order marks, embedded zero bytes, quoted fields, hexadecimal numbers and non-finite values are rejected. The C numeric locale must use a full stop; the library does not change locale behind the caller's back.

Sequence numbers must be consecutive and nonzero. Times must be nonnegative and cannot move backwards. Equal timestamps are permitted because sequence order still distinguishes observations. Replay does not sort a broken file or silently fill a sequence gap.

The CLI labels imported rows with the generic WORKSHOP / PRACTICE / GBP identity. It is a teaching importer, not an instrument-master lookup. Applications using the C API supply their own consistent canonical instrument. Only one instrument and a multiplier of one are supported in this profile.

7. Change the C strategy in Studio

Open framework/examples/research_replay/strategy.c in Studio. PracticeStrategy receives a borrowed UmiResearchView, a pointer to its threshold settings, and an output target. It returns a Framework status.

The view contains the current quote, its index, the current position, equity and pending instruction. It does not hand the callback the future dataset. A trusted callback could still obtain outside information or do other work; this is an interface discipline, not a security sandbox.

HOLD preserves a pending request. Repeating a new directional target replaces the previous instruction and restarts its latency. That is why the example returns HOLD while an instruction is waiting. Once the position is already at a requested target, requesting that target cancels any conflicting pending instruction.

The library owns its copied observations and trace. The application owns the callback's user data and must keep it alive until the replay is destroyed. Do not destroy or re-enter the replay from inside its callback.

Try changing the entry and exit thresholds in main.c, update the strategy tag to describe the changed example, rebuild and compare the trace. A strategy tag is only a caller-supplied label. It is not a verified hash of the compiled code.

8. Step, pause and cancel through the C contract

Create a run with UmiResearchReplayCreate. It validates and copies the whole input before returning a handle. UmiResearchReplayStep commits one observation. UmiResearchReplayRun commits up to a supplied observation budget. Calling neither function pauses progress naturally; there is no hidden timer.

UmiResearchReplayCancel ends an active run between calls. A cancelled run remains inspectable but cannot resume. Create a new run with freshly initialised strategy state to start again. All methods are synchronous and single-owner. A UI can schedule small budgets or give a worker sole ownership, but concurrent calls on the same handle are not supported.

A callback error or arithmetic failure puts the run into FAILED. The current candidate step is not published, so its tentative fill does not appear in the committed trace. Callback side effects outside the library cannot be undone. The failure is terminal rather than automatically retrying possibly changed strategy state.

Take a copied snapshot with UmiResearchReplaySnapshot and read committed rows with UmiResearchReplayTraceAt. Destroy the replay after callers have stopped using it. No database or live market authority is involved.

9. Read the fingerprint correctly

Every run records a SHA-256 fingerprint of its canonical instrument, observations, numerical configuration, fill-model identifier and caller-supplied strategy tag. Padding bytes and unused string storage are excluded. Numerical fields use an explicit binary64 representation and fixed byte order.

Changing an observation or a cost assumption changes this fingerprint. Stepping the same input in different-sized batches does not. The fingerprint is not a digital signature, an entitlement to external data, or an attestation of the strategy binary. Save the actual source/compiler/build identity separately for more demanding research.

Repeated runs were checked under the delivery's compiler configurations. Bit-for-bit equality across every processor, compiler optimisation mode or floating-point environment is not promised.

10. Why a rejected calculation must leave the old result alone

The shared completed-trade accumulator now rejects NaN and infinity, checks counter and floating-point overflow, and validates a candidate before replacing the previous state. A failed trade therefore cannot quietly increment the trade count while leaving invalid equity behind.

Its public interface and earlier metric conventions remain available. For compatibility, the old accumulator counts zero-net trades as wins and retains its old no-loss profit-factor sentinel. The new replay snapshot supplies profitFactorAvailable; do not interpret a legacy sentinel as a measured ratio. The new marked drawdown percentage uses each drawdown's contemporaneous peak rather than treating a later peak as the denominator.

11. Practise and check your answers

Exercise A: Change sequence 4 to sequence 5 in a copied CSV. Does the run sort the data or reject it? Answer: It rejects the broken continuity before beginning the replay.

Exercise B: Reduce observation 2's ask size to 0.5. Can a one-unit buy partially fill? Answer: No. This profile waits for enough displayed size. The later execution price can therefore change.

Exercise C: Add a long signal on the final observation. Does it fill at that observation's ask? Answer: No. It remains pending because there is no later observation.

Exercise D: Cancel after three steps. Is the trace empty? Answer: No. The three committed observations remain inspectable. Cancellation does not erase completed work or pretend the remaining data was processed.

Exercise E: Increase the price-impact setting by ten basis points in a copied C experiment. Should you subtract that cost again from closed P&L? Answer: No. The adverse price adjustment is already in the fill prices. The separately displayed slippage amount explains the effect rather than charging it twice.

12. Boundaries and next steps

There can be at most 65,536 observations in one copied run and at most 16 MiB in a CSV input. This is a full-fill, single-position, single-instrument research model. It does not simulate queue priority, partial fills, broker rejects, live latency distributions, session calendars or instrument-specific financing.

The example source, tests and installed-SDK client make a practical starting point for further work. They do not replace the existing market tape, strategy services, live risk authority or Trader GUI. Keep real provider connectivity and any privileged operation separately controlled.

No GUI, Windows runtime or full application-suite pass is claimed by this guide. Build and exercise those targets on the intended host before marking an integrated product release as qualified.
