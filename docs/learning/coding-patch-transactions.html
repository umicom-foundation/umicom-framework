Understand failed patch transactions

Applying an AI-proposed patch means asking a host to change several files. A write can fail after changing part of its file. Trying to restore earlier content can also fail. A single error code cannot tell a user which writes were attempted and whether restoration was observed.

Framework exposes UmiAiCodingPatchApplyWithReport and UmiAiCodingPatchRevertWithReport. They retain the primary failure as the return value and publish a separate transaction report. The existing apply and revert interfaces call the same service and keep their primary status behavior.

1. Separate admission, verification and mutation

  1. Admit the patch metadata, policy, revision and adapter before invoking callbacks. An invalid input leaves the report and patch unchanged.
  2. Check all current files against the reviewed before-content for apply, or after-content for revert. A conflict stops before the first mutation.
  3. Apply files in forward order. Revert them in reverse order.
  4. If a mutation callback fails, compensate that file too: a failure status does not prove it made no change.
  5. Continue compensating the earlier completed mutations in reverse order, recording every compensation failure.
  6. Read every affected file through the adapter after compensation. Record these restoration checks separately from callback success.

2. Keep the original failure

#include <umicom/ai/coding_patch.h>

UmiAiCodingPatchTransactionReport report = {0};
UmiStatus status = UmiAiCodingPatchApplyWithReport(
    reviewed_patch, &policy, &workspace_adapter, &report);
if (!report.admitted) {
    /* No complete transaction report was published; handle admission status. */
    return status;
}
/* Present report.primary_status and the separate recovery observations. */

The snippet assumes the host owns a reviewed patch, policy and workspace adapter. It does not create approval or provide filesystem containment. The host adapter remains responsible for workspace paths, permissions, stable access and the lifetime of its callback data.

Initialize a fresh report to zero before every attempt. An admission refusal leaves it untouched, so admitted remains zero. Once execution reaches file verification, every return supplies a complete report with admitted set to one. Reusing an old report without clearing it would retain its old admitted flag and mislabel a later refusal. Keep all operations on the serialized owner thread.

FieldInterpretation
admittedOne for a complete report. A freshly zeroed report remains zero on admission refusal.
primary_statusThe verification or mutation error returned by the operation, or OK.
failed_file_indexThe affected patch file index; SIZE_MAX means no file failed.
verified_filesSuccessful preflight file reads before mutation.
mutation_attempts / mutations_completedCallbacks entered and callbacks returning OK. A failed callback may still have changed a file.
compensation_attempts / compensation_failuresRecovery callbacks entered and those returning an error.
restoration_checks / restoration_failuresPost-compensation reads and those that failed or did not match the expected original state.
compensation_statusThe first compensation callback error, or the first restoration-check error if callbacks reported success.
revision_before / revision_afterThe patch observation revision. Any attempted mutation advances it once, including a failed operation.

A zero compensation error does not mean recovery occurred: also inspect the attempt counts. Readbacks establish observations through the adapter at that moment. They do not establish durable storage, prevent later external writes or make the multi-file operation atomic.

3. Do not hide a compensation failure

Suppose file one changes successfully, file two changes but returns IO_ERROR, and restoring file two returns PERMISSION_DENIED. The operation returns IO_ERROR. Its report records two mutation attempts, one completed mutation, two compensation attempts and the permission failure. Restoration checks then distinguish which expected file states can actually be observed.

On failure, the patch keeps its last committed logical state. An APPROVED or APPLIED state is not a claim that the workspace was restored. Show the failure and affected files, stop automatic retries, and inspect the workspace before another operation. A later retry still performs the ordinary conflict checks.

4. Refuse callback reentry

A host read or write callback may publish notifications. Those notifications can call back into application code. Without a guard, that code could add files to the patch or apply it a second time while the outer loop still uses it.

While a patch transaction borrows a patch, its init, add, approve, reject, apply and revert mutation APIs return BUSY for that same patch. Read-only integrity checks remain available. A nested transaction on a different patch is permitted, but it still cannot mutate any borrowed outer patch.

This is synchronous reentry admission, not a mutex. Serialize all threads that use a patch. Callbacks must return normally and must not directly edit or free the borrowed patch, report or callback data. Framework captures admitted callback slots before execution; copying function pointers does not extend the lifetime of their user data.

5. Exercise failures without touching real files

The in-memory regression adapter supports create, modify and delete operations. It can change bytes and then return an error, fail a compensation callback, fail a restoration read or call a mutation API from a callback. This permits precise recovery expectations without modifying a real project.

cmake -S . -B build/patch-transactions -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DBUILD_TESTING=ON

Run from the Framework repository, one command at a time, and stop on failure. Sixty transaction cases are authored alongside the existing admission coverage. Their registration does not establish a compiler or runtime pass.

6. Carry recovery evidence into an application

The assistant owns stored patches. Use UmiAiCodingAssistantApplyPatchWithReport and UmiAiCodingAssistantRevertPatchWithReport with an approved patch identifier rather than copying an owned patch into another mutable controller. These calls retain the service callback guard and publish the core transaction report.

UmiAiCodingPatchTransactionReport report = {0};
UmiStatus status = UmiAiCodingAssistantApplyPatchWithReport(
    assistant, reviewed_patch_id, &workspace_adapter, &report);
if (report.admitted && report.mutation_attempts != 0 && status != UMI_STATUS_OK) {
    /* Show primary_status, compensation_status and restoration failure counts.
     * Inspect the affected files before an explicitly requested retry. */
}

The assistant revision advances when the owned patch revision advances, including a failed mutation attempt. A refused input or a file conflict before mutation leaves that service revision unchanged. A revision is an observation marker, not a success flag.

Studio exposes matching UmiStudioCodingAssistantApplyPatchWithReport and UmiStudioCodingAssistantRevertPatchWithReport wrappers. Its existing patch command message shows the original error, recovery status and callback/readback failure counts after a failed mutation. The wrappers delegate to Framework; they do not implement a second recovery algorithm or approve a patch automatically.

  1. Start with a fresh, zeroed report for each request.
  2. Keep the report separate from the service, adapter and callback data.
  3. Use the returned status for the original operation. Do not replace it with a successful compensation status.
  4. If mutation was attempted and the operation failed, show recovery counts and ask the user to inspect the affected files.
  5. Refresh service-backed views after any changed revision. Do not treat a retained logical patch state as proof of restored files.

The Framework ownership regression target is umicom-ai-coding-owner-admission-test; its test filter is ^framework[.]ai[.]coding-owner[.]. Studio uses umicom-studio-coding-assistant-test and ^studio[.]coding_assistant$. The Studio fixture simulates a write or deletion that succeeds on disk and then returns an error, checking the report and restored file before a later successful operation. This coverage is authored; registration alone does not qualify the UI or filesystem workflow.

7. Read the automated agent's last patch outcome

An automated agent can apply a patch, run validation and attempt a revert. Its final run status alone does not explain which patch call changed files or whether recovery succeeded. UmiAiCodingAgentReadPatchOutcome copies the last completed call into a UmiAiCodingAgentPatchOutcome. Hosts using the composition service can call UmiAiCodingRuntimePlatformReadPatchOutcome instead.

UmiAiCodingAgentPatchOutcome outcome;
UmiStatus read_status = UmiAiCodingRuntimePlatformReadPatchOutcome(
    coding_platform, &outcome);
if (read_status == UMI_STATUS_OK) {
    /* Correlate outcome.task_id and outcome.patch_id with the user's task.
     * outcome.status is the patch call result.
     * outcome.transaction holds its admitted recovery report. */
}

NOT_FOUND means no patch call has completed for the current admitted task. Invalid arguments and missing or invalid observations leave the output unchanged, so inspect the return value before reading the output. The returned value is a copy; editing it does not change the agent.

The outcome records the task ID, patch ID, whether the call was a revert, its primary status and its transaction report. The report's admitted field may be zero when the assistant refused the call before file verification. A failed apply or revert is still a completed call and remains inspectable.

A successful patch call followed by a failed event notification has two different results: the retained patch outcome reports the successful patch, while the enclosing helper may return the notification error. Likewise, a failed validation can follow a successful apply. Never present the patch outcome as the result of the entire agent run.

Starting a new admitted task clears the previous task's outcome. A rejected start, such as an empty task ID or busy agent, preserves it. While a synchronous file callback is running, observation sees the previous completed outcome until the active patch call returns. Always compare both IDs: a newly generated patch may not have been attempted yet.

The focused target is umicom-ai-coding-agent-patch-outcomes-test, with filter ^framework[.]ai[.]coding-agent-outcome[.]. It substitutes the already-tested assistant transaction boundary and exercises actual agent/platform forwarding, notification failure, copy isolation and task reset. Its 27 cases are authored and require native qualification. This retained value is memory-only evidence; it does not prove durable storage or add a new Studio presentation workflow.
