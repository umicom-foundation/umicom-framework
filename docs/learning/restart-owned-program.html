Restart an owned program

Restart means ending one program and asking for another run. Ending a process takes time: a cancellation request is not a completed result. Framework keeps the request inside the project session that owns the program, while the frontend keeps collecting its output and completed phases.

Use Studio's existing Run menu

  1. Open a project and review its executable, working folder and workspace trust. Start the selected existing program with Run current executable, or let Build and Run reach its Run phase.
  2. Choose Run → Restart. It is available for an active program owned by that project session. It does not restart a debugger or interrupt Configure, Build or Test.
  3. Wait for the previous operation to finish. Its result is added to history before another operation is submitted. The new operation uses launch-only preparation, so unsaved drafts and source files are not saved or rebuilt.
  4. Review the new operation in Output. Queued means accepted for execution; it does not mean the program started successfully. Stop cancels a pending restart as well as the current process.

Connect another frontend

  1. Include umicom/build/run_restart.h and link Umicom::build. Keep the session alive throughout polling. Restart entry points run on the same owning thread as submission and destruction.
  2. Use UmiBuildRunRestartReview to derive control availability. Supply the current profile, current open project root and current trust decision. Review performs no cancellation or file creation.
  3. On an explicit user action, call UmiBuildRunRestartRequest with the same current inputs. This repeats admission rather than trusting an old enabled menu. A duplicate request returns BUSY. Do not request again from a timer.
  4. Keep copying completed results with umi_build_project_session_result_at and retain them in your normal history. Maintain the exact number retained for this operation.
  5. Call UmiBuildRunRestartAdvance with refreshed authority and that count. BUSY means completion or handover is still pending. A trust, project or settings mismatch clears the request. An excessive count is rejected; the session cannot verify a dishonest acknowledgement.
  6. On OK with submitted == true, reset your per-operation result counter to zero. Read the new session's output and eventual result. A failure is terminal for this intent; do not silently retry.

Preserve logs and authority

If the old operation captured a log, the new destination appends .restart-<next operation id> to its complete pathname. The same directory is used and no folders are created. Existing destinations are refused by exclusive creation. The old file stays intact, including when new-file creation fails. A run without log capture restarts without creating a log.

The admitted profile digest compares settings and project identity. It does not hash the executable, source files, inherited environment or mutable preset contents. Launch preparation checks the selected file and working directory again. Another process can still replace a file between inspection and launch; this interface is not a sandbox or executable attestation service.

The ordinary cancellation API can signal from another thread. An atomic stop signal keeps a concurrent cancellation from being lost during restart admission. If a new task was already queued, inspect its terminal cancellation result. Destroy joins the worker and never performs a deferred relaunch.

Exercise the contracts

After configuring and building a Framework test tree, run the controlled session cases. Substitute your actual build directory. Stop on a build error before running tests.

cmake --build build --target umicom-run-restart-test
ctest --test-dir build -R '^framework\.run_current\.restart\.' --output-on-failure --no-tests=error

The scenarios cover phase refusal, duplicate requests, current trust, changed settings, result handover, cross-thread Stop, disposal, missing executable and log collision. They use a controlled executor rather than a real child process. Studio's studio.first_use.gtk4.run-restart-* scenarios additionally use the native workbench and a bounded real child. Neither authored coverage nor a source review is an executed pass.

Recover deliberately

For a refused restart, retain the old result and read the current error. Restore trust only after reviewing the project, select a valid executable if it moved, or choose a new log destination through the normal launch workflow. A collision is evidence to keep, not a reason to delete a transcript automatically. Use a fresh explicit Run request after correcting the cause.
