1. Meet the three things you need

You can try an operating system without replacing the system on your computer. A virtual machine is a set of emulated hardware running as a program. Your computer is the host; the operating system inside that program is the guest.

Umicom Virtual Machine Manager keeps the machine's settings, prepares a reviewed launch and talks to QEMU through a private control channel. QEMU supplies the emulation. Umicom supplies the profile, checks, controls and connection to the rest of Framework.

Before the first guest run

This source update does not include QEMU binaries or a prebuilt Umicom OS image. You need an explicitly prepared QEMU runtime and a native image bundle from the preceding OS-image workflow. The Windows build and real guest combination must be qualified before distributing them to other people.

ItemWhat it containsWhat it does not prove
Sealed QEMU runtimeA declared emulator, qemu-img, firmware, supporting files, notices and runtime.umi.A matching hash does not identify a trusted publisher or establish licence compliance.
Native image bundleThe kernel, RAM-root filesystem and source-linked metadata produced by umicom-os-image.File verification alone does not prove a normal or recovery boot.
Saved profileA name, paths, architecture, memory, processor count and optional managed disk.Saving a profile neither reserves memory nor starts a process.

In this guide, sealed means that the runtime files have a recorded inventory and hashes. Qualified means that the chosen build has actually been tested on the stated host with the required guest and release checks. These are different steps.

Start with fictional information and a disposable practice machine. The initial profile uses TCG emulation, a serial text console and no network or shared folder. It is not yet the graphical Umicom OS desktop.

2. Build the manager and run the first lesson

Merge the full files into their matching repositories, keeping Umicom-Applications and umicomOS as sibling folders. The separate Build-and-Git.md gives the complete repository build, test and publication sequence.

After a successful build, begin with the memory-only lesson. It works without a QEMU installation or an OS image:

PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom-vm.exe" --self-test
if ($LASTEXITCODE -ne 0) { throw "QMP self-test failed." }
& ".\build\windows-ucrt64-all-debug\bin\umicom-vm-profile-example.exe"
if ($LASTEXITCODE -ne 0) { throw "Profile lesson failed." }

The first command checks an in-memory QMP reply. The second saves a profile in the real memory Data Server, loads it again and demonstrates why a stale edit is rejected. Neither command starts an emulator, contacts a server or creates a profile database on disk.

A focused Linux/WSL build is also available. Use a Linux terminal for this block, not PowerShell:

Linux terminal
OS="/mnt/c/umicom/umicomOS"
FW="/mnt/c/umicom/Umicom-Applications/framework"
BUILD="$HOME/umicom-builds/vm-manager"
cmake -S "$OS/tools/vm-manager" -B "$BUILD" -G Ninja     -DCMAKE_BUILD_TYPE=Release -DUMICOM_OS_FRAMEWORK_SOURCE="$FW"
cmake --build "$BUILD" --parallel 2
ctest --test-dir "$BUILD" --parallel 2 --no-tests=error --output-on-failure
"$BUILD/bin/umicom-vm-profile-example"

The focused build compiles the actual required Framework implementations, not the whole application suite. Its success is useful component evidence; it does not replace the Windows application build.

3. Create a practice profile

On Windows, open umicom-vm-manager.exe from the build's bin directory, or use its installed shortcut after a qualified release is installed. This is a separate application, not an extra dependency of the installer bootstrap.

The fields accept full paths. Paste paths without surrounding quotation marks into the graphical fields. Folder-browsing dialogs are not included in this version.

FieldPractice choice
Profile IDnotes-lab. Use lowercase letters, digits, hyphens or underscores.
NameUmicom OS practice machine.
Profile databaseA local SQLite file. The default is under your Local AppData Umicom folder. Its parent folder must exist.
Sealed QEMU runtimeThe directory containing runtime.umi, not the path to the executable alone.
Native image bundleThe complete bundle directory produced by the native image builder.
Managed diskLeave empty for the first diskless boot.
New run / checkpointA new directory under an existing practice parent, for example C:\Umicom-Practice\run-001. Do not create that final directory yourself.
ArchitectureMatch the runtime and image: x86-64 or RISC-V 64.
Memory MiB / CPUsBegin with 1024 MiB and 2 processors. These are guest resources, not a claim that every host can supply them.
Recovery bootLeave unchecked for normal boot. Use a separate reviewed run for recovery.

Choose Check runtime. The manager checks its declared files and exact inventory. Then choose Save profile. This records the settings through Framework's Data Server. It does not launch QEMU.

To continue a saved profile, enter its database and ID and choose Load profile before editing. A loaded revision protects you from overwriting a newer edit saved by another manager. If the revision is stale, reload and review the difference rather than forcing the save.

Small windows and high-DPI layouts have native scrollbars. Use Tab to move through controls; the form reveals the keyboard-focused control. These interface paths still need actual Windows qualification.

4. Review, start paused, then resume

Check inputsReview launchStart pausedResumeObserve

Choose Review launch. The manager validates the runtime and native image bundle, checks architecture and resource choices, and calculates a fingerprint over the selected inputs and new run location. The fingerprint is a change detector, not a signature or authenticated approval.

Choose Start paused only after checking those choices. The manager rechecks the fingerprint, creates the new run directory and launches the selected native emulator with -S. It negotiates QMP and requires an observed paused or prelaunch state. A process merely existing is not enough.

The next deliberate action is Resume. That begins guest instruction execution. Choose Read console to retrieve the serial output, and repeat while the guest starts. The initial ring buffer is bounded, so read it regularly during a noisy boot.

Refresh state queries QMP. The title bar also tracks the owned process and last observed QMP state without overwriting the previous action's error message. A state such as running means QEMU reports the guest CPUs running; it does not mean the guest finished booting, opened a database or passed its service checks.

Keep boot qualification separate

Use the native image builder's normal and recovery boot checks for source-linked boot acceptance. This interactive manager does not turn a QMP reply into a passed boot report.

Editing a launch field invalidates the review. Reusing an old fingerprint after changing memory, image or runtime must fail. Use a new run directory after an attempt; incomplete output is retained for investigation.

5. Use the console and stop deliberately

Pause requests that QEMU stop guest execution. Resume requests that it continue. Each successful request is followed by a state query. Neither operation saves a disk backup or a full machine snapshot.

The text beside Send to guest is sent to the guest's serial console, with a final newline. For the foundation recovery console, begin with help and status. It is guest input, not a Windows command box. The manager never passes it to a host shell.

To shut down that foundation guest, send poweroff and wait for the owned QEMU process to exit. The separate Request powerdown button asks QEMU to deliver a power request; a guest may ignore it. Its acknowledgement does not establish a completed shutdown.

Force stop terminates the owned process. Use it only after acknowledging that guest data may be inconsistent. Closing the manager while a machine or worker is active requires explicit confirmation; a timeout or lost control does not trigger an automatic retry of the last command.

A private QMP channel prevents accidental exposure of a TCP management port. It is not a security sandbox for an untrusted emulator or image. Only run sources you are authorised to use and have chosen to trust.

6. Create a blank disk and a cold checkpoint

A managed disk is optional. Keep it empty for the first foundation boot. The diskless foundation image does not acquire storage drivers, partitioning tools or persistent user storage merely because a virtual disk is attached.

To create a disk, stop the machine, enter a new directory in Managed disk, choose a size between 1 and 128 GiB in the graphical form, and choose Create blank disk. Framework calls the selected runtime's native qemu-img through the owned process channel. The result is a standalone QCOW2 version-3 disk, without a backing file or encryption in this initial profile.

The manager uses a retained lock file to exclude cooperating operations on that disk. Do not remove the lock file, start a second external QEMU against the same disk or edit it behind the manager.

For a Cold checkpoint, first shut down the guest cleanly and wait for exit. Leave the existing disk directory in Managed disk; put a different, new directory in New run / checkpoint. Choose Cold checkpoint. The source is checked, copied and checked again; it is not overwritten.

A disk copy is not a suspended computer

The checkpoint contains disk bytes, not RAM, CPU state, running processes or unsaved application memory. It is not proof that a guest filesystem was clean before the copy. Restore by selecting the new managed disk directory in a profile and reviewing a new run; do not overwrite the original.

QEMU's own image-tool documentation warns against modifying an image in use. Its full VM snapshots are a separate concept involving machine and storage state. This batch deliberately provides only the bounded cold-copy workflow described here.

7. Repeat the workflow from PowerShell

The CLI uses the same C library as the window. The paths below are examples for a practice directory whose parent already exists. Substitute your qualified runtime and native bundle paths.

PowerShell
$Tool = "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-vm.exe"
$Database = "C:\Umicom-Practice\profiles.sqlite"
$Runtime = "C:\Umicom-Practice\qemu-runtime"
$Image = "C:\Umicom-Practice\image-bundle"
$Run = "C:\Umicom-Practice\run-001"

& $Tool runtime-verify --root $Runtime
if ($LASTEXITCODE -ne 0) { throw "Runtime check failed." }

& $Tool profile-save --database $Database --id notes-lab `
    --name "Umicom OS practice machine" --runtime $Runtime --image $Image `
    --arch x86_64 --memory 1024 --cpus 2 --expected 0
if ($LASTEXITCODE -ne 0) { throw "Profile save failed." }

& $Tool profile-show --database $Database --id notes-lab
& $Tool review --database $Database --id notes-lab --directory $Run
if ($LASTEXITCODE -ne 0) { throw "Review failed." }

The review prints a Fingerprint: line. Read the profile and review result before copying that value into the next command:

PowerShell
$Fingerprint = Read-Host "Paste the reviewed fingerprint"
& $Tool run --database $Database --id notes-lab `
    --directory $Run --expect $Fingerprint
if ($LASTEXITCODE -ne 0) { Write-Host "The run did not finish normally; inspect the result." }

The prompt accepts only these named actions:

CommandMeaning
status, pause, resumeQuery or request the corresponding machine state.
consoleRead up to 2048 bytes from the serial ring buffer.
send help, send poweroffSend a line to the guest console.
powerdownRequest guest powerdown, without claiming that it occurred.
quit-qemuRequest QEMU's immediate host-side exit. This is not guest filesystem shutdown.
force-stopForce the owned process to stop; the CLI returns a non-success outcome.

Closing standard input also stops the owned child and reports an abnormal outcome. There is no detach-to-background or automatic reconnect in this version. leave explains how to finish safely; it does not abandon a running process.

A successful command exit is not an operating-system boot certificate. Exit 77 means a required capability was unavailable; do not count it as a passed run.

8. Prepare an optional runtime for an offline release

This section is for the person preparing a release. It is not necessary for the memory-only lesson. Begin with a trusted, authorised QEMU build, its complete runtime dependencies, the firmware needed by the chosen machine and the applicable notices/source information. Do not guess that copying one executable is enough.

The inventory is ordinary tab-separated data. The following is a format illustration, not a complete redistributable QEMU file list. Every listed path must exist, and a real inventory must add all required DLLs, firmware and distribution materials.

Inventory data · literal tabs
UMICOM_QEMU_INPUT	1
host	windows-amd64
architecture	1
version	qualification-label
emulator	bin/qemu-system-x86_64.exe
image-tool	bin/qemu-img.exe
firmware	share/qemu
licence	licences/QEMU-COPYING.txt
source-notice	licences/SOURCE-NOTICE.txt
file	bin/qemu-system-x86_64.exe
file	bin/qemu-img.exe
file	share/qemu/bios-256k.bin
file	licences/QEMU-COPYING.txt
file	licences/SOURCE-NOTICE.txt

Architecture 1 means x86-64 and 2 means RISC-V 64. This initial runtime profile has one guest architecture and one private bin directory. A Linux inventory uses the corresponding host label and native executable names.

PowerShell
& $Tool runtime-pack `
    --source "C:\Umicom-Publisher\qemu-source" `
    --inventory "C:\Umicom-Publisher\qemu-input.tsv" `
    --output "C:\Umicom-Publisher\qemu-sealed"
if ($LASTEXITCODE -ne 0) { throw "Runtime preparation failed." }

& $Tool runtime-verify --root "C:\Umicom-Publisher\qemu-sealed"
if ($LASTEXITCODE -ne 0) { throw "Runtime verification failed." }

& $Tool runtime-component --root "C:\Umicom-Publisher\qemu-sealed" `
    --output "C:\Umicom-Publisher\qemu-component.tsv"
if ($LASTEXITCODE -ne 0) { throw "Component preparation failed." }

These commands create new outputs only. The component file assigns the runtime to the umicom-vm-manager application in the native installer. It is data consumed by the C packer, not a package script.

During release configuration, set UMICOM_QEMU_COMPONENT_INPUT to that component file and choose a new UMICOM_SETUP_OUTPUT_DIRECTORY. Build umicom-native-installer. When VM Manager is selected, its declared runtime is installed below share/umicom/qemu. An application-only selection does not acquire these VM-owned files.

The release inspector treats the QEMU private bin as a separate loader namespace. A DLL in Umicom's main bin must not accidentally satisfy a dependency that the privately installed emulator cannot find.

Qualify the resulting installer on a clean Windows machine, with no development PATH, and run the exact normal/recovery guest profiles. Licence/source-notice presence is only a structural check. Review the actual distribution obligations for the exact build; the tool does not certify legal sufficiency or authenticate its publisher.

9. Read the C example

The public profile API borrows a Data Server connection. It does not expose SQLite calls to the GUI. The caller owns the connection and destroys it after the last operation. An expected revision of zero creates a previously missing ID; changing a saved profile requires its current revision.

The complete lesson below is the same source built by the regression project:

C23 · examples/vm_manager/profile_lesson.c
/*-----------------------------------------------------------------------------
 * Umicom Framework | Sammy Hegab, Umicom Foundation | MIT
 * A saved configuration is not a running machine. This complete lesson stores
 * a profile in the real memory Data Server and detects an outdated edit.
 *---------------------------------------------------------------------------*/
#include "umicom/vm_manager/manager.h"
#include <stdio.h>
#include <string.h>
int main(void) {
    UmiDataServer *server=NULL;
    UmiVmProfile profile,loaded;
    uint64_t revision=0;
    if(umi_data_server_create_memory(&server)!=UMI_STATUS_OK)return 1;
    UmiVmProfileInit(&profile);
    strcpy(profile.id,"notes-lab");
    strcpy(profile.name,"Umicom Notes practice machine");
#ifdef _WIN32
    strcpy(profile.runtimeDirectory,"C:/Umicom-Practice/runtime");
    strcpy(profile.imageBundle,"C:/Umicom-Practice/image");
#else
    strcpy(profile.runtimeDirectory,"/home/practice/runtime");
    strcpy(profile.imageBundle,"/home/practice/image");
#endif
    int result=1;
    if(UmiVmProfileSave(server,&profile,0,&revision)!=UMI_STATUS_OK||revision!=1)goto done;
    if(UmiVmProfileLoad(server,profile.id,&loaded)!=UMI_STATUS_OK)goto done;
    printf("Saved: %s\nMemory: %u MiB; processors: %u\n",loaded.name,loaded.memoryMiB,loaded.processors);
    loaded.memoryMiB=1024;
    if(UmiVmProfileSave(server,&loaded,loaded.revision,&revision)!=UMI_STATUS_OK)goto done;
    if(UmiVmProfileSave(server,&profile,1,&revision)!=UMI_STATUS_INVALID_STATE)goto done;
    puts("The older edit was refused. Reload before changing the profile again.");
    puts("Practice complete. Memory only; no runtime, guest image or virtual disk was opened.");
    result=0;
    done:umi_data_server_destroy(server);
    return result;
}

Notice that storing a path does not open or execute that path. Validation of settings, verification of runtime bytes and starting a process are separate operations. This makes a saved profile useful even before the qualified runtime has been copied to that machine.

A live session has a different lifetime. UmiVmStart returns an owned session only after the private protocol is ready. One worker at a time may call its blocking operations. The UI copies observations onto its own thread rather than changing controls from a callback. Destroying a session stops a remaining child; callers must tell the user before reaching that cleanup path.

QMP is a JSON machine-control protocol. The manager negotiates capabilities, sends a small allowlist of commands and matches replies by numeric ID. An event can arrive between replies, so an event is not treated as the acknowledgement for the last button press. A malformed frame or uncertain timeout disables further control rather than automatically replaying a possibly completed action.

10. Understand a refusal before retrying

Message or symptomWhat to check
The profile already exists or its revision changedLoad it from the selected database, inspect the saved settings and save with the current revision.
Runtime inventory differsCheck for changed, missing or additional files. Do not edit the manifest to conceal the difference; prepare and qualify a new runtime from trusted inputs.
Host or architecture unavailableA Windows executable cannot serve as the native emulator on Linux. Match the runtime's host and guest architecture to the selected machine and image.
Run directory existsChoose a new final directory under an existing parent. Keep the earlier attempt for diagnosis.
Launch fingerprint differsReview again after verifying the selected paths and resources. Do not bypass the expected fingerprint.
Disk lockedStop the cooperating session using it. Do not remove the retained lock file or work around it with an external writer.
Control lost after timeout or malformed dataThe last action's outcome can be uncertain. Inspect the owned process and diagnostics; use explicit force stop only after considering guest data. No automatic reconnect is attempted.
Powerdown acknowledged, but process remainsThe guest may not implement that power signal. Use its documented shutdown command and wait, or explicitly choose the forced path.
Console appears emptyRead after Resume, confirm the image's serial-console configuration and inspect process diagnostics. A paused machine cannot finish its boot.
Profile database cannot openCheck the local parent directory and permissions and confirm SQLite was built. The CLI does not silently switch to memory.

The protocol captures bounded stderr for diagnosis, not an unlimited log archive. A new run records the profile and image source relationship. The best-effort end record is diagnostic material, not a durable crash-recovery transaction or a security audit.

11. Know the current boundaries

The manager supports 64 saved profiles, 256–32768 MiB of requested memory, 1–16 requested processors, and runtimes with up to 1024 files and 4 GiB of recorded bytes. The disk service accepts standalone QCOW2-v3 images within its documented size and feature limits. Console reads/writes are bounded to 2048 bytes, and QMP frames to 65536 bytes.

The profile database is plaintext and is not an authenticated multi-user service. Protect it and the runtime/image directories using host permissions. Locks coordinate participating Umicom processes; they cannot make an external program honour the protocol. Do not treat reviewed hashes, private pipes or process ownership as a substitute for trusting the programs you choose to execute.

This version does not provide WHPX acceleration, live migration, RAM snapshots, guest-agent integration, graphical guest embedding, clipboard sharing, port forwarding, USB passthrough or remote control. The existing Setup Centre launcher remains available; it is not silently replaced.

Component tests use an explicitly inert native peer for repeatable protocol and failure checks. A separately registered real-QEMU protocol test is NOT RUN unless a trusted executable is supplied. Even that test uses no operating-system image and does not qualify a guest boot.

12. Practise, then explain what happened

Exercise A — A profile is not a machine

Run the memory lesson. Explain why the saved memory value is not proof that memory was allocated for a guest.

Answer

The profile is data in the Data Server. There was no launch request, owned process or QMP session. The value describes a future request.

Exercise B — Make a stale review

With a disposable qualified profile, review a new run, change the memory field and try to start. What should happen?

Answer

The UI invalidates the review; a direct library or CLI attempt with the old fingerprint is rejected on revalidation. A new review must bind the changed settings.

Exercise C — Two editors, one profile

Load the same profile in two windows. Save a change in the first and then save the older copy in the second.

Answer

The second save must report a revision conflict. Reloading is a deliberate chance to reconcile the two edits; silently replacing the first save would lose information.

Exercise D — Distinguish the evidence

You have a verified runtime, a paused QMP connection and a returned powerdown acknowledgement. Which proves that the guest completed its normal boot?

Answer

None. Runtime verification describes files; paused QMP describes emulator state; powerdown describes a request. The source-linked guest service and shutdown observations come from the separate image boot checks.

Exercise E — Restore without destroying the original

After a clean shutdown, make a cold checkpoint into a new directory. How would you try that copy?

Answer

Point a practice profile at the checkpoint directory, review a new run and start it separately. Keep the original. The copy does not resume the earlier RAM/CPU state.
