Umicom Framework · Practical release engineering · FW-01 checkpoint 1

Know what a Framework release has actually passed

You have compiled a Notes application and its worker tests pass. Can someone now install it, open two notes, save their changes and close it safely? Those are different questions. This guide shows how to keep each question visible instead of letting one successful test stand for the whole product.

The aim: read a release contract, recognise missing evidence, and keep a useful test result without exaggerating what it proves.

1. Build the tools in a separate folder

Close Umicom applications before merging the checkpoint. Copy only the supplied files into their matching Framework locations. Keep other files and your local edits. The build folder below is a small laboratory: it does not replace the normal all-application build.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\tools\release_baseline" `
    -B ".\build\fw01-baseline" `
    -G Ninja -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "Configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\fw01-baseline" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\fw01-baseline" --parallel 2 `
    --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Tests failed." }

Configuration prepares the build instructions. Compilation produces the executables. CTest runs their checks. Stop at a failed prerequisite; a missing test executable is not a passed test.

2. Run a small Notes release example

& ".\build\fw01-baseline\bin\umicom-release-baseline-example.exe"
if ($LASTEXITCODE -ne 0) { throw "The lesson failed." }

The example constructs five fictional requirements and just one fictional Linux test receipt. It does not launch Notes or run a real compiler inside the example. The expected output is:

One Linux test receipt is present; four required release records are missing.
The Windows Notes journey is not a Linux test result. Release remains blocked.
Practice complete. Memory only; no test, window, artefact or repository was opened.

The Linux result is kept. It is simply not allowed to answer a different question about an installed Windows window.

3. Read the proposed Framework Core contract

$Tool = ".\build\fw01-baseline\bin\umicom-release-baseline.exe"
$Core = ".\framework\docs\releases\core"
& $Tool show "$Core\CORE_REQUIREMENTS.tsv"
if ($LASTEXITCODE -ne 0) { throw "Contract could not be read." }

The contract has 47 named requirements. Each tells you the expected host, configuration, evidence kind and responsible Framework batch. The candidate label and source revision are expected context supplied by the author, not a live inspection of your Git checkout.

Now check the deliberately empty product-evidence book:

& $Tool check "$Core\CORE_REQUIREMENTS.tsv" "$Core\PENDING_EVIDENCE.tsv"
if ($LASTEXITCODE -ne 1) { throw "Expected the proposed release to remain blocked." }

Exit code 1 is expected here. It means the release evidence is incomplete, not that compilation failed. All 47 Core-release requirements remain missing in this initial book. The parser and queue regression results are kept separately; they are not the full Core acceptance evidence.

Do not change missing rows to passed to remove the warning. A zero exit code only means the supplied metadata is internally consistent. This tool does not verify signatures, read the referenced logs, check artefact bytes, authenticate a reviewer or authorise publishing.

4. Understand what a record means

Record elementQuestion it answers
Requirement IDWhich precise acceptance item does this result address?
Candidate and sourceWhich proposed build context does the producer claim to have checked?
Profile and configurationWas it Windows or Linux? Debug or Release?
KindNative test, installed journey, analysis or human review?
Counts and outcomeDo the supplied totals agree? Were any items failed, skipped or not run?
Digest and referenceWhich artefact and record should a reviewer independently inspect?

The small text format is tab-separated ASCII. It is not a script. A result must contain the literal word asserted because it is a producer's assertion. Unknown IDs, duplicate records, invalid counts or malformed input are rejected. A valid but stale or incomplete result remains a blocker.

Counts alone cannot detect a missing test replaced by a different test. Exact CTest inventories, original logs and the actual package must still be checked. That work belongs to the next Framework checkpoints, not an assumption hidden in this tool.

5. Keep ownership straightforward in C

UmiReleaseContractParse and UmiReleaseEvidenceParse copy their inputs. After success, the original text buffer may be released. A failed parse leaves the output pointer unchanged. The caller owns the resulting objects and releases each once after its readers have finished.

The evaluator constructs a complete candidate assessment before replacing the caller's output. It delegates the final combination to Framework's existing distribution gate. It does not create a second runtime capability registry or add availability flags to applications.

Read the complete compiled Notes example
/*-----------------------------------------------------------------------------
 * Umicom Framework | Sammy Hegab, Umicom Foundation | MIT
 * File: examples/release_baseline/review_notes_release.c
 * Purpose: Show why a Linux test receipt cannot complete a Windows Notes release.
 *---------------------------------------------------------------------------*/
#include "umicom/distribution/runtime/evidence.h"
#include <stdio.h>
#include <string.h>

int main(void)
{
    /* These fictional receipts explain policy. They are not real test evidence
     * for Notes or any Framework product and must never enter the release book. */
    const char contractText[] =
        "UMICOM-RELEASE-CONTRACT\t1\ncandidate\tnotes-practice\n"
        "source\t1111111111111111111111111111111111111111\n"
        "require\tsign\tsignature\tpackage\tRelease\treview\tFW-18\tInspect publisher identity\n"
        "require\tbytes\tchecksum\tpackage\tRelease\tanalysis\tFW-18\tCheck the installed package bytes\n"
        "require\tabi\tcompatibility\tlinux-x86_64\tRelease\tnative\tFW-03\tBuild an independent Notes client\n"
        "require\tunit\ttests\tlinux-x86_64\tRelease\tnative\tFW-05\tRun Notes worker tests\n"
        "require\twindow\tfrontend\twindows11-x86_64\tRelease\tinstalled\tFW-10\tUse both Notes windows after installation\n";
    const char evidenceText[] =
        "UMICOM-RELEASE-EVIDENCE\t1\n"
        "result\tunit\tnotes-practice\t1111111111111111111111111111111111111111\tlinux-x86_64\tRelease\tnative\tpassed\t8\t8\t0\t0\t0\tasserted\t"
        "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa\tpractice/worker.txt\n";
    UmiReleaseContract *contract = NULL;
    UmiReleaseEvidence *evidence = NULL;
    UmiReleaseEvidenceAssessment assessment;
    UmiStatus status = UmiReleaseContractParse(contractText,strlen(contractText),&contract);
    if (status == UMI_STATUS_OK) status = UmiReleaseEvidenceParse(evidenceText,strlen(evidenceText),&evidence);
    if (status == UMI_STATUS_OK) status = UmiReleaseEvidenceAssess(contract,evidence,&assessment);
    bool correct = status == UMI_STATUS_OK && assessment.reportedComplete == 1U && assessment.missing == 4U && !assessment.readyForOwnerReview;
    if (correct) {
        (void)puts("One Linux test receipt is present; four required release records are missing.");
        (void)puts("The Windows Notes journey is not a Linux test result. Release remains blocked.");
        (void)puts("Practice complete. Memory only; no test, window, artefact or repository was opened.");
    }
    UmiReleaseEvidenceDestroy(evidence); UmiReleaseContractDestroy(contract);
    return correct && ferror(stdout) == 0 ? 0 : 1;
}

6. Practise without changing the release book

Work on copies of the lesson's fictional records. First change its source revision: the old receipt must no longer satisfy the new context. Next mark one counted case skipped while leaving the outcome as passed: the checker must reject completion. Finally add a receipt for an unknown requirement: it must be an input error, not silently discarded evidence.

Review questions: Why is a matching digest string not proof that the file was checked? Why does a completed Linux test not complete an installed Windows journey? Why must a new candidate have its own source and artefact record?

Answers

A digest in a text file is only a supplied value until someone independently hashes the artefact and compares it. The native host, configuration and operation differ between those journeys. A new candidate can contain different source, dependencies or packaging even when an old component test still passes; its evidence must identify and test that actual candidate.

When something does not work

Input refused: check tabs, exact field names, duplicate IDs, lowercase hexadecimal values and count totals. Missing evidence: record and investigate the required work rather than hiding it. Wrong context: rerun against the intended candidate and host; do not relabel an old result. File error: use the named local files and inspect their access permissions.

Files are read-only. The tool opens only the explicit contract/evidence files, not referenced logs. Use ordinary trusted local files; network-mounted paths can still use filesystem network access. This is not a file-access sandbox.
