Save emitted build output to a new file

The live output viewer keeps a bounded tail so a long build does not consume unbounded memory. Optional log capture records all bytes received from the workflow in a new file while that viewer continues to update.

Capture a workflow

  1. Choose an absolute path in an existing directory that the developer controls. Use a new filename, preferably outside source checkouts, so build output is not accidentally included in source commits.
  2. Call UmiBuildProjectSessionSubmitLogged with the existing session, validated profile, requested phase, current trust decision and selected path. The path is reserved using exclusive creation: an existing file or symlink is refused rather than opened or overwritten. Parent aliases may be followed; this API is not a filesystem sandbox.
  3. Keep polling the live view and completed phase results as before. Call UmiBuildProjectSessionReadLog for copied file progress. The read performs no disk access and does not borrow the worker's file handle.
  4. After completion, inspect both the build status and the log status. capture_complete means all emitted bytes were written and the file closed successfully. A failed or cancelled build can still have a complete capture of the output it emitted.
  5. Retain or remove log files according to the developer's own policy. Starting another job or destroying the session does not delete earlier files. Logs can contain source paths, diagnostics and other program output.
#include "umicom/build/log_capture.h"

/* The host supplies an existing session and its reviewed project profile.
 * Choosing a file does not replace the workspace trust decision. */
UmiStatus StartLoggedBuild(UmiBuildProjectSession *session,
    const UmiBuildProfile *profile, bool trusted, const char *new_log_path)
{
    return UmiBuildProjectSessionSubmitLogged(session, profile,
        UMI_BUILD_PHASE_BUILD, trusted, new_log_path);
}

Know what is saved

The file concatenates raw merged standard output and standard error from every attempted phase. It has no added headers, separators or text conversion, and preserves NUL bytes and invalid text sequences. Commands, phase identities and structured diagnostics remain in completed-result history. Output not emitted by a tool cannot be recovered; for example, cancellation may prevent a tool from flushing its own buffers.

Logging uses native incremental writes and does not accumulate the whole file in memory. It has no automatic size limit or rotation. Slow storage can delay the worker and cancellation. The destination is opened before submission; that native filesystem operation can also take time. At completion the writer asks the operating system to flush, then closes its handle. Success is not a guarantee against power loss or later external edits.

Legacy custom executors expose only their bounded final output. That useful evidence is saved once per phase, but capture_complete remains false. An observed custom executor must synchronously emit all intended bytes before returning and must honour cancellation.

Recover from errors

  1. Already exists: choose another filename. Never retry with automatic overwrite.
  2. Not found: check that the selected parent folder already exists.
  3. Invalid argument: use an ordinary absolute path without dot segments. Windows requires a UTF-8 drive path and refuses UNC paths, device aliases and alternate data streams.
  4. Write, flush or close failure: retain the file as partial evidence. Compare bytes_received with file.bytes_written and inspect file.status. Later writes do not retry after an error. The build continues independently; it is not restarted or automatically cancelled.
  5. Cancelled job: inspect the saved prefix and the actual build status. No subsequent phase is invented, and the capture does not imply that the whole requested workflow ran.

For other Framework services, UmiOutputFileCreate, UmiOutputFileWrite, UmiOutputFileRead and UmiOutputFileClose expose the same file ownership rules. Serialize these calls on their owner and destroy the writer only after its final I/O operation. Destruction closes an open handle but leaves the file on disk.
