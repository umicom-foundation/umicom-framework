Opening applications and checking launch activity

The Umicom application menu belongs to Framework. Studio, Trader, Bank, the creative applications and other GTK workstations use the same menu. The Umicom OS user-space desktop also includes this menu in its branded titlebar.

Open another application

  1. Open the application menu in the titlebar. Search by application name or purpose. Filtering does not clear applications you have selected.
  2. If an application is unavailable, build or install its native GUI executable beside the current application or in a trusted directory on your system PATH, then choose Refresh. A console verification tool is not a substitute for the GUI executable.
  3. Choose Open beside one application, or select several and choose Open selected. Each native request is handled separately. A failed request does not establish that other requests failed.
  4. Reopen the menu and expand Launch activity. It shows the executable path and the observed result, newest first. The text is selectable for copying into a support report.
  5. If an instance opened from this window is still active, switch to that application's window. Standard Open will not create another tracked instance. Use New window beside a catalogue row to request another instance of that product explicitly. The titlebar's separate New window action opens another instance of the current product.

Understand the result

ObservationWhat it means
Process startedThe operating system accepted the executable. The application's window and services have not completed a readiness handshake.
Process exited with code 0The process reported a normal exit. This does not prove that every feature works; some applications may hand work to another process and exit.
Process exited with another codeThe process ended with an error or other application-defined result. A code of -1 means termination without a normal exit code on platforms that report that condition.
Process could not startThe native loader or file check refused the request. Check the executable, its permissions and required runtime libraries. Install missing dependencies, then retry explicitly.
Status could not be confirmedThe exit observer failed. Check the operating system's process list before opening another instance.

Lifetime and privacy

Closing the launching window does not send a termination request to applications it opened. Save and close those applications in their own windows. Launch activity is held only in memory and disappears when the launching window is released. It holds up to 64 receipts, retaining active or uncertain processes and replacing the oldest completed receipts when full. It is not a machine-wide process list: another window, another application or an earlier session may have launched additional instances.

The receipt contains application identity, the executable path and process outcome. It does not capture arguments, environment variables, credentials or process output. Console diagnostics continue to use the parent's ordinary output streams. Paths can identify local folders, so review the activity text before sharing it.

The child starts with its executable directory as the working directory. No shell command strings or automatically assembled arguments are constructed. The directory must be trusted: a format check and file-presence check are not code-signing verification, and they cannot prevent another program replacing a file between checking and execution.

Delegated application hosts

Umicom Desk can supply its own governed launch handler. Such requests retain that host's existing policy. The menu reports the request result but does not invent a native receipt; consult the host's process state. Launch activity covers only the default native launcher.

For contributors

UmiApplicationLaunchReceipts is the toolkit-neutral owner. Reserve a receipt before starting a child, mark a loader refusal as rejected, and mark an exit only after observing it. Receipt IDs are stable within their owner; indexes are display positions. UmiGtk4ApplicationProcesses connects this model to the platform through GIO asynchronous waits. The wait owns no GTK widget, and destruction immediately disconnects the observer. Additional frontends can reuse the C receipt model with their own native process adapter.

The GIO argument-array API and asynchronous wait API describe the native bridge's ownership contracts. A bootable OS image, installer, process activation across applications and application readiness handshakes require their own implementation and qualification.
