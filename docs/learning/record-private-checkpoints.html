Learning catalogue · Checkpoint API

Record a private learning checkpoint

A checkpoint is a short record of something you deliberately chose to note about a lesson. For example, after reading a guide and discussing its example, you might record reviewed. This is different from opening the guide. The reader does not decide that opening a page means you understood it.

The native learning catalogue can keep these records in a local database. A database is a file designed to store and retrieve structured records. Here it holds learner identifiers, lesson identities, checkpoint names and references to your evidence. It does not contain a password-protected account, an encrypted notebook or a teacher's assessment. Choose where to store it before recording.

1. Open the lesson you mean to record

  1. In Studio, open Guided Learning, then Open local learning catalogue.
  2. Choose a prepared learning pack, select Load learning pack, then open a lesson or guide from its results. Follow the catalogue guide if this is your first pack.
  3. Check the displayed title and content. A source example or image cannot receive a checkpoint. If you have opened a guide's example, use Back to return to the guide before recording progress.
  4. Expand Private learning checkpoints. These controls are available when the native build includes Framework's learning-progress service. A missing SQLite backend is reported when storage is requested; temporary storage is not silently substituted.

The current reader holds the pack revision and content hash that it verified. A revision is the pack publisher's version number. A hash is calculated from the exact file bytes. Together with the pack and resource identifiers, these values identify what you actually read. Accepting a newer pack in the catalogue does not change an already open reader; open the new result explicitly when you want it.

2. Choose private storage

Create a private folder that you control, outside your course and project repositories. For example, this PowerShell command creates a folder under the local working area:

New-Item -ItemType Directory -Force "C:\umicom\_local\learning"
  1. In Private database filename (absolute path), type C:\umicom\_local\learning\practice.sqlite3, or use the new-file chooser. An absolute path identifies the file without depending on Studio's launch folder. The parent folder must already exist.
  2. To continue a database from an earlier session, use the existing-file chooser or enter its complete path. The database is not copied into your learning pack.
  3. Enter a Local learner ID, such as learner-1. This is a label within your local database, not a sign-in identity. Choose the same label when inspecting earlier records.
  4. Enter a Checkpoint ID, such as reviewed. Use a term that describes the action honestly. The application does not verify that a self-recorded checkpoint was approved by an instructor.
  5. For recording, enter an Evidence reference, such as practice-1. This is a short label for your own supporting work, not a filename to open and not the work itself.

Identifiers start with an ASCII letter or digit and can then contain letters, digits, dots, hyphens and underscores. Their maximum length is 95 bytes. Do not enter personal notes, messages, passwords or filesystem paths in them. These controls do not inspect repository membership or protect the chosen folder's permissions. You are responsible for selecting private storage and keeping it out of public commits. An ignore rule alone does not untrack an already committed file.

3. Inspect before recording again

Select Inspect checkpoint. The operation opens an existing database read-only. It never creates a missing file. The evidence field is ignored for inspection because the query finds the latest event for the current document and checkpoint, whatever evidence reference that event used.

ResultMeaning
A matching event and sequenceThis learner already has that checkpoint for the exact pack revision and content hash.
No match, journal loadedThe database was read successfully, but no event matches this exact document and checkpoint. An earlier lesson revision may still have records.
Database could not be openedCheck the path, permissions and whether the file exists. This is not a successful empty-history result.
Journal could not be readPreserve the file for investigation. Malformed records are not replaced with an empty journal.

The status area captures the database, learner, checkpoint, document revision, event count and matching sequence used by that operation. Changing an entry field after clicking does not redirect it. Reading another lesson later does not relabel the receipt. The next explicit checkpoint operation replaces the displayed receipt.

4. Record one deliberate checkpoint

  1. Finish the learning action you want to record.
  2. Check the lesson, private path, learner, checkpoint and evidence reference.
  3. Select Record checkpoint once. Wait until the controls become available again. Accepting a request starts background work; it is not yet proof that the record was stored.
  4. Inspect the result. A successful new event has a sequence number and reports a matching event. The first event for a learner has sequence one.
  5. Select Inspect checkpoint to reopen the database and read the stored result through a fresh connection.

Repeating the identical event returns ALREADY_EXISTS; it does not append another event. A different evidence reference is a new event. The journal allows up to 256 events per learner. Records are append-only through this service, but an external database editor can change the file. This is not a signed ledger.

5. Handle an uncertain write

A storage error can occur after a database has accepted data but before the caller receives a reliable success result. Retrying automatically might record something twice. The catalogue therefore blocks further records when the storage owner reports commit or rollback uncertainty.

  1. Keep the database. Do not delete it to make the error disappear.
  2. Read the captured database path and learner ID from the receipt. Restore those exact values in the controls if you changed them.
  3. Select Inspect checkpoint. A successful fresh journal inspection, including a valid no-match result, releases this panel's record block for that same database and learner.
  4. Review what is stored. If the event is already there, no repeat is needed. If it is absent, deliberately choose whether to record again.

Inspecting another database or learner does not resolve the uncertain operation. Closing a window is not a recovery procedure: a later window has no memory of the earlier warning, so inspect the database before resuming. A damaged journal or failed inspection leaves the uncertainty unresolved.

6. Close and return later

An accepted write can finish after the catalogue closes. Closing does not cancel or undo it. In a normal GtkApplication host, accepted work holds the application open until completion cleanup; an explicit forced quit can bypass that orderly path. Let Studio finish closing, then inspect the database next time before retrying. Late results are not published to retired panels.

The database persists, but the catalogue's chosen fields and open packs currently do not persist across restart. Reopen the pack and select the same database and learner. For private backup, use the explicit export workflow in the checkpoint service guide. An export contains learner history; keep it private as well.

For application developers

UmiLearningProgressLocalExecute owns a database connection and journal for one operation on the calling thread. Use a worker because file access can block. The native adapter clones the verified reader before dispatch, copies the request, and publishes only a receipt. It never transfers a live SQLite connection between workers. A request accepted by UmiLearningCatalogueGtk4Progress reports its eventual status through CopyState and CopyProgressReceipt.

Read src/teacher/learning_progress_local.c, adapters/gtk4/learning_catalogue_progress.c and tests/learning_pack/test_catalogue_progress_gtk4.c together. The regression source covers copied inputs, refusal before I/O, reader revision changes, duplicate events, retirement and uncertain-write recovery. These are qualification checks to run on the selected build, not a claim that a particular binary has passed them.
