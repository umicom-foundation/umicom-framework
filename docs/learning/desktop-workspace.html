Umicom · A practical desktop lesson

Keep your desktop work and return to an earlier checkpoint

You are preparing a workshop. Your notes change as the plan develops, and you would like the same comfortable workspace when you return tomorrow. This lesson shows how to save the notes and their presentation together, then recover an earlier saved version without losing sight of what happened.

You will use Umicom Desktop Workspace, opened from Desk. The lesson begins with an empty workspace and follows one small note through several saved checkpoints. No account, payment, virtual machine or physical drive is involved.

For first-time users and new C programmers · Fictional practice information · Works offline

1. Drafts, saved revisions and checkpoints

A draft is the version you are editing. Changing a title or typing a sentence changes the draft. It does not immediately replace the saved workspace.

A checkpoint is a complete saved copy of this workspace: its notes, selected note and presentation preferences. Each successful save receives a larger revision number. The number lets the service distinguish the version you reviewed from a later version.

OpenEdit draftSave checkpointPreviewRestore as a new revision

Imagine revision 2 says “Prepare the Notes exercise” and revision 4 adds debugging. Restoring revision 2 does not renumber the history or pretend revision 4 never existed. It creates a new revision containing the earlier content.

The most recent eight checkpoints are kept. A checkpoint is useful protection against a recent editing mistake, but it is not a permanent backup. Once it leaves that eight-checkpoint window, it is no longer available through this workspace.

2. Open a private workspace

Start from Desk

Open the updated Umicom Desk application. Choose Open persistent desktop workspace. The new window is separate from Desk’s existing launcher, saved application groups and System Centre.

Read the directory displayed near the top. It is the location where this workspace will keep its database. The default comes from the current user’s application-data directory; the displayed path is the authority. It is not based on the folder from which you started Desk.

Choose Open workspace. On a new workspace, the first saved revision is an empty revision 1. Opening also records that a local workspace session is active. The window does not execute anything stored in the notes.

One cooperating editor at a time. Another window using the same directory should receive a busy result. Close the first window normally, then try again. Do not delete workspace.lock: the operating system releases the lock when its owning process ends, while the filename is deliberately retained.

Use fictional practice information. This component stores ordinary plaintext records and does not provide encrypted notebooks, user authentication or a replacement for your computer’s access controls.

3. Write and save your first note

Choose New note. Replace the suggested title with Workshop plan. In the body, enter:

Prepare the Notes exercise.
Bring a notebook and leave time for questions.

The status now describes an unsaved draft. Choose Save checkpoint, then wait for the saved message. With the fresh workspace from the previous step, the revision becomes 2.

Both lines and the title are saved in the same checkpoint. The title is a label; an internal stable identifier keeps the note’s identity when its title changes.

Add another note only after you are comfortable with the first. The note selector moves between notes. Valid edits remain in the draft when you switch notes. If a title or body is too large or invalid, the interface should keep you on that note so you can correct it.

Remove from draft removes the selected note from the editable draft. Its earlier saved checkpoint remains available until normal history retention retires it. Choose Discard draft to return to the current saved checkpoint instead of committing the removal.

4. Make the workspace comfortable

Choose Dark workspace or Light workspace, and set the font to a comfortable value between 10 and 28 points. System appearance leaves the colour choice to the current toolkit theme.

Choose Save checkpoint to record and apply the new preferences. In this example, selecting a 16-point font and dark appearance creates revision 3. These preferences affect the workspace content, not every Umicom application or the system desktop.

Show note list controls the note-selector area. If you hide it and save, the checkbox remains available so you can show it again. Preferences belong to the checkpoint just as the note body does; restoring an earlier checkpoint can restore an earlier appearance too.

Saving is explicit. A changed control creates a draft. The last committed checkpoint is unchanged until Save succeeds. A validation error or storage failure is not silently treated as a saved change.

5. Preview and restore an earlier checkpoint

Change the first line of the note to “Prepare the Notes and debugging exercises.” Save again. Following the lesson exactly, you now have revision 4.

Enter 2 in the checkpoint-number field and choose Preview checkpoint. A review window shows the current saved workspace on the left and the selected checkpoint on the right. Read the complete note titles and bodies, selected note, theme, font size and note-list visibility. Preview does not replace your current checkpoint.

Both panes are read-only. You can select and copy text. Choose Next difference to visit a changed line, or scroll either pane. If the notes exceed the line-alignment limits, the view explains why difference navigation is unavailable and still displays both full texts.

Choose Cancel first. Check that revision 4 and its note remain in place. Preview checkpoint 2 again, then choose Restore reviewed checkpoint. The result is revision 5, containing exactly the reviewed notes and preferences. The review window closes after submission, and the main window reports the save result.

The review owns copies of both snapshots. Applying uses the reviewed copy through the normal save transaction. A changed saved revision, closed session or new unsaved draft prevents the old review from applying. Dismiss it, resolve the draft, then preview again. A failed transaction does not advance the saved revision.

RevisionWhat this lesson saved
1The new empty workspace.
2The first workshop note and default preferences.
3The same note with a 16-point dark workspace.
4The revised note that also mentions debugging.
5A new saved copy of revision 2.

Save or discard an unsaved draft before previewing a restoration. This keeps the confirmation about saved versions rather than quietly discarding work still visible in the editor.

A workspace restoration changes only this component’s notes and preferences. It does not reverse a bank transfer, undo a trade, change an installed program or restore virtual-machine memory.

6. Close and reopen without surprises

Close the window normally. When a draft is unsaved, choose Save and close, Discard draft and close, or Cancel. Discard affects the unsaved draft, not existing checkpoints.

When storage work is already running, closing waits for that owned operation to finish. A failed save or failed clean-close record should leave the window open with an explanation rather than claiming success.

Open the workspace again. Its saved revision and appearance should return. No other application should be launched merely because a workspace was reopened.

After an abnormal process exit, the next opening reports that the previous session was not closed cleanly. It loads the last committed checkpoint. Text that never reached a successful save is not recovered. The marker reports an unfinished local session; it is not a diagnosis of the operating system or hardware.

The tests exercise abrupt child-process exit. There is no need to kill an application containing real work to practise this lesson.

7. Try the native command-line workflow

The same Framework service has a native command-line client. This is useful for understanding the saved revision before working on a graphical integration. It is not a second storage implementation.

Open PowerShell after building the updated source. The following creates a separate practice directory so the terminal exercise does not change the graphical example:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$Tool = ".\build\windows-ucrt64-all-debug\bin\umicom-desktop-workspace.exe"
$Workspace = Join-Path $env:LOCALAPPDATA ("Umicom-Workspace-Practice-" + [guid]::NewGuid().ToString("N"))

& $Tool show --directory $Workspace
if ($LASTEXITCODE -ne 0) { throw "Workspace opening failed." }

The new workspace is revision 1. show opens and cleanly closes a local session; it is not advertised as a no-write forensic database inspector.

& $Tool put --directory $Workspace --expected 1 `
    --id "workshop" --title "Workshop plan" --text "Prepare the Notes exercise."
if ($LASTEXITCODE -ne 0) { throw "The note was not saved." }

& $Tool settings --directory $Workspace --expected 2 --theme dark --font 16
if ($LASTEXITCODE -ne 0) { throw "The preferences were not saved." }

& $Tool restore --directory $Workspace --expected 3 --checkpoint 2
if ($LASTEXITCODE -ne 0) { throw "The checkpoint was not restored." }

This independent terminal sequence ends at revision 4. The note is retained and the preferences return to those in revision 2.

The --expected argument says which saved version you intend to change. Repeating the original command with --expected 1 now fails instead of replacing the newer workspace. Run show, read the current state and prepare a fresh operation.

Use --help to see the native operations. Linux uses the same arguments with its native executable. Windows command-line execution is a target-platform acceptance step; the delivered Linux tests do not establish that Windows execution passed.

8. Read a complete C example

The example below uses the actual memory Data Server. It creates a note, saves two versions and restores the first version as a new checkpoint. It does not open a file or window.

First, notice the ownership. The workspace is an opaque service object. The draft is caller-owned memory. Reading copies the saved snapshot into the draft, so editing it cannot silently change the authoritative copy.

Next, notice the revision. Commit receives the revision from the draft. After saving, read the new snapshot before preparing another change. This is a small, explicit form of optimistic concurrency: an old expectation is rejected.

Finally, notice the two close operations. Clean close records a completed session. Destroy releases memory and native resources. Destroy alone intentionally does not claim a clean ending.

framework/examples/desktop_workspace/notes_example.c

/*-----------------------------------------------------------------------------
 * Umicom Framework | Sammy Hegab, Umicom Foundation | MIT
 * A complete memory-only example: edit a note, save two checkpoints, then
 * restore the earlier note by creating a new checkpoint. No window is opened.
 *---------------------------------------------------------------------------*/
#include "umicom/desktop_workspace/workspace.h"
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
int main(void)
{
    UmiDesktopWorkspace *workspace = NULL;
    UmiDesktopWorkspaceSnapshot *draft = calloc(1, sizeof *draft);
    if (!draft) return 1;
    UmiStatus status = UmiDesktopWorkspaceOpenMemory(&workspace);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceRead(workspace, draft);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspacePutNote(draft, "workshop", "Workshop plan", "Prepare the Notes exercise.");
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceCommit(workspace, draft->revision, draft);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceRead(workspace, draft);
    uint64_t first = draft->revision;
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspacePutNote(draft, "workshop", "Workshop plan", "Prepare the Notes and debugging exercises.");
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceCommit(workspace, draft->revision, draft);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceRead(workspace, draft);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceRestore(workspace, draft->revision, first);
    if (status == UMI_STATUS_OK) status = UmiDesktopWorkspaceRead(workspace, draft);
    if (status == UMI_STATUS_OK) {
        printf("Checkpoint %" PRIu64 ": %s\n%s\n", draft->revision, draft->notes[0].title, draft->notes[0].body);
        status = UmiDesktopWorkspaceCloseClean(workspace);
    }
    UmiDesktopWorkspaceDestroy(workspace); free(draft);
    if (status != UMI_STATUS_OK) { fprintf(stderr, "Practice stopped with status %d.\n", (int)status); return 1; }
    puts("Practice complete. The workspace stayed in memory; no application, guest or network was started.");
    return 0;
}

Build and run umicom-desktop-workspace-example. On a successful run, the important output is:

Checkpoint 4: Workshop plan
Prepare the Notes exercise.
Practice complete. The workspace stayed in memory; no application, guest or network was started.

There is no need for Assembly in this example: it performs validation and storage orchestration rather than an architecture-specific instruction sequence. The public service and tools remain C23.

Use the restore review from C

The complete example examples/desktop_workspace/review_restore.c creates a memory workspace, saves two different notes, reviews the earlier checkpoint and explicitly restores it. Its expected final message contains saved revision 4 and Prepare the first exercise.

  1. Call UmiDesktopWorkspacePrepareRestore with the retained checkpoint number. A successful call returns an owned review; failure leaves your output pointer unchanged.
  2. Read UmiDesktopWorkspaceRestoreCurrent and UmiDesktopWorkspaceRestoreCheckpoint. They return borrowed, immutable snapshots. Keep the review alive while reading them; do not change or free those pointers.
  3. After confirmation, call UmiDesktopWorkspaceApplyRestore on the same live workspace. It checks the saved revision and commits the exact reviewed content. A successful review cannot be applied twice.
  4. Call UmiDesktopWorkspaceDestroyRestoreReview on every exit path. Cancelling needs only this destruction; it performs no save.

Keep all workspace operations serialised on one owner or one worker. A review holds copied evidence, not a reference that keeps its workspace alive. New frontends should use this contract instead of rereading the checkpoint when the confirmation button is pressed. The original direct UmiDesktopWorkspaceRestore API remains available for callers that do not offer a review step.

9. Understand what is kept

The directory contains a SQLite database and a lifetime lock file. SQLite may also use its own temporary journal files. The component never interprets a note as a command, file path or URL.

BoundaryMeaning
16 notesThe maximum number in a saved checkpoint.
95 title bytes; 4095 body bytesLimits are UTF-8 bytes, not necessarily visible characters. Many non-ASCII characters use more than one byte.
Eight recent checkpointsOlder checkpoint records are retired only inside the transaction that successfully publishes the new checkpoint.
Plaintext local dataChecksums detect accidental record corruption; they do not authenticate a person or encrypt a note.
One cooperating process lockOther instances using the same directory are refused. This does not defend against malicious code already running with your user identity.

Back up the complete private directory after closing the workspace. Do not edit its records or copy only a database fragment while work is running. An absent or corrupt checkpoint causes an error; the service does not quietly reset the notebook to an empty state.

The current diskless Umicom OS foundation keeps its runtime in memory. Merely adding this component does not make that guest persistent. A graphical OS profile and a qualified persistent volume must be supplied before a guest can keep these files across boots.

10. Build and test the component

A developer can build the native component independently of the complete desktop. In PowerShell, from the Framework checkout:

Set-Location "C:\umicom\Umicom-Applications\framework"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" -S ".\examples\desktop_workspace" `
    -B ".\build\desktop-workspace-checks" -G Ninja -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "Configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\desktop-workspace-checks" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\desktop-workspace-checks" `
    --parallel 2 --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Tests failed." }

This focused project compiles the real Data Server and digest sources needed by the workspace. It is not the complete Framework or Desk build. SQLite-dependent checks explicitly report unavailable support rather than silently using memory instead.

Use the accompanying build instructions for the full Applications preset, the changed Desktop module and repository publication order. GTK tests must run in an actual graphical environment; a missing-display skip is not a graphical pass.

11. Work through common problems

The workspace is busy

Another cooperating process owns the directory lock. Close that process normally. A filename left behind is not the same as a held operating-system lock. Deleting the filename can defeat safe coordination, so do not use deletion as the remedy.

The saved revision is different

The command or draft was based on an older version. Read the current workspace and prepare a new change. Do not simply substitute a new revision number without reviewing what changed.

SQLite is unavailable

The native build did not include the required backend. Rebuild with the canonical SQLite dependency available. This component refuses disk-backed opening rather than pretending a memory-only workspace will survive restart.

A save failed

Keep the draft visible, read the error and resolve the storage problem. A normal rollback leaves the previous saved checkpoint unchanged. If rollback itself fails, the object is marked unusable and refuses further mutations; close it and investigate the stored state before reopening.

An old checkpoint cannot be found

Read the displayed retained range. Only eight recent revisions are kept. An older permanent backup is a separate responsibility.

The restored appearance surprises you

Appearance is part of the checkpoint. Restoring the first note also restores the preferences saved with it. Make a new preferences change and save another checkpoint when needed.

12. Practise and check your understanding

Try these tasks in the separate practice workspace, not in a notebook containing personal information.

Exercise 1: change a draft without saving, then discard it. What should reopen?

The last committed checkpoint. Editing a caller-owned draft does not modify the saved workspace, and discard returns to that saved copy.

Exercise 2: save a note, change its title and save again. Is it a new note?

No. Its stable identifier is unchanged. The title is editable presentation text; the new checkpoint records the edited title.

Exercise 3: restore revision 2 from revision 4. Which revision should you see?

Revision 5, with the content and preferences from revision 2. The restore is a new recorded change rather than a rewrite of history.

Exercise 4: why does an outdated --expected value stop a command?

It shows that the operation was prepared against a different saved version. Refusal makes the caller review the current state instead of silently overwriting it.

Exercise 5: does an unfinished-session message recover every keystroke?

No. It reports the absence of a clean-close marker and reloads the last committed checkpoint. Unsaved draft text is not recovered.

C extension: add another note to the memory example.

Read the current snapshot, call UmiDesktopWorkspacePutNote with another identifier, commit using the draft’s revision, read again, and check that both notes are present. Preserve the existing note and its identifier.

When these steps make sense, you have practised several concepts that also appear in larger Umicom applications: explicit ownership, authoritative storage, draft editing, optimistic concurrency, atomic commits and honest recovery boundaries.
