Waiting for debugger replies

A debugger is another program. Studio asks it to pause a program, list threads or inspect a value. The answer travels through a byte stream. A request sequence is the number that connects an answer to the original question. Other answers and events can arrive first, so Framework keeps separate queues for responses and events.

A deadline is a boundary, not a new allowance for every read

A positive wait timeout starts one elapsed-time budget. Framework uses a monotonic clock: a clock intended for measuring duration rather than the date on a wall calendar. Each read receives only the remaining budget. A complete answer is checked again after the read returns. An answer at or beyond the deadline is late even if its sequence matches.

The clock cannot interrupt a synchronous callback. If a transport or event observer blocks, Framework can detect that it returned late, but cannot guarantee a hard wall-clock return time. Run these operations on the connection’s worker, not the graphical interface thread. Do not concurrently access the same adapter from several workers.

What happens to a late answer?

  1. The transport receives and decodes a frame. The frame has already been consumed from the stream.
  2. If the positive wait budget has expired, Framework does not replace the caller’s response output.
  3. A response is placed in the bounded response queue. An event is placed in the event queue without starting an event observer after expiry.
  4. The wait reports UMI_STATUS_TIMEOUT. A later, explicit wait can inspect the retained answer. This does not change the outcome of the earlier timed-out operation.
  5. If the destination queue is full, the wait reports the capacity error. It does not claim that it retained a message it could not store.

A timeout does not prove that the debugger failed to perform the requested action. Do not automatically send the same request again: launching, restarting or assigning a variable may already have happened. Decide whether to inspect the existing request, close the session or report uncertainty.

A nested request can receive the original answer before its own answer. The response queue preserves this ordering situation. If the observer finishes after the outer deadline, the original answer stays queued for later inspection. An observer must not destroy the adapter or recursively wait for the same sequence. It must consume a triggering event when issuing a nested request, as described in adapter.h.

Read the status without losing your previous result

This fragment illustrates the decision after sending a request. The adapter, sequence and response storage must already be valid. It does not start a debugger or provide a complete application.

/* candidate is fresh zeroed, heap-owned envelope storage. */
UmiStatus status = umi_debug_runtime_adapter_wait_response(
    adapter, sequence, 1000U, candidate);

if (status == UMI_STATUS_OK) {
    /* Inspect the matching successful response. */
} else if (status == UMI_STATUS_UNAVAILABLE &&
           candidate->kind == UMI_DEBUG_RUNTIME_MESSAGE_RESPONSE &&
           candidate->request_sequence == sequence) {
    /* Inspect the newly received unsuccessful response. */
} else if (status == UMI_STATUS_TIMEOUT) {
    /* Keep the previous accepted result. Do not resend automatically. */
} else {
    /* Report transport, decoding or queue-capacity failure. */
}

Use a fresh zeroed candidate for each operation and keep your previous accepted result separately. UMI_STATUS_UNAVAILABLE can mean a remote unsuccessful response or a transport refusal. The status alone does not prove that an error envelope was received. Verify the candidate’s kind and request sequence before reading remote error details.

The wait budget starts when the wait begins. The convenience invoke operation sends first and then waits; its synchronous write is not covered by the wait timeout. Transport ownership, sending policy and session cleanup are separate decisions.

Inspect a conversation through the installed SDK

examples/debug_reply_queue uses public SDK APIs and an in-memory transport. Choose ordered for replies in request order, interleaved for a later response arriving first with two events, or remote-error for a received refusal. The program checks sequence identity, event order, drained pending requests and unchanged output after an empty poll. It does not start a debugger, grant project trust or execute a target program.

Its standalone CMake project requires an explicit UMICOM_EXPECTED_SDK_PREFIX and the installed developer component. It checks that imports belong to that SDK. The three sdk.debug_reply_queue.* cases complement the clock-controlled source regressions; replay success alone cannot qualify native process transport.

Follow the implementation

The private src/debug_runtime/deadline.h calculates the remaining duration. adapter_wait.inc handles ordinary waits; adapter_observed_wait.inc adds event observation. Both use adapter_wait_private.h to retain late messages. Large candidate envelopes live on the heap so nested requests do not add large protocol records to normal thread stacks.

tests/debug_runtime/test_wait_deadline.c supplies a deterministic clock while linking the real transport, framer, decoder and queues. Its cases cover the exact boundary, partial frames, late events and replies, unchanged output, nested observers and capacity refusal. These cases complement native debugger and Studio workflow checks; they cannot establish compatibility with every debugger.
