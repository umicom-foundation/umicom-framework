Native AI application learning path

Build a model-discovery application with the Umicom SDK

Build a C application that reads model-list observations using an installed Umicom Framework SDK. You need basic pointers, structures and error handling, a C23 compiler, CMake and Ninja. The exercise uses synthetic JSON, so no provider account, network connection or model download is needed.

Lesson 1: separate a model from its current evidence

The same model ID can exist at several endpoints. Keep the reviewed endpoint and connection revision next to each observation. A local HTTP address identifies a destination, not necessarily where inference runs. For example, a local service can relay requests elsewhere.

Protocol inputInterpretationNot established
Ollama /api/tagsAvailable model metadataLoaded state or inference success
Ollama /api/psModels reported loaded; optional VRAM and context informationContinued availability after the observation
OpenAI-compatible /v1/modelsListed IDs at that endpointCapabilities, balance, account permissions or local execution

These mappings follow the Ollama inventory and loaded-model documentation. GPT4All documents a localhost API server, normally on port 4891, with a /v1/models route. Its LocalDocs collections are selected through its desktop UI; this decoder does not configure retrieval. See the GPT4All API guide.

Lesson 2: create a project from an installed SDK

  1. Install a matching Framework SDK using your normal qualified build. Choose a prefix such as C:\SDKs\Umicom; it must contain the CMake package and compiled libraries.
  2. Copy share/umicom/framework/examples/model_discovery from that prefix into your own project directory. It contains both main.c and CMakeLists.txt. Do not clone Framework into the application.
  3. Use the compiler family and architecture that built the SDK. The example verifies package origin and the SDK environment contract.
  4. Configure, build and run the offline test:
cmake -S C:/Projects/model-discovery -B C:/Projects/model-discovery/build -G Ninja -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DBUILD_TESTING=ON
cmake --build C:/Projects/model-discovery/build
ctest --test-dir C:/Projects/model-discovery/build --output-on-failure

Stop after any failing command. Expected program output identifies example:small as listed and reported loaded, and example:large as listed but absent from the loaded observation. It explicitly identifies the inputs as synthetic. These commands are a qualification procedure, not evidence that your installed SDK has passed it.

Lesson 3: follow ownership through the API

UmiAiDiscoverySnapshot *snapshot = NULL;
UmiStatus status = UmiAiDiscoveryDecode(
    UMI_AI_DISCOVERY_OLLAMA_AVAILABLE, json, json_length, NULL, &snapshot);
if (status == UMI_STATUS_OK) {
    UmiAiDiscoveredModel model;
    status = UmiAiDiscoveryFind(snapshot, "example:small", &model);
    if (status == UMI_STATUS_OK) {
        /* model is a caller-owned copy; inspect known bits before numbers. */
    }
}
UmiAiDiscoveryDestroy(snapshot);

The decoder copies and validates the response. It publishes one immutable snapshot only after every entry is valid. Each read copies a record. The snapshot may be read concurrently, but its owner must wait for readers before destroying it. Optional numbers have presence bits: a reported zero VRAM value differs from missing VRAM information.

The current limits are 4 MiB input, 65,536 JSON nodes, nesting depth 32, 1,024 models and 512 UTF-8 bytes per model ID. No ID is shortened. Repeated decoded IDs or object keys are refused. Numeric metadata requires an exact integer from zero through INT64_MAX. Unknown fields are validated and ignored; they do not grant a capability.

Lesson 4: test failure recovery

  1. Change the second synthetic ID to the first one. Expect UMI_STATUS_ALREADY_EXISTS and a null snapshot, not a partial list.
  2. Replace a numeric size with 1.5. Expect a parse error.
  3. Remove the optional size. Decoding should succeed; the size presence bit must be clear.
  4. Keep a prior good snapshot in your application and publish a new one only after successful decoding. Preserve the prior view on failure and display its observation age.

The Framework producer registers the native regression group framework.ai.model_discovery.*. A graphical picker, HTTP fetch, model download, chat execution and diffusion generation are separate responsibilities. This example implements none of those effects.

Troubleshooting and assessment

If CMake cannot find the package, point UMICOM_SDK_ROOT at the installation prefix, not its source checkout or a single DLL. If the environment check fails, use the matching toolchain or rebuild the SDK; do not bypass the check. If the program starts but lacks a runtime library, use the SDK's documented deployment process and inspect the exact missing dependency. A successful configure is not a successful link or launch.

Lesson 5 — Build a model browser from observations

A useful browser needs search, filters and repeatable ordering. Keep these operations over the immutable observation you already own. The native UmiAiDiscoverySelect function returns another owned snapshot, so rendering the result does not borrow mutable form fields or a temporary response buffer.

UmiAiDiscoveryFilter filter = {0};
strcpy(filter.search, "example:");
filter.size_limit_enabled = 1;
filter.maximum_size_bytes = 1048576;
filter.order = UMI_AI_DISCOVERY_ORDER_SIZE_ASC;
UmiAiDiscoverySnapshot *matches = NULL;
UmiStatus status = UmiAiDiscoverySelect(inventory, &filter, NULL, &matches);
if (status == UMI_STATUS_OK) {
    /* Use Count/At/Find as with any discovery snapshot. */
}
UmiAiDiscoveryDestroy(matches);

This fragment assumes inventory is a live decoded snapshot and the usual public header and string.h are included. The complete installed model_discovery example now performs this selection and checks its result. Build and run it with the earlier SDK commands, then record the actual results.

ControlMeaning
searchSubstring of ID, display name or family; ASCII letters are case-insensitive. Other Unicode bytes are preserved.
family / format / quantizationExact optional metadata facets. Empty means no facet restriction.
required_knownRequire explicitly reported numeric fields. Unknown values never silently become zero.
minimum_context_tokensA positive threshold requires a reported context value.
size limitAn enabled maximum requires reported size. It does not estimate peak RAM or prove device fit.
orderSource, complete ID, name, ascending reported size or descending reported context. Unknown numeric values sort last; complete ID resolves ties.

Keep the connection identity and revision alongside both snapshots. Filtering never merges providers, loads a model or refreshes a server observation. An Ollama available-model list remains that kind of observation after filtering; it does not become a loaded-model list.

  1. Filter the example by its reported size and explain why one model remains.
  2. Use a loaded observation with a reported size of zero and one with size absent. Apply a zero-byte maximum and explain why only the known zero can match.
  3. Sort equal-size models and confirm the full ID determines their order.
  4. Destroy the original snapshot after selection; confirm copied results remain readable. Retain the original until selection returns.
  5. Try an invalid filter or a requested cancellation. Keep the result NULL and preserve the previous displayed selection until a new query succeeds.

A zero-initialized filter is the simplest starting point. Initialise the result pointer to NULL; an occupied output is refused rather than leaked. Search does not implement Unicode case folding or locale-specific collation. Numeric metadata is provider-reported evidence, not a capability test.

Lesson 6: distinguish a list entry from model details

Ollama's /api/show response can describe one model's format, family, quantization, architecture and declared capabilities. These fields complement the inventory and loaded-model observations from earlier lessons. The official API reference and response schema describe the protocol. A response can omit optional metadata. Do not fill the gaps with assumptions from a familiar model name.

The Umicom SDK exposes umicom/ai/ollama_model_info.h. Its decoder accepts response bytes and a model label supplied by your application. That label records what you requested; the decoder does not authenticate a server or verify that the server answered for that model. Retain the reviewed connection, connection revision, request identity and observation time in your application.

ObservationHow to interpret it
Missing capabilitiesThe provider supplied no capability list. Declares returns UMI_STATUS_NOT_FOUND and preserves the output boolean.
"capabilities":[]A list was supplied and contains no declarations. Declares returns OK with false.
An unfamiliar capability namePreserved exactly for inspection. It does not enable an action in your application.
A numeric presence bit is clearThe associated number is unknown. A known zero is a different observation.
Context lengthRead from the key matching general.architecture. A family name is not substituted for the architecture.

Lesson 7: own a copied detail observation

#include <umicom/ai/ollama_model_info.h>
#include <string.h>

static UmiStatus inspect_details(void)
{
    const char response[] =
        "{\"model_info\":{\"general.architecture\":\"example\","
        "\"example.context_length\":8192},"
        "\"capabilities\":[\"completion\",\"future-feature\"]}";
    UmiOllamaModelInfo *info = NULL;
    UmiStatus status = UmiOllamaModelInfoCreate(
        "example:small", response, strlen(response), NULL, &info);
    if (status == UMI_STATUS_OK) {
        UmiOllamaModelInfoSummary summary;
        status = UmiOllamaModelInfoInspect(info, &summary);
        if (status == UMI_STATUS_OK &&
            (summary.known & UMI_OLLAMA_MODEL_CONTEXT_LENGTH)) {
            /* summary.context_length is reported metadata, not a fit test. */
        }
    }
    UmiOllamaModelInfoDestroy(info);
    return status;
}

This is a function fragment; the installed example supplies a complete main and assertions. Initialise the owner pointer to NULL. Creation publishes it only after the entire response is admitted. Keep the input stable until creation returns; afterwards the owner contains copied metadata. Summary and capability reads also copy their results. Wait for readers to finish before destroying the owner. No raw template, system prompt, licence text or tensor list is retained in this metadata owner.

Response identity is a SHA-256 digest of the exact supplied bytes, including whitespace. It helps detect changed observations; it is not a signature or proof of origin. The decoder performs no network request, model download, activation or inference.

Lesson 9: defend the boundary without hiding uncertainty

The detail decoder admits at most 4 MiB, 65,536 JSON nodes, nesting depth 32 and 64 capability names. A model label is at most 512 UTF-8 bytes; a capability is at most 128. Limits count bytes, not displayed characters. Repeated decoded capability names or object keys are refused. Exact nonnegative integer metadata is limited to INT64_MAX; fractional, negative and overflowing values are refused. Unknown fields are validated and ignored. A provider error response is an error, not an empty successful result.

  1. Remove the capability member, then use an empty list. Explain why a user interface should distinguish these results.
  2. Add an unfamiliar declaration and query it using its exact spelling. Change the case and observe the distinct result.
  3. Use 9007199254740993 for parameter count. Read it through the integer field; do not route it through a floating-point number.
  4. Change the architecture while retaining the old context key. The context presence bit must be clear.
  5. Try duplicate decoded keys, an oversized capability and a cancelled operation. Preserve the previously displayed owner if replacement creation fails.
  6. Run the producer's framework.ai.ollama_model_info.* tests together with existing model-discovery and model-query regressions, because those decoders share field admission.

Record which cases actually executed. Declared vision, tools or completion support still requires separate provider-specific execution and application permission checks. A context length does not predict peak memory or prove that the model fits a device. This lesson implements metadata interpretation, not Ollama server parity.
