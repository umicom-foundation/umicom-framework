Lesson 52 · 45–90 minutes · ID: foundations.assembly-branches

1. Understand the idea

Assembly exposes register-level operations and control flow. The calling convention decides where arguments and results live; it differs between Windows x64, Linux x86-64 and RISC-V.

TermPlain meaning
ABIThe binary-level calling and representation agreement.
Leaf functionA function that does not call another function.
Unsigned branchA branch interpreting comparison flags as unsigned ordering.

Review the first C programme, functions and memory basics. The workshop setup creates a separate build directory; it does not replace your application build.

Before writing code, say what counts as valid input, who owns each object, and what must remain unchanged when an operation fails.

2. Write and inspect the complete example

Open framework/examples/learning/programming/assembly_branches/main.c. The supplied file is the reference solution. Read it once, then type your own copy in a disposable practice workspace. For a first run you may build the supplied reference unchanged. Do not put deliberately broken examples into the shared Framework source.

The lines beginning with #include provide declarations. main is the programme entry point. EXIT_FAILURE reports a failed check; EXIT_SUCCESS reports success. The helper functions above main implement this lesson’s contract.

examples/learning/programming/assembly_branches/main.c
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/assembly_branches/main.c
 *
 * PURPOSE:
 *   Assembly registers, comparisons and branches.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include "../assembly_contract.h"

static uint64_t MaximumC(uint64_t left, uint64_t right)
{
    return left>=right?left:right;
}
int main(void)
{
    const uint64_t pairs[][2]={{0U,0U},{4U,9U},{9U,4U},{UINT64_MAX,1U},{1U,UINT64_MAX}};
    for (size_t index=0U; index<sizeof(pairs)/sizeof(pairs[0]); ++index) {
        uint64_t expected=MaximumC(pairs[index][0],pairs[index][1]);
#ifdef UMICOM_LAB_NATIVE_ASSEMBLY
        if (LabMaximumAsm(pairs[index][0],pairs[index][1])!=expected) return EXIT_FAILURE;
#else
        if (expected!=pairs[index][0] && expected!=pairs[index][1]) return EXIT_FAILURE;
#endif
    }
#ifdef UMICOM_LAB_NATIVE_ASSEMBLY
    puts("native Assembly matched C for five unsigned comparisons");
#else
    puts("C-only mode: enable UMICOM_LEARNING_BUILD_ASSEMBLY for native comparison");
#endif
    puts("PASS: assembly_branches");
    return EXIT_SUCCESS;
}

Native source: ../basics_x86_64.S (Windows / Linux x86-64)
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/basics_x86_64.S
 *
 * PURPOSE:
 *   Teach unsigned comparison and a zero-safe loop on Windows/ELF x86-64.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/

/* GCC/Clang preprocessed Assembly, AT&T syntax: source operand first. */
#ifdef _WIN32
#define FIRST %rcx
#define SECOND %rdx
#else
#define FIRST %rdi
#define SECOND %rsi
#endif
.text
.globl LabMaximumAsm
#ifndef _WIN32
.type LabMaximumAsm, @function
#endif
LabMaximumAsm:
    movq FIRST, %rax
    cmpq SECOND, %rax
    jae .Lmaximum_done
    movq SECOND, %rax
.Lmaximum_done:
    ret
#ifndef _WIN32
.size LabMaximumAsm, .-LabMaximumAsm
#endif

.globl LabSumAsm
#ifndef _WIN32
.type LabSumAsm, @function
#endif
LabSumAsm:
    xorq %rax, %rax
    testq SECOND, SECOND
    je .Lsum_done
.Lsum_next:
    addq (FIRST), %rax
    addq $8, FIRST
    subq $1, SECOND
    jne .Lsum_next
.Lsum_done:
    ret
#ifndef _WIN32
.size LabSumAsm, .-LabSumAsm
.section .note.GNU-stack,"",@progbits
#endif
Native source: ../basics_riscv64.S (RISC-V LP64)
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/basics_riscv64.S
 *
 * PURPOSE:
 *   Teach leaf functions with the RISC-V LP64 integer calling convention.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT

.text
.globl LabMaximumAsm
.type LabMaximumAsm, @function
LabMaximumAsm:
    bgeu a0, a1, .Lmaximum_done
    mv a0, a1
.Lmaximum_done:
    ret
.size LabMaximumAsm, .-LabMaximumAsm

.globl LabSumAsm
.type LabSumAsm, @function
LabSumAsm:
    mv t0, a0
    li a0, 0
    beqz a1, .Lsum_done
.Lsum_next:
    ld t1, 0(t0)
    add a0, a0, t1
    addi t0, t0, 8
    addi a1, a1, -1
    bnez a1, .Lsum_next
.Lsum_done:
    ret
.size LabSumAsm, .-LabSumAsm
.section .note.GNU-stack,"",@progbits

3. Follow the values through the code

The C contract uses uint64_t, so the native implementation must compare unsigned values. The final two pairs distinguish an unsigned branch from a signed one. Windows x64 passes the arguments in RCX and RDX; the Linux System V x86-64 convention uses RDI and RSI; RISC-V LP64 uses a0 and a1. The source files select the appropriate contract at build time.

Place your cursor at the first statement in main. Write down the input and expected output of each helper call. When you reach a rejection, check both the return value and any caller-owned output. Do not assume “no crash” means the result is correct.

Bad example — inspect only. The following fragment illustrates a defect or unclear contract. It is not part of the built targets. Examples with invalid memory access, mismatched formats or undefined behaviour must not be run.
Bad pattern: not compiled or executed
/* Signed branches compare unsigned high-bit values incorrectly. Choose the correct comparison. */

Good pattern: use the complete checked implementation above. Explain which precondition or comparison prevents the defect. A naming change alone cannot repair an ownership or bounds error.

4. Build and run it

First complete the workshop configuration once. Then run the following commands one line at a time. Stop on an error instead of continuing with an old executable. The two operating systems use different paths, but compile the same C sources.

Windows · PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-programming" --target umicom-learning-assembly-branches
& ".\build\learning-programming\bin\umicom-learning-assembly-branches.exe"
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-programming" --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.assembly_branches$'
Linux · terminal
cd "$HOME/umicom/Umicom-Applications"
cmake --build build/learning-programming --target umicom-learning-assembly-branches
./build/learning-programming/bin/umicom-learning-assembly-branches
ctest --test-dir build/learning-programming --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.assembly_branches$'

You should see the lesson’s explanatory output followed by:

Expected final line
PASS: assembly_branches

CTest should report one passing test for this exact filter. “No tests were found” is not success. Compilation errors concern C syntax or declarations; undefined references concern linking; a non-zero test exit concerns observed behaviour.

Use -DUMICOM_LEARNING_BUILD_ASSEMBLY=ON during configuration to execute the native comparison. With it OFF, the programme explicitly prints “C-only mode”; that result does not qualify the Assembly implementation. The supplied native sources support x86-64 Windows/ELF and RISC-V LP64 ELF, not every CPU.

5. Change one thing and test again

Read the matching .S file. Annotate the argument registers, result register, comparison and branch. Compile in native Assembly mode and explain why UINT64_MAX catches a signed-branch mistake.

Before editing, record your prediction. Rebuild the changed target and run it again; a previously built binary does not contain new source edits. Add at least one successful case, one rejected case and one boundary case. Preserve the original reference solution so a teacher can compare your attempt with known behaviour.

Review questions

Why test UINT64_MAX against one?

Read the explanation after answering

Its high bit distinguishes unsigned ordering from signed ordering and exposes the wrong branch condition.

What evidence did you produce? Record the source revision or the exact files you changed, compiler, build directory, command, observed output and any failure. Passing the supplied tests is not automatic proof that a new variation is safe.
