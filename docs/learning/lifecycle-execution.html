Execute a reviewed lifecycle

A lifecycle is an ordered set of development actions. The native workflow command uses Framework's existing plan and shared executor. It validates the complete typed request before invoking its adapters, then stops at the first nonzero backend result. This command concerns one project. Use repo publish-all to coordinate primary repositories, duplicate copies and parents.

Choose an intentional goal

GoalActions
verifyEnvironment/native dependencies, source scan, dependency audit
buildVerify, configure, compile/link
testBuild, then registered tests
publishVerify, repository review, publication
updateRepository review, checked update
completeTest, repository review, publication

Preview a request

  1. Install a CLI containing the shared lifecycle executor. Keep it outside the build and install destinations it supervises.
  2. Select an existing project and its real configure/build/test preset. Preview does not read the preset or establish that dependencies exist.
  3. Inspect the plan. Plan and dry-run invoke no host callbacks and create no execution log.
umicom workflow plan --goal test --source C:\work\my-project --preset debug --jobs 2
umicom workflow complete --source C:\work\my-project --preset debug --dry-run

Replace debug with a preset available in your project. Publication previews may omit the message; execution requires a nonblank message. Every option may appear once. An ineffective option is refused rather than silently ignored.

Run and read the result

umicom workflow test --source C:\work\my-project --preset debug --jobs 2

This executes real tools. A success summary reports completed backend actions. If build returns nonzero, no test or publication action runs. Missing required publication input for complete is rejected before environment checks, source scans or configuration.

Publication goals can stage, commit and push the selected repository. Use them only after reviewing the intended changes. They do not provide ecosystem dependency ordering. Do not infer a clean workspace or a successful GUI session from a workflow exit code.

Understand option scope

  • source applies to every goal; its default is the current directory.
  • preset and positive decimal jobs apply to build, test and complete. jobs must fit a positive C int.
  • message applies to publish and complete; remote and branch also apply to update.
  • no-submodules applies to update. The existing repository service keeps its own checkout and fast-forward policies.
  • strict requires external dependency vulnerability scanning and is refused for update, which has no audit stage.
  • goal is accepted only by plan. dry-run previews the selected command.

Use the shared C service

Include umicom/developer/lifecycle_execution.h and link Umicom::developer. Initialize the request, retain immutable borrowed strings until the call returns, and fill callbacks for every action in the goal. Framework checks the entire callback table before the first invocation. A missing final publisher therefore cannot leave earlier configure/build work behind. Preview accepts a null host.

Adapters are synchronous and return zero on success. The executor copies the request fields and callback table for the call, builds the canonical plan, groups adjacent stages that use one real service, and invokes each group once. It does not create a shell command, silently retry, roll back earlier work or turn optional audit labels into a fabricated pass. The existing audit backend decides whether unavailable external tooling is acceptable without strict mode.

Interpret partial progress honestly

The report contains planned actions, attempted/completed flags, the first failed action and its unchanged backend result. Environment and native dependency checks share one callback. Four source-analysis categories share one scan. Stage, commit and push share one repository-publication callback. If that callback fails, consult its own report: the executor cannot prove that staging or committing did not already happen. Retain prior evidence and correct the actual cause before choosing which work to rerun.

Qualify each boundary

cmake --build build --target umicom-lifecycle-execution-test umicom-lifecycle-workflow_cli-test
ctest --test-dir build -R '^framework\.developer\.lifecycle_(execution|workflow_cli)\.' --output-on-failure --no-tests=error

Use your configured Framework build folder. These controlled tests exercise admission, ordering, argument forwarding and failures without real external actions. Real tool execution, Git behavior and installed-consumer linking require their own qualification. Authored cases are not executed results.

For build-directory selection, definitions, targets, logs, JUnit output, install, package and application launch, use the individual commands in the development command guide. Those additional options are not forwarded by workflow. A PowerShell transcript remains the backup for a whole terminal session.
