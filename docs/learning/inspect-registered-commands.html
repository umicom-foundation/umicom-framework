Inspect registered commands

A command is a named application action. Menus, keyboard shortcuts, palettes and console adapters can refer to the same command identifier. The registry stores descriptive metadata and callbacks, while the application owns the state used by those callbacks.

Discovery must not accidentally perform the action it describes. Framework's command snapshots, prefix queries and policy summary read registered metadata without calling a handler or enablement callback. A command appearing in a list does not prove that it is currently enabled or that a user has permission to run it. Those are separate execution decisions.

Read policy totals

UmiCommandRegistrySummary summary;
UmiStatus status = UmiCommandRegistryCopySummary(registry, &summary);
if (status == UMI_STATUS_OK) {
    printf("%zu commands; %zu marked as background work\n",
        summary.command_count, summary.background_command_count);
}

The total and the counts for state mutation, background work, auditing and trust requirements come from one mutex-protected observation. A command can have several flags and contribute to several counts. Do not add the flag counts together to calculate the number of commands. This operation needs no metadata array and leaves the output unchanged on failure.

Count a namespace

size_t count = 0U;
UmiStatus status = umi_command_registry_find_prefix(
    registry, "document.", NULL, 0U, &count);
if (status == UMI_STATUS_OK)
    printf("%zu document commands\n", count);

A namespace prefix is a shared beginning of command identifiers. For example, document.open and document.save begin with document.. A count-only request passes no output array and uses zero capacity. An empty prefix matches every identifier. The runtime inventory prefix helper delegates to this existing registry operation.

Copy a list for a view

UmiCommandSnapshot rows[4];
size_t total = 0U;
UmiStatus status = umi_command_registry_find_prefix(
    registry, "document.", rows, 4U, &total);
if (status == UMI_STATUS_OK || status == UMI_STATUS_CAPACITY_EXCEEDED) {
    size_t copied = total < 4U ? total : 4U;
    for (size_t index = 0U; index < copied; ++index)
        printf("%s: %s\n", rows[index].command_id, rows[index].title);
}

A short array receives a valid prefix of the matching rows and an insufficient capacity status. The reported total can exceed the array size; read only the copied rows. Snapshot character arrays belong to the caller and remain readable after registration changes. They do not retain handler payloads, and old snapshots do not guarantee that the command remains registered.

Keep observation separate from execution

umi_command_registry_is_enabled asks application code whether a command is enabled. Unlike metadata discovery, it invokes the registered enablement callback. umi_command_registry_execute also checks that callback before invoking the handler. Follow the application's permission and trust policy when exposing execution; descriptive flags and permission names are not a substitute for that policy.

Keep the registry and borrowed callback payloads alive for their respective operations. A summary mutex coordinates registry reads with writes but cannot make concurrent registry destruction safe. Runtime inventory obtains separate command and service observations. It is not one atomic transaction across the whole application, and capability mutation still needs owner serialization.

tests/test_command_discovery.c registers all sixteen combinations of the four policy flags, checks mutation and prefix counts, and verifies that metadata capture never calls enablement or execution callbacks. Build umicom-command-discovery-test and select ^framework[.]command[.]discovery[.] in CTest. Existing framework.runtime.inventory_queries and framework.runtime.inventory_flag_matrix checks cover the combined inventory adapter. These names identify coverage to execute, not evidence of a pass on an untested build.

Distinguish an empty registry from a failed observation

A mutex protects the registry while a reader copies its entries. If the platform cannot acquire that mutex, status-returning queries report the failure before reading the registry. Their output remains unchanged on that pre-copy failure. Do not display an old report as a fresh successful observation.

The older count and boolean interfaces cannot carry an error code; they return zero or false when acquisition fails. Use a summary or snapshot when your application must distinguish that result from an empty registry or a missing command. Keep the registry owner alive during either form of query.

The framework.command.lock_failure cases compile the real command registry with a small test-only mutex implementation. They inject one failure and check unchanged registrations, unchanged copied metadata, no callback and no unlock of an unacquired mutex. This verifies the error boundary; it does not establish the behaviour of concurrent threads or replace platform testing.
