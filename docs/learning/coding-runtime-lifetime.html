Own a coding runtime through callbacks

A native coding agent coordinates several kinds of work: reading selected source, asking a model for a proposed change, applying a reviewed patch, and running configured validation. Each boundary calls code supplied by its host. That code can call Framework again before the first call returns. This lesson extends coding service ownership to the agent and the composition that owns it.

1. Separate execution activity from task state

A task state such as COMPLETED describes progress. It does not prove that every outer C function has returned. For example, a parent still updates its own revision after the agent returns. Freeing the parent during a callback would invalidate that later access even if the child were otherwise safe.

The agent therefore records whether an execution call is active. The platform records its own activity and also checks its agent and assistant. These checks cover calls made directly through the platform's borrowed child accessors. They are separate from the visible state machine.

2. Keep public reentry distinct from internal orchestration

The public run, apply and repair APIs admit one serialized operation. They mark activity, call the existing execution body and clear activity after it returns, whether the result is success or an error. Policy changes, approval, rejection, queue mutations and checked destruction refuse an active owner with UMI_STATUS_BUSY.

Automatic apply is already part of an admitted run. It uses a private internal function instead of calling the guarded public apply entry point. Otherwise a correct guard would accidentally reject the agent's own next step. Internal calls preserve the existing approval, patch, validation and repair logic; they are not a way for application callbacks to bypass admission.

Public run
  check idle
  mark active
  prepare → provider callback → review or internal apply → validation
  clear active
  return status

Nested public run or destroy from a callback → BUSY

3. Release the parent through its checked API

#include "umicom/ai_coding_runtime/platform.h"

UmiStatus release_coding_platform(UmiAiCodingRuntimePlatform **owner)
{
    if (owner == NULL) return UMI_STATUS_INVALID_ARGUMENT;
    UmiStatus status = UmiAiCodingRuntimePlatformDestroyChecked(*owner);
    if (status == UMI_STATUS_OK) *owner = NULL;
    return status;
}
  1. Retire UI aliases and independent workers before beginning shutdown.
  2. Call the checked parent destructor from the lifecycle owner.
  3. On BUSY, keep the handle. Return normally from the active callback and retry only after the outer operation finishes.
  4. On OK, clear the handle. Never read the old object again.
  5. Release borrowed external runtime, AuthorEngine and executor storage only after the platform has stopped using them.

UmiAiCodingAgentDestroyChecked provides the same rule for a separately owned agent. Legacy void destructors remain compatible and retain a busy owner, but cannot report the refusal. UmiAiCodingAgentCheckIdle and UmiAiCodingRuntimePlatformCheckIdle are read-only observations. They acquire no mutex and reserve no future lifetime.

4. Preserve cancellation and observation

Cancellation requests remain available during execution. They set the existing cooperative cancellation signal; they do not synchronously free the agent or force a provider to return. The normal execution path observes cancellation at its established checkpoints. A caller must still wait for that outer operation to return before destruction.

Serialized snapshots and event consumption remain available for monitoring. Borrowed history, audit, assistant and agent handles are not ownership transfers. Do not destroy those objects, rewrite their internals, or use them concurrently. A callback guard cannot protect a host that frees the external runtime or executor behind the agent's back. Callbacks must return normally; nonlocal jumps cannot skip the cleanup boundary safely.

5. Test real orchestration without real side effects

The focused fixture uses an in-memory source file, a deterministic provider response and a developer executor that returns a synthetic validation result. It calls real Framework planning, parsing, approval, apply, rollback and repair code. No model is contacted, no process is launched and no project file is written.

  1. Configure Framework with testing and its developer/AI capabilities enabled using your supported toolchain.
  2. Build the focused target.
  3. Run the lifetime test family and inspect every failure.
  4. Qualify the real provider, compiler, workspace and application UI separately.
# From the Framework source root, after configuration:
cmake --build build/windows-ucrt64-debug --target umicom-ai-coding-runtime-lifetime-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework\.ai\.coding-runtime-lifetime\.' --output-on-failure

Expected result: the selected scenarios pass. Automatic, queued, direct-agent, manual-review and repair flows must finish successfully after nested requests are refused. Failure scenarios must clear activity for later controlled recovery. A provider-time cancellation must prevent patch writes. Test registration and successful CMake generation are not evidence that these native cases have run.

6. Diagnose ownership and workflow errors separately

ObservationInvestigation
BUSY inside a callbackThis is the intended refusal. Move shutdown or mutation to a later owner-controlled step.
BUSY after the outer call returnsCheck for another active borrowed-child operation and confirm serialization. Never clear private flags to force progress.
Automatic apply now reports BUSYInspect whether internal orchestration accidentally calls a guarded public entry point.
Validation failsInspect its real output and configured rollback/repair policy. A lifetime guard does not make an invalid patch correct.

These guards do not add thread safety, guarantee rollback after every adapter failure, validate arbitrary pointers, or repair revision exhaustion. Each is a separate contract requiring its own implementation and evidence.
