Search inside offline learning resources

A guide can contain a useful explanation even when its title does not contain the word you remember. This walkthrough searches the paragraphs of a guide and the source text of its examples. It uses the same Framework services that applications can embed in their learning tools.

You need a Framework SDK with the developer component, its declared dependencies, CMake, Ninja and a matching C compiler. Start with Use the offline learning catalogue to learn about packs. The complete example is examples/learning_pack_inspector/body_search.c.

Interfaces: the shared C API and command-line SDK example are accompanied by the native catalogue’s Search inside guides and examples section. It offers explicit Search text, Refresh search and verified Read result actions. Metadata search and Find within the current document remain separate controls. Read result verifies the document and selects its first matching passage.

1. Understand a search snapshot

A resource is one declared guide, lesson, example or image. A manifest lists resources and the expected digest of each file. A digest is a fixed-size value calculated from the file's bytes; changed bytes should produce a different value. The manifest and files must come from a source you have chosen to trust. Matching a digest alone does not identify or authenticate their publisher.

A snapshot owns a copy of the searchable text at a particular moment. Building the snapshot reads and verifies files. Searching it later uses memory. This separation lets an application perform file access on a worker and keep the interface responsive. It also explains why search results can describe earlier content after a file changes.

2. Build the installed example

Use a new exercise directory. If it already contains work, choose another directory instead of overwriting it. These commands assume a matching SDK installed at C:\umicom\installed\framework. Stop when any command reports an error; the number printed by $LASTEXITCODE should be zero after configure, build and test.

New-Item -ItemType Directory "C:\umicom\examples\learning-text"
Copy-Item "C:\umicom\installed\framework\share\umicom\framework\examples\learning_pack_inspector\*" "C:\umicom\examples\learning-text"
Set-Location "C:\umicom\examples\learning-text"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\learning-text"
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DUMICOM_EXPECTED_SDK_PREFIX="C:/umicom/installed/framework" -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\learning-text\configure.log"
$LASTEXITCODE
cmake --build build --target umicom-learning-pack-text --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\learning-text\build.log"
$LASTEXITCODE
ctest --test-dir build -R "^sdk[.]learning_pack[.]text[.]" --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\learning-text\tests.log"

Configuration copies the example resources and calculates their actual hashes. The executable links installed libraries; this consumer does not rebuild Framework source. The three selected tests check a guide phrase, a source-code phrase and a missing phrase. Their exit status is checked along with the expected resource selection. The expected result is three passing tests. A missing executable is a build or installation problem, not a passing test.

3. Search the generated pack

& ".\build\umicom-learning-pack-text.exe" "$PWD\build\pack" learning-pack.json "verified body search" 2>&1 | Tee-Object "C:\umicom\_local\logs\learning-text\guide-search.log"
$LASTEXITCODE
& ".\build\umicom-learning-pack-text.exe" "$PWD\build\pack" learning-pack.json "argc < 3" 2>&1 | Tee-Object "C:\umicom\_local\logs\learning-text\source-search.log"
$LASTEXITCODE

The first command should identify resource guide. The second should include inspector, because its C source checks how many command-line arguments it received. Each result includes the pack and resource IDs, a byte range and a short text preview. A phrase can appear in several resources. The service returns the first occurrence in each matching resource.

Try a word absent from the pack. Zero results with a successful exit means the search completed and found nothing. It differs from a refusal, where the executable exits unsuccessfully and reports a status.

4. Trace the real C API

UmiLearningTextIndex *index = NULL;
UmiLearningTextProblem problem = {0};
UmiStatus status = UmiLearningTextIndexCreate(
    shelf, NULL, NULL, NULL, &index, &problem);

UmiLearningTextQuery query;
UmiLearningTextQueryInit(&query);
strcpy(query.phrase, "ownership");
UmiLearningTextSearch *search = NULL;
if (status == UMI_STATUS_OK)
    status = UmiLearningTextSearchCreate(index, &query, &search);

/* Read copied results only after a successful search. */
UmiLearningTextSearchDestroy(search);
UmiLearningTextIndexDestroy(index);

NULL for limits chooses documented defaults. The two following NULL arguments mean no cancellation callback or callback data. A callback is a function the service calls at defined boundaries. A graphical host can use one to notice a cancellation request, but it must not destroy or modify the shelf during construction.

The & operator passes the address of an output variable. A successful create call places a new owner in that variable. Failure leaves it null. Use a separate candidate variable when rebuilding: replace an application's earlier index only after the candidate succeeds. The destroy functions accept null and release each successful object once.

The complete program checks every status. The short fragment above explains the ownership pattern; it is not a standalone program. The source files src/teacher/learning_text_index.c and src/teacher/learning_text_search.c show how the implementation combines the existing verified reader, inert HTML projection and Editor literal-search engine.

5. Know which text and offsets are searched

ResourceSearchable contentResult offsets
HTML or HTM filenameShared reading projection. Visible paragraphs, headings and supported structure remain; scripts, styles and other excluded sections do not.Bytes in the reading projection.
Other non-image resourceComplete UTF-8 source text, including comments and markup if it is not classified as HTML.Bytes in the verified source.
Image resourceExcluded and counted without reading image bytes.No result.

A byte offset counts stored bytes from zero. Some characters take several UTF-8 bytes, so an offset is not necessarily a character count. The end offset is exclusive: it points just after the matched phrase. HTML tags and decoded entities change the reading text; never apply its offsets directly to raw HTML or to a newly changed document.

Phrase matching is literal. Square brackets are ordinary characters, not a regular expression. Case-insensitive search folds ASCII letters; it does not promise Unicode case folding or normalization. Whole-word boundaries use the Editor engine's ASCII identifier rules. Product filters match exactly; locale filters fold ASCII but do not fall back from en-GB to en.

6. Work within explicit budgets

The defaults allow 256 documents, one MiB of source per resource, 64 KiB of searchable text per document and eight MiB of searchable text overall. A byte is a unit of stored data; one KiB is 1,024 bytes and one MiB is 1,024 KiB. Configurable hard bounds are listed in learning_text.h. Zero does not disable a limit. The document limit must fit within the total limit.

An invalid, changed, missing or oversized non-image resource refuses the whole candidate. The optional problem record identifies the known pack and resource without exposing an absolute filesystem path. This gives the host an opportunity to explain the refusal while keeping an earlier index. There is no silent “mostly complete” search library.

A search retains at most 256 results. It still counts all matching documents and marks truncation when some were not returned. Results follow shelf and manifest order. The current service does not rank relevance, persist an index, download resources, scan undeclared files or provide fuzzy matching.

7. Reopen results safely

A result owns its pack revision, resource digest and preview. The shelf and index may be destroyed after the search. Keeping that result does not make changed files match it. Use UmiLearningReaderCreateFromShelf with the result's pack ID, expected revision, resource ID and expected digest when opening it. Apply offsets only after recreating the same reading representation.

Generation numbers help identify changes in the originating shelf. They are not globally unique identities and must not be compared across unrelated shelves as proof that two libraries match. A verified example remains source to inspect; searching or opening it grants no build or execution permission.

Search inside loaded guides and examples

  1. Load the learning packs you want to search, then expand Search inside guides and examples.
  2. Enter a phrase and choose Search text. The first search reads and verifies declared non-image resources on a worker. Later searches reuse the prepared text snapshot.
  3. Optionally enter a Product ID, a Language tag, or choose a Resource kind. Product IDs match exactly: studio differs from Studio. Language tags ignore ASCII letter case but do not fall back: en does not match en-GB. Leave an entry empty and choose All readable resources to remove those filters. Use the values declared in your pack manifest.
  4. Use Match case or Whole word when needed. These use ASCII case and identifier-boundary rules; they do not perform language-specific normalization.
  5. Choose a result and select Read result. The reader rechecks its revision, digest and current bytes, then selects and scrolls to the first match. The location is calculated from the verified text, including complete UTF-8 characters. Use Find in this resource or Ctrl+F to find later occurrences. A changed or missing file leaves the previous reading selection intact.
  6. Choose Refresh search after editing resource files to rebuild the snapshot deliberately. A changed or missing file refuses the new snapshot and keeps earlier results visible with a failure message. Update the reviewed manifest consistently before retrying.

Adding or replacing a pack makes the previous body results stale against the shelf. Search again before reading those results; the next search rebuilds automatically. A memory snapshot does not detect disk edits by itself. Image files are excluded, HTML scripts and styles are omitted, and source examples are searched without being executed.

The default snapshot allows 256 documents, 1 MiB per source file, 64 KiB of searchable text per document and 8 MiB overall. The visible controls retain up to 128 matching documents and reports truncation. Back, Forward and Reload retain their resource-navigation behavior; they do not replay a previous search highlight. Selecting Read result again reapplies that verified location. Empty phrases are refused. There is no automatic search on each keystroke, network request, fuzzy ranking or persisted index.

Filter from a native application

A filter narrows the set of resources searched; it does not modify a course or translate its text. Initialize a query before filling its fixed-size arrays, then validate it before dispatch. For example:

UmiLearningTextQuery query;
UmiLearningTextQueryInit(&query);
memcpy(query.phrase, "ownership", sizeof("ownership"));
memcpy(query.product, "studio", sizeof("studio"));
memcpy(query.locale, "en-GB", sizeof("en-GB"));
query.kind = UMI_LEARNING_RESOURCE_EXAMPLE;
UmiStatus status = UmiLearningTextQueryValidate(&query);
if (status == UMI_STATUS_OK)
    status = UmiLearningCatalogueGtk4SearchBodiesWithQuery(panel, &query, 0);

Include string.h and the native catalogue header in a GTK host. The call copies this query; the caller may release its local storage after acceptance. Observe CopyState until the panel is no longer busy. CopyBodySearchState includes the last successful query alongside its results, so a failed request cannot label older results as a new search. Native queries cannot carry callback pointers or borrowed cancellation state. Direct synchronous core searches retain their separate cancellation contract.

8. Diagnose and practise

  1. Missing SDK symbol: check that headers and libraries come from the same installed SDK. Reinstall the selected Framework build rather than borrowing a header from another checkout.
  2. Changed resource: compare the edited file with the source used to generate the pack. Reconfigure the example when the change is intended, then recreate the index. Do not bypass the hash check.
  3. Capacity exceeded: inspect the reported resource and limits. Use a smaller reviewed shelf or deliberately choose appropriate bounded limits. A larger budget cannot make malformed content valid.
  4. Unexpected zero results: check the literal phrase, product, locale, kind and case settings. Hidden HTML script text and metadata-only titles are not body text.
  5. Practice: search for a C function name in an example. Find it in the actual source, compare the byte range, then add a sentence to the source copy and explain why the old manifest refuses it.
  6. Design exercise: draw the lifetime of the shelf, index and results. Decide which objects an application must retain while a worker runs and which copied objects can safely outlive it.
