Using the learning catalogue

The learning catalogue is a local reader for product guides, lessons and source examples. A learning pack is a folder containing those files and a small catalogue named learning-pack.json. That catalogue is also called a manifest. It names the resources, describes their topics and records a hash for each file. A hash is a value calculated from the file's exact bytes. The reader checks it before displaying a resource so a changed file is not silently shown as the version named by the pack.

Umicom Framework supplies the catalogue and reader. Umicom Studio IDE supplies a button that opens the shared window. Other native applications can use the same Framework adapter. The first presentation is a text reader: HTML is converted to a bounded text preview, source examples appear as text, and images receive an explicit notice. It does not render interactive web pages, run examples or grant permission to build a project.

1. Prepare a pack you can inspect

A folder of unrelated files is not automatically a learning pack. Start with the complete example under examples/learning_pack_inspector in the Framework source. Its CMake configuration copies the supplied guide and C examples to a pack folder and hashes those copied bytes. The output includes a real learning-pack.json; the source template ending in .json.in is not the completed manifest.

The example can also be installed under share/umicom/framework/examples/learning_pack_inspector. Follow its guide.html to select an installed developer SDK and configure the example. Creating the sample pack is part of that example configuration. There is no need to rebuild the entire application set just to read an already prepared pack.

The sample pack uses Framework compatibility version 0.9.0. Studio's shared catalogue explicitly supplies the Framework version compiled into its reader. A different embedding application can supply another version; the pack service never guesses it from the executable name. Compatibility bounds in a manifest are inclusive.

2. Open it from Studio

  1. Start Studio and open Guided Learning.
  2. Select Open local learning catalogue. A separate Learning catalogue window appears. Existing lesson-library and practicum controls remain available in Guided Learning.
  3. In Learning pack folder, choose the sample's generated pack folder, or type its absolute path. An absolute path identifies a folder independently of the directory that launched Studio.
  4. Select Load learning pack. Wait for the reading message to finish. The controls temporarily stop accepting another operation while that request is in progress.
  5. Choose a result and select Open selected. The title and verified text appear below the controls.

For example, if the generated manifest is C:\umicom\practice\learning-inspector\pack\learning-pack.json, select C:\umicom\practice\learning-inspector\pack. Do not select its parent build folder. No project needs to be open in Studio to read this pack.

Loading records the manifest's description. Opening verifies the selected resource's bytes. Neither operation proves who authored the pack. Review where content came from before treating its examples as trusted code.

3. Find a guide or example

Type a title word or topic in the search field and select Search catalogue. Leave it empty to browse. Search covers resource identifiers, titles, topics and pack titles. It does not search every paragraph inside the files.

Up to eight words separated by ordinary spaces can be entered. Every word must match somewhere in those metadata fields. ASCII letters ignore case; other characters match their stored bytes. There are no wildcard or regular-expression operators. If results are shortened, refine the query. The panel displays up to 128 results, and the search summary reports the total matching resources.

Several packs can share a catalogue, up to the shelf's limit of 32. Their identifiers must be different. Loading the same identifier again reports that it already exists and keeps the earlier pack. To use an edited replacement, close this catalogue window, open a new one and load the replacement. This version does not provide an in-place pack replacement control or persist a list of loaded packs between windows.

4. Move through reading history

Open two resources from the same pack, then use Back and Forward. History belongs to the current reading session and retains at most 64 selections. Opening a resource from another pack starts a reader for that pack; history across different packs is not combined. Search results can change without modifying the current document.

Reload and verify reads the current selection again. If its file no longer matches the manifest, the reader reports a failure and keeps the previous verified content. It does not overwrite the manifest hash to make a changed file appear valid. Close the window and load a reviewed, newly generated pack when you intentionally revise its content.

5. Make a practice copy

A practice copy is a new file that you can inspect and edit without changing the supplied example. This action copies one declared example; it does not copy an entire project, open a project or grant permission to run code.

  1. Open a source example in the reader, or a guide whose manifest explicitly links to an example.
  2. Select Preview example details. Check the example identifier and relative filename in the status message. A guide without an example link reports that no example was found; no destination is written.
  3. Choose an existing practice folder that you control. In the destination field, enter an absolute filename which does not exist, such as C:\umicom\practice\my-learning-example.c. The parent folder must already exist. The file chooser also allows you to choose a new filename.
  4. Select Copy example to new file. This explicit action captures the current example and destination before work starts. Wait until the controls become available again.
  5. Expand Last example copy. Check the captured path, Verified source, Created, bytes written and Complete. A complete result means the byte copy finished; it is not a compiler, test or security result.
  6. Review the new file in Studio before building it. Follow the example's guide for its required headers, libraries and build settings. A single copied source file may depend on other project files.

The worker rechecks the source against the pack's hash before creating the new file. An existing destination is refused without overwriting it. A source that has changed is also refused. Changing search text or the selected document after completion does not relabel the saved receipt: it continues to identify the example and path used for that copy.

If a write fails after creating a file, the receipt identifies the partial new file. Inspect it before choosing another destination. The catalogue does not remove it automatically. Closing the window after accepting a copy does not cancel or undo that write. Let orderly application shutdown finish and inspect the destination before retrying.

6. Understand display and shutdown limits

SituationReader behaviour
UTF-8 source or plain textShown as text after byte verification; no compilation or execution.
HTML guideA bounded plain-text preview. Layout, interactive controls and illustrations are not rendered.
Image or binary contentAn explicit limitation notice; it is not interpreted as a program.
Resource larger than 1 MiBThe native reader refuses the read. The host's allocation budget is separate from pack metadata limits.
Close during readingNew operations are refused. An accepted native file read finishes privately and its result is discarded.

A native filesystem read can block, particularly on an unavailable mounted drive. Closing a panel does not promise to interrupt that operating-system operation. With a GtkApplication host, an accepted read keeps the application's event loop alive until its completion is handled. This prevents the last window from closing before callback cleanup. A host with its own main loop must keep that loop running until UmiLearningCatalogueGtk4PendingReads() returns zero. An explicit g_application_quit() ignores application holds; an embedding host must drain accepted jobs before calling it. This requirement applies to accepted reads and practice copies. Forced process termination is not orderly cleanup.

7. Diagnose a refusal

  1. No manifest found: check the selected folder contains learning-pack.json, including its exact filename. Select the generated pack rather than the source-template folder.
  2. Incompatible version: compare the manifest's compatibility bounds with the embedding reader's documented version. Do not widen them without reviewing the material against that version.
  3. Changed content: compare the file against its reviewed source. Reconfigure the example to generate a consistent copied pack. Loading a new window is necessary to adopt its new manifest.
  4. Too many search terms: use no more than eight words, or clear the field and browse.
  5. Path refused: use an ordinary absolute root. Resources must use declared relative paths below it; links and reparse points below the root are not followed.

When reporting a problem, include the operation, status text, application and Framework revisions, and a small non-private example that reproduces it. A passing command-line reader check does not prove the Studio interface works; verify the actual load, search, history and close workflow in the native host.

For application developers, Connect application help to verified learning packs explains exact command and diagnostic routes through this reader.

Applications can record explicit, revision-bound learning checkpoints through the separate Framework progress service. Progress controls are not yet part of this catalogue window.
