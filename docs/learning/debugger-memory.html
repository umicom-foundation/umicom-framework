Reading paused program memory

A debugger can return a memory reference for a variable. This reference is an opaque identifier owned by the adapter, not a pointer that the application should dereference. Framework passes it back to the same paused debug session and retains the returned bytes in an independent capture.

Capture bytes from an inspected variable

  1. Start a native debug session and pause at a breakpoint. Inspect a scope with UmiDebugScopeInspectionCapture and UmiDebugRuntimeInspectVariable, or inspect children of an expandable variable.
  2. Use UmiDebugVariablePageTarget to own the selected row. A scalar can expose memory even when it has no children. The compatibility root registry does not retain memory references; use the explicit scope or child page.
  3. Call UmiDebugRuntimeCheckMemory to check the current session, capability and reference. This performs no transport request.
  4. Call UmiDebugRuntimeInspectMemory with a signed byte offset, a count from 1 to 4096, and a nonzero timeout. A successful call returns an owned capture. Destroy it with UmiDebugMemoryCaptureDestroy.
  5. Copy bytes with UmiDebugMemoryCaptureRead, or format a report with UmiDebugMemoryCaptureFormat. A zero-capacity sizing call returns UMI_STATUS_CAPACITY_EXCEEDED and sets the required size, including the final NUL. Allocate that size and call again.

Understand the result

The report includes the adapter's returned address, the requested offset and count, the actual byte count, and any unreadable bytes reported after the data. Rows use relative offsets from the returned address. Hex bytes are shown in memory order. Printable ASCII bytes are shown alongside them; other bytes appear as dots. The report does not guess pointer width, Unicode encoding, byte order or data types.

Short data with no unreadable range means the adapter reached the end of readable memory. No bytes are invented to fill the request. An unreadable range may extend beyond the requested count. No follow-up read is sent automatically.

Handle changes and failures

BUSY means the workspace evidence changed or a native event is waiting. Process events and capture a fresh variable before reading again. NOT_IMPLEMENTED means the adapter does not advertise memory reads. NOT_FOUND means there is no memory reference or response body. Malformed responses and data larger than the requested count are rejected as a whole.

The request leaves root registries unchanged. Existing caller-owned captures remain readable after the session or workspace is destroyed, but they remain historical values. UmiDebugMemoryCaptureValidate compares workspace generations; it does not poll the adapter or prove memory is unchanged. All live operations belong to the debugger's owner thread and are synchronous with a bounded timeout.

The strict capture decoder accepts complete JSON and canonical padded base64. It rejects duplicate recognized members, invalid text, missing addresses, truncated payloads and excessive data. The earlier memory API and decoder remain available for existing consumers; applications needing the owned stopped-variable workflow should use this interface.

Extend the shared feature

Frontends should keep request orchestration thin and use Framework for validation, decoding and report formatting. Add display formats from the retained byte capture without contacting the adapter again. Any future memory-writing feature needs its own deliberate action and result handling; this inspection interface never sends a write request or evaluates an expression.

See the Debug Adapter Protocol memory request for adapter-side fields and capability negotiation.
