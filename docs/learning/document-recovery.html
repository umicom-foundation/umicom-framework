Own recovery drafts independently of the editor

Recovery separates three responsibilities: capture a coherent visible document on its owner thread, persist an independent record on a worker, and restore validated source through the document coordinator. Applications choose their storage namespace and expose the shared workflow.

Capture and persist

  1. Create an identity with UmiDocumentRecoveryKeyCreate. It uses the native operating-system random provider. A random identity reduces collisions; exclusive file creation still rejects an existing destination.
  2. Call UmiDocumentCoordinatorCaptureRecovery with the intended document ID. It copies complete visible source and selection without synchronizing, saving or altering history. The stored revision describes the underlying store, not a hash of pending typing.
  3. Resolve the per-user directory with UmiDocumentRecoveryDirectory. Resolution creates nothing. An explicit save workflow may prepare that trusted user directory on its worker.
  4. Give the owned draft to UmiDocumentRecoverySave. Do not borrow a live widget or coordinator on the worker. The save creates one new file exclusively and reports the actual flush/close result.
  5. Destroy the draft after the worker finishes. It remains valid independently of its original document and window.

Discover and restore

  1. Call UmiDocumentRecoveryList on a worker. It publishes a bounded, sorted catalogue only after enumeration succeeds. Rows describe files, not validated source.
  2. Load the explicitly selected key with UmiDocumentRecoveryLoad. Rooted-file reads refuse links, limit allocation and verify that the encoded identity matches the selected filename.
  3. Present the complete source and original path as literal text. Check that the displayed preview still matches the loaded draft before allowing restoration.
  4. On the coordinator thread, call UmiDocumentCoordinatorRestoreRecovery. It attaches a new unsaved working copy and restores its selection. No original path is opened and no existing document is replaced.

The GTK form uses weak window references for completion, an invalidatable editing lifetime and cancellation tokens. Workers receive copied paths, identities and owned drafts. The application supplies no second document model. A detached or closed form cannot restore source, even if its controls are retained by another observer.

Schedule periodic capture explicitly

  1. Create UmiDocumentRecoverySchedule, then configure an enabled interval with a monotonic millisecond timestamp. The model starts disabled and performs no I/O.
  2. On the document owner thread, collect UmiDocumentCoordinatorObserveRecovery and pass the complete set to UmiDocumentRecoveryScheduleObserve. The existing pending-text cache avoids copying unchanged drafts on every poll.
  3. Call UmiDocumentRecoveryScheduleBegin. A successful ticket identifies one changed dirty document; only one ticket can be pending. Capture that source immediately on the same thread, before yielding to native events.
  4. Write the independent draft on a worker. For bounded automatic storage use UmiDocumentRecoverySaveWithinBudget.
  5. Call UmiDocumentRecoveryScheduleFinish with the exact ticket and real storage result. Only a successful write acknowledges the captured revisions. Later observations are not marked saved by an older completion.
  6. Show failures and require an explicit enable to resume. Failures before Begin can use UmiDocumentRecoveryScheduleSuspend. Disabling prevents new work while allowing an already-started write to finish.

The GTK binding implements this sequence with a one-second scheduling poll, one storage worker and a session-only opt-in. The form uses a one-minute interval. Applications can observe status through UmiGtk4AdapterObserveRecovery to explain failures when the form is closed. The callback runs last on the owner thread and can retire its binding safely.

Document IDs must belong to one coordinator lifetime; they are not durable identities across application restarts. A ticket borrows its schedule identity until Finish. Keep the schedule alive while workers may complete, or retire their authority before destruction as the GTK binding does. Never accept a late result into a new coordinator with coincidentally reused document IDs.

The admission helper counts matching record sizes, refuses capacity overflow and reuses exclusive creation. It never prunes records. Serialize application writes; another process can race an admission check, so this is not a cross-process storage quota.

Record boundaries

The record uses ordered decimal lengths followed by raw UTF-8 metadata and source. Its decoder rejects unknown framing, signed or overflowing lengths, missing delimiters, embedded zeros, invalid UTF-8, invalid selection boundaries and trailing bytes. Selection offsets count UTF-8 bytes and cannot split a scalar or CRLF pair. Source is bounded to 8 MiB.

The catalogue uses a shallow streaming directory scan instead of collecting every filename before applying a limit. It allows 256 matching records within 4096 visited entries. No content is loaded until a caller chooses a row. New consumers can reuse UmiDirectoryScanShallow with a private candidate collection and publish it only after success.

Storage and concurrency

Use a directory controlled by the user. Exclusive creation refuses existing leaves, but trusted parent aliases and concurrent renames are not an isolation boundary. Rooted reads recheck selected paths. Serialize operations for a given application. A cancelled save writes nothing before creation; once creation starts it completes the bounded write and reports its outcome. A partial failed record may remain for diagnosis. Directory power-loss durability is not guaranteed.

Records contain plaintext private source; no API here is an encryption or credential vault. No network or automatic pruning occurs. The native form also offers explicit opt-in periodic recovery through the shared scheduler; it does not save original source files. The earlier recovery manager and its format remain available to existing callers and are not silently reinterpreted by this service.

When extending recovery, cover interrupted writes, malformed records, stale selection, retained windows, full document capacity and owner destruction. Keep original paths descriptive until the user explicitly saves the restored draft.
