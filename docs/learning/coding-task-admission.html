Use one provider identity when planning coding tasks

A coding task combines a request, general workspace context and repository context. Each may have a privacy classification. If the general planner treats a runtime as remote while the repository planner treats it as local, the resulting plan can violate the intended sharing limit. Framework therefore obtains the provider kind from the selected runtime catalogue entry and uses that identity throughout preparation.

1. Treat the caller's provider kind as an assertion

umi_ai_coding_assistant_prepare retains its existing provider-kind argument. An unknown value returns UMI_STATUS_INVALID_ARGUMENT. A known value that disagrees with the selected runtime returns UMI_STATUS_PERMISSION_DENIED. The argument cannot override or relabel the runtime.

Register a descriptor that accurately represents the actual integration. Catalogue admission checks its metadata, not the truth of a claimed endpoint, provider or network location. The host still owns configuration trust, connection policy and execution consent.

2. Classify the instruction as well as retrieved context

umi_ai_coding_request_validate accepts only public, internal, confidential or restricted classification values. Planning checks the request classification against the selected provider's sharing ceiling and sensitive-approval rules. It then asks AuthorEngine to plan general context and uses the same provider identity for repository context.

InputExample outcome
Public request; remote ceiling public; remote access permittedThe request may be planned. Internal repository files remain omitted.
Internal request; remote ceiling publicThe whole request is refused, even when there are no repository files.
Restricted request allowed locally; sensitive approval missingPreparation is refused while the approval rule applies.
Remote runtime labelled local by callerProvider mismatch is refused before context selection.

Classifications are supplied by the host. These checks do not inspect instruction content to discover secrets or establish that a classification is correct. Review the selected material and classify it conservatively.

3. Prepare through the native service

The following function assumes the host has already created an assistant, registered runtime.local accurately as a local provider and obtained any required consent. Literal strings below fit the fixed fields. Real input needs bounded copying with an explicit overflow response.

#include "umicom/ai/coding_assistant.h"
#include <string.h>

UmiStatus explain_source(UmiAiCodingAssistantService *assistant,
                         UmiAiCodingTaskPlan *plan)
{
    UmiAiCodingRequest request;
    umi_ai_coding_request_init(&request, UMI_AI_CODING_TASK_EXPLAIN);
    strcpy(request.request_id, "explain.1");
    strcpy(request.session_id, "editing.1");
    strcpy(request.runtime_id, "runtime.local");
    strcpy(request.workspace_root, ".");
    strcpy(request.active_path, "src/calculate.c");
    strcpy(request.language_id, "c23");
    strcpy(request.instruction, "Explain this calculation.");
    request.classification = UMI_AI_DATA_INTERNAL;
    return umi_ai_coding_assistant_prepare(
        assistant, &request, UMI_AI_PROVIDER_LOCAL, plan);
}

Allocate the large plan outside a small thread stack when appropriate. A successful plan contains copied request metadata, selected repository entries and token estimates. It does not read those files or invoke a provider.

4. Publish a complete plan or preserve the previous one

The shared value-construction helper builds a temporary candidate on the heap. Every refusal, including allocation failure, leaves the caller's previous output, task history and service revision unchanged. The request may borrow fields from the previous output because publication happens after all input reads.

Only a successful plan advances the service revision and enters history. At the fixed history capacity, the oldest accepted task is replaced. An exhausted revision or an invalid owner count is refused before publication. This prepare boundary does not establish the behavior of unrelated service mutations; those contracts need their own qualification.

5. Interpret readiness and budgets accurately

ready means that metadata planning was accepted. It does not prove that a model is healthy, a session exists, a complete serialized prompt fits, or execution is authorized. Context token values are estimates supplied by the host. The instruction and final prompt formatting still need token accounting at invocation time.

The repository budget is the smaller of the request's context budget and the space remaining after general context. A zero remaining repository budget is valid: optional repository entries are omitted and marked as dropped. Required general context that cannot be shared or fitted still refuses the plan.

Planning and eventual execution are separate operations. Policies, context and runtime configuration can change between them. Keep serialized owner access, review the accepted material and revalidate relevant identities and consent before invocation. A saved plan hash is a deterministic metadata indicator, not cryptographic authentication or a durable execution permit.

6. Exercise the refusal and history paths

  1. Configure and build Framework with tests enabled using the documented platform preset.
  2. Run ctest --test-dir <framework-build> -R "^framework[.]ai[.]coding-task[.]" --output-on-failure.
  3. Check invalid classifications and provider kinds, both directions of provider mismatch, request privacy refusal, remote-provider consent and mandatory general-context refusal.
  4. Check unchanged output and history after failure, borrowed output fields, exhausted revisions, rolling history and a zero repository budget.
  5. Run the installed local-model SDK consumer. Its task example plans offline metadata; it does not contact a provider.

Expected results are explicit refusals without publication for inadmissible requests, and one history entry and revision advance for accepted plans. Preserve the source identity and output for failed cases. Registered tests, written examples and successful configuration are not evidence that native tests or product workflows passed.
