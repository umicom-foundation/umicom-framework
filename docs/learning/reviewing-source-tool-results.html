Review source-tool results in an open document

A formatter or language server can finish after the user has typed more text. Framework's document source request keeps the original draft, identity and caret together. It stages a complete replacement for review and commits it through the same document history as ordinary editing.

Capture, work, review and apply

  1. On the document coordinator's owning thread, call UmiDocumentSourceRequestCreate with the intended document ID. An empty draft is allowed. A read-only draft is refused. Creation changes neither the live draft nor its saved file.
  2. Read the metadata with UmiDocumentSourceRequestInspect and the complete UTF-8 source with UmiDocumentSourceRequestRead. Copy both before starting a worker. Keep the request on its owning thread; a worker must not access the coordinator, workbench or GTK text buffer.
  3. Perform the source operation against the worker's copy. Convert byte offsets to language-server positions using UmiEditorTextViewPositionAt. Language-server columns count UTF-16 units, which can differ from UTF-8 bytes. The shared conversion rejects a position inside a character or CRLF line ending.
  4. Return a complete UTF-8 result and its proposed caret byte offset to the owning thread. Call UmiDocumentSourceRequestCheck before presenting it. Call UmiDocumentSourceRequestStage with the request's current review revision. Staging owns a copy and advances that revision; it does not edit the document. Empty text explicitly proposes deleting the entire draft.
  5. Read the exact staged text with UmiDocumentSourceRequestProposed and display it alongside the captured source. Give the user separate accept and cancel actions. Record the review revision being displayed.
  6. Only after acceptance, call UmiDocumentSourceRequestApply with that displayed revision and approval set. Framework repeats the identity, revision, conflict, text and caret checks. A changed active tab never redirects the edit to a different document.
  7. Destroy the request when the review ends. Destroying a request never applies its proposal. Keep its original coordinator, store and workbench alive until all checks and application attempts have finished.

Expected result and recovery

A successful text change is one Undo action. Typing that was already visible but not synchronized to the document store keeps its earlier Undo action. An unchanged result may move the caret without adding a text-history entry. Applying a result does not save the file or contact a provider.

If Check or Apply reports a changed state, discard the old answer and make a new request. Do not copy the old proposal into the widget as a fallback. If the review revision is old, show the newly staged result and ask for a new acceptance. Failed staging leaves the earlier proposal and its revision intact.

Limits and extension points

This service accepts complete text up to the document model's byte limit. It rejects embedded NUL, invalid UTF-8 and invalid caret boundaries. It does not execute tools, resolve language-server responses, persist credentials or create an automatic-save policy. Use a language-specific planner on the worker's copy before staging its result.

Current caret and selection values must match the capture. The service does not record every intermediate navigation event. A UI that treats moving away and back as invalidation should cancel its request when navigation occurs. Draft and saved-text revisions do detect intervening text changes even when the final bytes return to their earlier spelling.
