Choose and review a program launch

Project Settings separates three things: the executable to start, the folder it starts in, and the arguments it receives. Framework can describe these values before you save them. Reviewing settings does not build the project, start a debugger or run the application.

Select the program and its working folder

  1. Open your project in Studio, then choose Project Settings in the Build panel. The project folder identifies the open project and is read-only in this form.
  2. Choose Choose program file… and select the executable produced by your build. On Windows this is normally an .exe file. The chooser copies its complete local path into Program to run; it does not start it. If the file has not been built yet, enter its expected project-relative path manually, such as build/bin/notes.exe.
  3. Choose Choose working folder… to use an existing local folder for application data. Leave Program working folder empty to start in the project root. You may also enter a project-relative folder such as sample data. The executable path is independent of this folder.
  4. Use either the single literal argument field or the argument-list field. In the list, spaces separate values and quotes keep spaces within a value. "" supplies an empty argument. Clear the single argument before using the list.
  5. Choose Review launch settings. Read the Run program, native Debug program, working folder and numbered argument values. Backslashes, quotes and control characters in arguments are escaped for display so each value has a clear boundary. This description is not a shell command.
  6. Choose Apply Settings when the values are correct, or Cancel to discard the form edits. Build and Run/Debug remain separate application actions with their existing trust checks and build workflow.

Changing a launch field makes the description out of date. Review again before relying on it. A chooser result cannot replace a field that was edited while that chooser was open. A remote URI that has no local filesystem path is rejected; mounted remote storage may still appear as a local path.

The review highlights this last difference. To choose the same file for both actions, select its absolute path or enter a path beginning with ./. Framework does not guess which executable a bare name was intended to mean. On Windows, use a complete drive or network path; ambiguous spellings such as C:notes.exe and a rooted path without a drive are rejected by launch planning.

What the review does and does not establish

The review validates stored field bounds, argument syntax and path resolution. Control characters in paths are rejected so they cannot masquerade as extra review fields. It performs no filesystem read and no process launch. It does not prove that a file exists, is executable, matches the debugger architecture, has debug symbols, or has permission to access its working folder. A selected file can also change before launch. Relative paths and parent-folder aliases are not a security boundary.

The plan stores argument values in its own memory. Native Debug can still reject values that exceed its adapter protocol limits even when a Run description succeeds. Build tools continue using the project root for preset discovery; this working folder applies to the launched program.

Recover from a problem

  1. If review reports a missing program, choose an executable or enter its expected path. Do not put the program and arguments together in the program field.
  2. If argument review fails, check closing quotes, field lengths and whether both argument fields are filled. Clear the conflicting field, then review again.
  3. If the native chooser is cancelled or fails, existing field text is retained. You can enter paths manually. Choosing a path never silently saves the form.
  4. If launching fails after a successful review, check the build output, actual executable path, working-folder existence and permissions. For native Debug, also check the selected debugger, executable format and debug information.
  5. If a chooser is still open, finish or cancel it before applying settings. Closing the form cancels its pending chooser and prevents late results from editing a retired form.

Extend the shared behaviour

UmiBuildLaunchPlanCreate belongs to the build library and accepts an already absolute project root. Its result owns all strings and can be copied without rebinding pointers. It leaves caller output unchanged on failure. Use the shared description when adding another launch surface, and keep its compatibility distinction between unqualified Run names and project-relative debugger files visible.

UmiBuildLaunchSelectPath copies an explicit absolute selection into one profile field. It does not save the profile or grant trust. The native form retains its controller until the asynchronous chooser finishes, rejects stale selections and guards nested GTK notifications. Use the matching completion operation for file and folder selection; see the GTK file chooser API and folder chooser API.
