Bring a stock list safely into your workspace

A practical introduction to source data, reviewed imports, shared storage and clear operational decisions.

Start with a small stock list

Suppose you are preparing a community workshop. Your stock sheet says that you have twelve notebooks and eight pencils. You need to bring those figures into your application without losing track of where they came from.

Typing two numbers is easy. Doing it reliably takes a little more care. Someone should check the source, somebody else should review the proposed changes, and the application should remember what it actually imported. When a button is pressed twice, it must not create a second copy.

This lesson follows that complete journey through Umicom’s enterprise workspace. You will create a dataset, prepare a CSV import, inspect the proposed changes, approve a saved job and apply it. You will also see what happens when the source changes or an import is paused.

Use practice information.

The workspace in this lesson stores reference records on your computer. Use fictional labels and quantities, not passwords, personal information or customer records. Its practice-role selector is a teaching aid, not a login system.

You need a build of Umicom containing the Enterprise workspace. The five applications below share the same services and, by default, the same local database. Their starting tabs differ, but you can reach every tab from each application.

The Existing layouts switch keeps the earlier application workspace within reach. This lesson uses the new Enterprise workspace switch.

Understand the five things you will work with

A dataset is a named set of records. Our dataset, supplies, will contain one record for each kind of workshop material. Every record has an item ID, a label and a quantity.

A recipe tells the importer how to read the input. stock.csv preserves your labels. stock.csv.upper changes ASCII letters in labels to capitals. These are built-in rules, not downloaded programs.

A preview compares the input with the dataset. It shows inserts, updates and unchanged rows. Making a preview does not import anything.

A job is the saved instruction to perform one import. Preparing it freezes a copy of the input and the proposed before-and-after rows. Editing the form afterwards does not edit that saved job.

The activity history records accepted changes, including the practice identity, action, target and reason. A successful import saves its rows, job result and history entry together.

Source CSV→Preview→Frozen job→Review→Apply

Notice that review comes before application. This gives a person a chance to inspect the actual saved instruction, rather than approve a screen whose contents might later change.

1. Open the practice workspace

Open Umicom Marketplace. Select Enterprise workspace, then press Open practice storage. The panel displays the database path once it has tried to open it.

On a normal first run, the workspace has no datasets and no jobs. Both recipes start disabled. Opening the database does not import the example text shown in the form.

The default database lives beneath your operating system’s user-data directory, inside umicom/enterprise-workspace. The applications do not use your terminal’s current folder as their database location.

Keep an eye on Cached revision. A revision is a numbered saved change. Other open applications may still show an older revision until you press Reload shared workspace.

A useful habit

After changing data in one application, reload the workspace in the next application before continuing. This is especially important before preparing or approving a job.

When storage cannot open, read the message and check the displayed path, write permission and SQLite support in the build. The application does not silently replace failed storage with an empty, temporary workspace.

2. Enable the stock recipe

In Marketplace, choose Administrator (practice) in the role selector. Leave the recipe selector on stock.csv — preserve labels.

Open the Recipes tab and press Enable selected recipe. The recipe report should now say enabled.

You have enabled a rule for reading three CSV fields. You have not downloaded a plug-in, run a script or imported any records. Keeping these actions separate makes it easier to understand what each button does.

The second recipe is optional. Leave it disabled for now; the final exercise uses it to show how a transformation changes a preview.

3. Create a dataset for the supplies

Open Umicom Database Studio and press Open practice storage. If you already had it open before enabling the recipe, press Reload shared workspace.

Choose Author (practice). Set Dataset ID to supplies. On the Data tab, leave Dataset name as Workshop supplies, then press Create dataset.

The data report should show supplies, the name Workshop supplies, generation 1 and zero rows. A generation identifies a particular version of that dataset’s contents. It changes when an applied import changes those contents.

Use IDs that start with a letter or digit. After that first character, letters, digits, dots, underscores and hyphens are accepted. IDs are case-sensitive: supplies and Supplies are different names.

Creating the same dataset again with the same name does not make another dataset. Reusing its ID with a different name is rejected rather than overwriting it.

4. Read and preview the CSV

Open Umicom Integration Studio, open its practice storage and reload it if necessary. Choose Author (practice). Check that the Dataset ID is supplies and the recipe is stock.csv.

On the Import tab, the upper text area is editable. Replace its contents with the following text:

item_id,label,quantity
notebooks,Notebooks,12
pencils,Pencils,8

The first line is the header. It names the three fields and must be exactly item_id,label,quantity. Each following record gives an item’s ID, its label and its quantity.

Press Preview editable CSV. In the lower result area, look for two INSERT changes. The proposed quantities should be twelve and eight. Database Studio will still show zero rows: a preview has not changed its dataset.

When a label contains punctuation

A comma inside a label needs quotation marks around the field. A quotation mark inside a quoted label is written twice:

item_id,label,quantity
cards,"Cards, with a ""welcome"" message",4

Quoted labels may also contain line breaks. Quantities, however, must contain decimal digits only. A negative sign, decimal point or space in the quantity is rejected. Every item ID must occur only once within an import.

When the parser rejects a record, the message identifies the logical CSV record and field where possible. The header is record 1. Fix the input and preview again; a rejected preview has not partly imported the earlier rows.

5. Save the proposed import as a job

Return to the two-row notebooks-and-pencils example. Set Job ID to stock-opening, then press Prepare frozen job.

Open the Jobs tab. The job should be listed as Review required, with author recorded as its author. Its proposed rows remain visible in the Import tab’s result area.

The job ID also prevents accidental duplicate preparation. Pressing Prepare again with the same ID, same input, same dataset, same recipe and same author returns the existing job. Changed input under that same ID is refused.

To make the distinction visible, change the editable quantity 12 to 99 without preparing another job. You have changed the form, not stock-opening. Its saved proposed quantity is still twelve. Restore the editable form to twelve before continuing, or leave it changed to test the distinction carefully.

One ID, one saved instruction

When the intended input really changes, use a new job ID. Keep the previous job for review; cancel it when it should no longer be applied.

6. Review the saved job

Open Umicom Operations, open storage and reload. Choose Reviewer (practice). Enter stock-opening in Job ID.

On the Jobs tab, press Load frozen job. Now open the Import tab and read the lower result area. It shows the saved job’s proposal, not a new interpretation of the editable CSV above it. Check the dataset, recipe, row IDs, labels and quantities.

Return to Jobs. Leave the review reason as Checked against the stock sheet, or write your own clear explanation. Press Approve. The job should change to Approved.

The author cannot approve their own job, even when supplied with a role that otherwise permits review. In this lesson, choosing another practice identity demonstrates that separation. It does not prove that two real people have signed in.

Changing the practice role, reloading the workspace or completing a job action clears the panel’s review selection. Load the frozen job again before the next consequential action. Pressing Preview editable CSV also clears that selection, because the displayed proposal then belongs to the editable form instead.

7. Apply the approved import

Choose Operator (practice) in Operations. Press Load frozen job again, inspect the saved proposal, then press Apply approved job.

The job should now say Applied. Open Database Studio, reload its shared workspace and inspect the Data tab:

Item IDLabelQuantitySource job
notebooksNotebooks12stock-opening
pencilsPencils8stock-opening

The source-job column explains where each current row came from. The dataset generation is now 2 because its contents changed.

Back in Operations, load the applied job and press Apply again. The saved job remains Applied and the rows remain twelve and eight. The service recognises completed work rather than repeating it.

Inspect the activity history

The lower Jobs report records accepted changes. For this clean example, you should see recipe enablement, dataset creation, job preparation, approval and application. Failed attempts do not consume an accepted-change revision. This history is not a complete security-event log of every attempted action.

8. Update a record without replacing the dataset

In Integration Studio, reload, select Author and change the editable CSV to:

item_id,label,quantity
notebooks,Notebooks,20
pencils,Pencils,8

Use a new Job ID, stock-recount. Preview first. You should see one UPDATE, changing notebooks from twelve to twenty, and one UNCHANGED row for pencils.

Prepare, review and apply the new job using the same sequence as before. Reload Database Studio. Notebooks should now show twenty and source job stock-recount. Pencils keep their original source job because their value did not change.

An import updates or inserts only the listed rows. Leaving an existing item out of the CSV does not delete it. An import whose rows are all unchanged can still have a completed job record, but it does not advance the dataset generation.

9. Check access and practise pausing imports

Open Umicom Security Centre, open its practice storage and reload. Choose Viewer (practice). On Access, leave Capability as enterprise.job.execute and Resource ID as stock-opening. Press Check access without executing.

The result should be Denied. Select Operator and run the check again: that role has the execution capability. Neither check executes the job.

A capability is only one condition. A job must also be approved, its recipe must remain enabled, its target dataset must still match the reviewed generation, and imports must not be paused.

Choose Administrator and press Pause imports. Prepare a new job in the usual way. An attempt to apply it is refused while the pause remains in force. The approved job and existing rows remain saved. Resume imports as Administrator, reload the other application and inspect the job again before retrying.

The pause affects this enterprise reference-data workspace only. It does not stop Bank, Trader, operating-system processes or other Framework services.

10. Recover without guessing

Another application saved first

A stale workspace message means your local view no longer matches saved state. Press Reload shared workspace. Do not keep pressing Apply against the old view.

If the target dataset itself changed after a job was prepared, that job’s before-and-after comparison is no longer current. Cancel the unfinished job, prepare the intended input under a new ID, and review the new comparison. Merely reloading does not rewrite an old approved proposal.

Storage failed during application

The service writes the changed rows, job outcome and history in one transaction. When a write fails and rollback succeeds, none of those changes is published. Reload and inspect the job before retrying. An approved job remains retryable while its other conditions still hold.

If rollback itself fails, close the affected workspace instance and investigate storage before reopening it. Do not treat a failed recovery as a successful import.

A job was rejected or cancelled

A rejected or cancelled job is retained but cannot later be applied. Prepare a new job for corrected input. This keeps the original decision and explanation available.

You closed the application

Reopen its practice storage to read saved datasets and jobs. Opening or reloading storage does not automatically run jobs. An already Applied job is still recognised as completed.

Know what this workspace does—and does not do

The lesson uses deliberately small catalogues so that the entire import can be inspected and tested. One workspace supports eight datasets, sixty-four rows per dataset, thirty-two rows per import, sixteen retained jobs and 128 accepted changes. CSV input may contain up to 16,384 UTF-8 bytes. Labels may use up to 191 UTF-8 bytes; some characters use more than one byte.

These limits are enforced, not silently bypassed. The workspace does not erase old jobs or activity to make room. Keep a completed practice database and use a separate database for another exercise when necessary.

This is a reference-data import workspace. Database Studio does not gain an arbitrary SQL console from this lesson. Integration Studio does not contact an external service. Operations does not run background operating-system tasks. Security Centre’s roles are not authenticated sessions. Marketplace manages two built-in recipes rather than installing external packages.

The database contains plaintext source CSV, proposed changes and records. Its consistency checks detect accidental corruption; they are not encryption or a defence against somebody who can edit the database directly.

Use a separate practice database when launching from PowerShell

Set an absolute filename before starting an application. Every application taking part in the same exercise must inherit the same setting.

$env:UMICOM_ENTERPRISE_WORKSPACE_DB = "C:\umicom\Practice\workshop-two.sqlite"
& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-marketplace.exe"

A desktop shortcut will not automatically inherit a setting entered in a separate PowerShell process. The displayed path is the quickest way to check which database an application actually opened.

Follow the same workflow in C23

The applications share one public interface: umicom/enterprise_workspace/workspace.h. The example below is the source of the delivered command-line practice program. It uses the same parser, policy services and transactions, but stores its records in memory rather than a file.

UmiStatus is the result of an operation. The next step runs only when the previous one returned UMI_STATUS_OK. The workspace borrows the Data Server and authorisation service, so it is destroyed before those services.

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/enterprise_workspace_main.c
 * PURPOSE: Follow the same reviewed import from the command line, using memory only.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/

#include "umicom/enterprise_workspace/practice.h"
#include <inttypes.h>
#include <stdio.h>
#include <string.h>
/* This example uses real policy, parser and transaction implementations.
 * Practice actors explain duties; they do not authenticate a real person. */
int main(void)
{
    UmiEnterprisePracticeAccess *access=NULL;UmiDataServer *data=NULL;
    UmiEnterpriseWorkspace *workspace=NULL;UmiEnterpriseRow row;
    const char csv[]="item_id,label,quantity\nnotebooks,Notebooks,12\npencils,Pencils,8\n";
    UmiStatus status=UmiEnterprisePracticeAccessCreate(&access);
    if(status==UMI_STATUS_OK)status=umi_data_server_create_memory(&data);
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceOpen(data,UmiEnterprisePracticeAuthorisation(access),&workspace);
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceSetRecipe(workspace,UmiEnterprisePracticeActor(4),"stock.csv",true);
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceCreateDataset(workspace,UmiEnterprisePracticeActor(1),"supplies","Workshop supplies");
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspacePrepare(workspace,UmiEnterprisePracticeActor(1),"stock-opening","supplies","stock.csv",csv,strlen(csv),NULL);
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceReview(workspace,UmiEnterprisePracticeActor(2),"stock-opening",true,"Checked against the stock sheet");
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceExecute(workspace,UmiEnterprisePracticeActor(3),"stock-opening");
    for(size_t i=0U;status==UMI_STATUS_OK&&i<2U;++i){status=UmiEnterpriseWorkspaceRowAt(workspace,"supplies",i,&row);
        if(status==UMI_STATUS_OK)(void)printf("%s | quantity %" PRIu64 " | source job %s\n",row.id,row.quantity,row.sourceJob);}
    /* Exact repeated execution returns its saved result without importing again. */
    if(status==UMI_STATUS_OK)status=UmiEnterpriseWorkspaceExecute(workspace,UmiEnterprisePracticeActor(3),"stock-opening");
    if(status==UMI_STATUS_OK)(void)puts("Practice complete. Two rows imported once. No network request or file write was made.");
    else(void)fprintf(stderr,"Enterprise practice failed with status %d.\n",(int)status);
    UmiEnterpriseWorkspaceDestroy(workspace);umi_data_server_destroy(data);UmiEnterprisePracticeAccessDestroy(access);
    return status==UMI_STATUS_OK?0:1;
}

After building, run one of the umicom-…-enterprise-workspace-example.exe programs from the build’s bin directory. All five application examples use this same source. They should print the two quantities and finish with a message confirming that no network request or file write was made.

Try these exercises

1. A label containing a comma

Prepare a job containing an item labelled Notebooks, ruled. Quote the label correctly, then check the preview before saving the job.

Check your answer
item_id,label,quantity
ruled,"Notebooks, ruled",6

The preview should show one label containing a comma, not an extra field.

2. A harmless failed review

Prepare a fresh job as Author. Try to approve it without changing identity. What remains unchanged?

Check your answer

Approval is denied. The job remains Review required and no rows are imported.

3. A transformation you can inspect

Enable stock.csv.upper as Administrator. Prepare a new job using the label blue folders. What should appear in its proposed row?

Check your answer

The label becomes BLUE FOLDERS. The rule changes ASCII letters only. It does not claim to perform language-aware uppercase conversion for every script.

4. Two competing recounts

Prepare two jobs against the same dataset generation. Review and apply the first, making a real change to a row. Try to approve or apply the other. Explain why the application asks for a new proposal.

Check your answer

The second job describes an older starting state. A fresh preparation compares against the current dataset instead of silently using an outdated review.

When you can explain the difference between editable input, a frozen proposal and an applied result, you understand the central control in this workflow. That distinction is useful far beyond stock lists.
