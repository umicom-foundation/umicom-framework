Resolve type and implementation locations

The shared navigation API supports definitions, references, type definitions and implementations. Each operation has its own protocol method and provider capability, while complete result ownership, exact positions and source-opening checks stay in Framework.

  1. Include umicom/language_runtime/navigation_query.h and link Umicom::developer.
  2. Capture complete UTF-8 source, its exact document URI and the caret byte offset. Copy those inputs and the server profile before dispatching a worker.
  3. Choose UMI_LANGUAGE_NAVIGATION_TYPE_DEFINITION or UMI_LANGUAGE_NAVIGATION_IMPLEMENTATION in UmiLanguageNavigationRequest.kind. Set include_declaration to zero; that option affects references only.
  4. Call UmiLanguageNavigationQueryNative. Framework checks the requested provider independently, negotiates UTF-16 positions, synchronizes the primary draft and sends the selected request. Keep input memory alive until it returns.
  5. On success, inspect the owned UmiLanguageLocationCatalogue. Both new intents accept complete locations and location links. A link can distinguish the destination's surrounding range from the precise symbol selection, and can include an origin range in the captured source.
  6. Return results to the document owner. Recheck the captured identity and source, then use the shared document navigation operation to validate and open the chosen local destination.
  7. Destroy the catalogue when it is retired. No URI is opened, source edited or file saved by the protocol query itself.

Preserve operation boundaries

typeDefinitionProvider authorizes textDocument/typeDefinition; implementationProvider authorizes textDocument/implementation. Unsupported capabilities return an error before opening the source. The query never falls back to a different navigation intent.

Primary destination ranges and link origin ranges are checked against captured source. External destination ranges remain untrusted until checked against the actual destination text. A malformed row rejects the complete result rather than publishing a subset.

The existing native bounds apply: serialized messages must fit 65536 bytes, initialization and query reads share the caller's timeout, and read cleanup has a separate 250-millisecond allowance. Results are withheld when closure or shutdown fails. Cooperative cancellation does not interrupt native startup or synchronous writes. Only the direct child process is owned.

The OnServer API accepts an exclusively owned STARTING connection. Invalid preflight leaves it untouched; initialization transfers cleanup responsibility to the query. The caller destroys the server object after return.

Extend the client safely

Keep new navigation intents explicit in the enum validation, client capabilities, provider lookup and method selection. Reuse the complete location catalogue and document owner rather than adding a separate editable source model. An application should expose the chosen intent clearly and retire results after source or settings changes.

These queries synchronize one captured draft. They do not provide a persistent project index or automatically synchronize other open drafts. See source navigation for local destination handling.
