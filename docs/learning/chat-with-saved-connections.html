Chat with a saved connection

This workflow sends one reviewed text request through a connection you explicitly select. Framework owns the request, credential checks and reply handling. Studio provides access through its Connections window. No project files, previous messages or tools are added automatically. A reply is displayed as text and cannot run commands, apply a patch, publish code or change another application.

1. Select the destination

  1. Open AI Coding → Connections… in Studio.
  2. Select an enabled, saved connection with a model identifier. Save or discard any draft first. Follow Edit provider connections to create one.
  3. For OpenAI, use provider alias openai, a Remote HTTPS route and either https://api.openai.com/v1/responses or https://api.openai.com/v1/chat/completions. Use a vault: reference to a key in this application's local profile.
  4. For a compatible local server, use local-chat, Local loopback and http://127.0.0.1:8080/v1/chat/completions with your server's port. Keep the credential reference empty. Start the server separately.
  5. Choose Chat with selected saved connection…. Opening the window sends nothing. Its selected connection and revision are fixed for that window.

You can first run a model-catalogue check, but a listing does not prove that inference is available. A generation request can still fail because of account permissions, unsupported model options or server limits. Other remote providers, custom gateways and key-protected loopback servers are not supported by this adapter.

2. Prepare the text

  1. Type your prompt. It may contain up to 4,096 UTF-8 bytes. A character can occupy more than one byte, so non-ASCII text may reach the limit sooner.
  2. If needed, paste context into Optional context you choose to send, up to 8,192 UTF-8 bytes. Check it for private material before continuing. Context is part of the user message; it is not a grant of permission to execute tools.
  3. Choose an output-token limit from 16 to 4,096. This bounds output generation, including reasoning tokens where the provider counts them; it is not a spending limit for the whole account.
  4. Copy any previous reply you want to keep, then choose Review request. Starting another review clears the earlier reply. A worker reads saved settings and creates an immutable request. The window shows the exact destination, model, limit, saved revision and complete user message, including the context separator.

Changing the prompt, context or output limit discards the review. The window keeps the text so you can review it again. If another window changed saved settings, return to Connections, reload and open chat from the current selection. A draft or stale revision never silently selects a new destination.

3. Approve one send

  1. For a remote connection, enter the local profile password. It verifies access to the saved key on this computer; the password itself is not sent. See Manage local provider keys to create the profile and save a key.
  2. Read the displayed request and check I approve sending this reviewed text to the displayed destination. Changing the password removes this approval.
  3. Choose Send reviewed request once. The password entry clears, and the worker owns a short-lived copy until verification completes. Remote requests send the API key and reviewed text to the approved service and may incur charges.
  4. Wait for the reply or choose Cancel request. Cancellation stops waiting when the transport can observe it; it cannot retract a transmitted request or guarantee that remote generation stops.

Each approved attempt consumes its review, including denied credentials, timeouts and failed replies. To try again, choose Review request and approve a new attempt. There is no automatic retry: a timeout can leave the remote outcome uncertain. Normal closing waits for an active operation; forced retirement requests cancellation while the worker retains its own resources.

4. Read the result and clear local text

The result shows plain text and the model identifier reported by the provider, which may differ from an alias you selected. Refusals and output-limit truncation are labelled. A truncated answer is incomplete. Tool calls, unexpected output kinds, malformed JSON and oversized replies are rejected instead of being interpreted as actions.

  1. Review the reply as untrusted generated text. Copy useful material deliberately and check it before using it.
  2. For a follow-up, write another prompt and explicitly include any context you still want to send. Previous messages are not attached automatically.
  3. Choose Clear local text when finished, or confirm discarding the window's unsaved text before closing.

This workflow does not save a transcript or request body to the local database. It clears owned request, credential and reply buffers when they are retired. GTK, the operating system, clipboard history and third-party transport libraries may have internal copies outside that ownership boundary. Existing Studio chat, agent, comparison and patch controls keep their separate routes and approval policies.

Privacy and supported limits

Requests use the Responses API or the Chat Completions API according to the saved endpoint. They explicitly disable response storage and streaming and attach no conversation identifier or previous response. store:false is not a promise of zero provider retention: provider abuse-monitoring and other applicable data policies still apply. Read OpenAI data controls before sending private material.

Remote requests require the existing Windows native credential adapter and a freshly verified local profile password. A profile password is an application policy, not isolation from other programs running as the same operating-system user. Loopback requests contain no key; they do not authenticate the process listening on the port.

The shared HTTP transport requires its compiled capability. It verifies HTTPS certificates and hostnames, follows no redirects, uses no proxy or netrc credentials and makes no automatic retry. Replies are bounded to 65,535 bytes, 4,096 JSON tokens and 128 nesting levels. Visible reply text is limited to 16,384 UTF-8 bytes and the reported model to 512 bytes. Exceeding a limit leaves the reply inconclusive; text is not silently truncated to fit.

Troubleshooting

ObservationNext step
Review refuses changed settingsReload the connection in Connections and open a new chat window. Preserve your typed text before discarding the old window.
Send is unavailablePrepare a valid review. If transport support is absent, the adapter cannot send; it does not substitute a simulated reply.
Permission denied, HTTP 0Check the local password, profile scope, saved key and approval. Repeated denials introduce a delay in this window. Prepare a new review to retry.
HTTP 401 or 403Review the provider key and permissions in your account privately. A local key check does not prove remote access.
HTTP 429, 503 or timeoutWait and review the provider's limits. A transmitted request may have completed; decide deliberately whether to send again.
Malformed or unsupported replyCheck protocol compatibility. Raw error bodies are not shown. A reply containing actions is not accepted as an ordinary text answer.

A zero HTTP status means no valid status was recorded, not necessarily that no network activity occurred. A remote request may consume tokens even if the local application cannot decode its reply.

For contributors

Link Umicom::provider_chat. Prepare an opaque UmiProviderChatPlan, display its connection, exact input and output limit, then call Run only after approval. Keep the plan and borrowed store alive for the synchronous call; use a worker in graphical applications. Approved calls are single-use even when they fail. Destroy clears the immutable request; the caller owns and clears the result.

GTK hosts can use UmiProviderChatGtkPresent with an explicit saved connection ID, scope, absolute settings path and revision. Presentation remains in Framework. Add provider support through an explicit destination policy, bounded codec and regression coverage. Keep response text separate from any future coding or tool-execution approval.

To include an explicit Studio editor selection, follow Chat about selected code. The selected draft is copied locally before connection choice and full request review.

Continue with selected earlier text

The chat window can keep up to eight completed exchanges in memory. Select an excerpt from an earlier request or reply to replace the next request's context, then review and approve it again. Follow Choose context for a chat follow-up for history limits, forgetting entries and clearing local copies.
