Recover an import without losing the original review

Keep the old proposal, inspect the changed data, and create a new job that someone can review honestly.

1. What you will build

Imagine that your workshop has twelve notebooks. You prepare a file that will set the recorded quantity to twenty, and another person reviews it. Before you apply it, a stock count changes the saved quantity to fifteen. The original review no longer describes the change you would make.

The correct response is not to force the old job through or silently rewrite its approval. Keep the original, calculate a new proposal from the current data, and ask for a new review. In this lesson you will follow that sequence, then browse a stable copy of the resulting dataset.

Original review12 → 20Intervening stock countSaved quantity becomes 15New review15 → 20; old job retained

Umicom Database Studio, Integration Studio, Operations, Security Centre and Marketplace share the same enterprise workspace. Their starting tabs differ, but the data and workflow rules belong to Framework. This exercise changes only fictional reference data, not orders, bank balances or operating-system settings.

Before you start: use a successfully built Umicom installation and a disposable practice database. The command-line lesson uses memory only and is the simplest place to begin. Graphical steps require the GTK-enabled application and a build with SQLite support.

2. Understand the records before changing them

TermMeaning in this exercise
DatasetA named collection of rows, such as supplies.
RowAn item ID, a label, an unsigned quantity and the ID of its last applying job.
RecipeA supported mapping rule. stock.csv preserves labels; stock.csv.upper uppercases ASCII letters only.
JobThe frozen CSV and its before/after proposal, kept under a unique ID.
GenerationThe dataset’s change counter. A different generation makes an older import proposal stale.
Workspace revisionThe change counter for the whole workspace, including jobs, decisions and controls.
SnapshotAn owned copy of a particular loaded state. Paging through it does not fetch newer rows.

The CSV quantity is a replacement value, not an increment. A row containing 20 means “set this item to twenty”, not “add twenty”. Updating one item does not remove other rows that are absent from the import.

The named practice roles teach separation of duties. They are not logins or proof of a person’s identity. An application using these services for real work must supply authenticated identities and protect its saved data separately.

3. Run the complete memory-only lesson

Open PowerShell after the full build succeeds. The first command gives the essential result. The second also prints the proposal you are reviewing.

PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$Tool = ".\build\windows-ucrt64-all-debug\bin\umicom-enterprise-recovery.exe"
& $Tool --self-test
if ($LASTEXITCODE -ne 0) { throw "Enterprise lesson failed." }
& $Tool demo
if ($LASTEXITCODE -ne 0) { throw "Enterprise demonstration failed." }

The self-test finishes with:

Expected output
The approved delivery expected 12 notebooks. A stock count now records 15; the old job is refused.
A new job reviews 15 -> 20. The old job remains; its approval was not copied.
Copied result: notebooks = 20 | source job delivery-reviewed
Practice complete. Memory only; no files, network, scheduler or financial transaction was used.

No file, network connection or background scheduler is opened. Each run begins with a new in-memory Data Server and releases it when the exercise ends. The word “recovery” here means re-preparing a stale import; it does not mean repairing a corrupt database.

5. Save and apply the opening stock

Select the practice author and set Job ID to opening. On Import, replace the editable text with:

CSV
item_id,label,quantity
notebooks,Workshop notebooks,12
pencils,Pencils,8
  1. Choose Preview editable CSV. Both rows should be inserts.
  2. Choose Prepare frozen job. This saves the proposal, not its row changes.
  3. Select the practice reviewer. On Jobs, choose Load frozen job. Inspect its before/after rows on Import. Return to Jobs, enter a reason such as Checked the opening stock sheet, and choose Approve.
  4. Select the practice operator. On Jobs, choose Load frozen job again, inspect the saved proposal and choose Apply approved job.

The saved dataset now contains twelve notebooks and eight pencils. Loading the job again after each role change is intentional: the application does not treat an earlier person’s inspection as your own.

6. Make an approved proposal become stale

Prepare a delivery without applying it

Select the practice author, set Job ID to delivery, and enter this CSV on Import:

CSV
item_id,label,quantity
notebooks,Workshop notebooks,20

Preview it and prepare the frozen job. Select the reviewer, load the frozen job, inspect the proposed twelve-to-twenty update and approve it. Do not apply delivery yet.

Record a newer stock count

Select the author, change Job ID to stock-count, and enter:

CSV
item_id,label,quantity
notebooks,Workshop notebooks,15

Preview and prepare this job. As the reviewer, load it and approve it. As the operator, load it again and apply it. The notebook quantity is now fifteen; the pencils remain unchanged.

Try the old approved job

As the operator, set Job ID back to delivery, load the frozen job and choose Apply approved job. It is refused because its target generation has changed. The refusal must not set the quantity to twenty. Neither copying the old approval nor pressing Apply repeatedly solves the mismatch.

Pause here if your values differ. Check the Data report, job states and audit. Do not reuse an existing job ID with different CSV. Each ID identifies one frozen request, not a slot for interchangeable files.

7. Prepare a new review from the original CSV

  1. Select the practice author. Set Job ID to delivery. Open Import recovery.
  2. Choose Inspect original job again. Read the original and current dataset generations. The new proposal should show fifteen notebooks becoming twenty.
  3. Confirm the recipe and affected row. This action uses delivery’s frozen CSV, not whatever text is currently visible on the Import tab.
  4. Set New job ID to delivery-reviewed. Choose Prepare new reviewed job.
  5. The shared Job ID changes to the new ID. Its state is Review, not Approved. Select the reviewer, load the new frozen job, inspect the fifteen-to-twenty proposal, provide a new reason and approve it.
  6. Select the operator, load the new frozen job again and apply it. Capture the dataset or inspect Data to confirm twenty notebooks.

The original delivery job remains, with its original proposal and decision. The audit entry job.reprepare has the new job as its target and the original job ID as its detail. This records the relationship without changing the old event.

Re-preparation does not automatically cancel the original. Review and cancel obsolete work explicitly under the existing controls when that is appropriate. An already applied job is not eligible for re-preparation: retrying its original ID follows the existing idempotent path instead of creating another application.

Changing the role, job or dataset after inspection invalidates the graphical recovery review. Any intervening workspace change is also checked by the core on preparation. Reload when necessary, inspect again and use an unused ID. No automatic retry rewrites the proposal for you.

8. Browse stable, filtered pages

Open Dataset browser. Keep Dataset ID at supplies, leave Literal filter empty, choose ID ascending, then choose Capture dataset.

The report states its dataset generation and workspace revision. It contains at most sixteen rows per page. Previous page and Next page navigate the same captured data; they do not silently combine records from different revisions. This two-row exercise fits on one page, so Next page stays on that page.

Enter notebooks as the literal filter and capture again. Filtering checks item ID, label and source-job ID. It is case-sensitive and not a regular expression or SQL query. The notebook’s source should now be delivery-reviewed.

Change the sort to Quantity descending and clear the filter, then capture again. Quantity comparisons are numeric. Labels are ordered by their UTF-8 bytes, not by a language-specific dictionary. Equal primary values use ascending item ID so the ordering remains predictable.

After another operation changes the dataset, the captured report stays unchanged until you choose Capture dataset again. If a different application changes the database, first choose Reload shared workspace. Capturing copies the loaded state; it is not an implicit reload. Quantity-range filters are available through the C API, not extra fields on this graphical page.

9. Choose the right response to a failure

What happenedWhat to do
The dataset changed since the original proposal.Inspect it again and prepare a new job for a new review. Keep the old job.
A write failed, but rollback completed.The approved job remains retryable. Investigate storage first; use the existing Apply path when its assumptions are still current.
Rollback failed or storage is malformed.Stop using that workspace. Preserve the database and investigate recovery separately; do not overwrite its contents with a remembered view.
The recipe is disabled or access denied.Inspect the role and recipe controls. Do not change roles merely to bypass a real authorisation refusal.
Imports are paused.A new proposal can be prepared, but execution remains paused. Resumption is a separate controlled action.
The new job ID exists.Inspect that saved job. Choose another ID only for a genuinely new proposal.
SQLite is unavailable.Use a build with the actual dependency. The graphical storage path does not substitute a temporary memory database and call it saved.

The updated storage check compares the loaded workspace with all its stored chunks inside the save transaction. It also protects same-value requests that would otherwise be treated as no-ops. An altered chunk with an unchanged header is refused and retained for investigation. This check detects disagreement; it is not encryption, a digital signature or database repair.

10. Read and extend the native C example

The complete example is framework/examples/enterprise_recovery/lesson.c. It uses public enterprise contracts. The small ApplyCsv helper expresses the existing prepare/review/execute sequence; recovery creates a new Review job through the same service.

UmiEnterpriseWorkspace borrows Data Server and authorisation services, so they outlive it. The query and recovery objects own their copied records. Their destroy functions accept null, allowing one cleanup section to handle both success and early failure. A controller must serialise workspace operations; these objects do not turn an invalid lifetime into a safe concurrent access.

Complete lesson.c
C23 · complete file
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/enterprise_recovery/lesson.c
 * PURPOSE: Follow a stale stock import into a new reviewed job and browse its owned result.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/

#include "lesson.h"
#include "umicom/enterprise_workspace/practice.h"
#include "umicom/enterprise_workspace/recovery.h"
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define ACT(index) UmiEnterprisePracticeActor(index)
#define CHECK(call) do { status = (call); if (status != UMI_STATUS_OK) goto cleanup; } while (0)
static UmiStatus ApplyCsv(UmiEnterpriseWorkspace *workspace, const char *jobId, const char *csv)
{
    UmiStatus status = UmiEnterpriseWorkspacePrepare(workspace, ACT(1), jobId, "supplies", "stock.csv", csv, strlen(csv), NULL);
    if (status == UMI_STATUS_OK) status = UmiEnterpriseWorkspaceReview(workspace, ACT(2), jobId, true, "Checked the stock sheet");
    if (status == UMI_STATUS_OK) status = UmiEnterpriseWorkspaceExecute(workspace, ACT(3), jobId);
    return status;
}
int UmicomEnterpriseRecoveryLesson(bool detailed)
{
    UmiDataServer *data = NULL;
    UmiEnterprisePracticeAccess *access = NULL;
    UmiEnterpriseWorkspace *workspace = NULL;
    UmiEnterpriseRecoveryReview *review = NULL;
    UmiEnterpriseDatasetView *view = NULL;
    UmiEnterpriseRowQuery query;
    UmiEnterpriseRowPage page;
    UmiEnterpriseJob job;
    UmiStatus status = UMI_STATUS_OK;
    char *report = NULL;
    const char opening[] = "item_id,label,quantity\nnotebooks,Workshop notebooks,12\npencils,Pencils,8\n";
    const char delivery[] = "item_id,label,quantity\nnotebooks,Workshop notebooks,20\n";
    const char count[] = "item_id,label,quantity\nnotebooks,Workshop notebooks,15\n";
    CHECK(umi_data_server_create_memory(&data));
    CHECK(UmiEnterprisePracticeAccessCreate(&access));
    CHECK(UmiEnterpriseWorkspaceOpen(data, UmiEnterprisePracticeAuthorisation(access), &workspace));
    CHECK(UmiEnterpriseWorkspaceSetRecipe(workspace, ACT(4), "stock.csv", true));
    CHECK(UmiEnterpriseWorkspaceCreateDataset(workspace, ACT(1), "supplies", "Workshop supplies"));
    CHECK(ApplyCsv(workspace, "opening", opening));
    CHECK(UmiEnterpriseWorkspacePrepare(workspace, ACT(1), "delivery", "supplies", "stock.csv", delivery, strlen(delivery), NULL));
    CHECK(UmiEnterpriseWorkspaceReview(workspace, ACT(2), "delivery", true, "Reviewed against twelve notebooks"));
    CHECK(ApplyCsv(workspace, "stock-count", count));
    status = UmiEnterpriseWorkspaceExecute(workspace, ACT(3), "delivery");
    if (status != UMI_STATUS_BUSY) { status = UMI_STATUS_INTERNAL_ERROR; goto cleanup; }
    puts("The approved delivery expected 12 notebooks. A stock count now records 15; the old job is refused.");
    CHECK(UmiEnterpriseRecoveryInspect(workspace, ACT(1), "delivery", &review, NULL));
    if (detailed) {
        report = malloc(32768U);
        if (report == NULL) { status = UMI_STATUS_OUT_OF_MEMORY; goto cleanup; }
        CHECK(UmiEnterpriseRecoveryFormat(review, report, 32768U));
        puts(report);
    }
    CHECK(UmiEnterpriseRecoveryPrepare(workspace, ACT(1), review, "delivery-reviewed", NULL));
    CHECK(UmiEnterpriseWorkspaceJobFind(workspace, "delivery-reviewed", &job));
    if (job.state != UMI_ENTERPRISE_JOB_REVIEW || job.reviewer[0] != '\0') { status = UMI_STATUS_INTERNAL_ERROR; goto cleanup; }
    puts("A new job reviews 15 -> 20. The old job remains; its approval was not copied.");
    CHECK(UmiEnterpriseWorkspaceReview(workspace, ACT(2), "delivery-reviewed", true, "Inspected the new count before approval"));
    CHECK(UmiEnterpriseWorkspaceExecute(workspace, ACT(3), "delivery-reviewed"));
    UmiEnterpriseRowQueryInit(&query);
    (void)snprintf(query.text, sizeof(query.text), "notebooks");
    CHECK(UmiEnterpriseDatasetViewCapture(workspace, ACT(0), "supplies", &query, &view));
    /* The result owns copied rows, not borrowed database or widget pointers. */
    UmiEnterpriseWorkspaceDestroy(workspace); workspace = NULL;
    UmiEnterprisePracticeAccessDestroy(access); access = NULL;
    umi_data_server_destroy(data); data = NULL;
    CHECK(UmiEnterpriseDatasetViewPage(view, 0U, 1U, &page));
    if (page.count != 1U || page.rows[0].quantity != 20U) { status = UMI_STATUS_INTERNAL_ERROR; goto cleanup; }
    printf("Copied result: %s = %" PRIu64 " | source job %s\n", page.rows[0].id, page.rows[0].quantity, page.rows[0].sourceJob);
    puts("Practice complete. Memory only; no files, network, scheduler or financial transaction was used.");
cleanup:
    free(report);
    UmiEnterpriseDatasetViewDestroy(view);
    UmiEnterpriseRecoveryReviewDestroy(review);
    UmiEnterpriseWorkspaceDestroy(workspace);
    UmiEnterprisePracticeAccessDestroy(access);
    umi_data_server_destroy(data);
    if (status != UMI_STATUS_OK) fprintf(stderr, "Enterprise recovery lesson failed: status %d\n", (int)status);
    return status == UMI_STATUS_OK ? 0 : 1;
}

In a larger application, the Master Controller composes shared services and the enterprise Slave Controller owns the workflow. Widgets submit requests and display copied results. They do not create another SQLite connection for changing rows behind Data Server.

A query capture checks read permission once. A saved copy cannot automatically forget its contents when permissions change later. The host remains responsible for who can read a retained report and when it is destroyed.

11. Check your understanding

  1. After approving a job, pause imports. Can you inspect it and prepare another review? Can you execute it while the pause remains?
  2. Capture a dataset, change its quantity through an approved job, then move between pages. When should the new quantity appear?
  3. Change the editable Import CSV after preparing a job. Which text does recovery use?
  4. Why does a new proposal need a new review when its final quantity still says twenty?
  5. What does sourceJob tell you, and what does it not prove?
Answers

1. Inspection and preparation are allowed while execution is paused, subject to permissions and recipe eligibility. Applying remains blocked.

2. Paging preserves the capture. Capture again to use newer loaded data; reload first when another process changed the database.

3. The original job’s frozen CSV. Editing the form does not rewrite saved source.

4. The original comparison was twelve to twenty; the newer comparison is fifteen to twenty. The effect and context changed.

5. It identifies the applying job recorded on the row. It does not authenticate a person, prove an external stock count or replace a full audit trail.

12. Know this profile’s boundaries

This is a reference-data workspace with bounded, reviewed imports. It supports eight datasets, sixty-four rows per dataset, thirty-two rows per import, sixteen retained jobs and 128 audit entries. Labels have 191 UTF-8 data bytes; the CSV buffer accepts at most 16,384 data bytes. Reaching a bound is an explicit failure, not a reason to discard older evidence automatically.

The stored format and existing recipes remain unchanged. Recovery currently reuses the original recipe and CSV; it is not a general mapping designer, scheduler, external database connector or dead-letter transport. A Dataset browser page is not an unrestricted SQL console. Marketplace’s recipe controls do not become signed plug-in distribution through this change.

The native core and the supplied C examples have focused regression coverage. The delivered GTK integration still needs compilation and operation on the target graphical platform. Neither these examples nor source-level tests establish real financial, network or operating-system actions.
