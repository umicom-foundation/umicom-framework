Turn selected repository files into owned AI context

A context plan contains paths and estimated costs. A provider prompt needs actual text. Materialization is the step between them: Framework asks a workspace adapter to read each selected file, then keeps a bounded copy. This lesson follows that boundary and explains why a successful callback still needs validation.

1. Separate selection from reading

The context planner selects files using metadata, budget and policy. Materialization accepts a ready plan and rechecks the data it will use: the number of files, the active path, and every selected file's canonical metadata. The required positive priority is a ranking value; the required positive token estimate is a budget estimate. Neither is proof that a file exists.

Keep the privacy decision and workspace containment checks in their existing services. A relative path such as src/main.c is a useful lexical contract, but it does not prove that symlinks or a remote adapter cannot escape a workspace. A valid plan is also not fresh consent to send files to a different provider.

2. Implement the read callback carefully

The callback receives a buffer and its capacity in bytes. It reports the number of content bytes, excluding the final zero byte used by C strings. The following memory adapter illustrates the required accounting:

static UmiStatus read_example(void *user, const char *path,
    char *out_text, size_t capacity, size_t *out_length)
{
    static const char source[] = "int answer = 42;\n";
    const size_t length = sizeof source - 1U;
    (void)user;
    if (path == NULL || out_text == NULL || out_length == NULL)
        return UMI_STATUS_INVALID_ARGUMENT;
    if (strcmp(path, "src/main.c") != 0) return UMI_STATUS_NOT_FOUND;
    if (length >= capacity) return UMI_STATUS_CAPACITY_EXCEEDED;
    memcpy(out_text, source, sizeof source);
    *out_length = length;
    return UMI_STATUS_OK;
}

Include <string.h> and umicom/ai_coding_runtime/context_materializer.h in the C source containing this callback. Supply the other required workspace callbacks through the existing adapter contract. The example performs no filesystem or network operation.

  1. Return OK only after the reported bytes have been written.
  2. Keep the reported length strictly below capacity so a terminator fits.
  3. Do not include an embedded zero byte in text. Binary content needs a different representation.
  4. Keep callback state alive until materialization returns. Do not write the caller's output context from inside the callback.

3. Validate before using a reported length

The materializer checks an OK callback's length before hashing or indexing the text. A length equal to capacity or as large as SIZE_MAX is refused. Embedded zero bytes are refused because they would give byte-oriented hashing and string-oriented prompt construction different views of the same file. Framework then writes the trailing zero byte itself.

if (length >= sizeof target->text)
    return UMI_STATUS_CAPACITY_EXCEEDED;
if (memchr(target->text, '\0', length) != NULL)
    return UMI_STATUS_PARSE_ERROR;
target->text[length] = '\0';

This is the admission sequence, shown without the surrounding allocation and cleanup. It cannot repair a callback that has already written outside the supplied buffer. The callback remains responsible for respecting capacity while writing.

4. Publish one complete result

Framework stores a copy of the admitted plan and callback table, plus a candidate output, on the heap. Heap storage avoids placing these large bounded arrays on a small thread stack. Reads populate the candidate. Only a successful operation copies it to the caller's output. An error on the second file therefore leaves the previous output intact instead of exposing only the first new file.

The callback table and plan snapshots also keep a synchronous callback from redirecting subsequent reads by changing the original input objects. They do not copy the adapter's user data or keep a freed object alive. Serialize access and retain the borrowed callback state for the whole call.

NOT_FOUNDSkip this file and increment the skipped count.

The output has room for 24 files, while the metadata plan can describe up to 32. Extra selected files are counted as skipped and the output is marked truncated. Adding token estimates is checked before reads so an unsigned sum cannot wrap to a misleading small number.

5. Inspect and find owned files

UmiAiCodingMaterializedContextValidate checks every active record, including paths, lengths, terminators, unique paths, hashes and the total token estimate. umi_ai_coding_materialized_context_find uses that validation before returning a matching file. A valid first record cannot hide corruption later in the context.

The content hash detects an accidental mismatch between bytes and metadata. It is not a cryptographic signature. The revision is carried from the plan as provenance; it does not grant access or permission to execute changes.

6. Run focused regression checks

# From the Framework source root after configuration with testing enabled:
cmake --build build/windows-ucrt64-debug --target umicom-ai-coding-materializer-admission-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework\.ai\.coding-materializer\.' --output-on-failure

The fifty cases cover metadata refusal before any read, malformed successful callbacks, failures after one accepted file, zero-length text, maximum text length, adapter and plan changes during a callback, ordinary skips, output capacity, token limits, corrupted owned values, and lookup behavior. Expected result: all selected cases pass. These are qualification instructions, not a report that the native cases have run.

If setup fails, first check the canonical metadata fields, including priority and classification. If an OK read is rejected, inspect the callback's exact byte count and termination behavior; do not weaken the consumer's bounds check. Retain the prior output for diagnosis and fix the producer before retrying.
