Extend Studio through shared contracts

Begin with one complete user action: for example, opening a verified learning page. Write down the input, expected output, failure behaviour and lifetime before adding a button.

Trace the existing learning action

  1. Studio's workbench supplies the action and its parent window.
  2. Studio declares a content identity and resource to open.
  3. Framework prepares a candidate shelf and reader away from the GTK owner thread.
  4. Only a successful, still-owned completion replaces the displayed state.
  5. A failure leaves the earlier reader intact and reports a status.

Read applications/studio/src/gui/workbench/runtime/surfaces/learning.inc in Umicom Applications and adapters/gtk4/learning_catalogue_selection.c in Framework. The product supplies policy; the shared catalogue owns loading and presentation lifetime.

Develop one extension

  1. Define a narrow Framework API and document ownership.
  2. Add checks for success, invalid input and retained state on failure.
  3. Connect a Studio action to that API rather than duplicating it.
  4. Check mouse and keyboard activation, close/reopen and cancellation.
  5. Document the supported behaviour and any unfinished capability.

A content module is available for lessons and guides. It is not a general mechanism for loading executable plugins. Language servers, native plugins, permission grants and marketplace updates need their own contracts and implementation.
