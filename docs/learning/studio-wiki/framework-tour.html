How the Framework fits an application

Applications often need the same operations. A shared service gives them one implementation to call. A user interface gathers input and presents results; it should not need a second copy of the service's rules.

Follow the activity counter

console.c ─┐
           ├─ BtbActivityAdvance → Framework status
window.c ──┘

The Bits2Banking example in labs/native/framework-activity counts completed exercises. Its header activity.h declares the function. Its implementation activity.c checks the input and computes the next count. Both front ends call it.

A count from zero to 999 advances by one. At 1000 the service reports capacity exceeded. An invalid input or missing output pointer reports an invalid argument. A failure preserves the output value. These rules are the function's contract: what callers may rely on.

What belongs where?

  1. Put reusable behaviour in a shared library.
  2. Declare its public interface in a header.
  3. Make ownership and failure results explicit.
  4. Test the rule independently of a window.
  5. Connect a thin application callback to the service.

The counter is a teaching consumer of Framework's base component. A mature shared feature belongs in the appropriate Framework module after its contract and dependencies have been reviewed. See the source map.
