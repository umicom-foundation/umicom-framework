Create a learning content module

A content module is a folder containing learning-pack.json and the files declared by that manifest. A manifest describes what is in a package. It is data, not a program to execute.

Prepare the content

  1. Choose a stable pack identity and product name.
  2. Write the introduction and lessons in a clear order.
  3. Give each resource an identity, title, topic, kind and relative path.
  4. Calculate its SHA-256 digest after reviewing the final bytes.
  5. Declare the Framework compatibility range you have reviewed.
  6. Keep all local reader links within the declared pack.

The reader compares the actual file bytes with the declared digest. This detects changed content; it does not prove who published it. A trusted installer chooses which pack directories to distribute.

Bundle an offered module

Framework's UmicomLearningModuleBundle.cmake validates a selected module, stages declared files beside the application and includes them in installation. Studio resolves that location from its executable, not the current project directory. Its optional Bits2Banking source can be selected with UMICOM_STUDIO_BITS2BANKING_MODULE.

Opening a module is explicit. The UI does not run a post-install script, compiler or example. Missing files and mismatched hashes are reported while retaining the previous reader. A local folder can also be loaded through the catalogue.

Maintain several formats

Keep Markdown and HTML as reviewed source versions. Preserve unique explanations when comparing them. Regenerate a pack digest only after reviewing its changed HTML. Use a browser for full HTML presentation; the native reader supports a bounded structured reading view.

To host this wiki on the web, publish these HTML pages together under one directory. No hosting or online marketplace account is created merely by bundling them locally.

Lab: recover from a checksum mismatch

A checksum is a number calculated from a file's exact bytes. SHA-256 produces a 64-character hexadecimal value. Editing a paragraph or changing line endings changes that value. The manifest keeps the value for the reviewed version, so an out-of-date value stops module staging during configuration.

This lab uses the existing Framework CLI and the Bits2Banking collection. It needs a built umicom.exe that offers learning-pack verify and learning-pack prepare. A terminal is a window where you enter commands; on Windows, open PowerShell. Adjust the installation path if your repositories are elsewhere. The final argument, 0.9.0, is the host compatibility version declared for this example, not a compiler version.

  1. Locate the manifest named in the configure error. Review each listed file in an editor. Check that the edits belong to the intended course and that local links are still included in the module. A checksum update cannot repair an incorrect lesson or a missing linked page.

  2. Check the current manifest without changing any files:

    Set-Location "C:\umicom\Umicom-Applications"
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" learning-pack verify "C:/umicom/Umicom-Bits2Banking/content/courses/framework-and-finance" "learning-pack.json" "0.9.0"

    A stale manifest produces a resource error and a nonzero exit code. A successful check reports the resource count, pack identity and revision. This checks declared file bytes; it does not run lessons or prove that every navigation link is bundled.

  3. After reviewing the edits, prepare a separate candidate manifest:

    & ".\build\windows-ucrt64-all-debug\bin\umicom.exe" learning-pack prepare "C:/umicom/Umicom-Bits2Banking/content/courses/framework-and-finance" "learning-pack.json" "learning-pack.review.json" "0.9.0"

    The command calculates the current resource digests, increases the pack revision by one and creates the candidate file. It refuses an existing output filename. Review an existing candidate before choosing a new name; do not overwrite it blindly. The original manifest remains unchanged.

  4. Verify the candidate using learning-pack verify with learning-pack.review.json. Compare it with learning-pack.json. Review every digest change, the revision and the resource list. When the pack is also described by collection.json, keep that collection's revision and resource metadata in agreement with the approved manifest.

  5. Using your editor or version-control review, publish the approved candidate as learning-pack.json together with its matching lesson files. Retain the earlier manifest in revision history. Run verification against the published name, then configure the application again. Do not continue to build or install after a configuration error: the generated build rules may still describe an earlier source state.

Keep these course files encoded as UTF-8 with LF line endings, as specified by the repository's .gitattributes. Configure never approves changed content by recalculating the manifest automatically. If the CLI is not built yet, use a reviewed matching content-and-manifest delivery before configuring; disabling validation would hide the inconsistency.

Follow the implementation

tools/umicom/src/command_learning_pack.c handles the command arguments. src/teacher/learning_pack_authoring.c implements reusable revision preparation. cmake/UmicomStageLearningModule.cmake checks all declared bytes before staging. The regression in tests/learning_pack/check_module_staging.cmake changes later resources and checks that an earlier valid resource cannot partially replace an existing module.
