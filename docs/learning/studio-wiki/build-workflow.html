Configure, build, test and run

These words name different steps. A successful early step does not prove that later steps succeeded.

  1. Configure: CMake reads a project's description and writes build instructions.
  2. Build: a build tool runs the compiler and linker. The linker joins compiled objects and libraries.
  3. Test: CTest runs registered checks and reports their results.
  4. Run: start the application and check its actual workflow.
  5. Install: copy selected outputs to a chosen distribution folder.

One small exercise

In Bits2Banking, labs/native/framework-activity/CMakeLists.txt requests the installed Framework base component, builds the counter library and console, and registers six checks. The optional window also requires GTK4. Its README links the complete commands and setup lesson.

A target is a named build result, such as btb-activity-console. Building the same configured directory again lets the build tool use dependency records to update affected results. Reusing an incompatible compiler cache is a separate problem; use a different build directory when changing toolchain families.

Investigate the first failure

  • If configuration cannot find Framework, check the installed SDK and prefix.
  • If compilation fails, read the first source path and diagnostic before later consequences.
  • If linking fails, inspect the declaration, implementation and target dependencies.
  • If a test fails, compare expected and actual results with its input.
  • If a menu does nothing, record the action and UI observation separately from compiler success.

Do not treat an old executable as the result of a failed new build. Keep logs with the source revision and tool versions so another developer can reproduce the observation.
