Connect application help to verified learning packs

A contextual-help route connects an application command, diagnostic or topic to an exact guide identity. The Framework service resolves this policy against the packs an application has explicitly loaded. It does not scan folders, download documents, execute commands or infer a target from a translated title.

Read Using the learning catalogue for the native reader and its display limits. The complete console example is examples/learning_pack_inspector/help.c. Its command-line workflow uses the installed SDK without depending on GTK.

1. Define application-owned routes

UmiLearningHelpRoute route = {
    .request = {
        .product = "studio",
        .locale = "en",
        .kind = UMI_LEARNING_HELP_COMMAND,
        .key = "help.documentation"
    },
    .pack_id = "framework.learning-packs",
    .resource_id = "guide"
};
UmiLearningHelpMap *map = NULL;
UmiStatus status = UmiLearningHelpMapCreate(&route, 1U, &map);

This uses the sample pack's actual identifiers. The requesting product may deliberately point to another product's shared guide. No rule assumes that request.product equals the target pack's product. The interface owner chooses these routes; guide content does not replace application policy.

Every request contains four nonempty fields: product, locale, kind and key. Kinds distinguish command help, diagnostic help and general topics. Product and key compare exactly. Locale ignores ASCII case but has no automatic regional or language fallback. If a product offers another language, present that choice explicitly and submit a new request.

The map supports up to 128 copied routes. Duplicate request identities are refused, including identical duplicates. Keys and target identifiers use ASCII letters and digits with dots, hyphens and underscores after the first character. Every fixed-size string must contain a terminator. Creation publishes no partial map. On failure the output map is null.

2. Resolve the current target

UmiLearningHelpSelection selected;
if (status == UMI_STATUS_OK)
    status = UmiLearningHelpResolve(map, shelf, &route.request, &selected);

In this fragment, shelf already owns the loaded sample pack. Resolution performs no filesystem operation. It selects the exact route, finds its current pack and resource, checks the locale and requires a guide or lesson. All returned metadata is copied. Missing data never falls back to a vaguely similar title or the current working directory.

ResultMeaning and response
NOT_FOUNDA route, pack or resource is missing. Keep the current document and offer catalogue browsing.
UNAVAILABLEThe selected pack has another locale. Explain the mismatch and let the person explicitly choose an available language.
INVALID_STATEThe route targets an example or image rather than a guide or lesson. Correct application routing policy.
INVALID_ARGUMENT or CAPACITY_EXCEEDEDA request violates the bounded identity contract. Do not truncate it into a different request.

Refusals leave the caller's selection unchanged. Check status before reading output; an earlier value is not a new successful result. Serialize shelf operations while resolving. A copied selection can outlive the shelf, but it is a historical description after the shelf changes.

3. Verify bytes before display

UmiLearningReader *reader = NULL;
if (status == UMI_STATUS_OK)
    status = UmiLearningReaderCreateFromShelf(
        shelf, selected.pack.id, selected.pack.revision,
        selected.resource.id, selected.resource.sha256,
        1024U * 1024U, &reader);

The reader rechecks the selected edition and digest, then verifies the actual file bytes. A stale selection does not silently open a replacement pack. Reading may block, so desktop frontends dispatch it away from their UI thread. A consistent digest is not publisher authentication, and reading never grants permission to execute a source example.

4. Use the shared GTK reader

status = UmiLearningCatalogueGtk4OpenHelp(panel, map, &route.request);

The native catalogue must already contain the target pack. This operation does not depend on the current search rows and leaves them unchanged. It uses the same asynchronous ownership, verified reading and per-pack history as opening a search result. A busy or retired panel refuses a new request.

The map and request are borrowed only during this call. Accepted work owns its captured selection and pack data. OK means dispatched, not completed: inspect the catalogue state after its busy flag clears. A failure keeps the previous reading state. Retire a panel before destroying an externally retained host, and drain accepted work before an explicit application quit. See the catalogue guide for this shutdown contract.

This API provides the mechanism. It does not automatically bind every menu, keyboard shortcut or diagnostic panel in an application. The application must connect an appropriate help action, supply its reviewed route table and loaded packs, and test that complete user workflow.

5. Build and inspect the example

  1. Install an SDK containing the learning-help contract and developer library.
  2. Configure examples/learning_pack_inspector using its existing UMICOM_EXPECTED_SDK_PREFIX option. Configuration stages the example pack and calculates hashes from those staged bytes.
  3. Build the example's umicom-learning-pack-help target.
  4. Run it with the generated absolute pack root, learning-pack.json, the kind command, and key help.documentation.
  5. Confirm successful output identifies framework.learning-packs::guide and its verified byte count. Try absent.command and confirm refusal.

The example also maps diagnostic learning.content-changed and topic learning-packs. Its CTest checks require the expected process status and complete identity output. They do not claim that a graphical application has passed its help interaction checks.

Release readers, maps and shelves through their matching destroy functions. Do not retain pointers into temporary route arrays, and do not replace a failed verification with an unchecked filename open.
