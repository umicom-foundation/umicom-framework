Native AI application learning path

ComfyUI workflows and native Umicom clients

This course introduces ComfyUI workflows and develops a native client design around existing Umicom graph services. Allow two to three hours. You need JSON basics, the SDK lesson and access to a separately installed ComfyUI server for the optional inspection exercise. The native planning exercise works without that server.

Lesson 1: read a graph as typed dependencies

A node performs an operation. A port describes an input or output. A link makes one node depend on another's output. A text prompt, an image, a latent representation and conditioning are different values; drawing a line between them does not make them compatible.

Sketch four stages: prompt, image inference, Umicom watermark, export. Mark inference and watermark providers unavailable until real implementations are connected and qualified. A planning result must preserve that unavailable state rather than create a synthetic finished image.

Lesson 2: inspect the server contract

For a self-hosted server, ComfyUI documents /object_info for node descriptions, /models for model categories, and /models/{folder} for a category's models. POST /prompt submits work; a returned prompt identifier is a queue receipt. History and WebSocket messages provide later observations. These are protocol facts from the server routes, not proof that an Umicom adapter exists.

  1. Start your chosen ComfyUI installation using its documented procedure. Record its revision and installed custom nodes.
  2. For a server you control on the usual local port, inspect its declarations using these read-only requests:
Invoke-RestMethod -Uri http://127.0.0.1:8188/object_info -Method Get
Invoke-RestMethod -Uri http://127.0.0.1:8188/models -Method Get

Change the address to the actual reviewed server. Compare node class names, input names and types with one workflow exported in API format by that same installation. Do not assume the editor's layout JSON is a submission payload. A custom node is executable extension code on the server; a JSON schema is not a sandbox.

Lesson 4: design job observations without false success

ComfyUI distinguishes start, progress, success, error, interruption and cached-node messages. An executed message concerns a UI update; it is not emitted for every node completion. Correlate events with the submitted prompt_id. The exact fields are documented in server messages.

Do not resubmit automatically after a timeout: the first request may have been accepted. Keep a stable request fingerprint, scoped receipt and one monitoring owner. Framework's existing provider_connections/tasks.h, task_store.h and task_owner.h provide related ownership foundations; they are not a complete ComfyUI executor.

The documented interrupt route stops current execution. Do not expose it as a guaranteed per-job cancel without verifying the server's ownership behavior. Never turn a returned filename directly into a local path: retain its server scope and review the destination before downloading.

Assessment and current limits

Submit your graph, declared effects, actual native output and a proposed event-state table. Describe recovery after losing the network immediately after submission. Explain where an Umicom watermark must be applied and verified before Media exports an artifact. The graph declares this requirement; it does not implement the renderer.

The Framework code in these lessons supplies typed preflight, discovery observations and task ownership foundations. ComfyUI transport, custom-node execution, diffusion inference, media download and live provider qualification remain separate work. This course does not claim API compatibility or full feature parity.

Lesson 5: decode observations with the native SDK

The Umicom::comfy_protocol component now provides UmiComfyEventDecode and UmiComfyTaskObserveJson. This is a C protocol component; it does not open a WebSocket or execute a workflow. Include umicom/media_generation/comfy_events.h.

UmiComfyEvent event;
UmiStatus status = UmiComfyEventDecode(message_bytes, message_length, NULL, &event);
if (status == UMI_STATUS_OK && event.kind == UMI_COMFY_EVENT_SUCCESS) {
    /* Verify the reviewed connection and confirmed prompt ID before adopting. */
}

The decoder distinguishes nine documented text-message kinds. It rejects duplicate decoded JSON keys, invalid field types and out-of-range integers. The limits are 1 MiB, 32,768 JSON nodes, depth 32 and 128 UTF-8 bytes per prompt/node ID. Unknown message types return NOT_IMPLEMENTED; binary previews are outside this API.

For a confirmed receipt, UmiComfyTaskObserveJson requires provider comfyui, operation comfy.workflow.submit, the exact prompt ID and the observed receipt revision. It delegates running, success and confirmed error/interruption transitions to Framework's task state machine. Queue, UI, cached and executing observations cannot complete a task. A local cancellation token never creates a provider failure. Save an accepted transition using the task store's expected revision; this value operation does not persist it.

  1. Copy the installed share/umicom/framework/examples/comfy_observations folder to C:\Projects\comfy-observations.
  2. Configure and run its offline SDK exercise:
cmake -S C:/Projects/comfy-observations -B C:/Projects/comfy-observations/build -G Ninja -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DBUILD_TESTING=ON
cmake --build C:/Projects/comfy-observations/build
ctest --test-dir C:/Projects/comfy-observations/build --output-on-failure

Expect separate messages for a synthetic UI update and synthetic provider success, followed by an explicit statement that no server or generation ran. Change the prompt ID in one message and design a host check that refuses to attach it to a different receipt. Native producer regression coverage includes stale revisions, terminal-state protection and unchanged outputs after refusals. Compilation, execution and live protocol qualification must be recorded separately; successful registration is not a test pass.

Lesson 6 — Recover a confirmed job after a disconnect

A queue submission and an executed workflow are different events. An accepted /prompt reply supplies a prompt ID. Save that ID before waiting for the result. A disconnected client cannot infer whether an unconfirmed submission reached the server; resending it may create a second job.

  1. Create a task with the reviewed request digest and saved connection revision. Advance it to SUBMISSION_UNCERTAIN and durably save that revision before sending.
  2. Pass the matching HTTP response to UmiComfySubmissionDecode. An accepted response can still contain node errors for excluded outputs. Report node_error_count; acceptance is not a claim that every requested node ran.
  3. Use UmiComfyTaskConfirmJson to stage the shared receipt transition. Persist it by expected revision. A stale revision requires rereading the stored task.
  4. For a confirmed task, obtain that prompt's history through the same reviewed connection. Pass the complete JSON and confirmed ID to UmiComfyHistoryCreate.
  5. Use UmiComfyTaskObserveHistory to stage a terminal observation. Save it before presenting completion. Image metadata remains separate from bytes you have downloaded, checked and stored.
ObservationNative resultNext decision

Status absent/null, or success with completed falseUNKNOWNPreserve the last justified state and collect more evidence.
Success and completed trueSUCCEEDEDReview output references; no local delivery is implied.

Contradictory error and completed truePARSE_ERRORInvestigate the response/version; leave the receipt unchanged.

Why output names need a separate import step

UmiComfyHistoryImageAt returns a node ID, filename, subfolder and folder type from the provider. These are opaque metadata, not approved local paths. A string such as ../untrusted.png must never be joined directly to a destination folder. A future importer must encode request parameters, enforce the reviewed server and destination, validate actual media bytes, and apply Umicom branding. The decoder does none of those actions. It currently interprets the core images list; custom video/audio output schemas need their own qualified adapters.

Lesson 7: prepare the exact workflow you reviewed

Applications need one owner for request bytes. If a preview displays one workflow but a worker rebuilds a different JSON object, an approval or saved digest can describe the wrong job. The native SDK now provides UmiComfyPromptCreate, UmiComfyPromptInspect, UmiComfyPromptCheckConnection and UmiComfyPromptPrepareTask in umicom/media_generation/comfy_prompt.h. Link the existing Umicom::comfy_protocol component.

Understand the two workflow formats

The editor's saved document records visual layout as well as graph information. The API prompt is a mapping from node IDs to objects containing class_type and inputs. Export an API-format prompt from your qualified server's editor. Do not rename a layout file and assume it becomes an executable prompt. Server node implementations still decide which inputs, model files and connections are valid.

  1. Obtain an enabled saved comfyui connection and its nonzero scope revision. This adapter accepts an explicit http://127.0.0.1:port origin. It does not accept remote URLs, URL paths or credentials.
  2. Read the selected API JSON as bytes, with a maximum of 1 MiB. Supply a client ID identifying this observing client. That identifier is neither a password nor a server prompt ID.
  3. Create the immutable request. It validates complete JSON and duplicate keys, admits 1–1024 node objects, and requires a nonempty class name and an inputs object per node. This structural check cannot certify custom nodes, links, installed models or side effects.
  4. Inspect the URL, exact request body, node count, byte count and SHA-256. Review private workflow text in the correct application/profile; do not routinely print it to logs.
  5. Before a separate executor sends anything, reread the saved connection and use UmiComfyPromptCheckConnection. Changed settings or revision require a new review.
  6. Create the task receipt with UmiComfyPromptPrepareTask. Its digest comes from the same immutable request. Store and own that task through the shared services, then durably record submission uncertainty before transport.
UmiComfyPromptDraft draft = {workflow_bytes, workflow_length, "media-client"};
UmiComfyPrompt *prompt = NULL;
UmiStatus status = UmiComfyPromptCreate(&connection, saved_revision,
    &draft, NULL, &prompt);
if (status == UMI_STATUS_OK) {
    UmiComfyPromptReview review;
    const char *body = NULL; /* Borrowed until prompt destruction. */
    status = UmiComfyPromptInspect(prompt, &review, &body);
    /* Present the exact bytes to the review flow. No request has been sent. */
}
UmiComfyPromptDestroy(prompt);

The body preserves the workflow's original spelling, including whitespace and numeric spelling. The envelope escapes the client ID through the common JSON writer. A digest identifies bytes; it is not authentication, approval, a model-quality score or a guarantee that a provider executed those bytes. The request owner clears its own body before release. Copies made by the host remain the host's responsibility.

Exercises and recovery

  1. Change whitespace in the workflow. Predict which digest changes and explain why the decoded graph can remain equivalent.
  2. Change the saved connection label or timeout after preparation. Confirm that the check returns BUSY; a scope revision detects edits even if settings later return to an earlier value.
  3. Add an escaped duplicate object key. Explain why admission rejects ambiguity before any host reviews or sends a request.
  4. Destroy or change the source buffer after successful creation. The prepared body's bytes must remain intact until its own owner is destroyed.
  5. Compare a valid JSON object with an actually usable workflow. List checks that only the configured node schemas, model inventory and runtime can establish.

A shape refusal means correct the API prompt, not retry transport. A stale connection requires a fresh review. If a later request loses its reply, retain the uncertain task and follow the previous recovery lesson. This component provides no transport, persistence, retry, diffusion inference, output download or watermark renderer.

Lesson 8: inspect the server's node catalogue

ComfyUI exposes node descriptions through /object_info and /object_info/{node_class}. Its current server implementation returns input descriptions, output types and display metadata. Record the actual server revision: installed custom nodes and server versions can change these descriptions.

The native umicom/media_generation/comfy_nodes.h service decodes a host-supplied response into an owned catalogue. It copies class names, display/category text, input/output counts and known boolean flags. Input descriptors and the complete class schema remain available as immutable JSON spans. The service never imports Python, fetches a model or executes a node.

UmiComfyNodeCatalogue *catalogue = NULL;
UmiStatus status = UmiComfyNodeCatalogueCreate(&connection, saved_revision,
    response_bytes, response_length, cancel, &catalogue);
size_t index = 0;
if (status == UMI_STATUS_OK)
    status = UmiComfyNodeCatalogueFind(catalogue, "ExampleNode", &index);
UmiComfyNodeInfo info;
if (status == UMI_STATUS_OK)
    status = UmiComfyNodeCatalogueAt(catalogue, index, &info);
/* Copy needed data or consume borrowed spans before destroying the catalogue. */
UmiComfyNodeCatalogueDestroy(catalogue);

This fragment assumes a valid saved connection and a correctly bound response. ExampleNode is a synthetic fixture, not a promise that your server has that class. A missing class returns NOT_FOUND; it does not trigger installation.

  1. Read the example's input.required descriptor. Explain why the name and opaque JSON are useful before any widget is created.
  2. Inspect known_flags before reading enabled_flags. A missing api_node flag is unknown; it is not proof that a node has no network effects.
  3. Compare the catalogue's saved connection with current settings using UmiComfyNodeCatalogueCheckConnection. Changed settings or revision return BUSY; fetch and review a fresh observation through the host's explicit workflow.
  4. Change the input buffer after catalogue creation. The owned catalogue must remain stable. Borrowed schema spans live only until catalogue destruction and are not NUL-terminated.

The decoder requires unique class and input identities and refuses conflicting required/optional names. It supports up to 4096 classes, 256 inputs per group and 64 output type names within a 4 MiB response. It preserves source order and unknown JSON metadata. It does not interpret hidden inputs, custom widget descriptors, link types or output shapes. Render all provider text as untrusted data; do not execute a descriptor or treat it as HTML.

Lesson 10: check a workflow against a node observation

A workflow names node classes and supplies their inputs. A node catalogue describes what one server reported when the host captured /object_info. Comparing them can reveal a missing class or field before a costly submission. It cannot prove that a model is installed or that custom code will run successfully.

  1. Prepare an API workflow with UmiComfyPromptCreate. Keep the immutable owner alive.
  2. Decode the captured response with UmiComfyNodeCatalogueCreate, using the same saved connection and revision that actually produced the response.
  3. Call UmiComfyPreflightCreate with the current saved settings. A changed revision or settings fingerprint returns UMI_STATUS_BUSY; refresh and review the observations instead of silently retargeting them.
  4. Read UmiComfyPreflightSummary and copy diagnostics with UmiComfyPreflightIssueAt. Missing requirements are report data returned with UMI_STATUS_OK.
  5. Destroy the report when finished. It owns copied diagnostics; the original prompt and catalogue may be destroyed after report creation.
UmiComfyPreflightReport *report = NULL;
UmiStatus status = UmiComfyPreflightCreate(&connection, revision,
    prompt, catalogue, NULL, &report);
if (status == UMI_STATUS_OK) {
    UmiComfyPreflightSummary summary;
    status = UmiComfyPreflightInspect(report, &summary);
    /* Inspect missing requirements and omitted_issue_count.
       A report is an observation, not approval to submit. */
}
UmiComfyPreflightDestroy(report);

Every node is inspected in workflow source order. Missing classes appear first for their node. Known classes report missing required fields in catalogue source order, followed by true deprecated, experimental and API-node flags. Those flags describe the captured metadata; they do not grant network or process permission. Optional and hidden inputs are not required by this check.

A present null counts as present. A default in a descriptor does not supply an absent required field. Extra inputs, value types, link targets, cycles and model filenames are deliberately left to the appropriate typed planner or real server validator. The shared umi_ai_workflow_preflight service serves separately declared typed graphs; opaque custom-node descriptors must not be guessed into that type system.

The summary counts every finding while storing only the first 256 diagnostics. Always display omitted_issue_count when nonzero. all_node_requirements_observed means only that all classes and required field names were found. It does not mean the workflow is executable.

Lesson 11: identify the bytes that were reviewed

The report copies the request digest, catalogue response digest, saved connection fingerprint and revision. A digest is a fixed-size identifier derived from bytes. Whitespace changes the response digest even when decoded metadata is equivalent. This exact identity supports reproducible review; it is not a server signature or a freshness guarantee.

UmiComfyPromptWorkflow borrows the original workflow span within the owned request. Respect its length: it is not NUL-terminated. The request envelope adds JSON nodes and depth, so reparsing the whole envelope with the workflow's original limits could reject a previously admitted workflow. Reusing the exact span avoids that mismatch. UmiComfyNodeCatalogueInspect copies the observation identity without exposing mutable state.

For a real host, retain when and how the response was obtained and which server version was used. A server restart or custom-node update can invalidate metadata even if the connection settings are unchanged. Recheck current policy and task ownership before any later submission; this lesson does not implement transport, retries or generation.

Lesson 12: inspect saved observations from Media or the CLI

A workflow saved on disk can be reviewed before a server is available. It creates owned observations, compares class names and required input names, then releases the input buffers. This is a synchronous file operation; a graphical application should call it on an owned worker.

  2. For a first exercise, copy the three files from share/umicom/framework/examples/comfy_inspection in the SDK into a directory you control. Their Text class is synthetic teaching metadata, not a claim about installed ComfyUI nodes.
  3. Use absolute paths. In PowerShell, substitute your actual executable and input locations:

  'C:\Examples\Comfy\connection.umiconnection' `

Lesson 14: search a node catalogue without inventing capabilities

A node selector needs searchable names, categories and flags. It should not parse a server response on every keystroke or retain pointers to a discarded response. UmiComfyNodeSelect consumes an existing owned catalogue and creates an independent selection of copied metadata. It does not create a graphical palette or execute nodes.

UmiComfyNodeQuery query = {0};
strcpy(query.search, "image");
strcpy(query.category, "image");
query.required_false_flags = UMI_COMFY_NODE_DEPRECATED;
query.order = UMI_COMFY_NODE_ORDER_DISPLAY;
UmiComfyNodeSelection *selection = NULL;
UmiStatus status = UmiComfyNodeSelect(catalogue, &query, cancel, &selection);

Include umicom/media_generation/comfy_palette.h and string.h. Check the returned status, inspect the selection count, copy items with UmiComfyNodeSelectionAt, and finish with UmiComfyNodeSelectionDestroy. The selection survives destruction of its source catalogue. It retains names and counts, not input descriptors.

  1. Search compares class, display and category text. ASCII capitals fold to lowercase; other UTF-8 bytes remain literal. This is not fuzzy or full Unicode case-insensitive matching.
  2. A category filter matches the exact category and slash-delimited descendants. image matches image/filters, but not imagery or Image. Empty filters disable that restriction.
  3. Required true and false flags must both be known in the catalogue. Asking for a non-deprecated node excludes nodes whose deprecation flag is absent. Unknown is not false.
  4. Choose source order or byte ordering by class, display name or category. Display/category ties use the complete class ID, producing a deterministic order without locale state.

Before resolving a selected class's descriptors against another catalogue, call UmiComfyNodeSelectionCheckCatalogue. A changed connection, revision or exact response digest returns BUSY. Even whitespace changes the byte identity. A match still cannot prove that the running server is unchanged; obtain a fresh observation where the workflow requires one.

Lesson 15: inspect reference candidates without executing a graph

An API workflow often connects a node input to another node's output using a pair such as ["source", 0]. The string names a node and the integer names one output position. Reviewing references can reveal a missing node or output declaration before submission.

The upstream graph helper recognizes link-shaped pairs, while execution input handling also considers class metadata such as rawLink. Umicom calls these values candidates: inspecting their shape does not execute ComfyUI's Python contract.

  1. Prepare the workflow with UmiComfyPromptCreate and decode the matching captured node catalogue.
  2. Include umicom/media_generation/comfy_references.h and initialize an inventory pointer to NULL.
  3. Create the inventory using the host-supplied connection and revision. Mismatched prompt or catalogue identity returns BUSY.
  4. Copy the summary and each candidate, then destroy the inventory. The inventory owns copies independently of the prompt and catalogue.

Lesson 17: distinguish a queue observation from completion

ComfyUI exposes GET /queue separately from queue modification and interruption. The official server route reference is the starting point. A queue response describes jobs observed at one instant; it is not a durable receipt that a workflow succeeded.

The server implementation returns queue_running and queue_pending. Each tuple begins with a number, prompt ID, workflow object, extra-data object and output-node list. The native reader copies only the number, ID and category. Workflow and extra-data contents are temporary parser memory and are cleared when admission finishes. Prompt IDs themselves may still be sensitive; review them before logging or sharing.

The queue implementation maintains pending items as a heap. Its array order is not a fully sorted execution plan. Umicom preserves the supplied order and the number's exact JSON spelling, including signs, fractions and exponents. It does not turn these values into an estimated start time, percentage, position or floating-point rank.

Read a page without changing its meaning

The outer JSON object has origin: "offline-files". Its report contains complete running/pending counts, the page offset, page count, remaining count, next offset, connection revision, connection fingerprint and response digest. Each entry has its copied prompt ID, state, response index and number_json. Scheduling numbers are strings: values such as 9007199254740993, -0 and 2.5E+2 retain their exact spelling instead of passing through floating-point conversion. The historical revision is also a decimal string.

Running entries precede pending entries. Ordering within either list remains the captured response order. The limit is 1 through 256; the default is 256. Offset zero starts the first page. An offset equal to the total count produces a valid empty page; a larger offset fails. Exit 0 means a complete page was emitted, exit 2 indicates invalid command syntax, and exit 1 indicates a file, parse, page or output failure. None of these codes reports remote execution success.

A single UmiComfyQueue owns a stable copied observation until destruction. Separate console invocations reopen the files. Before appending pages from different invocations, compare response_sha256, connection_sha256 and connection_revision. If any changes, discard the combined view and refresh deliberately. The files are not read as one atomic filesystem snapshot, and the hashes provide no server authentication.
