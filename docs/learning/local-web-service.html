A local website and API in C

Framework can route an HTTP request to an ordinary C function. A handler receives a request, fills a response and returns a status. Native socket handling is separate, so the same service can also be exercised with a supplied byte transport.

1. Run the local example

After building the learning examples, start the executable with an explicit unused port:

umicom-web-local-service-example --port 8080

Open http://127.0.0.1:8080/ in a browser. The expected page says “Umicom local web service”. Select its health link to read JSON, or submit its form to send a POST request to the echo handler. The echo displays form-encoded text such as message=hello. The example does not decode that form, save data or run commands. Stop the process with Ctrl+C.

If startup fails because the port is occupied, choose another port, for example 8081, and use that port in the browser. A stopped process cannot serve a page; keep its terminal running while trying the example. The Web Studio build exposes the same source as umicom-web-studio-local-service.

2. Preview a small exported website

  1. Prepare a separate export folder containing the files intended for the browser. Put index.html at its top level. This example reads ordinary files from that folder; do not select a folder holding private source, credentials or unrelated documents.
  2. Supply its absolute path. On Windows, for example:
umicom-web-local-service-example --port 8080 --root "C:\Sites\MyExport"

On Linux, use an absolute path such as /home/sam/sites/export. Open the printed address. In this mode the exported files replace the demo routes completely. A path ending in a slash selects index.html in that directory. There are no directory listings, uploads or file changes.

HTML, CSS, JavaScript, JSON and common image types use the shared MIME lookup. Each complete file must be at most 16,383 bytes; larger files receive HTTP 413 instead of being cut off. An absent file receives 404. A forbidden path or filesystem link receives 403. Correct the export or use smaller assets; this bounded example does not yet provide streaming for larger websites or media. Stop and restart with a different root to preview another export.

3. Follow the ownership chain

  1. Create a UmiWebService. Add routes to its router with umi_web_route_init and umi_web_router_add. Register HEAD separately when a route supports it.
  2. Install UmiWebLoopbackRequestGate with UmiWebServiceSetRequestGate and a UmiWebLoopbackAccess containing your port. Create a server with the default loopback configuration and the service. Keep the service and all handler contexts alive.
  3. Start the listener, then call UmiWebServerServeNext on one dedicated owner thread. The call waits for one client, reads one bounded request, dispatches the service, writes one response and closes the accepted socket.
  4. Inspect the returned status and UmiWebExchangeResult. A complete error response can accompany a failed request. If dispatched is true, a handler may have changed application state even when the client disconnected before the response completed. Never automatically retry such an operation.
  5. When stopping, wait for the active call to return, destroy the server, and then destroy the service. Handlers must not start, stop or destroy their server/service.

4. Extend the example

Open examples/web/local_service.c. Its route table pairs an HTTP method and path with a C callback. Add a callback to return a small HTML page, JSON result or binary body. Validate user input in the owning Framework service before changing data. Return failure when an operation fails; do not disguise it as a successful empty response. The example supplies no application authentication, account access, provider credentials or remote API proxy. To combine exact API routes with a selected static root, install UmiWebStaticFilesHandle with UmiWebRouterSetFallback. An exact matching route keeps priority, even if it intentionally returns 404 or fails.

Use umi_web_response_set_text for bounded text. For binary output, set the response body bytes and exact body_length. The transport supplies Content-Length and Connection headers itself; a handler that supplies conflicting framing is refused. Header names and values are validated before any output is sent.

5. Understand local request admission

The example checks that Host names 127.0.0.1 or localhost with the selected port. If a browser sends Origin, it must identify the same HTTP origin. Fetch metadata must indicate a direct navigation or a same-origin request. An unrelated site's request receives 403 before any route or file read. Open the exact printed address if a custom hostname or proxy is refused.

This check reduces cross-origin and DNS-rebinding exposure; it does not authenticate a user or exclude other local processes. The Framework service gate is optional for other embedders, so install the appropriate policy explicitly. Exported scripts run as website content in the browser. Rooted file reads reject links at and below the selected root, but trust its ancestors and are not a privileged filesystem sandbox.

6. Know the current limits

AreaSupported behavior
Native hostWindows and POSIX sockets, IPv4 address 127.0.0.1, one connection at a time. This is a local development service, not public hosting.
MessagesHTTP/1.1 origin-form requests with one Host header and optional single decimal Content-Length. Chunked requests, Expect, protocol upgrades, persistent connections and pipelining are not implemented. Unsupported requests receive an error when possible.
SizeThe native server uses its existing maximum request setting, at most 16 KiB for the entire wire request. The portable exchange API permits at most 64 KiB, while the request body must remain below 16 KiB. Responses use the existing bounded response value and a 64 KiB serialization limit.
TimeSeparate 1–60,000 ms accept and exchange limits. Cancellation is checked during socket waits and between phases. A C handler is synchronous and must return; the transport cannot forcibly interrupt it.
ResponseOne response followed by connection close. HEAD retains the representation length but sends no body. Status 204 and 304 send neither body nor Content-Length in this implementation.
Other platformsThe byte exchange and routing services have no GUI dependency. Browser WebAssembly does not expose native listening sockets; it needs a separate host/transport adapter. Android and iOS packaging, permissions and lifecycle are not qualified by this desktop example.

Before public deployment, a separate reviewed deployment design must cover TLS, authentication, authorization, concurrent service ownership and operational limits. Existing in-memory parser/serializer and server lifecycle APIs remain available; the strict connection path is additive. Its message boundaries follow the concerns described in HTTP/1.1 message framing, with the smaller supported subset listed above.
