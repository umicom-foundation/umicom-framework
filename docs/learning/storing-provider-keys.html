Umicom Framework · Security

Store provider keys on this computer

A provider key lets a remote service recognise an account. Treat it like a password. The shared secret-provider interface lets application code refer to a key by an alias, such as vault://image-service, without saving the key in a project.

This guide describes a Framework API for application developers. It does not add a connection screen, authenticate with an AI company, or submit a generation request.

Choose a storage boundary

umi_secret_provider_platform uses Windows Credential Manager for the current operating-system user. Credentials persist on this computer; the adapter does not request roaming to another computer. Other platforms return UMI_STATUS_UNAVAILABLE until a secure native adapter is supplied. There is no fallback that writes keys into a text file or ordinary database.

An application's local database can keep the provider name, model selection and secret reference. Keep the secret value in the credential store. Do not include that value in database exports, source control, diagnostic reports, prompts, URLs or process arguments. A local password is different: store a salted password verifier through the local-profile service, not the password itself.

Connect the provider to your application

  1. Include umicom/security/platform_secrets.h and link your target to Umicom::security. Start with a zero-initialised provider.

  2. Choose stable, non-secret application and profile aliases. Each alias and key name is 1–96 characters, starts with a lower-case ASCII letter and contains only lower-case letters, digits, dots, underscores or hyphens. Use aliases rather than email addresses. Keep them stable between sessions so the same stored record can be found.

  3. Create the provider and check its result before offering persistent storage:

    UmiSecretProvider provider = {0};
UmiStatus status = umi_secret_provider_platform(
    "org.umicom.media", "local-owner", &provider);
if (status != UMI_STATUS_OK) {
    /* Explain that secure storage is unavailable. Do not save a plaintext copy. */
    return status;
}

  4. When the user explicitly chooses to save a key, pass their input buffer to umi_secret_set(&provider, "image-service", user_input). Check the status, then clear that input buffer with umi_secret_clear. The provider accepts 1–2048 bytes before the terminating NUL and preserves those bytes. Saving under an existing alias replaces its value; do not silently overwrite another account's key.

  5. Resolve a key only when an authorised operation needs it. Use a worker thread for native storage calls so the application remains responsive. Clear the returned buffer as soon as the provider request has finished using it.

    char key[UMI_PLATFORM_SECRET_VALUE_CAPACITY] = {0};
status = umi_secret_get(&provider, "image-service", key, sizeof(key));
if (status == UMI_STATUS_OK) {
    /* The service adapter may now authenticate to its reviewed HTTPS endpoint.
     * Keep the key out of logs and never forward it across a redirect. */
}
umi_secret_clear(key, sizeof(key));

  6. Dispose the provider after all operations using it have finished: umi_secret_provider_dispose(&provider). Disposal releases the local handle; it does not erase the user's saved credentials. To forget one local key after the user requests it, call umi_secret_remove with its exact alias. Forgetting a local key does not revoke it at the remote service.

Use references with the existing registry

You can transfer the provider into UmiSecretProviderRegistry under a name such as vault. A successful umi_secret_provider_registry_add takes ownership and clears the supplied provider. On failure, the caller still owns it. Then use vault://image-service with the registry's store, resolve and remove functions. Destroy the registry after its workers have stopped. The registry does not change the storage backend's scope or grant permission to use a remote account.

Understand the privacy limits

Profile aliases keep records separate, but they do not enforce separate security identities. Other processes running under the same Windows user can access generic credentials. A local-profile password does not encrypt these records. Applications must enforce their unlocked-profile policy before reading a key; use separate OS users when separate operating-system access is required.

Local credential storage is not offline inference. When the user chooses a remote provider, authentication is sent to that service and the submitted content leaves the computer. Show the destination and content before sending, enforce provider-specific TLS and authentication rules, and describe that service's retention policy separately. Do not embed a developer-owned shared key in a distributed application.

Handle failures without losing the user's intent

  • NOT_FOUND: no value exists under that application, profile and key alias. Ask the user to configure that connection; do not reuse a previous buffer.
  • CAPACITY_EXCEEDED: a name or value is too long, or the receiving buffer is too small. Reject the input without truncating a credential.
  • PERMISSION_DENIED or UNAVAILABLE: the OS store refused access or is unavailable. Keep the connection disconnected and explain the storage problem.
  • PARSE_ERROR: the stored value does not match the adapter's bounded text contract. Do not attempt authentication with the malformed value.

The native get callback clears the entire supplied output buffer before lookup, including unsuccessful lookups. Calls using a malformed provider object can fail in the generic helper before reaching that callback; callers should always initialise and clear their buffers. Concurrent writes are not a compare-and-swap transaction. Serialise changes to a connection and confirm the intended account before replacement.

Extend the service

A Linux keyring or macOS Keychain adapter should implement the same get, set, remove and destroy operations, with equivalent ownership and failure rules. Keep native credentials outside the project database. Add isolated failure cases as well as platform integration coverage; an in-memory fixture cannot establish the operating system's storage behaviour.
