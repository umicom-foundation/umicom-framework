Register application services safely

A module is a named part of an application. A capability describes something that part can provide, such as a document store or a price feed. Registration makes the capability discoverable. It does not start a worker, authenticate a customer, or open a file. Those actions belong to later lifecycle operations.

Umicom Framework owns the common registration rules. Studio and other applications supply module descriptions and service objects. This separation lets an application change its composition without implementing another service catalogue.

1. Understand the two catalogues

The Master Controller records modules and their capabilities. Both catalogues must agree. Suppose a module provides a document reader and a document writer. If the writer name conflicts with another provider, the module must be rejected as a whole. Keeping only the reader would make the catalogue describe an application that was never accepted.

2. Describe providers before publishing them

A UmiCapabilityDescriptor contains the capability identifier, version, provider module identifier and a borrowed provider pointer. “Borrowed” means the registry can refer to the object but does not own or free it. The object must remain alive while a consumer can use it.

UmiCapabilityDescriptor capabilities[] = {
    {
        .structure_size = sizeof(UmiCapabilityDescriptor),
        .capability_id = "example.documents.read",
        .capability_version = {1U, 0U, 0U},
        .provider_module_id = "example.documents",
        .provider = document_store,
        .flags = UMI_CAPABILITY_SINGLETON
    },
    {
        .structure_size = sizeof(UmiCapabilityDescriptor),
        .capability_id = "example.documents.write",
        .capability_version = {1U, 0U, 0U},
        .provider_module_id = "example.documents",
        .provider = document_store,
        .flags = UMI_CAPABILITY_SINGLETON
    }
};
UmiStatus status = UmiCapabilityRegistryRegisterBatch(
    registry, capabilities, 2U);

This fragment assumes that registry and document_store already exist. Check status before offering these capabilities to the rest of the application. On failure, neither entry from this call is added. Existing entries remain intact. On success, identifiers are copied into registry storage; the service object itself remains borrowed.

3. Choose single or multiple providers deliberately

UMI_CAPABILITY_SINGLETON means that a capability has one provider. A second provider cannot evade that rule by omitting the flag. The existing entry and incoming entry both participate in the conflict check. Multiple providers are allowed only when neither entry requires singleton ownership and their provider identifiers differ.

4. Let the controller register complete modules

Application composition normally calls umi_master_controller_register with a UmiModuleDescriptor. Its provided_capabilities is an array of string pointers terminated by NULL. The controller uses batch capability admission. If that step fails, it removes the provisional module catalogue entry without calling the module destructor. A corrected description can be retried under the same module identifier.

The module descriptor, its capability arrays and its module state remain borrowed. Do not edit them while registered. Complete registration before starting the controller. Diagnostic callbacks can inspect the composition, but cannot start, mutate or release the controller during the active registration call.

5. Reacquire descriptors after changes

Removing an entry compacts the capability catalogue. The implementation rebinds moved descriptors to their own identifier arrays. A caller must still reacquire a descriptor through find or at after mutation. A pointer into a catalogue is not a permanent identity.

Write operations use a registry lock. This does not make borrowed pointers safe for concurrent use after the lock is released. Serialize catalogue reading and mutation at the application ownership boundary. Removing a catalogue entry also does not stop a running module: stop its users and follow its lifecycle contract first.

6. Follow the implementation and regression cases

Read src/runtime/capability_registry.c for batch validation and identifier relocation, src/runtime/master_controller.c for module admission, and tests/test_registration_transactions.c for corrected retries. The tests fill a bounded catalogue, reject a group without partial insertion, remove an entry, and register another entry in the vacated space.

After configuring the Framework build, the following commands build and run this focused test target. Stop if a command fails; read its diagnostic before proceeding.

cmake --build build/windows-ucrt64-debug --target umicom-registration-transactions-test --parallel 2
ctest --test-dir build/windows-ucrt64-debug -R "^framework[.]registration[.]transaction[.]" --output-on-failure --no-tests=error

Each selected case must report a pass. These commands exercise registration contracts, not a complete application startup or shutdown. Continue with the lifecycle tests and application workflows before release.

Read command batch failures precisely

Commands use a related atomic registration API, umi_command_registry_register_many. Its UmiCommandBatchReport identifies the rejected descriptor with a zero-based index: 0 means the first command, 1 means the second. A duplicate inside the proposed group must identify the duplicate entry itself, not the entry after it.

SIZE_MAX means that no single rejected entry is identified, including a successful call or a batch-wide error such as insufficient registry space. Never use this sentinel as an array index. Check the returned status and then compare failed_index with the requested count before selecting an entry to display.

The cases in tests/test_command_batch_failures.c check duplicates at different positions, an existing command conflict, invalid input, capacity errors and corrected retries. All rejected groups leave membership unchanged.
