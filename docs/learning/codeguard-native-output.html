Present CodeGuard findings in a native output view

1. Let the service own the scan

A report widget should not start workers or retain an application service. Framework's review controller owns scan publication, while its native output adapter copies the evidence needed for display. Studio or another host polls its own controller and passes a snapshot with the result borrowed for the current context.

Read current-request ownership, checked report serialization and output callback lifetimes first. The presenter depends on those boundaries rather than providing a second scanner or a second implementation of Follow, Refresh and Copy.

2. Publish one coherent display input

GtkWidget *panel = UmiCodeGuardOutputGtk4Create();
/* Attach the floating panel through the host's established GTK composition. */
UmiCodeGuardReviewSnapshot snapshot;
UmiStatus status = UmiCodeGuardReviewPoll(review, current_context, &snapshot);
if (status == UMI_STATUS_OK) {
    const UmiCodeGuardResult *result = snapshot.has_report ?
        UmiCodeGuardReviewResult(review, current_context) : NULL;
    status = UmiCodeGuardOutputGtk4Update(panel, current_context, &snapshot, result);
}

Use the GTK owner thread. A zero current context means the workspace is closed. Only provide a result when has_report is true, and require its report context to match the current workspace. Keep the snapshot and result stable for the duration of the call. A successful update describes presentation, not a successful scan or a passed quality gate.

The adapter finishes all reads of borrowed findings before calling GTK. It then owns plain values and report bytes. A text-change notification may therefore close the application service without leaving a report pointer inside the widget. Nested publication returns BUSY; retry from a later owner-loop turn.

3. Preserve selection until the evidence changes

Polling often returns the same snapshot several times. Replacing text on every timer tick would erase the user's selection. The adapter compares named snapshot fields and summary values, avoiding structure-padding comparisons. Unchanged evidence leaves the display alone. New findings must arrive through a new review request; changing result storage behind an unchanged snapshot violates the presentation contract.

The shared controls still distinguish accepted evidence from displayed text. With Follow paused, a newer report is available but does not automatically replace the user's selection. The status says that retained findings are available; it does not claim that a paused display already shows them.

4. Clear a retired workspace even while paused

Pause is a reading preference, not permission to retain the previous workspace as the current report. When the host context changes or its report disappears, the adapter calls the shared reset operation before publishing the new state. Reset clears both accepted and displayed text while preserving the Follow setting. Refresh cannot revive the discarded workspace copy.

UmiStatus status = UmiOutputViewGtk4Reset(output_panel);
/* The owner must also stop old producers from submitting stale evidence. */

Reset restarts the presenter's identity admission. It does not cancel workers, change services or clear text previously copied to a clipboard. The host still owns context validation. If a new workspace already has a valid report while Follow is paused, its display stays empty until Refresh or Follow shows that new copy.

5. Report preview limits without hiding scan state

The adapter uses the shared output view's bounded capacity. It requests a complete plain-text report within that budget. A report that is too large, malformed or unavailable is represented by an explicit unavailable-preview status and empty text. The service retains its complete result for another export path. Partial JSON is never presented as a valid export.

A failed or cancelled scan may leave an older report for the same workspace. The view displays execution status and publication status separately and describes retained findings as available. A context change clears them. These distinctions prevent a previous successful result from becoming a success claim for the latest attempt.

6. Qualify the native transitions

cmake --build build --target umicom-output-view-reset-tests umicom-codeguard-output-gtk4-tests
ctest --test-dir build -R "^framework\.(output_view_reset|codeguard_output)\." --output-on-failure

Use a configured Framework or Applications build with GTK enabled. Reset cases cover paused text, accepted newer text, restarted identities, recursive calls and owner retirement. Quality-view cases cover success, pending and failed attempts, cancellation, stale contexts, closing a workspace, report loss, oversized or malformed records, unchanged selection, invalid input and callbacks that release the result owner.

A missing desktop display returns 77 and is a skip. Expected qualification is zero failed registered cases with skipped coverage reported separately. Configuration and authored tests do not demonstrate that these native cases ran.

7. Connect the host deliberately

The presenter itself registers no application command and creates no timer. A host must bind its existing scan/cancel commands, poll on its established event loop and put the presenter into the approved Output surface. Keep compiler and test output in their existing controls. On close or workspace change, invalidate the scan context and publish the matching view state. This lesson covers the shared presenter; an application's menu binding and full workflow require separate implementation and qualification.
