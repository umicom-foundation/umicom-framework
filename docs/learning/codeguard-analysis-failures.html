Keep incomplete analysis out of complete reports

1. A warning needs storage

A source analyser can recognize a problem and still fail to record it. Allocating another finding may fail; a bounded tracker may fill; reading the source may stop early. Returning success in any of these cases makes an incomplete report look complete. A status value describes whether analysis completed. A finding describes what completed analysis noticed. They answer different questions.

2. Follow the status through every layer

CodeGuard's checked lifetime API returns UmiStatus. The scanner checks it before continuing to another rule or line. Architecture checks return measurement, finding insertion, read and close failures. The retained service owns a separate candidate result; it replaces the visible report only when the whole operation succeeds.

UmiCodeGuardLifetimeTracker tracker;
UmiCodeGuardResult *candidate = NULL;
umi_codeguard_lifetime_init(&tracker);
UmiStatus status = umi_codeguard_result_create(8U, &candidate);
if (status == UMI_STATUS_OK)
    status = umi_codeguard_lifetime_scan_checked(
        &tracker, "example.c", 1U, "free(owner);", candidate);
if (status == UMI_STATUS_OK)
    status = umi_codeguard_lifetime_scan_checked(
        &tracker, "example.c", 2U, "owner->state = 1;", candidate);
/* Inspect findings only as a completed attempt when status is OK. */
umi_codeguard_result_destroy(candidate);

Include umicom/codeguard/lifetime.h and link Umicom::codeguard. This fragment uses the real API but is not a standalone program. The historical void function remains callable for compatibility; it cannot tell its caller that analysis failed. New coordinators should use the checked function.

3. Understand which state is transactional

Transactional means changes become visible together at a defined success boundary. A checked lifetime line stages its tracker changes, then commits them only after its findings were stored. A failed line leaves the tracker unchanged. The caller's result is append-only: earlier findings from the same line can remain after a later insertion fails. Discard that candidate rather than retrying it as though nothing happened.

The tracker holds at most 64 active freed names. Reassignment or an emitted dereference finding clears a slot, which can be reused. A new freed name with all slots occupied returns UMI_STATUS_CAPACITY_EXCEEDED. This is an analysis capacity failure, not a security finding. Increase neither success claims nor severity counts to hide it.

At the higher service boundary, a failed candidate is destroyed and the previous successful report remains available. Existing finding borrows survive the failed attempt. Display its failure separately, with the retained report's original identity. A previous empty report does not prove the new source was scanned successfully.

4. Preserve measurement outputs on failure

UmiCodeGuardSourceInfo measurement = {0};
UmiStatus status = umi_codeguard_source_measure(path, &measurement);
if (status != UMI_STATUS_OK) {
    /* measurement still contains its value from before the call. */
    return status;
}
/* Use measurement only after checking status. */

Include umicom/codeguard/source.h. Measurement stages a local structure, validates its path capacity, checks reads and close, and then publishes the result. Paths of up to 1023 bytes fit; longer paths return UMI_STATUS_CAPACITY_EXCEEDED. A path borrowed from the output structure remains usable because it is copied before publication. Uninitialized output remains uninitialized on failure: preserving bytes does not create a valid result.

Cleanup still runs after a failure. Preserve the first operation error if close also fails. Similarly, an analysis failure remains the returned error if cancellation arrives at the same boundary. Callers need the original cause to decide whether retrying is useful.

5. Test the difficult paths deliberately

  1. Build the tests with the same compiler and runtime as the library.
  2. Inject a failure on the first and second finding insertion; verify the status and partial result count.
  3. Fill all tracker slots, check refusal, clear a slot and verify it can be reused.
  4. Make a stream report an error after partial input, then make close fail separately. Verify the caller's prior measurement bytes survive.
  5. Make analysis fail and request cancellation together. Verify the failure reaches the scanner and the service retains its report.
cmake --build build --target umicom-codeguard-lifetime-failure-tests umicom-codeguard-analysis-failure-tests umicom-codeguard-cancellation-tests umicom-codeguard-ownership-tests
ctest --test-dir build -R "^framework[.]codeguard_(lifetime_failure|analysis_failure|cancellation|ownership)[.]" --output-on-failure --no-tests=error

Replace build with your configured Framework directory. The focused analysis fixtures register 14 lifetime cases and 26 measurement/architecture cases. They include the actual production analysis sources with narrow storage and stream hooks. Configuration registers these checks; only a successful build and execution establishes a pass. Keep the normal scanner suite and installed SDK checks as separate qualification.

6. Respect the remaining limits

These repairs make failure reporting explicit; they do not turn textual heuristics into a C parser. Name matching can produce false positives or miss aliasing. Fixed-size segments retain the historical long-line behavior. Profile-driven native text analysis now refuses embedded NUL rather than hiding later bytes; the standalone legacy measurement API retains its stdio contract. See bounded source input for the per-pass limits and candidate-publication rules. Architecture classification still uses path text, and several passes can observe different file contents if another writer changes the source. The scanner does not take a filesystem snapshot or prove absence of vulnerabilities.

Practice

  1. Draw the success boundaries for one finding, one lifetime line, one file and one retained service scan. Identify which level can contain partial findings.
  2. Explain why an allocation failure cannot be counted as a clean scan with zero warnings.
  3. Add a regression that preserves the first error when both analysis and cleanup fail. Keep setup outside assert so it runs in release builds.
