Prepare a launcher, then check what it will run

A launcher is a small file with a large responsibility: it tells your desktop which program to start. Before using one, you should be able to read its command and check the files it points to.

In this lesson you will use umicom-session-stage, a tool implemented in C23. It reads existing files, prepares a launcher in a new directory and checks that its recorded contents still agree. It does not hand its work to Python or a shell. You compile the tool once, then run the native executable.

The first exercise runs on Windows and checks an ordinary text file. The launcher exercise runs on Linux and needs an existing Linux build of Umicom Desk. These are different tasks: a Windows .exe is not a Linux program, and preparing a Linux launcher does not install a Linux desktop on Windows.

Work without changing the current desktop. Nothing in the staging workflow installs autostart, changes a login manager, starts Desk or boots an operating-system image. The result is a directory for you to review.

The source checkouts keep their established names:

C:\umicom\
    Umicom-Applications\
        framework\
        applications\
    umicomOS\

Framework owns the implementation. The OS repository supplies a build entry point and instructions, rather than maintaining another copy of the same tool.

Step 1

Meet the native tool

First merge the supplied source files and complete the build instructions that accompany this update. Open PowerShell, move to your Applications checkout, and ask the new tool to describe itself:

Set-Location "C:\umicom\Umicom-Applications"
$Tool = ".\build\windows-ucrt64-all-debug\bin\umicom-session-stage.exe"
& $Tool --help
& $Tool --self-test

The self-check should print:

Native C SHA-256 self-check passed. No file, subprocess or network request was made.

This small check confirms one known digest calculation in the executable you just built. It does not replace the complete test suite. The help text shows four operations: plan, stage, verify and digest. The first three prepare or inspect a Linux launcher; the last checks the bytes of a local regular file.

A regular file stores bytes, such as a source file or a compiled program. A directory, device or pipe is not a regular file. The tool rejects those different objects rather than treating them as ordinary documents.

Step 2

Check a file on Windows

Use the project README for a read-only exercise:

& $Tool digest --file "C:\umicom\Umicom-Applications\README.md"
if ($LASTEXITCODE -ne 0) {
    throw "The file check did not complete."
}

The result contains a 64-character hexadecimal SHA-256 digest, the selected path and a byte count. Your digest depends on the exact README in your checkout, so it is not printed here as a fixed expected answer.

A digest is a compact calculation over the file's bytes. Two identical files have the same digest. Editing a character or changing a line ending changes the input to that calculation. A matching digest is useful for checking a copy, but it does not tell you who wrote the file or whether the program inside it is trustworthy.

Try a harmless change

Make a separate practice text file in your own folder. Write one sentence using Notepad, save it and record its digest. Add another sentence, save again and repeat the command. Compare both the digest and the byte count. Do not edit a compiled application to perform this exercise.

On Windows, use an absolute local drive path. This operation rejects UNC/device paths, alternate data streams, remote drive letters and a final file that is a reparse point. It is a file-integrity check, not an inspection of the trustworthiness of every parent directory.

Step 3

Build the Linux tool

For the remaining steps, open a Linux terminal or a WSL terminal as your normal user. You need a working C compiler, CMake and Ninja. Keep the build and review directories inside your Linux home directory; do not use a broadly writable Windows-mounted directory for the staged application inputs.

In WSL, the two Windows checkouts are normally visible under /mnt/c. Set their locations explicitly:

OS="/mnt/c/umicom/umicomOS"
FW="/mnt/c/umicom/Umicom-Applications/framework"
BUILD="$HOME/umicom-builds/native-launcher"

cmake -S "$OS/tools/native-launcher" -B "$BUILD" -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DUMICOM_OS_FRAMEWORK_SOURCE="$FW"
cmake --build "$BUILD" --parallel 2
ctest --test-dir "$BUILD" --parallel 2 \
    --no-tests=error --output-on-failure

Stop if any command fails. cmake -S selects the source; -B selects a separate build directory. The build command compiles the C files. CTest then runs the native regression cases. No interpreter is required by this focused build or its primary tests.

TOOL="$BUILD/bin/umicom-session-stage"
"$TOOL" --self-test

This builds the delivery tool, not Desk. It does not download a desktop, a compiler or an operating-system image.

Step 4

Select the two existing programs

A Desk session launcher needs two native programs: umicom-desk, the desktop application, and umicom-desk-session, the explicit session handoff program introduced with the System Centre workflow. Both must already exist in your Linux installation.

The example below assumes that you installed those programs under $HOME/umicom-install/bin. Change these two assignments to the actual locations in your installation:

DESK="$HOME/umicom-install/bin/umicom-desk"
SESSION="$HOME/umicom-install/bin/umicom-desk-session"
OUTPUT="$HOME/umicom-launcher-reviews/desk-session"

mkdir -p "$HOME/umicom-launcher-reviews"

The review parent directory must belong to you and must not be writable by other users or groups. The final desk-session directory must not exist. Keeping reviews separate from the installed applications avoids confusing output files with program files.

The tool reads an executable's ELF header and checks its size and permissions. It recognises 64-bit little-endian x86-64, AArch64 and RISC-V headers, and requires both programs to describe the same architecture. The session executable path also rejects an equals sign or a trailing space, because its desktop-entry interpretation must be unambiguous. These are structural checks; they do not prove that shared libraries, graphical resources or a display server are available.

Use direct, canonical paths. Symbolic-link components, ., .., repeated slashes, control characters and percent field codes are refused. Do not relax directory permissions to bypass an error. Select the real installation path or make a properly owned native installation instead.

Step 5

Read the plan before creating anything

"$TOOL" plan --desk "$DESK" --launcher "$SESSION" --output "$OUTPUT"

The command prints the two selected paths, their file digests, a plan fingerprint and the proposed desktop-entry text. It does not create the review directory. In the proposed Exec line, look for the session program, followed by --run --desk and the Desk path you selected.

A desktop-entry command has its own quoting rules. It is not a shell script. Framework encodes quotes, dollar signs, backticks and backslashes as literal argument characters, rather than asking a shell to interpret them. Percent field codes are excluded from paths in this workflow.

The plan fingerprint covers the selected paths, executable digests, the frozen icon and the generated entry. Copy the complete 64-character fingerprint from your terminal into a variable:

EXPECTED="paste the complete plan fingerprint here"

Do not use the explanatory words in that assignment as a fingerprint. Replace them with the value you actually reviewed. This ties the next command to the inputs you inspected, instead of merely accepting whichever files happen to be present later.

Step 6

Create a new review directory

"$TOOL" stage --desk "$DESK" --launcher "$SESSION" \
    --output "$OUTPUT" --expect-plan "$EXPECTED"

The native tool prepares the plan again and compares it with the fingerprint you supplied. If a selected executable or another plan input changed, it stops before creating the directory. On a matching plan, it rechecks the executable files, creates a private directory and writes three files:

desk-session/
    umicom-icon.png
    umicom-desk-session.desktop
    manifest.json

The Umicom icon is embedded in the native library, so the default does not depend on the terminal's current directory. An explicit --icon option can select a different bounded PNG file; structural validation cannot establish that an arbitrary image is an authorised brand asset.

The manifest is written last as the completion record. It records the two executable paths and digests, the review location and the digests of the two generated files. The tool never overwrites an existing destination, even when that destination appears empty.

A failed write is not erased. A disk-full error, interrupted write or failed synchronisation can leave a partial directory. Inspect it. Do not treat the mere presence of a manifest file as proof of success; a partial manifest is possible too. Use verification, and choose a new destination for another staging attempt.

Step 7

Verify the result before use

"$TOOL" verify --output "$OUTPUT"

Verification reads the stored manifest, checks that the directory contains exactly the three expected files, validates the icon envelope and compares all recorded digests. It also regenerates the expected desktop-entry command. Changing an entry and updating only its recorded hash therefore does not make an arbitrary command acceptable.

Finally, it re-reads both referenced executables. A successful result says:

Stage and referenced executable bytes agree. This is not a signature or a graphical-session test.

Do not move the review directory after staging it. The icon reference and manifest identify its original absolute location. A moved directory is rejected; prepare a new one at the desired location instead.

The manifest schema remains the same as the earlier Python tool's schema. Normal stages from that tool can be verified natively. The native verifier is intentionally stricter about duplicate fields, directory contents, paths, ownership, PNG structure and the generated command. An older stage that fails one of those additional checks should be recreated after review, not silently accepted.

This lesson stops at verified review files. Starting Desk is a separate action in an already working graphical session. Staging does not test that action or install the entry into a system menu.

Step 8

Recognise a changed input

After you rebuild or replace Desk, verify its old stage again. A changed executable should no longer agree with the earlier recorded digest. That is useful feedback: the old review describes a different set of bytes.

Read the new plan, select a new output directory and stage again. Do not edit the old manifest to manufacture a successful result. Keeping each review separate makes it possible to explain which build was inspected.

The optional --expect-plan argument is especially useful for this two-command review. Calling stage without it is still an explicit staging operation, but it does not tie the new invocation to a fingerprint copied from an earlier human review.

When an operation stops

Message or resultWhat to do next
Destination already existsKeep that review intact and choose a new directory name.
A parent directory has unsafe ownership or permissionsUse the real, properly owned Linux installation. Do not run as root merely to bypass a check.
Input changed; review againFinish the build or other file writer, then create and inspect a fresh plan.
Manifest or entry is invalidInspect the files. Unknown fields, malformed values, extra files and a different command are rejected rather than guessed.
Exit code 77The requested operation is unsupported on this host. It is not a successful or skipped verification.

Exit code 0 means the selected operation completed; 1 means it failed; 2 means the command arguments were invalid. Read the operation's message as well as its exit code. A successful digest calculation is not the same operation as a successful stage verification.

Use the same service from C

A future installer, Studio command or graphical review panel can call the same Framework library. It should not reimplement the filesystem rules inside an application.

#include "umicom/native_launcher/stage.h"

UmiStatus PrepareReviewedLauncher(
    const UmiNativeStageConfig *config,
    const char *reviewedFingerprint)
{
    UmiNativeStagePlan *plan = NULL;
    UmiNativeStageReport report = {0};
    UmiStatus status = UmiNativeStagePlanCreate(config, &plan, &report);

    if (status == UMI_STATUS_OK) {
        status = UmiNativeStageCommit(plan, reviewedFingerprint, &report);
    }

    UmiNativeStagePlanDestroy(plan);
    return status;
}

The configuration borrows your input strings only while creating the plan. The plan owns its copied paths, icon bytes and generated text. The two executables are streamed, not loaded completely into memory. A commit attempt consumes the plan even if it fails, so a retry needs a newly prepared plan.

An application should display report.phase and report.detail, and should retain the distinction between a created partial directory and a completed stage. Keep filesystem work off a graphical event thread when large files could make the interface wait. The library does not create worker threads or provide cancellation in this version.

Know what the checks establish

Each referenced executable is limited to 512 MiB, an icon to 1 MiB, and a manifest or generated text buffer to less than 64 KiB. PNG validation checks its signature, bounded chunk structure, CRCs and basic ordering; it does not decompress the pixels. ELF validation checks the supported header shape and bounded program-header table; it does not perform a complete loader analysis.

Hashes are unkeyed calculations. Anyone who can replace the manifest and the selected executables can create a different self-consistent set. Use trusted sources and review the paths. These checks are not signatures, authenticated approval, malware scanning or a defence against another process operating with your own user identity.

The primary library, command-line tool and new regression cases are C23. Earlier Python workflows remain available as alternatives. The separate OS-image builder has not been replaced by this tool, and no claim is made here that the operating-system image or graphical session has booted successfully.

Further reading

The Desktop Entry Specification explains the file format and its two quoting layers. NIST's Secure Hash Standard defines SHA-256. Implementing that algorithm does not confer certification or validation.
