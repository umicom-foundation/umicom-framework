Manage local provider keys

A provider key is a private value issued by a service. A key alias is a name you choose, such as personal-key. Save the private value in the operating system credential store, then put its reference, vault:personal-key, in connection settings. The reference identifies the key without containing its value.

This workflow currently uses Windows Credential Manager. Other platforms report unavailable until a native adapter exists. There is no plaintext file or database fallback. Saving a key does not switch Studio's active AI provider or connect to any remote account.

1. Open the correct scope

  1. In Studio, open AI Coding, choose Connections…, then Manage local keys….
  2. Read the application and local profile displayed at the top. Studio currently uses application studio and profile desktop for these settings.
  3. Keep that scope when saving a reference. An identically named key in a different application or profile is a separate record.

The profile name shown in this editor is a storage scope, not proof that Studio has signed in. Each key operation verifies a local profile password. Local settings remain accessible as ordinary metadata for the OS user; this panel does not add authentication to the rest of the Studio workspace.

2. Create a local profile if needed

  1. Enter a separate local password of 12 to 256 UTF-8 bytes. Some characters use more than one byte. Do not enter your broker or provider account password here.
  2. Repeat the password in the confirmation field.
  3. Select Create this new local profile, then choose Create local profile.
  4. Wait for the result. A successful operation stores a salted password verifier, not the password itself. If the profile already exists, use its existing password; this action does not reset it.

Keep your local password safely. This panel does not provide password recovery or profile removal. Creating a verifier does not claim ownership of any pre-existing keys in the same OS-user namespace.

3. Save or replace a provider key

  1. Enter the local profile password again.
  2. Enter a key alias of 1 to 96 characters. Start with a lower-case letter, then use lower-case letters, digits, dots, hyphens or underscores.
  3. Paste the API key into Provider API key. Values may contain up to 2048 bytes. They are not trimmed or normalised.
  4. After entering the values, select Save or replace the key at this alias.
  5. Choose Save or replace key and wait for the result. This explicitly replaces an existing value at the same alias.
  6. Return to the connection editor and set its credential reference to vault: followed by your alias. Save that settings draft separately.

Editing a field clears earlier confirmations. Private entry fields are cleared when an operation is submitted, including rejected input; re-enter them to retry. The panel does not show or copy a stored key. Pasting uses the operating system clipboard, which this panel does not erase or control.

The native store and SQLite settings are separate systems. Saving a key does not save a connection, and saving a connection does not create a key. If only one step succeeds, complete or correct the other step deliberately. There is no combined transaction or automatic deletion of a possibly shared credential.

4. Check availability or remove a key

  1. Enter the local profile password and alias.
  2. Choose Check local key availability. Success confirms that a nonempty key can be read locally. Its value is discarded without display; no remote authentication occurs.
  3. To remove it, re-enter the password, select Remove this local key; keep its saved connection references, then choose Remove local key.
  4. Update any connection references that relied on the removed key. Revoke an issued key separately through its provider when needed.

Understand the privacy boundary

Windows protects the credential store for the current OS user. The local profile password is an application check; it does not encrypt each key or isolate it from other programs running as the same OS user. The native adapter requests local-machine persistence rather than credential roaming. Keep the Windows account and device protected.

The panel performs password derivation and credential access on a worker so the GTK thread can keep processing events. Framework clears its temporary password and key buffers before presenting a result. Password controls are marked private for Framework recording, automation text inspection and screenshot capture. These measures do not control external screen capture, other programs, clipboard history, swap files or crash dumps.

No network request happens in this workflow. A compatible future request adapter must approve the destination, obtain fresh profile authorisation, use the captured connection settings, and clear its key after use. Remote service authentication and data-retention rules still apply when an application actually sends a request. Interactive Brokers TWS and Gateway authentication is a separate workflow.

Recover from a problem

ResultWhat to do
Access deniedCheck the local profile password and Windows credential permissions. Wait for the short retry delay. Five consecutive denied operations in the same panel impose a 30-second delay. This is a UI retry control, not an OS-wide lockout.
Alias not foundCheck the application, profile and alias. An availability check cannot find a key saved in another scope.
Storage unavailableConfirm that the platform adapter and OS credential store are available. No plaintext fallback is attempted.
Unsupported or damaged recordPreserve the record for investigation. The panel does not automatically replace a verifier or repair malformed key bytes.
Operation could not be confirmedCheck local availability before repeating a write. An availability check proves presence, not which key value is stored. If necessary, explicitly replace it with the intended value after confirming the scope.
Window closed during workNormal closing waits for work to finish. Forced application shutdown may leave a completed write whose result was not displayed. Reopen and inspect availability; closing does not promise rollback.

A second window or process may write the same alias. Coordinate key changes; this native store does not provide revision-based conflict detection. The last completed save replaces the earlier value.

Extend the shared implementation

GTK hosts link Umicom::ui_gtk4 and call UmiProfileKeysGtkPresent(parent, application_id, profile_name). For an embedded panel, call Create, attach its borrowed Widget, consult CanClose, and call Destroy when retiring it. Use the GTK owning thread. The implementation copies its scope and job inputs; a worker never reads widgets or retains application runtime pointers.

Headless callers link Umicom::security and include umicom/security/profile_secrets.h. The Platform constructor creates matching profile and key-store adapters. Register creates a verifier; Get, Set and Remove require the password each time. Clear caller-owned sensitive buffers after use, serialise operations, and join all callers before Destroy.

Create supports trusted injected adapters for other platforms and isolated tests. They must belong to the same application/profile namespace and provide a cryptographically sound profile backend. A fake test verifier is never a production fallback. Avoid wrapping this service in a long-lived Boolean “unlocked” flag, or bypassing it with an unguarded native lookup when a profile check is required.
