Outgoing financial messages and recovery

An outbox stores the exact message an application intends to deliver. Framework commits that message before a worker starts an attempt. The worker supplies the transport result afterward. This service stores local evidence; it does not connect to a bank or execute a payment.

Try the synthetic walkthrough

  1. Build a financial console against a Framework SDK that exports UMICOM_HAS_UFMP_OUTBOX.
  2. Run one of these commands from the build output directory: 
    .\umicom-bank-console.exe --outbox-recovery
.\umicom-trader-console.exe --outbox-recovery
.\umicom-accountant-console.exe --outbox-recovery
.\umicom-tms-console.exe --outbox-recovery
  3. Expect one retry after a known unsent attempt, followed by manual review after an ambiguous attempt. The output states Automatic retry after ambiguity: no, Network requests: 0 and Financial postings: 0.

The example uses disposable memory and does not prove crash durability. If the command reports unavailable support, rebuild against the SDK containing Umicom::financial_inbox and the outgoing-message header. Existing console commands remain supported.

Integrate a worker

  1. Validate the participant, authorization, business schema and payload before enqueueing. The local digest is an integrity check, not a digital signature.
  2. Open an application-owned Data Server. Choose SQLite when records must survive reopening. Link Umicom::financial_inbox and include umicom/financial_messaging/outbox.h.
  3. Call UmiUfmpOutboxEnqueue. Save the returned ID and revision. The exact envelope, body, retry policy and identity indexes commit together. Do not edit reserved keys directly.
  4. Call UmiUfmpOutboxTransition with BEGIN, the observed revision and a trusted timestamp. Send only after success. Perform transport I/O outside the transaction.
  5. Use the revision returned by BEGIN when reporting the result. A revision is a sequence number that prevents an older worker's result from overwriting a newer state.
  6. After restarting, stop any previous worker before applying RECOVER to an in-flight record. It becomes manual review; the service does not assume that a missing reply means the destination received nothing.

Inspect saved outgoing records

Select an existing application Data Server database. Each product can read up to 32 checked records without changing delivery state or displaying message bodies:

.\umicom-bank-console.exe --outbox-list "C:\umicom\_local\finance\outgoing.sqlite3"
.\umicom-bank-console.exe --outbox-list "C:\umicom\_local\finance\outgoing.sqlite3" <next-cursor>

Use the cursor printed by the first command when More is yes. Trader, Accountant and TMS expose the same option. Missing databases are refused, never created. This is a current per-row view; refresh from the beginning to see records inserted before the cursor. Participant labels and IDs may be private; review the output before sharing it.

Product responsibilities

Bank and TMS can use the service to track delivery of independently approved instructions. Accountant can retain delivery evidence alongside its own reconciliation workflow. Trader can use it for reviewed reporting messages. These integrations must still implement their own permissions, operator review and transport adapters. The current console walkthrough is synthetic; no live banking or broker route is supplied by it.

Recover from a refusal

  • BUSY: reread the record. It may have changed, be inside another transaction, or not yet be due. Never send on a failed BEGIN.
  • ALREADY_EXISTS: an identity was reused with different content or policy. Inspect the original; do not change identifiers merely to bypass this check.
  • PARSE_ERROR: stored evidence is malformed or inconsistent. Preserve the database for diagnosis; do not delete evidence and create another outgoing message automatically.
  • TIMEOUT from BEGIN: the envelope expired. RECOVER can persist EXPIRED. A replacement operation requires a separate reviewed workflow.
  • PERMISSION_DENIED: a read-only store cannot enqueue or transition. It can load records for inspection.

Limits

Payloads are bounded to 1,024 bytes and attempts to 32. SQLite durability follows Data Server and storage configuration. There is no background sender, cross-process worker supervisor, network authentication, canonical CBOR/COSE wire encoder, automatic retention, manual reopening UI, or exactly-once financial guarantee. Read-only catalogue pages do not create a global snapshot or dispatch workers. Terminal states cannot be reset through this API.
