Review workspace text changes

A language server can propose changes to several documents when renaming a symbol or performing a refactoring. A valid reply is a proposal: it does not establish that the documents are still current or that the user has approved it. Framework keeps decoding, source preview and application separate so applications can show the complete proposal first.

Read the proposal

  1. Include umicom/language_runtime/workspace_edit_catalogue.h. Pass a correlated reply and its expected request ID to UmiLanguageWorkspaceEditCatalogueReadResponse. Use UmiLanguageWorkspaceEditCatalogueCreate only when you already have the result value itself.
  2. Check the returned status before using the catalogue. Failure clears its output pointer; no partially decoded edit set is published.
  3. Use UmiLanguageWorkspaceEditCatalogueCount and UmiLanguageWorkspaceEditCatalogueDocument to list document URIs, optional required protocol versions and edit counts.
  4. Use UmiLanguageWorkspaceEditCatalogueEdit to inspect each range and complete replacement text. Ranges are zero-based UTF-16 coordinates. An edit's annotation index is SIZE_MAX when absent.
  5. Read annotations using UmiLanguageWorkspaceEditCatalogueAnnotation. Show their labels and descriptions, and preserve each needs_confirmation requirement in the application's review state.

The reader accepts basic changes maps and text-only documentChanges. If both are present, documentChanges takes precedence. An integer version identifies the source revision requested by the server; null means the protocol supplied no required revision. This does not make a later arbitrary file read safe to edit.

Preview captured source

  1. Capture the complete current source for every affected document through its document owner. Preserve unsaved drafts. Resolve aliases before creating a transaction so two URIs cannot unknowingly modify the same document twice.
  2. Call UmiLanguageWorkspaceEditCataloguePreview for one document index, passing the captured UTF-8 bytes, caret and known protocol version. A required version that is missing or different returns UMI_STATUS_INVALID_STATE.
  3. Read the complete proposed text with UmiLanguageTextEditPreviewRead. The shared preview service validates exact Unicode coordinates, refuses overlapping replacements and preserves the response order of inserts at the same position. The original source remains unchanged.
  4. Display all proposed changes and annotation requirements. Keep the catalogue until review finishes. Creating a preview does not collect confirmation, edit a document or save a file.
  5. Before any separate apply operation, recheck every source capture, permission and required confirmation. Use a document transaction with a defined failure and Undo policy. Release previews and the catalogue when the review ends.

Bounds and unsupported operations

The catalogue accepts up to 1 MiB of JSON, 256 distinct document URIs, 4096 total edits and 256 annotations. Each URI allows 8192 UTF-8 bytes and each replacement allows 65536 bytes. Annotation identifiers allow 4096 bytes; labels and descriptions allow 65536 bytes each. Preview currently supports at most 256 edits for one document, 1 MiB of serialized edit data, and 16 MiB each for original and proposed text.

Repeated document entries return UMI_STATUS_ALREADY_EXISTS because their sequential interpretation would require intermediate document states. A referenced annotation that does not exist returns UMI_STATUS_NOT_FOUND. Unknown edit shapes and file creation, file renaming or deletion return UMI_STATUS_NOT_IMPLEMENTED for the entire proposal. These operations are never silently omitted.

The legacy fixed-size workspace-edit reader now uses this validation and publishes only complete results. It refuses document-version requirements and annotations because its output structure cannot represent them. It also reports capacity errors instead of publishing an initial subset of changes.

This module reads and previews proposals; it does not launch a server, open URIs, perform a rename, apply a multi-document transaction or save files. A syntactically valid URI may identify a nonlocal resource. Hosts must choose an authorized document provider rather than treating it as permission for network access.
