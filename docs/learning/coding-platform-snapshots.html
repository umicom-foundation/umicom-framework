Capture a complete coding platform observation

A runtime view combines several services: the coding agent, the assistant, the repository index and queue counts. Updating the visible result after each child read can leave a mixture of new and missing information if a later read fails.

Framework's umi_ai_coding_runtime_platform_snapshot gathers these values into a bounded local candidate. It replaces the caller's destination only after all three child snapshot operations succeed. A refused capture leaves the previous observation intact.

1. Keep the last complete result

UmiAiCodingRuntimePlatformSnapshot last_complete = {0};
int have_observation = 0;

/* platform is a live owner retained by the application. */
UmiStatus status = umi_ai_coding_runtime_platform_snapshot(
    platform, &last_complete);
if (status == UMI_STATUS_OK) {
    have_observation = 1;
    /* Present last_complete as the latest completed capture. */
} else {
    /* Report status. Retain the prior value only if have_observation was true. */
}

In an application, keep last_complete and have_observation in the view model across refreshes. On failure, display the error and make clear that any retained observation is older. Do not turn an initialized all-zero object into a claimed successful result.

2. Publish after the last fallible read

The implementation follows this order:

  1. Check the required owner and output pointers.
  2. Initialize a local candidate containing values only.
  3. Read the agent, assistant and repository snapshots into that candidate.
  4. If any child refuses, return its status immediately.
  5. Capture queue counts and the platform revision.
  6. Assign the complete candidate to the caller's output.

This bounded local value requires no heap allocation. It is not a transaction over external resources, and it does not run a model, scan a directory or consume events. The existing child getters remain responsible for their own validation.

3. Respect ownership while observing

The caller must keep the platform and its children alive and serialize observation with mutations. A snapshot call does not acquire a lock or make concurrent access safe. Output storage must be separate from the platform and its children.

Read-only observations remain available during a serialized active operation, including callbacks where the owner contract allows observation. Activity is not itself a reason to overwrite a valid display with an empty object.

4. Interpret revisions carefully

Each child revision describes that child's own observation. The platform revision is a separate field. They need not be equal, and this snapshot does not make them one transaction token. A completed capture is not proof that every operation succeeded or that no child can change later.

Retaining complete output on failure also does not repair producer sequence exhaustion or revision accounting. Those are separate state-owner responsibilities. Avoid using a revision from one service as permission to replace another service's data.

5. Verify failure at every child boundary

# From the Framework source root after configuring with testing enabled:
cmake --build build/windows-ucrt64-debug --target umicom-ai-coding-platform-snapshot-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework\.ai\.coding-platform-snapshot\.' --output-on-failure

The 17 cases substitute child read boundaries and compile the composition implementation unchanged. Each child deliberately writes some candidate fields before returning its selected failure. The test then checks that the caller's prior bytes remain untouched and later reads were not attempted.

Additional cases cover successful capture from inactive and active owners, copied count metadata and invalid arguments. Expected result: all selected cases pass. These focused fixtures do not exercise live providers or a graphical application; native compilation, execution and integration evidence are still required.
