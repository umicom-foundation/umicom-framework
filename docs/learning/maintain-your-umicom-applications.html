Umicom learning · installation and maintenance

Update, repair and remove Umicom applications

A useful installer must do more than copy files once. It should help you replace an older application, put a missing library back, or remove an application you no longer use. It must also explain what happened when an operation stops halfway through.

This guide follows Umicom Notes and a second installed application. You will first read an installation record, review a proposed change, and then inspect the result. You do not need to know C to follow the graphical steps. The last lesson opens the C interface for readers learning to build their own tools.

Before you begin

Use a practice installation and fictional documents for your first run. Keep a separate backup of anything important. Close all applications using that installation, including background processes, before applying maintenance. Reviewing a plan reads files; applying it changes application files.

Use the new Setup Centre from a separately extracted, trusted release folder. Do not run the maintenance executable from the installation whose files you are replacing. On Windows, an executable or DLL that is still open can prevent a file move. Keep the release folder outside the installation folder.

You need an installation created by the native Umicom installer, with its umicom-install.umi receipt. An older NSIS installation without that receipt is not automatically adopted. Do not invent or edit a receipt to make such an installation appear compatible.

The maintained profile is a trusted, local application directory. Network shares, ambiguous paths, symbolic links/reparse points and multiply linked files are not supported maintenance inputs. The Linux build is also useful for native integration testing; it is not a replacement for a Linux distribution's package manager.

1. Understand the three choices

Choice What it does Which release you need
Update installed applications Keeps the currently installed application set and replaces its recorded files with those from the selected release. A trusted release containing every installed application under the same application identifiers and entry paths.
Repair from the original release Restores missing or damaged files to the exact bytes recorded in the installed receipt. The original matching payload, not merely a newer release with a similar name.
Remove checked applications Moves unmodified files owned only by the selected applications into a recovery archive and removes their ownership from the receipt. No release folder is required.

“Update” means use this explicitly selected release. This edition does not infer which release is newer from a version number, check an online channel or verify a publisher signature. Choosing an older compatible payload can change the application files back to older bytes. Check the release's identity and compatibility yourself before continuing.

Shared files remain while another application is installed. When you remove the last application, its active receipt is archived too. Personal extra files are not searched for or deleted. Locally edited files belonging to an application being removed stay in their original locations, but cease to be installer-owned.

This conservative removal does not reclaim the space occupied by retained recovery archives. It leaves directories, shortcuts and Windows registration alone. A shortcut may therefore remain after its target has been removed. Do not mistake that shortcut for proof that an application is still installed.

2. Find the installed folder

Open Umicom-Setup.exe from the extracted release and choose the Maintain applications tab. The original Applications, Umicom OS in QEMU and Boot media tabs remain available.

In Installed folder, choose the directory containing umicom-install.umi, not its bin subdirectory. For example:

C:\Users\YourName\AppData\Local\Umicom Applications
    umicom-install.umi
    bin\
    share\

Click Load installed / pending. A normal installation shows its application list. If an unfinished change is found instead, the status area shows a transaction ID. Go to the recovery lesson below rather than starting another update.

The application list belongs to a particular receipt. If another operation changes that receipt, the next review refuses the stale list. Load it again and make the selection from the new list; do not reuse an old selection by its position on screen.

3. Review an update without changing anything

Choose Update installed applications. In Offline release folder, select the directory containing suite.umi and payload. This is different from the installed folder.

Click Review maintenance. Setup Centre first uses the Windows release inspector, then asks the shared maintenance service to compare the installed files with the proposed payload. It shows the installation path, before/after receipt identities, a plan fingerprint, application counts, replacement size and changed paths.

Read those paths. Install replacement means new bytes will be written. Move to recovery archive means an old owned file is no longer in the selected release. Files marked Keep already agree. The graphical report is bounded; for a very large plan, the native review command prints the complete changed-path list.

An update refuses an existing owned file that has been locally edited. This protects an unexpected change rather than deciding that it is disposable. Back up the file and investigate it. A repair is appropriate only after you have decided that the recorded original is the version that belongs there.

At this point no application file has changed. Changing the installed folder, release folder, action or removal selection discards the review. A fingerprint is a compact check of the reviewed state; it is not a digital signature or permission from a publisher.

4. Apply the reviewed update

Check again that every application using this installation is closed. Click Apply reviewed maintenance, read the confirmation and continue only when the folder and operation are correct.

The service re-reads the plan under an installation lock. It stages and checks replacement files before changing the active installation. It then records an unfinished transaction, moves original files into the archive, moves replacements into place and publishes the new receipt. The unfinished marker is retired only after the resulting owned state agrees.

A second maintenance operation cannot proceed under the same lock. This lock does not stop an unrelated application or editor from changing files; closing those writers is still necessary.

When the operation completes, retain its transaction ID and archive path. A completed copy operation does not prove that the application starts. Use Verify installation on the Applications tab with the same installation path, then open each updated application and exercise an ordinary workflow. A static file inspection and an actual application test answer different questions.

5. Repair a missing or damaged file

For a first repair exercise, use a disposable copy of a qualified practice installation. Move one known supporting file to a separate backup folder, without opening any application. Do not experiment on your only working installation.

Load the installation on the maintenance tab, choose Repair from the original release, and select the saved release that supplied its recorded files. Click Review maintenance.

A missing file appears as a replacement. A damaged owned file also appears as a replacement, but its current bytes are retained in the recovery archive. The repair does not silently throw away those bytes. A similarly named file from a different release is rejected when it does not match the receipt's size, hash and ownership.

Apply the reviewed repair and verify the result. Repairing an already matching installation reports that no payload change is needed. Do not download an arbitrary DLL from an unrelated site to satisfy a missing-file message; use the matching Umicom release.

6. Remove one application while keeping another

Load the installation and choose Remove checked applications. Check only the application to remove. Check all and Check none affect this removal list; the checkboxes are not used to choose update or repair components.

Click Review maintenance. Shared runtime files should remain when another application needs the shared installation. If a retained application's files are already damaged, removal refuses the operation and asks you to repair those files first.

Apply the plan. The remaining application's receipt and files should still verify. Your unowned notes and other extra files remain. An edited file associated with the removed application remains too; the status records that it was preserved. Such a file can still exist physically even though the application is no longer in the active receipt.

Removing the last application leaves the folder, personal extras and archive. It does not recursively erase that folder or remove Desktop and Start-menu shortcuts. Review any later space-reclamation work separately.

7. Recover an unfinished change

A cancelled operation, failed file move or terminated maintenance process may leave umicom-maintenance.pending in the installation root. It tells maintenance-aware receipt readers not to present a partly changed installation as a complete one.

Reopen the current Setup Centre and choose Load installed / pending. Save the transaction ID and read the message. Click Recover unfinished change to restore the exact file snapshot from before the attempt. Recovery uses the retained original files; it does not need to download or execute an application.

Recovery first checks the whole reversal. If a later edit or an unexpected file occupies a destination, it refuses to overwrite it. Preserve that file and investigate the conflict. Do not remove the pending marker or edit the journal to make the error disappear.

If recovery itself is interrupted, load the pending transaction again and repeat recovery. The service recognises the file moves already completed. Native tests exercise actual process termination during both maintenance and recovery; sudden power loss and filesystem/device durability still require platform-specific qualification.

Use the current maintenance-aware tools. An older installer that predates the pending-marker contract does not know how to interpret this state.

8. Undo a completed change

Undo completed change is different from recovery. It starts from a completed transaction and restores its earlier file snapshot only while the resulting installed state still agrees with the recorded transaction. Supply the transaction ID from the successful operation.

A newer maintenance transaction or a local edit may make an older undo ineligible. That refusal protects later work. Do not force it by copying the old receipt over the current one.

Undo is about application files, not database contents. It does not reverse a schema migration, a payment, a saved business transaction or an application's changed personal settings. An older executable may not understand data already changed by a newer application. Do not undo application files across such a change without a separately qualified data-recovery procedure.

Undoing a repair restores the pre-repair snapshot, which may contain a missing file or damaged bytes. That is a faithful reversal, not a promise of a healthy application. Verify the restored state separately.

9. Read the recovery folder

A transaction uses a new directory under the installation:

.umicom-maintenance/
    owner.txt
    lock
    <transaction-id>/
        identity.umi
        plan.umi
        before.umi
        after.umi
        old-receipt.umi
        new/
        old/
        undone/

Not every file exists at every phase. after.umi is absent after removal of the last application. The old directory retains the original changed files; new holds staged replacements until they move into place. undone retains files moved aside during a reversal. The plan maps numbered slots to their real relative paths.

The native service creates these records once per attempt and checks their hashes before recovery. A changed journal is an error. These files are not signed or tamper-proof against someone who controls the directory. Treat the installation and its archives as trusted local data, and keep a separate backup. There is no automatic archive-pruning operation in this edition.

10. Use the native command-line tool

The graphical interface and the command-line tool call the same Framework implementation. In the following PowerShell example, edit the two paths to match your own installation and trusted extracted release:

$Tool = "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-maintain.exe"
$Installed = "C:\Users\YourName\AppData\Local\Umicom Applications"
$Release = "C:\Users\YourName\Downloads\Umicom Release"

& $Tool review --root $Installed --action update --release $Release
if ($LASTEXITCODE -ne 0) { throw "Review failed. Do not apply it." }

Read the output and copy the 64-character value after Plan:. Applying is deliberately a second command:

$ReviewedPlan = Read-Host "Paste the plan fingerprint you reviewed"
& $Tool apply --root $Installed --action update --release $Release --expect-plan $ReviewedPlan
if ($LASTEXITCODE -ne 0) { throw "Maintenance stopped. Read the pending state before continuing." }

For repair, use --action repair and the original release in both commands. For removal, omit --release and use an application identifier reported by the installed catalogue:

umicom-maintain review --root <absolute-installed-folder> --action remove --remove <application-id>
umicom-maintain apply --root <absolute-installed-folder> --action remove --remove <application-id> --expect-plan <reviewed-fingerprint>

The angle-bracket names above are placeholders, not commands to paste unchanged. Identifiers are exact catalogue values, not display titles. Use --all instead of --remove only after reviewing removal of every installed application.

Check pending state with:

& $Tool pending --root $Installed
$PendingExit = $LASTEXITCODE
# 0: no pending marker; 3: pending transaction found; 1: inspection failed.
# A malformed or unreadable marker is an error, not a clean installation.

Restore using the recorded transaction ID, not the plan fingerprint:

$Transaction = Read-Host "Paste the transaction ID from the maintenance report"
& $Tool recover --root $Installed --transaction $Transaction
if ($LASTEXITCODE -ne 0) { throw "Recovery refused or incomplete. Preserve the files and inspect the conflict." }

Use undo in place of recover only for a completed transaction that is still eligible. The plan fingerprint identifies proposed content; the transaction ID identifies a particular attempt. Repeating the same plan after recovery creates a different archive.

11. A small C lesson: ownership and review

The complete, compiled example is examples/setup_maintenance/review_client.c, with its declaration in review_client.h. It reads a current installed list, binds the review to that list and prints every planned row. It never calls Apply.

UmiSetupMaintenanceConfig config = {
    .installationRoot = installation,
    .releaseRoot = release,
    .action = UMI_SETUP_MAINTENANCE_UPDATE,
    .removeMask = 0U,
    .expectedReceipt = UmiSetupMaintenanceReceiptIdentity(installed)
};
status = UmiSetupMaintenancePlanCreate(&config, &plan, NULL, NULL, &report);

A structure groups the inputs. An opaque pointer such as plan lets the caller use a service without depending on its private layout. The returned plan owns copies of the required configuration and its catalogues. A summary or row pointer is borrowed from that plan: use it while the plan is alive, and do not free it yourself.

Read the example's finish path. Both owned objects are destroyed there, whether the review succeeded or failed. This is a practical reason to think about memory ownership before adding more buttons.

The maintenance implementation combines three familiar ideas: a Command describes the requested action, a plan freezes the state being reviewed, and a journal retains what is needed to recover. The GUI only presents those services. It does not decide independently which files are safe to remove.

12. Practise, check and explain

Exercise A — explain the difference. Which source would you select to repair a missing library: the newest release, or one that supplies the exact recorded bytes? Explain why.

Exercise B — preserve a document. In a disposable installation, add a fictional personal note outside the receipt's inventory. Remove one application. Check the note, the remaining application and the archive separately.

Exercise C — inspect without applying. Run the native review twice without changing the inputs. Compare the fingerprints. Then change only the proposed release and review again. Do not apply either plan until you can explain the changed rows.

Exercise D — recovery in the test laboratory. Build the source and run the process-crash and recovery-process-crash regression cases. Read their C source. They terminate a child process inside a newly created test fixture, then recover it. Do not imitate that interruption on your only working installation.

Check your answers

A: repair uses matching recorded bytes; a newer release belongs to an update. B: personal extras stay, shared files remain while another application is installed, and retained archives consume space. C: an unchanged plan is reproducible; its fingerprint detects a change but authenticates no publisher. D: successful process-crash recovery does not by itself qualify sudden power-loss behaviour or Windows filesystem execution.

When to stop and investigate

Message or observation Next step
The displayed list is stale Load the installation again and review a new selection.
A local edit blocks an update Preserve and investigate it; do not force replacement.
The repair source does not agree Locate the original matching release.
A pending marker is present Recover the recorded transaction before ordinary use.
A journal or backup cannot be trusted Keep everything; investigate or restore from a separate verified backup.
A file is in use or access is denied Close the owning application; do not blindly elevate or weaken permissions.
A static inspection passes but startup fails Investigate the actual loader/resource/startup diagnostic. The inspection was not a runtime test.

This edition maintains an existing native receipt and its application files. It does not add online updates, signed release channels, automatic version ordering, database migration, shortcut cleanup, application registration, a recursive uninstaller or physical boot-media writing. Those are separate capabilities, with separate acceptance tests.
