Using the broker account workspace

Framework owns the broker transport and native account presentation. An application supplies its parent window and a copied connection plan, then embeds the returned widget. It must not copy or independently pump the inspector's connection.

  1. Create a Paper or Live UmiBrokerAccessPlan. A Guest plan belongs to the application's demo workflow and is rejected by this component.
  2. Call UmiBrokerWorkspaceGtkCreate on the GTK main thread. Keep the returned controller until application disposal.
  3. Parent the borrowed widget returned by UmiBrokerWorkspaceGtkWidget. Creating it does not present an inspector or open a socket.
  4. Use the component's connection button, or call UmiBrokerWorkspaceGtkOpenConnection from an explicit user action. Repeated calls reuse the same inspector while it exists.
  5. Call UmiBrokerWorkspaceGtkDestroy once when disposing the application controller. Closing the parent retires connection activity immediately, but the application still releases its controller ownership through Destroy.
#include "umicom/broker_connectivity/workspace_gtk4.h"

/* Run on the GTK main thread after creating the parent window. */
UmiBrokerAccessPlan plan;
UmiBrokerWorkspaceGtk *workspace = NULL;
UmiStatus status = UmiBrokerAccessPlanCreate(UMI_BROKER_ACCESS_PAPER, &plan);
if (status == UMI_STATUS_OK)
    status = UmiBrokerWorkspaceGtkCreate(parent, &plan, &workspace);
if (status == UMI_STATUS_OK)
    gtk_window_set_child(parent, UmiBrokerWorkspaceGtkWidget(workspace));

/* At application disposal, including after closing the parent: */
UmiBrokerWorkspaceGtkDestroy(workspace);
workspace = NULL;

This example illustrates ownership; the disposal call belongs at the end of the application's lifetime, after its event loop or owning controller has finished. Store the workspace pointer in that controller rather than in a short-lived callback variable.

Observations and authority

UmiIbkrGtkCopySnapshot copies observations on the main thread. Before connection it returns an IDLE snapshot; a retired inspector returns CANCELLED and preserves the caller's destination. UmiIbkrGtkReadAccount delegates an explicit selected-account overview request to the existing connection owner. The core service checks membership, readiness and the one-report-per-session rule.

Account values and quantities remain provider strings. Summary and positions have independent completion markers. A healthy socket does not make an old completed report current. Closing the inspector marks the workspace's retained observation stale; reopening replaces the old rows before another account is read. The selected Paper/Live mode is intent, not broker attestation. These APIs expose no order-submission authority.

Share market-data controls

The workspace's Market data page subscribes to one selected contract through the same inspector. UmiIbkrGtkQuoteSubscribe, UmiIbkrGtkQuoteCancel and UmiIbkrGtkCopyQuote expose that selection to other native clients without transferring transport ownership. Parse form input through UmiIbkrQuoteContractParse; a rejected identifier leaves the destination unchanged.

Subscribe requires an API-ready connection and no active selected quote. Cancelling a quote never cancels an order. If the outgoing request queue cannot accept cancellation, the stream remains active and Stop remains available. A successful cancellation retains the last observation as stale. A new inspector or connection without a quote clears the old instrument.

Copy recalculates each field's age even when account data has not changed. The workspace uses a 15-second local receipt threshold and preserves the provider's real-time, delayed or frozen classification. A recently received delayed price remains delayed. Missing and unavailable values have explicit labels, never an invented zero.

The native command boundary holds the inspector while notifications are published and rejects nested quote commands. A parent or inspector closed by a notification retires the operation. Retained widgets cannot issue requests after their controller is destroyed.

Choose a market-data delivery mode

The Requested data selector offers Real-time, Frozen, Delayed and Delayed frozen. Real-time asks for streaming current prices; Frozen asks for the last available quote when current streaming data is unavailable. Delayed requests a delayed stream, and Delayed frozen permits the retained delayed quote. Availability depends on the contract and account permissions. None of these selections purchases data or changes an order.

  1. Enter a broker contract ID and its exchange.
  2. Choose the requested delivery mode before Subscribe.
  3. Read both Requested and Received in the status line. A delayed request may receive real-time data when the account is entitled; the request alone never proves that a returned price is delayed or live.
  4. Choose Stop quotes before changing the mode. If cancellation fails, the controls remain locked to the active subscription.

Native callers can use UmiIbkrGtkQuoteSubscribeWithDataType. Headless clients use UmiIbkrQuoteSubscribeWithDataType. The original subscribe functions remain available and request real-time data. The core queues the mode and contract frames together, preserving the previous queue if either frame cannot fit. Because the broker setting belongs to the connection, concurrently active quote streams must share a requested mode. A different mode returns BUSY until all prior streams, including refused requests, are cancelled. This prevents one client panel silently changing another panel's delivery policy.

Regression coverage to run

The native ownership cases use the real inspector without opening a socket. The projection cases substitute only the inspector boundary with synthetic observations and exercise the actual widget/controller. Run both groups and Trader's startup cases after building their targets. A skipped GTK case means GUI coverage did not run; it is not a pass.

Real broker compatibility additionally requires an authenticated local Paper session and recorded TWS/Gateway version. Synthetic observations cannot establish API compatibility or trading readiness.

Find an instrument by name

  1. Connect to the local broker application and open Market data.
  2. In Find an instrument, enter a symbol or company name and choose Search.
  3. Wait for the search to complete. Review each candidate's security type, currency, listing exchange and contract ID. Several instruments can share a symbol; no candidate is selected automatically.
  4. Choose the intended candidate, then Use selected contract ID. This prepares the ID field and clears the previous exchange. It does not subscribe or send an order.
  5. Enter a broker-supported request exchange for that contract. A listing exchange is descriptive information and is not necessarily the route accepted for a market-data request.
  6. Choose a data mode, then Subscribe. Stop an active quote stream before replacing its instrument.

The search and inspector share one broker connection and one paced search service. Wait at least one second between requests; a pending search must complete or be abandoned first. Abandon search marks the local request stale. It does not cancel quotes or orders. An empty completed result means no candidates were returned for that query.

Results from a closed connection remain labelled stale and cannot be applied. A new connection clears them. If another search replaces the visible result before you apply it, choose a candidate from the current completed result. Malformed display text is made readable without changing the underlying contract identity.

Native clients share the inspector through UmiIbkrGtkSearchInstruments, UmiIbkrGtkCopyInstrumentSearch and UmiIbkrGtkAbandonInstrumentSearch. Copying observes the current request without pumping transport. Call these APIs on the GTK thread and retain neither widget callbacks nor result pointers beyond their documented owner lifetime.

Review orders entered through the broker

  1. Connect to your local broker application, wait for Ready, then open Open orders.
  2. Choose the scope. Leave Include all broker-visible clients and accounts clear for this API client only. Select it to request orders visible from other clients, including orders entered in TWS. Broker access limits still apply.
  3. Choose Recover open orders once. Wait for Complete. Receiving, Failed and STALE are not complete current evidence.
  4. Read the account on each row. The account selector on the separate account page does not filter this table. Client / order identifies the broker API client and its order ID. Unbound manual orders can share zero API IDs; Permanent ID distinguishes their broker identities.
  5. Review quantity, limit price, time in force, status, filled and remaining. Values retain the broker's decimal text. Not received means that callback has not arrived; it is not a zero quantity or an order cancellation.
  6. Reconnect before requesting a fresh capture. An empty completed table applies only to the requested scope. This API client can have no orders while TWS has orders.

Recovery is a point-in-time observation, not a guaranteed all-orders subscription. Summary and status callbacks have separate ages. Retained results become stale after connection closure, failure or expiry. A partial row remains visible with its missing fields identified. Execution and commission records must be inspected separately for fills and fees.

This view does not submit, modify, bind or cancel orders. Advanced order fields are retained by the core decoder but are not interpreted as a complete order ticket. A captured broker order is evidence, not permission to trade.

Reusable clients call UmiIbkrOrderReportCopy on the connection owner thread, or UmiIbkrGtkCopyOrderReport on the GTK thread. The report is a bounded value copy; allocate it on the heap to avoid a large native callback stack. Any copy error preserves the previous output. No copy pumps the socket. Use UmiIbkrGtkRecoverOrders only from an explicit user action; the inspector and embedded workspace share its one-capture lifetime.

Review recent trades and commissions

  1. Authenticate in the local broker application and connect the workspace. Open Trades.
  2. Choose an account from the session's account list, then choose Read recent trades. This uses the broker's available recent execution window and default client filter. It does not retrieve a complete account statement.
  3. Wait for End marker received. While Receiving, an empty or partial table is not evidence that no trade occurred. The capture's account label belongs to the returned report; changing the picker does not change that identity.
  4. Review the execution ID, broker time, instrument, side, quantity, price, currency, exchange and permanent order ID. Time text is preserved as supplied by the broker; the workstation's time zone is not assumed.
  5. Review Commission and Fee evidence. A fee can arrive after the execution end marker. Not received is unavailable, not zero. Conflicting reports show both the first and latest amount and currency for review.
  6. Choose Stop local capture to abandon an unfinished read. This does not cancel an order. A completed or abandoned capture can be replaced by an explicit new read.

Execution quantities and prices use exact decimal formatting. The view does not add cumulative quantities to individual fills, combine correction reports, convert currencies or calculate a portfolio balance. Keep correction IDs visible and reconcile them against the broker's authoritative records.

Closing the connection marks retained evidence stale. Reconnecting clears the old capture before another account is read. If another broker view starts a newer capture, a delayed Stop action cannot abandon it: the expected request ID must still match.

Native applications use UmiIbkrGtkReadExecutions, UmiIbkrGtkCopyExecutions and UmiIbkrGtkAbandonExecutions on the GTK thread. Copy observes the shared capture without network I/O and leaves the caller's output unchanged on failure. Allocate the bounded UmiIbkrExecutionSnapshot on the heap. The inspector owns the socket, request namespace and late commission matching.

Read and navigate a historical chart

  1. In Market data, select or enter the contract ID and its broker-supported exchange. In Chart, choose a bar interval and price source. A bar summarizes prices during one interval.
  2. Set the duration in seconds. Start with 3,600 seconds and one-minute bars: this asks for about one hour. The bounded reader accepts at most one day and no more than 511 intervals. Increase the interval if the requested duration would exceed that limit.
  3. Leave End time empty for the latest available history, or enter a UTC time such as 20261030 12:00:00 UTC. UTC is a shared time standard; the field does not use your computer's local time zone. Choose Regular hours only if required.
  4. Choose Read chart history and wait for a completed capture. A historical capture is a finite response, not a live-updating chart. The last candle can still be unfinished.
  5. Use Visible bars (zoom) to change how many retained bars are shown. Increase Bars back (pan) to view earlier bars. These controls do not request more data.
  6. Read the captured contract, exchange and interval above the chart. Editing the request fields does not relabel an existing capture. The details retain the broker's reported open, high, low, close and volume text; an unavailable volume is not zero.
  7. Choose Cancel chart request to cancel an unfinished historical request. This leaves orders and quote subscriptions unchanged. If another view replaced the request, the old Cancel action refuses to cancel the newer one.

Allow at least 15 seconds between bar requests. A busy response preserves the previous capture. On timeout, connection closure or capture expiry, the chart clears and reports unavailable or stale evidence. Reconnect and explicitly request a new capture. Changing zoom does not bypass these checks.

The chart uses Framework's existing historical-data model and Cairo renderer. A build without the chart adapter can still show reported values and explains why drawing is unavailable. A blank completed capture is shown as no bars; the application does not invent candles. Provider permissions, data availability and supported protocol versions still apply.

GTK clients share UmiIbkrGtkReadHistory, UmiIbkrGtkCopyHistory, UmiIbkrGtkCopyHistoryBar, UmiIbkrGtkCreateHistoryScene and UmiIbkrGtkCancelHistory. Call them on the GTK thread. Scene creation returns an owned immutable scene; destroy it with umi_chart_render_scene_destroy. Copy and scene operations do not pump the socket. A failed operation preserves its output, and request IDs prevent an old view from reading or cancelling a replacement capture.

Read a market-depth ladder

Market depth shows the bid and ask levels reported by the broker. Each side can arrive independently. These are observations of available liquidity, not a promise that an order will fill.

  1. Connect the local broker session and select a contract ID and exchange in Market data. Use the instrument search to resolve the intended contract.
  2. Open Market depth and choose the maximum levels per side, from 1 to 50. A larger request does not guarantee that the broker will return that many levels.
  3. For a direct exchange, leave SMART aggregation off. To request aggregated depth, set the exchange in Market data to SMART and turn the checkbox on. Mismatched settings are rejected.
  4. Choose Subscribe to depth. The table fills as observations arrive. Prices and sizes retain their exact decimal values. A zero size is displayed as zero; a missing side is marked Not received.
  5. Use Stop depth before changing the subscription. This stops the market-data stream; it does not cancel quotes or trading orders.

Rows retain the provider's position. The venue or market-maker column is shown only when supplied. Each row can age independently; STALE means it must not be treated as a current price. A provider reset clears both sides until fresh updates arrive. A failed stream remains visible and can be stopped before retrying.

Editing an instrument field does not change the identity of an active stream. The heading continues to identify the captured contract and exchange. If another view replaces the request before Stop is processed, the workspace refuses to stop that different request.

If no levels arrive, check the broker connection, instrument, exchange and market-depth permissions. The adapter supports the existing legacy protocol range 151–176. There is no complete-order-book marker, and the table does not infer missing liquidity. The controls share Framework's existing depth service and native connection; they do not start a second broker session.

Follow account and position profit and loss

Profit and loss (P&L) describes a reported gain or loss. Daily, unrealized and realized values have different meanings and reset rules. The workspace displays the broker's observations instead of estimating them from the last price.

  1. Connect the local broker session and open Profit and loss. Choose an account from the advertised account list.
  2. Leave Model empty for the account scope, or enter a model code configured for that account. The workspace does not discover model codes.
  3. Leave Contract ID empty for account P&L. For a position, enter its positive contract ID. A symbol is not a contract ID: resolve the instrument in Market data first.
  4. Choose Subscribe to P&L. Waiting means no observation has arrived; it does not mean a zero balance. A reported zero is displayed as zero.
  5. Review the captured account, model and contract above the values. Position and Market value apply to a contract subscription. Provider values that cannot be represented exactly show Unavailable and retain the reported text in the evidence column.
  6. Choose Stop P&L before selecting another scope. A failed stop leaves the stream active. If another view has replaced the request, the old Stop action refuses to cancel the new one.

The broker's portfolio P&L reset schedule can differ from its account-update values. These callbacks do not carry a currency field; do not infer the currency from another instrument or add values across accounts. Editing a field never changes the identity of previously received values.

On disconnection or age expiry, retained observations are marked STALE. Reconnect and explicitly subscribe again. Repeated screen refreshes only copy observations; they do not start additional subscriptions. A failed stream can be stopped before retrying. Model permissions, instrument availability and the supported broker protocol still apply.

GTK clients use UmiIbkrGtkSubscribePnl, UmiIbkrGtkCopyPnl and UmiIbkrGtkCancelPnl on the GTK thread. The connection inspector owns the socket and shared request. Copy performs no network I/O and preserves output on failure; cancellation requires the expected request ID.

Find ranked contracts with a market scanner

A scanner searches an instrument family, such as stocks, within a market location and ranks the matching contracts. Its results identify instruments; they do not include current bid, ask or last prices.

  1. Connect the local broker session and open Scanner. Enter the instrument family, location code and scan code supported by your broker. The initial stock scan is a starting example, not a guarantee of availability.
  2. Choose the maximum results, from 1 to 50, and select Start scan. Wait for a complete refresh. An empty completed refresh means there were no matching contracts; a waiting response is not an empty market.
  3. Review the ranked table, including type, currency, listing and contract ID. The captured scan codes remain above the results even if an input field is later changed.
  4. Choose a result from the selector and select Use selected contract ID. Then open Market data, enter its broker-supported exchange and choose a data mode before subscribing. The scanner does not start quotes or place an order.
  5. Choose Stop scan before starting another. A rejected cancellation leaves the current subscription visible. If the request changed in another view, the old Stop action does not cancel the replacement.

Ranked results can change between refreshes. The selection clears when a new refresh arrives so that a different instrument cannot silently occupy the selected row. Stale or failed results remain visible but cannot be applied. Reconnecting clears the previous session's results.

Allow at least one second between requests. Use Connection and account tools for the scanner parameter catalogue and additional filters. Available scans and filter permissions depend on the broker. This workspace shares the inspector's one selected scan, while the underlying service supports up to ten independent scans in a session.

GTK clients use UmiIbkrGtkStartScanner, UmiIbkrGtkCancelScanner, UmiIbkrGtkCopyScanner and UmiIbkrGtkCopyScannerRow on the GTK thread. Copy calls perform no I/O and preserve output on failure. A row requires the captured request ID and generation, which together identify its ranked refresh.

Review completed orders

A completed order has reached an end state reported by the broker. It may have been filled, cancelled without a fill, or cancelled after some quantity was filled. It is different from a single execution, which records one fill.

  1. Connect the local broker session, then open Completed orders.
  2. Leave API-origin orders only selected to request orders submitted through API clients. Clear it to include other completed orders visible to the logged-in broker session. Neither choice limits the report to the account selected on another page.
  3. Select Read completed orders. The table may receive rows before the end marker arrives. Wait for End marker received and inspect the freshness label.
  4. Review each row's account, permanent order ID, requested and filled quantities, order state and completed status. Prices and quantities retain the broker's spelling. A missing value is shown as Not reported, never an invented zero.
  5. Use Trades to review individual executions. For the existing execution comparison and CSV export controls, open Connection and account tools and expand Completed orders and execution review.

This is the broker's available completed-order window, not complete account history. The permanent ID is not a client order ID and cannot be used here to repeat a trade. Broker timestamps remain labelled text; the application does not guess their time zone. A row can be old even when a recent end marker completes the report.

There is one completed-order request per connection. After a timeout or completed capture, reconnect before requesting another. If queuing the first request fails, it remains available to retry. Losing the connection marks retained results stale; a new session clears the previous capture. Opening or refreshing this page does not send another request automatically.

Native clients use UmiIbkrGtkReadCompletedOrders and UmiIbkrGtkCopyCompletedOrders on the GTK thread. Headless clients use UmiIbkrCompletedOrderReportCopy on the connection owner thread. The report owns its values, uses one observation time, performs no I/O, and leaves the destination unchanged on failure. Allocate the bounded report on the heap for native event handlers.

Embed the connection window in a GTK application

Create the connection window on the GTK thread with UmiIbkrGtkCreateForPlan, passing a valid Paper or Live plan and an optional native parent window. The constructor copies the settings and prepares the controls before application window observers run. It does not log in or open a socket.

Check the returned window before presenting it. A parent that has already closed is refused. If a host observer closes the new window or parent, removes the application association, or replaces the window content during construction, the constructor returns NULL. Commands and observation-copy APIs are unavailable until construction returns successfully.

Use UmiBrokerWorkspaceGtkOpenConnection to reuse one inspector for a workspace. A repeated call during its creation or presentation returns BUSY; it must not open a second socket or window. Closing the parent retires the workspace and inspector even if another component retains their widgets.

Read an instrument description

An instrument description identifies the security returned by the broker. It is separate from a price subscription: opening this page does not start quotes or place orders.

  1. Open the broker workspace and connect the existing inspector to your local broker session.
  2. Choose Instrument. Enter a positive contract ID and its exchange route. Use an identity returned by instrument search or your broker.
  3. Alternatively, choose Use current quote to copy the quote's contract ID and route into these fields. This fills the form without sending a request.
  4. Choose Read description. The capture heading records the identity actually requested. Editing the fields later does not rename the retained response.
  5. Read each returned description and its completion status. Missing values appear as “Not reported”; an empty completed response means the broker returned no matching description.
  6. If a request is no longer needed, choose Abandon lookup. A late reply cannot become a new result for the abandoned request.

The page preserves exact received decimal text and marks a capture stale after 60 seconds or a disconnected session. Incomplete or failed captures remain distinguishable from completed ones. A minimum tick is descriptive metadata, not proof that an order price is valid on every route or price band.

Option-contract lookups made in the inspector share this request namespace. Their heading retains the requested symbol, expiry, right, strike and exchange instead of displaying a misleading zero contract ID. The currently supported legacy contract-description decoder is limited to server versions 164–176; bond-specific descriptions are not implemented.

Native clients use UmiIbkrGtkReadContractDetails, UmiIbkrGtkCopyContractDetails and UmiIbkrGtkAbandonContractDetails on the existing inspector. The reusable UmiIbkrContractDetailsCopyWithAge returns an owned copy and performs no network I/O. Failed copies leave the caller's output unchanged.

Explore option definitions

An option is a contract with a particular expiry, strike price and right (call or put). A chain groups candidate definitions for an underlying instrument. The lists do not guarantee that every expiry and strike combination is a tradable contract.

  1. Connect the existing local broker session and choose Options.
  2. Enter the underlying instrument's positive contract ID, symbol and type. A stock, index and future use different underlying types. The optional Chain exchange filters discovery; it does not choose a quote route.
  3. Choose Read option definitions. Wait for Complete. An incomplete, failed or stale capture cannot be resolved. An empty completed capture means no chains were returned.
  4. Select the chain and trading class, then select an expiry and strike. No first result is selected for you when the list changes.
  5. Choose Call or Put and enter its currency and explicit resolution route. Choose Resolve selected candidate. This asks for one instrument description.
  6. Open Instrument to inspect the response. Zero matches means the candidate was not resolved; multiple matches need further review. Do not infer a contract ID from a list position.

Definitions expire after 60 seconds. The heading retains the actual requested underlying, independently of edited input fields. If another view replaces a request, a selection or abandon action for the earlier request cannot operate on the replacement. An unavailable chain stays in its original list position. Abandon definitions retires the local lookup; the broker does not offer a matching chain-cancel request.

This page does not subscribe to quotes, exercise options or submit orders. Its limits are 32 chains, 128 expiries and 512 strikes per chain. Overflow and unsupported protocol versions remain explicit errors. The current legacy chain decoder supports server versions 151–176; resolving one option requires 164–176. Authentication and permissions belong to the local broker session.

Framework clients share UmiIbkrGtkReadOptionChains, UmiIbkrGtkCopyOptionChains, UmiIbkrGtkCopyOptionChain, UmiIbkrGtkAbandonOptionChains and UmiIbkrGtkResolveOption on the GTK owner thread. Headless clients can use bounded-age snapshots and UmiIbkrOptionContractRequestWithAge. Copies perform no network I/O, preserve output on failure and own their values. Request IDs retain the identity of a particular capture.

Follow Time & Sales

A tick is one market observation. A trade tick reports a price and quantity; a bid/ask tick reports quoted prices and sizes. The midpoint is the centre between bid and ask. These observations are not confirmations that your own order traded.

  1. Connect the local broker session. In Market data, enter the contract ID and broker-supported exchange for the instrument you want to observe.
  2. Open Time & Sales. Choose Last trades, All Last trades, Bid / Ask or Midpoint. Use Ignore size changes only with Bid / Ask.
  3. Choose Start Time & Sales. A successful request means it was queued; wait for received ticks. Your broker account needs the appropriate live tick permissions. Selecting delayed quotes elsewhere does not enable delayed ticks.
  4. Read the table in sequence order. Exchange timestamps are shown in UTC. Equal price/time observations remain separate events; the application does not invent trade identifiers or remove apparent duplicates.
  5. Review the receipt-state column. A row becomes stale after 15 seconds without a recent receipt, or when its session fails or stops. A recent receipt does not prove a recent exchange event.
  6. Choose Stop tick stream before choosing another subscription. The core spaces requests at least 15 seconds apart. If stopping fails, keep the existing stream visible and retry after reviewing the error.

The page shows the newest 64 events from a bounded 512-event buffer. Its heading distinguishes older retained events outside the view from events already evicted from the buffer. The buffer is not an archive. Prices and sizes retain the exact reported text, including values too precise for the arithmetic model. Missing fields do not become zero; zero-price trade markers remain visible with their flags.

Repainting does not subscribe again. Closing the connection retains stale observations; reconnecting clears the previous session's data. No order is submitted, cancelled or modified by these controls. The current legacy tick decoder supports server versions 151–176; support outside that range must be qualified separately.

Native applications share UmiIbkrGtkStartTimeSales, UmiIbkrGtkStopTimeSales and UmiIbkrGtkCopyTimeSales on the GTK owner thread. Headless clients use UmiIbkrTimeSalesReportCopy on the connection owner thread. The report owns its values, performs no I/O and preserves the destination on failure. Allocate this bounded report on the heap in native callbacks.

Changing or closing a connection

Connect uses the mode, program, port, client ID and Live acknowledgement shown when you choose it. If those settings change while the window prepares the connection, it stops before opening a socket. Review the settings and choose Connect again. Closing the connection window retires the session and its polling timer.

Connect, Disconnect and account requests share one command owner. A repeated action during an update does not start another session or report. Wait for the current action to finish, then try again. Connecting remains read-only: authentication happens in your local provider application, and these controls do not submit orders.

Arrange broker pages

The broker workspace has two resizable panes. Account and positions starts on the left and Chart starts on the right. Each pane has tabs, so you can keep an account report beside a chart or compare market data with a trade report.

  1. Choose a page from the page selector and select Show to reveal it. The choice refers to the page itself, even after you rearrange its tabs.
  2. Choose Move to other pane to move that page. Its inputs, captured observations and subscription identity stay with it. Moving a page does not open another broker connection.
  3. Drag a tab within its pane to change its order. Use the move button to transfer it between panes.
  4. Drag the divider to resize the panes. Choose Stacked for one pane above the other, or Side by side for left and right. Narrow pages scroll so their controls remain reachable.
  5. If you move all pages into one pane, the empty pane hides. Moving a page back reveals it again.

This arrangement lasts for the current workspace. Automatic saving of the broker layout is not provided yet. Application layout-library commands for the separate Umicom Demo workspace do not save this broker page arrangement.

Framework hosts can capture the arrangement with UmiBrokerWorkspaceGtkCopyLayout and restore a validated copy with UmiBrokerWorkspaceGtkApplyLayout. Page IDs remain stable when tab positions change. Hosts own any persistent storage. Layout operations do not request quotes, submit trades or change broker permissions.

Follow live five-second bars

A price bar summarizes an interval: its first price, highest price, lowest price and last price. The Chart page now offers Historical and Live five-second views. Historical requests have a defined end; a live subscription continues receiving bars until it stops.

  1. Connect the local broker session. In Market data, select a resolved contract ID and exchange route. A symbol alone is not a contract identity.
  2. Open Chart, then Live five-second. Choose Trades, Midpoint, Bid or Ask. Decide whether to include only regular trading hours.
  3. Choose Start live bars. The waiting message means a request was queued. It does not prove that the account has market-data permission or that the market is open.
  4. Read the received, retained, evicted, gap and duplicate counts. Up to 512 bars are retained. The chart advances as new bars arrive, including after the buffer fills.
  5. Use Visible bars (zoom) to change the number of bars shown and Bars back (pan) to look earlier in the retained window. Zero offset follows the newest bar. Panning is relative to a moving buffer; it does not pin a timestamp.
  6. Switch to Historical or move the Chart page between panes without creating another subscription. Both chart views retain their own controls.
  7. Choose Stop live bars before requesting another stream. Allow at least 15 seconds between new historical or live-bar requests. Account-wide broker limits still apply.

The heading identifies the contract actually requested even if the Market data fields are edited later. The last visible bar retains reported decimal text. Missing volume is labelled Unavailable; an observed zero remains zero. Volume units come from the broker and are not converted into shares or lots.

A stopped, failed or stale stream clears its drawing. No receipt for 15 seconds makes this view stale; a quiet or closed market can cause that state. Gaps are shown as gaps, with no invented prices. After reconnecting, choose Start again explicitly. Use Connection and account tools for streaming CSV export and the retained raw report.

These controls share the connection window's single selected stream and request ID. Another view cannot silently replace an active subscription. Stop acts only on the request observed when the action began. This is an observation workflow; it does not submit, change or cancel trading orders.

Use the native stream boundary

GTK applications can call UmiIbkrGtkStartRealtime, UmiIbkrGtkStopRealtime, UmiIbkrGtkCopyRealtime, UmiIbkrGtkCopyRealtimeBar and UmiIbkrGtkCreateRealtimeScene through connection_gtk4.h. Calls belong on the GTK owner thread. The native connection owns one selected stream, even though the headless service supports four independent slots.

Copy calls do no network I/O and leave outputs unchanged on failure. Bar, scene and Stop requests require the expected request ID, preventing an old action from targeting a replacement. The scene caller owns a successful scene. Cache it by request, received-bar counter and visible range, and discard it when stale: the retained count alone stops changing when the buffer fills. Closing the window during a notification retires the owner and returns Cancelled.
