Test, install and publish your application

Finishing an application means more than seeing its window once. Another developer should be able to obtain the same source, build it, run its checks and understand where its files are installed. We will finish the Notes exercise with that repeatable sequence.

Test behaviour, including rejection

The Notes model test checks edit history, refusing New while a draft is unsaved, successful saving and protection against an external file change. These tests remain active in a Release build because they do not rely on assert being enabled.

Run the test before editing it. Then make one deliberately incorrect change, such as allowing New to discard an unsaved draft, and confirm that the test fails. Restore the correct implementation afterwards. A test that never detects a broken behaviour is not providing useful protection.

Read a failed build carefully

Open Output and read the compiler’s first useful diagnostic. A missing include, undeclared identifier and linker error occur at different stages. Find the affected source and explain the cause before changing unrelated files.

Use sanitizers in a separate compatible compiler build to find memory and undefined-behaviour errors. They complement, rather than replace, functional checks. A note can be saved to the wrong file without causing an invalid memory access. Both kinds of defect matter.

Install into a new directory

Installation applies the project’s install rules. Use a new practice location, not a working installation you depend on. Launch the installed executable from outside the source directory so that a missing resource is not accidentally found in your checkout.

On Windows, a development installation may still use DLLs from the MSYS2 toolchain. That is different from a self-contained installer for another person’s computer. Before distributing a package, test it in the environment where you expect it to run.

Keep Git steps in the right order

Check git status before changing branches. When the repository is on the intended main revision, review the files, use git add -A, inspect the staged changes, commit and push. A commit records a source snapshot; it does not run your tests for you.

For Umicom Applications, publish changed child repositories first. Framework owns these lessons and shared services. Studio owns its thin integration changes. Update the parent’s native repository lock only after those child commits have been pushed, then commit and push the parent. The separate Git lesson includes every application submodule and the second-machine workflow.

Continue towards larger applications

The same approach scales to a banking training application with account lists, a transfer form and an audit panel. Start with tested account operations, then attach the widgets. Add persistence through the owning Framework Data Server rather than writing SQL from a button.

Your next topics are organised in the course map: deeper C types and pointers; algorithms and data structures; module lifecycle and design patterns; threads and process supervision; databases and transactions; networking and security; and debugging, packaging and performance. Return to one running application as you add each concept. A pattern is easier to judge when you can see the problem it solves.

Build and run the supplied example

Configure the learning targets once using the course setup. Run the commands below one at a time. Stop when a command reports a failure; do not continue to run an older executable.

Windows · PowerShell

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --build --preset windows-ucrt64-all-debug --target umicom-learning-notes-session --parallel 2
& ".\build\windows-ucrt64-all-debug\bin\umicom-learning-notes-session.exe"

Linux · terminal

cd "$HOME/umicom/Umicom-Applications"
cmake --build --preset linux-gcc-all-headless-debug --target umicom-learning-notes-session --parallel 2
./build/linux-gcc-all-headless-debug/bin/umicom-learning-notes-session

Source to study and edit

These are the supplied files for this lesson. Open them in Studio to follow the code. The Notes model is shared by the terminal example and the window; keep one implementation while trying different frontends.

test_notes_model.c

framework/examples/learning/projects/test_notes_model.c

/*-----------------------------------------------------------------------------
 * Umicom Framework — application development lessons
 * File: examples/learning/projects/test_notes_model.c
 * PURPOSE: Check the real Notes model without requiring a graphical display.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/

#include "notes_model.h"
#include "umicom/platform/filesystem.h"
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define CHECK(test) do { if (!(test)) { fprintf(stderr, "line %d: %s\n", __LINE__, #test); return EXIT_FAILURE; } } while (0)
int main(void)
{
    UmiLearningNotes *notes = NULL;
    char *text = NULL;
    UmiDocumentWorkingCopySnapshot state;
    CHECK(!umi_fs_exists("notes.txt"));
    CHECK(UmiLearningNotesCreate(&notes) == UMI_STATUS_OK);
    CHECK(UmiLearningNotesSetText(notes, "first draft\n") == UMI_STATUS_OK);
    CHECK(UmiLearningNotesSetText(notes, "second draft\n") == UMI_STATUS_OK);
    CHECK(UmiLearningNotesExecute(notes, "notes.new", NULL) == UMI_STATUS_INVALID_STATE);
    CHECK(UmiLearningNotesExecute(notes, "notes.undo", NULL) == UMI_STATUS_OK);
    CHECK(UmiLearningNotesCopyText(notes, &text) == UMI_STATUS_OK);
    CHECK(strcmp(text, "first draft\n") == 0); umi_document_store_free_text(text);
    CHECK(UmiLearningNotesExecute(notes, "notes.save", "notes.txt") == UMI_STATUS_OK);
    CHECK(UmiLearningNotesSnapshot(notes, &state) == UMI_STATUS_OK && !state.dirty);
    /* Deleting every character of a saved note is still an unsaved edit. */
    CHECK(UmiLearningNotesSetText(notes, "") == UMI_STATUS_OK);
    CHECK(UmiLearningNotesExecute(notes, "notes.new", NULL) == UMI_STATUS_INVALID_STATE);
    CHECK(UmiLearningNotesSetText(notes, "third draft\n") == UMI_STATUS_OK);
    CHECK(umi_fs_write_text("notes.txt", "external change\n") == UMI_STATUS_OK);
    CHECK(UmiLearningNotesExecute(notes, "notes.save", "notes.txt") == UMI_STATUS_INVALID_STATE);
    CHECK(umi_fs_read_text("notes.txt", &text, NULL) == UMI_STATUS_OK);
    CHECK(strcmp(text, "external change\n") == 0); umi_fs_free_text(text);
    CHECK(UmiLearningNotesExecute(notes, "missing.command", NULL) == UMI_STATUS_NOT_FOUND);
    UmiLearningNotesDestroy(notes); CHECK(remove("notes.txt") == 0);
    puts("Notes model checks passed."); return EXIT_SUCCESS;
}
