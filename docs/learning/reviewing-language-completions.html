Reviewing language-server completions

A completion can do more than insert a word. A language server may replace part of a line and add an import elsewhere in the same document. Framework keeps those edits together and checks them against the document that produced the request. Preparing a plan does not change the editor buffer or save a file.

Connect the editor workflow

  1. Keep one owner for the language platform and its editor buffers. Synchronize the document text through umi_language_runtime_platform_open_document or umi_language_runtime_platform_change_document. Protocol writes can block, so put the platform on a worker and exchange owned messages with a GUI. Do not access its buffers concurrently.
  2. When the user requests completion, call UmiLanguageRuntimePlatformRequestCompletionReview with the document identifier, cursor position and that same authoritative buffer. The platform records the buffer revision. Lines start at zero; columns count UTF-16 units. A character outside the basic Unicode plane occupies two such units.
  3. Pump the owning connection. Framework associates each reply with both the server and request number. A document change, close or newer request retires obsolete answers. Diagnostics are also checked against the sending server and, when provided, the document version.
  4. Obtain the current choices with UmiLanguageRuntimePlatformCompletionCatalogue. This is borrowed storage: copy display values using UmiLanguageCompletionCatalogueAt before the next platform mutation. A platform retains one recent catalogue, not a permanent catalogue for every tab. If the list is incomplete, request it again as the user types.
  5. On selection, call UmiLanguageRuntimePlatformCompletionPlan. Supply the editor's word range and choose insertion or replacement. A server-provided range takes precedence. The fallback word range is used only when no server range exists.
  6. Show the planned primary and additional edits. On acceptance, apply the returned Editor set with umi_editor_workspace_edit_set_apply_document and require_matching_revision=1. Keep using the same authoritative buffer. If it changed while the menu was open, request fresh completion instead.
  7. Synchronize the accepted buffer back to the language platform, refresh the editor view, and let the normal save workflow write it to disk. Destroy the edit set after use. Destroying the platform releases its retained catalogue and connections.

Convert the editor cursor correctly

A text widget may report a character index while a source buffer uses bytes. Obtain a stable UmiEditorTextBufferView and use UmiEditorTextViewPositionAt to convert a known UTF-8 byte offset into a protocol line and UTF-16 column. Use UmiEditorTextViewResolvePosition for the reverse direction. Release the borrowed view before changing its buffer.

The conversion treats LF, CRLF and standalone CR as line endings. It refuses offsets inside a UTF-8 character or between CR and LF. It also refuses a column between the two UTF-16 units of a supplementary character. No coordinate is rounded or clamped. Completion planning checks the request cursor using this same service, as well as resolving every edit endpoint.

Use an already received result

A transport adapter can use UmiLanguageCompletionCatalogueReadResponse for a complete JSON-RPC response and expected numeric request ID. A caller that already correlated the envelope can use UmiLanguageCompletionCatalogueCreate with only the result value. Each owns its input copy. Neither changes a live model. UmiLanguageCompletionPlanCreate prepares the selected entry against the supplied request revision and buffer.

The existing display-only completion API remains available. It does not capture a buffer revision, so its replies cannot be applied through the platform's reviewed-plan API. The older display registries also keep their existing field and item limits; use the owned catalogue when edit metadata matters.

Try the learning example

The completion-review example uses a captured response for puts and its standard-library include. With no arguments it prints a preview. With --apply it applies both edits to an in-memory lesson buffer and prints the resulting text. It does not launch a server or touch a source file. Its target is umicom-completion-review-example when learning examples are enabled.

Limits and recovery

The owned reader accepts up to 1 MiB of JSON and 2,048 choices. Display fields have explicit capacities in the public header. A selected plan supports at most 64 additional edits and 511 UTF-8 bytes per replacement or expected span. Oversized values are refused rather than shortened. The existing persistent transport still has its smaller message and token limits; a larger catalogue limit does not enlarge that transport.

If planning reports a stale revision, update document synchronization and request again. A range that cuts through a Unicode character or refers outside the buffer is refused. If a server requires snippets or commands, retain the user's text and explain that this completion cannot yet be applied. Hosts should advertise only capabilities their acceptance path implements; the established initialization API remains unchanged.

Server-to-client requests still require a host handler. Consuming one does not satisfy a client's pending request that happens to have the same number. Notification messages without a document version cannot prove freshness; Framework checks their connection and open document instead.

The native connection panel checks startup and advertised capabilities only. Studio's separate Complete… editor action now captures a document request, sends copied source to a worker and presents a complete result for explicit review. Application uses the document coordinator and its Undo history. Automatic completion while typing remains a separate integration task.
