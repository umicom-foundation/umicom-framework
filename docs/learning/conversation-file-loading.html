Load conversations without losing state

A conversation file is external input even when it lives on the same computer. It can be incomplete, edited by another program or copied from an older workspace. A failed load should report the problem while preserving the record already displayed in the application. This lesson follows the native Framework parser and its two file-reading interfaces.

Prerequisites: C pointers, return values and conversation records and revisions. The public contracts are in conversation_archive.h. Parsing and reading do not run a model or grant permission to persist or transmit a conversation.

1. Prepare a candidate before replacing the current value

An unsafe loader clears the caller's record and writes fields into it as lines arrive. A malformed line near the end then returns an error after destroying the previous valid record. Transactional parsing means building a separate candidate and publishing it only after every required check succeeds.

  1. Check the input pointer, exact byte length and format-size limit.
  2. Copy input into temporary storage and allocate a separate record candidate.
  3. Parse and validate the complete candidate.
  4. Replace the caller's record only after success; free temporary storage on every path.

UmiAiConversationRecordParse follows these steps. Its input is an explicit byte span, so a zero byte hidden in the middle cannot silently truncate the file. The input may even borrow bytes from the previous output record: the copy is complete before publication. A failure, including allocation failure, preserves the previous record.

#include "umicom/ai/conversation_archive.h"

UmiStatus read_selected_conversation(
    const char *absolute_path, UmiAiConversationRecord *current)
{
    /* The application has already obtained the user's selected path.
     * On any error, current keeps its previous complete value. */
    return UmiAiConversationArchiveLoadBounded(
        absolute_path, UMI_AI_CONVERSATION_FILE_MAX_BYTES, current);
}

The maximum accepted format size is 1 MiB. It exceeds the worst-case escaped representation of this fixed-capacity record. Applications can choose a smaller file budget. This is a format/resource boundary, not a claim that all files below the limit are valid.

2. Require one complete meaning for each field

The v1 writer emits thirteen metadata fields and three fields for each declared message. Each appears exactly once. Their order is free; empty lines, CRLF line endings and a missing final newline are accepted. An optional message name or text may be empty, but its field still has to appear. Use the Framework writer to produce files instead of hand-building an incomplete header.

format=umicom-ai-session-v1
session.id=session.example
session.provider=provider.local
session.model=model.chat
session.created=1
record.workspace=workspace.example
record.title=Example
record.classification=2
record.remote-approved=0
record.persistence-approved=0
record.updated=1
record.revision=1
message.count=0

A second classification field could override an earlier privacy choice. A second message field could replace text the first reader displayed. The parser rejects both. It also rejects message fields beyond the declared count, missing fields, unknown keys and unknown format versions. A duplicate index spelled as 00 still refers to index zero and cannot bypass duplicate detection.

The writer escapes special bytes with percent notation: a newline becomes %0A, percent becomes %25, and an equals sign becomes %3D. Valid escapes are decoded. An escaped zero byte, %00, is refused because it would hide subsequent bytes from C string consumers. This format does not add signatures, encryption, provider identity or proof that generated text is trustworthy.

3. Check numbers before narrowing them

Standard unsigned conversion functions can accept a leading sign or whitespace. Those spellings are unnecessary for this file format. Framework's shared umi_ascii_uint64_parse accepts unsigned decimal digits and checks overflow before arithmetic. The conversation parser translates invalid numeric fields into a parse error.

Classification is checked while still represented as a 64-bit value, before conversion to its enum. Otherwise a large value could narrow into a valid-looking classification. Message indices are checked before indexing storage. Timestamps and serialized revisions may use the complete unsigned 64-bit range; an archive assigns its own new stored revision when a loaded record is inserted.

InputOutcome
Ordinary unsigned digits within the field's domainAdmitted
-1, +1, leading whitespace or trailing textParse error
A value larger than the unsigned 64-bit maximumParse error
Classification outside the declared enum rangeParse error before narrowing
Message count or index outside fixed storageParse error before access

4. Choose the file reader deliberately

APIInput and resource behavior
UmiAiConversationRecordParseParses existing bytes; no filesystem access; enforces the format-size bound.
UmiAiConversationArchiveLoadBoundedRequires an ordinary absolute regular-file path and a byte budget. Rejects an oversized file before allocation using the shared input-file service.
umi_ai_conversation_archive_load_recordRetains compatibility with the existing relative-path/link behavior. Allocates the whole file before the parser applies its size bound.

The bounded reader rejects a final symbolic link, reparse point or device. Parent aliases can still be followed, so choose a trusted directory; this is not a directory sandbox. It checks the same open handle for observable changes, but that is not a guarantee against every concurrent writer. File I/O can block: an interactive application should call from an owned worker and publish the result only to the request that selected it.

Both file interfaces now share staged parsing. Complete files emitted by the existing writer remain supported. Incomplete or ambiguous files that earlier code happened to accept are refused. Keep the original file for investigation; do not quietly fill in missing privacy metadata or drop duplicate messages.

On Windows, start in the Framework repository with its configured UCRT64 toolchain available. Use the existing Debug preset, then build the focused targets and run the selection below. Stop after a failed command.

The forty parsing scenarios cover valid complete files, line endings, field order, maximum message counts, exact integer limits, aliased input and malformed values. The file round trip checks both readers, an exact byte budget, an insufficient budget and unchanged output after a late parse failure. Registration alone does not prove these tests passed.

  1. Load a valid record and keep a copy of its title and messages.
  2. Remove one required field from a test file. Expect a parse error and the original record still present.
  3. Add a second message text field or an out-of-count message. Confirm refusal instead of silent replacement or omission.
  4. Set a byte budget smaller than the valid file. Expect CAPACITY_EXCEEDED before the bounded reader allocates the file buffer.
  5. Restore the valid file and reload it. Successful recovery should not require resetting unrelated application state.

If a test is absent, reconfigure from the updated source. For a parse error, inspect a copy of the file and its exact fields; avoid placing sensitive conversations in public logs. For a capacity error, compare the real file size with the chosen budget and field capacities. Missing exported symbols in an installed application require rebuilding and reinstalling a matching SDK, then running its consumer example. That example exercises parsing offline; its invalid-path check only resolves bounded-load admission and does not qualify real file I/O.

6. Import the parsed record into a live service

Parsing answers whether a file represents a complete conversation. Importing asks a separate question: may this candidate replace the record currently owned by the service? Another user action may have edited that record while a worker was reading the file. Keep those two decisions separate.

UmiAiAuthorEngineImportSession takes an already parsed record and an expected stored revision. Zero means insert only when the session identifier is absent. A nonzero value means replace only the matching existing record at that revision. A conflict returns UMI_STATUS_BUSY and preserves the archive, active session, service revision and output report. Do not resolve a conflict by automatically retrying with a newly read revision: show the current record and let the user choose.

#include "umicom/ai/authorengine_service.h"

/* Run on the serialized service owner after the application confirms that
 * this completion still belongs to the request that selected the file. */
UmiStatus adopt_loaded_session(
    UmiAiAuthorEngineService *service,
    const UmiAiConversationRecord *candidate,
    uint64_t selected_stored_revision,
    UmiAiConversationImportReport *report)
{
    return UmiAiAuthorEngineImportSession(
        service, candidate, selected_stored_revision, report);
}
  1. When replacing an existing session, read its stored record and retain that revision. For an explicitly new session, use zero.
  2. Read and parse the selected file into worker-owned storage. Keep the service itself on its serialized owner.
  3. On completion, check the application's initiating request and workspace identity before touching the service. Conditional record admission alone does not detect that the user switched to another workspace.
  4. Call the import function with the captured stored revision. On success, use the report to identify the newly active session. On failure, retain the current display and report the cause.
  5. Release the candidate after the call; the archive owns its own copy.
Report fieldMeaning
source_record_revisionThe historical value from the candidate or saved file. It may be zero or the unsigned maximum.
stored_record_revisionThe new revision assigned by the destination archive. Use this identity for a later conditional edit.
service_revisionThe service revision after successful import and active-session selection.
replacedWhether this operation replaced the explicitly selected existing record.

Do not compare revisions across independent archives or use a file's historical number as a destination revision. Counters describe their own owner. At counter exhaustion the operation refuses before publishing state; it does not wrap to an old identity.

For a synchronous command, UmiAiAuthorEngineLoadSessionBounded combines the bounded reader with conditional import. It can block for file I/O and requires exclusive serialized ownership throughout. The separate parse/import workflow is more suitable for an interactive application. These APIs add no worker thread or GUI file chooser.

Import does not register a provider, load a model, contact an endpoint or modify the service's provider/privacy policy. Saved classifications and approval flags remain record metadata; importing them is not proof of fresh user consent or of the file's authenticity. Review the current policy and consent at any later execution or persistence boundary. The legacy umi_ai_authorengine_service_load_session still exposes its compatibility reader and unconditional replacement behavior; its output contains the historical parsed record rather than this new import report.

Create an independent conversation branch

A branch lets someone try a different explanation or question from a chosen point in a saved conversation. It is a new document in the existing native archive, not a replayed provider request or learned model memory. UmiAiConversationArchiveBranch copies an explicitly selected prefix and keeps the original session unchanged.

  1. Read the source record from the archive and retain its current revision. Present the selected message count, new session identifier and title for review.
  2. Call the branch operation on the serialized archive owner thread. Zero messages creates an empty branch with the same provider/model/workspace selection; a larger count must fit the source's visible message extent.
  3. On success, use the returned source/destination IDs and revisions to identify the operation. Read the new record through the existing archive API. The containing application chooses whether to activate it; the branch operation does not switch the current session.
  4. Review current policy before sending the copied content to any provider or saving it to disk. The new record deliberately has both remote_approved and persistence_approved cleared.
  5. Persist the branch through the existing approved archive workflow when requested. The version 1 conversation file stores the new record, but not the separate branch receipt. A host that needs lasting parent relationships must store that metadata explicitly in its own reviewed project records.
/* archive is an existing serialized owner; source_revision came from Find. */
UmiAiConversationBranchReceipt branch;
UmiStatus status = UmiAiConversationArchiveBranch(
    archive, "session.source", source_revision,
    "session.alternative", "A different explanation", 3U,
    creation_time_ns, &branch);
if (status == UMI_STATUS_OK) {
    /* branch.destination_revision identifies the newly accepted record.
       No provider request, disk write or active-session change occurred. */
}

The branch keeps the provider, model, workspace and data classification of its source. It receives a new session and conversation ID, explicit title and supplied creation/update timestamp. A timestamp is caller-provided metadata, not proof of when a remote operation happened. Messages retain their historical roles and visible names/text; unused slots and bytes after string terminators are not copied. A historical tool-role message is not evidence that a tool ran and does not authorize executing it.

ResultWhat the host should do
BUSYThe selected source revision changed. Reread it and review the intended prefix again. An unrelated record edit does not invalidate a still-current source revision.
ALREADY_EXISTSThe proposed destination ID already belongs to a record. Choose a new ID; branching never overwrites the source or an earlier experiment.
NOT_FOUNDThe source was removed or the ID is incorrect. Preserve the draft choice and select an existing source.
CAPACITY_EXCEEDEDThe archive has no free record slot or its revision counter is exhausted. Do not evict history or wrap revisions automatically.
OUT_OF_MEMORY or invalid inputThe archive and output receipt remain unchanged. Report the refusal; no partially created branch needs to be removed.

This operation shares the archive's bounded record/message limits. It does not add an unbounded transcript store, clone model state, synchronize multiple processes or grant consent inherited from another session. Keep owner access serialized and preserve any operation receipt your product needs before its own next action.

Export a selected conversation for reading

An archive preserves the complete native record. A transcript is a reading view of messages that the user chose to disclose. UmiAiConversationTranscriptMarkdown creates a Markdown content fragment in caller-owned memory. It performs no file write, network request or tool execution.

  1. Obtain a stable record snapshot through the archive API. Keep it unchanged while measuring and rendering.
  2. Select a zero-based range and an explicit role mask. UMI_AI_TRANSCRIPT_DIALOGUE selects user and assistant messages. System and tool messages require their own explicit role flags. A range may select zero messages.
  3. Measure the fragment, then allocate the reported byte count plus one byte for the terminating zero. The same selection must remain valid when rendered.
  4. Render and review the fragment. Title and classification are included. Session, provider, model and workspace identifiers, timestamps and approvals are omitted. Message names are included only when requested.
  5. Compose the fragment into the product's approved branded document using Framework's resource catalogue and supplied SVG assets. This formatter does not create a complete document or add a watermark by itself.
  6. Before saving or sharing, check the current privacy policy and destination. Use the existing persistence check for a file export and the appropriate sharing check for a remote destination. Rendering text does not approve either action.
#include "umicom/ai/conversation_transcript.h"
#include <stdlib.h>

/* The caller owns a stable record and receives text only after success. */
UmiStatus make_dialogue_fragment(const UmiAiConversationRecord *record,
    char **out_text, size_t *out_bytes)
{
    if (record == NULL || out_text == NULL || out_bytes == NULL)
        return UMI_STATUS_INVALID_ARGUMENT;
    UmiAiConversationTranscriptOptions selection = {
        0U, record->conversation.message_count, UMI_AI_TRANSCRIPT_DIALOGUE, 0
    };
    size_t bytes = 0U;
    UmiStatus status = UmiAiConversationTranscriptMeasure(record, &selection, &bytes);
    if (status != UMI_STATUS_OK) return status;
    char *text = malloc(bytes + 1U);
    if (text == NULL) return UMI_STATUS_OUT_OF_MEMORY;
    status = UmiAiConversationTranscriptMarkdown(record, &selection, text, bytes + 1U, &bytes);
    if (status != UMI_STATUS_OK) { free(text); return status; }
    *out_text = text;
    *out_bytes = bytes;
    return UMI_STATUS_OK; /* The caller releases text with free. */
}

The output retains original one-based message numbers after filtering, so selecting messages 2 and 3 does not rename them to 1 and 2. A historical role is a label, not proof of tool execution. The classification remains the record's original classification even when some messages are omitted; the formatter never downgrades it.

Every title, optional name and message body appears in a literal fenced block. The fence is longer than every run of tilde characters in that field, so a message containing a fence, HTML or a heading remains literal text in a CommonMark-compatible viewer. This deliberately preserves code examples instead of treating model output as trusted formatting. The fragment is not HTML and cannot be imported as an archive. A host must not pass its raw bytes to an HTML interpreter.

The service first validates the complete bounded record, then validates UTF-8 in fields that will actually be emitted. It accepts tabs and line endings, but refuses other ASCII control characters and malformed encoding. It preserves other Unicode characters without checking visual confusables or changing normalization. Invalid UTF-8 in an excluded message is not emitted; an unterminated active record field still fails the complete-record check.

ResultRecovery
CAPACITY_EXCEEDEDMeasure the current immutable input again and provide that many bytes plus one. A failed render leaves the previous buffer and byte count unchanged.
PARSE_ERRORInspect the encoding of the selected title, name or body. Do not silently discard bytes or claim a complete export.
INVALID_ARGUMENTCheck record termination, message extent, role mask, output pointers and control characters. The output objects must not overlap the input record or selection.

The formatter allocates no memory and has a one-megabyte output limit. The example allocates a destination explicitly; allocation ownership belongs to the caller. Revisions, consent and selected content may change after rendering, so a later save/send workflow must still confirm the intended snapshot and current destination policy.

The transcript regression source covers an exact expected fragment, selection, omitted fields, fence-containing content, Unicode, line endings, full records and unchanged output on failure. Use the conversation service from your own application

The offline C example constructs three synthetic messages, stores them in the native archive, creates an independent branch and prints only the user/assistant transcript. Its standalone CMake recipe links the installed Umicom::ai target. It does not need a Framework source checkout, model server, provider account or database file.

  1. Build and install a matching Framework SDK that includes the current conversation APIs and the ai component. Use the same supported compiler/runtime family as that SDK.
  2. Copy the complete share/umicom/framework/examples/conversation_archive directory from the installed package into your own project directory. Both CMakeLists.txt and main.c are required. The full Framework, selective FrameworkSDK and documentation packages carry these sources; a documentation-only package does not supply linkable libraries.
  3. From that copied directory, configure with the absolute path to your installed SDK, then build and run the offline test. Stop on errors.
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DUMICOM_SDK_ROOT="C:\SDKs\UmicomFramework"
cmake --build build
ctest --test-dir build -R '^sdk[.]conversation[.]branch_transcript$' --output-on-failure --no-tests=error
& ".\build\bin\umicom-sdk-conversation.exe"

Replace the example SDK prefix with your actual installation. Expected output is a literal Markdown fragment titled Alternative explanation, with classification internal and messages numbered 2 and 3. The synthetic system message is excluded. Exit zero requires successful archive construction, permission-reset checks, selected formatting, output and cleanup. These are expected results to verify, not evidence that the consumer has already run.

The recipe reuses SDK origin and ABI checks and the shared application-branding helper. That helper supplies approved resources and the Windows icon; icon appearance still needs visual qualification. If a symbol is missing, rebuild and reinstall matching libraries and headers together. Do not add Framework implementation files to the consumer to hide a mismatched SDK.

The producer also registers the same C source as an offline integration exercise. It checks public API composition within the producer build, which is separate from validating an installed package:
