Select source relative to its workspace

1. Separate a file address from a policy path

A file address tells the filesystem what to open. A policy path tells an analyser where that file belongs inside the workspace the caller selected. Using the full address for exclusion rules lets unrelated ancestor directory names change the result. For example, selecting C:\build\projects\demo must not silently exclude demo\src\main.c because build appears outside demo.

2. Reuse the Framework path service

char relative[UMI_PATH_CAPACITY];
UmiStatus status = umi_path_relative(
    workspace_root, visited_path, relative, sizeof relative);
if (status != UMI_STATUS_OK)
    return status;
/* Apply workspace selection to relative, while opening visited_path. */

Include umicom/platform/path.h and link Umicom::platform. Both inputs must be expressed in a compatible coordinate system. Directory traversal supplies paths derived from its selected root. This calculation is lexical: it processes path text without accessing storage, discovering the working directory or resolving symbolic links.

Normalization represents an empty relative location as a dot. A dot has zero named components. From "." to "src/main.c", the correct relative result is "src/main.c". From "src" to ".", it is "..". Counting the dot as a directory would introduce an unnecessary ascent. Framework handles this boundary centrally so CodeGuard does not invent another path parser.

3. Match directory components, not substrings

CodeGuard excludes .git, node_modules, third_party and adjacent codeguard/rules directories below the selected root. By default it also excludes build and _CPack_Packages; scan_generated opts into those two directory categories. Language flags still decide which source files are admitted. The names build-tools and rules-extra do not match. A file named build.c does not match a build directory. Component comparison uses Framework's existing platform case behavior: ASCII case-insensitive on Windows and case-sensitive on POSIX. Unicode bytes are preserved; this does not imply Unicode case folding.

Workspace-relative templates/workspace payloads are still scanned, but they are omitted from duplicate comparisons against the live workspace. A templates/workspace ancestor outside the selected root does not suppress duplicate comparisons inside the selected project. Direct-file scanning remains an explicit request and bypasses recursive workspace exclusions.

4. Keep the boundary honest

A relative result beginning with a parent ascent means the visitor supplied a path outside the expected lexical root. The scanner rejects that inconsistent state instead of applying inside-workspace policy to it. Prefixes must end at a component boundary: project and project-other are different roots.

This is selection policy, not a security sandbox. Traversal retains its existing no-follow-symbolic-links setting, but lexical checks do not prevent filesystem races, aliases or hard links. Excluded directories are still traversed by the current walker before their files are filtered; this change does not add pruning or improve traversal cost. Keep the process working directory stable while using relative scan roots. Prefer an absolute root for a long-lived service.

Path tests exercise Unicode spelling without opening files. Native file reading has separate platform and encoding requirements; passing a lexical Unicode case does not qualify every Unicode filesystem workflow. Profile-driven reads now use the shared native UTF-8 reader; separate actual-file regressions cover a UTF-8 leaf name. Those authored cases still require execution on supported hosts. See bounded source input. Architecture rules retain their separate path classification, and file contents may change between analysis passes.

5. Build a fixture that can expose the bug

  1. Create a disposable workspace below an ancestor named build.
  2. Place eligible files under src and build-tools. Place generated files inside the workspace's own build directory.
  3. Scan the workspace by absolute path, relative path and dot from inside it. Compare selected source, not just exit status.
  4. Select the inner build directory explicitly and verify its source is considered relative to that new root.
  5. Call the direct-file API on one generated file and verify that the explicit request still scans it.

The configured fixture contains eight eligible source files and seven excluded source files. A deliberately small line-length threshold produces one predictable finding for each selected file. These findings make a wrongly empty scan observable. Other analyses are disabled for this fixture; their own tests remain necessary.

cmake --build build --target umicom-path-relative-current-tests umicom-codeguard-path-policy-tests umicom-codeguard-workspace-exclusions-tests
ctest --test-dir build -R "^framework[.](path_relative_current|codeguard_path_policy|codeguard_workspace_exclusions)[.]" --output-on-failure --no-tests=error

Use your configured directory in place of build. The suite registers twenty shared path cases, twenty-nine policy cases and six real-scanner selection cases. Run the existing path, scanner and cancellation checks too. Successful configuration only creates build rules and fixture input; it is not execution evidence.

Read scan profiles for language selection and generated-source options. The eight-file fixture above uses the default generated-source policy.

Exercises

  1. Explain why selecting a directory named build differs from selecting its parent.
  2. Add a nonadjacent codeguard/other/rules path and verify it remains eligible.
  3. Compare an ASCII case variant on Windows and POSIX, then explain why that test says nothing about Unicode case folding.
  4. Describe the additional filesystem controls needed for a security boundary. Keep those controls separate from ordinary source-selection policy.
