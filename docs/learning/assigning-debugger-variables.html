Assigning debugger variables

A debugger can change a variable in a paused program without editing its source file. The adapter, which connects the debugger to the running program, must advertise support for this operation. Framework provides an explicit assignment API for captured root variables and children.

Use a current captured row

  1. Start the native debugger, pause it and inspect its stopped frame. Keep the platform and its workspace on one owner thread.
  2. Capture a root with UmiDebugVariableTargetCapture, or capture a child from an inspected page with UmiDebugVariablePageTarget.
  3. Display the captured name and value. Let the user enter a replacement and deliberately confirm the change.
  4. Call UmiDebugRuntimeCheckVariableAssignment for presentation, then UmiDebugRuntimeAssignVariable for the actual action. The assignment repeats all state checks.
  5. Check both the returned status and attempted. If an attempt occurred, all earlier variable captures are stale. Read the current scope again before offering another edit.
#include "umicom/debug_runtime/variable_assignment.h"

/* platform, workspace and target belong to the current inspected stop.
 * replacement comes from the user's reviewed draft. */
UmiDebugVariableAssignment result;
UmiStatus status = UmiDebugRuntimeAssignVariable(
    platform, workspace, target, replacement, 1500U, &result);
if (result.attempted) {
    /* Discard interactive rows made from earlier captures. Do not retry here.
     * Offer a separate inspection action to obtain current values. */
}
if (status == UMI_STATUS_OK && result.confirmed) {
    /* result.value.result is the adapter's reply, not an independent readback. */
}

Understand the result

attempted == 0 means this call did not submit an assignment. A stale capture returns BUSY; an unsupported adapter returns NOT_IMPLEMENTED. Duplicate sibling names return ALREADY_EXISTS because the protocol identifies a variable by its parent container and name, not its visual row index.

attempted == 1 means transport submission began. The program may have changed even if the reply timed out, was rejected or could not be decoded. Framework clears retained variable registry rows and invalidates captured targets before submission. Owned target text remains readable for an explanation, but it cannot authorize another assignment.

confirmed == 1 means a complete successful reply arrived with no buffered debugger events. It does not guarantee that every related value stayed unchanged. Assignment can run target-language code, and automatic retries are inappropriate.

Limits and recovery

  • Replacement text must be valid UTF-8, at most 1023 bytes. The adapter interprets it in the target language; Framework does not evaluate or rewrite it. An empty replacement is allowed.
  • The native session must still be paused in the captured frame. Queued events are retained for normal processing and cause a refusal or an unconfirmed outcome.
  • A scope is a container, not an assignable variable. Expand it to select an actual child. Scalar variables can be assigned even though they have no expandable child reference.
  • After any attempt, process pending debugger events and inspect the current scope before deciding whether another change is needed. If execution resumed, pause and inspect again.
  • There is no automatic undo, retry, watch evaluation or source-file edit. This workflow uses setVariable; expression-only adapters do not gain assignment support through it.
  • The older low-level setters remain available. Their strict decoder now reads assignment replies correctly, and they invalidate prior variable captures before a request attempt. They do not provide the captured-workspace policy of UmiDebugRuntimeAssignVariable.

Extend the implementation

The shared target retains the parent reference separately from the child's expansion reference. Keep these identities separate when adding new variable views. Protocol decoding lives beside the child-list decoder, while the native platform owns capability checks and transport. Add a focused regression for any new response field or adapter behavior before exposing it in another application.

The Debug Adapter Protocol specification defines the container/name request and the response's value field. This differs from an evaluate response's result field.
