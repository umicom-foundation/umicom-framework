Review recent broker executions

An execution is a reported fill. A single order can produce several execution reports. Framework captures these reports through the existing read-only TWS connection and presents them in Umicom Trader's broker window.

Read a capture

  1. Start TWS or IB Gateway and enable its API connection. Follow the connection guide. Keep the provider's read-only API setting enabled for this workflow.
  2. Open Trader's broker connection window, connect to the intended Paper or Live session and select an account from the advertised accounts list.
  3. Expand Recent executions and stock quantity comparison and select Read selected account's recent executions.
  4. Wait for the execution end marker. Until it arrives, the view remains incomplete. An empty completed capture means no matching reports were returned.
  5. Inspect the execution IDs, times, quantities, prices, permanent order IDs and contract IDs. The capture contains up to 256 distinct execution reports.
The capture covers the recent reports TWS makes available to this API client. It is not an account statement or a complete history. API client settings can limit visibility. The end marker finishes this request; it does not mean every order has finished.

Compare an intended stock quantity

  1. Copy the positive permanent order ID and contract ID from the captured rows into the matching fields.
  2. Select Bought or Sold and enter the intended stock quantity, such as 7000.
  3. Read the comparison below the capture. Reports for exactly that permanent order, contract and side are added using exact decimal arithmetic. For example, distinct fills of 10 and 6,990 total 7,000. Repeating the same report does not add its quantity again.
  4. If the observed total is below the intended quantity, check the order in TWS. A further execution may still arrive after the capture. The application does not infer cancellation, rejection or finality from a smaller total.

Related execution IDs may indicate a correction. Both versions remain visible, but quantity aggregation is withheld because arrival order does not establish which corrected report should be used. Combo-style execution IDs and other asset classes remain visible but are outside this stock-only comparison.

Read commission reports

Commissions arrive separately. Each matching execution shows its reported amount and currency when received. The comparison shows a commission total only when every selected stock execution has a consistent exact amount in the same currency. A missing fee is not treated as zero, and different currencies are not converted or added together.

The view retains the first and latest texts when amounts or currencies conflict and asks for review. Negative reported amounts, such as rebates, remain negative. Fees outside the exact decimal range remain visible as provider text, with no total.

Fee reports have no request ID. This capture accepts them only for an execution already received, during the connection's capture timeout window, including after its execution end marker. Reports arriving before their execution or after that window remain unavailable. Request another capture and compare against TWS if fees are missing. Captured fees are observations, not guaranteed final charges.

Recover from an incomplete capture

  1. If the request times out or is refused, read the message and inspect TWS diagnostics. Partial rows are retained as incomplete.
  2. Abandon local execution capture retires the local read request. It never cancels or modifies a broker order.
  3. Start another capture when ready. A new accepted request replaces the previous capture. Late replies from the old request are ignored.
  4. After disconnecting, retained results are labelled stale. Reconnect and request another capture before relying on the comparison.

Final order-state reconciliation and transmission of FOK or AON orders are separate capabilities. This view cannot guarantee full-quantity execution or prevent a commission. See full-quantity order policy for the distinction between a local liquidity watch and an enforceable broker instruction.

Extend the shared implementation

The connection owns request identity and copied observations. New interfaces can use UmiIbkrExecutionsRequest and UmiIbkrExecutionsCopy without depending on GTK. Keep large capture snapshots on the heap. Do not combine cumulative quantity with individual fills or use an API order ID as an account-wide identity. Add provider-specific correction and combo reconciliation before broadening aggregation beyond ordinary stock executions.

Protocol layouts are supported for the connection's negotiated legacy range of 164 through 176. Unsupported layouts are refused. Decimal values requiring more than nine nonzero fractional places or exceeding the coefficient range are refused rather than rounded.

Provider references: request execution details, receive execution details and execution ID behavior.

See IBKR commission report documentation for the separate provider event.

Keep order status separate from execution totals

Execution totals answer how much the captured reports contain. They cannot establish whether an order is still working. In the shared API, UmiIbkrReviewOrderObservation retains the broker status and its cumulative filled and remaining quantities. A working order with fills and a positive remainder can be classified as partially filled. A cancellation request remains pending until confirmed. The status-only compatibility mapping now leaves its output unchanged for Inactive, warnings and pending cancellations.

  1. Match a status observation to the order identity in your connection owner before using it.
  2. Display the original status alongside filled and remaining quantities. Do not add cumulative quantities as if they were new executions.
  3. Use the proposed local status only when hasCanonicalStatus is true, and apply the journal sequence checks before updating retained state.
  4. If Filled is paired with no filled quantity or a nonzero remainder, retain the conflicting evidence for review. Do not infer that FOK or AON was enforced, or that a cancelled order had no fills.

This classification API does not request or subscribe to order-status messages in the read-only connection panel. A status such as Inactive alone does not establish rejection; inspect the accompanying broker error and order context. See IBKR order-status meanings.
