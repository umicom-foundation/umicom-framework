Update a learning pack without losing your place

A product guide can change while someone is reading it. Replacing the catalogue's copy immediately could make a link open a different lesson or cause a practice example to come from a revision the reader has never seen. Umicom separates the catalogue from each reading session. You review the proposed catalogue update, accept it explicitly, then choose when to begin reading that new revision.

This guide describes the shared Framework catalogue opened from Studio's Guided Learning surface. It updates in-memory catalogue metadata. It does not install software, download a pack, rewrite a manifest or overwrite course files. Start with Using the learning catalogue if you have not loaded and opened a pack before.

Understand the three records

RecordWhat it meansWhat it does not mean
Pack revisionA positive number in the manifest identifying an edition of one pack.A larger number does not prove the material is correct or the publisher is trustworthy.
Shelf generationA counter changed whenever this catalogue successfully adds, removes or replaces a pack.It is not a global version shared by every application or user.
Review serialA local identifier for one successfully prepared replacement in this window.It is not an account credential, signature or permission to run examples.

A manifest is the pack's learning-pack.json file. It contains identifiers, titles, resource filenames, hashes and compatibility bounds. A hash is calculated from a file's bytes; a changed file produces a different value. The catalogue admits a manifest first. A later resource open reads the file and checks its bytes against that admitted hash.

1. Prepare a separate updated folder

  1. Keep the currently loaded pack folder available. Its reader may still need it when you select Back, Forward, a local link or Reload and verify.
  2. Obtain or create an updated pack in a separate folder. For a course you maintain, review the source material and regenerate a consistent manifest and file hashes.
  3. Keep the same pack identifier, product identifier and locale. Increase the pack revision. For example, a Framework English guide at revision 1 can be replaced by revision 2 of the same guide. A different product or language is a different identity.
  4. Keep the compatibility bounds accurate for the host application. The replacement manifest passes the same compatibility admission as a newly loaded pack.

Do not edit the loaded folder merely to make a checksum error disappear. An existing reader intentionally keeps its admitted hashes. Using a separate folder lets the previous reader continue checking the previous edition while new readers use the updated edition.

2. Review the proposed replacement

  1. In the catalogue's Learning pack folder field, choose the updated folder. This changes the path field; it does not change a loaded pack.
  2. Expand Replace a learning pack.
  3. Select Review replacement. Wait for preparation to finish. The request owns a copy of the selected path, so changing the field afterward cannot redirect the accepted read.
  4. Read the displayed pack identifier, product, locale and revision transition. The proposed revision must be strictly greater than the currently admitted one.
  5. Expand Resource changes. Review added, removed and modified resources. Modified entries show previous and proposed filenames and SHA-256 values, plus changed titles, topics, resource kinds and linked-example identifiers. An unchanged hash means the two manifests declare the same bytes; it is not proof that either current file has been checked.

Preparation reads the manifest in the background and prepares a separate catalogue candidate. The displayed document, current search and admitted shelf remain unchanged. It does not read every resource in the pack or authenticate its author. A missing manifest, incompatible product version, absent pack identifier or non-increasing revision is refused.

There is one pending review per catalogue. A successful new preparation replaces the earlier pending review. A failed preparation keeps it. Always read the review shown in the window before accepting; a failure message does not imply that an earlier review was discarded.

3. Accept or discard

  1. Select Accept reviewed replacement only after checking the review. The catalogue first prepares results for the current search query.
  2. If the shelf changed since preparation, acceptance is refused. For example, loading another pack changes the shelf generation. Review the replacement again against the current catalogue.
  3. If search preparation fails, the earlier catalogue, search and pending review remain available. Correct an invalid query, or address the reported resource problem, before retrying.
  4. Use Discard replacement to abandon the pending candidate. This does not remove or change an already loaded pack.

The commit point is deliberately small: once candidate metadata and search results are prepared, their ownership is transferred together. A model notification cannot expose a new result list backed by the old shelf. Another operation is refused while publication is in progress, including one started from a callback.

4. Choose when to switch your reading session

After acceptance, the currently displayed reader still owns its previous pack, verified text and history. Back, Forward, local links, linked examples and practice copies continue to use that reading session's revision. The original files must remain available and match its hashes when read again.

Select a new catalogue result and choose Open selected when you want to switch. If that new resource has changed or cannot be read, the previous reader is kept. A successful open starts a reading session for the new revision; it does not combine old and new histories or re-label earlier practice-copy receipts.

Use the same service in another application

Reusable ownership rules live in Framework. A command-line or non-GTK host can use UmiLearningShelfCopySnapshot, UmiLearningShelfClone and UmiLearningShelfReplace. Replacement consumes a candidate pack only on success. Every refusal leaves the caller responsible for that pack. A clone owns independent metadata and does not perform filesystem reads.

UmiLearningShelfSnapshot observed;
UmiStatus status = UmiLearningShelfCopySnapshot(shelf, &observed);
if (status == UMI_STATUS_OK) {
    /* candidate was admitted against this host's compatibility version. */
    status = UmiLearningShelfReplace(shelf, observed.generation, &candidate);
}
/* On success candidate is NULL; on refusal it remains caller-owned. */

UmiLearningPackCompare provides a copied resource-change list. It matches exact resource identifiers rather than array positions: reordering a manifest does not itself change a resource. Renaming an identifier is reported as a removal and an addition. The comparison performs no file reads. The host serializes all shelf operations. A generation check detects an intervening mutation; it is not a substitute for thread synchronization. Core replacement preserves order and count, advances the counter without wrapping, and performs no allocation or filesystem access at its commit point. Native hosts also need to prepare their presentation before publishing; the GTK adapter does this for its shelf and search results.

GTK hosts prepare with UmiLearningCatalogueGtk4PrepareReplacement, wait until CopyState reports that the operation is no longer busy, and inspect CopyReplacement. Pass that review's serial to AcceptReplacement or DiscardReplacement. Do not invent a serial or reuse one from another window.

Limits and recovery

  • There is no automatic network update, saved pack registry, publisher signing or rich document rendering in this workflow.
  • Loaded packs and pending reviews are in-memory window state. Closing discards them. Accepted filesystem reads finish privately and require orderly callback cleanup.
  • Discarding a review does not undo an already accepted replacement. Reopening a catalogue and explicitly loading a chosen older pack is a separate user decision;
  • A text-preview allocation failure keeps the earlier verified reader. It does not prove that the resource is unsafe or that more memory is always the right fix.
  • Record the operation, exact status and tested source revision when reporting a failure. Keep private course content and local paths out of public issue reports.
