Cancel a CodeGuard scan without losing its report

1. A request is not a stopped worker

A scan can visit many files. A user may change workspaces or cancel while it runs. Framework supplies a thread-safe UmiCancellationToken. Requesting it sets shared state; it does not terminate a thread or close files behind the scanner. CodeGuard observes that state and returns UMI_STATUS_CANCELLED at its next supported boundary.

2. Keep ownership in the shared service

UmiCancellationToken *token = NULL;
UmiCodeGuardService *service = NULL;
UmiStatus status = umi_cancellation_token_create(&token);
if (status == UMI_STATUS_OK)
    status = umi_codeguard_service_create(workspace_root, &service);
if (status == UMI_STATUS_OK)
    status = umi_codeguard_service_scan_cancellable(service, NULL, token);
/* The synchronous scan has returned; these objects are no longer borrowed. */
umi_codeguard_service_destroy(service);
umi_cancellation_token_destroy(token);

In an asynchronous host, the existing job coordinator owns these objects until the worker finishes. It may request cancellation from another thread with umi_cancellation_token_request(token). It must wait for completion before destroying the token, service or callback data. Reset is only for reuse after the previous operation returns. The example above is synchronous and creates no worker.

3. Preserve the complete report

The service scans into a separate owned candidate. A successful scan swaps that complete candidate into its stable result object. Cancellation before work, during traversal, or before publication discards the candidate and preserves the previous report, summary and borrowed finding pointers. Display the cancelled attempt separately from the date and identity of the retained report. Do not label the old report as a new clean scan.

The final token check occurs before publication. A request that races after that check may arrive after a successful result is committed. Treat the returned status as the completed attempt outcome. Cooperative cancellation does not promise that any request always wins a race.

4. Know the observation boundaries

  1. Directory traversal uses UmiDirectoryWalkCancellable, including name collection and empty-folder traversal.
  2. Per-file scanning checks before and after each line read and around architecture analysis.
  3. Workspace scanning checks around duplicate analysis and before returning success.
  4. The retained service checks before candidate allocation and before replacing its previous report.

A filesystem call, rule, architecture pass or duplicate pass already in progress cannot be interrupted by this API. There is no cancellation latency guarantee. Scanning observes files over time; it does not create an atomic snapshot of a changing workspace. Existing scanner line and file handling limits are unchanged.

5. Distinguish direct scanning from retained service scanning

umi_codeguard_scan_cancellable and umi_codeguard_scan_file_cancellable append directly to caller-provided results. Failure or cancellation can leave partial findings there. Use umi_codeguard_service_scan_cancellable when incomplete attempts must not replace complete reports. NULL token preserves ordinary synchronous behavior; existing scan entry points remain available.

An earlier I/O or analysis error is retained if cancellation also arrives. Do not rewrite a specific failure as cancellation merely because the token is set. Invalid arguments are rejected before work. Studio forwards its guard, explicit profile and token to Framework; it does not duplicate scanner rules or own the token.

6. Qualify boundaries without timing guesses

The scanner regression includes production scanning with narrow read, traversal and analysis boundary hooks. They request a real token at deterministic points. Rules, directory traversal, result storage and token atomics remain Framework implementations. The ownership regression separately makes a scan return success after a late request and checks that the service retains its old report. These checks require execution with the actual Framework build before claiming a pass.

cmake --build build --target umicom-codeguard-cancellation-tests umicom-codeguard-ownership-tests
ctest --test-dir build -R "^framework[.]codeguard_(cancellation|ownership)[.]" --output-on-failure --no-tests=error

Use your configured build directory in place of build. Scanner tests register twenty-two boundary cases; ownership tests register thirty cases, including five token-specific checks and bounded-analysis failure retention. Inspect failures; an empty selection is not a pass. Qualify the Studio facade separately in the application build.

7. Try the installed SDK example

The SDK consumer accepts --cancel-before-scan, returning 4 for cancellation. It creates no worker or unsafe signal handler. Build it against the installed SDK and verify its dependencies. Framework configuration alone does not establish SDK or GUI behavior.

Continue with checked analysis failures to distinguish an incomplete scan from a completed report with findings.

Exercises

  1. Explain why destroying a token immediately after requesting cancellation can create a use-after-free. Identify the completion event that makes destruction safe.
  2. Compare low-level append-only findings and retained service findings after two findings are written and a scan cancels.
  3. Create a deterministic test where analysis fails and requests cancellation together. Verify that the original error remains visible.
  4. Reset a token only after its prior scan returns. Verify the result object address remains stable while successful replacement ends old finding borrows.
  5. Explain why putting API setup inside assert makes a release test unreliable. Ensure setup executes when NDEBUG is defined.
