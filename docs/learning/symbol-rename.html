Review a symbol rename

This guide describes the single-draft mode. For the explicit additional-drafts workflow, see Review a complete multi-document rename.

A symbol is a name with a meaning in source code, such as a function or a local variable. A language server can propose changes to that symbol's uses. This differs from replacing every matching word: the server uses its understanding of the language and project to decide which occurrences belong together.

Rename in Studio

  1. Open a writable source document and place the caret on the symbol. The current unsaved text is the source for the request. A selection is not treated as a text-search replacement.
  2. Choose Rename… in the editor toolbar. Opening this form captures the draft and caret; it does not start a server.
  3. Enter an absolute path to an installed language-server executable, its arguments, and the absolute project folder. You can choose Load saved server to reuse preferences for this language. Enter the New symbol name.
  4. Choose Request rename. The selected local program receives the captured draft and project location. It may inspect other files in that project. If it supports rename preparation, Framework first checks that its returned range belongs to the captured position.
  5. Read the proposed document list. The form can apply a complete proposal for this captured document only. If the server includes any other document, the entire proposal stays unapplied. Opening the other file does not bypass this restriction.
  6. Choose Preview complete draft. Compare the original text with the proposed result. The notes list changed ranges and refer to numbered explanations supplied by the server. Read every explanation marked Confirmation required.
  7. Select I approve the displayed rename and all listed confirmation requests, then choose Apply to captured draft. This changes the draft through the document owner. One Undo restores its captured text; saving remains a separate action.

Changing the new name or server settings clears the proposal and approval. If the draft, permissions, caret or selection changes, close the form and capture again. Retrying with an earlier approval does not authorize a new result. Cancel leaves the draft unchanged.

How the shared services fit together

UmiLanguageRenameQueryNative owns a temporary process connection and returns an immutable UmiLanguageWorkspaceEditCatalogue. It sends the complete captured document with a known protocol revision, performs the query, closes the document and shuts down before returning a usable result. It does not apply an edit or write a file.

  1. Capture the source using UmiDocumentSourceRequestCreate on the document owner's thread. Copy the text and metadata before giving them to a worker.
  2. On the worker, create a rename request with the copied source, exact UTF-8 byte caret and new name. The query converts that caret to the UTF-16 coordinates expected by the server. Keep the inputs alive until the query returns.
  3. Retain the returned document versions and annotations. A server may return another document; its content has not been synchronized by this temporary request. Do not assume that a URI or a successful JSON parse proves its edits match an open unsaved draft.
  4. For a host that owns one draft, call UmiLanguageWorkspaceEditCataloguePreviewSingleDocument. It rejects the whole proposal if more than one document is listed or the exact URI differs. Its preview checks source coordinates, document revisions and overlapping edits.
  5. Back on the owning thread, check the original source request. Stage the complete proposed text, show the comparison and all required explanations, then apply only the revision that the user explicitly approved. Destroy the catalogue and preview when they are no longer needed.

Change explanations are literal text. They do not execute HTML, open URLs or run server commands. Range labels start at line and column one; columns use the protocol's UTF-16 units. Most characters use one unit, while a supplementary character such as an emoji uses two. The text comparison shows the actual characters.

Supported boundaries

SituationBehaviour
Rename preparation is unavailableA server that advertises rename without preparation can receive the rename request directly.
Preparation returns no rangeNo rename is sent when preparation returns null. Default-behaviour preparation is not advertised or accepted.
A required document revision differsThe proposal is refused. Framework does not guess which source the server intended.
Several documents or file create/rename/delete operationsStudio does not apply any part of that proposal. The text catalogue refuses resource operations; a complete multi-document transaction is a separate capability.
Server text contains markupThe form displays it literally and requires ordinary review.

The new name must be nonempty UTF-8, at most 1024 bytes, without ASCII control characters. The language server decides whether it is a valid name in that language. Native messages allow 65,536 bytes including escaped source and protocol fields; large drafts can exceed that limit. Studio permits five seconds of total response-reading time and a short additional cleanup allowance. These are temporary explicit requests, not a persistent project index. Other open unsaved drafts are not synchronized.

If a request cannot be used

  1. Check that the server executable and project paths are absolute, and that the program is a language server for this document's language.
  2. Try a valid symbol position and a valid new name. An empty result may mean the server cannot rename that symbol.
  3. If the source changed, cancel and reopen Rename. Do not reuse a comparison for a different draft.
  4. If other documents are listed, cancel this review. Use a tool that reviews and applies the whole project change, or keep the existing symbol name. Applying only the current file would leave the project inconsistent.
  5. For a timeout or transport limit, inspect the server's local setup and project size. The form does not silently fall back to text replacement.
