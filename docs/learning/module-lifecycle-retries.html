Design retryable module lifecycles

A Framework module is a named piece of an application with declared capabilities and lifecycle callbacks. A capability describes a service the module provides or needs. For example, an editor can need a document service, and the document service can need storage. The Master Controller uses those dependencies to start providers before their consumers.

startup:  storage → documents → editor
shutdown: editor → documents → storage

The direction changes during shutdown because an editor may still use documents while it closes. If the editor cannot stop, stopping documents and storage anyway would remove services that the editor still needs.

Define what each callback owns

CallbackResponsibilityFailure contract
configurePrepare the module's configuration.A failed configure must unwind its own partial operation. The controller has not yet established successful configuration for this entry.
initialiseCreate resources for a configured module.Preserve a state that stop can clean after successful configuration. Do not leave an undocumented background owner.
startBegin the module's ordinary work.Return an error for incomplete startup. The controller still calls stop for the successfully configured entry.
quiescePrevent or settle new work before stopping a started module.Keep unfinished work represented and allow a later quiesce retry. Stop and provider shutdown do not proceed past this error.
stopFinish cleanup that can fail.Retain unfinished obligations for retry. Do not report success while required workers or resources remain active.
destroyRelease final state after checked cleanup.This void callback cannot report failure. It must tolerate a registered module that never completed startup and must return normally.

A callback is a function supplied by the module. Framework calls it with a context containing shared services and the module's own state pointer. The descriptor, its strings and module state remain borrowed by the controller until destruction finishes. Keep them alive; a pointer is not a copy.

Separate progress from a visible failure state

A module can be marked UMI_MODULE_FAILED after its stop callback fails even though quiesce already succeeded. The next stop attempt should not repeat successful quiesce. Similarly, a module whose initialise callback failed can still have a completed configure phase that requires cleanup.

Framework retains those obligations independently of the public state enum. It records whether an entry still needs stop, whether a started module needs quiesce, and whether quiesce has completed. A failure report remains visible without erasing that progress.

  1. Stop the last started dependent first.
  2. If quiesce fails, retain that module and all earlier providers.
  3. If quiesce succeeds but stop fails, retain the module and providers while remembering completed quiesce.
  4. On retry, skip modules already stopped and skip completed quiesce.
  5. Continue toward providers only after the dependent's stop succeeds.

This conservative order can also retain an unrelated earlier module until the failed module is handled. It favours preserving required services over trying to optimise partial shutdown. It does not force termination or promise a time limit for application callbacks.

Handle failed startup

Startup returns the original configure, initialise or start error. The controller then attempts reverse cleanup of successfully configured entries. If that cleanup also fails, the original startup error remains the return value and cleanup remains pending. Health and diagnostic records identify the additional rollback problem.

Use UmiMasterControllerNeedsStop to observe whether startup or rollback still requires stop under the controller's serial ownership contract. Do not assume that a failed start means no resources exist. Retry stop or checked release before starting a new lifecycle.

UmiStatus status = umi_master_controller_start(master);
if (status != UMI_STATUS_OK) {
    /* Preserve the startup status in diagnostics. */
    UmiStatus cleanup = UmiMasterControllerRelease(&master);
    if (cleanup != UMI_STATUS_OK) {
        /* master remains owned. Report cleanup too and retain all
         * borrowed descriptors and dependent application data. */
    }
}

The snippet illustrates two independent results: the startup error and its cleanup result. A successful rollback does not turn failed startup into a successful application launch.

Release the owner explicitly

UmiMasterControllerRelease(&master) stops outstanding modules, then invokes destruction callbacks and frees shared authorities and registries. It clears the pointer only on success. With a complete validated dependency order, module destruction follows its reverse order; a never-started or incompletely validated composition retains reverse registration as its fallback.

The existing void destroy function remains available, but retains the owner if checked cleanup fails. New lifecycle code should use checked release and handle its result. A parent must keep its own payload alive when a child owner has not been released.

Controller operations belong to one serial owner. These functions are not concurrent container APIs. Start, stop, release, module/authority registration and dependency validation are refused during a lifecycle callback. Read-only observations do not grant ownership. Never escape a callback using a nonlocal jump or native thread termination.

Study the real regression fixture

tests/test_master_lifecycle.c registers three modules in the opposite order to their dependencies. It verifies ordinary restart cycles, failed quiesce, failed stop, retained legacy destruction, callback reentry and startup rollback. The rollback cases distinguish a failed configure from a failure after configuration and check a second failure during rollback.

With Framework tests configured, build umicom-master-lifecycle-test and run CTest using -R "^framework[.]master[.]lifecycle[.]" --output-on-failure --no-tests=error. Record the compiler, source revision and individual results. These synchronous fixtures do not qualify every application's asynchronous module callback.

Studio propagates this contract through its bootstrap: pending Framework cleanup is handled even when Studio never reached its own started flag. The general ownership pattern is the same as background process lifetimes and file watcher lifetimes.

Before startup, register complete modules and service capabilities safely. Failed admission must leave the original composition intact.
