Learning with Umicom

Umicom Accountant · Umicom Exchange

From a practice trade to a closed accounting period

Follow one small transaction from the buyer’s order to the seller’s balance. Along the way, you will create accounts, read a journal, see why funds are reserved and close a period without leaving unfinished work behind.

You do not need previous accounting or programming experience. Work through the steps in order and keep the application beside this guide. Every name, amount and instrument in the exercise is fictional.

Use practice data only. These operations run in a local simulation. They do not connect to a bank, broker, payment network or custody provider. Actor labels such as maker and checker demonstrate different responsibilities; they are not a sign-in or a security permission. Do not enter passwords, personal records or live financial instructions.

Where to begin

1. Open your practice book

After the source has been built, open Umicom Accountant or Umicom Exchange. The new page is called Operations. The Existing layouts page keeps the previous workspace available. A panel there may still describe a service that has not been connected; the operations in this lesson use the new command form.

The two applications open the same financial practice book by default. Its exact database path appears near the top of the Operations page. This is separate from Umicom Bank’s practice workspace. The book is saved through the Framework Data Server, not in the folder from which you happened to launch the program.

Begin with an empty book: the overview should show zero records. When a book already contains work, keep it. For a separate exercise, the developer section explains how to select a new database file. Never delete a working database merely to make a lesson’s numbers match.

Learn the three identifiers

The Record identifier names the item you are working on, for example buyer.cash. It is different from the Request identifier, which names this particular submission. Leave the generated request identifier alone during an ordinary retry: it prevents the same request from being posted twice.

Choose New request before preparing a different submission with the same operation. Changing the operation in the dropdown also prepares a new request. Review the actor, record and other visible fields, then choose Apply operation. Preparing the form alone does not change the book.

An accepted submission displays its receipt and a revision, the book’s running count of accepted operations. A refused submission leaves that count unchanged. Read the message before trying again.

Use amounts without guessing their units

This exercise uses GBP with decimal scale 2. The entry fields use minor units: 50000 means GBP 500.00, and 6000 means GBP 60.00. Enter whole numbers without commas, currency symbols or decimal points. The account and trial-balance reports show formatted amounts for easier reading.

2. Create three ledger accounts

A ledger account collects one kind of balance. Here, control represents the practice cash held for participants. The two participant accounts record how much of that cash belongs to the buyer and seller. That is why the participant accounts use Liability, rather than Asset, in this example.

Choose Create ledger account. Set the actor to operator, currency to GBP and decimal scale to 2. Create the following accounts one at a time. Choose New request between rows.

Record identifierDisplay nameAccount class
controlPractice cash controlAsset
buyer.cashPractice buyer cashLiability
seller.cashPractice seller cashLiability

Choose Ledger accounts in the report dropdown. All three balances should be zero. Creating an account does not put money into it.

Open the accounting period

Choose Open accounting period. Use record september, actor operator, first date 2026-09-01 and last date 2026-09-30. Apply the operation. The Accounting periods report should show September as Open.

The dates deliberately stay fixed throughout this lesson. The application checks real calendar dates and rejects overlapping periods. An open period is where this exercise’s dated journal entries will be posted.

3. Record GBP 500.00 of practice funding

A journal records the two sides of a movement. In this practice funding entry, the cash-control asset increases by GBP 500.00 and the amount owed to the buyer increases by the same amount. No real deposit occurs.

Choose Enter balanced journal. Use record funding, actor maker, reference identifier september and date 2026-09-25. In Journal lines, enter exactly:

control,50000,0
buyer.cash,0,50000

Each row is account,debit-minor,credit-minor. The total debit is 50000 and the total credit is 50000. Apply the operation, then open the Journals report. The entry is a Draft; account balances have not changed yet.

Next choose Approve journal, keep record funding and change the actor to checker. Apply it. Finally choose Post journal, again using record funding and actor checker, and apply it.

The application requires a different maker and checker label. Posting must use the recorded checker. For this lesson, changing the label lets you practise both responsibilities; it does not prove that two different people reviewed a real transaction.

Return to Ledger accounts. The expected balances are control GBP 500.00, buyer.cash GBP 500.00 and seller.cash GBP 0.00. Repeat the unchanged successful Post request once. You should receive the original receipt, with no second posting.

4. Prepare participants and a practice instrument

A participant is the party placing an order. Choose Register exchange participant and create buyer, display name Practice buyer, linked to ledger account buyer.cash. Then choose New request and create seller, display name Practice seller, linked to seller.cash. Use actor operator for both.

Now choose List instrument. Use record practice, display name Practice instrument, actor operator, currency GBP, scale 2, Minor units per tick 1, Units per lot 1 and Maximum lots per order 100.

A tick is one price step in this model. With one minor unit per tick and one unit per lot, a price of 1000 ticks means GBP 10.00 per lot. A lot is the whole quantity used for an order. The exercise does not use fractional lots.

The new instrument starts Halted. Choose Open or halt instrument, record practice, actor operator, and select Open. Apply it. Opening permits new orders; it does not create a price feed or connect to a market.

Give the seller simulated inventory

Choose Add simulated custody lots. Set record to seller, instrument to practice, quantity to 100 and actor to custodian. Apply it. The Custody lots report should show 100 booked and 100 available lots for the seller.

This is an explicit addition of fictional inventory for the lesson. Custody lots belong to participants in this model; they are not silently booked as assets owned by the exchange.

5. Place an order, then match part of it

Choose Place limit order. A limit specifies the worst price this order will accept. Use record sell.1, participant seller, instrument practice, side Sell, price 1000, quantity 10, date 2026-09-25 and actor trader.

Apply it. In Order book and history, the order should be Resting with ten lots remaining. In Custody lots, the seller still owns 100 lots, but ten are reserved for the order. Only 90 are available for another sale.

Choose New request and enter the opposing order: record buy.1, participant buyer, instrument practice, side Buy, price 1100, quantity 6, the same date and actor. Apply it.

The buyer accepts up to GBP 11.00 per lot. The older seller was already offering at GBP 10.00, so the execution uses the seller’s resting price: six lots at GBP 10.00, a total of GBP 60.00. The buyer’s order is Filled; the seller’s order has four lots remaining.

Open Fills and settlement. A fill is the part of an order that actually matched. In a new book the identifier is system.fill.000001. Read the identifier from your report rather than assuming it when practising in a book that already has trades.

Matched is not settled. At this point the buyer’s booked cash is still GBP 500.00. GBP 60.00 is reserved for the fill, leaving GBP 440.00 available. The seller’s ten reserved lots comprise six for the unsettled fill and four for the remaining order. No cash journal has yet been posted for the fill.

The shared service also rejects an unfunded buy, an oversold quantity, an oversized order and a crossing self-trade. It processes better resting prices before worse ones; at the same price, the older accepted order has priority.

6. Clear the fill and settle both sides

Choose Clear fill locally, record system.fill.000001 and actor clearing. Apply it. The fill report should now say Cleared, awaiting settlement. This records the local settlement obligation; it does not perform central-counterparty novation or send an external instruction.

Choose Settle cash and lots locally. Use the same fill record, accounting period september, date 2026-09-25 and actor settlement. The settlement actor must differ from the clearing actor. Apply it.

The service moves the two sides together: it transfers six custody lots from seller to buyer and posts GBP 60.00 from the buyer’s participant balance to the seller’s. A storage failure rejects the entire candidate change rather than leaving one side settled.

Buyer cashGBP 440.00 booked; no cash reserved for this completed fill
Seller cashGBP 60.00 booked
Buyer custody6 lots booked

FillSettled locally, with its generated journal identifier

In Journals, inspect the generated settlement entry. It debits buyer.cash and credits seller.cash by 6000 minor units. Here a debit reduces the buyer’s liability balance, while a credit increases the seller’s. The control balance remains GBP 500.00.

Finish the remaining order before closing the period. Choose Cancel remaining order, record sell.1, participant seller and actor trader. Apply it. The four remaining lots are released; the earlier six-lot fill stays in the history.

7. Reconcile the balances and close the period

Reconciliation compares the ledger with an observation from outside that ledger. In this lesson the expected figures are supplied below. In a real workflow, a separate statement or controlled source would supply the observation; copying a balance simply because it is displayed would not be an independent check.

Choose Reconcile account balance, use actor reconciler, and submit these three observations. Choose New request between rows.

Record identifierLedger account identifierExternal balance in minor units
reconciliation.1control50000
reconciliation.2buyer.cash44000
reconciliation.3seller.cash6000

The reconciliation report should show a match for each observation. A different observed number is recorded as a difference to investigate; it does not overwrite the ledger. Another posting would make the earlier observation stale and require a new check.

Choose Prepare period close, record september and actor closer. Apply it. The service checks for unfinished journals, remaining orders, unsettled fills and missing, stale or unmatched reconciliations. An earlier period must already be closed.

When those checks pass, the period waits for review. Choose Confirm period close, record september and actor reviewer. Apply it. The different reviewer label completes this simulated maker/checker step. The period should now read Closed.

Select Trial balance. Enter period september, currency GBP, scale 2, then choose Refresh report. The period’s debit and credit movements should each total GBP 560.00: GBP 500.00 of practice funding plus GBP 60.00 of settlement. The closing debit and credit balances each total GBP 500.00. Movements and closing balances answer different questions.

A positive opening or closing amount in this report is a debit balance; a negative amount is a credit balance. Buyer GBP 440.00 and seller GBP 60.00 together account for the GBP 500.00 control asset. “The trial balance agrees” checks these totals; it is not a tax return or a full set of statutory financial statements.

8. Save a report and return to the same work

First select the report you need and refresh it. Copy report copies the displayed text. To save a file, enter a new absolute path in the report path field, such as C:\umicom\practice-september-trial-balance.txt, then choose Save report. The parent folder must exist. The application will not overwrite an existing file.

Close the application, reopen it and inspect the closed period and its journals. The accepted operations are replayed from the local database. Preparing a form or choosing a report does not create a new financial event.

When both applications are open, use Reload shared book in the second window after a change in the first. The service refuses a stale writer rather than silently replacing another window’s changes. Review the reloaded values before trying your operation again.

The Accepted operations report records each accepted request, actor label, record and revision. A failed reload keeps the last known view readable but blocks new writes until a complete reload succeeds. It never presents damaged stored data as an empty new book.

9. Correct a manual journal without erasing history

Keep the completed lesson as it is. For a separate practice correction, use an open period and a posted manual journal. Choose Prepare compensating journal. Give the correction a new Record identifier; put the original journal identifier in Reference identifier; choose the correction’s open accounting period and date.

The result is another draft, with the original debits and credits exchanged. A different actor must approve it, and that checker posts it. Both entries remain visible, and reports include each on its own accounting date. The original does not disappear.

Do not use this operation to reverse a settlement cash journal. That would leave the custody side inconsistent, so this service refuses it. A full trade-unwind workflow is not provided here. Likewise, Reopen unconfirmed review can reopen a prepared close before confirmation; it cannot reopen a finally closed period.

When an operation is refused

Check the record identifier first, then the actor, accounting date, state and units. A request conflict usually means an already-used request identifier now carries different fields: choose New request for a genuinely different submission. An unavailable balance may mean funds or lots are already reserved. A busy or stale-book result calls for Reload shared book and a review of the current values.

For a storage error, keep the displayed database path and exact message. Do not repeatedly submit different request identifiers while the outcome is uncertain. Reopen or reload the book, inspect its accepted requests and retry the original request where appropriate.

How far this practice workspace goes

This is a bounded local book: up to 64 accounts, 16 periods, 32 instruments, 64 participants, 128 orders, fills, journals and reconciliation records in each catalogue, and 512 accepted operations overall. Journal entry supports two to eight lines. Historical records count towards these limits; reaching a limit does not delete them.

It supports exact minor-unit accounting, whole-lot limit/GTC matching, reservations, local clearing and settlement, manual reconciliation and period review. It does not supply live connectivity, authenticated approvals, fees, tax, payroll, consolidation, foreign-exchange conversion, market orders, central-counterparty netting or statutory reporting. A future operational deployment needs those controls and integrations where relevant.

10. Build the applications from source

This section is for readers working with the existing Windows Umicom development checkout. PowerShell is the command window; CMake prepares the build; the compiler creates the programs; CTest runs their automated checks. Run each block in order and stop when it reports a failure.

Merge the full source files

Close running Umicom applications. Extract the batch into a separate staging folder. Compare its Umicom-Applications folder with C:\umicom\Umicom-Applications, then merge Framework, Studio, Accountant and Exchange in that order, followed by the parent CMake helper. Copy the included files, not a replacement of the entire checkout. Preserve destination-only files and review newer local changes before accepting a whole-file replacement.

The folder Delivery-Evidence contains source provenance and validation material. Keep it beside the extracted delivery; do not merge it into the application repositories. Existing source retained inside explained #if 0 blocks is there for engineering review, not for deletion during the merge.

The source baseline is Framework 53182902fa38, Studio 6b832de62aa5, Accountant eb5b4c26354eb, Exchange c8e88d2aa078 and Applications 25c204fc60cd. A different local commit is a reason to compare carefully, not to reset or discard work.

Configure

Set-Location "C:\umicom\Umicom-Applications"
$ErrorActionPreference = "Stop"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --preset windows-ucrt64-all-debug `
    -DBUILD_TESTING=ON `
    -DUMICOM_BUILD_NATIVE_TOOL=ON

if ($LASTEXITCODE -ne 0) { throw "Configuration failed. Stop here." }

Build every configured target

The two-job limit keeps the build modest in resource use. Ninja’s -k 0 continues independent work after an error so the log can show more than the first failure. It does not turn a failed build into a successful one.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build `
    --preset windows-ucrt64-all-debug `
    --parallel 2 `
    -- -k 0

if ($LASTEXITCODE -ne 0) { throw "Build failed. Do not run tests or commit yet." }

Run the full test suite after the build succeeds

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --preset windows-ucrt64-all-debug `
    --parallel 2 `
    --no-tests=error `
    --output-on-failure

if ($LASTEXITCODE -ne 0) { throw "Tests failed. Review the failures before committing." }

For a closer look at the changes in this batch, run the following selection as well. It does not replace the full suite. A skipped display-dependent test is not a graphical pass.

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --preset windows-ucrt64-all-debug `
    -R '^(framework\.finance_operations\.|framework\.developer_operations\.projection_coexistence$|accountant\.operations\.|exchange\.operations\.)' `
    --parallel 2 `

if ($LASTEXITCODE -ne 0) { throw "Focused tests failed." }

Use a separate practice database

Close both applications first. Set the same absolute path in PowerShell before launching each application from that window. Choose a new filename; do not remove the existing book. A variable set in one PowerShell window does not automatically apply to an application launched elsewhere.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$env:UMICOM_FINANCE_OPERATIONS_DB = "C:\umicom\practice\september-lesson.sqlite"

The service creates the parent folder when possible. It reports an error rather than substituting an empty in-memory book when persistent storage cannot open. Close both applications before changing the path for another exercise.

11. Record and share the checked source

The Framework and application modules have separate Git histories. Publish each changed child repository first so the parent can point to commits that actually exist remotely. These commands use the established main branch; they stop when a checkout is detached or on another branch.

Review before staging. git add -A stages all changes in the current repository, including unrelated work. Keep passwords, databases, local build output and unrelated edits out of the commit. A commit is a saved source revision; a push sends that revision to the configured remote repository.

Framework first

Set-Location "C:\umicom\Umicom-Applications\framework"
if ((git branch --show-current) -ne "main") { throw "Stop: this repository is not on main." }

git status --short --branch
git diff --check
if ($LASTEXITCODE -ne 0) { throw "Resolve the reported source formatting errors." }

git add -A
if ($LASTEXITCODE -ne 0) { throw "Staging failed." }
git diff --cached --stat

git commit -m "feat(framework): add accounting and exchange operations with projection compatibility"
if ($LASTEXITCODE -ne 0) { throw "Commit failed. Stop here." }
git push
if ($LASTEXITCODE -ne 0) { throw "Push failed. Stop before updating the parent." }

Applications parent last

The repository-lock command records the child revisions after their commits have been pushed. The parent commit then records the updated pins together with the native-host selection change.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

if ((git branch --show-current) -ne "main") { throw "Stop: the parent is not on main." }

& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .
if ($LASTEXITCODE -ne 0) { throw "Repository lock failed. Do not commit stale pins." }

git diff --submodule=log
git diff --check
if ($LASTEXITCODE -ne 0) { throw "Resolve the reported source formatting errors." }

git add -A
if ($LASTEXITCODE -ne 0) { throw "Parent staging failed." }
git diff --cached --stat

git commit -m "chore(applications): enable and pin accountant exchange operations"
if ($LASTEXITCODE -ne 0) { throw "Parent commit failed." }

git push --recurse-submodules=check origin main
if ($LASTEXITCODE -ne 0) { throw "Parent push failed. Check the child repository pushes." }

git submodule foreach --recursive 'git status --short --branch'
if ($LASTEXITCODE -ne 0) { throw "Submodule status inspection failed." }
