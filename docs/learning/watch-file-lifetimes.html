Watch files without releasing live callbacks

A file watcher notices changes in a folder and calls a function supplied by the application. Studio uses this pattern to update its project file index. Framework owns the polling worker and the watcher data; the application owns the callback's separate sink_user_data payload.

Know when the callback can still run

The polling backend scans the folder in a background thread. The fake backend delivers explicit events synchronously and is useful for deterministic tests. An explicit polling scan can also call the sink before the scan function returns. Even a watcher with no background thread can therefore have a live callback.

A callback must return normally. It must not release its watcher, change the watcher's root, start or stop its lifecycle, or recursively scan the same watcher. Those operations return UMI_STATUS_INVALID_STATE. Framework tracks nested sink calls too: if watcher A calls watcher B's sink, B cannot release A while A's callback is still on the call stack.

Request a stop from a callback

Use UmiWatcherRequestStop to request cancellation. It does not join the worker or free memory. The controller that owns the watcher must later call umi_watcher_stop or UmiWatcherRelease.

/* Inside a sink, while its watcher is still borrowed and alive: */
UmiStatus status = UmiWatcherRequestStop(watcher);
/* Report a failure through the application's existing diagnostic route.
 * Do not free watcher or sink_user_data here. */

This is a fragment illustrating the API boundary, not a complete application. The complete regression example is tests/test_watcher_lifecycle.c. It exercises a real polling worker and nested fake events without replacing the production watcher.

Release from the lifecycle controller

UmiStatus status = UmiWatcherRelease(&owned_watcher);
if (status == UMI_STATUS_OK) {
    /* owned_watcher is now NULL. The callback can no longer use its payload. */
} else {
    /* Keep owned_watcher and the payload alive. Record the status and retry
     * only after investigating the native lifecycle failure. */
}

The controller must exclude other users before release. Serialise start, stop, root changes, explicit scans and release. Do not explicitly scan while the polling worker is scanning. Cancellation-token requests may come from the sink, but the borrowed pointer must not race release or a new start.

umi_watcher_stop blocks until the worker is joined. A failed join or native handle close leaves the owner available. If joining succeeded but handle release failed, a retry closes the remaining handle without joining twice. The running flag remains set until the controller completes stop; it is not a measurement of whether the worker is executing an instruction at that moment.

The older umi_watcher_destroy interface remains available. Because it cannot return an error, it retains the watcher when stopping fails. Use the checked release when the owner needs to observe failure and retain a pointer for retry. Do not destroy the enclosing application services merely because a void child-destruction function returned.

Review the targeted regressions

After configuring your normal Framework build, the watcher ownership target can be built separately. For the Applications build on Windows:

cmake --build "C:/umicom/Umicom-Applications/build/windows-ucrt64-all-debug" --target umicom-watcher-lifecycle-test --parallel 2
ctest --test-dir "C:/umicom/Umicom-Applications/build/windows-ucrt64-all-debug" -R "^framework\.watcher\.lifecycle$" --output-on-failure --no-tests=error

This target links the shared platform library. It checks nested callbacks, refused reentrant destruction, stop requests, a real polling event, restart after join, and pointer clearing. Linux GNU/Clang builds additionally register framework.watcher.lifecycle-fault.join, framework.watcher.lifecycle-fault.release and framework.watcher.lifecycle-fault.legacy. They inject one failure at the native join or handle-release boundary, then require a successful retry.

These checks are authored regression coverage. Their presence is not a claim that your build has executed them. Preserve the actual test results and any platform-specific omissions. A graphical close operation needs its own UI qualification because a blocking stop should not freeze the event thread.
