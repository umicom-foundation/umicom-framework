Recording jobs that survive an application restart

A running process and its saved history describe different things. The process does the work; the history records what the application has observed. If the application stops before saving a final result, the history cannot tell whether the outside operation finished.

Use the shared Data Server

  1. Create a Data Server at a private, absolute SQLite database path. A memory server uses the same API but does not survive closing the application. Keep the database outside source repositories.
  2. Create a UmiJobHistory with a stable scope such as studio.build. The scope separates one feature's records from another feature's records.
  3. Call UmiJobHistoryBegin before scheduling work. Keep the returned identifier and revision. A revision is a counter that changes whenever the record changes.
  4. Save a RUNNING checkpoint before starting the authorised operation. Use the returned revision for the next update. If storage refuses a checkpoint, stop before starting more work.
  5. Save progress after each completed step, then record success, failure or cancellation. Success requires every planned step to have completed.
  6. On a later launch, call UmiJobHistoryCapture to read previous outcomes. Display unfinished entries as uncertain. Do not automatically submit them again.
  7. Join all workers, destroy the history handle, then close the Data Server.

The example examples/data/job_history.c demonstrates ownership and transitions. It records an example operation in memory and does not launch a compiler, trade, payment or provider request.

Attach history to a build session

UmiJobHistory *history = NULL;
/* database remains owned by the host until all session workers are joined. */
UmiStatus status = UmiJobHistoryCreate(database, "studio.build", &history);
if (status == UMI_STATUS_OK)
    status = UmiBuildProjectSessionSetHistory(session, history);

Handle a failure before submitting a build. If attachment succeeds, use the existing project-session submission API. Framework writes a prepared record before queueing, records the start before the first phase, and saves progress between phases. The existing workspace trust decision is still required.

UmiBuildProjectSessionReadHistory copies published metadata without reading the database. Use it for UI polling. If a storage error occurs after a successful phase, that phase's result remains available. The workflow stops before the next phase and the saved record may remain unfinished. Do not label the entire build successful from one phase result.

Understand refusals

ResultWhat to do
BusyA competing transaction or a newer revision prevented the update. Read fresh evidence. A history write may be retried by its owner after review; this is never permission to replay the outside operation.
Capacity exceededEach scope holds 64 jobs. Use UmiJobHistoryPruneFinished when the user chooses to discard finished metadata. It retains unfinished records and never reuses identifiers.
Parse errorRecords are malformed, inconsistent or use an unsupported storage format. Preserve the database for diagnosis. Do not replace unknown data with an empty history.
I/O errorCheck the private directory, free space and database access. Inspect the actual build outcome separately. A failed history write does not undo external work.

Extend without duplicating policy

Media generation, imports and desktop tasks can reuse the store with their own scope and short captions. Their hosts must still implement provider-specific reconciliation and cancellation. The store does not manage worker leases, reconnect a provider, cancel a remote operation, guarantee exactly-once execution, or make payments and trades safe to replay.

Each call owns a short Data Server transaction. Do not call from inside another transaction. Handles may share a server, but destruction requires all users to be stopped. SQLite persistence depends on the filesystem and storage hardware; history is not a power-loss guarantee or a tamper-proof audit log.

Store only non-sensitive metadata. This database is not encrypted by the history API. Credentials, account details, prompts, signed URLs, command lines and raw output belong elsewhere. Captions are bounded byte strings; frontends should validate or repair UTF-8 before displaying them.
