Reviewing repository and submodule changes

A repository can contain another repository as a submodule. The parent records a commit identifier for that child. It does not own the child's uncommitted files. This distinction explains why a parent can show “modified content” while Git reports that nothing is staged for a commit.

Inspect from Studio

  1. Open your project and choose the Source Control surface.
  2. Expand Repository and submodule review. Check the displayed repository path.
  3. Select Inspect repository. The interface remains available while Framework reads local Git status.
  4. Read the summary, then use Next paths and Previous paths to review entries. Each page contains up to 50 paths.
  5. Select Stop to request cancellation. Hiding or closing the panel also requests cancellation. The process may take a short time to finish.
  6. Inspect again after editing, staging, switching branches or committing. Results describe one observation, not a live filesystem monitor.

Understand the result

ObservationMeaning
Staged changeThe parent's index contains a change that can enter its next commit, unless unresolved conflicts prevent that commit.
Child commit changedThe checked-out child revision differs from the revision recorded in the parent's index. Review the revision before staging the parent's submodule path.
Child tracked files changedFiles already tracked inside the child have changed. Review and commit them in the child repository.
Child untracked filesThe child contains files that Git does not yet track. Review them there before deciding whether to add them.
Detached HEADThe checkout names a commit directly rather than a local branch. Decide how you will retain new commits before proceeding.
Upstream comparison unavailableGit did not report an ahead/behind comparison. This is not evidence that the checkout matches a remote server.

The index and worktree codes come from Git: . unchanged, M modified, A added, D deleted, T type changed, R renamed and C copied. Untracked paths use ?; ignored paths use !. Unmerged records identify unresolved conflicts separately.

Keep ownership clear

  1. Review files inside each changed child repository.
  2. Commit and publish the intended child revisions using your normal repository workflow.
  3. Return to the parent and inspect again. Review the child revision change before recording it in the parent.

The review panel never stages, commits, pushes or fetches. It cannot prove that a child commit has been published or that tests passed. Ahead/behind counts compare the locally recorded upstream; a remote may have changed since the last fetch.

Use the shared C interface

#include "umicom/vcs/working_tree.h"

UmiVcsWorkingTreeRequest request = {0};
UmiVcsWorkingTree *tree = NULL;
request.repository_root = absolute_project_path;
request.timeout_ms = 30000U;
UmiStatus status = UmiVcsWorkingTreeRead(&request, &tree);
if (status == UMI_STATUS_OK) {
    UmiVcsWorkingTreeSummary summary;
    status = UmiVcsWorkingTreeDescribe(tree, &summary);
    /* Copy values needed by your application before releasing the observation. */
}
UmiVcsWorkingTreeDestroy(tree);

Call the synchronous reader from a worker. Interactive clients can use UmiVcsWorkingTreeJobCreate, Submit, Read and Take with a Framework task queue. Creation copies the root and executable strings. The task owns cancellation. Wait for a terminal state before destroying it; a cancelled task does not transfer a result.

Results are immutable. Entry pointers remain valid until the containing observation is destroyed. A failed parse or read leaves the caller's output pointer unchanged. Destroy a previous successful result yourself before replacing your application's ownership.

Review from the native command

Run umicom repo review --root "C:\\Work\\My Project" --children to focus on child repositories. Omit --children to see every changed path. Add --timeout-ms 60000 for a slow local repository. The command reads status only; it does not stage, commit, fetch or push.

The native entry point captures Windows Unicode arguments before dispatch, so a path containing non-ASCII characters is passed to Git without the legacy command-line code page losing characters.

Limits and troubleshooting

  • Git must support its detailed porcelain status format. The reader invokes an argument vector with NUL-delimited output and optional index locking disabled.
  • The input limit is 32 MiB. The result limit is 4,096 changed paths; each stored path must fit the shared 2,048-byte path field, including its terminator. Exceeding a limit reports an error instead of silently omitting changes.
  • The default process timeout is 30 seconds. Core callers can set a longer explicit timeout for a large repository.
  • Filenames are stored exactly. Control characters are escaped in review text. Display labels are not paths to pass back to Git.
  • If a refresh fails, the panel preserves the previous observation and labels the failed refresh. Treat those older results as potentially stale.
  • The GTK adapter currently requires nonblocking native joins, supported on Windows and non-Android Linux. Other platforms can use the portable reader or job with their own frontend lifetime handling.
  • Do not stop the GTK main context while background inspection is draining. Closing a panel cancels its process without waiting inside the close handler.

For the underlying record definitions, see the Git status manual.

Identify the source before a build

The shared summary displays Commit (HEAD), the branch, locally recorded upstream, ahead/behind counts and stash count when those observations are available. HEAD is Git's current commit. It does not include uncommitted files, so record the changed paths alongside it.

  1. Run the review from a clearly identified repository path. It performs one local status observation; it does not contact a remote server.
  2. Copy the commit ID and read the index/worktree details. A clean parent can still point at an older child commit.
  3. Run the review again inside each child whose source will enter the build. Record the parent pins separately when the project has submodules.
  4. Keep the source record beside the tool inventory, exact build command and test output. Recheck after any source or branch change.
umicom repo review --root "C:\work\application"
umicom repo review --root "C:\work\application\framework"
umicom repo review --root "C:\work\application" --children

--children filters the detailed changed entries, while the summary still describes the whole observed repository. It is not a recursive inventory of every unchanged or uninitialized submodule. Use the existing git submodule status --recursive fallback when that complete listing is needed; retain git rev-parse HEAD as a direct commit-ID alternative.

Displayed stateInterpretation
Commit IDThe commit recorded by the captured status result. It does not hash current working files.
UnbornThe branch has no commit yet. Do not invent an all-zero source revision.
Not reportedThe supplied observation omitted that field. Unknown upstream/stash data must not be treated as zero or synchronized.
Detached HEADThe commit is known, but a local branch does not own the checkout. Preserve unpublished work before deciding how to proceed.

The C formatter reads identities already stored in UmiVcsWorkingTreeSummary. It does not issue a second Git command that could observe a different HEAD. Its output remains unchanged if the caller's buffer is too small. Names containing control bytes are escaped for display; those labels must never become command arguments.

Exercise: same commit, different source

Two records show the same commit ID. The second review lists a modified C file. Can the first test result qualify the second working tree?

Answer: No. The commit identity excludes that uncommitted edit. Capture the changed source and rerun the affected qualification against it. A source-observation archive can hash the files declared by the release inventory, but it does not cover unlisted files automatically.

If a path begins with a dash, use an explicit relative spelling such as .\-sample. A missing --root value, a second option in its place, or malformed native argument storage is refused before inspection. A timeout or failed read is a failed observation; it is not a clean repository result.

Observe every recursive child revision

Use the native observation command when you need the recursive listing, including unchanged entries. It invokes the existing Framework Git-capture service and validates the complete result before publishing counts.

umicom repo submodules "C:\work\application"
# Direct Git alternative, from that same repository:
git submodule status --recursive
  1. Run the command from a known repository or supply its path. No initialization, fetch, checkout or publication occurs.
  2. Read each commit and its leading marker. A space means initialized at the indexed revision; - means uninitialized; + means a different checked-out revision; U means an unresolved submodule merge conflict.
  3. Use umicom repo review --root PATH inside an initialized child to inspect its working-file changes. A matching revision alone does not prove that its files are unchanged.
  4. Retain the listing alongside the parent's commit record and qualification evidence. It describes local state, not the remote server.

A successful observation exits with zero even when it reports a missing or mismatched child. Read the result before proceeding. Bad arguments exit with two; failed capture, timeout, malformed output or display failure exit with one. The capture limit is 4 MiB and the command timeout is ten seconds. An unavailable Git executable, truncation or unexpected diagnostic line is an incomplete observation, never an empty healthy inventory. Partial or rejected output is displayed without publishing counts.

The tail of each Git line is human-readable evidence, not a machine-readable path. Control and non-ASCII bytes are displayed with escapes. Unusual names may be rejected by the record validator. Do not paste an escaped display label into a command. In the legacy C summary, dirty counts merge-conflicted entries reported by this probe; it does not count all edited child files. The parser's output stays unchanged on refusal; the older probe API retains its zero-on-read-failure contract.

Exercise: mismatched but clean

A child has marker +, and its own working-tree review shows no changed files. Did either command repair the parent pin?

Answer: No. The child is clean at a revision different from the parent's index. Review that revision, its publication state and its qualification before deliberately recording a new parent pin. Observation does not select the correct revision.
