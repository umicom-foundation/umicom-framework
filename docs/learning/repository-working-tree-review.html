Reviewing repository and submodule changes

A repository can contain another repository as a submodule. The parent records a commit identifier for that child. It does not own the child's uncommitted files. This distinction explains why a parent can show “modified content” while Git reports that nothing is staged for a commit.

Inspect from Studio

  1. Open your project and choose the Source Control surface.
  2. Expand Repository and submodule review. Check the displayed repository path.
  3. Select Inspect repository. The interface remains available while Framework reads local Git status.
  4. Read the summary, then use Next paths and Previous paths to review entries. Each page contains up to 50 paths.
  5. Select Stop to request cancellation. Hiding or closing the panel also requests cancellation. The process may take a short time to finish.
  6. Inspect again after editing, staging, switching branches or committing. Results describe one observation, not a live filesystem monitor.

Understand the result

ObservationMeaning
Staged changeThe parent's index contains a change that can enter its next commit, unless unresolved conflicts prevent that commit.
Child commit changedThe checked-out child revision differs from the revision recorded in the parent's index. Review the revision before staging the parent's submodule path.
Child tracked files changedFiles already tracked inside the child have changed. Review and commit them in the child repository.
Child untracked filesThe child contains files that Git does not yet track. Review them there before deciding whether to add them.
Detached HEADThe checkout names a commit directly rather than a local branch. Decide how you will retain new commits before proceeding.
Upstream comparison unavailableGit did not report an ahead/behind comparison. This is not evidence that the checkout matches a remote server.

The index and worktree codes come from Git: . unchanged, M modified, A added, D deleted, T type changed, R renamed and C copied. Untracked paths use ?; ignored paths use !. Unmerged records identify unresolved conflicts separately.

Keep ownership clear

  1. Review files inside each changed child repository.
  2. Commit and publish the intended child revisions using your normal repository workflow.
  3. Return to the parent and inspect again. Review the child revision change before recording it in the parent.

The review panel never stages, commits, pushes or fetches. It cannot prove that a child commit has been published or that tests passed. Ahead/behind counts compare the locally recorded upstream; a remote may have changed since the last fetch.

Use the shared C interface

#include "umicom/vcs/working_tree.h"

UmiVcsWorkingTreeRequest request = {0};
UmiVcsWorkingTree *tree = NULL;
request.repository_root = absolute_project_path;
request.timeout_ms = 30000U;
UmiStatus status = UmiVcsWorkingTreeRead(&request, &tree);
if (status == UMI_STATUS_OK) {
    UmiVcsWorkingTreeSummary summary;
    status = UmiVcsWorkingTreeDescribe(tree, &summary);
    /* Copy values needed by your application before releasing the observation. */
}
UmiVcsWorkingTreeDestroy(tree);

Call the synchronous reader from a worker. Interactive clients can use UmiVcsWorkingTreeJobCreate, Submit, Read and Take with a Framework task queue. Creation copies the root and executable strings. The task owns cancellation. Wait for a terminal state before destroying it; a cancelled task does not transfer a result.

Results are immutable. Entry pointers remain valid until the containing observation is destroyed. A failed parse or read leaves the caller's output pointer unchanged. Destroy a previous successful result yourself before replacing your application's ownership.

Review from the native command

Run umicom repo review --root "C:\\Work\\My Project" --children to focus on child repositories. Omit --children to see every changed path. Add --timeout-ms 60000 for a slow local repository. The command reads status only; it does not stage, commit, fetch or push.

The native entry point captures Windows Unicode arguments before dispatch, so a path containing non-ASCII characters is passed to Git without the legacy command-line code page losing characters.

Limits and troubleshooting

  • Git must support its detailed porcelain status format. The reader invokes an argument vector with NUL-delimited output and optional index locking disabled.
  • The input limit is 32 MiB. The result limit is 4,096 changed paths; each stored path must fit the shared 2,048-byte path field, including its terminator. Exceeding a limit reports an error instead of silently omitting changes.
  • The default process timeout is 30 seconds. Core callers can set a longer explicit timeout for a large repository.
  • Filenames are stored exactly. Control characters are escaped in review text. Display labels are not paths to pass back to Git.
  • If a refresh fails, the panel preserves the previous observation and labels the failed refresh. Treat those older results as potentially stale.
  • The GTK adapter currently requires nonblocking native joins, supported on Windows and non-Android Linux. Other platforms can use the portable reader or job with their own frontend lifetime handling.
  • Do not stop the GTK main context while background inspection is draining. Closing a panel cancels its process without waiting inside the close handler.

For the underlying record definitions, see the Git status manual.
