Recover and review broker orders

The broker connection window can request the currently open orders visible to an API client. Framework retains the returned contract and order summaries, the separate order-status reports and the identities needed to tell orders apart. Trader uses this shared window.

This is an observation workflow. It does not place, change, bind or cancel orders. An open-order snapshot is not an execution history, and an order status is not a commission report. Use the execution review alongside this view when investigating fills.

Before connecting

  1. Log into TWS or IB Gateway. For initial qualification, use your paper environment.
  2. Enable socket API access and check its port. Keep the API read-only setting enabled.
  3. Use a positive API client ID that is not already in use. Client ID zero has special order-binding behaviour and is refused by this connection owner.
  4. In Trader, open Broker Connections and the Paper / Live connection window. Match the program, port and intended environment to TWS or Gateway.
  5. Connect and wait for Read-only API ready. Check the account and environment in the broker application: a port number or a local Paper/Live selection does not prove the broker environment.

Recover open orders

  1. Expand Open orders and broker identity.
  2. Leave Include orders from all visible clients/accounts unchecked to request orders belonging to this API client. Check it to request all open orders visible to the connection. This scope is independent of the account selector used by the account-value panel.
  3. Select Recover open orders. Wait for the provider's end marker. Rows displayed before that marker are a partial capture.
  4. Review each row's client ID, API order ID and permanent ID before comparing its symbol, currency, quantity, limit price and time in force. A permanent ID of zero means it has not been reported.
  5. Read cumulative filled quantity and remaining quantity as the latest broker report. Duplicate status messages are counted, but their quantities are never added again. An unfamiliar status, including Inactive, is displayed as reported; it is not automatically classified as a rejection.
  6. To obtain a new snapshot, disconnect and reconnect, then request recovery again. The protocol end marker does not carry a request ID, so this owner accepts one recovery request per connection. It does not retry a timed-out request behind the user's back.

Understand identities and freshness

ValueMeaning
Client ID and API order IDTogether they identify an API binding. Negative order IDs are retained. The same order number from another client is a separate row.
Permanent IDAn additional broker identity. Unbound manual orders with a zero client/order pair are distinguished by their nonzero permanent IDs. Conflicting identities for an established nonzero binding stop the connection rather than merge different orders.
Next-ID hintFramework retains the latest broker next-valid-ID report and a conservative floor above the nonnegative IDs it has decoded in order observations and accepted execution captures. The floor never moves backwards in the connection. It is not an allocation, reservation or persistent order journal. Ignored execution streams and unimplemented callback types are not covered.
Old summary / old statusThe two channels have separate receipt times. Updating a status does not make an old contract summary fresh. The native panel marks observations older than fifteen seconds as old.
Stale or incomplete snapshotThe capture is unfinished, timed out, disconnected or older than the panel's freshness limit. Later individual statuses do not renew the original snapshot's completion time.

Requesting all open orders is a one-time recovery; it does not establish a subscription to every client's future orders. Later callbacks depend on TWS client and Master Client configuration. Missing callbacks cannot establish that an order was cancelled or filled. The report retains observations rather than removing rows when it sees a terminal-looking status.

Use the shared C interface

Include umicom/broker_connectivity/order_recovery.h and link the existing Umicom::ibkr_connection target. Keep these calls on the thread that owns and pumps the connection.

  1. Call UmiIbkrOrdersRequest after the connection becomes ready. Choose the client-only or all-clients scope explicitly. A full transmit queue leaves the request opportunity available for a later attempt.
  2. Continue pumping the connection. Use UmiIbkrOrdersCopy to inspect completion, failure, count and scope. Supply the same monotonic clock and a positive age limit.
  3. Use UmiIbkrOrderCopy for each row. Check hasOpenOrder, hasStatus and the two stale flags. Status-only rows do not yet identify an account or instrument.
  4. Check each numeric value's exact flag before arithmetic. Raw text remains available when a value is unset or outside the Framework exact-decimal range; it is not replaced with a financial zero.
  5. For diagnostic tooling, UmiIbkrOpenOrderFieldCopy copies one raw field from the retained payload. Index zero is the message ID. Query the required byte count with a null buffer and zero capacity; a short buffer returns UMI_STATUS_CAPACITY_EXCEEDED and leaves the buffer untouched. Field indices and extension layouts depend on the negotiated protocol.

The interpreted open-order structure covers the stable prefix through the permanent ID: contract descriptors, action, quantity, order type, prices, time in force, OCA group, account, open/close, origin and order reference. Advanced conditions, combo legs, algorithms, allocations and OrderState fields are retained as opaque wire evidence. This is not a complete typed Order/OrderState implementation. Raw fields must never be replayed as outgoing order instructions.

Limits and recovery

  • The connection uses the negotiated legacy protocol range 151–176. Protobuf transport and later order fields are not interpreted by this adapter.
  • A connection retains at most 64 order rows. Each open-order payload is bounded to 65,536 bytes and 1,024 fields. Exceeding a bound stops observation with an explicit connection failure; partial rows are not presented as a complete recovery.
  • A capture that times out cannot become complete after a late end marker. Reconnect after investigating the broker's API log and account permissions.
  • No rows after a successful end marker can mean there are no visible open orders. It does not mean there were no trades or completed orders. Client-only recovery may be empty when another client placed the orders.
  • Completed-order history, automatic order binding, order modification and transmission remain separate work. Existing simulation and local policy panels do not gain live-trading permission from this report.
  • Account names and order references are private information. Raw evidence is held in memory until the connection is destroyed; this feature does not write it to disk or send it to another service.
