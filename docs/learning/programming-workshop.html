Start with a small, working programme

This course extends the original 20 Foundation lessons with one complete Git workflow lesson and 32 focused programming labs. The same Framework catalogue supplies Studio and the Education module. The new material is a substantial beginning, not a claim to exhaust every programming concept.

Read lessons 1–20 first when C and terminals are new to you. The extended track then moves from bits and a tiny CPU model to C values, contracts, ownership, containers, architecture and two native Assembly comparisons. The Git guide remains available as an in-course lesson with all 25 repository recipes.

The rhythm: read → predict → type → build → run → inspect → change one thing → test again. A copied answer without an explanation is not completion.

These exercises teach concepts independently of production services. They do not add a second security engine, queue service, controller framework or learning-progress database. Real reusable features continue to belong to the existing Framework owners.

Configure once, then build one lesson at a time

Start from a checkout containing the previous learning batches and this batch. Choose the commands for your system. Run one line at a time and stop at the first error. There are no prompts asking you to type a particular capitalised word and no recursive Git helper script.

Windows: these paths use MSYS2 UCRT64 GCC, CMake and Ninja. Confirm those tools exist first. Linux: use a compiler capable of the repository’s C23 mode, CMake 3.24 or newer and Ninja. CMake selects the language flag supported by that compiler.

Windows · PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" -S ".\framework\examples\learning\programming" -B ".\build\learning-programming" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_MAKE_PROGRAM="C:/msys64/ucrt64/bin/ninja.exe" -DUMICOM_LEARNING_BUILD_ASSEMBLY=ON
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-programming" --parallel 2
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-programming" --no-tests=error --output-on-failure
Linux · terminal
cd "$HOME/umicom/Umicom-Applications"
cmake -S framework/examples/learning/programming -B build/learning-programming -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=gcc -DUMICOM_LEARNING_BUILD_ASSEMBLY=ON
cmake --build build/learning-programming --parallel 2
ctest --test-dir build/learning-programming --no-tests=error --output-on-failure

With native Assembly enabled on x86-64 Windows/ELF or RISC-V LP64 ELF, both comparison labs call real Assembly. On another CPU configure with -DUMICOM_LEARNING_BUILD_ASSEMBLY=OFF; the C-only runs explicitly identify themselves. Do not treat a C-only run as Assembly qualification.

The programme binaries live in build/learning-programming/bin. Each lesson gives its exact target, executable and test filter. The full workshop expects 32 tests.

Write your own version safely

Use a separate checkout or a personal practice directory. For single-file lessons, create main.c in that directory and type the complete code shown. Save the file before compiling. The multi-file lesson also needs score.h and score.c; the Assembly lessons additionally need their supplied shared header and selected native source. Build those through the supplied CMake project rather than guessing a linker command.

Linux single-file practice; Windows uses gcc.exe and .\practice.exe
# In your own single-file practice folder (not the Framework repository):
gcc -std=c23 -Wall -Wextra -Wpedantic -Wconversion -Wshadow main.c -o practice
./practice

With an older Clang that names the draft mode c2x, use the CMake route rather than changing project standards. Record the compiler actually used. Do not use -ffast-math for the finite-input lab.

Practice evidence and assessment

Every C lab has success and boundary checks in its entry point. Many also verify that rejection leaves output unchanged. The code uses explicit conditions rather than checks that disappear with NDEBUG. The Git lesson produces local commits and a second checkout. Preserve the evidence you actually observed.

Record: lesson ID; source version or private file change; compiler and operating system; configure/build/run commands; exit status and output; your explanation; next experiment. The existing Framework score fields describe learning thresholds. A successful build or a PASS line does not automatically award a score, update persisted progress, certify competence or grant execution permission.

Only the corrected example programmes are compiled. Unsafe fragments are visible in lessons for discussion, not included in runnable targets. Run personal experiments in disposable workspaces with no credentials, financial orders or production data.
