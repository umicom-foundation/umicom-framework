Attach completed findings to the right workspace

1. Completion and publication are different operations

A background job can finish while a user changes projects or closes a quality session. The worker should not hold a widget pointer or directly clear the visible report. Framework keeps completed findings private until the creating thread explicitly transfers or adopts them. A retained service is an owner that keeps the last complete report available between attempts.

Begin with the [background job lesson](codeguard-background-jobs.html). This lesson adds workspace admission: the result must belong to the service receiving it. The check happens before the one-shot transfer, so a rejected destination does not consume the completed job.

2. Prepare independent input

UmiCodeGuardJob *job = NULL;
UmiStatus status = umi_codeguard_service_create_job(service, &profile, &job);
if (status == UMI_STATUS_OK)
    status = UmiCodeGuardJobSubmit(job, shared_queue);

This fragment assumes service, profile and shared_queue already belong to your host. Creation copies the service root and selected profile. A NULL Framework profile uses defaults; the Studio facade requires an explicit profile. Creation does not start scanning. Submission failure leaves ownership with the caller. A job does not borrow its service, so closing that service does not invalidate copied worker input. Keep the job alive until it is created-but-unscheduled or terminal before destroying it.

3. Adopt on the creating thread

UmiCodeGuardJobSnapshot snapshot;
UmiStatus status = UmiCodeGuardJobRead(job, &snapshot);
if (status == UMI_STATUS_OK &&
    (snapshot.state == UMI_TASK_SUCCEEDED || snapshot.state == UMI_TASK_FAILED ||
     snapshot.state == UMI_TASK_CANCELLED)) {
    status = umi_codeguard_service_adopt_job(service, job);
    if (status == UMI_STATUS_OK) {
        const UmiCodeGuardResult *report = umi_codeguard_service_result(service);
        /* Render or copy findings while this service remains unchanged. */
    }
}

The snippet illustrates an event-loop polling step, not a complete event-loop implementation. The host still handles errors, refreshes widgets and retires terminal jobs. Serialize service access and adopt on the thread that created the job. The worker never calls the retained service.

Adoption compares the current resolved service root with the immutable job root. A different lexical workspace returns INVALID_STATE before taking findings. The same workspace then follows the job status: BUSY, cancellation and scan failure preserve the previous report. A successful transfer swaps owned finding arrays without allocation. The retained result object keeps its address, but pointers to individual old findings are invalid after success. An empty successful result deliberately replaces the old findings with an empty report.

4. Understand identity and ordering limits

Job creation normalizes an absolute lexical path. UmiCodeGuardJobCopyRoot copies it into a caller buffer without truncation. UmiCodeGuardJobMatchRoot resolves another input with the same policy and returns a checked comparison. A capacity or resolution failure leaves the caller output unchanged.

Lexical equality compares normalized path text under Framework platform rules. It does not prove directory object identity, resolve every link, detect a replaced directory, or create a content snapshot. If a service uses a relative root and the process changes its current directory, adoption may correctly refuse the old job. Prefer an absolute service root for stable host behavior.

Two completed jobs for the same root may represent different moments or profiles. This service does not choose the newest one. The host must track its active request and explicitly choose which job to adopt. A successful job already taken elsewhere returns NOT_FOUND. A second adoption also returns NOT_FOUND and preserves the published report.

5. Keep Studio thin

UmiCodeGuardJob *job = NULL;
UmiStatus status = umi_studio_codeguard_create_job(guard, &profile, &job);
/* Submit and poll using Framework job APIs. */
/* On the owner thread, after completion: */
status = umi_studio_codeguard_adopt_job(guard, job);

These facade operations delegate to Framework. They add no scanner, thread system, root parser or result container. The caller owns the job separately from the Studio facade. This source integration does not itself add a menu action, a progress panel or automatic GUI refresh. Those workflows require their own lifecycle wiring and qualification.

6. Exercise the installed SDK example

Build the [installed-SDK example](../../examples/sdk_codeguard/README.md) against a package containing the new job and service symbols, not headers alone. The existing background executable accepts an optional adoption mode:

& ".\build\umicom-sdk-codeguard-background.exe" "C:\Practice\quality-demo" --adopt
$LASTEXITCODE
& ".\build\umicom-sdk-codeguard-background.exe" "C:\Practice\quality-demo" --adopt --cancel-before-submit
$LASTEXITCODE

A completed report exits 0 when its severity gate passes and 1 when it fails. Setup/usage errors return 2, operational or report failures return 3, and cancellation returns 4. The cancellation example starts no scan. The console drains its own private queue; do not copy that blocking shutdown into a GUI callback.

7. Qualify the ownership boundary

cmake --build build --target umicom-codeguard-job-identity-tests umicom-codeguard-job-adoption-tests
ctest --test-dir build -R "^framework\.codeguard_job_(identity|adoption)\." --output-on-failure
# In an Applications build that includes Studio:
cmake --build build --target umicom-studio-codeguard-jobs-test
ctest --test-dir build -R "^studio\.codeguard_jobs\." --output-on-failure

Run these commands from the relevant configured source/build workspace. Expected success is zero failed cases, with no skipped coverage substituted for a pass. Identity tests cover complete copies, short buffers, normalized paths and relative-context changes. Adoption tests exercise failed and cancelled jobs, an empty replacement, duplicate consumption, wrong threads and a destroyed service. Studio tests retain the explicit-profile policy and prove a job can run after its facade is released.

If linking fails, check that headers and libraries come from the same SDK build. If a workspace mismatch occurs, inspect both absolute roots before changing the application request policy. If a job remains BUSY, keep its input alive and allow the worker to finish; requesting cancellation is not permission to free a running payload. A successful configure step or authored test file is not evidence that these runtime contracts passed.

8. Practice

Start two jobs for one absolute workspace using different profiles. Record a host request number beside each job and permit adoption only for the active request. Cancel the older request and continue polling it until terminal so its payload can be released safely. Then repeat after replacing the host session. Explain which decisions belong to host request selection and which guarantees the Framework service supplies. Do not label a stale result current merely because its root matches.

Framework learning index

Use a shared current-request owner

The Framework review controller adds one outstanding job, a host context token and stale-publication suppression over this explicit adoption API. It preserves the direct job and service APIs for hosts with another lifetime policy.
