Inspect model layout metadata in C

Learn what a model header can establish before any tensor payload is loaded.

A downloaded filename is not sufficient evidence that a model can run. A useful first step is to inspect the declared layout: the element types, dimensions and byte ranges that describe stored tensors. A tensor is an array of numerical values; its shape gives the size of each dimension.

1. Separate the header from the payload

Safetensors starts with an eight-byte little-endian header length, followed by a UTF-8 JSON object and then tensor data. Tensor records declare a data type, shape and offsets relative to the payload. The format requires unique object keys and a complete payload layout without holes. Its optional metadata object holds string values. See the official format description.

Framework's UmiSafetensorsHeaderInspect accepts a memory prefix containing that length and the complete header, plus the independently observed total file size. It uses the existing bounded JSON tree and whole-subtree uniqueness service. It does not introduce another JSON parser.

The prefix and file size in the example below are synthetic. No tensor payload exists. Success means that the supplied metadata describes a consistent layout; it does not mean that actual bytes, a model architecture or an inference engine have been verified.

2. Build a complete native example

This program describes two F32 elements. F32 uses four bytes per element, so the declared span is eight bytes. The inspector returns a summary only after every header check succeeds.

#include "umicom/model_formats/safetensors.h"
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    const char json[]="{\"example\":{\"dtype\":\"F32\",\"shape\":[2],\"data_offsets\":[0,8]}}";
    size_t header=strlen(json),size=8U+header;
    unsigned char *prefix=malloc(size);
    if(prefix==NULL) return 1;
    for(size_t i=0U;i<8U;++i) prefix[i]=(unsigned char)((uint64_t)header>>(8U*i));
    memcpy(prefix+8U,json,header);
    /* Synthetic declared payload length; no model file or tensor bytes exist.
     * A real caller must obtain this size from the same owned file it hashes. */
    UmiSafetensorsHeaderInfo info;
    UmiStatus status=UmiSafetensorsHeaderInspect(prefix,size,(uint64_t)size+8U,NULL,&info);
    free(prefix);
    if(status!=UMI_STATUS_OK) {
        fprintf(stderr,"Header inspection refused: %d\n",(int)status);
        return 1;
    }
    printf("Header describes %zu tensor, %" PRIu64 " elements and %" PRIu64 " payload bytes.\n",
        info.tensors,info.elements,info.data_bytes);
    puts("Metadata only: no tensor data read and no model executed.");
    return fflush(stdout)==0 && !ferror(stdout)?0:1;
}

Expected output after a separately qualified build:

Header describes 1 tensor, 2 elements and 8 payload bytes.
Metadata only: no tensor data read and no model executed.

The input prefix can include payload bytes, but this API ignores them. Its size cannot exceed the supplied file size. Keep the input and output storage separate and alive for the call. On any refusal, the previous output summary remains unchanged.

3. Understand the supported inspection boundary

CheckFramework behavior
EnvelopeRequire the complete length prefix and header, a leading opening brace, and space-only padding after the JSON object.
JSONValidate the complete document, UTF-8 and all decoded member-name uniqueness, including fields later rejected by the schema.
Tensor schemaRequire exactly dtype, shape and data_offsets. Additional fields and unsupported types report NOT_IMPLEMENTED.
DimensionsRequire unsigned integer spelling, check multiplication before overflow, support scalars and zero-element shapes.
LayoutCompare each declared span with its element count and width, sort private ranges, and require complete nonoverlapping coverage.
MetadataRequire string values. An empty archive with no payload is admitted but is not identified as a useful model.

The native profile bounds the header to 16 MiB, declared file size to 1 TiB, tensors to 65,536, rank to 64 and decoded tensor names to 4,096 bytes. The shared JSON reader also limits nodes and depth. A valid file outside these limits can be refused; do not relabel a capacity refusal as proof of a corrupt publisher file.

The supported byte-aligned types are BOOL, U8/I8, U16/I16, U32/I32, U64/I64, F16/BF16/F32/F64, C64 and the listed F8 variants in the public header. Sub-byte types are not implemented. Names and storage widths are checked against the official datatype definitions; the native implementation does not decode their numerical values.

4. Investigate refusals without replacing accepted state

  1. Duplicate names: inspect the publisher metadata, including escaped names. Do not choose a first or last value to make the ambiguity disappear.
  2. Truncated header: obtain the full declared header from the same owned file. Rechecking a different file path can introduce an identity mismatch.
  3. Shape or span mismatch: compare the element count, declared width and offset difference. For example, two F32 elements cannot occupy a four-byte span.
  4. Gap, overlap or trailing data: inspect all ranges together. Individually plausible ranges can still describe an inconsistent archive.
  5. Unsupported format or capacity: select a qualified backend or add a reviewed extension with regression coverage. Do not change limits merely to suppress an error.
  6. Allocation failure or cancellation: retain the previous accepted summary and release the input owner when appropriate. A partial result is not published.

Cancellation is cooperative. The parser and inspector check it between bounded units of work; allocation, sorting and an individual key decode are not interrupted. This is a metadata admission service, not a real-time execution guarantee.

7. Connect inspection to an application workflow

Media and LLM applications can display a metadata summary alongside a pinned component selection. Studio can explain why a proposed model asset was refused. Before accepting actual model bytes, a separate file owner must establish size and digest identity from the same file, keep that identity stable during inspection, and record the result. Backend compatibility and readiness still need their own evidence. None of those application integrations is supplied merely by calling this header API.

8. Bind the summary to actual file bytes

The memory-prefix API cannot establish which file its caller inspected. Use UmiSafetensorsFileInspect when an application needs an observed SHA-256, actual byte count and header summary from one checked file read. This service reuses Framework's regular-file stream reader and incremental SHA-256 implementation.

  1. Choose an ordinary absolute UTF-8 path under trusted parent directories. The shared reader refuses a final symbolic link or reparse point and requires a regular file.
  2. Run inspection on a worker when used from an interactive application; file I/O can block.
  3. The service retains only the bounded header prefix while hashing every streamed byte. It waits for the reader's before/after metadata and cleanup checks before proceeding.
  4. When you have a reviewed expected identity, supply its exact byte count and 32-byte binary SHA-256. The size also bounds reading. A matching digest establishes byte identity, not publisher trust.
  5. Publish the returned identity and layout together only on success. All prior output bytes remain unchanged on a refusal, including a late close failure or cancellation.

The expected identity may borrow inspection.file from a previous result. The service snapshots that identity before starting. This permits reinspection without clearing the digest being compared. An oversized input is refused by the reader's capacity bound; a shorter input or changed digest is refused as an identity mismatch.

UmiSafetensorsFileInspection inspection;
UmiStatus status = UmiSafetensorsFileInspect(path, NULL, cancel, &inspection);
if (status == UMI_STATUS_OK) {
    /* Recheck the same expected bytes; a refusal retains the earlier result. */
    status = UmiSafetensorsFileInspect(path, &inspection.file, cancel, &inspection);
}

The installed example directory also contains umicom-model-inspect. After building it through the SDK instructions above, select a real local file explicitly:

& C:/Projects/model-header-build/umicom-model-inspect.exe C:/Models/publisher/model.safetensors

The example prints the observed byte count, SHA-256 and tensor summary. There is no expected digest in this command, so it records identity without confirming a publisher's assertion. It never executes the model. No example digest or output is supplied here as if a real model had been inspected.

The checked reader is not an immutable snapshot or a filesystem sandbox. It compares metadata before and after the read, but a file path can refer to different bytes later. Keep trusted parent ownership and revalidate identity when a later operation needs the file. Numerical tensor values and backend compatibility remain outside these inspections.

Qualify the file and capture contracts separately:

cmake --build --preset windows-ucrt64-debug --target umicom-safetensors-file-test umicom-safetensors-file-ownership-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework\.model_formats\.safetensors_file(_ownership)?\." --output-on-failure

The native file cases create exclusive synthetic fixtures in the test working directory and retain them as evidence. The Windows link case reports a skip if the required link-creation capability is unavailable; record that separately from passes. Capture tests inject split chunks and late I/O statuses into the real inspection body. Those injections verify propagation and ownership, while the shared reader's own suite qualifies actual handle and cleanup behavior.

9. Reuse the service from both model consoles

The shared native model command now delegates Safetensors inspection to the checked file service. Neither console contains its own JSON parser or file hashing loop. Run umicom models --help to see whether this optional component was compiled, then inspect an existing file:

umicom models inspect-safetensors 'C:\Models\Umicom\weights.safetensors'
umicom-models inspect-safetensors 'C:\Models\Umicom\weights.safetensors'

The report contains observed identity and layout. The command does not take an expected digest or an apply flag. Use the SDK expected-identity parameter when your application must compare a reviewed size and digest atomically with inspection. A successful report is still not evidence of model compatibility or inference.

The console regression suite covers argument refusal, occupied session ownership, unavailable components, original GGUF compatibility, status propagation and failed report delivery. Separate integration cases create tiny synthetic files, including a Unicode name, and call the linked command. They require no real model weights or network access. After building these targets in your own qualification environment, run the registered cases:

ctest --test-dir build/windows-ucrt64-debug -R '^framework\.local_models\.cli_tensor(_file)?\.' --output-on-failure

These commands assume the ordinary Framework debug build directory and the default enabled model-format component. A deliberately disabled build registers the unavailable-command case only. Source and configuration checks do not replace compiling and executing these cases.

10. Separate stored bytes from inference memory

A file's byte count describes storage. An inference backend may expand those weights, retain a key/value cache for the conversation, allocate temporary work buffers and keep its own runtime state. A small file is therefore not proof that a model fits in RAM. Framework's UmiModelMemoryAssess keeps these four cost categories separate and compares their declared total, plus a host reserve, with an existing UmiDesktopSystemSnapshot.

  1. Obtain resident-weight, cache, workspace and runtime costs for the selected backend and configuration. Use its qualified estimator or measured upper bounds. Do not substitute file size without evidence that it represents resident weights.
  2. Mark a component as known only when its value is established. An unknown component has a zero value and an absent mask bit. Known cache, workspace or runtime costs may be zero; known weights must be positive. An incomplete estimate produces UMI_MODEL_MEMORY_INCOMPLETE, even if the known costs appear small.
  3. Use Framework's existing desktop capture service and check its memoryStatus. Other capture sections can fail independently. Record elapsed age using one monotonic host clock; do not subtract timestamps from unrelated clock origins.
  4. Supply a nonzero maximum observation age and a deliberate host reserve. A fixture, unavailable memory or an old observation cannot establish current host capacity.
  5. Inspect the assessment verdict after an OK status. The status means the calculation was admitted. WITHIN_DECLARED_BUDGET means only that the supplied numbers fit the observed available RAM; it is not a reservation or a launch guarantee.

For backends that actually retain dense key/value arrays, UmiModelDenseKvCacheBytes checks every multiplication and addition. Its geometry is explicit: token capacity × simultaneous sequences × layers × heads × dimensions × bytes per element, separately for keys and values. It does not infer architecture from a filename. Compressed, paged, sliding-window, recurrent and hybrid caches need their own backend-specific accounting.

The following function is an illustrative calculation, not a real model profile. It receives an already captured snapshot and age; it performs no capture or launch. The chosen dense cache requires 268,435,456 bytes for keys and the same for values, totaling 512 MiB. One MiB is 1,048,576 bytes.

#include "umicom/local_models/memory_plan.h"

static UmiStatus review_example_budget(const UmiDesktopSystemSnapshot *snapshot,
    uint64_t age_millis, UmiModelMemoryAssessment *assessment)
{
    const UmiModelDenseKvShape shape = {
        .token_capacity = 2048U, .sequence_capacity = 2U, .layers = 32U,
        .key_heads = 8U, .value_heads = 8U,
        .key_dimensions = 128U, .value_dimensions = 128U,
        .key_element_bytes = 2U, .value_element_bytes = 2U
    };
    UmiModelKvFootprint cache;
    UmiStatus status = UmiModelDenseKvCacheBytes(&shape, &cache);
    if (status != UMI_STATUS_OK) return status;
    const UmiModelMemoryRequirements costs = {
        /* Illustrative supplied costs; replace with evidence for your backend. */
        .weights_bytes = UINT64_C(8) * 1024U * 1024U * 1024U,
        .cache_bytes = cache.total_bytes,
        .workspace_bytes = UINT64_C(1) * 1024U * 1024U * 1024U,
        .runtime_bytes = UINT64_C(256) * 1024U * 1024U,
        .known_components = UMI_MODEL_MEMORY_ALL
    };
    return UmiModelMemoryAssess(&costs, snapshot, age_millis, 1000U,
        UINT64_C(1) * 1024U * 1024U * 1024U, assessment);
}

Link this pure calculation through Umicom::local_models. A host that also performs a capture must link the existing Umicom::desktop_system component. This planner does not add another platform memory probe. Shared GPU memory is part of system RAM, so do not add it a second time. Dedicated GPU admission, concurrent model reservations and actual peak-memory measurements remain separate responsibilities.
