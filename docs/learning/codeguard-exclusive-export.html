Save a report without replacing evidence

A native preview is intentionally bounded. A useful report can be larger than that preview, so export should use the complete findings and an explicit output policy. This lesson extends report serialization with a new-file operation. The API, CLI option and regression fixtures are authored; runtime and installed-SDK qualification remain necessary.

1. Choose a file contract deliberately

The existing umi_codeguard_report_file replaces the contents of an existing destination. That compatibility behavior remains available. The new umi_codeguard_report_file_new requires an absolute destination which does not already exist. It never deletes a previous file or creates parent directories.

Checking whether a name exists and then opening it for ordinary writing is insufficient: another writer can create the file between those operations. Framework delegates to UmiOutputFileCreate, which reserves the leaf exclusively using the native operating-system API. If two writers choose the same name, only one can create it; the other receives ALREADY_EXISTS.

Exclusive creation differs from atomic replacement. Once the new file exists, another reader can observe a partial report while writing continues. A write, flush or close failure leaves that newly created file for diagnosis. Parent directories must be trusted and stable; this is not an adversarial filesystem sandbox.

2. Validate and measure before creating anything

UmiStatus status = umi_codeguard_report_file_new(
    absolute_path, UMI_CODEGUARD_REPORT_SARIF, stable_result,
    64U * 1024U * 1024U);
if (status != UMI_STATUS_OK) {
    /* Explain the failure. Do not delete an existing or partial destination. */
}

The writer first validates path syntax and every finding. It then runs the same serializer into a counting sink. A sink is a destination for emitted bytes; this first destination counts instead of writing. The byte budget applies to the serialized payload, including JSON escapes, punctuation and final newline. An oversized or malformed report is refused before file creation.

The result must remain alive and unchanged throughout both passes. This API does not copy the findings or lock an application service. A synchronous console can keep its service alive for the call. A responsive GUI needs an independently owned stable report and a worker for storage I/O; passing a service borrow to another thread is not sufficient.

3. Stream with bounded working memory

After exclusive creation, the writer serializes again through an 8 KiB staging buffer. Small punctuation and field tokens accumulate before reaching the native writer. This avoids one operating-system write for every token without allocating a second complete report. The existing findings still occupy memory; the staging bound is not a bound on the scanner's entire memory use.

All output formats use the same serialization code as the existing stream and memory functions. Text, JSON and SARIF exports therefore share validation, escaping and path rules. A final incomplete buffer is written, the file is flushed and closed, and the first failure remains the result. A later cleanup error must not hide the cause of an earlier write failure.

4. Use the native Umicom CLI

From a qualified build with the new service and CLI handler, choose an existing parent directory and a fresh absolute filename:

umicom quality scan "C:\Practice\quality-demo" --format sarif --output-new "C:\Practice\reports\quality-new.sarif"
$LASTEXITCODE
umicom security scan "C:\Practice\quality-demo" --format json --output-new "C:\Practice\reports\security-new.json"
$LASTEXITCODE

The same option is available to architecture and memory scan commands. These routes use their established profiles and filtering. The CLI limits a new report to 64 MiB. The C API lets a host choose its own explicit payload budget.

  1. Verify that the parent folder exists and that the intended filename is new.
  2. Run one command and inspect its exit status.
  3. Read the report and review the findings; successful export does not prove the source is safe.
  4. Use another filename for another run. Do not interpret ALREADY_EXISTS as permission to replace earlier evidence.

--output-new cannot be combined with --output or --summary, and cannot appear twice. Relative destinations and missing values are usage errors. The legacy --output retains overwrite behavior, including its existing interaction with summary mode.

The existing CLI exit convention remains: 0 for a completed passing gate, 1 for a failing gate or operational/output failure, and 2 for invalid usage. Because 1 covers more than one outcome, read the diagnostic and report status. The independent SDK export example uses 3 for operational/output failures and distinguishes them from a completed failing gate.

5. Do not lose failures at standard output

Saving a report and printing its completion message are separate outputs. A redirected standard-output stream can fail even after a file was saved. The native scan handler now checks and flushes its summary and saved-file acknowledgement, as it already does for the full report stream. An output failure therefore cannot become a successful command merely because the severity gate passed.

If the acknowledgement fails, a complete report may already exist. Inspect that destination before retrying; a fresh exclusive export should refuse the existing name. Diagnostics written to standard error are best-effort explanations, while the nonzero exit code carries the failure to the calling shell.

6. Qualify boundary and failure behavior

The export fixture compares native file bytes with the shared serializer and covers each format, exact and insufficient budgets, malformed records, Unicode filenames, existing files, directories, missing parents and concurrent creation. Random leaf names retain each run's artifacts for inspection instead of removing earlier evidence.

Six linker-wrapped cases inject create, write and close failures, retain a seven-byte partial write, check first-error precedence and count bounded write chunks. The CLI fixture calls the real scan handlers and uses an operating-system read-only descriptor to exercise standard-output failure.

cmake --build build/windows-ucrt64-debug --target umicom-codeguard-export-tests umicom-codeguard-export-cli-tests
ctest --test-dir build/windows-ucrt64-debug -R "^framework\.codeguard_export(_cli)?\." --output-on-failure

# GNU-compatible linker wrapping:
cmake --build build/windows-ucrt64-debug --target umicom-codeguard-export-fault-tests
ctest --test-dir build/windows-ucrt64-debug -R "^framework\.codeguard_export_fault\." --output-on-failure

There are 29 ordinary export cases, six controlled native-output cases and 20 CLI cases. These commands must use a matching configured Framework build. A successful configuration only registers them; it does not prove compilation or test success. Keep existing report-grammar regression results and qualify the installed SDK example separately.

Filesystem capacity, permissions, network-mounted storage and power loss can still affect real writes. No physical-device, GUI-export or crash-durability qualification is implied by these source-level contracts.
