Compare SDK contents with native C fingerprints

An SDK is a set of headers, compiled libraries, tools and package metadata that lets an application use Framework without cloning its source. A useful installation check begins by asking whether the expected files exist. A distribution check also needs to ask whether the declared files contain the same bytes as a reviewed baseline. These questions are related, but they are not interchangeable. This lesson builds that second check from the shared C APIs used by the native Umicom CLI.

1. Separate presence, content and compatibility

The existing sdk inspect command reads installation metadata and observes the base package layout. The sdk artifacts command reads sdk-artifacts.txt and checks the paths declared by the generated artifact receipt. Neither command loads a DLL, compiles a program or proves that a library implements the ABI expected by your application. The fingerprint command adds a reproducible content identity for the exact receipt and every physical artifact it declares.

An ABI, or application binary interface, is the agreement between compiled pieces: calling conventions, data layouts and other binary rules. Matching file hashes means matching bytes within this observation. It does not establish that those bytes suit your compiler, processor, runtime or application. Continue with an independent installed-SDK consumer after recording the fingerprint.

2. Observe a quiet installation

  1. Finish installing the SDK into a dedicated prefix such as C:/SDKs/Umicom. Stop writers that could replace its receipt or libraries while you observe them. Keep the directory under your control.
  2. Use a qualified Umicom CLI build that includes the fingerprint command. Check sdk --help first. An older executable will not acquire the new command merely because the source folder was updated.
  3. Run the commands below. Record the full fingerprint and the installation/build identity alongside your distribution records. The command reads files but does not stage, install or launch any artifact.
  4. Copy the whole SDK through your normal distribution process. Run fingerprint against its new prefix with --expect and the full recorded digest. Prefix relocation alone does not change the fingerprint.
& "C:\Tools\Umicom\umicom.exe" sdk --help
& "C:\Tools\Umicom\umicom.exe" sdk inspect "C:\SDKs\Umicom"
& "C:\Tools\Umicom\umicom.exe" sdk artifacts "C:\SDKs\Umicom" --all
& "C:\Tools\Umicom\umicom.exe" sdk fingerprint "C:\SDKs\Umicom"
& "C:\Tools\Umicom\umicom.exe" sdk fingerprint "D:\SDKs\Umicom" --expect "<64 hexadecimal characters from your reviewed baseline>"

Replace the executable and prefix paths with your actual installation paths; the angle-bracket digest above is explanatory and will be rejected. Run each command separately and stop on an error. Exit code 0 means a complete observation, and a match when an expected digest was supplied. Exit code 1 means the complete fingerprint differs from the expected value. Exit code 2 means invalid arguments, a failed or incomplete observation, or a report-output error. A failed read does not print a complete fingerprint.

3. Understand the coverage boundary

The generated version-1 artifact receipt identifies archives, shared libraries, import libraries, tools and interface targets. Interface targets contribute through the receipt bytes but do not name a physical file. A receipt containing only interfaces is refused because it cannot establish the physical SDK observation this command promises. Windows DLL and import-library records are both read. Two different records naming one physical path count twice in the total byte budget.

Headers, package scripts, documentation and other files absent from the receipt are outside the fingerprint. Adding or editing an unlisted file does not change it. This is deliberately not an archive digest or a complete installation-directory digest. Keep the SDK ZIP checksum, installed header checks, package-origin checks and consumer tests as separate evidence. A malicious party able to replace both files and your expected digest can make an unkeyed hash comparison pass; obtain the expected digest through a trusted channel.

4. Call the Framework service from C

#include <inttypes.h>
#include <stdio.h>
#include "umicom/sdk/artifact_fingerprint.h"

static int inspect_sdk(const char *absolute_prefix)
{
    UmiSdkFingerprint result;
    UmiSdkFingerprintLimits limits = {
        UINT64_C(512) * 1024U * 1024U,
        UINT64_C(4) * 1024U * 1024U * 1024U
    };
    UmiStatus status = UmiSdkArtifactFingerprint(
        absolute_prefix, &limits, NULL, &result);
    if (status != UMI_STATUS_OK) {
        fprintf(stderr, "SDK observation failed: %s\n", umi_status_text(status));
        return 1;
    }
    printf("%zu files, %" PRIu64 " bytes\n%s\n",
        result.files, result.bytes, result.sha256);
    return 0;
}

Link the consumer to Umicom::sdk through the installed UmicomFramework CMake package. The service requires an absolute UTF-8 prefix and never consults a later working directory. The CLI accepts a relative prefix for convenience and resolves it once before calling the service. Do not pass overlapping input and output storage. The result owns its scalar values and fixed-size strings; there is no borrowed inventory pointer for the application to retain.

A graphical application should run this blocking observation on a worker and publish the returned value only if its window/request is still current. Pass a live UmiCancellationToken when cancellation is needed. Keep that token alive until the call ends. Cancellation is checked before observation, between records and during streamed chunks; it does not forcibly interrupt an operating-system read already in progress.

5. Bound memory and work separately

UmiInputFileRead owns the small receipt buffer, capped at one MiB. UmiSdkArtifactInventoryParse checks its existing grammar, declared count and safe relative paths, with at most 4,096 records. UmiInputFileVisit reads each artifact in 64 KiB chunks through the same checked file handle. A multi-gigabyte archive therefore does not require a multi-gigabyte allocation. The inventory and two bounded receipt buffers remain additional memory costs.

Passing NULL for limits selects an eight-GiB per-file ceiling and a 64-GiB total ceiling. An application can lower either ceiling; values above the hard limits are invalid arguments. An explicit zero is a real zero budget, not a request for defaults. It admits empty files only. Before each artifact, the service uses the smaller of the per-file ceiling and the remaining total budget. These byte limits bound data processed, not elapsed time on slow storage.

6. Make the fingerprint reproducible

A digest needs an unambiguous preimage: the precise byte sequence it hashes. Version 1 starts with the ASCII bytes umicom.sdk.fingerprint/1 followed by LF, without a terminating NUL. It then appends the receipt byte length as an unsigned 64-bit little-endian integer, the 32 raw SHA-256 receipt bytes, and the physical-record count encoded the same way. For each physical record in receipt order, it appends the file length in that encoding and the 32 raw file-digest bytes. SHA-256 of this complete sequence is the displayed lowercase hexadecimal fingerprint.

The receipt is hashed exactly as stored. Reordering records, changing a declared relative path or configuration, or converting LF to CRLF changes the fingerprint even when file contents are otherwise equal. Absolute installation paths and timestamps are excluded. This distinction makes relocation possible while binding the declaration that tells the service which files to read. Do not normalize receipt text when comparing an already recorded fingerprint.

7. Refuse incomplete evidence

The service assembles a candidate result privately. Missing files, directories in place of files, final symlinks/reparse points, malformed receipts, budget exhaustion, cancellation and read failures prevent publication. On failure every output field is cleared, so a caller cannot accidentally reuse a previous successful fingerprint. Parents may still contain aliases: the selected directories must be trusted and stable. This API is not a filesystem confinement mechanism.

The shared reader checks observable metadata around each individual read. After all artifacts, the service rereads the receipt and compares its exact bytes with the original. An observed receipt change returns BUSY. These checks cannot create an atomic snapshot across several files. A library could change after it was read, and metadata checks cannot detect every adversarial writer. Establish baselines from a quiescent installation or a separately managed immutable snapshot.

8. Diagnose a mismatch and qualify the implementation

  1. If the receipt is missing or malformed, inspect the installation log and reinstall into a separate prefix. Do not invent a receipt by copying one from a different build.
  2. If the fingerprint differs, compare receipt hashes first. A changed receipt can reflect configuration, order, paths or line endings. Equal receipt hashes with unequal fingerprints point to changed declared content or lengths.
  3. Check the SDK origin and installed headers, then build and test an independent consumer against the intended prefix. A matching fingerprint does not replace those checks.
  4. For Framework contributors, build the new native test target and CLI, then run framework.sdk.fingerprint tests. Keep platform link-fixture skips visible. Configuration and test registration alone are not execution evidence.
cmake --build "<Framework build directory>" --target umicom-sdk-fingerprint-tests umicom
ctest --test-dir "<Framework build directory>" -R "^framework\.sdk\.fingerprint\." --output-on-failure

The service tests include a fixed digest calculated independently from the documented binary preimage, a multi-chunk binary fixture, relocation, same-size edits, record and line-ending changes, repeated paths, shared/import pairs, missing or linked leaves, exact and exhausted budgets, cancellation and output reset after failure. CLI fixtures check expected-digest matches and mismatches, Unicode/relative prefixes, help and invalid arguments. These are qualification instructions and authored regression coverage, not a claim that a particular Framework binary has passed them.

Continue with installed SDK inspection and an independent C23 consumer. Read the public fingerprint contract before integrating it into a worker.

9. Bind a model application to the selected SDK

Artifact hashes answer which listed bytes you observed. CMake package selection answers which installation an application is about to use. A model application needs both questions answered. Framework's independent model example now ships in share/umicom/examples/local_models/sdk_consumer in the ordinary and selective SDK components.

  1. Finish building and installing the SDK into its own prefix. Keep the compiler and architecture consistent with that producer.
  2. Configure the installed example with an absolute UMICOM_SDK_ROOT and a fresh consumer build directory. See the model manager guide for complete commands. External dependency prefixes remain available through CMAKE_PREFIX_PATH.
  3. Read the selected-prefix diagnostic. The consumer invokes Framework's existing installed-layout, full public-header and environment guards. Required ABI 2 belongs to the consumer; copying the producer's ABI into the expected value would make the check meaningless.
  4. Build, link and run the independent consumer. It resolves model planning, ownership, health and catalogue APIs using offline operations. It neither downloads weights nor proves real inference.

As an exercise, configure successfully against SDK A, then change only UMICOM_SDK_ROOT to SDK B in the same build directory. A cached UmicomFramework_DIR can still select A. The example must refuse that mismatch. Preserve the earlier directory and configure B in a new one. Do not silence the check by adding source headers. With no explicit root, ordinary discovery remains supported and is labelled as discovery; the returned installation still undergoes the same consistency checks.

Seventeen framework.local_models.sdk_selection fixtures cover this selection boundary. They configure the real example against small synthetic packages and placeholder archives, with no consumer compilation, launch or real branding staging. Negative cases repeat to expose cache residue. These tests complement the independent installed-library exercise; they cannot replace it.

Reference: CMake find_package describes cached package locations and explicit search options. An explicit search option alone does not establish the origin of an already cached result.
