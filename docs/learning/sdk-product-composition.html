Build Media and OS with the Umicom Framework SDK

This course shows how a product consumes an installed Framework SDK instead of compiling another Framework checkout. An SDK contains public headers, compiled libraries, package metadata, shared build helpers, examples and branding resources. A DLL alone does not describe its headers, ABI or dependent libraries.

Lesson 1: choose one dependency owner

Use source mode while developing Framework itself. Use installed mode when building a separate product against a qualified package. Keep separate build directories: a CMake cache remembers compiler and package paths. Do not repair a mismatch by adding another Framework include directory.

ProductSource modeInstalled mode
MediaThe Applications parent supplies Framework targets.Configure the Media module directly with UMICOM_SDK_ROOT.
OS user spaceThe default uses its reviewed Framework checkout.Set UMICOM_OS_USE_INSTALLED_FRAMEWORK=ON and an absolute SDK prefix.
Kernel and boot imageSeparate projects and qualification.This switch does not package a kernel or bootable image.

Lesson 2: understand the composition helpers

The package supplies umicom_extend_thin_application_runtime for product-owned runtime, readiness and command files; umicom_add_application_productisation_contribution for the product contribution; and umicom_attach_creative_workspace for linking the existing creative component and its example. Installed helpers define consumer targets without rebuilding Framework implementation files.

The creative example is SDK teaching source under share/umicom/framework/examples/creative_workspace. Its path is exported by the package. An imported component must use that installed example even when a source checkout happens to be nearby. Missing package content produces an error instead of an accidental fallback. Source composition retains its original example.

Lesson 3: build Media independently

Obtain a matching installed SDK containing Framework, application, creative_workspace, public headers and external dependencies. A package built before the composition helpers were added must be rebuilt and reinstalled. The following assumes a Media module checkout at C:\Projects\UmicomMedia and a UCRT64 SDK at C:\SDKs\Umicom. Stop at the first failed command.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S C:/Projects/UmicomMedia -B C:/Projects/UmicomMedia/build/sdk-debug -G Ninja -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build C:/Projects/UmicomMedia/build/sdk-debug
ctest --test-dir C:/Projects/UmicomMedia/build/sdk-debug --output-on-failure
cmake --install C:/Projects/UmicomMedia/build/sdk-debug --prefix C:/Apps/UmicomMedia

Make the installed SDK runtime DLLs and matching external dependencies available through your deployment process before launching the console:

& "C:\Apps\UmicomMedia\bin\umicom-media-studio-console.exe"

Configuration checks the selected SDK origin and declared environment. It does not prove linking or execution. SVG and ICO resources are resolved by the shared branding helper. The creative example's CTest exercise runs only when you actually execute tests.

Lesson 4: build OS user space from the same SDK

This builds the host-side console, not a distributable operating-system image. Installed mode can use an OS checkout without its Framework submodule. Match the SDK compiler and dependencies.

cmake -S C:/Projects/UmicomOS -B C:/Projects/UmicomOS/build/sdk-debug -G Ninja -DUMICOM_OS_USE_INSTALLED_FRAMEWORK=ON -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DUMICOM_OS_GUI=OFF -DUMICOM_OS_BUILD_TESTS=ON -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_BUILD_TYPE=Debug
cmake --build C:/Projects/UmicomOS/build/sdk-debug
ctest --test-dir C:/Projects/UmicomOS/build/sdk-debug --output-on-failure
cmake --install C:/Projects/UmicomOS/build/sdk-debug --prefix C:/Apps/UmicomOS --component UmicomOS
& "C:\Apps\UmicomOS\bin\umicom-os.exe"

For the desktop shell, use a separate directory with UMICOM_OS_GUI=ON and an SDK exporting ui_gtk4, desktop_workspace_gtk4 and desktop_system_gtk4. The consumer links prebuilt components instead of including producer CMake files. Qualify GTK runtime dependencies, window lifetime and actual appearance separately.

Lesson 5: diagnose the dependency boundary

SymptomRecovery
Missing composition helperRebuild/install a matching SDK containing its helpers. Do not copy a helper beside unrelated binaries.
Missing creative exampleCheck the SDK data directory and installation component. Do not hide missing package content with another source clone.
Source target rejectedUse an independent consumer build directory. Do not combine source and installed targets.
ABI, compiler or header mismatchUse a matching package/toolchain and record both identities. A version label cannot repair incompatible binaries.
GUI component absentInstall a package actually containing those GTK components or select console mode.
Link or DLL failureInspect built archives and runtime dependencies; configuration success is insufficient evidence.

Assessment: build a consumer in a directory with no sibling Framework checkout. Record configure, build, test, install and launch results, package prefix, header identity and runtime dependencies. Explain which files belong to the SDK and which belong to the product. Configuration-only regression fixtures use declared imported targets to inspect helper behavior; they do not certify binary ABI or application execution.

Compose an offline ComfyUI client

Media selects the exported comfy_protocol component alongside its application and creative-workspace dependencies. Its console delegates comfy inspect to Framework, preserving the no-argument composition report. The independent inspector lesson demonstrates a smaller consumer. With testing enabled, umicom_add_comfy_inspection_command_tests locates SDK-owned synthetic fixtures and registers six command checks. Installed-consumer configuration, linking and execution must be qualified against your actual SDK; registration alone establishes none of these results.

Structured OS observations

The captured boot JSON course adds a small installed-SDK client using Umicom::boot_report_tools. OS discovers that component from its selected Framework and can require it with UMICOM_OS_REQUIRE_BOOT_REPORT_JSON=ON. The shared serializer validates before publishing output and compares semantic fields without interpreting them as present machine health.
