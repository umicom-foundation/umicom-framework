Review completed orders and fills

The broker connection window can request completed orders and compare their reported filled quantities with a separate execution capture. Framework owns the connection, decoding and comparison. Trader uses the same controls, and other native applications can reuse the Framework window.

An order can finish through cancellation after only part of its quantity was filled. A completed order is therefore not necessarily a fully filled order. This view preserves the broker's status and quantities separately. It does not submit, bind, modify, repeat or cancel orders.

Connect and read completed orders

  1. Log into TWS or IB Gateway and enable its socket API. Start qualification with a paper account and keep the broker API read-only setting enabled.
  2. In Trader, open Broker Connections, then the Paper / Live connection window. Choose the program, port and intended account environment. Use a positive client ID that is not already in use.
  3. Select Connect and wait for Read-only API ready. Verify the account environment in TWS or Gateway; the local mode selector does not prove which environment is running.
  4. Expand Completed orders and execution review. Leave Only API-origin completed orders selected to request that scope. Clear it to include other completed orders the login can see. This is not a filter for the current API client or for the account selector above.
  5. Select Read completed orders. Wait for the end marker. Before that marker, the displayed rows are only a partial capture.
  6. Read the account, permanent order ID, instrument, original quantity, reported filled quantity, order state, completion status and broker time together. The permanent ID identifies the broker order; it is not a client order ID and cannot be used as a replacement for one.

Compare captured executions and commission

  1. Select the account shown on the completed-order row.
  2. Use the existing Recent executions and stock quantity comparison section to read executions. The execution request must finish independently of the completed-order request.
  3. Return to the completed-order section. Matching ordinary stock executions are grouped by account, permanent order ID, contract ID and side. The comparison uses the completed row's filled quantity.
  4. Inspect the commission result separately. A total is shown only when each selected execution has a consistent, exactly representable fee in one currency. Missing fees remain unavailable. Conflicting or mixed-currency reports require separate review.

For example, an order for 7,000 shares could show Cancelled with a filled quantity of 10. Ten captured shares agree with that reported fill, but they do not mean 7,000 shares traded or that a full-quantity restriction was enforced. A broker status alone does not establish the commission charged.

Save a local report

  1. In the completed-order section, enter a new absolute CSV path in a private folder. The report contains every account in the captured scope, independent of the account selector.
  2. Select Write new completed-order report. The application captures an owned copy before starting the background write. Closing the window after writing starts does not cancel that requested write.
  3. Wait for the saved confirmation. If the file already exists, choose a new name; existing files are never replaced. A failed write can leave a partial new file, which remains available for inspection.
  4. Import provider quantity, identifier and time columns as text in a spreadsheet. This preserves decimal spelling and identifiers. Formula-like provider text receives a protective apostrophe under Framework's CSV policy.
  5. Read the scope, completion, failure, freshness and connection columns alongside every order row. A metadata row is present even when no orders arrived. Partial or old captures are exportable as labelled evidence; saving them does not make them complete or fresh.

The report contains completed-order observations and original receipt times. It does not include a commission statement, all raw advanced fields, or a promise of complete account history. It is saved locally only when requested, and no report data is sent to an online service by this workflow.

Understand the limits

AreaCurrent behaviour
History scopeThe broker supplies its available completed-order window. Receiving an end marker does not prove that all historical trades or all account activity were returned.
Capture lifetimeOne completed-order request is accepted per connection because these callbacks carry no request identity. Reconnect to start another capture. Queue failure does not consume the opportunity.
FreshnessThe native view uses a 15-second age limit. A disconnected, expired or incomplete capture cannot produce a fresh comparison. Library callers provide their own positive age limit.
Exact quantitiesReported decimal text is retained even when it cannot be represented exactly. Zero or inexact completed filled quantities do not produce a positive execution comparison.
Execution comparisonOrdinary stocks only. Corrections and ambiguous execution structures require review; the application does not choose a correction by arrival order. Other asset classes remain available as completed-order observations when their message layout is supported.
Message layoutsLegacy protocol 151 through 176 is supported here. The decoder walks conditional sections for combo legs, scale orders, hedges, algorithms and known condition types. Advanced fields remain raw evidence unless a public property explicitly represents them. Structural decoding is not full semantic support for constructing or transmitting these order types.
BoundsAt most 64 completed records, 1,024 fields per message and 65,536 payload bytes. Variable sections allow up to 32 combo legs or conditions and 64 tag/value pairs. Unknown layouts and over-capacity responses fail explicitly rather than shifting fields or dropping evidence silently.
Repeated recordsByte-identical records with the same permanent ID are counted as duplicates. A conflicting record retains the first evidence and fails the connection for review.

Use the Framework interface

  1. Include umicom/broker_connectivity/completed_orders.h and link Umicom::ibkr_connection.
  2. After the connection becomes ready, call UmiIbkrCompletedOrdersRequest with the intended API-origin scope and monotonic time. Continue pumping the same connection.
  3. Copy the capture with UmiIbkrCompletedOrdersCopy. Inspect complete, failed and stale before presenting a qualified result.
  4. Copy individual rows with UmiIbkrCompletedOrderCopy. Caller-owned copies remain independent of the connection. Raw-field access uses UmiIbkrCompletedOrderFieldCopy; field zero is the message identifier, and the required buffer size includes the string terminator.
  5. Call UmiIbkrCompletedOrderReviewExecutions with the execution request ID. Check its return status before reading the result, then inspect quantity flags and feeAvailable separately. Failure leaves the caller's result unchanged.

To create a report in another application, include umicom/broker_connectivity/completed_report.h and call UmiIbkrCompletedOrdersExportCsv on the connection's owning thread. The returned UmiCsvDocument owns its bytes. Save it on a worker with UmiIbkrObservationsWriteNew from observation_export.h, then release it with UmiCsvDocumentDestroy.

Extend the public projection by adding a named property, validating its wire representation and adding independent fixtures for every conditional layout it affects. Keep raw observations separate from order commands so historical evidence can never become an accidental instruction to trade.

Recover from an unavailable view

  1. If the capture is incomplete or timed out, inspect the connection message and the TWS API diagnostics. Retained rows are partial evidence.
  2. If the completed row and execution account differ, select the matching account and request executions again. The application does not join records from different accounts.
  3. If the view is old, reconnect and request both captures again. Historical rows remain useful to read but cannot become current merely by repainting the window.
  4. If the broker reports an unsupported message layout, retain the diagnostic for investigation. Do not disable bounds or guess field positions to make it appear successful.

See open-order recovery and execution and commission review for the related workflows. IBKR's TWS API documentation describes the broker interface. Its order-status guide explains why pending cancellation and cancellation must be interpreted carefully.
