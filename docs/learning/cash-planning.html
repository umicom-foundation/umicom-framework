Plan dated cash movements

A cash plan records amounts you expect to receive or pay on particular dates. Framework calculates a projected closing balance for each date with activity and shows when the balance first falls below your chosen buffer. TMS, Bank and Trader open the same planner through the Cash planning button.

This is a local planning workspace. Values are entered by you; they are not downloaded balances, broker buying power or permission to make a payment. The planner does not submit payments or trades. No network connection or API key is needed.

Create a plan

  1. Open Cash planning. Each window starts with an independent, empty plan.
  2. Enter a title, currency, opening amount, minimum buffer, start date and end date. Dates use YYYY-MM-DD. Both range endpoints are included.
  3. Choose decimal places explicitly. For GBP amounts such as 125.50, choose 2. Currency codes do not automatically choose a scale. The opening amount may be negative; the buffer must be nonnegative.
  4. Click Apply settings before editing an entry. If you have already changed entry fields, first add/update that entry or use Reset fields to discard unapplied fields.
  5. Give the entry a unique ID and a readable label. Enter its date and nonnegative amount. Check Inflow for money received, or uncheck it for an outflow.
  6. Leave Include entry checked and click Add entry. The report immediately reflects stored assumptions.

To edit an existing entry, choose it in the list, change its fields, and click Update selected. Selecting an entry loads its stored fields, replacing unapplied entry fields. To create another entry from it, change the ID and use Add. Uncheck Include and update to keep an entry without including it in the projection. Remove selected removes it from this plan. Undo last change restores one previous stored plan; this history lasts only while the window remains open.

Understand a shortfall

Try an opening balance of GBP 1,000.00, a buffer of 200.00, an outflow of 850.00 on the third day, and an inflow of 500.00 on the twentieth day.

ObservationBalanceHeadroom above buffer
Opening1,000.00800.00
After the outflow150.00-50.00
After the inflow650.00450.00

The first projected shortfall is the third day, even though the final balance is above the buffer. Opening is included when finding the minimum and first shortfall. Equal minimum balances retain the earliest date.

All movements on a date are grouped into one end-of-day result. Receiving money later on the same day can therefore offset an earlier payment in the report. This does not establish that funds would have been available earlier that day. There is no intraday sequencing, interest, exchange-rate conversion or holiday adjustment.

Enabled entries before the start or after the end are retained and counted separately. They do not alter opening or closing balances. An overdue payment is not automatically moved to today. Disabled entries are counted as disabled, regardless of their date.

Save, review and export

  1. Apply or reset all edited fields. Reports and file operations use the stored plan, not unfinished fields.
  2. Enter an absolute path in an existing folder you control, such as C:\Users\YourName\Documents\cash-plan.json on Windows or /home/yourname/Documents/cash-plan.json on Linux.
  3. Choose Save new JSON. Use a new filename for each saved revision. Existing files are never overwritten.
  4. To restore, enter the saved file path and choose Load for review. The report area shows the complete current and loaded assumptions. Loading alone does not replace your plan.
  5. Read both documents, check the review confirmation, then choose Apply reviewed plan. Editing fields or changing the selected entry invalidates that review. Undo can restore the previous plan after a successful apply.
  6. For a spreadsheet report, choose a new path ending in .csv and select Export new CSV.

CSV amounts are exact integer minor units, accompanied by currency and scale columns. An amount of 15000 at scale 2 represents 150.00. The file contains an opening row, activity rows, and a closing row. It is an export report, not a plan import format; use JSON to preserve entry IDs, labels and enabled states.

Files are ordinary local documents, not encrypted storage. Choose the folder and its access permissions accordingly. Closing a window discards its unsaved in-memory plan. A save already dispatched to a worker can finish after closing, but a load never applies itself.

Recover from a refused operation

  • Invalid argument: check real calendar dates, nonnegative entry/buffer amounts, decimal places and currency. Decimal text does not accept thousands separators, exponents or excess decimal places.
  • Already exists: choose a unique entry ID, or a new filename when saving.
  • Invalid state: finish or reset entry edits before changing plan settings, and apply settings before editing an entry. File operations require all edited fields to be applied or reset.
  • Capacity exceeded: plans hold at most 128 entries. A calculation can also refuse an integer overflow. Correct the amount; values are never wrapped, rounded or silently saturated.
  • Changed while loading: load again after settling your edits. The earlier result was not applied.
  • File failure: check the absolute path and folder permissions. A failed write may leave a partial new file; inspect it and select another filename. The application does not delete it.

A currency or decimal-scale change is refused while any existing entry uses the old unit, including disabled entries. Open a new planner for another unit. The application does not relabel amounts as a different currency.

Reuse the Framework owner

Link Umicom::cash_planning and include umicom/cash_planning/plan.h. Create an opaque plan, add copied entries, and call UmiCashPlanProject. Use document.h for strict JSON, CSV and new-file operations. Keep each plan on one owning thread; copy it before handing it to a file worker.

The JSON reader validates every entry and publishes the complete new owner only after success. It refuses unknown or duplicate members, invalid dates, fractional integer amounts and inconsistent input. A syntactically valid plan can still contain assumptions whose aggregate arithmetic overflows; projection and CSV export then refuse without publishing a partial result. A JSON save remains available so those assumptions can be inspected and corrected.

The example in examples/cash_planning/main.c demonstrates one complete projection. Native applications link Umicom::ui_gtk4 and can add UmiGtk4CashPlanLauncherCreate() without copying the model, arithmetic, editor or file logic. Web and mobile hosts can use the portable C owner, but this feature supplies no browser or mobile screen.
