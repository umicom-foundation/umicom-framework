C23 · application delivery · Windows

Check a Windows release before sharing it

An application is more than its main executable. A Notes window may also need a library, an icon and a starter document. Copying only the executable can leave a perfectly good program without the files it needs.

In this lesson, you will inspect an Umicom release, read the results, install a selection and try a small Notes application. You will also learn why checking files and opening an application answer different questions.

Use a practice installation and fictional notes. The inspector does not contact a network, load a DLL or start an application. Installation and the later Notes exercise are separate, deliberate steps.

Working from source? Build the update first using Build-and-Git.md. This lesson describes the Windows build of the tools; a source ZIP is not a ready-to-run Windows installer.

1. Understand the three checks

A static inspection reads files without running their code. It can compare recorded hashes, examine executable metadata and look for declared dependencies. A startup test asks Windows to load the actual program. A workflow test asks whether a real task works after the window opens.

For Notes, those questions become: are the executable, model DLL and starter document present? Can Windows load the executable and DLL? Can a person edit and save a new note?

Check Useful evidence What it does not prove
Recorded bytes A file agrees with the release catalogue The publisher is authentic or the code is harmless
Executable metadata A Windows image has the supported architecture and readable import records All requested functions exist or Windows can load it
Private dependencies A named DLL is included in the selected bin inventory Every dynamically requested plug-in is known
Actual startup A particular program starts on the tested machine Every menu, database operation or screen works

Windows has its own DLL search rules, including API sets, known system libraries and application directories. The inspector deliberately does not imitate that loader or search the development machine's PATH to make an incomplete package look complete. Microsoft's DLL search documentation explains those distinctions.

2. Start with an intact release folder

A native Umicom offline release normally contains Umicom-Setup.exe, suite.umi and a payload directory. Keep them together. suite.umi is the catalogue: it records the applications and the files prepared for them. payload contains those files.

Obtain the release from a trusted publisher. Hash agreement is not publisher verification: someone who replaces a file and its recorded hash could make both agree. This lesson does not introduce signed-release verification.

Open the supplied Setup Centre. On Applications, choose the release folder and select Load applications. Inspect the displayed application names. Choose the applications you need, or Select all. Selecting a release does not install it.

Now choose Inspect selected Windows files. This reads the selected applications and their shared files. It also checks the standalone installer copy when that copy is recorded in the native release.

A scan can take time for a large collection. Stop asks the worker to cancel; the interface waits for the current bounded read to return. Closing the window while work is active asks whether that work should be stopped. It does not remove the release.

3. Read the result without guessing

A successful summary says that static inspection completed and explicitly states that no application was launched. Keep that last sentence in mind. A private import is a DLL name the program declares. A deferred system import is a Windows-provided name or API-set requirement that still needs a real Windows test.

Result Meaning Sensible next step
File bytes agree The observed file matches its catalogue size and SHA-256 Continue with the other checks
Private import found A dependency is declared in the selected private bin inventory Read that dependency's own image/file results too
System requirement deferred Host/API-set availability is not established by this scan Include it in target-Windows startup testing
Private DLL absent A required name is missing, or belongs only to an unselected application Ask the release builder to repair the dependency inventory
Resource absent A required GTK/SourceView resource is missing or empty Rebuild the coherent runtime/resource package
Image rejected The file is malformed or outside the selected AMD64 release profile Check that the correct executable was packaged
Bootstrap differs The clickable setup file no longer matches its inventoried copy Stop and obtain or rebuild a coherent release

Do not fix a missing DLL by downloading a random same-named file. The package builder needs the matching dependency from the runtime used for that application. Do not turn an inspection failure into a pass by changing the catalogue by hand.

The current resource checks cover the runtime marker, compiled schema file, selected Umicom branding and the external GtkSourceView language schema. Their presence and recorded bytes are checked. This is not a complete test of every theme, font, plug-in or resource format.

4. Save a detailed JSON report

The graphical window shows a summary and the first issue. The command-line inspector can write the complete bounded observation list as JSON. JSON is a structured text format that another program can read.

Open PowerShell. Change the release path below to the actual folder you prepared. The report filename uses a new identifier so that a previous report is not overwritten.

Set-Location "C:\umicom\Umicom-Applications"

$Inspector = ".\build\windows-ucrt64-all-debug\bin\umicom-release-inspect.exe"
$Release = "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\packages\Debug\native-suite-b23"
$Report = Join-Path $env:TEMP ("Umicom-release-" + [guid]::NewGuid().ToString("N") + ".json")

& $Inspector release --root $Release --output $Report
if ($LASTEXITCODE -ne 0) {
    Write-Host "Inspection or report publication did not complete successfully. Read the messages above."
}
Write-Host "Requested report location: $Report"

Reports contain local paths and application names. Review them before sharing them with someone else.

Open the report with a text editor. Look at complete, issues, system_deferred and runtime_tested. A complete scan may still have issues. runtime_tested remains false because this command never runs an application.

The private_imports and system_deferred counters count observed dependency declarations, not unique DLL names. A DLL used by three programs may appear three times. The bytes value is a decimal string so software does not silently round a large integer.

With --apps id,id, the command inspects an explicit subset. Use application identifiers from the catalogue, not guessed display names. Leaving --apps out selects all catalogue applications. Repeating an identifier or naming an unknown application fails rather than silently changing your selection.

Reports are created exclusively. An existing output is not replaced. A write failure can leave the newly created partial file; the command reports the failure and a later attempt needs a new filename.

5. Review and install a selection

Return to Applications. Choose a new installation folder. This release of Setup Centre does not upgrade or repair an existing installation, so do not point it at a folder containing work you want to keep.

Choose whether to create current-user Desktop and Start-menu shortcut groups. Select Review selection. The review performs static inspection before creating the installation fingerprint. It shows the destination, selected applications and shortcut choices.

Changing the selection, destination or shortcut checkboxes invalidates that review. This is intentional: checking a box should not add an unreviewed filesystem effect to an earlier decision. Review again after changing a choice.

Choose Install reviewed selection when the review matches your intention. The installer rechecks the selected Windows files before copying and keeps the existing byte-checked installation transaction. Its completion receipt is written after the payload has been copied. Failure or cancellation can leave the new partial directory; it is not reported as a completed installation.

A shortcut failure is reported separately from a completed payload copy. Installation, shortcut creation and application startup are not interchangeable results.

6. Inspect the installed files

Choose Verify installation in Setup Centre with the installation folder selected. This now uses the recorded installation receipt to inspect installed bytes, image metadata, private dependencies and the selected resource checks.

For a detailed report, use the installed inspector or the build-tree inspector:

$Installed = Join-Path $env:LOCALAPPDATA "Umicom practice installation"
$Report = Join-Path $env:TEMP ("Umicom-installed-" + [guid]::NewGuid().ToString("N") + ".json")
& $Inspector installation --root $Installed --output $Report
if ($LASTEXITCODE -ne 0) {
    Write-Host "The installation needs investigation. Do not treat this as a startup pass."
}

Replace $Installed with your actual practice destination; the example does not create that directory. Personal files not listed in the receipt are not inspected or removed. Receipt checksums still do not authenticate the original publisher.

Only after the file checks should you open the installed applications and exercise real tasks. For a release qualification, use a clean standard-user Windows machine rather than relying only on the development computer.

7. Build the Notes release laboratory

The included Notes laboratory is deliberately small. It has a real Windows executable, a separate model DLL, an executable-relative starter text file and embedded Umicom branding. It is not a replacement for the existing Framework document/editor services.

After configuring the repository, build the example and its acceptance program:

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build --preset windows-ucrt64-all-debug `
    --target umicom-release-notes umicom-release-windows-install-test `
    --parallel 2
if ($LASTEXITCODE -ne 0) { throw "The release laboratory did not build." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --preset windows-ucrt64-all-debug `
    -R '^framework\.release_inspector\.windows\.' `
    --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "The Windows release laboratory did not pass." }

These are Windows acceptance steps, not a statement that they have run on your machine. The source-delivery validation describes which host checks were actually performed.

The acceptance program packages and installs the laboratory in a new temporary path containing spaces and café. It starts the installed executable from an unrelated working folder, with the child's PATH limited to the Windows system directory. Separate cases prepare incomplete copies without the DLL or starter document. They never remove a dependency from your actual installation.

Those checks use the real Windows loader and the real Framework process runner when executed on Windows. Their --smoke-test path does not display the Notes window, so manual interface testing remains a separate step.

8. Edit and save a practice note

In File Explorer, open the build's bin directory. Double-click umicom-release-notes.exe. Keep umicom-release-notes-model.dll and example-note.txt beside it.

The starter text should appear. Add a sentence about the next Umicom feature you would like to build. Choose Count words. The model counts words separated by ASCII whitespace; it is an intentionally simple exercise, not a full natural-language word analyser.

Choose Save a new copy... and select a new .txt filename in your practice folder. The file is UTF-8. Choosing an existing filename is refused; use a new name rather than overwriting earlier work. The text limit is 32 KiB after conversion to UTF-8.

Close and reopen the original executable. It loads its packaged starter, not the personal copy you saved. This keeps the exercise clear: a packaged resource belongs to the installation, while a saved note belongs to the person using the application.

The example's native UI has intentionally modest scope: one note, a word counter and save-as-new. It does not offer autosave, session recovery or multi-document editing.

9. Learn from a missing file in a disposable copy

Create a new folder just for this experiment. Copy the Notes executable, its model DLL and the starter text into it. Open that copied executable once before making a change.

Rename example-note.txt in the disposable copy only, then open the copied program again. The window should explain that the starter resource is missing or invalid. Restore the filename after observing the message.

The automated missing-DLL test is the better way to investigate loader failure: it creates its own incomplete directory and bounds the child process. Do not delete or rename DLLs in Windows, MSYS2, the source tree or your real installation.

The two failures happen at different points. The absent DLL can prevent the program from reaching its entry point. The missing starter document is handled by program code after loading. A useful diagnostic tells you which boundary failed instead of calling every problem “the application crashed”.

10. Read the native code behind the checks

Begin with include/umicom/release_inspector/inspection.h. The public API describes ownership, cancellation and limits. Then follow pe.c, inspection.c and cli.c: byte parsing, catalogue inspection and user-facing reporting are separate responsibilities.

A caller can inspect a loaded catalogue without implementing its own PE parser:

UmiSetupBundle *bundle = NULL;
UmiSetupReport opening = {0};
UmiReleaseInspection observation = {0};

UmiStatus status = UmiSetupBundleOpen(releasePath, &bundle, &opening);
if (status == UMI_STATUS_OK) {
    status = UmiReleaseInspectBundle(bundle, UmiSetupAllApplications(bundle),
        NULL, NULL, &observation);
}
UmiSetupBundleDestroy(bundle);
/* Check status before accepting the static result.
 * No application execution is implied, even when status is OK. */

The GUI calls the same service on a worker thread. It does not place PE parsing in a button callback. An observer may ask for cancellation; any path/detail pointers supplied to it are borrowed and must be copied before retaining them.

The path-validation repair is in src/setup_centre/text.c. A filename extension must not stop validation of the remaining characters. The old implementation is retained in an explained disabled block so its behaviour can be reviewed alongside the replacement. The current check also recognises the reserved superscript device digits documented in Windows filename rules.

11. Know the boundaries of this inspection

The release profile accepts AMD64 PE32+ executables and DLLs, with GUI or console subsystem declarations. The portable parser can also read PE32 metadata, but that does not make a 32-bit application eligible for this 64-bit release profile.

Up to 96 PE sections and 512 ordinary/delayed import descriptors are inspected per image. One image is held in memory at a time, with a 256 MiB limit. The observation list is capped at 262,144 and JSON uses the existing bounded Setup Centre text writer. Limits produce failures rather than truncated success.

The parser checks file-backed metadata and DLL names. It does not validate every PE directory, walk every imported symbol, resolve forwarded exports, verify Authenticode, prove CPU-instruction compatibility or emulate Windows. Legacy virtual-address-based delay descriptors are reported as unsupported. Microsoft's PE format reference describes the distinction from relative virtual addresses.

These checks are an observation, not a lock against later changes. Catalogue bytes are checked at both ends; each payload file is checked as it is read. The installer still performs its own revalidation and copy checks. Treat system dependencies as deferred host requirements and retain the real startup/workflow tests.

12. Practise explaining the result

Exercise: A report says complete: true, issues: 0 and runtime_tested: false. Write one sentence describing exactly what has been established.

Answer: The selected recorded files passed this bounded static inspection; no application startup or workflow has been tested by that command.

Exercise: Notes starts in the build directory but not in an installation directory. Which three files from the laboratory would you check first?

Answer: Its executable, umicom-release-notes-model.dll and example-note.txt. Then compare the release/receipt observations and the real loader result. Do not assume that a same-named DLL elsewhere is suitable.

Exercise: Why does changing a shortcut checkbox require another review?

Answer: Shortcut creation changes the user's filesystem. The reviewed action should reflect the user's current choice, not an earlier selection with a new side effect added afterwards.

Next practice: Read the Notes model's test, add an input with tabs and blank lines, predict the word count, then run the test before opening the window. You are testing a domain rule independently from the DLL loader and the user interface.
