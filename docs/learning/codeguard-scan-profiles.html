Make scan settings change observable behavior

1. Treat configuration as an executable contract

A setting is useful only when every relevant operation honors it. A source scanner can appear to respect a language setting while still admitting the same files into its duplicate detector. Keep admission in the shared Framework service so the CLI, editor and SDK consumers receive the same behavior.

CodeGuard has independent C, C++ and header flags. A nonzero value enables a category. The extension recognizer retains its existing case-sensitive suffix rules: .c; .cc, .cpp and .cxx; .h, .hpp and .hh. Enabling a language does not make this textual scanner a compiler for that language.

UmiCodeGuardConfig config = umi_codeguard_config_default(workspace_root);
config.profile.scan_c = 0;
config.profile.scan_cpp = 1;
config.profile.scan_headers = 1;
config.profile.scan_generated = 0;

This configuration omits C source from direct-file analysis, workspace analysis and duplicate collection. It includes supported C++ and header paths. The separate scan_source_names flag controls repository filename checks; those checks can still report a filename whose source language is disabled.

Policy uses directory components beneath the selected root. Enabling generated source does not opt into vendor, node_modules, VCS or CodeGuard rule sources. Traversal still skips hidden entries and does not follow symbolic links. Template/workspace payloads remain excluded from duplicate comparison even when their source is scanned.

The direct-file API bypasses directory selection because the caller explicitly chose a file. It still honors language flags. An explicitly selected build directory becomes the workspace root; its own name is not an excluded child component. These choices are selection policy, not a filesystem sandbox.

3. Use one language gate before every analysis phase

if (!umi_codeguard_source_supported(path,
        config->profile.scan_cpp, config->profile.scan_headers))
    return 0;
return config->profile.scan_c ||
    !umi_codeguard_source_supported(path, 0, 0);

The first check reuses Framework's extension recognizer. The second allows a recognized C source only when C scanning is enabled. The same private gate runs in direct-file scanning and in the workspace visitor before duplicate admission. Keeping extension knowledge in the existing recognizer avoids competing language lists.

4. Preserve the reason a report could not be completed

A finding is a diagnostic about source. A storage failure is an error in producing the report. Do not turn every insertion error into an allocation error: an exhausted capacity has a different cause. Return the exact status and stop adding further findings.

UmiStatus status = umi_codeguard_result_add(result, &finding);
if (status != UMI_STATUS_OK)
    return status;

The pattern scanner retains earlier findings if a later insertion fails. A caller using this low-level append-only API must treat that result as partial. UmiCodeGuardService publishes only a completed candidate and keeps its previous complete report when an attempt fails.

5. Verify behavior with controlled input

  1. Create an isolated fixture with one C file, one C++ file and one header, each containing the same short line.
  2. Add generated C files under build and _CPack_Packages. Add vendor and rule files, including vendor files nested under build.
  3. Disable architecture, filename and duplicate checks, then set max_line_length to one. Each selected source produces exactly one line-length finding.
  4. Expect three findings by default and five with generated scanning enabled. Expect one for each individual language category and zero when all three categories are disabled.
  5. Enable duplicate collection and restore the ordinary line limit. Three identical admitted files produce three pair candidates; disabling C leaves one pair; five admitted files produce ten pairs.
  6. Test direct-file requests separately. A disabled language returns success without opening even a missing path. Success in that case means the file was outside the selected language policy.

Pair counts are n × (n − 1) / 2 for this identical-content fixture. They are evidence that the intended files reached comparison, not proof that arbitrary matching fingerprints identify identical files.

cmake --build build --target umicom-codeguard-profile-selection-tests umicom-codeguard-pattern-failure-tests umicom-codeguard-path-policy-tests
ctest --test-dir build -R "^framework[.]codeguard_(profile_selection|pattern_failure|path_policy)[.]" --output-on-failure --no-tests=error

Replace build with your configured directory. The suites register seventeen real-scanner selection cases, ten pattern cases and twenty-nine lexical policy cases. The pattern fixture uses the real registry and matcher while controlling insertion failures. It checks raw/code/include modes, coordinates, early stop and preservation of the first successful finding. Configuration creates build rules; execute the targets and tests to obtain qualification evidence.

6. Recognize the remaining boundaries

The max_file_bytes profile member now reaches the native reader on every source, architecture and duplicate pass. Zero admits empty files only; oversized files fail with CAPACITY_EXCEEDED. It is a per-file byte budget, not a total workspace resource limit or a filesystem sandbox. Read bounded source analysis for native path policy, NUL text refusal, retained compatibility APIs and multi-pass race limits.

Existing text matching, long-line chunk behavior and native stream limitations still apply. This change adds no background worker, editor command wiring, content snapshot or graphical workflow. Source availability and successful configuration do not establish a passed runtime or installed-SDK check.

Exercises

  1. Explain why a successful direct-file request can produce no findings without opening a file.
  2. Add a generated header and predict the result with only header scanning enabled.
  3. Inject a failure on the second matching rule and verify that the first finding remains and the original status returns.
  4. Describe how you would distinguish a configured input budget from a budget enforced while bytes are consumed.
