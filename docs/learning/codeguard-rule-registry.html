Keep registry inputs alive during growth

1. Separate a descriptor from the text it references

A CodeGuard rule descriptor contains a match mode, severity and pointers to pattern and diagnostic strings. The registry owns its array of descriptors. It borrows the strings. Copying a descriptor copies those pointers; it does not copy the text they address.

UmiCodeGuardRule rule = {
    .rule_id = "EXAMPLE-PATTERN",
    .cwe = "",
    .severity = UMI_CODEGUARD_MEDIUM,
    .category = UMI_CODEGUARD_CATEGORY_MEMORY,
    .confidence = 100U,
    .match_mode = UMI_CODEGUARD_MATCH_CODE,
    .needle = "review_me(",
    .message = "Review this call",
    .remediation = "Check its ownership contract"
};
UmiStatus status = umi_codeguard_rule_registry_add(registry, &rule, 1U);

String literals remain alive for the program's lifetime. A dynamically created pattern must stay alive and unchanged until the registry is destroyed. A short-lived local text buffer is unsafe if the registry outlives it. The caller may discard the descriptor variable after successful insertion because its fields were copied.

2. Check element counts before calculating byte counts

A size_t value cannot represent every mathematical integer. Addition and multiplication can wrap. First calculate the largest representable number of descriptors, then compare the incoming count with the remaining element capacity. Only after that check is addition safe.

const size_t maximum = SIZE_MAX / sizeof(UmiCodeGuardRule);
if (count > maximum - registry->count)
    return UMI_STATUS_CAPACITY_EXCEEDED;
const size_t required = registry->count + count;

The implementation also checks that current count and capacity are internally consistent before subtracting. Capacity doubling clamps to maximum when another doubling would overflow. A representable byte count can still exceed available memory; allocation failure remains a separate outcome.

3. Keep input alive until the copy finishes

registry_at returns a borrowed pointer into the descriptor array. A caller can use a valid range of these entries as input to add. Calling realloc first may move and release that same array, leaving the incoming pointer invalid before the copy begins.

  1. Validate the incoming descriptors and required capacity.
  2. If the existing allocation has room, copy the descriptors with memmove and update count.
  3. If growth is needed, allocate a candidate array while the old array remains alive.
  4. Copy the existing descriptors, then copy the incoming range into the candidate.
  5. Release the old array and publish the new pointer, capacity and count.

During growth, both allocations exist briefly. That additional peak storage preserves the input lifetime and makes allocation failure leave the registry unchanged. A failed add keeps old borrows valid. Successful growth invalidates descriptor borrows, so callers must fetch fresh pointers afterward. The borrowed strings remain the caller's responsibility.

const UmiCodeGuardRule *borrow =
    umi_codeguard_rule_registry_at(registry, 0U);
UmiStatus status = umi_codeguard_rule_registry_add(registry, borrow, 1U);
/* On success, fetch a fresh descriptor pointer before using it again. */

4. Validate a batch before publishing it

The matcher requires a valid pattern pointer. Reject a descriptor whose needle is NULL before appending any entry from that batch. Optional diagnostic strings may remain NULL because the matcher already handles them as empty text. An empty, valid needle retains its existing whole-line match behavior; NULL and an empty string are different inputs.

Invalid arguments, inconsistent internal state, unrepresentable capacity and allocation failure have distinct status values. A single add either appends its complete batch or leaves the registry unchanged. The builtin loader still appends several groups: if a later group fails, earlier groups remain. A scanner that creates a candidate registry discards that candidate after failure.

These checks cannot prove that an arbitrary caller pointer addresses readable memory or a terminated string. The public contract still requires a readable array of count descriptors and valid referenced text. Registry mutation and scanning are not synchronized; serialize access.

5. Test ownership, not just the final count

  1. Fill the initial allocation with 128 valid descriptors, borrow two entries, then append them back to force growth. Check the new entries retain their original identifiers.
  2. Repeat a self-append when spare capacity exists. Confirm no allocation occurs.
  3. Refuse the next allocation. Check the original array pointer, count, capacity and borrowed descriptors remain unchanged.
  4. Place a NULL pattern in the last entry of a batch. Verify that no earlier entry from that batch was appended.
  5. Exercise arithmetic boundaries by refusing allocation before a simulated large range could be copied. Do not allocate enormous buffers merely to test an overflow guard.
  6. Run real builtin registration and matching with optional text and an empty pattern to preserve supported behavior.
cmake --build build --target umicom-codeguard-registry-ownership-tests umicom-codeguard-pattern-failure-tests
ctest --test-dir build -R "^framework[.]codeguard_(registry_ownership|pattern_failure)[.]" --output-on-failure --no-tests=error

Replace build with your configured directory. The registry suite registers twenty-five cases. Its allocator hook controls descriptor-array allocation; rule catalogues, matching and result storage use the real services. A successful configuration is not a runtime pass. Build and execute these tests with the actual Framework toolchain before accepting the implementation.

Exercises

  1. Draw the lifetimes of the old array, incoming borrowed range, candidate array and pattern strings during a growing self-append.
  2. Explain why checking required > capacity after an unchecked addition is too late.
  3. Describe what a caller must do after a failed builtin load, and why that differs from a failed single add.
  4. Design a separate deep-copy contract for dynamically supplied rule text. State ownership, allocation failure and destruction behavior before implementing it.
