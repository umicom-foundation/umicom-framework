Admit providers and retain ownership

A provider is a small C function table that connects an application to an inference implementation. A registry keeps those tables together. Before calling a function pointer, Framework must check that the registry is coherent and the current policy permits that provider. This lesson follows the actual shared AI runtime, including how it behaves when a descriptor is invalid.

1. Separate identity, classification and permission

The provider identifier answers “which adapter?”. Its kind classifies it as local, remote, AuthorEngine or test. Policy answers whether that class may run, and whether a remote call needs approval. An unknown enum value is invalid; it must not inherit local permission just because it is not equal to the remote value.

UmiAiProvider provider = {0};
provider.structure_size = (uint32_t)sizeof(provider);
provider.abi_version = 1;
provider.provider_id = "example.local";
provider.kind = UMI_AI_PROVIDER_LOCAL;
provider.instance = adapter;
provider.generate = Generate;
provider.destroy = Destroy;

Generate, Destroy and adapter are integration points implemented by your adapter. The registry does not authenticate an endpoint or prove that a provider labelled local stays on the machine. Configure the adapter and transport separately.

2. Transfer ownership only after successful registration

  1. Initialize fresh registry or runtime storage.
  2. Construct a valid provider table and keep its identifier alive.
  3. Call umi_ai_provider_registry_add.
  4. On success, the registry owns the registered instance cleanup obligation. On failure, the caller still owns it.
  5. Keep the borrowed identifier readable and unchanged until release.

Registration copies the function table, not the string or private instance. Duplicate identifiers return ALREADY_EXISTS, including when the table is full. A distinct entry beyond capacity returns CAPACITY_EXCEEDED. Invalid existing storage returns INVALID_STATE without inserting a new owner.

Do not initialize an already populated registry to clear an error. Initialization would discard the only references to its owners. Use checked release for valid storage and diagnose invalid storage before deciding how to recover it.

3. Validate storage before traversing it

UmiAiProviderRegistryValidate first checks the entry count against the fixed array capacity. It then checks each descriptor and rejects duplicate identifiers. The order matters: a loop must not read entries using an untrusted count before checking its bound.

Legacy umi_ai_provider_registry_find still returns a borrowed pointer or NULL. For a precise structural result, call Validate. No C function can establish that an arbitrary non-null pointer is still alive. Callers remain responsible for readable, terminated identifiers, valid function pointers and serialized access.

4. Admit immediately before external work

UmiAiProvider *selected = NULL;
UmiStatus status = UmiAiRuntimeAdmitProvider(
    &runtime, "example.local", approved, &selected);
if (status == UMI_STATUS_OK) {
    /* Inspect the borrowed table while retaining serialized runtime ownership. */
}

Admission validates the current registry, resolves the identifier and evaluates the current policy. It does not invoke generation. The output pointer stays unchanged on failure. An earlier successful admission is not a permission token: changing policy or replacing a provider requires another admission before dispatch.

Generation uses the same admission service immediately before invoking a provider. Use UmiAiRuntimeGenerateChecked when the previous response must survive a failed attempt. Section 9 explains its value-validation and publication contract; the legacy entry point remains available for callers that require provider-written failure output.

5. Preserve reviewed workspace behavior

The AI workspace has additional responsibilities: freeze the requested provider and model, collect review, retain evidence identity, and publish RUNNING before an external call. Shared admission does not replace those steps. A changed provider kind still returns BUSY so the caller can obtain a new review, even if the new kind is currently denied by policy.

The workspace now reuses runtime admission while retaining that review boundary. A malformed registry is refused before publishing RUNNING or calling the provider. The lower-level local streaming job remains a separate transport owner; it does not independently implement workspace review or durable job state.

6. Release once, or retain evidence

UmiStatus status = UmiAiRuntimeRelease(&runtime);
if (status != UMI_STATUS_OK) {
    /* Retain the runtime for diagnosis. Do not clear it or claim cleanup passed. */
}

Checked registry release validates all entries before invoking any destructor. It releases instances in reverse registration order, then clears the registry. During teardown it marks the registry unavailable, so a destructor cannot recursively release or add providers through the registry API. The implementation snapshots the small tables before callbacks; no allocation is required.

Callbacks must return normally and must not directly mutate or reinitialize the registry. These functions do not add cross-thread synchronization. The legacy void destroy wrappers remain available; they leave invalid storage intact but cannot report the error. Use the checked Release functions where cleanup evidence matters.

The provider tests cover malformed counts and descriptors, duplicate identity, capacity, borrowed identifiers, reverse cleanup, callback reentry, current policy and dispatch result propagation. The kind-policy test exercises all four supported kinds against local/remote permission, approval requirements and zero/nonzero approval values. The workspace case checks that refusal leaves the approved job unchanged.

9. Validate values before publishing an answer

A provider table can be valid while the request supplied to it is malformed. A fixed array holds a bounded number of bytes, but it is only a C string when a zero byte appears within that array. Likewise, check message_count before using it to index the message array.

UmiAiRequestValidate checks both identifiers, the active messages' names, text and roles, and a finite temperature. A count larger than UMI_AI_MAX_MESSAGES returns CAPACITY_EXCEEDED before traversal. Malformed text, roles or temperature return INVALID_ARGUMENT. Empty drafts and unused message slots are allowed. Model availability, provider-specific temperature ranges and token limits still need separate checks.

UmiAiResponseValidate checks all four fixed text fields and the finish-reason domain. Empty text and FINISH_NONE are valid. A provider's model alias, reported token counts and identity strings remain evidence to interpret; structural validation does not authenticate them or invent a missing token total.

#include "umicom/ai/runtime.h"

UmiStatus GenerateReviewedReply(UmiAiRuntime *runtime, int approved,
    const UmiAiRequest *request, UmiAiResponse *last_reply)
{
    UmiAiGenerationReport report;
    UmiStatus status = UmiAiRuntimeGenerateChecked(
        runtime, "example.local", approved, request, last_reply, &report);
    if (status != UMI_STATUS_OK) {
        /* last_reply still holds its previous value.
         * report.dispatched distinguishes refusal from an attempted callback.
         * Check response_checked before reading response_status. */
        return status;
    }
    /* response_published is now true; the reply is structurally valid.
     * Apply the application's identity, content and presentation rules next. */
    return UMI_STATUS_OK;
}
  1. Initialize and populate the request, then keep its complete storage unchanged for the call. Use heap or owner-managed storage for this large record if the calling thread has a small stack.
  2. Keep the provider identifier readable and terminated. Supply separate response and optional report storage; neither output may overlap the request or runtime.
  3. Call the checked operation. It validates the request, rechecks registry and policy, then invokes the provider into private response storage.
  4. Read the returned status first. A provider error is retained even if its unfinished output is malformed. Such output is not published.
  5. If a provider returns OK but its response is malformed, the operation returns INTERNAL_ERROR. The report records the successful callback status and the failed response check separately.
  6. Only a structurally valid successful response replaces the caller's previous response. Display failures as failures; do not present the retained old response as a new answer.

The coding provider executor uses this checked path. Invalid configuration or request values preserve both outputs. Once input is admitted, execution metadata records the attempt. Finish reason and usage are populated only when a response was published, so a failed attempt cannot inherit the previous answer's usage. Provider selection is captured before invoking external code.

The legacy umi_ai_runtime_generate entry point now checks request bounds, but continues to expose provider-written error output for compatibility. It does not promise unchanged response storage on failure or validated response publication. Use the checked operation when those guarantees are needed. Both calls require serialized ownership. Native callbacks remain trusted code; direct memory mutation remains unsupported. Section 11 explains the shared guard against supported API teardown and recursive generation during the callback.

11. Keep the provider alive until its callback returns

Generation now records the active registry in a thread-local stack frame. A frame is a small record on the current call stack, linked to any outer invocation. Public registry and runtime layouts stay unchanged. Framework uses the frame only to detect synchronous reentry; it is not a mutex and does not make concurrent calls safe.

During generation, checked release, provider insertion and recursive generation on the same registry return BUSY. The legacy void initialize and destroy functions preserve the active owner. Read-only registry validation and lookup remain available. A nested call using a different registry is allowed, and its callback still cannot release an outer active registry.

UmiStatus status = UmiAiRuntimeCheckIdle(&runtime);
if (status != UMI_STATUS_OK) {
    /* Retain this runtime and all dependent owners. */
    return status;
}
/* Keep external lifecycle serialization until release completes. */
return UmiAiRuntimeRelease(&runtime);

UmiAiRuntimeCheckIdle checks invocation activity and provider registry structure. Use it before releasing siblings in a composition owner. UmiAiProviderRegistryCheckIdle only observes activity and does not validate table contents. Neither grants a lease for later execution. Callback code must return normally without freeing, copying or directly rewriting its owner. Calls through raw provider function pointers, arbitrary tool callbacks, nonlocal jumps and other threads are outside this guard.

After a callback returns, its frame is removed even if the provider reports an error or the checked response later fails validation. Shutdown can then be retried under the host's lifecycle rules. The response report marks refused recursive calls as not dispatched. It does not claim that a failed attempt generated a reply.

12. Share callback ownership with health refresh

AuthorEngine health refresh now uses the same registry ownership scope, retaining the runtime through both provider health callbacks and descriptor-aware probes. Generation, registry mutation and teardown on that runtime return BUSY until refresh returns. 13. Admit a tool catalogue before executing a callback

A tool combines a stable identifier, description, permission label, function pointer and borrowed context. The label explains the operation; it does not grant permission. Framework still checks the runtime tool policy and the caller's approval decision before invoking the function.

  1. Create a descriptor with umi_ai_tool_init. All three text inputs must be readable terminated strings. The identifier must be nonempty. The constructor copies into a temporary descriptor and publishes only after every field fits; a refused input leaves the previous descriptor unchanged. Inputs may refer to the destination's old text.
  2. Register it with umi_ai_tool_registry_add. Framework checks the candidate, the existing count, every active descriptor and unique identifiers. It copies the descriptor, but does not acquire ownership of user_data. Keep that context alive for every callback.
  3. Use UmiAiToolRegistryResolve when the reason for lookup failure matters. Malformed catalogue storage returns INVALID_STATE; a missing valid identifier returns NOT_FOUND. A failed lookup preserves the output pointer.
  4. Invoke through umi_ai_runtime_invoke_tool so lookup and current policy are checked together. Admission failures preserve the output buffer and do not call the tool. Once dispatched, the existing callback output contract applies, including any text written before an error.
UmiAiTool *selected = NULL;
UmiStatus status = UmiAiToolRegistryResolve(&runtime.tools, "echo", &selected);
if (status != UMI_STATUS_OK) return status;
/* The pointer is borrowed; keep the catalogue serialized and alive. */
return umi_ai_runtime_invoke_tool(&runtime, selected->tool_id,
    approved, "{}", output, output_capacity);

The resolver validates the complete active catalogue before comparing identifiers. Finding a matching first entry must not hide a malformed later entry. Inactive slots are not records. Empty descriptions and permission labels remain compatible metadata, and flags remain opaque. Validation does not inspect JSON, execute the callback, verify what its permission label means, or protect against direct writes by native code.

14. Publish an MCP bridge as one registration

An MCP bridge connects remote tool descriptions to the same Framework tool registry used by native tools. The bridge stores a session pointer and remote name for each registered callback. These bindings must remain at stable addresses while a registry can invoke them; copying or clearing a live bridge would invalidate that relationship.

  1. Prepare the session and discovered catalogue through the existing MCP client. Registration itself makes no transport request. It validates bounded server text and the complete catalogue before formatting local identifiers or permissions.
  2. Pass a fresh bridge and the destination registry to umi_ai_mcp_tool_bridge_register. Framework checks the registry before subtracting its count from capacity. A malformed count is a state error, not available space.
  3. Framework builds a private candidate containing both the proposed bindings and a copy of the existing registry. Every projected tool goes through the shared descriptor and registry services. A late duplicate, long identifier, long fallback permission or allocation failure leaves both original destinations unchanged.
  4. After every entry succeeds, Framework publishes the bindings and registry without invoking external callbacks between the writes. Hosts must serialize registration and invocation; this paired publication is not a concurrent transaction.
  5. Retain the bridge and session until all their tools have been retired. Re-registration returns BUSY if the supplied registry still points to any binding slot. A bridge belongs to one registry; this check does not discover references held by a different registry or arbitrary native code.
UmiStatus status = umi_ai_mcp_tool_bridge_register(
    &bridge, &session, &catalogue, &runtime.tools);
if (status != UMI_STATUS_OK) {
    /* The old registry and bridge are still available for diagnosis. */
    return status;
}
return umi_ai_runtime_invoke_tool(&runtime, "mcp.test.read_file",
    approved, "{}", output, output_capacity);

The local name combines mcp., the server ID and remote tool name. An explicit descriptor permission is retained; otherwise Framework joins the server permission prefix and remote name. Existing tool policy remains the authorization boundary. Permission labels and flags are metadata, and schema termination checks do not prove valid JSON or a verified server capability.

15. Complete a transport reply before publishing it

A transport callback receives a writable result buffer and its capacity. Returning OK must mean that it wrote a terminated string within that capacity. A decoder that uses ordinary C-string operations cannot safely interpret a successful reply whose terminator is missing.

  1. Use UmiAiMcpTransportRequestChecked when a failed or unfinished reply must preserve the previous result. It copies the callback tuple, allocates a separate buffer and fills that buffer with nonzero bytes.
  2. The selected callback writes into that staging buffer. If it returns an error, Framework returns that same status and discards the candidate. Error text is not published through this checked API.
  3. If the callback returns OK, Framework searches only within the supplied capacity for a terminator. Missing termination returns INTERNAL_ERROR. No output at all is also rejected; an intentional empty reply must write its zero byte.
  4. Only a completed string, including its terminator, is copied to the caller. Bytes beyond that string remain unchanged. Allocation refusal returns OUT_OF_MEMORY before invoking the callback.
char result[1024] = "previous accepted result";
UmiStatus status = UmiAiMcpTransportRequestChecked(
    &transport, "tools/list", "{}", result, sizeof(result));
if (status != UMI_STATUS_OK) {
    /* result still contains the previous accepted bytes. */
    return status;
}
/* Now pass the completed text to the appropriate protocol decoder. */

The existing umi_ai_mcp_transport_request remains the direct forwarding API, including its callback error output. High-level MCP initialization, ping, discovery, tool calls, resource reads and prompt retrieval use the checked boundary. This admits text termination; it does not prove valid JSON, UTF-8, remote identity or successful tool execution. Native callbacks must obey their buffer capacity and borrowed-input lifetime contracts.

16. Keep accepted catalogues when discovery fails

A list refresh can fail after receiving several valid entries. Clearing the current catalogue before the request finishes would discard usable information, while publishing each entry as it arrives would expose a partial replacement. MCP discovery now constructs each replacement privately and publishes it only after the list has been accepted by the existing decoder.

  1. Keep the current catalogue available while requesting a list. A failed session check, allocation, transport, parse, duplicate check or capacity check leaves its previous bytes unchanged.
  2. After the transport returns, Framework requires the session to remain ready at the revision that made the request. A changed revision or readiness refuses the reply before list publication. Keep server and transport configuration stable for the whole operation.
  3. Use umi_ai_mcp_client_discover to refresh negotiated tools, resources and prompts together. Each list is staged; a later failure preserves all three previous catalogues. Unsupported catalogues retain their earlier state and trigger no list request.
  4. Only a successful complete client refresh publishes its supported catalogues. The session and registered bridge bindings are not relocated. Keep discovery and invocation serialized under the application's ownership rules.
UmiStatus status = umi_ai_mcp_client_discover(&client);
if (status != UMI_STATUS_OK) {
    /* Keep displaying the last accepted catalogues and report this failure. */
    return status;
}
/* The negotiated catalogue set has been replaced together. */

Successful discovery retains the existing fresh-catalogue revision behavior: initialization starts a new catalogue, then accepted entries advance that construction token. It is not a monotonically increasing identity across refreshes. The session check also does not prove that several remote lists came from one server-side snapshot. Native callbacks must keep owners alive and must not mutate the destination catalogues during discovery.

17. Preserve session identity across callbacks

A session revision identifies a lifecycle change. When an external callback returns, the caller must check that the same session operation still owns the next state transition. Otherwise an initialization reply could mark a session ready after a callback disconnected it.

  1. Initialization requires the connected state and an available revision. An exhausted counter returns UMI_STATUS_CAPACITY_EXCEEDED before encoding or calling the transport.
  2. Framework captures the revision before the request. After the request returns, that revision and the connected phase must still match before decoding negotiated capabilities.
  3. The initialized notification sees the negotiated capabilities in the initialized phase, as before. Its completion must still match the captured revision and initialized phase before Framework publishes ready and advances the revision.
  4. A callback error remains the reported error. Framework writes failed only when it still owns the expected phase. A successful callback that changed the revision or phase instead returns UMI_STATUS_INVALID_STATE, retaining the newer state.
UmiStatus status = UmiAiMcpSessionDisconnectChecked(&session);
if (status == UMI_STATUS_CAPACITY_EXCEEDED) {
    /* The complete session is unchanged. Stop scheduling work through this owner.
     * Retire every borrowed reference before constructing a fresh lifetime. */
    return status;
}
if (status != UMI_STATUS_OK) return status;
/* Negotiated capabilities are cleared; metadata and transport remain. */

Disconnect now has a checked entry point. At the largest representable revision it refuses without clearing state or wrapping the counter. The existing void disconnect delegates to it and retains the session on refusal; use the checked API when the application needs to report that outcome. The last available revision may still be used successfully. Reinitializing storage that other objects still borrow is not a safe workaround for exhaustion.

These comparisons assume callbacks return normally and keep the session alive. They are not a lock, a memory-lifetime lease or protection against arbitrary native writes. Serialize access, keep transport configuration stable during an operation, and require ready before ordinary session use. A transport completion check does not itself validate the negotiated protocol response.

18. Admit negotiated metadata before using it

Receiving terminated text is only the first boundary. A server's initialization reply must also contain usable metadata. The MCP lifecycle specification describes the exchange of protocol version, capabilities and implementation information before normal operation. Framework's initialization decoder now uses its existing owned JSON parser to inspect that result.

  1. Parse the complete bounded result. Invalid JSON, invalid Unicode and invalid text in an otherwise unused extension refuse the response.
  2. Read protocolVersion, capabilities and serverInfo from the root object. Read the server name and version from serverInfo. Framework requires a nonempty protocol and name; the version must be a string and may be empty.
  3. Recognize tools, resources, prompts and logging only as direct object members of capabilities. An unrelated nested object named tools does not grant a capability.
  4. Refuse duplicate interpreted names, including names that become equal after decoding JSON escapes. Unknown extensions remain allowed and do not grant permissions or implemented capabilities.
  5. Publish the complete capability value only after all checks succeed. A failed decode preserves the caller's previous output. Session initialization separately requires the supported protocol constant before publishing capabilities or notifying the server.
UmiAiMcpServerCapabilities negotiated;
UmiStatus status = umi_ai_mcp_decode_initialize_result(result_json, &negotiated);
if (status != UMI_STATUS_OK) return status;
/* Decoding checks structure and bounds. Session initialization additionally
 * checks whether this client supports negotiated.protocol_version. */

The parser accepts at most 32,767 result bytes and 128 nested containers. Required strings must fit their public inline arrays after Unicode decoding. Duplicate interpreted members return UMI_STATUS_ALREADY_EXISTS; missing fields, wrong kinds and malformed text return UMI_STATUS_PARSE_ERROR. Size limits return UMI_STATUS_CAPACITY_EXCEEDED, and allocation refusal remains an error. Unrelated duplicate extension names are retained by the parser; this is not a complete MCP schema validator. Recognized capability objects may contain uninterpreted sub-capabilities.

An unsupported negotiated protocol returns UMI_STATUS_NOT_IMPLEMENTED from session initialization. The session enters failed, retains its prior capabilities and revision, and sends no initialized notification. The host must close or retire its transport as appropriate and report the incompatibility. Do not label the session ready or silently retry using an unimplemented protocol.

The generic JSON tree and Unicode text implementations are now compiled into Umicom::protocol. Their existing header paths and C symbols stay available. Developer consumers retain the protocol dependency; AI consumers use that smaller shared owner. The SDK's existing protocol archive carries these symbols, so source and installed consumers use the same implementation.

19. Resolve catalogue entries from admitted storage

A bounded array is safe to traverse only when its declared count fits the array and its active records contain usable text. Resource and prompt catalogues now validate every active descriptor before returning a match. This prevents an early matching identity from hiding malformed later records.

  1. Initialize the catalogue before use. A resource needs a nonempty URI; a prompt needs a nonempty name. All inline text must contain a terminator within its declared array, while optional text may be empty.
  2. Use the descriptor validator before accepting externally constructed records. Use the catalogue validator to check the declared count, every active record and unique identities. Unused slots remain outside the active catalogue.
  3. Use checked resolution when the caller needs an error status. Invalid arguments return UMI_STATUS_INVALID_ARGUMENT, malformed catalogue storage returns UMI_STATUS_INVALID_STATE, and an absent identity returns UMI_STATUS_NOT_FOUND. Failure leaves the output pointer unchanged.
  4. Additions validate the candidate and current catalogue before checking duplicates and capacity. Successful addition stages the descriptor, publishes it and advances the revision. A refused addition leaves the catalogue unchanged.
const UmiAiMcpResourceDescriptor *resource = NULL;
UmiStatus status = UmiAiMcpResourceCatalogueResolve(&resources, uri, &resource);
if (status == UMI_STATUS_NOT_FOUND) {
    /* The admitted catalogue does not contain this identity. */
    return status;
}
if (status != UMI_STATUS_OK) return status;
/* Consume resource while its catalogue stays alive and unchanged. */

UmiAiMcpPromptCatalogueResolve provides the same contract for prompts. Existing pointer-returning find and indexed-access APIs remain available; they return null on invalid storage. These pointers borrow their catalogue. Do not retain them across catalogue mutation or destruction, and serialize access in the owning application.

The existing revision-exhaustion refusal still takes precedence before nested mutation work. An exhausted catalogue can be read when its storage is valid, but cannot accept another addition. These validators do not parse schemas, validate URI syntax or authorize a remote request. A terminated metadata string is not evidence that its content is safe to execute.

20. Optional metadata still needs validation

Optional means a field may be absent. It does not mean a present malformed field should silently become empty text. The MCP tool, resource and prompt decoders now parse the complete descriptor and stage its contents before changing caller output.

  1. Read the required identity from the root object: name for a tool or prompt, and URI for a resource. Empty identities, wrong kinds and nested lookalikes are refused.
  2. Keep omitted optional fields empty for compatibility. When description, resource name or MIME type is present, require a string that fits its declared storage after Unicode decoding.
  3. When present, tool inputSchema must be an object and prompt arguments must be an array. Preserve their validated JSON spelling, including internal spacing and escapes, within the existing schema capacity.
  4. Reject duplicate interpreted fields and malformed text anywhere in the descriptor. Publish the complete copied value only after every interpreted field has passed.
UmiAiMcpToolDescriptor replacement;
UmiStatus status = umi_ai_mcp_decode_tool(object_json, &replacement);
if (status != UMI_STATUS_OK) return status;
/* Registration applies its own bounded catalogue and permission rules. */

The decoder preserves its destination on parse, duplicate, capacity or allocation failure. This also lets discovery retain its previous accepted catalogue when a later entry has an invalid optional field. Unknown extensions are still parsed for valid JSON but are not interpreted. Omitted optional fields remain supported; these routines are not full MCP schema validators and do not authorize execution. Resource URI syntax and schema behavior require their own consumers.

Raw schemas and decoded strings have different bounds. A string is measured after decoding escapes into UTF-8. A raw object or array must fit with its original JSON punctuation, spacing and escapes plus the terminating byte. Retaining raw JSON avoids rebuilding or silently changing its meaning.

21. Validate the list before calling its visitors

A visitor is a function called once for each accepted object in a list. Calling it may change application state, so finding the first opening bracket is not enough. The shared MCP list reader now parses the complete reply, finds an unambiguous root member and checks that every list element is an object before the first visitor runs.

  1. Provide one complete JSON object with a direct tools, resources or prompts array. A matching name inside an extension object is not the requested list.
  2. Handle a missing member as UMI_STATUS_NOT_FOUND, duplicate matching members as UMI_STATUS_ALREADY_EXISTS, and malformed JSON or non-object elements as UMI_STATUS_PARSE_ERROR. Escaped and literal spellings of the same key identify the same member.
  3. Keep callback data alive throughout the call. Each callback receives a temporary, terminated raw JSON object. Copy it if it must outlive that callback. The reader owns a snapshot of the source, so changes to the original input during a callback do not alter later objects.
  4. Publish application state only after the complete visit succeeds. The completed count remains zero on failure and the original callback status is returned. Existing discovery functions already build a temporary catalogue and preserve their previous accepted catalogue on failure.
static UmiStatus inspect_object(const char *object_json, void *context)
{
    /* Decode into the caller's unpublished candidate, then return its status. */
    return collect_descriptor(context, object_json);
}
size_t completed = 0;
UmiStatus status = umi_ai_mcp_json_array_visit_objects(
    reply_json, "tools", inspect_object, &candidate, &completed);
if (status != UMI_STATUS_OK) {
    discard_candidate(&candidate);
    return status;
}
publish_candidate(&candidate);

The collect, discard and publish functions in this sketch belong to the application example; they are not additional Framework APIs. An arbitrary visitor can still perform irreversible work. The reader cannot roll that work back, so defer external effects until the owning operation has accepted the whole result.

Replies must terminate within UMI_AI_MCP_TEXT_CAPACITY bytes. Complete parsing also limits container nesting to 128 levels; lookup keys are limited to 4096 bytes. Empty arrays need no callback buffer. Malformed trailing fields, misplaced commas, invalid Unicode and later non-object elements are rejected before callbacks. Unknown extensions are checked for valid JSON, but their application meaning is not interpreted.
