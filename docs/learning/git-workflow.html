Umicom Git learning guide

Start here: one repository at a time

This guide teaches how to save and publish source changes without helper scripts. Use Windows PowerShell or Linux Bash; the platform buttons change the path examples. Read the lesson once, then use the individual repository recipes as a daily reference.

The working rule for this project is development on main. Check the current state first, switch safely when needed, review the files, then add, commit and push. Finish Framework and the affected application repositories before the parent. This follows your requested Umicom workflow; it is not a claim that every Git project uses the same branching policy.

Copy one command line, press Enter, read the result. Stop on an error. These are manual instructions, not a block to paste and run unattended. Never copy a terminal prompt such as PS C:\...>, >> or $. A leading $HOME in a command is different: it is part of the path.
Your taskWhere to start
You have never used GitLesson 1, then the private practice exercise.
You have already edited or merged a batchBranch checkpoint, then the repository recipes. Do not automatically pull over pending work.
You need a fresh checkoutClone Umicom.
You are moving to a second machineReceive the published snapshot.
A command stopped or Git looks unfamiliarTroubleshooting. Preserve the current work.

Reading the guide changes nothing in Git. Publishing happens only when you run the commands yourself. A successful Git push is not a successful build, test, installation or release qualification.

Lesson

1. What the Git words mean

Think of editing a recipe. Saving the file changes the copy on your desk. Staging selects what belongs in the next recorded revision. Committing creates that revision in your local history. Pushing shares committed history with the remote. These are separate actions; saving in an editor does not upload anything. [record] [commit]

WordPlain-English meaning
Repository / repoA project with Git history. Your computer has a local repository; GitHub can host a remote copy.
Working treeThe files and directories you are currently editing.
Staging area / indexThe selected file content for the next commit. git add -A updates this selection.
CommitA recorded project snapshot with a message, author and identifier.
mainThe branch used for Umicom development in this guide. Spell it in lowercase.
HEADGit’s reference to the currently checked-out position in history.
originThe remote name normally created when you clone. It is a name, not a password.
origin/mainYour local record of the remote branch, refreshed by fetching. It is not a live network lookup.
SubmoduleA separate repository checked out inside a parent directory.
Parent / superprojectThe repository recording which submodule commits belong together.
The four stages — illustration, not commands
Edit and save a file
        | git add -A
Staged file content
        | git commit -m "Describe the change"
Local committed history
        | git push origin main
Remote main on GitHub

git add -A includes new files, modified tracked files and deletions in the current repository. It normally respects ignored untracked files. Review before staging: build/ output, credentials, secrets/secrets.env and personal data do not belong in a source commit. Adding a tracked secret to an ignore file does not remove it from history. [add] [ignore]

Why Umicom needs a child commit and a parent commit

Your checkout contains one parent plus 25 directly configured submodules: Framework and 24 applications. The parent stores references to child commits, not a second copy of each child’s staged files. Changing Framework therefore requires a Framework commit/push and a later parent commit/push recording that new reference. [gitmodules] [submodules-book]

Repository ownership — a folder can be a separate repository
Umicom-Applications/              parent repository
  .gitmodules                    names and locations of child repositories
  framework/                     separate Framework repository
  applications/
    studio/                      separate Studio repository
    trader/                      separate Trader repository
    ...                          other application repositories
  tests/                         tests owned by the parent
  docs/                          documentation owned by the parent

For this lesson, reusable services belong in Framework; application-specific composition belongs in the respective application. Put a change in its actual owning repository, then publish that repository. Do not create parallel validation or learning implementations merely to make a product-specific commit.

2. Prepare Git and sign in once per machine

Step 1 — open your terminal and check the tools

Git commands — either system
git --version
gh --version

If a command is not found, install Git from the official Windows/Linux instructions and install GitHub CLI separately. Reopen the terminal afterwards. Git handles version control; gh is used below for browser sign-in and the private practice repository. [git-install-win] [git-install-linux] [gh]

Step 2 — give commits your own name and email

Replace both example values before running these commands. Use your own identity, not Sammy’s. The author name is not your GitHub sign-in, and the email becomes part of commit metadata. Use your GitHub-provided no-reply email when you need email privacy. --global applies to repositories for your user account on this machine; it does not change other developers’ settings. [identity] [commit]

Git commands — either system
git config --global user.name "Your Name"
git config --global user.email "YOUR-COMMIT-EMAIL"
git config --global --get user.name
git config --global --get user.email

Step 3 — authenticate through your browser

Git commands — either system
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status

Follow the device-code/browser instructions, sign in to the correct GitHub account and approve the connection. gh auth setup-git connects Git to the CLI credential helper. Your account still needs permission to each repository you intend to push. Do not paste tokens into source files, remote URLs, screenshots or this guide. [auth] [auth-setup]

GitHub account passwords are not used for Git HTTPS password authentication. The browser sign-in above is the teaching route here. If your organisation requires extra authorisation or access approval, finish that before cloning private submodules or pushing. [github-auth]

Step 4 — recognise the two path conventions

SystemUmicom checkout used throughout
Windows PowerShellC:\umicom\Umicom-Applications
Linux Bash$HOME/umicom/Umicom-Applications

On Linux, preserve the exact capital letters in Umicom-Applications. $HOME means your home directory; do not replace it with the word “HOME”. The Git operations are the same on both systems. Only directory navigation, file editing and the native executable path differ.

Lesson

3. Check the branch before switching

Yes: include git switch main in the normal workflow. But first inspect the checkout. Switching selects a branch; it does not merge detached work into that branch or publish it. Do this preparation before editing, merging a batch or qualifying a build whenever possible. [switch]
Git commands — either system
git status
git branch --show-current

Run those commands inside the repository you are about to change. If you are unsure which repository owns the current directory, use git rev-parse --show-toplevel. Its path must match the repository you intended. [rev-parse]

What you seeWhat to do
On branch mainProceed. Already being on main is fine; git switch main does not create another branch.
HEAD detached at ... and a clean working treeUse the detached-HEAD check below before switching.
Detached HEAD or another branch, with modified/untracked filesStop before switching. Preserve and review those files first; do not force the switch.
A different branch with a clean working treeUse the same history comparison below; do not leave unmerged commits behind.
Conflicts or an unfinished Git operationStop. Resolve that existing operation before beginning this recipe.

Detached HEAD, explained using Trader

A normal submodule checkout can select the parent’s exact commit without attaching to a branch. That is useful for reproducing a build. It is not a failure. Before making development commits, attach the relevant Umicom repository to main. You do not need to switch untouched dependencies merely to read or build them. [submodule]

When a local main branch exists
git branch --list main
git log --oneline main..HEAD

The second command asks, “Does my current checkout contain commits that local main does not contain?” No output means no such commits were found. If it prints any commits, or reports an error, stop before switching and keep the current checkout intact. A clean working tree alone does not prove that detached commits are safely included in a branch. [log]

When that comparison is empty and your working tree is clean, continue:

Git commands — either system
git switch main
git branch --show-current
git status

The branch command should now print main. If the detached commit was older than main, switching can change the checked-out source. Review and rerun the relevant tests before calling that different source qualified. If both commits were identical, only the branch attachment changes. [switch]

Only when local main does not exist

If git branch --list main prints nothing, fetch the remote record and compare against it:

Git commands — either system
git fetch origin
git log --oneline origin/main..HEAD

Continue only when the comparison succeeds with no output and the working tree is clean:

Git commands — either system
git switch --track origin/main
git branch --show-current
git status

This creates a local main tracking the existing remote branch, not a feature branch. If origin/main is missing, or the comparison lists detached work, stop; do not recreate or reset main blindly. [switch] [fetch]

Update before starting new work, not in the middle of unknown edits

Once you are on main and have no pending edits or unfinished child work, this moves forward only when the remote history permits it:

Git commands — either system
git pull --ff-only --no-recurse-submodules origin main
git status

A fast-forward-only pull refuses divergent history instead of inventing a merge. If it refuses, use the troubleshooting lesson. If your current source already contains an uncommitted batch on main, do not insert a pull into the middle of staging it. Review, test and commit that work first; resolve any later push rejection explicitly. [pull]

Lesson

4. Practice: create, change, commit and push one file

Use a personal private practice repository outside Umicom. This makes the first exercise independent of the real Framework and application histories. All publishing commands in this exercise target your practice repository. Do not run git init inside an existing Umicom repository or submodule.

Step 1 — create a new practice folder

Run this once on the first machine. If the folder already exists, stop and inspect it rather than overwriting it. To repeat the lesson, choose a new unused practice name consistently.

Windows PowerShell
New-Item -ItemType Directory -Path "$HOME\umicom-git-practice"
Set-Location "$HOME\umicom-git-practice"
Linux Bash
mkdir "$HOME/umicom-git-practice"
cd "$HOME/umicom-git-practice"
Git commands — either system
git init -b main
git status

The new local repository starts on main. It has no commits yet. [init]

Step 2 — create a harmless text file

Windows PowerShell
"My first Git lesson." | Set-Content -Path "learning-note.txt" -Encoding utf8
Get-Content "learning-note.txt"
Linux Bash
printf '%s\n' 'My first Git lesson.' > learning-note.txt
cat learning-note.txt
Git commands — either system
git status

Look for learning-note.txt under untracked files. Git sees the file, but it has not yet been selected for a commit. [status]

Step 3 — stage and inspect it

Git commands — either system
git add -A
git status
git --no-pager diff --cached

Now the file should appear under changes to be committed. Read the staged text. For this tiny exercise, the note should be the only selected file. [add] [diff]

Step 4 — create the first local commit

Git commands — either system
git commit -m "docs: add my first Git practice note"
git log -1 --oneline
git status

The message explains the change. The displayed commit ID is generated by Git; your ID will differ from any teaching illustration. Nothing has been uploaded yet. [commit] [log]

Step 5 — create a private remote under your own GitHub account

Check gh auth status to confirm the account. The next command creates a new private repository called umicom-git-practice for that account and adds it as origin. Do not use an Umicom organisation path for this exercise. If the name already exists, stop; use the existing practice repo or choose a different unused name. [gh-create]

Git commands — either system
gh auth status
gh repo create umicom-git-practice --private --source . --remote origin
git remote -v
git push -u origin main

The first push sets main’s upstream with -u. Later pushes can use git push origin main. Visit your practice repository on GitHub and confirm the note and commit are visible. [push]

Step 6 — change the file

Windows PowerShell
"I can now add, commit and push." | Add-Content -Path "learning-note.txt" -Encoding utf8
Get-Content "learning-note.txt"
Linux Bash
printf '%s\n' 'I can now add, commit and push.' >> learning-note.txt
cat learning-note.txt
Git commands — either system
git status
git --no-pager diff
git add -A
git --no-pager diff --cached
git commit -m "docs: expand my Git practice note"
git push origin main
git status

The first diff shows unstaged edits; the cached diff shows the staged version. If you edit again after staging, run git add -A again before committing the new content. Staging is not a live link to your editor. [record] [diff]

Step 7 — learn one safe correction

If you accidentally stage the note too early, this removes it from the next commit without discarding its working-file edits:

Git commands — either system
git restore --staged learning-note.txt
git status

This exercise has existing commits, which the command uses as its reference. Restage it when ready. Do not remove --staged: restoring a working file is a different operation. [restore]

5. Clone the complete Umicom project

Cloning creates a new local checkout from an existing remote. You need read access to the parent and its private child repositories. Use an unused destination. If your existing checkout is already present, use the update instructions instead. [clone]

Windows — first checkout

Windows PowerShell
New-Item -ItemType Directory -Path "C:\umicom" -Force
Set-Location "C:\umicom"
git clone --branch main --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
Set-Location "C:\umicom\Umicom-Applications"
git status
git submodule status --recursive

Linux — first checkout

Linux Bash
mkdir -p "$HOME/umicom"
cd "$HOME/umicom"
git clone --branch main --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
cd "$HOME/umicom/Umicom-Applications"
git status
git submodule status --recursive

--recurse-submodules also initialises the submodule checkouts. It does not mean “put every child on its latest main”. The parent’s recorded revisions are the starting snapshot. Detached child checkouts are therefore expected. [clone] [submodule]

If you cloned without the submodule option

From the clean parent checkout, complete the missing children with:

Git commands — either system
git submodule update --init --recursive --checkout

Do not use this as a repair for a checkout containing uncommitted or unpublished child work. --checkout requests the recorded commits and may detach children that were previously on branches. [submodule]

See the actual list, not a guessed list

Git commands — either system
git config --file .gitmodules --get-regexp "^submodule\..*\.path$"

The catalogue in this guide follows the 25 direct paths currently in the parent’s .gitmodules. A future module must be added to the guide when it is added to that file. The catalogue does not claim to enumerate unrelated repositories elsewhere on your computer. [gitmodules]

6. Make one small Framework documentation change

Use this optional exercise only with the maintainer’s agreement: unlike the personal practice exercise, it changes the real Framework repository. It demonstrates why you later publish the parent as well. To avoid unnecessary project files, you can instead apply the same steps to a genuine small documentation correction.

Step 1 — prepare Framework before editing

Windows PowerShell
Set-Location "C:\umicom\Umicom-Applications\framework"
git status
Linux Bash
cd "$HOME/umicom/Umicom-Applications/framework"
git status

Complete the branch checkpoint if the checkout is detached or on another branch. When safe:

Git commands — either system
git switch main
git status

If clean and starting new work, update with the fast-forward-only pull from lesson 3. If you already have an intentional batch on main, review that batch instead of pulling first.

Step 2 — create a note in your editor

Use an unused filename docs/git-practice-note.md. If it already exists, read it first and choose a different name rather than replacing someone else’s file. On Windows, open it in Notepad; on Linux, use Nano or your preferred text editor.

Windows PowerShell
notepad ".\docs\git-practice-note.md"
Linux Bash
nano docs/git-practice-note.md
Text to save in the note — not terminal commands
# Git practice note

I check the repository and branch before committing.
I publish Framework before the parent repository.

In Notepad, save the file and close the window. In Nano, use Ctrl+O, Enter, then Ctrl+X. Confirm that the file is saved as .md, not .md.txt. Open the saved file to check it.

Step 3 — inspect, stage, commit and push Framework

Git commands — either system
git status
git --no-pager diff
git add -A
git --no-pager diff --cached
git diff --cached --check
git commit -m "docs(framework): add Git practice note"
git push origin main
git status

Before the commit, only the agreed changes should be staged. A new untracked file does not appear in ordinary git diff; review it in your editor and in the cached diff after staging. Stop on any failure except the no-change case explained below. [diff] [status]

Step 4 — record the child revision in the parent

Follow the parent publication lesson. A parent status of framework (new commits) is expected after the Framework commit; it means the parent has not yet recorded the newer revision. It does not mean your Framework push failed. [submodules-book]

Lesson

7. The daily routine and the commit message

The same routine applies in each repository. Inspect first, attach to main safely, review the intended changes, stage, commit and push. There is no need to create empty commits in unchanged repositories. Use a default message when saving a mixed development update, and a more specific message when the change is known.

MessageUse it for
chore(framework): save current development changesA general Framework development update.
chore(studio): save current development changesA general Studio update. Replace the scope with the actual repository.
fix(framework): reject invalid inputA real defect correction.
docs(framework): explain Git publicationA documentation change.
test(trader): cover invalid order inputA test change.
chore(applications): update repository lock and submodule revisionsThe parent’s integration and revision update.

These prefixes are a suggested message convention, not special Git commands. Do not say “tests passed”, “qualified” or “released” in a message unless the relevant evidence exists. For one feature spread across repositories, keep the messages related but explain what each repository actually changed.

Two normal results: nothing to commit, working tree clean means there is no new snapshot to create; continue to the push if main may have unpublished commits. Everything up-to-date means the specified push needed no remote update. Neither result by itself checks a detached checkout against the branch you pushed. [commit] [push]

For this guide, clean read-only children can remain at the parent’s pinned commits. Use the recipes below for repositories you intend to publish from main. Switching every untouched child to a different main revision can itself change the parent’s dependency selection and requires review and qualification.

8. Every Umicom submodule: individual commands

Work through Framework first, then the applications you changed. All 25 direct submodules are listed so none needs to be guessed. Each recipe includes a starting status check, git switch main, another status check and a default message. These commands assume the repository exists and has passed the branch checkpoint. [gitmodules]

Pause after the first status command. If it says detached HEAD or names another branch, use lesson 3 before executing git switch main. If a directory change fails, stop: the following Git commands would otherwise run in the old directory.

At the second status, expect On branch main. At the status after staging, check every filename. If git diff --cached --check prints an error, do not commit. If it prints nothing, that check succeeded; it is not a compiler or test run. Only push changes you have reviewed and qualified as required. [diff]

Lesson

9. Publish the parent repository last

Only start after every changed child repository has been committed and successfully pushed. The parent must record published child revisions. Finish the required build and tests for the exact source combination you intend to record. [submodules-book]

Step 1 — check the parent and child working trees

Windows PowerShell
Set-Location "C:\umicom\Umicom-Applications"
git status
Linux Bash
cd "$HOME/umicom/Umicom-Applications"
git status

The parent is normally already on main. If it is not, use the branch checkpoint before switching, especially when it already contains intended edits. Then:

Git commands — either system
git switch main
git status
git submodule foreach --recursive 'git status --short'

The last command prints each initialised child name and any pending file changes. Child file changes must be finished first. A different recorded revision in a containing repository also needs a containing commit; work from the inside out. This is a built-in Git inspection command, not an automatic commit loop. [submodule]

Step 2 — update the Umicom repository lock

The following is an Umicom command, not a Git command. Use the native tool from your successful local build. It must finish successfully before the next step. The dot means the current parent directory. Do not replace a missing tool with a hand-edited lock file. [lock]

Windows PowerShell — run from the parent directory
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .
Linux Bash — run from the parent directory
./build/headless-debug/bin/umicom repo lock .

The Linux command above assumes you used the existing headless-debug preset. If your successful build used a different preset, use that build directory’s bin/umicom. Do not run a Windows executable on Linux or copy a Windows build cache there. The build-tool path is separate from Git’s own submodule references. [presets]

Native tool not built yet?

Complete the project’s toolchain setup and build qualification first. The optional commands below show the named build locations; they are not a replacement for installing the required compilers, dependencies and GUI libraries. A failure means stop, not skip the lock.

Windows PowerShell — only if the required native tool is missing; run one line at a time
& "C:\msys64\ucrt64\bin\cmake.exe" --preset windows-ucrt64-all-debug -DUMICOM_BUILD_NATIVE_TOOL=ON
& "C:\msys64\ucrt64\bin\cmake.exe" --build --preset windows-ucrt64-all-debug --parallel 2
Linux Bash — only if the required native tool is missing; run one line at a time
cmake --preset headless-debug -DUMICOM_BUILD_NATIVE_TOOL=ON
cmake --build --preset headless-debug --parallel 2

Step 3 — stage and review parent changes

Git commands — either system
git add -A
git status
git --no-pager diff --cached --submodule=log
git diff --cached --check

You should see the intended parent files and the changed child references. For example, the earlier naming update changed the parent test integration, its qualification guide and the Framework reference. Do not expect the entire Framework source diff to be duplicated in the parent commit.

Step 4 — commit and push

Git commands — either system
git commit -m "chore(applications): update repository lock and submodule revisions"
git push --recurse-submodules=check origin main
git status

--recurse-submodules=check refuses the parent push if required changed child commits cannot be found through the child remotes it checks. It does not commit or push the children for you, and it is not a guarantee that every future recipient has permission to those remotes. [push]

Step 5 — final checks

Git commands — either system
git status
git submodule status --recursive
git submodule foreach --recursive 'git status --short --branch'

No changed-file entries should remain for the work just published. In git submodule status, a leading space means the checked-out child matches its recorded revision; + means it differs, - means it is uninitialised, and U indicates a conflict. Any unexpected marker needs investigation. [submodule]

Branch ahead/behind information uses locally stored remote-tracking information. For a direct remote comparison, run these inside the particular repository being checked:

Git commands — either system
git branch --show-current
git rev-parse HEAD
git ls-remote origin refs/heads/main

The first command must print main for this main-publication check. Compare the full hash from the second command with the first field of the final command’s output. Equal hashes mean the checked-out main and the remote main agree at that moment. No remote output or an error is not confirmation. [ls-remote] [rev-parse]

Lesson

10. Clone or update on another machine

Think of the handover as two separate actions: send from machine A, receive on machine B. Publishing only Framework is not enough for a second machine to reproduce the suite; publish the parent’s recorded selection too. Do not copy build/, credentials or your entire .git directory between systems.

Machine A — finish publication

Commit and push the changed child repositories, run the native lock command, commit and push the parent, and check the final statuses using lessons 8–9. Record the parent identifier:

Run from the parent repository on machine A
git rev-parse HEAD

A later authorised push by somebody else may make remote main newer. Matching this exact recorded parent hash is how you identify the particular handover snapshot, rather than assuming that “latest” never changes.

Machine B, with no checkout yet

Install/sign in on that machine using lesson 2, then use the complete Windows or Linux clone in lesson 5. A fresh clone’s recursive child revisions follow its parent. Compare the parent hash with machine A; if newer upstream work has arrived, investigate the intended snapshot rather than forcing a branch backwards. [clone]

Machine B, with an existing checkout — inspect before updating

Windows PowerShell
Set-Location "C:\umicom\Umicom-Applications"
Linux Bash
cd "$HOME/umicom/Umicom-Applications"
Git commands — either system
git status
git submodule foreach --recursive 'git status --short --branch'
git submodule status --recursive
Receiving-checkout condition: all earlier local work must already be saved and published. Stop if there are edited/untracked files, unfinished operations, unpushed commits or an unexplained + child revision. A clean detached child can still contain a commit you created; do not assume clean means published. If you have only used this checkout to receive/build and never made local changes, continue.

Machine B — update the parent, then the recorded children

After the branch checkpoint and the receiving-checkout condition, run one line at a time. The examples are repeated for both systems so the correct root is visible.

Windows PowerShell
Set-Location "C:\umicom\Umicom-Applications"
git switch main
git status
git pull --ff-only --no-recurse-submodules origin main
git submodule sync --recursive
git submodule update --init --recursive --checkout
git status
git submodule status --recursive
Linux Bash
cd "$HOME/umicom/Umicom-Applications"
git switch main
git status
git pull --ff-only --no-recurse-submodules origin main
git submodule sync --recursive
git submodule update --init --recursive --checkout
git status
git submodule status --recursive

The pull advances the parent only when it can fast-forward. Sync refreshes registered child URL settings from the current .gitmodules; it does not download source changes by itself. Update selects the commits recorded by the parent. Stop if either operation fails. [pull] [submodule]

Do not add --remote to the update command for this handover. That asks for child remote-branch tips instead of the parent’s recorded selection. Likewise, switching every child to main afterwards may change the just-reproduced snapshot. Leave read/build-only children pinned; switch only the repositories you are about to develop in, using lesson 3. [submodule]

Confirm the received snapshot

Git commands — either system
git rev-parse HEAD
git submodule status --recursive

Compare the parent identifier and child identifiers with machine A’s intended snapshot. If both match and the working trees are clean, the tracked source selection matches. Ignored build files, local configuration and machine-specific runtime dependencies are not transported by this comparison.

Reconfigure and rebuild on machine B using its own toolchain and build directory. A source update is not an installation. Do not run repo lock . just to receive an existing snapshot: the parent already carries the published lock. Changing dependency revisions for development is a separate, reviewed change.

Lesson

11. Read the result: continue or stop

Message or situationMeaning and next action
Already on mainNormal. Continue after checking the intended changes.
nothing to commit, working tree cleanNo new commit is needed. Push existing main commits if necessary.
Everything up-to-dateThe specified branch push required no change. A detached checkout is not validated by that message.
HEAD detached at ...Use lesson 3 before development. It is normal for receiving/build-only submodules.
Directory does not exist / not a git repositoryStop immediately. Check the path and clone/initialisation status. Do not continue in the previous directory.
Unknown author identitySet your own Git name and email in lesson 2, then retry the commit.
Authentication failed / permission deniedUse gh auth status, confirm account and repository access. A web password is not the Git HTTPS authentication method.
Push rejected / non-fast-forwardFetch and inspect as below. Never force-push to make the error disappear.
Changes would be overwritten by checkout or mergeStop. Preserve the current files. Do not force-switch, reset or clean the directory.
framework (new commits) in the parentRecord the intended child commit after its successful push. Use the parent lesson.
A child shows modified contentCommit inside that child first. Parent staging cannot turn child file edits into a child commit.
Native umicom tool not foundComplete the required build or use the actual successfully built native-tool path. Do not skip the Umicom lock step when publishing changed revisions.
Remote protection requires a different workflowStop and ask the maintainer. Do not bypass required reviews, checks or permissions.
A test or build failsA Git commit does not fix or certify it. Keep the failure evidence and correct the source before qualified publication.

These are interpretation rules, not an automatic recovery script. The relevant command contracts are linked here. [status] [commit] [push] [github-auth]

Rejected push: inspect before choosing a repair

Git commands — either system
git fetch origin
git status
git log --oneline --left-right main...origin/main

In this comparison, < marks commits found only on local main; > marks commits found only on origin/main. If both appear, history has diverged: preserve both sides and ask for a reviewed integration. If only remote commits exist and there are no pending local changes, the fast-forward-only pull can advance your branch. If local commits exist, do not reset them away. [log] [pull]

Avoid the earlier folder-move problem

A Git folder rename is not required just to publish files already at their correct paths. If you use git mv, confirm that the source exists and the intended destination does not already exist as a directory. Otherwise the source may be placed inside that directory, producing an unintended nested folder. Do not repeat a migration command after merging its replacement files. [mv]

Review actual paths with git status --short and your file manager. Keep any backup outside the repositories. Once the working tree contains the reviewed final arrangement, git add -A stages that arrangement. Git’s rename display is based on change detection; a separate rename command is not the only way to record a move. [add] [diff]

Commands deliberately excluded from this beginner workflow

Do not use force-push, a hard reset, forced switching, branch deletion or destructive cleaning as a default response to an error. There is no script here that commits every directory automatically, no case-sensitive confirmation word to type, and no assumption that “no output” always means success: read the preceding command result.

Lesson

12. Check your understanding

1. You saved a file in an editor. Is it on GitHub?

No. Save changes the working file. Stage, commit and push are separate steps.

2. Framework was pushed, but the parent still shows “new commits”. Is the push broken?

Not necessarily. The parent still needs to record the new Framework revision and publish its own commit.

3. Trader is clean but detached. Is it safe to assume main contains its commit?

No. Compare history using the branch checkpoint before switching. Clean means no pending file edits, not necessarily no unpublished commits.

4. When does the default commit message create an empty commit?

It does not. Ordinary git commit refuses to create a new commit when nothing is staged; do not add an empty-commit option just to make every repository show a new hash.

5. Should the second machine use submodule update --remote to reproduce the first machine?

No. Use the parent’s recorded child revisions for reproduction. Remote-branch tips are a different dependency selection.

6. What belongs last in the publishing order?

The parent, after changed children and their own changed dependencies are published.

7. Does main matching GitHub prove the applications work?

No. Version-control synchronisation and runtime qualification are separate checks.

8. You edited a file after staging it. What should you review?

Review the final file and stage it again if that new content belongs in the commit; inspect the cached diff before committing.

Practice completion: create two commits in your personal repository, confirm them on GitHub, and read the second revision on another checkout. Then explain in your own words why a Framework change requires a parent integration commit. Do not mark a real application release complete merely because this exercise passed.

Lesson

13. The short reminder

Before editing: correct directory → status → safe switch to main → status → update only when clean. After editing: review/test → add → inspect → commit → push. For Umicom: changed children first → native lock → parent last.

Inside one repository, after the branch checkpoint
git status
git switch main
git status
git add -A
git status
git diff --cached --check
git commit -m "chore: save current development changes"

The default message above is a fallback. Use the scoped defaults in lesson 8 for Umicom. The parent uses its own lock and push-check steps in lesson 9. Do not treat this short reminder as permission to skip an error or an unknown detached state.
