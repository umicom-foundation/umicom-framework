Learn with Umicom

Umicom Desk · System Centre

Get to know your desktop
and the computer behind it

Open a few applications, take a fresh look at memory and processes, and learn what the numbers can—and cannot—tell you. Then explore an explicit way to start Umicom Desk inside an existing Linux graphical session.

Start with observation. System Centre is read-only. It does not end processes, change network settings, mount a disk, install updates or reboot your computer. The Linux launcher later in this lesson opens Desk only when you ask it to.

You can follow the first part on a Windows build of Umicom Desk or on Linux. The second part is for Linux only. It needs a working Linux version of Desk and an existing graphical session; it does not turn the small recovery system from the previous lesson into a graphical operating system.

Part one · Learn by looking

1. Take your first look

Imagine that Umicom Studio is open while you are also using a Notes project. You would like to know which programs are running and how much memory is available. You do not need to change anything to answer those questions.

Open the panel

First finish the normal build of your Umicom applications. In File Explorer, open the folder below and double-click umicom-desk.exe.

C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin

In Desk, choose Open System Centre. The new window has four tabs: Overview, Processes, Network and Boot checks. Your existing launcher, application controls, shared contexts and saved-workspace controls remain in Desk.

The panel initially says that no capture has been taken. Opening the window does not collect a report. Leave Filesystem path blank for the default volume and choose Refresh.

While the capture is running, the Refresh button is temporarily unavailable. Any older values still on screen are labelled as belonging to the previous capture. When the capture finishes, read each tab's status rather than assuming that every source was available.

Three different messages

Available means that this source was read successfully. Access denied means that the host refused that read. Not present on this host means that the requested information was not found. None of the last two messages means “the answer is zero”.

The panel does not refresh on a timer. You choose when to take another observation, and no report is saved automatically.

2. Read memory and CPU without guessing

Memory: total is not the same as available

The Overview tab shows total memory and memory available according to the host's native measurement. It displays whole mebibytes, written MiB; one MiB is 1,048,576 bytes. The text report retains the underlying byte counts.

On Linux, available memory is an estimate that includes memory the kernel expects to reclaim for new work. It is not simply a count of completely unused pages. The kernel documentation explains the difference between MemAvailable and other memory fields.[1]

A value observed in a container, WSL environment or virtual machine belongs to the view exposed there. Do not automatically treat it as the memory allowance of one application or as a complete measurement of the physical computer.

CPU: the first reading sets a starting point

After the first Refresh, the CPU section asks for another capture. This is expected. A processor's accumulated counters need two observations before the work done between them can be calculated.

Wait a moment, use an application normally, then choose Refresh again. The displayed percentage covers the interval between the two captures. It is not an instantaneous reading and it is not the CPU use of a selected process.

A simple example

Suppose the counters increase by 200 ticks in total, with 50 of those classified as busy by this adapter. The interval result is 25.00%. If the counters go backwards or there is no measurable interval, the panel establishes a new baseline instead of inventing a percentage.

The Linux calculation excludes idle and I/O-wait ticks from busy time. On Windows, this adapter declines CPU reporting when more than one processor group is active: the underlying timing call is group-limited on those very large hosts.[1][2] Memory and the other sources can still be read independently.

3. Find an application in the process list

A process is a running instance of a program. Open Processes and look for an application you recognise. The list includes a numeric PID, its parent's PID, a short name and any available start identity.

The short name is a display label, not a command that the panel can execute. Names containing control characters or characters outside this adapter's display subset are sanitised. The collector does not read process command lines, environment variables or credentials.

A PID can be used again after a process exits. For that reason, an available start identity is shown separately. Its units depend on the host; compare it only within the same host and capture system. On Linux, the resident-memory figure is an estimate, not a complete accounting of private memory.[1] The Windows adapter deliberately leaves that figure uncollected rather than requesting extra memory-reading access.

Check the counts above the list

The collector keeps at most 128 rows, ordered by PID, and inspects at most 4,096 candidate processes. If the scan limit is reached, the displayed observed count is not a total for the machine. Processes may also finish between enumeration and reading; those cases remain visible in the unreadable-or-exited count.

Open a harmless application, refresh the panel, close that application normally, and refresh again. This is a useful way to see why a snapshot must have a clear age. There is intentionally no “kill” button in this panel.

4. Separate network counters from connection tests

The Network tab lists up to 32 interfaces. Each interface has accumulated received and sent byte counters. An interface might represent a physical adapter, a virtual adapter or the local loopback path.

These are totals for the interface's counter lifetime, not a current transfer speed. For example, a counter changing from 1,000 to 1,600 bytes indicates an increase of 600 bytes. Without the corresponding time interval, it is not a bytes-per-second rate.

A non-zero counter does not prove that the Internet is reachable, that a website is healthy or that a brokerage connection works. This panel does not ping a server, inspect packets, collect IP addresses or change an interface.

Inspect one filesystem

Return to Overview. To inspect a different local filesystem, type an absolute path into Filesystem path, then refresh. An absolute path starts from the root of a drive or filesystem rather than from whichever folder an application happens to be using.

HostExampleBlank-field default
WindowsC:\umicomC:\
Linux/home/

The result describes the filesystem containing that path, not the combined size of files beneath the folder. “Available to this user” may differ from all unused space because the operating system can reserve capacity.

Use a local path for this exercise. Filesystem calls can take time, especially on a slow or remote mount. Refresh runs away from the graphical thread, but it does not impose a timeout on the host's filesystem call. A path that cannot be read is reported as unavailable; the application does not substitute zero.

5. Understand an absent boot report

An ordinary Windows or Linux installation will usually have no Umicom boot report. In that case, Boot checks says so. This is not a reason to reinstall anything.

On a Linux system using the earlier Umicom boot foundation, the default report location is /run/umicom/boot.report. The reader checks that report through the existing shared Framework contract. A valid report can show the initial boot state, completed checks, planned checks and the reason recorded by the boot controller.

“Ready” has a boundary. A ready boot report describes those initial checks. It does not prove that a desktop is visible, that an application has opened correctly or that a financial workflow has completed.

This desktop update does not add GTK, a compositor or Desk to the previous diskless image. That guest remains a separate boot-and-recovery exercise. Do not use a displayed report as evidence of a graphical boot that has not taken place.

6. Read the same information as text

The command-line report is useful when you need to inspect the data without opening a window. Run this in PowerShell from the built Applications checkout:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom-system-report.exe"
if ($LASTEXITCODE -ne 0) { throw "The system report could not be produced." }

The output is JSON, a text format that pairs field names with values. An overall successful report can still contain an unavailable source: inspect the status alongside each section. Status 0 means that section was available. Unknown optional process values appear as null.

Large 64-bit counters are written as decimal strings, for example "123456789". That preserves their exact value when another tool's JSON number representation cannot hold every 64-bit integer. Do not remove the quotation marks merely to make them look like smaller numeric fields.

The program writes to the terminal. It creates no report file. Saving or sharing its output is a separate choice: process names and paths may still reveal information about your work, even though commands and credentials are not collected.

Developers can use --fixture-proc for test data. Reports produced that way are explicitly labelled as fixtures. Do not present them as observations of a running Umicom guest.

Part two · Linux session handoff

7. Build the small Linux tools

Here, “session handoff” means that a small launcher replaces its own process with Umicom Desk. It does not replace your operating system, terminate your current desktop, authenticate you or start a display server.

Begin with CMake, Ninja, a C23-capable compiler and Python 3 available in your Linux terminal. The source folders in the examples below mirror the Windows checkout names exactly. On native Linux, replace the two source paths with the corresponding absolute paths on your machine.

set -eu
OS="/mnt/c/umicom/umicomOS"
FW="/mnt/c/umicom/Umicom-Applications/framework"
BUILD="$HOME/umicom-builds/desktop-system"

cmake -S "$OS/desktop" -B "$BUILD" -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DUMICOM_OS_FRAMEWORK_SOURCE="$FW"
cmake --build "$BUILD" --parallel 2
ctest --test-dir "$BUILD" --parallel 2 \
    --no-tests=error --output-on-failure
"$BUILD/bin/umicom-system-report"

This focused build compiles the actual desktop-system code and the canonical boot-report dependency. It is not a full build of the Framework, Desk or the OS image. The two programs appear under $BUILD/bin.

A Windows .exe is not a Linux Desk binary. For the following steps, select an already working Linux installation of umicom-desk, including its normal runtime libraries and resources. Building the two small tools above does not create that installation.

8. Check the session before starting Desk

Run this from your normal user account inside an existing Linux graphical session. Do not run it as root or with sudo. The example Desk path below is a placeholder for your installation, not a directory created by this lesson.

DESK="$HOME/umicom-install/bin/umicom-desk"
LAUNCHER="$BUILD/bin/umicom-desk-session"

"$LAUNCHER" --inspect --desk "$DESK"

The check expects a native 64-bit little-endian ELF executable for the current supported architecture. It refuses a script, a Windows executable, a symlink at the executable path, a set-id executable or a binary writable by other users or groups.

The current session supplies its display information. When WAYLAND_DISPLAY is set, the launcher uses that socket name inside XDG_RUNTIME_DIR. The runtime directory must belong to you and have mode 0700, and the selected socket must belong to you. Otherwise, a local X11 display such as :0 can be used. Remote display and remote session-bus addresses are rejected.

A successful inspection prints:

Native preflight passed. No program or compositor connection has been started.

This checks identity, paths and basic file properties. It does not test whether the display server will accept Desk or whether all graphical libraries are installed. When a check fails, read the explanation and review the selected installation or session. Do not weaken another session's permissions to bypass the check.

WSL can be used for the focused command-line build. A graphical WSL environment must independently satisfy the same runtime-directory and display checks; the launcher does not configure WSLg or promise that every WSL environment will satisfy them.

9. Open Desk deliberately

After reviewing a successful inspection, use --run to request the handoff:

"$LAUNCHER" --run --desk "$DESK"

Desk becomes the launcher process. The parent terminal waits for that process in the usual way and returns when it exits. The launcher does not install an automatic restart, start a second process supervisor or make a system-wide desktop selection.

Framework gives Desk a small, explicit environment: home, the selected graphical backend, an optional local session bus, language and a fixed executable-search path. Inherited library-injection variables and unrelated environment values are not passed on. Inherited descriptors above standard input, output and error are closed at the execution boundary. The working directory becomes your home directory.

The process also sets no_new_privs before execution. Treat this as one restriction, not as a security sandbox or a replacement for trusted application binaries. Desk and the applications it launches still run with your ordinary account's access.

No commands run automatically if inspection or execution fails. An execution failure can mean that a native binary still lacks its required runtime libraries. Fix the installation rather than substituting an unchecked shell command.

10. Prepare a launcher file for review

A .desktop file describes a Linux application launcher. It is metadata read by a desktop environment; it is not a shell script. Its argument escaping has its own rules.[3]

The following command prepares a new review directory. It does not copy Desk, install anything into your application menu, register a login session or change autostart.

mkdir -p "$HOME/umicom-session-reviews"
STAGE="$HOME/umicom-session-reviews/desk-first-review"

python3 "$OS/tools/desktop_session.py" --framework "$FW" stage \
    --desk "$DESK" --launcher "$LAUNCHER" --output "$STAGE"

python3 "$OS/tools/desktop_session.py" --framework "$FW" verify \
    --output "$STAGE"

The directory contains umicom-desk-session.desktop, the Umicom icon and manifest.json. Open them in a text editor or file viewer to inspect the chosen paths. Preparing the stage does not open the application.

The manifest records hashes of the referenced binaries and staged files. A hash is a fingerprint of those bytes, not proof of the author's identity or permission to execute them. Verification detects changed files; it is not an automatic signature policy enforced by the C launcher.

The stage records absolute locations. Moving the directory or rebuilding a referenced binary makes the old review stale. Create a new stage after reviewing the new installation. An existing destination is refused, and a partially written new directory is retained for inspection after a write failure.

For this lesson, continue opening Desk with the explicit command in step 9. Installing a launcher into your desktop's menu is a separate deployment decision. This tool does not perform it for you.

11. Try a short observation exercise

  1. Establish a baseline. Open System Centre and choose Refresh. Explain why the first CPU result has no percentage.
  2. Watch one harmless application. Open a Notes window, refresh, and look for the running program. Close it normally and refresh again. Remember that the program name may differ from its document title.
  3. Test an unavailable path. Enter a clearly nonexistent absolute folder and refresh. Explain the difference between “unavailable” and “zero space”. Restore a real local path afterwards.
  4. Keep boot and desktop evidence separate. Read Boot checks. Write one sentence describing what an absent report or a ready initial report actually establishes.

For the Linux extension, first run --inspect and confirm that it opens no application. Then run --run deliberately. Close Desk normally when finished. A successful handoff shows that the selected Desk ran in your existing session; it does not demonstrate a boot of the separate Umicom OS image.

12. Where this leaves the desktop

You now have a read-only view of the host and a way to review a Linux Desk handoff before using it. The observation service, parsers, report format and launcher checks live in Umicom Framework. Desk contributes a button; the OS checkout contributes a small build entry point and packaging wrapper.

This keeps reusable behaviour available to other applications without copying another system monitor or launcher into each one. It also leaves the independent recovery foundation intact.

A complete Umicom OS desktop still needs its graphical image integration, display-server and login-session choices, persistent-user storage, system-service administration, installation and update/rollback work. Those are not hidden behind the read-only controls in this lesson.
