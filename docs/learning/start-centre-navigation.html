Keep Welcome separate from your documents

A start screen helps people create projects, open recent work and find lessons. It is a view over an application, not a source document. If opening Welcome closes the editor’s active document, a navigation action can accidentally affect unsaved work. Umicom keeps the document owner and the Start Centre navigation state separate.

Use the Studio workflow

  1. Open a C source file and make a small unsaved edit. Select a few characters so you can check the selection later.
  2. Choose Help > Welcome. Studio reveals the existing Welcome content in the retained Editor surface. It keeps the source document open.
  3. Leave Welcome open while ordinary status refreshes occur. The explicit choice should remain visible; a timer should not immediately send you back to the editor.
  4. Choose Return to editor from the Welcome tools row. Check the text, dirty indicator, cursor and selection. Returning does not save the file.
  5. Open or activate a different document. Normal editor presentation resumes for that new document. You can choose Help > Welcome again whenever you need the start screen.

With no ordinary document, the normal view remains Welcome. There is no source to return to, so Return to editor is unavailable. Opening a start screen does not create a project, run a build, connect a model or grant workspace trust. Those are separate explicit actions.

Understand the shared C state

UmiStartCentreNavigation is a small value owned by one workbench. Initialise it to zero. It remembers the last observed document identity and whether the person explicitly requested Welcome. The identity is opaque: Framework does not interpret it as a path or open the file. Studio maps its special welcome-document placeholder to an empty identity before calling the shared API.

UmiStartCentreNavigation navigation = {0};
int show_welcome = 0;
UmiStatus status = UmiStartCentreNavigationUpdate(
    &navigation, "draft.c", UMI_START_CENTRE_SHOW_WELCOME,
    &show_welcome);
/* If status is OK, select the existing Welcome view.
   Keep documents in their current document owner. */

OBSERVE is for normal refreshes. It preserves an explicit request while the active identity stays the same. SHOW_WELCOME records an explicit navigation choice. SHOW_EDITOR clears that choice when an ordinary document exists. An empty SHOW_EDITOR request returns NOT_FOUND. Invalid state, an unsupported action or an identity that exceeds the bounded capacity leaves the state and output unchanged. Keep mutation on the workbench’s owning thread.

Build the complete exercise

The complete example is examples/learning/projects/start_navigation.c. It prints a sequence of view choices without opening a native window or writing documents. Use the following commands from the Framework repository with the UCRT64 tools available. This builds the learning target through the same Framework tree; it does not clone another Framework copy. Stop on a failed command.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B build/start-navigation -G Ninja -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DBUILD_TESTING=ON
cmake --build build/start-navigation --target umicom-learning-start-navigation
ctest --test-dir build/start-navigation -R "^framework[.]learning[.]projects[.]start-navigation$" --output-on-failure --no-tests=error

Expected output starts with Empty workspace: Welcome and Open draft: Editor. Choosing Help Welcome and refreshing the same document both report Welcome. Returning to the editor and activating another document report Editor. These are expected results to verify in your build, not a claim of an executed native workflow.

Qualify the application boundary

A correct value transition does not prove that a GUI remained alive. Studio holds an independent runtime token across native panel publication, then checks it after the visible child changes. The return path also guards against a synchronous observer reopening Welcome before editor restoration completes. Retained buttons from a closed workbench must stay inert.

cmake --build build/windows-ucrt64-all-debug --target umicom-studio-welcome-navigation-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio[.]welcome[.]navigation[.]gtk4[.]" --output-on-failure --no-tests=error

Run those native commands from the Applications repository after configuring Studio’s GTK4 tests. Compare dirty bytes and selection as well as the visible view. A skipped GTK case needs a usable native environment; a headless state test cannot replace it. If Welcome disappears immediately, inspect who changed the active identity. If the window closes during navigation, cancel the pending action and never reuse its retired runtime.
