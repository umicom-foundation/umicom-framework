Validate model-stream deltas

A complete SSE event is a transport record, not necessarily usable model text. Its payload may describe a role, text fragment, usage report, finish reason, error or unsupported action. Framework's local-chat codec now has a private text-stream decoder so transport code can validate those meanings before publishing text.

1. Separate three contracts

  1. The SSE receiver reconstructs one complete event from arbitrary byte fragments.
  2. The provider codec validates that event's JSON fields and copies a bounded delta value.
  3. A response owner checks cross-event identity and order, then decides whether text or a terminal state can be published.

The first two layers do not prove the third. EOF, a finish chunk and an exact [DONE] marker are distinct observations. A transport must also succeed; an error after a partial answer must not be reported as a complete answer.

2. Read a narrow provider profile

The Chat Completions streaming schema describes chunks carrying a completion ID, model and choices with deltas. llama.cpp's server documentation describes its compatible chat endpoint. These references guide the wire format; they do not establish compatibility with your installed server revision.

{
  "id": "local-example",
  "object": "chat.completion.chunk",
  "model": "reviewed-model",
  "choices": [{
    "index": 0,
    "delta": {"content": "Hello"},
    "finish_reason": null
  }]
}

This is an authored fixture, not captured inference output. Framework's current text profile requires a nonempty completion ID, the chunk object type, and a model string matching the requested model. It accepts one choice at index zero. A separate usage-only chunk may have no choices if its usage fields are present and valid.

Each text fragment must fit the existing AI text capacity, including its terminator. An empty string is a valid delta. Missing or null content produces no text. A role, when present, must be assistant. Only stop and length finish reasons are admitted. Length means the output was limited; it should remain distinguishable from a natural stop.

3. Preserve permission boundaries

Tool and function-call fields are refused even when the client did not request them. Audio, explicit refusal content and separate reasoning-content payloads are outside this narrow adapter and return UNAVAILABLE. Ordinary text mentioning a command remains inert text. Decoding never executes commands, loads media, writes files or grants tool permission.

Usage counts must be nonnegative integers within the codec's signed 64-bit range, with total equal to input plus output. These values are server reports, not independently measured billing or execution evidence. A stateful consumer must still decide when a usage report is allowed and whether a second report conflicts with the first.

4. Stage output before admitting it

The decoder builds a local candidate value, reusing the existing strict JSON parser, UTF-8 handling and bounded-copy helpers. Malformed or unsupported input leaves the caller's output unchanged. The candidate becomes visible only after every required field has passed.

/* Framework-internal regression or provider code only. */
AwLocalChatDelta delta;
UmiStatus status =
    AwLocalChatDeltaDecode(request, event_data, event_bytes, &delta);
if (status == UMI_STATUS_OK) {
    /* Validate sequence/identity against the response owner before use. */
}

This private header is not an installed application SDK contract. Applications should use Framework's public services instead of including source-tree internals. The new decoder alone does not enable streaming in the existing local provider.

5. Keep the old request mode intact

The full-response encoder and streaming encoder share one admission function. Both retain request limits, supported roles, JSON escaping and denied tool requests. The existing provider still selects full responses. The separate public stream job selects streaming explicitly and composes shared cancellation, endpoint restrictions and output ownership.

When optional native HTTP/JSON support is absent, the codec reports UNAVAILABLE. It does not create a synthetic response. A skipped optional codec test is also separate from a passing test.

6. Qualify the codec independently of a model

cmake --build build/windows-ucrt64-debug --target umicom-local-chat-delta-test umicom-local-chat-delta-boundary-test umicom-local-chat-delta-offline-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework\.ai_workspace\.delta" --output-on-failure

There are 57 registered cases: 43 JSON fixtures, 13 boundary/request-mode cases and one build of the real offline branch. With native HTTP/JSON support, the expected result is 57 passes. Without it, 56 optional cases should explicitly skip while the offline contract runs. These are expected results; authored tests and successful configuration are not executed runtime evidence.

On failure, preserve the input, selected model and status. Check whether rejection came from framing, JSON syntax, identity, capacity or unsupported content. Do not weaken a permission check simply to admit an unexpected server reply. Extend the supported profile and its tests deliberately.

Continue with request-owned text for the publication layer. The stateful sequencer and private HTTP exchange now compose these layers. Public application worker/UI integration and live server compatibility remain separate unqualified work.

7. Distinguish bad input from exhausted memory

A conversion helper can fail before JSON parsing starts. Returning only a null pointer hides whether input was invalid or allocation failed. The shared codec now carries a separate status through conversion, so chat, health and delta decoders report OUT_OF_MEMORY for either conversion allocation failure while preserving the caller's output.

The fault regression includes the real codec with allocation interception limited to that source file. It fails the input copy and ASCII conversion allocation separately, checks cleanup, and then repeats the same valid request without failure. This avoids depending on json-c's internal allocation order.

cmake --build build/windows-ucrt64-debug --target umicom-local-chat-allocation-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework\.ai_workspace\.json_allocation\." --output-on-failure

The six cases require optional native HTTP/JSON support at configuration. They are authored regression checks, not a claim of executed success. A memory failure should lead to bounded recovery or a clear failure report; it should not be blamed on a model's JSON syntax.
