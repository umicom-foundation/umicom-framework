Keep a coding service alive during file callbacks

A native service may call application code while it is still using its own state. For example, Framework asks a host adapter to write an approved patch. That callback can call Framework again. This is reentry: a second call begins before the first call finishes. It can invalidate a patch array, change its policy or free its owner unless the service defines an explicit boundary.

1. Admit owner state before traversal

The coding assistant checks physical history capacities, its nonzero revision, patch policy, child context metadata, stored task requests and patch integrity before using those records. Patch lookup bounds its query string before comparing it. Failed inspection leaves the supplied destination unchanged.

These checks describe a live object created by the API. They cannot make a dangling pointer or arbitrary memory address valid. The host must retain the service and its borrowed AuthorEngine dependency for the full operation and serialize access.

2. Reserve the next revision before effects

Setting policy, preparing a task, recording a patch, approving, rejecting, applying and reverting all need another service revision. At UINT64_MAX, mutation is refused before history changes or file callbacks. Reading the final accepted state remains possible.

Patch records and the repository context index have their own revision identities. A patch revision is not compared numerically with the service revision as if they were one clock. Each owner enforces its own contract.

3. Block mutation while permitting inspection

During forward and compensation callbacks for apply/revert, valid same-service mutation requests return UMI_STATUS_BUSY. Read APIs can still show task history, the stored patch and a service snapshot. The guard remains active until the outer patch operation returns normally, then is cleared on both success and failure.

/* Inside an adapter callback: inspect, but do not begin another edit. */
UmiAiCodingAssistantSnapshot snapshot;
UmiStatus status = umi_ai_coding_assistant_snapshot(service, &snapshot);
if (status != UMI_STATUS_OK) return status;

/* A request to mutate the active owner must be scheduled after this
   callback returns; the service rejects it as BUSY here. */

The adapter's function slots are copied at entry so changing the original adapter structure does not replace callbacks midway through an operation. Its user_data and everything that callbacks borrow must still remain alive. Callbacks must return normally; escaping with a nonlocal jump bypasses normal guard cleanup.

4. Use checked destruction when lifetime matters

UmiStatus status = UmiAiCodingAssistantDestroyChecked(service);
if (status == UMI_STATUS_OK) {
    service = NULL;
} else if (status == UMI_STATUS_BUSY) {
    /* Keep this handle and its dependencies alive.
       Retry after the outer apply/revert call has returned. */
}

The existing void destroy API remains available. It also refuses to free a busy owner, but cannot return the reason. New lifetime-sensitive code should use the checked form and clear its handle only after success. Passing NULL to checked destruction is accepted.

Destruction does not traverse the task or patch arrays, so a damaged metadata count does not prevent releasing an otherwise live service. This does not authorize passing corrupted allocation pointers to destruction.

5. Keep the limits explicit

This is a callback-reentry guard, not a thread lock. It does not synchronize concurrent threads or independently borrowed child context/catalogue owners. It also does not turn multi-file I/O into an atomic filesystem transaction.

Existing patch compensation attempts can fail. A guard prevents a callback from mutating the service being used; it does not prove that every file was restored. Preserve the operation's failure, inspect affected files and qualify the host adapter's recovery behavior before retrying.

6. Exercise lifetime and identity boundaries

  1. Configure and build Framework with tests enabled.
  2. Run ctest --test-dir <framework-build> -R "^framework[.]ai[.]coding-owner[.]" --output-on-failure.
  3. Verify every mutator refuses an exhausted service revision without callbacks and can accept the last available revision.
  4. Verify malformed owner counts, stored text, history identities and patch queries are refused before traversal.
  5. Exercise nested mutation, checked and legacy destruction, read-only inspection and adapter-slot replacement from read, write and compensation callbacks.
  6. Check that a later ordinary mutation succeeds after the outer operation returns, including after an injected write failure.

The fixtures use memory adapters and never modify a real workspace. Expected results are an explicit refusal for nested mutations, valid read-only inspection and a live service until checked destruction succeeds. Authored fixtures and successful configuration are not proof of native execution or GUI qualification.
