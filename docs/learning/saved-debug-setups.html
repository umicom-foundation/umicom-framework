Save and review a debugger setup

A breakpoint tells the debugger where to pause. A watch is an expression whose value you can inspect while a program is paused. A saved setup keeps these choices so you can restore them during a later Studio session.

The setup stores source locations, enabled flags, conditions, log messages and watch expressions. It does not store a running process, adapter executable, evaluated values or credentials. Conditions and expressions may reveal private project details, so choose a local folder you control.

Save your current settings

  1. Open Studio's Run and Debug surface. Add or edit the breakpoints and watches you want to keep.
  2. In Saved breakpoint and watch setups, enter a descriptive title.
  3. Enter a complete file path in an existing private folder, such as C:\Users\YourName\Documents\debug-parser.json on Windows or /home/yourname/Documents/debug-parser.json on Linux. Replace the example user name with your own. The file must not already exist.
  4. Choose Save new setup. Wait for the result and check the displayed destination. The saved settings were captured when you clicked; edits made later need a new save.

Saving can finish after the window closes. This action creates a new file and never replaces an existing file. If a write fails, a partial new file may remain. Inspect that file and use a new name for the next attempt.

Load, compare and apply

  1. Stop any running or pending debug launch. A setup replaces desired settings for the next session.
  2. Enter the absolute path of your saved file and choose Load and review.
  3. Read the complete Current settings and Proposed settings JSON documents. JSON is structured text: breakpoints and watches are ordered lists. A line is one-based; column zero means no specific column. enabled: false retains a disabled item.
  4. Check every source location, condition, log message and expression. Loading does not check whether a source file exists or whether an expression is safe to evaluate. Keep source paths appropriate for the project and machine you will debug.
  5. Check Replace current breakpoints and watches with the reviewed settings, then choose Apply reviewed setup. Both lists are replaced together. Empty lists deliberately clear the corresponding current settings.
  6. Inspect the refreshed Breakpoints and Watches lists. Restored breakpoints begin unverified, and watches have no previous evaluation result. Starting a later debug session and evaluating expressions remain separate actions.

If a breakpoint, watch, debug session or configuration changed after the review, Studio refuses the old review. Load again and inspect the new comparison. Changing the title or path also discards the displayed approval. Clicking Apply without approval makes no change and requires another review.

Review a reversal

  1. After a successful application, choose Review previous settings in the same panel.
  2. Inspect the comparison with the settings replaced by the last successful application.
  3. Confirm replacement and choose Apply reviewed setup again.

The previous-settings copy lasts only while that panel is open. It restores desired settings, not old process values or adapter confirmation. A later successful application replaces this single retained copy; it is not a permanent history.

Limits and recovery

SituationWhat to do
More than 64 breakpoints or 64 watchesThis setup format refuses the entire capture. It does not silently omit entries. Keep the current settings and reduce them explicitly before saving if appropriate.
File already existsChoose a new name. Save new setup does not overwrite.
Missing, malformed or incompatible JSONCurrent settings stay intact. Select the intended file or save a fresh setup from a known working session.
Path or title edited while loadingThe loaded result is discarded. Choose Load and review again.
Two breakpoints on the same source line with different columnsThe Framework format represents them, but Studio's legacy protocol projection accepts one per source line. Studio refuses such a replacement without changing either current list.
Project moved to a different pathSaved source locations are unchanged. This feature does not remap paths or move source files. Review and adjust a copy of the JSON or recreate the breakpoints before using it.
Window closed while loadingNo loaded settings are applied after close. Reopen the panel and load explicitly.

Use the shared API in another application

Link the Debug owner for in-memory setup and review operations. Link Developer for JSON and native files. The public headers are umicom/debug/setup.h and umicom/debug/setup_document.h.

  1. Capture on the workspace owner thread with UmiDebugSetupCapture, or construct a setup with the typed append operations.
  2. Transfer an independent copy to a worker for UmiDebugSetupSaveNew or load a new owner using UmiDebugSetupLoad. Release it with UmiDebugSetupDestroy.
  3. Back on the owner thread, create a review with UmiDebugSetupReviewCreate and present its Before and After copies.
  4. Immediately before applying, exclude any active or pending native runtime owned by your host. Framework's controller model cannot infer another process owner's liveness.
  5. Call UmiDebugSetupReviewApply after explicit acceptance. Serialize all access. Do not run callbacks or concurrent registry writes during publication.

New fields should be added to the typed settings, validation, strict JSON codec and review presentation together. Keep live process results separate from desired settings. A saved document supplies data; it does not supply authority to execute it.
