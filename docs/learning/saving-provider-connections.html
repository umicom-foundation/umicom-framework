Save provider connection settings

A connection combines a provider name, an endpoint, a model choice and a reference to a credential. An endpoint is the address an adapter will contact. A credential reference names a key in a separate store; it is not the key itself.

Umicom::provider_connections supplies this shared C service. It saves settings through the Data Server, checks edits against the last reviewed revision, and obtains credentials only when the host explicitly requests an enabled connection. It does not authenticate a user, launch a model server or make a network request. Application connection screens and individual remote provider adapters must compose this service.

What is saved

InformationLocation and purpose
IDs, display label, endpoint, model, timeout, enabled stateThe host's local settings database. These are non-secret settings; they are not encrypted by this service.
vault:personal-keyA reference in the same database. The part before the colon selects a registered secret provider; the part after it is that provider's key alias.
Actual API keyA separate credential store, such as the native secret provider. It is never passed to the settings save API.
Application/profile scopeA namespace that keeps settings separate. It does not grant access rights or independently encrypt a user's data.

1. Choose the storage owner

Link your host target to Umicom::provider_connections and include umicom/provider_connections/connections.h. Open a Data Server with umi_data_server_create_sqlite at an absolute per-user path chosen by the host. Do not derive the path from the process's current directory. Keep the file outside source checkouts and published content. A memory Data Server is useful for temporary work and lessons, but loses its settings when destroyed.

Call UmiProviderConnectionsOpen(server, "studio", "owner", &store). The application and profile aliases each allow 48 characters: a lower-case ASCII letter followed by lower-case letters, digits, dots, underscores or hyphens. Do not use an email address or a password as an alias. Keep the Data Server alive while this store exists.

2. Read before editing

Allocate UmiProviderConnectionSnapshot with calloc in hosts with small thread stacks, then call UmiProviderConnectionsRead. An empty scope has zero records and revision zero. A revision is a number identifying the saved state you reviewed. Preserve it while the user edits their draft.

UmiProviderConnection connection = {0};
strcpy(connection.id, "personal");
strcpy(connection.provider_id, "example");
strcpy(connection.label, "My provider connection");
strcpy(connection.endpoint, "https://api.example.invalid/inference");
strcpy(connection.model, "example/model");
strcpy(connection.secret_reference, "vault:personal-key");
connection.route = UMI_PROVIDER_CONNECTION_HTTPS;
connection.timeout_ms = 30000U;
connection.enabled = false;

uint64_t saved_revision = 0U;
UmiStatus status = UmiProviderConnectionsPut(store, &connection,
    false, snapshot->revision, &saved_revision);

The example address is deliberately non-working. The assignments above copy known short literals; bound and validate user-entered text before copying it into fixed fields. Check every returned status before proceeding. Passing false creates a new record and rejects a duplicate ID. Passing true replaces an existing record and rejects a missing ID. Successful saves return a new revision. Failure leaves the output revision unchanged.

3. Handle competing edits

If another window saves first, your save returns UMI_STATUS_BUSY. Read again, show the latest values beside the user's draft, and let them review the conflict. Do not automatically retry with the new revision, because doing so could overwrite their other window's work. The revision belongs to the whole application/profile scope, so even an edit to another connection requires a fresh review.

Removal uses UmiProviderConnectionsRemove(store, id, reviewed_revision, &saved_revision). Removing the last record preserves the revision. Removing and recreating an ID therefore cannot make an older draft valid again. Removing settings does not remove or revoke a credential, which might still be used by another connection.

4. Prepare an approved request

  1. Unlock the host's local profile through its authentication flow. This settings service does not perform that step.
  2. Have the provider-specific adapter approve the endpoint and authentication method. URL syntax alone does not establish that a destination is trustworthy. An IBKR TWS session, for example, must not be treated as a generic API-key connection.
  3. Register a secret provider belonging to this application/profile scope. For native storage, create it with umi_secret_provider_platform and add it to the registry as vault. Successful registry registration transfers provider ownership to the registry. Check each status; unsupported secure storage must not fall back to a plaintext database.
  4. Store or replace a credential only after the user explicitly requests it. Secret-store writes and settings writes are separate operations. If saving settings fails after saving a key, report that distinction and let the user decide whether to keep or remove the key.
  5. After reviewing and enabling the saved connection, call UmiProviderConnectionsAcquire with the reviewed revision. It rejects disabled or stale settings before invoking a credential callback. Settings reads and saves never look up credentials.
  6. Use the returned settings and secret together. Do not fetch a different endpoint afterwards. The adapter must verify TLS, apply its own destination policy and prevent credential forwarding to redirected destinations. Clear the secret buffer with umi_secret_clear after use, including failed requests. Never log it.

Acquisition ends the database transaction before calling the credential provider. A later edit affects future acquisitions, not an operation already prepared. The host must coordinate cancelling pending work when the user locks their profile or disables a connection. Remote requests still send authentication and selected content to that provider; local key storage does not make remote processing offline.

5. Configure a local model

Use UMI_PROVIDER_CONNECTION_LOOPBACK and an endpoint such as http://127.0.0.1:8080/v1/chat/completions. The port must be between 1024 and 65535, and the secret reference must be empty. This prevents this route from obtaining a stored API key. The host still needs a compatible, trusted server and a transport adapter. This service does not download models, start processes or verify which process owns the port.

Remote endpoints use lower-case https:// with an ASCII host, optional port, and a restricted path. Query strings, fragments, user information, percent escapes, backslashes and dot path segments are rejected. Model identifiers allow ASCII letters, digits, dots, underscores, hyphens, slashes and colons; an empty model means the adapter must obtain that choice elsewhere. Labels accept single-line UTF-8. Never put credentials in any of these fields.

Recovery and limits

ResultResponse
BUSYAnother edit changed the scope or another operation owns the database transaction. Preserve the draft, reread when available, and review.
PARSE_ERRORSaved metadata is damaged or inconsistent. Preserve the database for recovery; do not overwrite it with an empty catalogue.
CAPACITY_EXCEEDEDThe scope has 32 records, a field exceeds its limit, the Data Server has no space, or a secret buffer is too small. Explain which operation failed and retain the draft.
INVALID_STATE after a database failureThe store could not confirm rollback. Stop using it, join its workers, close it, and recover or reopen the Data Server before creating a replacement. Do not report the edit as saved.
Missing credential or unavailable secure storeKeep the non-secret settings. Ask the user to reconnect or provision the missing credential through the host's secure flow.

The index is authoritative; records outside it are not listed. A new save refuses to overwrite an orphan record with the same ID. External database edits and file rollback bypass the service's revision protocol. Treat the local database as host-controlled storage, not as an authenticated audit log.

Join all users before destroying the store, registry and Data Server, in that order. Run synchronous database and vault work on the host's owned worker when it could block a graphical interface. The existing integration designer's in-memory connection catalogue remains available; this separate service adds durable, reviewed storage without changing that catalogue's API.

For a small credential-free example, read examples/provider_connections/saved_connections.c. Its expected output is Saved draft: Local model server (disabled). The example uses memory and performs no network or vault operations.
