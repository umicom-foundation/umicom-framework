Reversible Zen layouts in Umicom Studio

A workspace layout records where panels belong. Zen mode selects the existing editor-focused arrangement. A useful toggle must also remember where to return. This lesson follows the native C implementation and explains why selecting a layout, rendering its panels and saving a checkpoint are different operations.

What you will learn

You will trace a menu identifier into Framework, preserve an existing arrangement while changing the active selection, reject transitions during an edit and test a refusal without confusing it with a successful no-op. You need basic C structures, strings and return-status checks. No project build, debugger or language server is required to perform the layout exercise.

Use the existing menu

  1. Open a practice document and enter an unsaved sentence. Select part of that sentence so selection preservation can be checked too.
  2. Choose an existing layout, or create and apply a named canvas through the established workspace controls. Note the layout name and visible panels.
  3. Apply and lock any layout edit. If you are still editing geometry, cancel that edit instead. Zen does not silently commit it.
  4. Choose View → Zen Mode. The command identifier is view.zen. The selected layout becomes umicom.studio.layout.zen; document contents remain with their document owner.
  5. Use the existing command palette shortcut, Ctrl+Shift+P, search for Zen Mode, and invoke the toggle again. This provides an exit path when normal workspace chrome is hidden.
  6. Check that the previous layout is active and its panel arrangement, document text, dirty marker and selection are intact. Save the document separately when you want to keep its contents.
These are acceptance steps for the implemented route. Configuration and registered tests do not demonstrate a working native menu, keyboard shortcut, display or font rendering. Run the native checks on the target GTK environment and record the observed result.

Remember identity rather than duplicate state

The Framework contract lives in workspace_zen.h. Each workspace owns a zero-initialised UmiStudioWorkspaceZenState. Its return-layout field contains an identifier. The layouts themselves remain in UmiUiWorkspaceCustomisation, alongside their existing revision and edit state.

UmiStudioWorkspaceZenState zen = {0};
/* model is an existing, seeded workspace on the same owner thread. */
if (umi_studio_runtime_workspace_zen_can_toggle(model, &zen)) {
    UmiStatus status = umi_studio_runtime_workspace_toggle_zen(model, &zen);
    /* Check status before presenting the selected layout. */
}

The availability query is read-only. The operation repeats validation because a previous availability result is not permission to use stale state. The first toggle remembers the active ID and selects Zen. The second selects that remembered layout and clears the transient return ID. Layout records, context groups and the layout library are not rewritten. In particular, returning does not restore an old copy over newer changes to the same layout.

Handle missing and changed context explicitly

If Zen was selected directly with studio.layout.zen, or restored from a saved layout without an in-memory return ID, the toggle exits to the existing default layout. The same fallback applies when the remembered layout was removed. Framework returns UMI_STATUS_NOT_FOUND if the required existing target is unavailable; it does not recreate a missing layout behind the user's back.

If another layout is selected while Zen is active, the next toggle remembers that newly active arrangement. A return ID is associated with one current session, not a permanent promise to select a layout from an earlier project. Keep one state object with each workspace owner, and do not share it between unrelated models.

An active layout edit returns UMI_STATUS_BUSY. Fixed-size IDs without a terminating zero, duplicate IDs, an invalid active selection and out-of-range counts are rejected before string comparison or array traversal. An exhausted model revision is also refused. In every refusal, both the model and return-state object retain their previous bytes.

Publish native presentation carefully

Studio creates a heap candidate of its existing model and a small candidate return state. Framework validates and toggles these candidates. The established native workspace publisher renders the candidate and projects it into compatibility shell state. Only after that succeeds does Studio commit the new return identity. The original document buffers remain owned by the document adapter throughout the operation.

This separation prevents a failed presentation from recording a return destination for a transition that was not accepted. The native command also rejects unexpected arguments and guards overlapping toggles. It uses the existing weak owner token before accessing the runtime after publication. This does not replace qualification of GTK callbacks, focus and retained widgets on each supported platform.

Build and run the focused checks

Configure the normal product build first. From a configured Framework source checkout, the following commands build and execute the model checks. Run each command separately and stop on an error.

cmake --build build/windows-ucrt64-debug --target umicom-studio-runtime-workspace-zen-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework[.]studio_runtime[.]workspace-zen[.]" --output-on-failure

From a configured Applications checkout, use the native Studio target and its focused selection:

cmake --build build/windows-ucrt64-all-debug --target umicom-studio-zen-menu-test
ctest --test-dir build/windows-ucrt64-all-debug -R "^studio[.]zen[.]menu[.]gtk4[.]" --output-on-failure

The Framework scenarios cover reversible selection, a missing return destination, direct Zen selection, intervening selections, edit refusal, missing required layouts, revision exhaustion and malformed identities. The native scenarios exercise the actual View menu, direct invocation, a custom canvas, argument refusal, an active edit and a retained button after owner destruction. All verify their own state observations; a GTK-unavailable exit is a skip, never a GUI pass.

Diagnose a failed exercise

  1. If the command is disabled, apply or cancel the current layout edit and check that the active and target layouts exist.
  2. If it returns a refusal, retain the status and compare the model before and after the attempt. Do not compensate by clearing an edit or replacing the user's library.
  3. If selection changes but panel visibility or the palette exit path fails, inspect the native publisher and shell projection. A model test alone cannot establish native rendering.
  4. If a document changes, compare its buffer identity, bytes and selection separately from panel geometry. A layout operation must not stand in for document saving.

Saving a layout checkpoint, saving the entire layout library and saving source documents remain explicit, independent actions.
