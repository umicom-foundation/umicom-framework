Read captured boot reports with the Umicom Framework SDK

This short course builds a C23 client that turns an admitted boot report into JSON. JSON is structured text with named fields; another application can read those fields without scraping console sentences. A capture records an observation. It does not prove that a machine is healthy now or that its publisher is trusted.

Lesson 1: choose the right component

Umicom::platform owns report parsing, file admission, validation and semantic comparison. Umicom::boot_report_tools adds JSON presentation using the existing protocol writer. Protocol already depends on platform, so putting the JSON writer dependency back into platform would create a cycle. This separate SDK component keeps dependency direction clear.

The SDK needs public headers and compiled libraries from the same build. Select an installed package that exports boot_report_tools; a copied header alone cannot supply the library. Follow the SDK composition course to qualify the package and its compiler environment first.

Lesson 2: build the standalone example

  1. Install a matching UCRT64 Framework SDK at C:\SDKs\Umicom.
  2. Copy the installed share/umicom/framework/examples/boot_report_json folder into C:\Projects\BootReportJson.
  3. Run these commands separately and stop at the first failure.
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S C:/Projects/BootReportJson -B C:/Projects/BootReportJson/build -G Ninja -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build C:/Projects/BootReportJson/build
ctest --test-dir C:/Projects/BootReportJson/build --output-on-failure
& "C:\Projects\BootReportJson\build\bin\umicom-sdk-boot-report-json.exe"

The teaching program constructs two synthetic observations. Expected JSON has scope equal to captured-boot-comparison, same_source equal to true, and changed_fields equal to ["state","completed"]. These are expected results for your execution, not a claim that your SDK has already passed. The shared branding helper attaches the supplied Umicom icon and stages approved resources.

Lesson 3: load a real selected capture

Include the file and JSON headers, then keep loading separate from formatting:

#include "umicom/platform/boot_report_file.h"
#include "umicom/platform/boot_report_json.h"

UmiBootReport report;
char json[UMI_BOOT_REPORT_JSON_CAPACITY];
size_t length = 0;
UmiStatus status = UmiBootReportLoad(selected_absolute_path, NULL, &report);
if (status == UMI_STATUS_OK)
    status = UmiBootReportJson(&report, json, sizeof json, &length);

Only use json and length after success. They are preserved on refusal. The capacity includes the final NUL byte; the returned length excludes it. The loader accepts a bounded regular file at an absolute path. Parent-directory aliases may be followed, so select a trusted parent directory. File reads can block; interactive programs should use their existing worker service. Neither function writes to the capture.

Lesson 4: interpret comparison honestly

FieldMeaning
schema_versionVersion 1 of this presentation contract, independent of a product version.
same_sourceThe two report source strings match. It does not prove a shared machine or boot.
changed_fieldsChanged semantic fields in mode, state, planned, completed, reason, source order.
before / afterReports in caller-supplied order, without a claim about timestamps.

Changing a source ID can mean a different boot plan. Do not label a higher completed count as a repair across unrelated plans. Keep both snapshots available for review. An empty change list means equal semantic fields, not identical file bytes.

Lesson 5: use the OS console

When configuring an OS SDK consumer, add -DUMICOM_OS_REQUIRE_BOOT_REPORT_JSON=ON to require the component. A missing component then fails configuration. Without that requirement, an older Framework keeps the existing text commands and responds to JSON commands with an explicit unavailable error. No startup operation is substituted.

& "C:\Apps\UmicomOS\bin\umicom-os.exe" --boot-report-json "C:\Captures\boot.report"
& "C:\Apps\UmicomOS\bin\umicom-os.exe" --compare-boot-reports-json "C:\Captures\earlier.report" "C:\Captures\later.report"

An optional --source followed by a lowercase 64-character SHA-256 string checks the selected single report against an expected identity. It is an equality check, not authentication. Exit 0 means the selected reports were admitted and JSON was written; exit 1 means a load, capability, formatting or output failure; exit 2 means unsupported command syntax.

Lesson 6: diagnose and verify

  1. If configuration lacks boot_report_tools, install a Framework package containing this component and select that prefix. Do not combine unrelated headers and archives.
  2. If a report is rejected, check its documented version, exact LF framing, counts, reason and lowercase source ID. See the report format.
  3. If output capacity is insufficient, allocate UMI_BOOT_REPORT_JSON_CAPACITY bytes. Failed formatting does not publish a partial document.
  4. Run the producer tests matching framework.os_foundation.boot_report_json. and the OS tests matching os.boot_report_json_cli. against the actual binaries.
  5. Record configuration, compilation and runtime results separately. Registered tests and a successful CMake configuration do not establish execution.

Exercise: compare equal reports, a starting/ready transition and different source IDs. Then pass malformed and undersized inputs. Explain why a copied byte snapshot is used to test nonmutation: C struct assignment need not preserve padding bytes, even when its members are equal.
