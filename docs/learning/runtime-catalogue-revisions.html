Keep AI runtime observations current

A runtime catalogue describes a provider, a model and the place where they are hosted. It lets applications discover configured choices. The catalogue does not load a model, run inference or authenticate a server. This lesson develops a narrower responsibility: store valid descriptions and refuse observations that refer to an older description.

Prerequisites: bounded strings, callbacks and provider ownership. The examples use the public runtime catalogue API.

1. Separate a record from an observation

A record can say that runtime.local uses model.initial. A health callback starts checking that configuration. Before its result is published, an application replaces the record with model.replaced. Publishing the old result by identifier alone would make the replacement inherit an observation made about something else.

Each successful catalogue write assigns a larger revision number. Read the record before a probe, retain its revision, and require that same revision when publishing the result. An unrelated record can change without invalidating your observation; the comparison is against the selected record, not the catalogue's most recent global revision.

StepRecordResult
ReadInitial model, revision 2Remember revision 2
Replace configurationReplacement model, revision 3New metadata accepted
Publish old healthExpected revision 2, current 3BUSY; replacement unchanged

2. Admit a complete bounded description

Initialize the entire descriptor, then fill required identifiers, display name, model name, provider kind, transport and token limits. The endpoint and health message may be empty. Every character array must have a terminating zero within its capacity. A first character check cannot establish this: an array containing only nonzero bytes has a first character but is not a C string.

UmiAiRuntimeDescriptor descriptor = {0};
/* Fill these from already validated application settings. */
strcpy(descriptor.runtime_id, "runtime.local");
strcpy(descriptor.provider_id, "provider.local");
strcpy(descriptor.display_name, "Local chat");
strcpy(descriptor.model_id, "model.initial");
descriptor.provider_kind = UMI_AI_PROVIDER_LOCAL;
descriptor.transport = UMI_AI_RUNTIME_HTTP;
descriptor.capabilities = UMI_AI_RUNTIME_CHAT;
descriptor.context_tokens = 8192;
descriptor.max_output_tokens = 1024;
descriptor.configured = 1;
descriptor.local = 1;

UmiStatus status = UmiAiRuntimeDescriptorValidate(&descriptor);
if (status == UMI_STATUS_OK) {
    status = UmiAiRuntimeCatalogueUpsertIfRevision(catalogue, &descriptor, 0);
}

The literal strings above fit their arrays; use checked copies for variable input. Expected revision zero means “insert only if absent.” A conflicting record returns BUSY. The catalogue assigns the stored revision rather than accepting a revision supplied by the caller. Configuration is not health: the zero-initialized record is unavailable until an observation is explicitly recorded.

3. Publish a probe against its captured revision

UmiAiRuntimeDescriptor observed;
UmiAiHealth health = {0};
UmiStatus status = umi_ai_runtime_catalogue_find(
    catalogue, "runtime.local", &observed);
if (status == UMI_STATUS_OK) {
    /* Run the application's approved health probe here.
       Populate health only from its actual observation. */
    status = UmiAiRuntimeCatalogueSetHealthIfRevision(catalogue,
        observed.runtime_id, &health, observed.revision);
}

This skeleton deliberately records unavailable health until a real probe fills it. A nonempty health provider identifier must match the current record; an empty identifier remains accepted for compatibility. Do not turn an HTTP success into a claim that the intended model, executable or process owns that endpoint. Those identities require separate evidence.

On BUSY, discard the stale observation and read the current configuration before deciding whether to probe again. Do not repeatedly retry the same result with the new revision: that would erase the protection. A rejected write leaves count, stored records and revisions unchanged. Revision exhaustion returns CAPACITY_EXCEEDED; wrapping a counter would allow an old revision to appear current again.

4. Understand callback and threading limits

Keep one serialized owner for catalogue access. Revision checks handle delayed work and callback-driven changes on that owner; they are not atomic operations and do not make concurrent reads and writes safe. A worker can return a copied result to the owner thread, which then attempts conditional publication.

The AuthorEngine service captures the number of records at the start of a refresh. A callback that appends a record does not extend the current traversal. A callback that replaces the record being probed causes stale publication to fail. Earlier successful updates stay applied if a later record fails, and the caller's output count is unchanged on failure. Keep the service, runtime and provider instances alive across every callback.

5. Inspect and run the focused regressions

Admission tests cover every fixed text field, token bounds and untouched read outputs. Revision tests cover stale writes, capacity, saturation and corrupted private state. Service tests use a deterministic callback to replace or append a record without a model or network.

From a configured Framework source tree with BUILD_TESTING=ON, substitute your build folder and run these commands in order. Stop after a failed command.

6. Extend the exercise

  1. Read one record, update a different record, then publish the first record's health. Explain why its revision still matches.
  2. Publish two results captured from the same revision. The first accepted update advances the revision; the second must be refused.
  3. Fill a text array without a terminator. Confirm admission fails and the previous record remains unchanged.
  4. Design a UI message for stale observations: show that configuration changed and offer a new probe, without calling the replacement unhealthy based on the old result.
Existing unconditional upsert and health setters remain available for explicit owner actions. Prefer conditional updates whenever work was prepared from a prior snapshot. Catalogue availability remains descriptive metadata; runtime startup, readiness, policy and inference have separate contracts.

7. Route health checks by runtime configuration

A provider identifier names an adapter. It is not necessarily an endpoint: two local servers can use the same adapter and even the same model alias on different ports. The original provider-wide health callback receives its adapter instance, but no runtime descriptor. Keep it for provider-wide observations. Use UmiAiAuthorEngineRefreshRuntimeHealth when an application must choose a probe from a runtime's endpoint, model and settings.

static UmiStatus observe_runtime(
    void *context, const UmiAiRuntimeDescriptor *runtime, UmiAiHealth *health)
{
    /* Resolve runtime->endpoint and runtime->model_id against the
     * application's approved adapter configuration. This teaching callback
     * deliberately performs no I/O and reports unavailable. */
    (void)context;
    (void)runtime;
    health->available = 0;
    return UMI_STATUS_OK;
}

size_t healthy;
UmiStatus status = UmiAiAuthorEngineRefreshRuntimeHealth(
    service, observation_time_ns, observe_runtime, NULL, &healthy);
/* Read healthy only after OK. A returned error may follow earlier writes. */

The callback borrows an immutable descriptor snapshot only for the duration of the call. Copy any data needed later. The service initializes health and its provider identifier, then supplies the timestamp when an observation is accepted. The callback is responsible for consent, routing, timeout and transport checks. This API does not itself perform network requests or grant permission to do so.

Return OK to publish an observation, including an unavailable result. Return a transport error or cancellation to stop without publishing that runtime. Earlier accepted records remain updated; the output count stays unchanged on failure. Replacing a probed record causes BUSY and discards its stale result. A record appended during a callback waits for the next refresh.

Refresh owns a guard until it returns. Nested calls through either the legacy or descriptor-aware API return BUSY before callbacks or catalogue writes. This protects synchronous callback reentry; it is not a thread lock. Serialize all service access, keep service/runtime/context alive, and defer destruction until the callback and refresh have returned. The guard is released on failures so a later explicit refresh can gather fresh observations.

The legacy provider API retains its prior error behavior: a failed provider health callback is converted into an unavailable observation. The new descriptor-aware API propagates the callback error and leaves the current record unchanged. Choose the API deliberately; neither result authenticates a process or proves which weights it loaded.

8. Observe partial progress without wrapping identities

A service snapshot lets a view decide whether it needs to refresh. Its revision is a change counter, not a success counter. Consider two health checks: the first updates one runtime, then the second fails. The overall call returns an error, but the view must still be able to discover the accepted first update. Advancing a counter only at the end would hide that change from a view that compares revisions.

OperationService revisionWhat callers may read
Read snapshot10Original health
Accept first runtime health11First observation updated
Second probe fails11Fresh snapshot includes the partial update; output count was not assigned

The AuthorEngine service advances its revision immediately after each accepted health row. A successful empty refresh still advances once, preserving its established behavior. Successful policy changes, runtime registration, session creation, message append and session load each advance the counter. Direct writes through the exposed child catalogue, context broker or conversation archive have independent identities: a service snapshot revision cannot detect every edit made outside the service.

UmiAiAuthorEngineServiceSnapshot before, after;
UmiStatus status = umi_ai_authorengine_service_snapshot(service, &before);
if (status == UMI_STATUS_OK) {
    size_t healthy = 0;
    UmiStatus refresh_status = UmiAiAuthorEngineRefreshRuntimeHealth(
        service, observation_time_ns, observe_runtime, NULL, &healthy);
    status = umi_ai_authorengine_service_snapshot(service, &after);
    if (status == UMI_STATUS_OK && after.revision != before.revision) {
        /* Read current records to redraw the application's existing view. */
    }
    if (refresh_status == UMI_STATUS_OK) {
        /* healthy now describes the completed traversal. */
    } else {
        /* Report failure while retaining any accepted earlier observations. */
    }
}

A 64-bit counter is large, but wrapping it is still an invalid identity transition. Mutating service operations refuse an exhausted counter with CAPACITY_EXCEEDED before changing owned state. During health refresh the service checks before each callback and again before publishing its observation: a callback may legitimately consume a revision through another service operation. A callback's accepted change remains visible even if this prevents its health result from being published.

The checks do not roll back earlier accepted rows, reset exhausted objects or add thread synchronization. Keep serialized ownership. A refused message append also leaves its conversation unchanged when the loaded record has an exhausted revision. Snapshots remain readable at exhaustion; use them for diagnosis. Do not work around exhaustion by resetting the counter on a live object, because observers may still hold older identities.

  3. For a partial-refresh failure, read a new snapshot and inspect both runtime records. The first should change and the second should retain its previous observation.
  4. For saturation, inspect callback counts and before/after data. A refusal should not execute another callback or change the refused record.

9. Edit saved conversation state without losing a newer change

Conversation archives hold bounded records in memory. Each record contains session identifiers, a title, a workspace, classification and a fixed maximum number of messages. Saving a record to disk is a separate, policy-checked operation. Start with umi_ai_conversation_record_init, then use the public archive functions; do not construct or reset the opaque archive itself.

UmiAiConversationRecordValidate checks that every visible text field terminates inside its array, required fields are nonempty, message count stays within capacity, and message roles and classification are recognized. It reuses Framework's bounded snapshot-field validator. Optional conversation IDs, message names and message text may be empty. Unused message slots and nonzero approval flags retain their existing compatibility behavior. Validation does not sanitize generated content, grant persistence permission or authenticate a provider.

Suppose one panel reads a title, while another panel changes the same conversation. An unconditional update is still available for deliberate owner replacement, but a delayed edit should name the revision it read. The conditional API returns BUSY if that record changed. Re-read the current conversation and resolve the conflict with the user's intent; merely retrying the old record with a new revision would overwrite the newer work.

UmiAiConversationRecord *draft = malloc(sizeof(*draft));
if (draft != NULL) {
    UmiStatus status = umi_ai_conversation_archive_find(
        archive, "session.local", draft);
    if (status == UMI_STATUS_OK) {
        uint64_t expected_revision = draft->revision;
        /* This literal fits title; validate variable-length user input. */
        strcpy(draft->title, "Research notes");
        status = UmiAiConversationArchiveUpsertIfRevision(
            archive, draft, expected_revision);
        if (status == UMI_STATUS_BUSY) {
            /* Preserve the draft for review and reload current stored state. */
        }
    }
    free(draft);
}

Use expected revision zero to insert only when the identifier is absent. Any accepted write assigns a fresh archive revision to the stored record; the input record's revision is not an instruction to reset it. A different conversation can change without invalidating this record's revision. Conditional removal similarly needs the selected record's nonzero revision, returns NOT_FOUND for an absent ID, and preserves neighbouring records and their identities.

UmiSnapshotCapture capture;
UmiStatus status = UmiAiConversationArchiveCapture(archive, &capture);
if (status == UMI_STATUS_OK) {
    /* capture.count and capture.revision describe this archive.
     * They are independent of a containing AuthorEngine service revision. */
}

Capture and indexed reads preserve their outputs on refusal. The explicit archive validator distinguishes a valid empty archive from invalid stored state; the older count function returns zero for either an invalid owner or an empty archive. An exhausted owner still permits valid reads but refuses writes before records move or change. These are serialized in-memory contracts, not locks or multi-step database transactions. Keep one owner for archive access.

  3. Edit a different record, then use the original selected record's still-current revision. That edit should remain admissible.
  4. Exercise malformed text, storage capacity and counter limits using the focused fixtures below. Counter fault injection belongs in tests, not application code.

10. Retain health owners until refresh returns

A recursion guard prevents a second refresh from starting, but it does not by itself prevent a callback from destroying the first refresh's service. AuthorEngine now uses the same scoped provider ownership mechanism as generation, while keeping its own health-refresh activity flag.

Both health entry points validate runtime ownership before entering the refresh. Throughout callback traversal and health publication, checked service destruction, registry release, provider insertion and generation on the same runtime refuse with BUSY. The void destroy wrappers retain their active owners. Another service borrowing the same runtime cannot begin a competing refresh. Catalogue edits still use the existing captured-record revision checks: replacing a record invalidates an old observation, while appended records wait until a later refresh.

#include "umicom/ai/authorengine_service.h"

UmiStatus CloseAuthorEngine(UmiAiAuthorEngineService **owner)
{
    if (owner == NULL) return UMI_STATUS_INVALID_ARGUMENT;
    UmiStatus status = UmiAiAuthorEngineServiceDestroyChecked(*owner);
    if (status == UMI_STATUS_OK) *owner = NULL;
    return status;
}

Use this wrapper under the application's lifecycle serialization. On BUSY, retain the handle, return normally from the callback and retry after refresh finishes. UmiAiAuthorEngineServiceCheckIdle reports service activity; NULL is idle. The runtime has a separate idle check because it can also be busy generating a response.

The guard is removed after every normal return, including callback errors, malformed health values and stale-record refusal. Error semantics remain distinct: the legacy provider-health path records a failed callback as unavailable health, while the descriptor-aware probe path returns the probe's error. Partial accepted observations keep their revisions. A new guard does not turn these outcomes into successful inference.

Health callbacks remain responsible for endpoint-specific consent and transport rules. The ownership mechanism does not authorize network access, authenticate a model or synchronize threads. Raw callback calls, direct mutation or freeing of owners, nonlocal jumps and independent concurrent workers remain outside the contract.
