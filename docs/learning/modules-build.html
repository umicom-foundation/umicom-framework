Lesson 40 · 45–90 minutes · ID: foundations.modules-build

1. Understand the idea

A header declares a contract; a source file defines it. Separate translation units must agree on declarations and must be linked together exactly once.

TermPlain meaning
DeclarationThe name and type information promised by a contract.
DefinitionThe implementation or storage for that declared entity.
Translation unitA source file after preprocessing its includes.

Review the first C programme, functions and memory basics. The workshop setup creates a separate build directory; it does not replace your application build.

Before writing code, say what counts as valid input, who owns each object, and what must remain unchanged when an operation fails.

2. Write and inspect the complete example

Open framework/examples/learning/programming/modules_build/main.c. The supplied file is the reference solution. Read it once, then type your own copy in a disposable practice workspace. For a first run you may build the supplied reference unchanged. Do not put deliberately broken examples into the shared Framework source.

The lines beginning with #include provide declarations. main is the programme entry point. EXIT_FAILURE reports a failed check; EXIT_SUCCESS reports success. The helper functions above main implement this lesson’s contract.

examples/learning/programming/modules_build/main.c
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/modules_build/main.c
 *
 * PURPOSE:
 *   Headers, linking and separate compilation.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/

#include <stdio.h>
#include <stdlib.h>
#include "score.h"

int main(void)
{
    unsigned result=999U;
    if (!NormaliseScore(80U,100U,&result) || result!=80U) return EXIT_FAILURE;
    if (NormaliseScore(2U,0U,&result) || result!=80U) return EXIT_FAILURE;
    if (!NormaliseScore(1U,4U,&result) || result!=25U) return EXIT_FAILURE;
    puts("separate header/source linked; 1 of 4 = 25 percent");
    puts("PASS: modules_build");
    return EXIT_SUCCESS;
}
Also create score.h beside main.c
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/modules_build/score.h
 *
 * PURPOSE:
 *   Declare a bounded score normalisation contract.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/
#ifndef UMICOM_LEARNING_PROGRAMMING_SCORE_H
#define UMICOM_LEARNING_PROGRAMMING_SCORE_H
#include <stdbool.h>
/* 0 <= value <= maximum <= 100; output remains unchanged on rejection. */
bool NormaliseScore(unsigned value, unsigned maximum, unsigned *outPercent);
#endif
Also create score.c beside main.c
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/modules_build/score.c
 *
 * PURPOSE:
 *   Implement the small score contract with bounded arithmetic.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/
#include "score.h"
#include <stddef.h>
bool NormaliseScore(unsigned value, unsigned maximum, unsigned *outPercent)
{
    if (outPercent==NULL || maximum==0U || maximum>100U || value>maximum) return false;
    *outPercent=(value*100U)/maximum;
    return true;
}

3. Follow the values through the code

This lab adds score.h and score.c beside main.c. The prototype is included by both caller and implementation so the compiler checks consistency. The header guard prevents repeated declarations within a translation unit. The link step still needs score.c: an include directive does not compile the implementation.

Place your cursor at the first statement in main. Write down the input and expected output of each helper call. When you reach a rejection, check both the return value and any caller-owned output. Do not assume “no crash” means the result is correct.

Bad example — inspect only. The following fragment illustrates a defect or unclear contract. It is not part of the built targets. Examples with invalid memory access, mismatched formats or undefined behaviour must not be run.
Bad pattern: not compiled or executed
/* Do not put ordinary external function definitions in a header included by many .c files. */

Good pattern: use the complete checked implementation above. Explain which precondition or comparison prevents the defect. A naming change alone cannot repair an ownership or bounds error.

4. Build and run it

First complete the workshop configuration once. Then run the following commands one line at a time. Stop on an error instead of continuing with an old executable. The two operating systems use different paths, but compile the same C sources.

Windows · PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-programming" --target umicom-learning-modules-build
& ".\build\learning-programming\bin\umicom-learning-modules-build.exe"
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-programming" --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.modules_build$'
Linux · terminal
cd "$HOME/umicom/Umicom-Applications"
cmake --build build/learning-programming --target umicom-learning-modules-build
./build/learning-programming/bin/umicom-learning-modules-build
ctest --test-dir build/learning-programming --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.modules_build$'

You should see the lesson’s explanatory output followed by:

Expected final line
PASS: modules_build

CTest should report one passing test for this exact filter. “No tests were found” is not success. Compilation errors concern C syntax or declarations; undefined references concern linking; a non-zero test exit concerns observed behaviour.

5. Change one thing and test again

Add a second function to score.h, implement it in score.c and call it in main.c. First omit score.c from a manual compile command to recognise an undefined-reference linker error, then fix the command.

Before editing, record your prediction. Rebuild the changed target and run it again; a previously built binary does not contain new source edits. Add at least one successful case, one rejected case and one boundary case. Preserve the original reference solution so a teacher can compare your attempt with known behaviour.

Review questions

Does including score.h compile score.c?

Read the explanation after answering

No. The header supplies declarations. The implementation source must also be compiled and linked.

What evidence did you produce? Record the source revision or the exact files you changed, compiler, build directory, command, observed output and any failure. Passing the supplied tests is not automatic proof that a new variation is safe.

Where does this belong in Umicom? The exercise is a teaching example under Framework. A real reusable feature belongs in an existing Framework module with public contracts and tests. Studio and Education consume those modules rather than copy this laboratory as an application-local implementation.
