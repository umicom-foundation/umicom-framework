Lesson 30 · 45–90 minutes · ID: foundations.functions-contracts

1. Understand the idea

A function should state valid input, ownership, result and failure behaviour. A status value separates failure from legitimate data such as a zero result.

TermPlain meaning
PreconditionWhat must be true before a call.
PostconditionWhat success guarantees afterwards.
Output parameterA pointer naming storage where a function writes a result.

Review the first C programme, functions and memory basics. The workshop setup creates a separate build directory; it does not replace your application build.

Before writing code, say what counts as valid input, who owns each object, and what must remain unchanged when an operation fails.

2. Write and inspect the complete example

Open framework/examples/learning/programming/functions_contracts/main.c. The supplied file is the reference solution. Read it once, then type your own copy in a disposable practice workspace. For a first run you may build the supplied reference unchanged. Do not put deliberately broken examples into the shared Framework source.

The lines beginning with #include provide declarations. main is the programme entry point. EXIT_FAILURE reports a failed check; EXIT_SUCCESS reports success. The helper functions above main implement this lesson’s contract.

examples/learning/programming/functions_contracts/main.c
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/learning/programming/functions_contracts/main.c
 *
 * PURPOSE:
 *   Functions with explicit contracts.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

/* Scores must be 0..100; on rejection, *outMean is unchanged. */
static bool MeanScore(const unsigned *scores, size_t count, double *outMean)
{
    if (scores==NULL || outMean==NULL || count==0U || count>1000U) return false;
    uint32_t total=0U;
    for (size_t index=0U; index<count; ++index) {
        if (scores[index]>100U) return false;
        total+=scores[index]; /* At most 100,000, within uint32_t range. */
    }
    *outMean=(double)total/(double)count; return true;
}
int main(void)
{
    const unsigned scores[]={70U,80U,90U}, invalid[]={50U,101U};
    double mean=-1.0;
    if (!MeanScore(scores,3U,&mean) || mean!=80.0) return EXIT_FAILURE;
    if (MeanScore(invalid,2U,&mean) || mean!=80.0 || MeanScore(scores,0U,&mean))
        return EXIT_FAILURE;
    puts("mean=80.0; rejected inputs preserved the output");
    puts("PASS: functions_contracts");
    return EXIT_SUCCESS;
}

3. Follow the values through the code

MeanScore validates every element before writing the output. The count bound also bounds the accumulation; the uint32_t accumulator can represent every total up to 100,000. The caller must still supply count readable elements: a non-null pointer alone does not establish the extent of an allocation.

Place your cursor at the first statement in main. Write down the input and expected output of each helper call. When you reach a rejection, check both the return value and any caller-owned output. Do not assume “no crash” means the result is correct.

Bad example — inspect only. The following fragment illustrates a defect or unclear contract. It is not part of the built targets. Examples with invalid memory access, mismatched formats or undefined behaviour must not be run.
Bad pattern: not compiled or executed
return total / count; /* Division by zero and input validity are unexplained. */

Good pattern: use the complete checked implementation above. Explain which precondition or comparison prevents the defect. A naming change alone cannot repair an ownership or bounds error.

4. Build and run it

First complete the workshop configuration once. Then run the following commands one line at a time. Stop on an error instead of continuing with an old executable. The two operating systems use different paths, but compile the same C sources.

Windows · PowerShell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-programming" --target umicom-learning-functions-contracts
& ".\build\learning-programming\bin\umicom-learning-functions-contracts.exe"
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-programming" --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.functions_contracts$'
Linux · terminal
cd "$HOME/umicom/Umicom-Applications"
cmake --build build/learning-programming --target umicom-learning-functions-contracts
./build/learning-programming/bin/umicom-learning-functions-contracts
ctest --test-dir build/learning-programming --no-tests=error --output-on-failure -R '^framework\.learning\.programming\.functions_contracts$'

You should see the lesson’s explanatory output followed by:

Expected final line
PASS: functions_contracts

CTest should report one passing test for this exact filter. “No tests were found” is not success. Compilation errors concern C syntax or declarations; undefined references concern linking; a non-zero test exit concerns observed behaviour.

5. Change one thing and test again

Change the output contract to reject fractional means or return an integer plus remainder. Document the new rule and add boundary tests.

Before editing, record your prediction. Rebuild the changed target and run it again; a previously built binary does not contain new source edits. Add at least one successful case, one rejected case and one boundary case. Preserve the original reference solution so a teacher can compare your attempt with known behaviour.

Review questions

Can the function verify the allocation behind scores?

Read the explanation after answering

No. The caller must supply the stated number of readable elements; pointer non-null checks do not establish allocation extent.

What evidence did you produce? Record the source revision or the exact files you changed, compiler, build directory, command, observed output and any failure. Passing the supplied tests is not automatic proof that a new variation is safe.

Where does this belong in Umicom? The exercise is a teaching example under Framework. A real reusable feature belongs in an existing Framework module with public contracts and tests. Studio and Education consume those modules rather than copy this laboratory as an application-local implementation.
