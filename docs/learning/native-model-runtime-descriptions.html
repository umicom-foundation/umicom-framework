Describe a native model runtime

A model manager needs to explain what it plans to run before it starts anything. An application also needs to distinguish those settings from what a process or endpoint later reports. This lesson connects Umicom's native run-plan service to its AI catalogue through a pure conversion. A pure conversion computes a value without opening files, sending requests or starting a process.

1. Identify the evidence you have

ValueWhat it describesWhat it does not prove
Run planAdmitted executable/model paths, expected digest, alias, port and CPU settingsFile existence or compatibility
Runtime descriptorProvider identifier, endpoint, alias, token limits and configurationProvider registration or health
Session plan copySettings captured when this owner submitted a processCurrent process state or loaded weights
Process snapshotRunner state and bounded diagnosticsEndpoint identity or successful inference
Health observationWhat the selected endpoint reportedAuthenticated ownership of that endpoint

2. Preview the catalogue description

With the native manager built, run this command using paths for your reviewed installation. The description itself does not require those files to exist.

umicom models describe qwen2.5-0.5b-q4 'C:\Tools\llama.cpp\llama-server.exe' 'C:\Models\Umicom\model.gguf' 8080 2048 4

Expect a local-chat provider identifier, the model alias, http://127.0.0.1:8080/v1/chat/completions, context 2048, planned output limit 256, unavailable health and an unassigned revision. The command refuses --apply. To start a model, return to the separate reviewed run/serve workflow.

For a custom model, describe-file accepts an absolute engine path, model path, 64-character lowercase expected digest, alias, port, context and thread count. These inputs reuse run-plan validation; there is no second permissive parser for the preview.

3. Use the shared C service

Link Umicom::local_models and include umicom/local_models/runtime.h. Create a UmiModelRunPlan with the existing factory. Then convert it into a complete descriptor:

UmiAiRuntimeDescriptor descriptor;
UmiStatus status = UmiModelRuntimeDescriptorCreate(&plan,
    "runtime.assistant", "Local assistant", 256, &descriptor);
if (status == UMI_STATUS_OK) {
    status = UmiAiRuntimeCatalogueUpsertIfRevision(catalogue,
        &descriptor, 0);
}

Use expected revision zero only for a new identifier. If replacing a record, first read its revision and use that value. See revision checks for stale observations. The descriptor is configured but unavailable: its chat and streaming flags describe the planned adapter interface, not capabilities measured from this particular model.

The service validates all run-plan fields again, including the expected guard filename and working directory. It refuses malformed text and output limits outside 1..context. On failure it leaves the caller's output unchanged. That lets a form keep its previous valid preview while displaying the new validation error.

4. Read the settings captured by an owner

A UI can edit a “next model” form while a previous session exists. The session must not read from that mutable form when explaining its own configuration. It stores a full plan copy after admission; metadata reads copy that owned value back to the caller.

UmiModelRunPlan submitted;
UmiStatus status = UmiModelSessionReadPlan(session, &submitted);
if (status == UMI_STATUS_OK) {
    /* Display submitted.alias/port/context as configuration, not health. */
    status = UmiModelSessionRuntimeDescribe(session,
        "runtime.assistant", "Local assistant", 256, &descriptor);
}

Keep the session alive and serialize these calls with start/read/stop operations. A failed start may retain an owner only because cleanup needs retry. An owner with no submitted job returns INVALID_STATE rather than being presented as an active configuration. A process that later exits can still have a captured plan; read its process snapshot separately.

5. Bind applications explicitly

The descriptor names umicom.local-chat, the existing canonical provider. Creating a descriptor does not create that provider or change its port. Register the intended provider through the shared factory, retain its session and use the exact alias in the reviewed request. A list containing several descriptions does not by itself route each request to a different endpoint.

This separation keeps Studio, Media and other clients thin: Framework owns plan admission and descriptor construction. Product-specific controls still decide what is shown and approved. This lesson does not add a new graphical layout, automatic model replacement, GPU admission, embeddings, image or video generation.

6. Treat failed review output as a refusal

A console review can fail when an output stream is closed or cannot be flushed. The native download, launch and chat paths now check that the review was delivered before acting. An explicit apply flag does not justify silently proceeding after that failure. Errors after a session starts still go through normal checked cleanup; a cleanup error remains a distinct failure.

The CLI regression compiles the actual parser with failure hooks around output and side-effect boundaries. It checks both flush failure and an already-failed stream, asserts an error exit, and requires zero download, file-inspection, provider-create and process-start calls.

Retain an owner when a command returns

A local variable disappears when its function returns, but a failed shutdown can leave the native session alive. Returning only an integer loses the caller's way to retry. UmiModelsCommandWithSession solves this by writing the session into a slot owned by the embedding application. The slot must outlive the call.

int command_result = UmiModelsCommandWithSession(argc, argv, &console_session);
if (console_session != NULL) {
    /* Keep this slot in the host. Report incomplete cleanup and offer a
       deliberate retry using UmiModelSessionStop(&console_session). */
}

The exit code describes the command result; the pointer describes the remaining ownership obligation. A failed stop can retain the pointer, while another cleanup error can consume it. Do not infer one from the other. Starting a new command with an occupied slot returns the busy diagnostic before parsing or side effects.

The legacy entry keeps its own compatibility owner. Its query and checked release functions support explicit retry without changing old command arguments. They never release an explicit caller's session. Serialize these operations; the console streams remain process-wide.

The owner regression injects inert start/read/stop and input boundaries. It demonstrates both retained and consumed failures, late output failure and recovery of the compatibility slot. These tests do not prove that an operating system will terminate a real child correctly. Keep native process qualification separate.

7. Qualify the source and installed SDK separately

Build and run the focused targets using the commands in the manager guide. Inspect pure projection tests, partial-owner tests and the finite process fixture. The pure cases need no model or network. Executing the fixture tests starts its inert child program and must be reported separately from pure checks.

The existing installed SDK consumer now resolves the projection and conditional catalogue symbols as well as earlier model APIs. Configure it against an installed package, not Framework source. Its build and execution establish consumer linkage only; they do not qualify an inference engine. The SDK supplies its approved application branding through the shared resource helper.

  1. Project a valid plan and confirm healthy-runtime selection refuses it.
  2. Edit the caller's next-run plan after submission, then confirm the session copy still describes the original settings.
  3. Replace a catalogue record while an observation is pending and confirm its old revision cannot publish.
  4. Break console review delivery in the injected test and confirm no side-effect boundary is reached.
