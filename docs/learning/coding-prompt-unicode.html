Keep UTF-8 characters intact when splitting AI messages

A message capacity is measured in bytes. A visible character may require more than one byte. Splitting a source file every 2,047 bytes can therefore turn valid UTF-8 text into two invalid message strings, even when concatenating the original bytes would have produced valid text.

1. Recognize the boundary problem

The euro sign uses three UTF-8 bytes: E2 82 AC. If E2 becomes the final byte of one message, that message ends in an unfinished scalar. The next message starts with continuation bytes that have no leading byte. Providers receiving separate strings cannot assume that those fragments belong together.

A Unicode scalar is one valid encoded code point, excluding surrogate values. A user-perceived character can contain several scalars, such as a letter followed by a combining mark. This implementation preserves scalar boundaries; it does not attempt to find grapheme boundaries or normalize text.

2. Reuse the shared validator

#include "umicom/base/utf8.h"

if (!UmiUtf8Validate((const unsigned char *)text, length, NULL))
    return UMI_STATUS_PARSE_ERROR;

Framework Base already owns strict UTF-8 validation. It rejects truncated sequences, overlong encodings, surrogate code points, invalid continuation bytes and values above U+10FFFF. Prompt construction calls that service instead of introducing another decoder.

The full span is validated before it is divided. Message names, message text, the request ID and the selected model ID are also checked before a complete request is published. Invalid encoding returns PARSE_ERROR and leaves the previous request unchanged.

3. Move a proposed split to a scalar boundary

After validating the whole span, start with the largest byte count that fits one message. If the first byte of the next chunk is a continuation byte, move the split backward until that byte is no longer a continuation byte:

while (count != 0U && count < remaining &&
       (((unsigned char)text[offset + count] & 0xc0U) == 0x80U)) {
    --count;
}

The count < remaining condition prevents reading beyond the span when this is the last chunk. The mask recognizes the UTF-8 continuation-byte prefix 10. This short boundary rule is safe here because the canonical validator has already admitted the complete sequence.

Copy the selected bytes, add a C string terminator, append the message, and advance the offset by that exact byte count. Nothing is transcoded or discarded. Some chunks may have a few unused bytes to keep the next scalar intact.

4. Preserve failure behavior across the whole request

Source text and validation feedback use the same chunking helper. If malformed text is discovered after earlier messages were prepared, the staged request is discarded. The caller keeps its previous complete request. Capacity errors remain explicit: smaller Unicode-aligned chunks can require an additional message slot.

Do not replace malformed bytes silently. The workspace or feedback adapter should identify the original encoding and convert it deliberately before constructing a UTF-8 request. The byte-span API still rejects embedded zero bytes because provider messages are C strings.

5. Test byte preservation and individual message validity

  1. Place a two-, three- or four-byte scalar at every relevant position around the chunk limit.
  2. Build the request once with that text as source and again as validation feedback.
  3. Validate every resulting message independently.
  4. Concatenate the messages for that source or feedback and compare their bytes with the original span.
  5. Supply malformed sequences and confirm PARSE_ERROR with an unchanged destination.
