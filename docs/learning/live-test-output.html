Reading test output while an attempt runs

CTest runs tests registered by a configured CMake project. A single selected test can also run setup and cleanup fixtures: helper tests needed before or after the selected body. Framework captures that whole invocation while it runs and keeps the latest 65,535 bytes for a responsive frontend.

Connect a test explorer

  1. Create a UmiCtestJob from copied test requests and submit it to the existing task queue. Keep the job and queue alive while it runs. The job validates selection, build root and repeat limits.
  2. Allocate a UmiCtestOutputSnapshot on the heap. Large output records should not consume a small UI thread stack. Call UmiCtestJobReadOutput on each frontend refresh.
  3. Read invocation before presenting a result. Zero means no attempt has started. attempt counts repetitions; invocation counts all started selected attempts. A new invocation clears the bytes and increases the revision within the same job.
  4. For GTK, create UmiCtestOutputGtk4Create() once, then pass successful snapshots to UmiCtestOutputGtk4Update on the GTK thread. The widget owns display copies and never starts tests.
  5. Use the job progress summary and completed UmiTestResult records for outcomes. Output arriving, an empty buffer, or a skipped test does not establish a pass. Inspect the completed result for report errors, fixture failures and launch diagnostics.
  6. On Stop, request cancellation and keep polling. Release the job only after its queued or running work finishes. UmiCtestJobDestroy returns BUSY while that lifetime is still active.

Observe a synchronous invocation

UmiCtestRunObserved uses the same exact-name selection, fresh JUnit report, cancellation, timeout and process-tree ownership as UmiCtestRunConfigured. Its optional observer receives borrowed raw chunks on the executing thread. Copy the bytes promptly; do not touch GUI objects or re-enter the running adapter from that callback. A NULL observer preserves the ordinary quiet invocation.

The observed path requests --verbose so CTest exposes passing-test output as well as failures. The final verdict still comes from validated report and process evidence. See CTest's output options. The adapter requires CTest with JUnit report support; an absent or malformed report is an error.

The source example examples/testing/live_output.c demonstrates a command-line host. It streams bytes to the console, checks write failures separately, and accepts only a verified passed result as success.

Reuse the shared output components

UmiOutputTailAppend accepts caller-owned storage and a zero-initialised state. It retains raw bytes without allocating, locks or character conversion. Supply separate state, input and destination regions and hold your own lock across reads and writes. Invalid inputs leave storage unchanged. Both build and test workers use this policy.

UmiOutputViewGtk4Create is the reusable native presenter. A host maps domain evidence into a copied UmiOutputViewSnapshot with plain-text context and status. Identity and revision prevent older captures replacing newer jobs. Build and test adapters preserve their own public APIs.

Read the limits correctly

  • The tail is a temporary view, not a complete or persistent log. Slow polling may miss an entire attempt. Earlier completed results remain available separately.
  • Both standard output and standard error are merged. CTest adds its own progress and fixture text. This is a transcript viewer, not an interactive terminal.
  • tail.length includes embedded NUL bytes. The spare terminator is only a convenience. GTK displays NUL as ␀ and repairs invalid UTF-8 only in its display copy.
  • Truncation removes the oldest bytes. Total-byte and revision counters saturate instead of wrapping. If counters_saturated is set, update the display on every poll.
  • Test programs can buffer their own output. A quiet display does not prove a hung test; use its configured timeout or Stop when appropriate.

Troubleshoot a capture

  1. If there is no attempt, inspect queue and cancellation state in the job summary.
  2. If output seems frozen, enable Follow output or select Refresh output. A paused display intentionally keeps the text you are reading while accepting newer captures.
  3. If the status reports a launch, report or capture error, inspect the completed result. Never recover by treating process exit zero or readable text alone as a successful test.
