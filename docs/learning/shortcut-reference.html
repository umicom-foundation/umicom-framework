Expose the shortcuts your application actually uses

A shortcut reference should describe the keys installed by the running application. A copied table can drift: a command is renamed, its key changes, or an action needs an open document. The reference still looks convincing while teaching a binding that does nothing. Umicom Studio reads its native keyboard profile table when Help > Keyboard Shortcuts opens. The keyboard dispatcher and the reference therefore share their source of binding identities.

Try the Studio workflow

  1. Open Studio and choose Help > Keyboard Shortcuts. The existing Documentation panel displays the reference. It does not create a source document.
  2. Read the shortcut, caption and command identity together. The identity is useful when looking up commands in source or reporting a problem.
  3. Notice available and unavailable states. They are a snapshot taken when the reference opens. Opening a project, changing selection or finishing a task can change admission later.
  4. Open or edit a source document and reopen the reference. Confirm that the same document, unsaved text and selection remain. Viewing Help does not save or discard work.
  5. Use the Documentation search field to find a caption or command. The generated reference has no file address; its address field is empty. Existing browser history is retained. Reload can return to the last actual document.

This view lists the bindings installed in Studio’s native profile catalogue. It does not claim to enumerate every editor-specific key, operating-system shortcut or dynamically supplied third-party binding. It does not edit key assignments. Keep those distinctions visible when extending the application.

Separate capture, formatting and publication

The host captures three strings and an availability value for each binding. Framework validates the supplied snapshots and formats readable UTF-8. A GTK adapter then publishes that text into an existing read-only preview. Keeping these jobs separate allows another application or a console tool to reuse the same formatter without importing Studio’s widget code.

#include "umicom/developer_workbench/shortcut_reference.h"
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    const UmiShortcutReferenceEntry entry = {
        "file.save", "Save", "Ctrl+S", 1
    };
    size_t bytes = 0;
    if (UmiShortcutReferenceFormat(&entry, 1, NULL, 0, &bytes) != UMI_STATUS_OK)
        return 1;
    char *text = malloc(bytes + 1);
    if (text == NULL) return 1;
    UmiStatus status = UmiShortcutReferenceFormat(&entry, 1, text, bytes + 1, &bytes);
    if (status == UMI_STATUS_OK) puts(text);
    free(text);
    return status == UMI_STATUS_OK ? 0 : 1;
}

The example deliberately supplies one binding. In an application, copy from the actual binding owner instead of treating this example as a universal shortcut table. Querying the byte count first avoids guessing a destination size. Required bytes exclude the terminating zero, so allocation reserves one additional byte. A short output buffer returns CAPACITY_EXCEEDED without partially replacing text. Other invalid inputs preserve both output values.

Validate copied metadata

Each command, caption and shortcut must terminate inside its fixed array and contain valid UTF-8. Empty fields are rejected. Availability must be exactly zero or one. The service accepts at most 512 rows and keeps the host’s order, including deliberately repeated command identities with different bindings. It escapes C0 controls, DEL and backslashes so a line break embedded in a caption is visible as an escaped byte. It does not parse or execute the command strings.

In Studio, GTK produces the native shortcut label from the same key and modifier values used for keyboard matching. Control plus Tab has a specific document-navigation role; a reference must not invent a bare Tab command that would interfere with ordinary focus traversal. Command admission is queried separately and rechecked when a real action executes. The reference itself never executes the actions it lists.

Publish safely when observers can close the window

GTK notifications run synchronously. Replacing a text buffer or changing a summary label can invoke application code before the publishing function returns. That callback may close the owner, replace the buffer, reparent a widget or request the same command again. A pointer that was valid before publication is not sufficient evidence afterwards.

UmiGtk4TextPreviewPublish retains the native objects, prepares a complete replacement buffer and checks that both controls still belong to the live owner. It refuses editable views and nested publication. The caller’s strings are copied before notifications, so borrowed label text cannot disappear halfway through publication. A changed owner, buffer or published value returns CANCELLED. The function does not undo an observer’s own changes with a blind rollback. Cancellation can therefore leave partially published controls; the caller must respect the result.

Studio also holds an independent weak owner request across opening the Documentation surface, reading admission and clearing the address. After each observable operation it resolves the original runtime again. The application guard prevents a nested Help request from replacing the current publication. Retained menu buttons continue to use the established weak command route.

Exercise the contracts

  1. Format an empty binding list and confirm the report explains that no bindings were supplied.
  2. Supply invalid UTF-8 or a full array without a terminating zero. Verify that output bytes and the required-size sentinel remain unchanged.
  3. Allocate exactly the queried byte count without the additional terminator byte. Confirm refusal, then add one byte and retry.
  4. Retain the old read-only buffer before publishing. Its contents should remain valid for that holder after the view switches buffers.
  5. Attach a buffer-change observer that closes the window. The native publisher should return CANCELLED without dereferencing the retired application runtime.
  6. Attach a nested publication observer. It should receive BUSY; a later independent publication should work after the guard is released.

Configure and qualify the implementation

The following Framework commands prepare and run the focused regression targets. Run them from a Framework checkout with the selected GTK development package available. A successful configure only generates build rules. It does not establish that the compiler, tests or desktop interaction passed.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B build/shortcut-reference -G Ninja -DBUILD_TESTING=ON -DUMICOM_BUILD_GTK4_ADAPTER=ON
cmake --build build/shortcut-reference --target umicom-shortcut-reference-test umicom-text-preview-gtk4-test
ctest --test-dir build/shortcut-reference -R "^framework[.](shortcut_reference|gtk4[.]text_preview)[.]" --output-on-failure --no-tests=error

Check the project’s GTK option before using a different preset. If GTK cases return skip code 77, no display-backed result was obtained. If the compiler probe fails before configuration, verify the selected toolchain and its runtime search path. Preserve that first log when retrying; a successful retry does not erase the environmental failure.

For Studio, build umicom-studio-shortcut-reference-test in the Applications build and select ^studio[.]shortcut_reference[.]gtk4[.] in CTest. Review real menu opening, repetition, source preservation and observer cancellation separately from the portable formatter tests. These commands describe qualification steps; the lesson does not claim they have already passed on the reader’s machine.
