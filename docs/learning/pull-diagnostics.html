Capture an explicit diagnostic report

Explicit, or pull, diagnostics use a request and correlated response. The server computes problems for the currently synchronized draft. Framework keeps this workflow separate from notification diagnostics, while sharing owned message rows, exact source-range checks and native process cleanup.

Use a temporary source connection

  1. Include umicom/language_runtime/diagnostic_query.h and link Umicom::developer. Copy the complete UTF-8 draft, exact document URI, language ID and absolute project settings into worker-owned storage.
  2. Fill UmiLanguageDiagnosticRequest and call UmiLanguageDiagnosticQueryPullNative with an enabled local server profile. Inputs remain alive until the call returns.
  3. The query negotiates UTF-16 coordinates, document synchronization and an object-valued diagnosticProvider. It preserves an optional provider identifier in the request. Unsupported or malformed capabilities fail before opening the source.
  4. After opening the draft, it sends textDocument/diagnostic without a previous result ID and requires a full result. Notification traffic cannot substitute for the correlated response.
  5. On success, use the same catalogue metadata and row accessors as notification capture. The catalogue owns complete messages, related locations and original diagnostic JSON. No document version is invented for a pull report.
  6. Return the catalogue to the document owner, recheck the captured draft and identity, then show or navigate a selected diagnostic. Destroy the catalogue when the result is retired.

For an already constructed, exclusively owned server in STARTING state, call UmiLanguageDiagnosticQueryPullOnServer. Invalid preflight does not touch it. Once initialization begins, the query owns cleanup; destroy the server object after return. Every usable result is withheld until document closure and shutdown succeed.

Decode reports from another transport

  1. Call UmiLanguageDiagnosticCatalogueReadPullResponse with the exact JSON byte span, expected numeric request ID and source URI.
  2. A fresh request requires kind: full and complete items. An unchanged report returns INVALID_STATE. Malformed or duplicate known members reject the complete response. Advertise relatedDocumentSupport: false; nonempty related-document reports return NOT_IMPLEMENTED.
  3. Use UmiLanguageDiagnosticCataloguePullResultId to borrow an optional result ID. NOT_FOUND means none was supplied; an empty supplied ID remains distinguishable. Temporary native queries retain the value for inspection but never reuse it across connections.
  4. Call UmiLanguageDiagnosticCatalogueValidateSource before using positions. Pull freshness comes from the exclusive synchronized source, not an invented protocol version. Reusing result IDs in a persistent client requires separate provider and previous-report ownership.

Limits and recovery

The complete reader retains the existing 1 MiB JSON and 4096-row bounds. A result ID is bounded to 8192 decoded bytes. Native messages are limited to 65536 bytes and provider identifiers to 4096 decoded bytes; escaping may exceed the smaller request buffer. Initialization and response reads share the caller's timeout, followed by up to 250 milliseconds of read cleanup.

Cancellation is cooperative between operations. Native startup and synchronous writes retain their existing cancellation limits. The direct child is owned; a server can read project files and start descendants. Server-to-client requests, dynamic registration, workspace diagnostic refresh, partial reports, related document reports and cached unchanged reports are not implemented by this temporary workflow.

A server error is returned without automatically repeating the request. A failed or oversized report is never published as a partial list. An empty full report is not proof that a build or project analysis has completed.
