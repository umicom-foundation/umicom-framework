Read build results without losing the evidence

Follow a Notes program from a good build to a failing test, then inspect what actually happened.

For people learning to develop and support applications. No financial connection or operating-system image is needed.

Start with three different questions

A source file can compile successfully and still contain a mistake. A test can fail without producing a compiler error. A filtered Problems list can be empty while the operation itself has failed. Learning to separate these situations makes development much less frustrating.

In this lesson, you will build a small Notes word counter, introduce a deliberate counting error, and use its results to decide what to fix. You will also learn how Studio’s Review build history window keeps an earlier result separate from the work you are doing now.

QuestionWhere to look
Did the tool finish successfully?The recorded operation state, status and exit code.
What explanation did it give?The Problems entries and captured output.
Does the application behave correctly?Tests and a real application workflow, not compilation alone.
Use a practice copy. The lesson deliberately changes a small program. Use the supplied practice project, not an irreplaceable document or a connected financial application.

Understand the words before using the tools

Configure asks CMake to read a project and prepare build rules. Compile translates a C source file into an object file. Link joins the necessary objects and libraries into a program. Test runs checks against that program or its functions. These are related operations, but they answer different questions.

A diagnostic is a message such as a warning or error, sometimes with a source filename, line and column. A history record stores the outcome and the output retained for one operation. A snapshot is an independent copy of selected records at one moment. It does not keep changing when another build finishes.

Existing build history→One locked copy→Read-only review

The new review window copies up to eight of the most recent records still retained by the build service. It does not start another build, run a test, open a source file, or query a database.

1. Prepare the Notes project

After merging and building this update, find the complete practice project here:

Folder
C:\umicom\Umicom-Applications\framework\examples\build_review\notes_project

Copy this folder to a new practice directory. The following PowerShell commands create a unique destination and leave the repository example unchanged:

PowerShell
$Repository = "C:\umicom\Umicom-Applications"
$Practice = Join-Path $env:TEMP ("Umicom-Notes-Practice-" + [guid]::NewGuid().ToString("N"))
Copy-Item -LiteralPath "$Repository\framework\examples\build_review\notes_project" -Destination $Practice -Recurse
Write-Host "Practice project: $Practice"

The project contains notes.c, its public header, a command-line program, a test program and a CMake definition. NotesWordCount counts words separated by ASCII spaces, tabs and line breaks. It treats non-ASCII UTF-8 bytes as part of a word; this is a deliberately stated teaching rule, not a complete language-aware word-segmentation engine.

Open the practice directory as a project in Studio using its existing project controls. Keep its build directory inside the practice copy. Opening the new review window is not a substitute for configuring the project through Studio’s existing build settings.

2. Obtain a known-good result

First build the unchanged project. These PowerShell commands use the same compiler installation as the main Umicom workspace:

PowerShell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" -S $Practice -B "$Practice\build" -G Ninja `
    -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "Practice configuration failed." }
& "C:\msys64\ucrt64\bin\cmake.exe" --build "$Practice\build" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Practice build failed." }
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir "$Practice\build" --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Practice tests failed." }
& "$Practice\build\umicom-notes-practice.exe" "Prepare the workshop note"

The final command should print:

Expected output
Words in note: 4

The test program also checks empty text, repeated whitespace, a UTF-8 currency symbol and invalid input. Its checks use explicit return values, so a Release build does not disable them.

Two histories are not one. These PowerShell commands do not insert records into Studio. To populate Studio’s Build history, run an operation through Studio’s existing build service. Test Explorer and other tools may retain separate records; an absent entry in this review does not prove that an operation never ran.

3. Introduce a fault that still compiles

In the practice copy of notes.c, locate this assignment:

C
*outCount = count;

Change only that line to:

C
*outCount = count + 1U;

Build again. The code is still valid C, so compilation can succeed. Run the tests again: the empty note now incorrectly reports one word, and the test should fail. This is the difference between a syntax error and a behavioural error.

Restore the original assignment, rebuild and repeat the tests. A passing test after a repair is useful evidence only when it was actually run against the repaired program. Keep the failed and repaired results distinct; do not simply replace the failed output with a later success message.

For a separate syntax exercise, remove a semicolon in the copied project. The compiler should report a source location. Restore it before continuing. Never introduce either fault in the canonical Framework source merely to practise.

4. Open the recorded build review

In Studio, open the Build panel and choose Review build history. The existing Configure, Build, Test, Run, Install, Cancel and other controls are not replaced by this button.

The review contains a Recorded operation selector, a Minimum severity selector, a Contains field and a read-only text report. It starts with the newest copied record. Select an earlier operation to inspect that operation’s own status, command and output.

Displayed outcomeMeaning
Recorded successThe retained state says success, with an OK status and zero exit code. It is not a product-quality certificate.
Recorded failureThe retained state says failed and its status or exit code indicates failure.
Recorded cancellation / timeoutThe corresponding state and status agree.
Not finishedThe copied record was created or running. This frozen window does not follow later changes.
Inconsistent outcome fieldsThe retained fields disagree; the review does not choose a reassuring interpretation.
UnrecordedA plain log was imported without an observed process result.

Close and reopen the review to take another snapshot. The existing window does not retain a pointer to the Studio runtime or its live history after the copy finishes.

5. Filter the view without rewriting the result

Select Error and above to hide notes and warnings from the Problems section. Type a filename, diagnostic code or part of a message into Contains. Matching is literal and case-sensitive; there is no regular-expression language.

The report shows both the visible count and the total retained count. It also reports the producer’s dropped-diagnostic count separately. Captured output remains visible and is not filtered.

Try Fatal only on a failed result containing ordinary errors. The Problems section may show zero visible entries, but the recorded failure must remain a failure. This is intentional.

The filter accepts up to 255 UTF-8 bytes. A character can occupy more than one byte. An oversized filter is refused with an explanation rather than silently shortened.

6. Notice what the older record cannot tell you

The existing build-result contract retains an operation identifier, phase, state, status, exit code, profile identifier, formatted command, timing, diagnostic list and bounded output. It does not retain every fact needed for a fully reproducible build.

The report therefore says Source revision: unavailable, Original working directory: unavailable and Output completeness: unknown. It does not borrow the current project’s directory or Git commit and present them as facts about an older run.

For the same reason, this window does not offer automatic source navigation. A relative path in an old log cannot safely be resolved merely by looking at the directory currently open in Studio. Existing source-navigation tools remain available separately.

The review can state how many older records were omitted from the copy while still retained in history. It cannot count records already evicted before the copy; that number remains unknown.

7. Inspect a saved text log

The native command-line tool accepts an explicitly selected plain-text log:

PowerShell
Set-Location "C:\umicom\Umicom-Applications"
& ".\build\windows-ucrt64-all-debug\bin\umicom-build-review.exe" log "C:\Practice\compiler.log"
if ($LASTEXITCODE -ne 0) { throw "The log could not be inspected." }

Use UTF-8 or ordinary ASCII text, no embedded NUL bytes, and at most 65,535 bytes. UTF-16 text commonly contains NUL bytes and is not accepted. On Windows this command-line path currently uses the C runtime’s argument/path encoding; qualify non-ASCII paths in your actual host environment.

A successful inspector exit means the log was read and rendered. It does not mean the build described by the log succeeded. A line saying “100% tests passed” remains text, not a newly observed process outcome.

Control characters, invalid UTF-8 and certain bidirectional-format bytes are escaped in the report. For example, an escape byte is shown as  rather than being interpreted as a terminal command. The original captured bytes remain in the private snapshot.

Review before sharing. Logs can contain local paths, source snippets and credentials placed in command arguments. Nothing is uploaded automatically. Check the content before copying it into a support request.

8. Follow the C ownership model

This complete example constructs one in-memory failed result, copies its history, destroys the original history, then inspects the independent copy. It does not run a compiler:

C
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/build_review/main.c
 *
 * PURPOSE:
 *   Show why a failed process cannot become successful merely by filtering its problems.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/

#include "umicom/build/review.h"
#include "umicom/build/parser.h"
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    UmiBuildHistory *history = NULL;
    UmiBuildReview *review = NULL;
    UmiBuildResult *result = calloc(1U, sizeof *result);
    UmiBuildReviewSummary summary;
    UmiBuildReviewFilter filter = {UMI_BUILD_DIAGNOSTIC_FATAL, ""};
    UmiStatus status = result == NULL ? UMI_STATUS_OUT_OF_MEMORY : umi_build_history_create(2U, &history);
    if (status != UMI_STATUS_OK) { free(result); return 1; }
    result->operation_id = 1U;
    result->phase = UMI_BUILD_PHASE_BUILD;
    result->state = UMI_BUILD_STATE_FAILED;
    result->status = UMI_STATUS_IO_ERROR;
    result->exit_code = 1;
    strcpy(result->profile_id, "notes.debug");
    strcpy(result->command, "cmake --build build");
    strcpy(result->output, "C:/Umicom Notes/main.c:8:5: error: expected ';' before return\n");
    status = umi_build_parse_output(result->output, &result->diagnostics);
    if (status == UMI_STATUS_OK) status = umi_build_history_append(history, result);
    if (status == UMI_STATUS_OK) status = UmiBuildReviewCapture(history, 2U, &review);
    /* The copied review does not depend on the worker or history lifetime. */
    free(result);
    umi_build_history_destroy(history);
    if (status == UMI_STATUS_OK) status = UmiBuildReviewSummarise(review, 0U, &filter, &summary);
    if (status == UMI_STATUS_OK) {
        printf("Outcome: %s\nVisible problems after filtering: %zu\n",
            UmiBuildReviewOutcomeText(summary.outcome), summary.visibleDiagnostics);
        puts("Filtering did not turn the failed build into a successful build.");
        puts("Practice complete. Memory only; no compiler, files, database or network was used.");
    }
    UmiBuildReviewDestroy(review);
    return status == UMI_STATUS_OK ? 0 : 1;
}

The large result is allocated on the heap rather than placed on a small thread stack. UmiBuildReviewCapture copies records while holding the history’s existing mutex once. Once it returns, the review owns those bytes. UmiBuildReviewDestroy releases them.

The history must remain alive during capture. The review must remain alive while readers use it, and the caller must not change a filter during a call. This ownership agreement is what makes independent reads predictable; a mutex cannot rescue a pointer to an already destroyed object.

Run umicom-build-review-example.exe to see a recorded failure remain failed when its error is hidden by a fatal-only filter. The small demonstration is also compiled as part of the regression suite.

Read a CMake configuration error

CMake prepares the build before the compiler starts. Its error header names a file and line, while the following indented lines explain what went wrong. Framework keeps these lines together as one diagnostic, so Studio's build review can search the explanation as well as the filename.

  1. Open Review build history after a Configure operation, or inspect a saved UTF-8 log with the command-line reviewer described above.
  2. Choose Error and above. For a duplicate-target error, enter same name already exists in Contains.
  3. Read the complete diagnostic and the captured output. A call stack explains which CMake files included one another; it remains in the transcript and does not replace the error's original source location.
  4. Correct the configuration and run Configure again. Continue to Build and Test only after configuration succeeds. Running an old test executable does not validate a configuration that has just failed.

The header and explanation share a limit of 1,023 UTF-8 bytes. An oversized record increases the dropped-diagnostic count instead of publishing a shortened message. Its original text remains in captured output, subject to that output's existing capture limit. Colour escape sequences and Windows line endings are normalised for the diagnostic; the transcript is preserved.

This grouping applies to recognised CMake location headers and their indented explanations. Localised output, arbitrary terminal controls and other tools' multiline formats are not inferred. Existing single-line compiler parsing continues to use the same API.

Troubleshooting

What you seeWhat to check
No retained build operationsRun an operation through the existing Studio build service, then open a fresh review. Shell commands do not automatically appear in it.
An earlier “running” state never changesThe window is a frozen snapshot. Close and reopen it after the operation finishes.
No visible problemsClear Contains, choose All severities, inspect the total and dropped counts, and read the captured output.
Cannot capture historyRetain the original log and report the error. The review refuses invalid retained records instead of walking beyond their buffers.
Import fails with capacity or parse errorCheck the file size and encoding. Do not truncate a path or invent an exit status to make the tool accept it.
Review button is missingCheck that Framework and the Studio surface file from this update were both merged and the actual GUI target rebuilt.

Exercises and answers

Try these first

Why can a successful build have a failed test? What should happen when Fatal only hides every problem in a failed build? Why is the current Git revision not automatically a valid label for yesterday’s result? What is the difference between a dropped diagnostic and an omitted history record?

Read the answers

A compiler checks whether it can translate the source; a test checks selected behaviour. Filtering changes the displayed subset, not the operation outcome. A source revision must be captured at execution time to identify that run; today’s revision can be different. A dropped diagnostic was not retained or could not be parsed within the producer’s bounds. An omitted history record was still retained but excluded from this particular snapshot; earlier evictions remain unknown.

A small design exercise

Add another case to the copied Notes test for text containing only spaces and line breaks. Explain the expected count before running it. Then consider how a future execution contract could capture the source revision, working directory and output-truncation state without changing what an old record claims to know.

The next development step is richer execution-time provenance. It should be captured by the operation owner, not guessed later by a presentation window.

Developer reference and boundaries

The stable build-result and diagnostic structures are unchanged. The additive history-copy function and Umicom::build_review target are shared Framework services. Studio adds only the button that selects its existing history producer.

The older compiler API now adapts the canonical Framework parser used by the build service. Its smaller fields and 32-bit positions are checked before copying. Old implementations remain in explained disabled blocks for review. CMake author/deprecation headers are recognised rather than suppressed.

The native service keeps at most 16 records per review; the GUI requests eight. Each retained result contains bounded output and up to 256 diagnostics. These are local read-only review limits, not a claim to implement the full Studio roadmap, a durable build archive, an editor replacement, an LSP server or a debugger.

GTK signal bindings use weak owner references, and the dropdown constructor owns its supplied model. The build integration defers target composition until the owning CMake directory finishes declaring its canonical dependencies.
