C Language and Safer Programming Reference

This offline guide explains the C language from first principles and shows the checks that keep native programs predictable. Read it in order as a course or use the contents as a small built-in wiki.

1. A program and its tools

A source file is text written by a developer. A compiler translates it into object code, a linker joins object files and libraries, and the operating system starts the resulting program. A build description records which files belong together, while tests check observable behaviour.

#include <stdio.h>

int main(void)
{
    puts("Hello from Umicom");
    return 0;
}

#include makes declarations visible. main is the starting function. Returning zero reports success to the caller.

2. Values, types and conversion

A type tells the compiler how a value is represented and which operations make sense. Use size_t for object sizes and indexes, fixed-width integer types when a data format requires an exact width, and bool for true-or-false state.

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

size_t item_count = 12U;
uint32_t protocol_version = 1U;
bool ready = true;

Never assume that converting to a smaller or unsigned type is harmless. Check the source value against the destination range first.

3. Conditions and loops

An if statement chooses work. A loop repeats work. Braces make the boundary of each block visible, and a simple condition makes review easier.

for (size_t index = 0U; index < item_count; ++index) {
    if (items[index].enabled) {
        process_item(&items[index]);
    }
}

The comparison occurs before indexing, so index cannot name an element beyond the array. A while loop must change the state used by its condition or it may never finish.

4. Functions and contracts

A function should do one understandable job. Its contract explains valid inputs, ownership, output and failure. Validate pointers before dereferencing them and leave output in a known state when work fails.

UmiStatus read_total(const Record *record, size_t *out_total)
{
    if (record == NULL || out_total == NULL) {
        return UMI_STATUS_INVALID_ARGUMENT;
    }
    *out_total = record->total;
    return UMI_STATUS_OK;
}

Callers can now distinguish bad input from a valid total of zero.

5. Arrays and strings

An array contains a fixed number of adjacent elements. C does not check an index automatically, so carry the element count with the array. A C string is a character array ending with a zero byte; its capacity and current length are different facts.

char label[32];
size_t source_length = strlen(source);

if (source_length >= sizeof(label)) {
    return UMI_STATUS_CAPACITY_EXCEEDED;
}
memcpy(label, source, source_length + 1U);

The final copy includes the terminator only after the complete string is known to fit.

6. Pointers and ownership

A pointer stores an address. It may refer to an object without owning it, or it may be the handle responsible for releasing an allocation. Write that distinction in the API documentation.

RelationshipRule
Borrowed pointerUse it only while the owner guarantees the object is alive.
Owned pointerRelease it exactly once through the matching operation.
Optional pointerCheck for NULL before use.
Output pointerValidate it and document the state written on failure.

7. Dynamic memory

Dynamic allocation is useful when size is known only at runtime. Calculate the size safely, check the result, initialise the object, and make every later failure follow a cleanup path.

if (count > SIZE_MAX / sizeof(*items)) {
    return UMI_STATUS_CAPACITY_EXCEEDED;
}

Item *replacement = realloc(items, count * sizeof(*items));
if (replacement == NULL) {
    return UMI_STATUS_OUT_OF_MEMORY;
}
items = replacement;

The temporary pointer preserves the original allocation if resizing fails.

8. Safe size arithmetic

Integer overflow can turn a large required buffer into a small allocation. Check before arithmetic rather than checking the already-overflowed result.

if (left > SIZE_MAX - right) {
    return UMI_STATUS_CAPACITY_EXCEEDED;
}
size_t combined = left + right;

For multiplication, check count > SIZE_MAX / element_size. Also reject zero element size when the surrounding contract requires progress.

9. Text, input and formatting

Input is untrusted until checked for length, syntax and range. Bounded formatting still reports truncation, so inspect its return value.

int written = snprintf(buffer, sizeof(buffer), "%s: %u", name, value);
if (written < 0 || (size_t)written >= sizeof(buffer)) {
    return UMI_STATUS_CAPACITY_EXCEEDED;
}

For numeric text, use a conversion that reports where parsing stopped, inspect its range indicator, and verify that no unexpected characters remain.

10. Files and other resources

Files, sockets, locks, database statements and graphical objects all have a lifetime. Acquire as late as practical and release in reverse order. Check whether close or flush can report loss of important data.

FILE *stream = fopen(path, "rb");
if (stream == NULL) return UMI_STATUS_IO_ERROR;

UmiStatus status = read_content(stream);
if (fclose(stream) != 0 && status == UMI_STATUS_OK) {
    status = UMI_STATUS_IO_ERROR;
}
return status;

11. Headers, source files and libraries

A public header describes the stable contract. A source file owns private implementation. Include guards prevent repeated declarations. Keep private helper functions static, use opaque owner types for complex state, and avoid exposing toolkit objects from reusable modules.

Applications should call Framework contracts rather than copy their logic. This keeps fixes, tests and documentation in one place.

12. Errors and cleanup paths

Use explicit result values for expected failure. Preserve the first useful error instead of replacing it with a later cleanup result. Initialise owned fields to zero so a destroy function can safely handle partial creation.

Owner *owner = calloc(1U, sizeof(*owner));
if (owner == NULL) return UMI_STATUS_OUT_OF_MEMORY;

UmiStatus status = create_first(&owner->first);
if (status == UMI_STATUS_OK) status = create_second(&owner->second);
if (status != UMI_STATUS_OK) {
    owner_destroy(owner);
    return status;
}

13. Warnings, tests and analysis

Compiler warnings are design feedback. Treat conversions, truncation, shadowing and missing initialisers as issues to understand, not messages to silence. Tests should cover success, invalid input, boundaries, full capacity, repeated cleanup and simulated failure.

Static analysis finds suspicious paths without running the program. Runtime sanitizers catch invalid memory and undefined behaviour while tests run. Neither replaces clear ownership and bounds in the design.

14. Threads and shared state

Assume mutable data belongs to one thread unless the contract says otherwise. Protect shared state with one documented synchronization rule. Do not call unknown extension code while holding an internal lock, because callbacks may re-enter the service or wait on another lock.

Use message passing and immutable snapshots when possible. They reduce the number of places that can race over the same memory.

15. Using Framework contracts

Read the public header first. Create or initialise an owner, check every returned status, borrow snapshots only for the documented lifetime, and call the matching destroy function. Keep application code focused on composition and presentation.

The editor can combine offline C help, project indexes, language servers and optional model providers. Completion candidates identify their provider, replacement range, document revision and trust needs. This prevents a stale suggestion from silently editing the wrong text.

When uncertain, prefer a small explicit contract, bounded storage, one owner, one cleanup path and a focused test.
