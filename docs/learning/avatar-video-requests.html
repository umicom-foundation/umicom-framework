Shared avatar video requests

Link Umicom::heygen and include umicom/media_generation/heygen.h to prepare a request without contacting a service. Native clients can compose UmiHeyGenGtkCreate from Umicom::ui_gtk4; web and mobile clients can use the same non-UI owner with an appropriate trusted transport.

  1. Zero-initialize a UmiHeyGenDraft and select one operation. Populate only its fields. Creation needs a unique request key and a script/description. Avatar creation and avatar videos also need a title/name; avatar videos need avatar and voice IDs. Scene creation instead accepts a duration from 5 to 15 seconds and an optional existing provider image asset ID. Leave its name, voice, motion and subtitle fields empty. An image scene follows the image shape, so its portrait flag must be false. Catalogue cursors come from the preceding page.
  2. Start with a null plan pointer and call UmiHeyGenPrepare. The owner copies and validates fields. Show the strings returned by UmiHeyGenReview to the user without logging them.
  3. Invalidate the plan when the form changes. Collect explicit approval for this exact creation and its provider cost. Keep all plan calls serialized.
  4. On a worker, call UmiHeyGenExecuteWithProfile using the correct local profile and saved key alias. It resolves the key only after approval and wipes its temporary key buffer before returning. Raw-key hosts instead call UmiHeyGenExecute and remain responsible for clearing their own input.
  5. Inspect both status and the result. creation_may_exist survives an uncertain submission; creation_confirmed identifies a decoded receipt. A successful creation can still be pending or later fail. Never treat local cancellation as remote rollback.
  6. Keep the resource ID private and use an explicit status request. Completed video links may contain temporary access tokens; never store them in public logs or project metadata. Downloading requires a separate credential-free policy.
  7. Destroy the plan after the worker finishes. All returned review pointers then expire. Large result structures should be heap allocated.

Native transport reuses the configured optional libcurl dependency, verifies TLS, disables redirects and proxies, bounds replies, and makes one transfer. It accepts no configurable credential destination. The API can also be exercised with an injected trusted transport; this seam does not itself enforce a third party transport's TLS policy.

Limits are deliberately explicit: twenty catalogue items per page, bounded JSON, a script of at most 8192 UTF-8 bytes and a character prompt of at most 1000 bytes. Unexpected field types, missing required fields, malformed or over-capacity replies fail without exposing partial results. Unrecognised provider status strings remain visible and do not imply completion. Scene requests can generate from text or animate an already-uploaded image; they do not train or create a reusable avatar. There is no remote cancellation, persistent queue, automatic retry, local photo upload, digital-twin training or complete video editor in this owner.

See the provider creation contract for account capabilities and required API metadata.
