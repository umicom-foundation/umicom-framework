Native AI application learning path

Native AI applications with the Umicom Framework SDK

Learn to build native applications that keep model identity, user choices, resources and job outcomes explicit. The course connects real Umicom C APIs with lessons from Streamlit and ComfyUI. It does not reimplement either framework or claim that their feature sets are already available in Umicom.

Prerequisites: basic C functions, pointers and structures; familiarity with a terminal; CMake and a matching C23 toolchain. The Streamlit comparison lab additionally uses Python because that is the subject being studied. Plan six to eight hours for the core path, plus time for your own qualification runs.

Core sequence

  1. Model observations: complete the SDK discovery lesson and explain each evidence kind.
  2. Settings: follow saved provider connections and reviewed connection checks. Keep selection separate from a request.
  3. Forms: compare Streamlit's submission model with native typed changesets.
  4. Runtime identity: read native runtime descriptions and catalogue revisions. Reject stale publication.
  5. Workflow planning: complete the ComfyUI course and typed native preflight.
  6. Provider ownership: study admission and ownership before connecting a live provider.
  7. Streaming: use request-owned streams to keep output attached to its request.
  8. Capstone: build an offline model-review utility with complete IDs, recorded source format, explicit absent metadata and unchanged state after invalid input.

Capstone acceptance criteria

The utility must decode synthetic available and loaded observations, distinguish missing information from zero, preserve provider ordering, and refuse repeated decoded IDs. It must link the installed SDK rather than compile Framework sources. It must never infer that a listed model is ready for chat or image generation. Use the installed branding helper for SVG/ICO resources and Windows metadata.

Extend the capstone by designing a draft-settings screen using an approved product layout. Keep a running job's captured settings immutable while the user edits the next draft. A future Media export must include and verify the approved Umicom watermark; a graph node bearing that name is not proof that watermarking occurred.

What the current exercises implement

The native discovery project implements offline response decoding and evidence-aware lookup. Framework supplies the typed form, workflow-planning and ownership services linked from this course. It does not supply a drop-in Streamlit runtime, a complete ComfyUI server or all models advertised by a hosted aggregator. Live adapter qualification, resource usage, rendering, provider errors and deployment require separate evidence.

How to report results

Record the exact SDK revision or package identity, compiler, commands, exit codes and failed or skipped cases. Keep configure, compile, test and GUI observations separate. If a dependency is unavailable, preserve that result and explain recovery instead of marking the exercise successful. Never publish credentials or private prompts in a lesson report.

Project extension: prepare a native workflow request

Continue the ComfyUI request-ownership lesson and build the installed comfy_prompt example as an independent C23 project. Explain how an immutable request digest, saved connection revision and persistent task owner solve different problems. Review preparation, server acceptance, provider completion and local media delivery as separate milestones.

The example is offline. A local server can run custom nodes with file or network effects; the loopback destination does not establish a sandbox or prove local-only inference.

Build a complete product from the SDK

Follow Build Media and OS with the Umicom Framework SDK to separate product sources from Framework binaries, retain branded resources and diagnose missing consumer helpers. The exercises distinguish source composition, installed package identity, linkage and launch.

Project extension: submit native settings atomically

Build the form-draft SDK exercise. Keep model-search edits isolated until submission, refuse stale live context, and distinguish one local data commit from a durable provider request. The service has no rendering or network effects.

Project extension: inspect available node schemas

Use the ComfyUI node-catalogue SDK project to distinguish advertised classes and required inputs from model readiness or graph validity. Preserve unknown capability flags and compare saved connection identity before using an observation.

Check workflow requirements before submission

The ComfyUI course, lessons 10–11, connects immutable requests to captured node metadata. Work through the missing-input SDK example, then distinguish field presence from value validation, generation readiness and permission to execute. Reports identify exact request and catalogue bytes and disclose omitted diagnostics.

Exchange settings without activating a provider

Continue with the portable settings SDK lessons. Export and import one observed record, preserve 64-bit revisions and distinguish a historical file from the current scoped store. The complete C example verifies canonical identity without vault or network access.

Use the same offline workflow report in multiple applications

The native CLI, Media console and a small installed-SDK example now share Framework file inspection. Study offline observations and exit codes, then build the SDK inspector. This lesson separates file metadata from current provider authority and covers bounded reads, owned reports, Unicode arguments and escaped JSON.

Build trustworthy selectors from observations

Study native node catalogue queries to reuse metadata in Media and Studio selectors. The lesson covers copied ownership, deterministic ordering, category boundaries and the difference between unknown and explicitly false flags. Model and node searches share Framework’s ASCII-folded text matcher; neither search establishes provider readiness.

Compare answers without hiding failures

Complete model comparison with the installed SDK. Build a synthetic captured-result example, validate every report before selection, preserve unavailable results and distinguish comparison from routing or a model judge. Learn why a bounded count, successful selected slot and nonwrapping revision belong in Framework rather than each product.

Inspect workflow references as observations

Continue with ComfyUI reference inventories. Use one copied native report to distinguish absent targets, unknown output declarations and unsupported slot values. Build the installed SDK example and explain why matching metadata still does not authorize custom-node execution.

Read model download progress safely

Build the Ollama progress SDK project. Learn newline-delimited JSON, chunk framing, callback lifetime and terminal evidence. The offline exercise distinguishes provider success from verified installation and covers truncated input and late cancellation.

Observe queued generation work

Build the ComfyUI queue SDK project. Preserve exact scheduling numbers and distinguish running, pending and absent jobs. Learn why captured queue order, saved settings identity and completion receipts answer different questions.

Build a source-backed assistant from the installed SDK

Follow the local document retrieval course. Learn from GPT4All LocalDocs and Streamlit's retained session state, then build an independent C project using canonical Umicom collection search, immutable copied results, explicit evidence selection and separate review. The offline lesson demonstrates stale-corpus refusal and extractive preview without claiming model inference or automatic folder indexing.

Inspect device reports without promising capacity

Build the ComfyUI system observation SDK project. Learn exact byte counters, unknown-versus-zero values, copied lifetimes and saved-connection drift. Compare Streamlit metric presentation with native ownership while keeping reported free memory separate from model-fit and execution claims.
