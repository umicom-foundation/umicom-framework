Validate coding configuration domains

A C type describes storage and operations. An application's domain describes which values are meaningful. A floating-point setting may contain NaN, and an enum object can arrive with a value outside its named choices. Native configuration needs to check these domains before executing work or accepting restored state.

1. Understand why a range comparison is insufficient

The coding runtime accepts temperature from zero through two, including both endpoints. The old range expression rejected ordinary numbers outside that interval but did not reject NaN: both comparisons with NaN are false. The validator now requires a finite value as well.

if (!isfinite(config->temperature) ||
    config->temperature < 0.0 || config->temperature > 2.0) {
    return UMI_STATUS_INVALID_ARGUMENT;
}

isfinite comes from <math.h>. It rejects NaN and positive or negative infinity. Negative zero remains valid, as does positive zero. This is the existing Framework configuration interval; accepting it does not establish which values a particular model supports.

2. Check the provider kind independently of its ID

The provider ID is a string naming a configured adapter. The provider kind is one of the public choices LOCAL, REMOTE, AUTHOR_ENGINE or TEST. A nonempty ID does not prove that the numeric kind is valid. Unknown kinds are now refused before composition or typed archive publication.

The validator still preserves existing nonzero-is-true flag behavior. It does not silently normalize flags, connect to a provider, grant remote consent or activate tools. Runtime selection, current policy and actual execution remain separate checks. See Coding task admission for provider identity and privacy checks.

3. Exercise the direct API

#include <math.h>
#include <string.h>
#include "umicom/ai_coding_runtime/config.h"

int main(void)
{
    UmiAiCodingRuntimeConfig config;
    umi_ai_coding_runtime_config_init(&config);
    strcpy(config.provider_id, "example.local");
    strcpy(config.model_id, "example-model");
    if (umi_ai_coding_runtime_config_validate(&config) != UMI_STATUS_OK)
        return 1;
    config.temperature = NAN;
    return umi_ai_coding_runtime_config_validate(&config) ==
        UMI_STATUS_INVALID_ARGUMENT ? 0 : 1;
}
  1. Build the example as C23 against an installed Framework SDK and its Umicom::developer target.
  2. Run it. Expected exit status is zero: valid defaults with IDs are accepted, then NaN is refused.
  3. Replace NaN with 2.0 and change the expected result to OK. Repeat with a value above two and expect INVALID_ARGUMENT.
  4. Set an unknown provider kind and confirm refusal without starting any provider.

The literal IDs fit their fixed arrays. When accepting user input, copy with explicit capacity checks and a terminator. This example validates data only; it downloads no model and launches no process.

4. Keep envelope checks and typed checks distinct

A saved archive has a schema, length and checksum. These help identify its representation and detect damage. A correct checksum does not make every field acceptable. The archive's typed decoder must still validate the reconstructed configuration.

The shared archive reader and writer already reject nonfinite doubles. The direct configuration validator now applies the same requirement, while provider-kind admission also protects all decoders through their existing call to that validator. The regular decoder, caller-workspace decoder and conditional decoder each stage incoming data before publishing a destination.

OperationRefused-input behavior
Direct config validationReturns INVALID_ARGUMENT for an unknown kind or nonfinite/out-of-range temperature; changes no value.
Encode invalid configReturns before replacing the destination buffer or reported byte count.
Decode a nonfinite wire doubleThe shared reader returns PARSE_ERROR; the destination remains unchanged.
Decode an unknown kind or finite out-of-range temperatureTyped validation returns INVALID_ARGUMENT; the destination remains unchanged.
Decode using caller scratch storageScratch may change during parsing. The destination still publishes only after acceptance.

5. Qualify the same contract through every entry point

# From the Framework source root after configuration with testing enabled:
cmake --build build/windows-ucrt64-debug --target umicom-ai-coding-config-domains-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework\.ai\.coding-config-domain\.' --output-on-failure

The sixteen scenarios cover all named kinds, range endpoints, signed zero, flag compatibility, unknown kinds, NaN, infinities and ordinary out-of-range numbers. The fixture deliberately recomputes the checksum on hostile archived fields so that it tests typed admission rather than accidental checksum failure. Each decoder must preserve the prior destination when it refuses the candidate. Expected result: all selected cases pass; registration alone is not an executed result.

If a previously accepted configuration is refused, inspect its exact kind and temperature. Correct the draft deliberately rather than coercing an unknown kind into a local provider or silently replacing NaN. Retain the original archive for diagnosis. Never interpret restored configuration as authorization to execute it.
