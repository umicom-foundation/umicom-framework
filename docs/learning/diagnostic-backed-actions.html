Request fixes with fresh diagnostics

Some language-server fixes depend on diagnostic data that identifies a problem and its proposed remedy. Studio can capture this data and request actions while the same server connection remains open. This gives the server its original context without replaying data from a previous process.

Use the option in Studio

  1. Open a writable source draft, place the caret near a reported problem or select the relevant expression, and choose Actions….
  2. Enter or load the local language server and project settings.
  3. Select Include fresh diagnostics for fixes. It is off by default because it requires the server to publish diagnostics when the captured document opens.
  4. Choose Request code actions. Framework opens the captured draft, waits for a matching publication, checks its source ranges, then sends relevant diagnostic objects with the action request. Those operations share the same read timeout.
  5. Select an available action. Preview its complete result, inspect all confirmation explanations, approve the displayed proposal, then apply it. One Undo restores the draft; Save remains separate.

Changing the option retires previous choices and approval, including a pending result. The same rules still refuse disabled actions, commands, deferred resolution, resource operations and proposals that cannot be applied completely to the captured document.

What is included

Framework preserves the original JSON of relevant diagnostic objects, including numeric or string codes and opaque data supplied by the server. Nonempty ranges are compared as half-open intervals: a range ending at the selection's start does not overlap it. A zero-length diagnostic or a caret also matches a touching boundary, which keeps missing-token messages at a selection endpoint useful. Related locations alone do not select a primary diagnostic.

An empty matching publication is valid and produces an empty diagnostic context. A missing publication, wrong source ranges or an oversized request causes a reported failure. The option does not silently retry without context, infer a successful build, synchronize other unsaved documents or keep a persistent diagnostic subscription.

Extend another Framework host

  1. Use UmiLanguageCodeActionQueryNativeWithDiagnostics with the ordinary captured source-range request. The existing basic query remains available when diagnostic capture is not needed.
  2. For an already owned STARTING server, use UmiLanguageCodeActionQueryOnServerWithDiagnostics. Give the operation exclusive ownership until it returns and destroy the server object afterward.
  3. If implementing another transport, use UmiLanguageDiagnosticContextCreate with the publication, exact source identity, known version and range. It validates the complete source publication before selecting rows and creates its own JSON array.
  4. Read the array with UmiLanguageDiagnosticContextJson while the context owner lives. Destroy it after sending. The catalogue and source can be released after context creation, but its opaque data must stay within the server session that produced it.
  5. Retain the existing document review boundary. Diagnostic context helps the server propose an action; it does not approve or apply the action.

If no fixes appear

  1. Check whether the selected server publishes diagnostics and has the project's compile options. A pull-only server cannot supply this option's publication.
  2. If startup or analysis times out, correct the server configuration or retry after reducing the project workload. Disabling the option is an explicit choice to request range-only actions.
  3. If the source changed, close and recapture it. Do not transplant opaque diagnostic data from an earlier connection.
  4. If the response or outgoing context exceeds native message limits, reduce the source or choose a more focused workflow. Framework never sends a truncated set as though it were complete.
