Inspect saved test reports

A console log explains what happened during a test run. A JUnit report is an XML file containing structured test results. Umicom reads CTest's JUnit format to keep passed, failed, timed out, skipped, disabled and unrun tests separate.

umicom test-report reads a saved file. It does not build the project, execute tests, check Git revisions or establish that the current source passed. A successful parse also cannot prove that an old report belongs to today's build.

1. Record a new test run

Build your selected configuration first. Choose a new report name for each run because CTest overwrites an existing output file. Keep reports outside the public repository: test output can contain local paths or other private data.

Set-Location "C:\umicom\Umicom-Applications"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\testing"
ctest --preset windows-ucrt64-all-debug --parallel 2 --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\testing\application-tests.log" --output-junit "C:\umicom\_local\logs\testing\application-tests.xml"
$LASTEXITCODE

Stop and review a nonzero CTest exit code. Save the matching source revision, configuration and console log alongside the XML. A report with skipped or disabled cases is not evidence that every feature was exercised.

2. Inspect the saved results

& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" test-report "C:\umicom\_local\logs\testing\application-tests.xml"
$LASTEXITCODE

The command prints all outcome counts and lists non-passed cases. Add --all to include passed cases. It accepts relative or absolute paths, including Windows Unicode paths. It reads a regular file without changing it. The Framework reader rejects a symbolic-link final component; select the actual saved report.

Command exit codeMeaning
0The saved report contains at least one testcase and every record passed.
1The saved report is empty or contains a failure, timeout, runtime skip, disabled test or unrun test.
2The arguments, file access or report format could not be accepted. No complete result is reported.

3. Investigate incomplete evidence

A console excerpt that stops before the final summary cannot establish the whole suite result. Do not pass a text transcript to this command. Supply the XML produced with --output-junit. Missing closing tags, inconsistent totals and duplicate decoded test names are rejected. An interrupted run can leave no usable report; retain its console log and rerun qualification after fixing the cause.

A structurally complete report may cover only a selected subset. Compare the intended test selection and recorded configuration before calling a product qualified. Do not merge unrelated runs by concatenating their XML.

4. Compare two saved runs

Use reports from the same intended configuration and test selection. Save the first as before.xml and the new completed run as after.xml; keep their original logs and revision records too.

& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" test-report --compare "C:\umicom\_local\logs\testing\before.xml" "C:\umicom\_local\logs\testing\after.xml"
$LASTEXITCODE

The command matches exact test names after XML decoding and prints changed outcomes in name order. Different execution order, timings and diagnostic wording do not count as an outcome change. Neither input file is modified.

ChangeMeaning
RecoveredThe same named test changed from a non-passed outcome to passed in the saved evidence.
RegressedA previously passed test now failed, timed out, was skipped, was disabled or did not run.
Other outcome changeA non-passed test changed to another non-passed state. Disabled and runtime skipped are distinct.
Added or removedA test exists in only one report. A removed failure is not counted as a repair.

Comparison exits with 0 only when both reports contain the same names and the current report is nonempty and entirely passed. It exits with 1 for changed inventory or non-passed current results, and 2 for invalid inputs. A deliberately added passing test still changes inventory: review the selection and results rather than treating exit 1 as a parser error.

These are comparisons of observations. They cannot prove which source change caused an improvement, whether a renamed test is equivalent to an old one, or whether either report is current. Record that context separately. Reports from a headless build and a GTK build normally have different test inventories and should not be described as identical qualification.

Applications can include umicom/testing/ctest_report_comparison.h and call UmiCtestReportCompare on two imported reports. The comparison owns its changed-name records, so both input reports may then be destroyed. Read counts with UmiCtestReportComparisonReadSummary, borrow each changed record with UmiCtestReportComparisonAt, and release the comparison with UmiCtestReportComparisonDestroy. This shared service reads no files and launches no process.

Supported format and limits

The importer accepts one CTest testsuite root, up to 100,000 unique testcase names, and at most 64 MiB of UTF-8 XML. Names must fit the Framework test-name limit of 255 UTF-8 bytes. Decoded XML attribute values are limited to 1023 bytes and outcome messages to 255 bytes. It validates declared totals when provided, XML nesting, outcomes and durations. External entities and document type declarations are refused. This is not a general importer for every vendor's JUnit dialect.

Large output captured by tests can exceed the report byte limit. Select a smaller test group or limit diagnostic output at its source while retaining the full original logs. Do not remove failed records merely to make a report import.

Using the Framework service

Include umicom/testing/ctest_report.h and link Umicom::testing. Call UmiCtestReportImport with the complete byte span, read its summary and indexed records, then call UmiCtestReportDestroy. Import owns copied records; the input buffer can be released after success. Borrowed entry pointers expire when the report is destroyed.

The existing selected-test execution service and its public interfaces remain available. Both consumers use the same XML grammar. Suite inspection checks totals and duplicate identities across all records, while the established selected-test interface keeps its compatibility rules.
