From a saved note to a tested program

Work through short lessons, check your understanding and build three real projects in your own practice folder.

You do not need to understand an entire framework before making your first useful change. Start with a note, learn how its values and memory are handled, follow a small Assembly loop, and then put a shared Framework service behind a window.

Read a lesson→Try the questions→Build a project→Keep the evidence

1. Open your learning space

Open Umicom Education Studio and choose Learning practicum. In a source build, its executable is umicom-education.exe in the build’s bin directory. The application must be built before it can run; the separate build instructions explain that step.

You can reach the same practicum from Umicom Studio. On its welcome page, choose Open Interactive Learning, or use Help → AI Teacher. In Guided Learning, choose Open learning practicum and saved progress. The earlier lesson cards and C reference stay in that page; they have not been replaced.

The practicum opens without running a compiler, a student program or an AI model. Browse a lesson first. You will see an explanation, an example, a practical task and three questions. Open a learner record when you are ready to keep your work.

Three kinds of work, three clear places.

Read and answer questions in the practicum. Edit and build projects in Studio or your terminal. Keep actual CTest results with those projects. The quiz record does not replace the practical tests.

2. Create a learner record

For this walkthrough, enter workshop-learner in Learner ID to open and Workshop learner in Display name for a new record. Choose Open learner record.

The identifier is a short, stable name for your saved work. It may contain letters, numbers, a hyphen or an underscore, up to 48 characters. Avoid spaces, slashes and punctuation. The display name may contain ordinary UTF-8 text, up to 96 bytes. A character can use more than one byte, so a byte limit is not always a character limit.

Read the Active learner line before saving anything. Editing the ID field does not switch records by itself: you must choose Open learner record. Reopening an existing ID uses that record’s saved display name. Typing a different display name does not rename it.

The status message shows the exact storage path. The application uses an umicom/education/learning.sqlite file beneath the operating system’s user-data directory. Opening the database can create that local file; opening a new learner does not create learning events until you make a saved learning action.

Use fictional information.

This is local self-study, not an authenticated school account. The learner ID is not a password. Names, notes and answers are stored as plaintext, without encryption or a signed certificate. Do not add passwords, private customer details or confidential source material.

When another learning window has saved newer work, choose Reload saved record before continuing. A stale window is refused rather than silently overwriting newer progress. Save or explicitly discard a draft note before reloading.

3. Read your first C lesson

Select notes — 1. Values that belong to a note. Begin with the difference between capacity and count. A notebook may have room for eight notes while containing only one. Treating its free slots as saved notes is a programming mistake, not a display preference.

Now look at a character array. Ordinary C text ends with a zero byte, written '\0'. An array of 64 bytes therefore has room for at most 63 text bytes plus that terminator. The C project uses named constants so that the available space can be checked before a change is accepted.

C — part of the supplied Notes program
NoteBook book;
NotesInit(&book);
if (NotesSet(&book, "meeting", "Bring a notebook") != 0) {
    return 1;
}

NotesInit prepares an empty notebook. NotesSet asks it to save text under the key meeting. The return value tells the caller whether that request succeeded. The if statement stops this example from continuing as though a failed save had worked.

Read the whole explanation, then choose Mark lesson read. This records that you have read it; it does not pass its quiz. Choose Show hint when you need a starting point for the practice task. Viewing a hint is saved separately and does not reduce or increase a quiz score.

You may read any lesson at any time. To submit a later quiz within a course, first pass the preceding quiz in that course. The first lesson of each of the three courses is available independently. For a new programmer, the Notes course is the most comfortable starting point.

4. Check your understanding

For each question, open its answer list and choose one of the three responses. The initial Choose an answer entry is a reminder, not an answer. Choose Check my answers when all three are selected.

The feedback tells you which answers were correct and explains the idea behind each one. A wrong answer is useful: read the explanation, return to the example, then try again. Every accepted submission is a separate practice attempt. Clicking the button twice records two attempts, so there is no need to click repeatedly while waiting.

One correct answer gives 33 out of 100; two give 66; all three give 100. These percentages round down. All three answers must be correct to pass this small quiz. The record keeps both your latest score and your best score. After a pass, a later practice attempt does not erase the previous pass or relock the next lesson.

After passing the first quiz, the summary should show 1/12 quizzes passed. That describes the twelve practicum quizzes only, not the entire Umicom learning library or all of C programming. The practical project still needs to be built and checked.

Try this before moving on.

Explain the difference between “marked read”, “quiz passed” and “program tests passed” in your own words. These describe different kinds of evidence. None should be silently substituted for another.

5. Keep a useful learning note

Write a short explanation in Your learning note. For example:

Count is the number of saved notes. Capacity is the number of slots available. I should validate the text before changing either.

Choose Save learning note. Each lesson has its own note, up to 1,023 UTF-8 bytes. Saving an unchanged note does not add another event. Clearing the editor and saving deliberately clears the saved note; Discard note edits instead restores the last saved version.

Unsaved note edits stop ordinary lesson switching, record rebinding, reloading and window closing until you save or discard them. This protects the draft from an accidental navigation click. It is not crash recovery: unsaved edits are still lost if the process is killed or the computer fails. Save at natural stopping points.

The editor is read-only until a learner record has been opened. If storage reports an error, do not assume that your last action was saved. Keep any draft text you need, read the status message, and use a newly opened record connection when recovery is required.

6. Export a project without overwriting your work

A project is a small collection of source files, tests and build instructions. This batch provides three complete projects. Export makes a one-way copy into your own practice directory. It does not compile the code, download dependencies or change the Framework repository.

First create a parent folder. Open PowerShell and run:

PowerShell
New-Item -ItemType Directory -Path "C:\umicom-practice" -Force | Out-Null

Back in the practicum, select a Notes lesson. Enter C:\umicom-practice\notes-first in New project directory, then choose Export this course project. The destination notes-first must not already exist—even an empty existing directory is refused. The parent umicom-practice should already exist.

Open the exported directory in File Explorer. You should find CMakeLists.txt, notes.h, notes.c, main.c, test_notes.c, README.md and LICENSE. The header declares the contract, the implementation carries it out, the small application uses it, and the test checks it.

Exports never replace learner files. For a second copy, choose a new destination such as notes-second. If an export fails halfway through, it leaves the new partial directory for inspection instead of deleting files behind your back. Keep your practice directory under your own control; the exporter is not a security sandbox.

Expected program output

9. Follow a real Assembly loop

Choose the Assembly course and work through its first lesson. Export it into a new directory, such as C:\umicom-practice\stock-total-first. Use the same configure, build and CTest commands, but run umicom-stock-total.exe at the end.

This project sums small workshop quantities. Read stock_total.h first: both implementations return a 32-bit unsigned result. stock_total.c is the reference C implementation. stock_total.S is actual x86-64 Assembly, written for the GNU assembler—not pseudocode.

On a supported 64-bit x86 GNU or Clang build, configuration reports native x86-64 Assembly selected. The tests then compare the native routine with the C reference. On an unsupported platform, or when you disable Assembly, configuration explicitly reports that the C reference is selected. Do not call that a native Assembly test.

Assembly — complete stock_total.S
/* Umicom Framework teaching project: assembly / stock_total.S
 * Author: Sammy Hegab, Umicom Foundation. Licence: MIT.
 * This inspectable lesson is not a replacement for production Framework services. */
/* GNU assembler, AT&T syntax. This leaf routine touches no stack storage and
 * uses only caller-saved registers for the selected ABI. */
.text
.globl StockTotal
#ifndef _WIN32
.type StockTotal, @function
#endif
StockTotal:
    xorl %eax, %eax
#ifdef _WIN32
    testq %rdx, %rdx
    je .Ldone
.Lagain:
    addl (%rcx), %eax
    addq $4, %rcx
    decq %rdx
#else
    testq %rsi, %rsi
    je .Ldone
.Lagain:
    addl (%rdi), %eax
    addq $4, %rdi
    decq %rsi
#endif
    jne .Lagain
.Ldone:
    ret
#ifndef _WIN32
.size StockTotal, .-StockTotal
.section .note.GNU-stack,"",@progbits
#endif

On Windows x64, this routine receives the array address in RCX and the count in RDX. It clears the result, handles a zero count before reading memory, adds one 32-bit value, moves the address by four bytes and reduces the remaining count. The complete file also contains the System V path used by the Linux test build.

The normal example prints Workshop quantities: 24. The tests also compare many arrays and check wraparound deliberately. Arithmetic is modulo 2³² here: this is an instruction-level lesson, not a money or production-inventory calculation. A real business total needs its own checked-range policy.

To compare the explicitly labelled C-only path without replacing the native build, configure a separate directory:

PowerShell
cmake -S . -B build-reference -G Ninja -DBUILD_TESTING=ON -DUMICOM_LESSON_USE_ASSEMBLY=OFF
if ($LASTEXITCODE -ne 0) { throw "Reference configuration failed." }
cmake --build build-reference --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Reference build failed." }
ctest --test-dir build-reference --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Reference checks failed." }

Keep both outputs. Explain which result came from native Assembly and which came from C. The distinction matters more than seeing the same final number.

10. Put a Framework service behind your application

The third project replaces local notebook storage with the real Framework Data Server interface. Export it into a new directory such as C:\umicom-practice\framework-notes-first. Its headless program and test need an installed Umicom Framework SDK, or a parent build that already supplies Umicom::data.

An SDK is the set of headers, libraries and CMake package files another project uses to build against Framework. After the full suite build succeeds, a developer can install the built suite to a separate SDK prefix:

PowerShell
Set-Location "C:\umicom\Umicom-Applications"
& "C:\msys64\ucrt64\bin\cmake.exe" --install ".\build\windows-ucrt64-all-debug" --prefix "C:/umicom/Umicom-SDK"
if ($LASTEXITCODE -ne 0) { throw "SDK installation failed." }

This is an installation operation and writes files to that prefix. Use a dedicated location, not your source directory. Then configure the exported project with that location:

PowerShell
Set-Location "C:\umicom-practice\framework-notes-first"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B build -G Ninja -DBUILD_TESTING=ON -DCMAKE_PREFIX_PATH="C:/umicom/Umicom-SDK"
if ($LASTEXITCODE -ne 0) { throw "Check the installed Framework SDK path." }
cmake --build build --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Framework notes build failed." }
ctest --test-dir build --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Framework storage tests failed." }
& ".\build\umicom-framework-notes.exe"
if ($LASTEXITCODE -ne 0) { throw "The Framework example failed." }

The program should print Framework note: Workshop plan. Its test writes an original note, changes it inside a transaction, rolls the transaction back and checks that the original remains. It then commits a change and checks the new value. These are calls to the actual Data Server, not a substitute mock.

The suite also builds headless practical checks directly from these teaching files, under framework.education_workspace.practice.*. Those checks are useful before you have installed an SDK. They still do not automatically credit a learner’s quiz record.

Ownership stays explicit. The application creates the Data Server, passes a borrowed pointer to a view, and destroys the service after the view’s event loop finishes. The view requests reads and writes through public functions. It does not reach into a database or own a second copy of storage rules.

This window is a memory-storage exercise. Its note disappears when the application exits. That is different from the practicum’s SQLite learning record. The small example is also a developer-run program, not a packaged click-ready application; the terminal’s toolchain path supplies its development runtime.

12. Keep a record and return later

Enter a new absolute filename, such as C:\umicom-practice\workshop-learning.html, in New learning-record HTML file. Choose Export learning record. Open that file in a browser. It contains the saved learner name, quiz summary, per-lesson scores and learning notes, with Umicom branding included in the file.

The report contains saved state only; an unsaved editor draft is not silently included. Existing files are refused, so use a new filename for a later export. Keep exported reports private when they contain personal notes. They are readable plaintext and are not identity-verified certificates.

Close the learning window, reopen it and open the same learner ID. Saved reads, hints, attempts, best scores and notes should return. The question controls start with “Choose an answer” again; opening a record does not submit another attempt or run a project.

A learner record accepts up to 256 saved changes. Reading an already-read lesson, revealing an already-viewed hint or saving an unchanged note does not consume another change, but a new quiz submission does. At the limit, export the record and begin a different learner ID for further practice. The previous record is retained; it is not automatically deleted.

If storage is reported as malformed or recovery-required, keep it for inspection rather than resetting it. Close all learning windows before backing up the containing storage directory. A failed write is not a successful save; reopening establishes which committed state is available.

A useful finishing task.

Keep three things together: your edited project, the actual passing CTest output, and a learning note explaining one mistake you found and repaired. That is a small but real piece of engineering work.

Course readings to keep beside the projects

These readings mirror the built-in practicum. Use them beside the source, not as a replacement for running the tests. The broader foundations catalogue remains available in Studio.

notes · 1. Values that belong to a note

A notes application needs to remember text and explain whether it saved a change. Start by separating those two jobs. The text is data. A return value is a message from one function to another: the requested operation either succeeded or it did not.

In the Notes project, a NoteBook stores a small collection of notes. Its count tells us how many slots contain valid notes. The array may have room for eight notes, but that does not mean eight notes already exist. Capacity is available space; count is the amount currently used.

Read the declarations before running the program. size_t is the unsigned type used for object sizes and array positions. A char array stores bytes. Ordinary C text ends with a zero byte, written '\0'. That terminator takes one slot, so an array of 64 bytes can hold at most 63 text bytes plus its terminator. A displayed character may occupy several bytes in UTF-8.

These distinctions prevent a common user-facing fault: an application saying Saved when the text was actually too large. Our function checks its input and reports the failure instead of silently discarding the end of a note.

Supplied lesson example
char title[64];       /* At most 63 text bytes, then the terminator. */
size_t count = 0;       /* No notes have been created yet. */
const size_t capacity = 8;
Practice

Export the notes project. Locate NOTE_CAPACITY and NOTE_TEXT_CAPACITY in notes.h. Predict whether a 63-byte title fits in an array of 64 bytes. Write your prediction in the learning note before checking the code.

notes · 2. A function makes a promise

A function contract tells the caller what it may provide and what it may expect back. NotesSet receives a notebook, a key and some text. The caller still owns the input strings. The notebook keeps its own copies when the operation succeeds.

Look at the order of the checks. Null pointers, invalid keys and oversized text are rejected before the notebook changes. This gives the caller a useful guarantee: a failed update leaves the previous note intact. It also makes a unit test straightforward. Save a valid note, try an invalid replacement, then read the original note again.

A const char pointer allows the function to read a string without promising to modify it. It does not say that the memory will live forever. When NotesFind returns a pointer into the notebook, that pointer is borrowed. Copy the text when it must survive later edits or destruction of the notebook.

The header is the public promise; notes.c contains the implementation. Keeping them separate lets another application use the contract without depending on private decisions such as where the checks are placed.

Supplied lesson example
int result = NotesSet(&book, "meeting", "Bring a notebook");
if (result != 0) {
    /* Explain the failure; do not report that the note was saved. */
}
Practice

In test_notes.c, find the oversized replacement check. Describe the value that must remain after the rejected update. Add a similar test for an empty key.

notes · 3. Read only the entries that exist

An array provides indexed storage, not an automatic list of valid entries. A loop over notes must stop at count. With count equal to three, the valid indices are zero, one and two. Index three is already outside that set.

Memory safety is not only about avoiding a crash. Reading an unused slot may display stale or misleading text while the program appears healthy. Writing beyond an array can damage unrelated state. Both faults break the user’s expectation that one note operation affects only its intended note.

Trace the search loop on paper. Begin with i equal to zero, compare i with count, inspect the current entry only when the comparison succeeds, and then increment i. For an empty notebook the loop body must not execute at all.

The Notes project uses fixed-capacity storage so you can inspect its ownership without first learning an allocator. A production component may allocate memory dynamically, but it still needs the same boundaries: who owns the object, which entries are valid, and when the storage stops being usable.

Supplied lesson example
for (size_t i = 0; i < book.count; ++i) {
    /* Only entries below count are valid. */
}
Practice

Run the empty-notebook test. Then add notes until capacity is reached and verify that one extra insertion fails without increasing count. Do not remove the existing assertions.

notes · 4. Prove a change with a focused test

A useful test checks a promise that matters to the user. For the Notes project, the promises include inserting a new key, replacing an existing key without adding another entry, and keeping old data after a rejected change.

Configure, build and test are separate steps. CMake configuration describes the build. The build invokes the compiler and linker. CTest runs the registered checks. A successful configuration does not prove that a C source file compiles, and a successful compilation does not prove that its behaviour is correct.

Read a failing assertion as a question: which expected property did the program violate? Begin with the first failing check rather than deleting it. Keep the existing test and make the smallest justified correction. Run the focused checks again, then the wider relevant suite.

The quiz record in Education Studio is separate from this evidence. Passing a multiple-choice quiz does not compile your edited project. The real project tests run in your development environment, and their output must be inspected there.

Supplied lesson example
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --no-tests=error --output-on-failure
Practice

Build the exported notes project in Studio or PowerShell. Add an assertion that replacing meeting leaves count unchanged. Run CTest and record what the assertion proves in your learning note.

assembly · 1. Quantities as bits and bytes

A computer can represent a workshop stock count as a binary integer. Decimal 12 and hexadecimal 0x0C are two written forms of the same value. The value does not change merely because a debugger displays it in another base.

The Assembly project totals an array of uint32_t quantities. That type has 32 value bits. This lesson deliberately defines its total modulo 2 to the power of 32: a result that exceeds the largest value wraps around. The C reference and Assembly routine follow the same stated rule.

This is a lesson about machine arithmetic, not a recommendation for financial totals. A banking balance or stock-control service may instead require checked addition and an explicit overflow error. The appropriate behaviour belongs in the contract, not in an accidental side effect of the chosen instruction.

Before reading the Assembly, calculate a small total yourself. Use 12 notebooks, 8 pencils and 4 folders. The expected value is 24. You now have an independent expectation rather than merely trusting two implementations that could share the same mistake.

Supplied lesson example
uint32_t quantities[] = {12U, 8U, 4U};
/* Expected ordinary total: 24. The lesson contract uses modulo 2^32. */
Practice

Export the assembly project. Read stock_total.h and write down its overflow policy. Convert 12 to hexadecimal, then predict the total of the three supplied quantities.

assembly · 2. Follow the calling convention

A C caller and an Assembly function must agree on where arguments arrive and where the result is returned. That agreement is part of the platform’s calling convention. The same processor can use different conventions on different operating systems.

For this small x86-64 routine, the Windows branch receives the array pointer in RCX and the count in RDX. The System V branch used by this Linux build receives them in RDI and RSI. Both branches return the 32-bit total in EAX, the low part of RAX.

Read the conditional source rather than copying one register list into every platform. The routine uses only registers permitted to change across the call, makes no nested calls and does not allocate stack storage. Larger routines have additional preservation, alignment and unwind obligations.

On a platform without the supported Assembly build, the project explicitly selects its C reference and labels that choice. A C fallback is useful for portability, but it is not evidence that the Assembly implementation ran.

Supplied lesson example
#ifdef _WIN32
    /* array pointer: RCX; count: RDX */
#else
    /* System V x86-64: array pointer RDI; count RSI */
#endif
    /* result: EAX */
Practice

Open stock_total.S beside stock_total.c in Studio. Find the platform branch. Build the project and read whether the test output says Assembly or C reference.

assembly · 3. Trace the loop before changing it

An Assembly loop is a series of small changes to machine state. This routine clears the total, checks the number of remaining entries, adds one quantity, advances the pointer by four bytes and decreases the remaining count.

The first count check matters. A caller may supply a null pointer when the count is zero, because the function will not read any element. Removing the check would turn that documented empty-input case into an invalid memory access.

The pointer advances by four bytes because each uint32_t occupies four eight-bit bytes on the supported target. It does not advance by one whole arbitrary object. A mismatch between element size and pointer step would make the routine read the wrong memory.

Trace the state for two quantities, 12 and 8. After the first iteration the total is 12 and one entry remains. After the second, the total is 20 and none remain. The routine returns instead of reading a third element.

Supplied lesson example
/* Conceptual C equivalent of the Assembly loop. */
uint32_t total = 0;
for (size_t i = 0; i < count; ++i) total += quantities[i];
Practice

Use the two-entry example to write a trace table: iteration, total and remaining count. Add a zero-count test without removing the existing one, then explain why the pointer is not read.

assembly · 4. Compare independent expectations

Testing Assembly requires more than checking that the linker found a symbol. The returned values must satisfy the contract, including empty input, ordinary quantities and the deliberate modulo boundary.

The project keeps a readable C reference and compares it with the selected implementation. It also checks hand-calculated examples, because two implementations can repeat the same mistake. A deterministic generated sequence supplies more varied arrays without making test results depend on chance.

Run the tests before editing the routine. Save a copy of your explanation, change one operation, and observe which expectation fails. Restore or correct your change without deleting the assertion. Compiler diagnostics and failed tests are feedback, not obstacles to hide.

Do not infer a performance improvement simply because a function is written in Assembly. Establish correctness first. A meaningful performance comparison would need representative inputs, an appropriate measurement method and the same build settings. This project does not claim a speed advantage.

Supplied lesson example
/* Both a direct expectation and a reference comparison matter. */
CHECK(StockTotal(values, 3) == 24U);
CHECK(StockTotal(values, 3) == StockTotalC(values, 3));
Practice

Run the comparison tests. Explain the difference between a hand-calculated expected value and comparing two implementations. Keep the test output beside your source changes in Studio.

framework · 1. Put reusable behaviour in Framework

A notes window is an application view. Reading and writing Umicom-owned state is a shared service responsibility. The Framework Notes project keeps this distinction visible: its view requests storage through UmiDataServer and does not call SQLite directly.

The Master Controller composes the application and decides when its services are created and released. A small application-specific controller can translate a button click into a storage request. The shared Data Server remains the authority for persistence, and the view receives a result rather than reaching into a database handle.

This boundary is useful even in a small application. Another view can use the same storage contract, and a test can exercise that contract without opening a graphical window. A different backend need not change the meaning of the application’s request.

The project starts with a memory Data Server. Its contents deliberately disappear when the program ends. A later exercise may select SQLite explicitly, but a memory demonstration must never be described as durable storage.

Supplied lesson example
UmiDataServer *server = NULL;
UmiStatus status = umi_data_server_create_memory(&server);
if (status == UMI_STATUS_OK) {
    status = umi_data_server_set(server, "note", "Workshop plan");
}
umi_data_server_destroy(server);
Practice

Export the framework project. Locate every umi_data_server call. Identify which object owns the server and when it is destroyed. Confirm that the example does not call a SQLite API.

framework · 2. Save related changes together

A transaction groups related writes into one unit. Consider changing both a note and its category. Either both changes should become visible together, or the earlier state should remain. A half-applied update could mislead another panel that reads the category beside the text.

The Framework Data Server exposes begin, commit and rollback through its public C contract. Begin starts the unit of work. Commit accepts it. Rollback restores the previous state when the operation cannot complete. Every return value matters; issuing commit is not the same as proving it succeeded.

The reference project includes a rollback test. It saves an original note, begins a transaction, changes the note and rolls back. A later read must return the original note. That is observable behaviour, not merely a check that a function was called.

The Education Workspace uses this same Data Server for learning records. It saves an accepted action and its new revision in a transaction. When another open application has a newer revision, the stale writer is rejected so an old view cannot silently replace new progress.

Supplied lesson example
status = umi_data_server_begin(server);
if (status == UMI_STATUS_OK) {
    status = umi_data_server_set(server, "note", "Updated plan");
    if (status == UMI_STATUS_OK) status = umi_data_server_commit(server);
    else (void)umi_data_server_rollback(server);
}
Practice

Run the Framework project tests. Read the value before, inside and after the rollback. Explain why calling commit without checking its result is not enough.

framework · 3. Connect the window to the service

The optional GTK view has an editor, a Save button, a Load button and a status label. Those controls do different jobs. Typing changes the editor buffer; it does not save the note automatically. Clicking Save requests a service update and then displays the returned outcome.

A signal connects a user action to a callback. The callback receives a borrowed pointer to application state. That state must remain alive for as long as the callback can run. Closing the window ends the application run before the owner releases its Data Server.

The view uses plain text for stored content and status messages. User-written note text must not be interpreted as a command or as trusted markup. A note containing angle brackets is still a note, not an instruction to execute something.

The GUI is optional so the shared storage example and tests can be built without GTK. Enabling the GUI requires the actual GTK development dependency. A headless pass does not establish that the buttons, focus handling or window lifetime have passed their graphical checks.

/* The callback translates an action into a service request. */

/* Load: Data Server get -> replace editor text only on success. */

framework · 4. Keep the learning record and the build evidence honest

You now have two useful records: your self-study quiz progress and the source plus tests of a real project. They answer different questions. The quiz checks your interpretation of a lesson. The project build and tests check the compiled implementation that you edited.

Use Studio’s existing Guided Learning page to open the same new practicum window. The earlier foundations lesson cards remain available, so you can revisit a topic without losing that established route. The standalone Education Studio and Studio practicum use the same Framework learning-record service.

Before publishing a change, inspect exactly what is staged. Keep existing tests, comments and licence notices. Make a focused commit on the intended main branch only after validation. In a suite with submodules, push changed child repositories before the parent records their revisions.

The exported HTML learning record is a local self-study summary. It is not an identity-verified qualification, a signed audit trail or proof that every practical exercise ran. Its notes are plaintext, so do not add passwords, private customer data or live financial information.

What you seeWhat to check next
The quiz is not ready.Mark the current lesson read and pass the preceding quiz in the same course. Choose all three answers before submitting.
A lesson will not change.There are unsaved note edits. Save them or deliberately discard them first.
Storage is busy or newer progress exists.Another connection may have saved newer work. Preserve your draft, reload, and review the active learner before submitting again.
The export destination exists.Choose a new directory or filename. Existing learner files are never overwritten by export.
CMake cannot find UmicomFramework.Check that the SDK install succeeded and point CMAKE_PREFIX_PATH at its installation root, not at a source folder or one header file.
The Assembly build selects C.Read the configure message. Native Assembly requires the supported 64-bit x86 GNU/Clang path; C fallback is a different, explicitly labelled check.
A project test fails after your edit.Read the first failed condition, compare actual and expected behavior, and fix the cause. Keep earlier tests and comments.
The GUI dependency is unavailable.Continue with the headless project, but do not treat it as validation of the optional window.
