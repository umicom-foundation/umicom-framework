Choose project presets and a program working folder

A preset is a named set of project options. CMake has separate names for configuring a build folder, building targets and running tests. Studio's Project Settings can save one name for each stage, so a project does not have to reuse the same name for all three.

Use a project's existing presets

  1. Open the project folder in Studio. Read its CMakePresets.json and, if present, your local CMakeUserPresets.json. Find the exact names in configurePresets, buildPresets and testPresets. These files belong in the project root. See the official CMake preset guide for inheritance and required tool support.
  2. In the Build panel, choose Project Settings. Clear the existing shared CMake preset field before filling any separate stage field. Keeping both forms filled is rejected so an old setting cannot silently override a new one.
  3. Enter the configure name in Configure preset (separate stage), the build name in Build preset (separate stage), and the test name in Test preset (separate stage). For example, one project might use notes-configure, notes-build and notes-check. Use names defined by your own project.
  4. Set Build folder to the effective binaryDir of the chosen presets. Set the configuration consistently too. Studio still uses these fields for diagnostic paths, installation, packaging and debugger checks; it does not discover or verify a preset's resolved output folder. The three presets should describe the same build tree.
  5. Review the executable and install paths. Apply Settings saves the values without starting a build or granting trust automatically. Select the trust checkbox only after reviewing the project's code and build scripts.
  6. Choose the intended action in Studio. Existing multi-step actions can configure before building and build before running; every stage uses its own setting. Follow progress and failures in the Build panel.

Which options control each stage?

SelectionBehaviour
Explicit configure presetCMake resolves that preset's generator, environment, cache values and binary directory. Studio does not add its ordinary generator or compiler fields to that command.
Explicit build presetThe preset controls its targets, configuration and parallel jobs. The form's ordinary target, configuration and job count do not override it. Clean uses the build preset with an explicit clean target; the selected generator must provide that target.
Explicit test presetCTest uses its filters, configuration and execution settings. Studio continues to request failure output and to treat an empty selected suite as an error.
A blank stage fieldThat stage uses ordinary profile fields. It does not borrow a name from another stage. This allows a configure preset with ordinary build-folder commands when a project has no build or test preset.
Only the original shared presetExisting behaviour is retained: configure and test use that name; Build uses the saved build folder. Clear all separate stage fields when retaining this arrangement.
Install, Package and native DebugThese continue to use the saved profile paths and their existing workflows. There is no install, package or workflow-preset selector in this form.

Preset names are passed as individual process arguments. They are not shell commands. The chooser below reads directly declared names. CMake and CTest still resolve inherited settings and report missing, disabled or invalid presets when the action runs. Studio does not guarantee that selected stage names use the same build tree.

Choose names from the project files

  1. Open Project Settings and check Project folder. This read-only field shows the open project's absolute root. Open another project to change that root.
  2. Choose Read project preset files. Framework reads CMakePresets.json and CMakeUserPresets.json in that folder on a worker, so the form can remain responsive. Wait for the read to finish before applying settings; Cancel remains available while it is running. Opening the form alone does not read them. No build tool starts and no file is written.
  3. Open the searchable list. Each row shows its stage, exact name, optional display name, and whether it comes from the project or user file. Choose a row to inspect its description, directly declared configure reference and build folder. These values have not had macros expanded or inherited settings applied.
  4. Clear the shared CMake preset field, then choose Use selected name. This copies only that row's name into its configure, build or test field. It preserves the other stage names and ordinary settings. Hidden base presets and entries with a literal false condition cannot be selected.
  5. Repeat for the other stages you need. Check the effective build folder and configuration using the project's documentation. Choose Apply Settings to save, or Cancel to discard the edits. Reading a list and copying a name do not save settings or grant permission to execute the project.

If you change the project folder after reading, read again before selecting. If you edit a preset file on disk, refresh the list too: it is a snapshot of declarations, not a live view. A name may still become unavailable before a later build.

Understand an incomplete list or a read error

Read project preset files reads only direct declarations and marks unread includes. Choose Read included presets when you want to discover supported shared definitions. The expanded action follows declared local paths, including paths outside the project, so use it only for preset files you trust. It shows each definition's actual source file and resolves inherited configure references, build-folder expressions and literal condition metadata.

Review included definitions

  1. Choose Read included presets and wait for the file and declaration counts. The read runs on a worker. Cancelling or closing the form retires the pending result.
  2. Select a row. Inspect Source to identify its defining file. An inherited value is marked in the details. Build-folder expressions remain expressions; check their effective location with your project's CMake settings before using that path elsewhere.
  3. Choose Use selected name for the intended stage. This copies one name into the form. Check the other stages, then apply settings separately.
  4. If the read fails, inspect the reported file. Missing required includes, repeated names, include or inheritance cycles, and inheritance from an inaccessible file reject the whole snapshot. Manual preset entry and the direct-only action remain available.

Expanded discovery accepts literal include paths and ${sourceDir} or ${fileDir} expressions where the preset format permits them. Environment, vendor and other include expressions are reported as unsupported rather than silently skipped. No environment variables are expanded by this reader.

The expanded read accepts at most 64 documents, 2 MiB per document and 8 MiB overall, with up to 128 declarations across configure, build and test stages. Its owned JSON reader limits each document to 262,144 nodes and 128 nesting levels. A failed read publishes no partial list. File reads are separate snapshots; refresh after edits.

Names, display names, descriptions and hidden state are local to each definition. The displayed inherited fields follow parent order, with local fields taking precedence. Object conditions, environment settings, cache entries and macros within preset values are left to CMake. This reader does not validate the entire CMake schema, list package/workflow presets or prove that a selected configuration can build successfully.

One standard file may be absent. If both are absent, the form reports that nothing was loaded. A present but empty, malformed or unreadable file rejects the whole read, including when the other file is valid. A failed refresh clears the old choices so they cannot be mistaken for a current result. Manual fields remain unchanged.

For the direct-only action, each file must be ordinary UTF-8 JSON and no larger than 65,535 bytes. The reader accepts an optional UTF-8 byte-order mark, limits the combined catalogue to 128 declarations, and applies the shared JSON reader's 4,096-token and 128-level nesting limits to each file. Names must fit the profile's 160-byte field, including the ending zero byte. Duplicate names within a stage are rejected across both files; the same name in different stages is allowed. A final-component symbolic link or special file is refused by the shared file reader. Parent-directory aliases may be followed, so this is not directory confinement.

  1. For a read error, check the full project folder, file permissions and JSON syntax in both files. Correct duplicate names or oversized fields, then read again.
  2. For a missing choice, check whether it is declared in an included file. Enter its name manually if necessary, and keep the ordinary profile paths consistent with its resolved settings.
  3. If CMake rejects a selected name later, review the condition, inheritance, environment and installed CMake support. The declaration reader checks the data it displays; it is not a complete CMake schema validator.

Choose where the program starts

The program working folder is the starting folder used when your application opens a relative file such as data/settings.json. It is separate from the location of the executable.

  1. In Project Settings, set Program to run to the executable's path relative to the project, such as build/bin/notes.exe, or its full path.
  2. Leave Program working folder blank to start in the project root. Enter sample data to start in that project subfolder, or a complete path to use another folder. The folder must already exist when the program starts.
  3. Apply Settings. Both Run and the native Debug workflow resolve the folder through Framework. The executable path still starts at the project root; it is not moved underneath the data folder.
  4. If the program cannot find a relative file, check where that file sits relative to the chosen folder. If launching fails, confirm the folder exists and is accessible. Applying settings does not create it.

On Windows, use a full drive path such as C:/Users/You/Documents/notes-data, a complete network path, or an ordinary project-relative folder. A drive-relative path such as C:notes or a rooted path without a drive is rejected because its meaning depends on process state. Build tools continue to run from the project root to find their preset files.

Saved settings and recovery

Framework saves the complete profile in one transaction. If another window saves first, reopen the settings and review its values before retrying. A missing required field or a damaged record is reported; it is not replaced with an empty preset or working folder. Older stored profiles receive empty new fields and preserve their earlier behaviour. Older executables may refuse the expanded format; use matching Framework and Studio builds.

Cancel closes the form without applying changes. An acceptance error leaves it available for correction. Controls retained by extensions after a form closes cannot apply another result. Contributors should keep the dialog handle alive while its callback context exists, destroy it before releasing that context, and clear their stored handle if destroying it from inside a callback.

Extend the shared implementation

UmiBuildProfile owns the stage names and working folder. Initialize it with umi_build_profile_init; appending public fields means every consumer must be rebuilt. Providers validate the record before constructing commands. The profile store compares revisions before saving, and the GTK form only collects values for its application's acceptance callback.

UmiBuildProfileLaunchDirectory takes an already absolute project root and resolves the folder without inspecting storage or changing the process directory. It updates the output only on success. Use this shared operation for additional launch surfaces so Run and Debug keep the same meaning. A valid profile does not prove that a tool, preset, executable or folder exists; those checks belong to the operation using it.

UmiProjectPresetCatalogue owns bounded copies of the declarations. Parsing and selecting names are independent from process execution, so other front ends can reuse the same service. Its two file reads are not an atomic disk snapshot. File I/O runs off the GTK thread; closing a form discards its pending result when the read finishes. It does not forcibly interrupt a blocked operating-system read.

When extending the native chooser, keep GTK mutations on its owning thread. Retain the controller through asynchronous completion, revoke callbacks when the owner destroys the form, and guard synchronous notifications during selection. A newly added control must not apply settings as a side effect of displaying a result.
