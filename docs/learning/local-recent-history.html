Manage local recent history

A recent-item registry holds small descriptions of resources such as project folders and lessons. Removing a description is different from deleting the resource. Studio uses the shared registry for its Welcome page, and other applications can use the same model while choosing their own local storage and presentation.

Choose ownership before adding buttons

  1. Create or load one UmiRecentItemRegistry for the feature. Its owner destroys it after all users have finished.
  2. Choose an absolute metadata path in an existing trusted local directory. Resolve that path once; do not let a later working-directory change redirect writes.
  3. Copy a record with umi_platform_recent_items_registry_find. Store its ID and revision in the displayed action, rather than retaining a pointer into private registry storage.
  4. Serialize mutations through one owner. The registry and saved file do not implement multi-writer conflict resolution.
  5. On removal, call UmiRecentItemsRemoveLocal with the displayed ID, revision and metadata path. Update the visible list only after inspecting its status.

Why both an ID and a revision?

The ID identifies a record. The revision identifies its state within the live registry. If the same record was touched, pinned or replaced after a button was displayed, the old revision is stale. Removal returns UMI_STATUS_INVALID_STATE; refresh the list and let the user review the current entry. A change to an unrelated record does not invalidate this item’s revision. Revisions are live model counters, not hashes of the saved file and not persistent cross-process lock tokens.

UmiRecentItemSnapshot displayed;
UmiStatus status = umi_platform_recent_items_registry_find(
    registry, selected_id, &displayed);
if (status == UMI_STATUS_OK) {
    status = UmiRecentItemsRemoveLocal(registry, displayed.id,
        displayed.revision, absolute_metadata_path);
    /* Inspect status before changing the user-visible list. */
}

This fragment assumes that the registry, selected ID and path already belong to a valid application operation. A real interface copies the snapshot while rendering and uses that earlier revision when the user activates the button.

What the shared operation does

  1. Validate the arguments, find the item and check its revision.
  2. Allocate a private copy of the bounded registry.
  3. Remove the entry from that candidate.
  4. Serialize and replace the metadata file through the native local-file service.
  5. Publish the candidate into the existing live registry address only if saving succeeded.
  6. Release the temporary candidate on every path.

The listed URI is never opened or deleted by this operation. Pinned entries can be removed explicitly. The old live registry remains unchanged on failure. Other records retain their values, and the registry address stays stable for borrowers. This operation may block on file I/O; arrange ownership and worker completion carefully in a responsive application.

StatusMeaning and response
OKRefresh the visible history from the live registry.
INVALID_STATEThe displayed item changed. Refresh and request a new deliberate selection.
NOT_FOUNDThe item is no longer present. Refresh without inventing a deletion.
INVALID_ARGUMENTCheck the supplied identity, nonzero revision and ordinary absolute file path. A directory destination is refused.
Other errorReport storage, capacity or allocation failure. Keep the live row and allow a deliberate retry after the cause is understood.

Build the standalone SDK example

First install a compatible Framework SDK containing the platform component. The commands below assume that installation is at C:\umicom\installed\framework; substitute your actual installation path. The example deliberately consumes that SDK rather than compiling a second Framework source tree. Run one command at a time and stop on an error.

Set-Location "C:\umicom\Umicom-Applications\framework"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

cmake -S ".\examples\recent_history" -B ".\build\recent-history-example" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DUMICOM_EXPECTED_SDK_PREFIX="C:/umicom/installed/framework"
cmake --build ".\build\recent-history-example" --parallel 2
ctest --test-dir ".\build\recent-history-example" --output-on-failure --no-tests=error

Configure checks the package location and SDK environment metadata. A stale cached package outside your chosen prefix is rejected. Use a new example build directory or explicitly correct the cache; do not bypass the origin check. Compiler success and the seven console cases do not qualify the Studio GUI.

Run a sample you can inspect

Use a dedicated sample metadata file. Do not point this demonstration at Studio’s own preferences: the program writes two named teaching entries. It preserves other valid records but is not a general history editor. A malformed existing file is refused.

New-Item -ItemType Directory -Force "C:\umicom\_local\practice\recent-history"
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" remove
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" stale
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" storage-refusal

remove confirms that the sample project entry was removed while a lesson entry remained, then reloads the saved file. stale changes the live item after capturing its revision and confirms refusal. storage-refusal deliberately supplies the parent directory as the destination, checks refusal and compares the original metadata bytes. Each mode seeds its two sample entries first, so it can be repeated in this dedicated file.

Keep a project near the top with a pin

UmiRecentItemsSetPinnedLocal accepts the registry, copied item ID, copied item revision, an integer pin value and the absolute metadata path. Zero means unpinned; any nonzero value means pinned. It saves a candidate before publishing the preference, just like removal. A stale revision is refused even when the requested value matches the current value.

UmiStatus status = UmiRecentItemsSetPinnedLocal(registry,
    displayed.id, displayed.revision, 1, absolute_metadata_path);

Pinning preserves the resource URI, last-opened time and open count. It does not open a project or grant trust. Queries place pinned entries ahead of unpinned ones; automatic trimming keeps pinned entries. Explicit history removal remains possible.

& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" pin
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" unpin
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" pin-stale
& ".\build\recent-history-example\umicom-recent-history.exe" "C:\umicom\_local\practice\recent-history\sample-history" pin-storage-refusal

The first two modes reload the saved preference and confirm that resource metadata was kept. The refusal modes verify that a stale selection or directory destination cannot publish the new pin. Each run uses only the dedicated teaching file.

Review the limits

Native replacement avoids publishing a partially serialized file during normal operation. It does not guarantee survival of power loss or provide a transaction with a second process. Another writer can replace the metadata file without changing your in-memory item revision. Use one writer and a trusted directory. The path checks reject a final link or device; they are not a filesystem sandbox against changes to parent directories.

Metadata contains resource paths and labels. Keep real history local and outside public commits. Example state is also separate from source: do not copy its generated files into an SDK or a lesson package.

Follow the source

The public contract is include/umicom/platform/recent_items.h. The private transaction is src/platform/recent_items_remove.inc, included by recent_items.c. The source regressions in tests/platform/test_recent_items_remove.c cover stale selection, unrelated changes, pinned entries, native paths and failed-save preservation. The corresponding pin transaction is src/platform/recent_items_pin.inc, with ordering and failed-save cases in tests/platform/test_recent_items_pin.c. The standalone consumer lives in examples/recent_history.

Studio’s UmiStudioServicesForgetRecentWorkspace restricts removal to workspace records. Welcome uses copied action identities and weak window references so retained controls do not reach a destroyed host. Its user guide is docs/recent-projects.html in the Studio module.
