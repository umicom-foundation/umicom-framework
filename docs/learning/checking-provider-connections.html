Check a saved provider connection

A connection check asks a server for its model catalogue and looks for the model you saved. You approve the destination before each request. No prompt, source file, chat history or tool request is sent. Saving settings and managing local keys remain separate operations; neither starts this check.

A successful check means the reply listed your model. It does not establish that the model is loaded, that your account can run it, that you have a balance, or that a chat will succeed. It does not change Studio's active AI provider. Generation, model downloads and automatic coding actions are separate workflows.

When ready to make a separate generation request, choose Chat with selected saved connection… and follow Chat with a saved connection. That action has its own prompt/context review, local password verification and approval; the catalogue check never starts it automatically.

1. Prepare a supported connection

  1. In Studio, open AI Coding → Connections… and wait for the saved settings to load. See Edit provider connections if this is your first connection.
  2. Choose New or select an existing connection. Use one of the settings below, enter the exact model identifier you intend to use, and enable the connection.
  3. Choose Save draft. Resolve any saved-settings conflict before continuing. The check uses the saved record, never an unsaved draft.

Remote checks accept only the official OpenAI destination above. Extra ports, trailing slashes, gateways and lookalike hosts are refused. This check does not yet support other remote providers or a local server that requires a key. Local loopback means this computer; it does not prove which process is listening there.

For OpenAI, use a model identifier available to your API account. The check follows the official model-list endpoint and uses the saved API key. ChatGPT product access alone is not the credential used by this request. Organisation and project header overrides are not configured by this adapter; it uses the key's default scope. See the API authentication documentation.

Start a compatible local model server separately. With llama.cpp, the model ID may be a model path unless an alias was configured. Copy the ID reported by your server, or use its --alias option when starting it. A router may list models before they are loaded. See the llama.cpp server guide. The saved model field accepts up to 128 ASCII letters, digits and the characters ._-/: excluding spaces; choose a compatible alias if necessary.

2. Keep the key in the local credential store

  1. For a remote connection, choose Manage local keys…. Create the local profile if needed, then save your API key under the alias used in the connection reference.
  2. Use the same application and profile scope as the connection. Studio currently uses studio and desktop for the current operating-system user.
  3. Return to Connections. Enter your local profile password in the model-check password field. This password is verified locally; it is not the provider's API key and is not sent to the server.

See Manage local provider keys for storage and recovery limits. Windows Credential Manager is the current native adapter; other platforms report unavailable for remote checks. Local checks do not need a password or key. Keys stay out of the settings database, repository and result label. The local password enforces an application policy; it does not isolate the operating-system vault from other programs running as the same user.

3. Review, approve and check

  1. Read the displayed GET destination, model and saved revision. GET requests data from the service; here it requests only the model list.
  2. Check I approve this model-catalogue request to the displayed destination. Changing settings or typing another password invalidates that approval.
  3. Choose Check saved connection. The password field clears immediately. A worker performs the request while the settings form is disabled; the window stays responsive.
  4. To stop waiting, choose Cancel connection check. Cancellation cannot retract a request already transmitted. The worker releases its credential and HTTP resources before completion is reported.
  5. Read the result, HTTP status, catalogue count, connection ID and saved revision. Results always name the reviewed record; they are not a claim about later edits.

The worker checks the saved revision before credential access and again afterwards. A settings change blocks a stale check before dispatch. A later edit cannot revoke a request already in flight. Normal closing waits for the operation; forced window retirement requests cancellation and keeps worker resources alive until completion.

4. Understand failures

ResultWhat to do
Model listed, HTTP 200The catalogue check succeeded. Qualify chat and inference separately before relying on them.
Model not found, HTTP 200Compare the saved ID with the provider's catalogue or the local server alias. Save and review the correction.
Permission denied, HTTP 0Check approval, profile scope, local password and credential availability. A rejected check clears the password. Wait before retrying; repeated denied attempts introduce a longer delay in this window.
HTTP 401 or 403The remote service refused access. Review the key and its permissions privately in the provider's account settings.
Changed settings or busyReload saved settings and review the connection again. HTTP 429 or 503 instead indicates that the remote service asked you to wait.
UnavailableHTTP support, local storage or the native credential adapter is unavailable. There is no simulated success or plaintext fallback.
Timeout or I/O failureCheck that the service is reachable and the local server is running. The adapter does not retry, follow redirects or use a proxy.
Malformed or oversized replyThe result is inconclusive. Check server compatibility; raw service output is not displayed or copied into logs by this adapter.

A zero HTTP status means no valid response status was recorded; it does not prove that no network attempt occurred. Local key removal does not revoke a provider-issued key. Revoke a compromised key through the provider.

For contributors

Link Umicom::provider_connection_checks and include umicom/provider_connections/check.h. Prepare a plan from saved settings, show it to the user, then run that unchanged plan only after explicit approval. Give each worker its own Data Server connection and keep borrowed inputs alive until it returns. Do not hold a settings transaction across credential verification or network I/O.

The adapter reuses Framework's profile-verification service and complete JSON parser. Reply storage is limited to 65,535 bytes, parsing to 4,096 tokens and 128 nesting levels, and decoded catalogue IDs to 512 bytes. Required catalogue fields cannot be duplicated. TLS certificate and host verification are enabled for HTTPS; redirects, proxy routing and netrc credential loading are disabled. Caller-owned password, key and response buffers are cleared after use; library and operating-system internal copies are outside that ownership boundary.

UMICOM_PROVIDER_CONNECTION_CHECK_HTTP accepts AUTO, ON or OFF. AUTO enables transport when pkg-config finds libcurl 7.85 or later; ON requires it; OFF exposes the API with an unavailable result. Installed CMake consumers resolve the same optional dependency. Capability availability is a build property, not a successful connection test.

Add another provider through an explicit destination policy, credential policy and response decoder, with denied, stale, malformed, cancellation and lifetime coverage. Do not generalise this adapter into an arbitrary credential-bearing URL request. The native editor owns presentation; shared request behaviour belongs in Framework.
