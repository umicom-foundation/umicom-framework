1. Build the lesson

A source file contains instructions written for a compiler. A build directory contains the resulting program and temporary build files. Keep these separate so you can inspect and change the source without confusing it with generated output.

This project uses the existing Framework Data Server. It does not provide a second database implementation. After merging the update, open PowerShell and run:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\examples\data_safety" `
    -B ".\build\data-safety-practice" `
    -G Ninja `
    -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "Configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build ".\build\data-safety-practice" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed." }

The complete source is framework\examples\data_safety\notes_transaction.c. The focused project is useful for learning and quick checks; it does not replace a full build of Studio, Bank, Desk and the other applications.

2. Understand a transaction

Suppose the Notes application stores two records: the note itself and the statement that someone reviewed it. Saving only the review state would be misleading when the note text was not saved. A transaction groups those writes into one decision.

Begin→Change records→Commit or roll back

Commit accepts the complete group. Rollback cancels its changes and returns to the saved state before the group began. In this example, the first experiment is cancelled, and the second group is accepted.

status = umi_data_server_begin(server);
if (status == UMI_STATUS_OK)
    status = umi_data_server_set(server, "notes.workshop",
        "Prepare and test the Notes exercise.");
if (status == UMI_STATUS_OK)
    status = umi_data_server_set(server, "notes.state", "reviewed");
if (status == UMI_STATUS_OK)
    status = umi_data_server_commit(server);

Each result matters. Do not ignore a failed write and commit the remaining changes as though the complete task succeeded. The example checks results, rolls back an active unsuccessful group where possible, and destroys its server before returning.

& ".\build\data-safety-practice\bin\umicom-data-transaction-example.exe"

You should see:

After rollback: Prepare the Notes exercise.

Practice complete. Memory only; no files, devices or network connections were opened.

The original note survived the cancelled experiment. The second group left two records. All of this happened in memory: closing the program releases the records. A program using a SQLite-backed server has a different storage lifetime, but should use the same transaction operations.

Now run the checks:

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\data-safety-practice" `
    --parallel 2 --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Review the failed checks." }

A skipped SQLite case means that its optional backend was unavailable or deliberately disabled. A skip is not proof that the SQLite path worked. This source package has Linux test results; your Windows compiler and runtime still need their own run.

4. Introduce another worker

A thread is an independently scheduled sequence of work inside a process. An editor might save a note while another worker refreshes a list. Protecting one function call at a time is not enough to protect a transaction that spans several calls.

With this update, the worker that successfully begins a transaction retains responsibility until it commits or rolls back. A different worker using the same server receives UMI_STATUS_BUSY for data operations. Its write has not been accepted; it must not tell the user that the work was saved.

Worker AWorker B
Begins a transaction.Attempts to save a different record.
Still owns the unfinished group.Receives BUSY; no record is changed.
Commits or rolls back.May submit a fresh request afterwards.

The regression tests create actual native threads. They check reads, writes, deletion, begin, commit, rollback, counting, enumeration, snapshots and the trusted SQL entry point. No native thread identifier is treated as a permanent identity: the core assigns non-reused tokens so a later worker cannot inherit an old transaction accidentally.

A thread is not an authenticated person. This ownership rule prevents accidental transaction mixing. It does not implement user login, permission checks or financial maker/checker approval.

5. Handle failure honestly

A failed read is not a missing note

A missing key gives UMI_STATUS_NOT_FOUND. A failed SQLite binding, a storage error or an insufficient destination buffer must produce its own failure. Otherwise a caller might create a replacement note and hide the real fault.

A count needs a result code too

size_t count = 0;
UmiStatus status = UmiDataServerCountChecked(server, &count);
if (status != UMI_STATUS_OK) {
    /* Report the failure; do not describe this as an empty notebook. */
}

The older count function remains available and returns zero on failure for compatibility. New callers should use the checked function when the distinction matters.

A failed rollback may leave work unfinished

When SQLite still has an active transaction after a rollback error, Framework retains its owner and refuses ordinary work. The owner can retry rollback after the cause has been addressed. It must not silently start a new group or report that cancellation succeeded.

SQLite can also abort a whole transaction automatically. The service records that loss, refuses further ordinary statements and requires the original owner to acknowledge it by calling rollback. That call returns an error because it did not perform a new rollback. Consumers such as Desktop Workspace can then stop the current instance and ask for a clean reopen rather than continuing with uncertain assumptions.

Keep your own diagnostic text

char explanation[512];
UmiStatus copyStatus = UmiDataServerCopyError(
    server, explanation, sizeof explanation);

This copies the currently retained diagnostic into memory you own. It is not a complete history or a guarantee that the message belongs to the immediately preceding request when several callers share a server. Keep each operation's status and correlation information in your controller.

6. Understand memory and lifetime

The server owns its memory records and rollback backup. The caller owns strings passed to it and the output buffer used for a read. Enumeration callbacks receive borrowed strings: use them only during that callback or copy them before retaining them.

Callbacks run while the server lock is held. Direct re-entry into a data operation on that server returns BUSY. Do not destroy the server, jump out of the callback, wait for another worker or perform long-running tasks inside it. Cross-server callback ordering remains your responsibility.

The Master Controller must ask dependent Slave Controllers to stop work and join their workers before destroying shared services. An internal lock cannot make a freed object safe to use. Nor does a worker disappearing automatically commit or roll back its transaction.

The memory-backend limits remain unchanged: 2,048 records, 191 usable key bytes and 4,095 usable value bytes. SQLite has separate limits. Text limits count bytes rather than displayed letters, which matters when using UTF-8.

7. Practise and check your answers

  1. Change the first experiment to a different sentence. Explain why rollback still returns the original sentence.
  2. Add a third record to the committed group. Predict the final count, then build and run again.
  3. Find the compete_0 test. Explain why BUSY is preferable to a successful write that disappears later.
  4. Find rollback_denied. Identify the check that proves the backend transaction is still active.
Compare your answers

The saved pre-transaction state is restored by rollback, independently of the draft sentence. A successful third write raises the final count to three. BUSY tells the competing worker no change was accepted. The rollback-denial test compares the Framework observation with a real SQLite transaction and verifies ordinary writes are refused until rollback succeeds.

Windows build troubleshooting

The related boot-media repair preserves the former disk-attribute query and compiles the active query only when the required SDK symbols are present. Missing declarations, malformed responses and an offline disk are not converted into permission to write. A reduced SDK may therefore build the ordinary-file tools while physical-device acquisition remains unavailable.

Keep UMICOM_BOOT_MEDIA_ENABLE_DEVICE_WRITES=OFF. This lesson does not qualify USB writing, optical burning, firmware booting or any physical disk. The full build and publication commands are in the separate Build-and-Git document.
