1. Understand what you are building

You do not need to replace Windows to learn how an operating system starts. In this lesson, you will prepare a small Umicom OS image and run it in an explicitly selected virtual machine. Your working documents stay on the host computer; the supplied guest profile has no host disk, shared folder or network interface attached.

The host is the computer doing the work. When you use Windows and a Linux terminal in WSL, that Linux environment is the build host. The guest is the small operating system started by QEMU. Compiling a host tool does not compile the guest kernel, and opening a file successfully does not prove that a guest booted.

This lesson supplies source and tools, not a prebuilt OS. The native components and fixture tests have been exercised. The selected Buildroot cross-build, actual guest boots, Windows execution and BIOS/UEFI boot remain acceptance work for the target environment. Expected boot results below are things to establish, not results already obtained.

The operating-system profile contains a Linux kernel, a small initialisation program, two one-shot checks and a restricted recovery console. It is a text-console foundation. It does not yet provide a graphical desktop, disk installation or persistent guest documents.

PartWhat it does
Framework host toolChecks inputs, records their identity, starts explicitly chosen build tools, creates the archive and evaluates observations.
BuildrootBuilds the selected cross-toolchain, Linux kernel and guest programs using the existing Umicom recipes.
Guest initRuns as process 1, prepares the guest environment, supervises the two checks and retains recovery.
Framework probeUses the actual in-memory Data Server to check commit and rollback inside normal guest operation.
QEMUStarts the selected machine profile. Its serial output supplies observations that the native tool can evaluate.

Reusable host behaviour belongs to Umicom Framework. The kernel choices, initialisation program and independent recovery implementation belong to umicomOS. This division lets a later installer use the same tools without creating a second image engine.

2. Put the files in the right places

Merge the source folders into their matching checkouts. Keep the spelling of umicomOS, including its capital letters. Do not copy it into an application module named os.

C:\umicom\
    Umicom-Applications\
        framework\
    umicomOS\
        framework\
        boot\foundation\
        image\native\
        tools\os-image\

The two framework directories are checkouts of the same Framework repository. The build examples below explicitly select the one inside Umicom-Applications. After publication, align the OS checkout's Framework submodule using the separate Build-and-Git instructions.

The new native workflow uses .umi records. The older Python tool remains available, but its prepared JSON directories are not interchangeable with the new native records. Start a new native workspace rather than renaming old metadata.

Do not work directly inside an earlier release or an existing image output. These commands deliberately refuse to merge new output into an existing destination.

3. Check your Linux build environment

Use a normal Linux account, either on Linux itself or inside WSL. Run the configure and build stages as that account, not as root. Administrator privileges may be needed to install host packages; they are not needed to build this image.

You need a C23 compiler, CMake, Ninja, Git and GNU Make. The focused source was tested with GCC 14.2 and Clang 17. GNU gzip and cpio are useful independent readers used by a regression test. Image construction additionally needs Buildroot's documented host prerequisites, and booting needs the appropriate QEMU system emulator.

cc --version
cmake --version
ninja --version
git --version
make --version
gzip --version
cpio --version
id -u

The final command prints your numeric user identity. Zero means root: switch to your normal account before continuing. A missing command or compiler without C23 support needs to be resolved through your Linux distribution's installation instructions before configuration.

Follow the Buildroot host requirements for its additional tools. Check the selected release's own manual as well. A successful build of the small host tool does not establish that every cross-build dependency is installed.

Keep build output in Linux storage. The examples use $HOME/umicom-builds. They read the repositories through /mnt/c in WSL, but do not build the cross-toolchain there. This avoids mixing the host's source checkout with generated image contents. All selected build paths must be absolute and contain no spaces or shell metacharacters in this profile.

Buildroot may download its required source archives during its build. The native Umicom tool does not implement a downloader, and the absence of a guest network device does not prevent the host's build tools from using the network.

4. Build and test the native host tool

Open your Linux terminal and define three paths. OS names the operating-system checkout, FW selects the Framework implementation, and BUILD names generated host-tool output. On a native Linux computer, replace the first two with your actual checkout locations.

set -eu

OS="/mnt/c/umicom/umicomOS"
FW="/mnt/c/umicom/Umicom-Applications/framework"
BUILD="$HOME/umicom-builds/os-image"

mkdir -p "$HOME/umicom-builds"

test "$(id -u)" -ne 0 || {
    echo "Use your normal Linux account, not root."
    exit 1
}

cmake -S "$OS/tools/os-image" -B "$BUILD" -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DUMICOM_OS_FRAMEWORK_SOURCE="$FW"

cmake --build "$BUILD" --parallel 2

ctest --test-dir "$BUILD" --parallel 2 \
    --no-tests=error --output-on-failure

TOOL="$BUILD/bin/umicom-os-image"
"$TOOL" --self-test
"$BUILD/bin/umicom-os-image-archive-example"

set -eu stops this shell sequence when a command fails or an unset variable is used. Do not continue through a configuration or test failure. These are terminal instructions; the feature implementation is the native C executable, not a shell script.

The self-check should print:

Native archive self-check passed. No file, build or guest was started.

The example creates a Notes welcome archive entirely in memory. Its final message is:

Practice complete. The archive stayed in memory; no files were extracted and no guest was started.

Passing these checks establishes that the selected host build runs its tests. The pipeline tests intentionally use synthetic image headers and a named inert process. They do not start a Linux guest.

5. Select the pinned Buildroot source

A repeatable project names the source it expects. The existing Umicom recipes select Buildroot 2025.02.18 at commit d030e36bbc9669230c015be971b14b6e062cfdde and Linux 6.12.109. This batch keeps those choices rather than silently updating them.

Use a new, dedicated directory for the external Buildroot source. The commands below fetch one release tag, check out its exact commit and print the result. They do not alter either Umicom repository.

BR="$HOME/src/buildroot-umicom"
mkdir -p "$HOME/src"

test ! -e "$BR" || {
    echo "That Buildroot directory already exists. Inspect it; do not overwrite it."
    exit 1
}

git init "$BR"
git -C "$BR" remote add origin https://github.com/buildroot/buildroot.git
git -C "$BR" fetch --depth 1 origin tag 2025.02.18
git -C "$BR" checkout --detach d030e36bbc9669230c015be971b14b6e062cfdde
git -C "$BR" rev-parse HEAD
git -C "$BR" status --short

The printed commit must match the one above, and the status should be empty. Detached HEAD is deliberate for this external dependency checkout; it does not change the direct-to-main policy of the Umicom repositories. A failed fetch or a mismatched commit is a stop condition, not a reason to choose the latest branch automatically.

The native prepare stage performs its own clean-commit check using the explicitly supplied Git executable. The profile at umicomOS/image/native/profile.umi also records the expected Linux source-archive SHA-256. Hash agreement identifies bytes; it is not a publisher-signature check or a security assessment of a release.

6. Capture a new image workspace

Begin with the RISC-V profile. It allows the same learning workflow to explore a different processor architecture without changing the source-level ownership rules.

RUN="$HOME/umicom-builds/native-riscv-b25"

"$TOOL" prepare \
    --os "$OS" \
    --framework "$FW" \
    --buildroot "$BR" \
    --output "$RUN" \
    --arch riscv64 \
    --git /usr/bin/git

Preparation validates the declared source list, then reads, hashes and copies its files into inputs. It does not recursively copy all your repositories. The completion record is input-manifest.umi; its SHA-256 becomes the image's source identifier.

The current profile captures 36 selected files. That identity is specific to those captured bytes, not a claim that the entire repository or compiler installation has been recorded. Absolute checkout locations are kept separately, so they do not change the source identifier.

The expected completion message says that no kernel build or guest boot was attempted. You can inspect the manifest as text. Do not edit its captured source files as a way to patch a build: a subsequent check will reject the mismatch. Change the original source deliberately and prepare another new workspace.

A refused destination protects earlier work. When the output already exists, keep it and choose a new RUN. A partial preparation is not a completed workspace and is not silently removed.

7. Configure and build the guest

Configuration turns the selected profile into Buildroot settings. Building then compiles the cross-toolchain, kernel and guest programs. These are separate operations so a configuration change cannot silently become part of an already reviewed build.

"$TOOL" configure --output "$RUN" --make /usr/bin/make

"$TOOL" build --output "$RUN" --make /usr/bin/make --jobs 2

The native tool supplies argument arrays to Framework's process runner. It selects an out-of-tree build directory, the captured external recipes and a workspace-specific downloads directory. Buildroot still uses its normal build tools and recipes; native orchestration does not mean that Linux or Buildroot has been reimplemented.

After configuration, configured.umi records the exact generated configuration. After a successful build, the tool checks important kernel settings, the three static guest executables, the kernel image and the selected Linux source archive. It writes built.umi only after those checks agree.

Expect the first cross-build to do substantially more work than the host-tool build. Each invocation has a four-hour limit and a 64 MiB captured-output limit. Build output is retained in memory and saved at command return; this edition is not a live, durable log viewer. Ctrl+C in the Linux host requests cancellation of the owned process group. Do not repeatedly press it while cleanup is completing.

Failed build attempts retain their output and can be retried after addressing the cause. A failed configuration that created its build directory needs a new prepared workspace. A successful build marker is not overwritten. A sudden host termination can leave an attempt without final logs or a result; treat it as incomplete.

No kernel or guest binary is produced by a unit-test fixture for distribution. Only the real build above can produce the requested guest build inputs. Its success still needs the boot checks later in this lesson.

8. Assemble and inspect the root filesystem

The root filesystem is the guest's first set of files. The native packer admits a fixed list rather than copying your host filesystem. It describes the two required character-device entries inside the archive; it does not create device nodes on the host.

"$TOOL" pack --output "$RUN" --bundle "$RUN/bundle"
"$TOOL" verify --bundle "$RUN/bundle"
"$TOOL" archive --file "$RUN/bundle/umicom-rootfs.cpio.gz"

A RISC-V bundle contains exactly these four files:

bundle/
    Image
    umicom-rootfs.cpio.gz
    input-manifest.umi
    image.umi

The x86-64 variant uses bzImage instead of Image. The archive includes the initialisation program, platform check, Framework probe, configuration and generated source/package information.

The packer produces canonical newc inside gzip framing. Its DEFLATE blocks store the bytes without attempting compression, keeping the implementation small and dependency-free. The result is deliberately larger than a highly compressed archive. The reader accepts this stored-block profile and canonical raw newc, not every possible gzip stream.

Verification checks the complete bundle inventory, sizes, hashes, archive structure, permitted entries and recorded source relationships. It does not extract files or start code. The bundle's manifest continues to say boot not-run; boot results are stored separately rather than modifying the image to claim success.

For an independent view, the standard tools below list the archive without extracting it. Check both commands if your shell does not preserve failures in a pipeline; the regression suite performs the independent checks itself.

gzip -t "$RUN/bundle/umicom-rootfs.cpio.gz"
gzip -dc "$RUN/bundle/umicom-rootfs.cpio.gz" | cpio -it

Do not add a log or a README inside the bundle and expect verification to ignore it. Put notes beside the bundle. The exact-inventory check is intentional.

9. Run a normal QEMU boot check

Install the QEMU system emulator appropriate to your Linux distribution. Select the actual native executable, not a script wrapper, and confirm its location before the first run.

/usr/bin/qemu-system-riscv64 --version

"$TOOL" boot \
    --bundle "$RUN/bundle" \
    --qemu /usr/bin/qemu-system-riscv64 \
    --mode normal \
    --result "$RUN/boot-normal" \
    --timeout 90

This automated profile uses the RISC-V virt machine, TCG, one virtual CPU, 256 MiB RAM and QEMU's default OpenSBI path. It uses a serial console, not a graphical window. There is no guest network, host-disk attachment or shared folder in the supplied arguments.

The new result directory records the requested input identities, captured console bytes and outcome:

boot-normal/
    request.umi
    console.log
    result.umi

Normal acceptance requires the init marker, successful platform-check, successful framework-probe, a matching source identifier, a final report of two completed services, and a shutdown marker. The process must also exit successfully. A zero process exit by itself is not enough.

A missing QEMU executable returns exit code 77: the boot was unavailable or not run, not passed. A timeout is a failure to establish the requested result. Inspect the retained console rather than replacing it with a manually edited success line.

The recorded QEMU hash helps identify the selected executable; it is not protection against choosing a malicious program that imitates a guest. Use a trusted QEMU distribution. This command is a direct-kernel boot check, not a BIOS, UEFI, Secure Boot, ISO or physical-media test.

10. Check recovery independently

A normal boot cannot prove that recovery works. Start a separate run with forced recovery:

"$TOOL" boot \
    --bundle "$RUN/bundle" \
    --qemu /usr/bin/qemu-system-riscv64 \
    --mode recovery \
    --result "$RUN/boot-recovery" \
    --timeout 90

This automated mode requests recovery and automatic shutdown. It is not an interactive console session. The normal services must not run: the expected final report has planned=2, completed=0, recovery state and requested-recovery reason.

Compare the two console files. Normal mode exercises the Framework Data Server probe; forced recovery demonstrates the separate recovery path. Both reports must identify the same captured source set, but their service counts and states differ.

Each new run needs a new result directory. Reusing a directory is refused so a previous success cannot be mistaken for the current attempt. Running the checks never changes the bundle's boot=not-run field: the result belongs to the particular run and selected QEMU executable.

11. Repeat with x86-64

Architecture is an explicit input, not a label added after compilation. Prepare and build a separate workspace for x86-64:

RUN_X86="$HOME/umicom-builds/native-x86-b25"

"$TOOL" prepare --os "$OS" --framework "$FW" --buildroot "$BR" \
    --output "$RUN_X86" --arch x86_64 --git /usr/bin/git
"$TOOL" configure --output "$RUN_X86" --make /usr/bin/make
"$TOOL" build --output "$RUN_X86" --make /usr/bin/make --jobs 2
"$TOOL" pack --output "$RUN_X86" --bundle "$RUN_X86/bundle"
"$TOOL" verify --bundle "$RUN_X86/bundle"

"$TOOL" boot --bundle "$RUN_X86/bundle" \
    --qemu /usr/bin/qemu-system-x86_64 --mode normal \
    --result "$RUN_X86/boot-normal" --timeout 90
"$TOOL" boot --bundle "$RUN_X86/bundle" \
    --qemu /usr/bin/qemu-system-x86_64 --mode recovery \
    --result "$RUN_X86/boot-recovery" --timeout 90

The x86 profile uses QEMU's q35 machine and the selected bzImage. Its validation results stand on their own. Success for one architecture must not be copied into the other's release record.

Before considering redistribution, collect Buildroot's legal-information output:

"$TOOL" legal-info --output "$RUN_X86" --make /usr/bin/make

Read its notices and warnings. This command gathers information through the selected Buildroot recipes; it does not certify that all obligations for every distributed component have been met. It does not bundle QEMU.

12. Read the C example and make one change

Open framework/examples/os_image/archive_lesson.c in Studio. The program deliberately stays in memory so the first lesson cannot accidentally install files or start a guest.

An entry describes a name, a mode, optional device numbers and a byte span. Directory entries have no content. The file entry points at a constant welcome message. The array is the proposed archive; it is not an instruction to write those paths on the host.

static const unsigned char message[] = "Umicom Notes practice workspace\n";
UmiOsImageEntry files[] = {
    { "etc", 0040755U, 0, 0, NULL, 0 },
    { "etc/umicom", 0040755U, 0, 0, NULL, 0 },
    { "etc/umicom/welcome.txt", 0100444U, 0, 0,
      message, sizeof message - 1U }
};

The leading zero on the mode constants means octal notation. The mode contains both entry type and permissions. This is why a directory and a read-only file have different values. sizeof message - 1U excludes the C string terminator; the archive member stores the actual text bytes.

UmiOsImageArchiveBuild returns allocated bytes. The caller owns that allocation and calls free. UmiOsImageArchiveOpen creates an independently owned reader object. Names and data returned by UmiOsImageArchiveAt are borrowed views that remain valid only until the reader is destroyed.

Read the complete file's cleanup path. Both reader destruction and freeing the returned bytes occur even when an intermediate operation fails. This is a small example of explicit ownership at a stable C boundary.

Change the welcome message, rebuild and run the example. Its file size changes, but it should still say that no file was extracted and no guest was started. Then try a traversal name such as ../welcome.txt; it must be rejected. Restore the valid example and rerun the tests before committing your exercise.

13. When a step stops

What you seeWhat it means and what to do
Output already existsThe tool is preserving earlier data. Inspect that directory and choose a new one; do not delete evidence just to obtain a successful command.
Buildroot identity differsThe selected commit or working tree does not match the profile. Review the dedicated external checkout and its status.
Captured inputs changedA recorded file no longer agrees. Prepare another workspace from the intended sources instead of editing the manifest.
Configuration differsThe exact generated settings changed. Intentional configuration work requires a new reviewed preparation; a source-identical-looking filename is not sufficient.
Another operation owns the workspaceThe native lock is held or invalid. Let the owning process finish. Do not bypass its lock file while work is running.
Build failed or was cancelledRead its attempt output after the command returns. Fix host prerequisites or recipes, then use the appropriate retry/new-workspace path.
ELF or kernel mismatchThe file's structure or architecture is outside the chosen profile. Renaming an executable does not change its machine code.
Archive format unavailableThe reader intentionally supports canonical newc and its stored-gzip profile, not every compression mode. Do not interpret that as permission to skip integrity checks.
Boot exit 77The required execution capability was unavailable. Record NOT RUN and arrange the real target test.
Exit zero, boot check failedThe console did not prove the expected sequence, identity and final state. Read it for a panic, missing service, repeated record or wrong mode.

Archive members are limited to 32 MiB each, 128 entries and 64 MiB of raw archive content. The fixed guest uses 24 entries. Source manifests are bounded to 256 files and 64 MiB combined. These are deliberate input controls, not promises that all future OS profiles fit them.

There is no automatic source cleanup, raw-disk writer, ISO producer, USB erase operation or optical burner in this tool. Use the separate distribution workstreams for those capabilities rather than changing a filename extension and calling the result bootable.

14. Check your understanding

Answer these questions after running the memory example. The later practical tasks require the real build and guest environment; do not mark them complete based on a fixture.

Why are preparation, packing and booting three different results?

Preparation records selected source bytes. Packing creates and checks a fixed artifact set. Booting observes execution in a particular machine configuration. None of the first two proves the third.

Does a matching SHA-256 tell you who published a file?

No. It compares bytes with a recorded value. Publisher authentication needs an independently trusted signature and its verification policy.

Why must recovery complete zero normal services?

Forced recovery intentionally avoids the normal path. Its result must show that separation rather than quietly running the checks it is meant to bypass.

Can the in-memory lesson free an entry returned by ArchiveAt?

No. It is a borrowed view owned by the archive object. Destroy the reader, and separately free the output allocation created by ArchiveBuild.

What does a native pipeline test using an inert C executable establish?

It can establish argument handling, state checks, cancellation and interpretation of controlled output. It does not establish that Buildroot compiled a real guest or that QEMU booted it.

Practical milestones

First, modify and rebuild the welcome archive example. Next, create two native preparations from the same selected bytes and compare their source identifiers. Then change one declared source file in a disposable source copy and confirm that a new preparation receives a different identity.

With a qualified build host, complete normal and recovery runs for one architecture and retain their request, console and result records. Finally, repeat for the other architecture. Explain which results are still missing before describing either profile as a distributable operating system.

15. Use the host tools from Windows appropriately

The full Windows Applications build includes the new library, command-line source and memory example. The supplied Windows file adapter and entry point have not been compiled or run in the delivery environment; run the target-platform checks before relying on them.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& ".\build\windows-ucrt64-all-debug\bin\umicom-os-image.exe" --self-test
if ($LASTEXITCODE -ne 0) { throw "Native image self-test failed." }

& ".\build\windows-ucrt64-all-debug\bin\umicom-os-image-archive-example.exe"
if ($LASTEXITCODE -ne 0) { throw "Archive lesson failed." }

These commands exercise host functionality. prepare, configure, build and legal-info still require Linux or WSL. The public library does not install signal handlers; GUI hosts must provide their own cancellation token and run blocking work on a worker thread.

This batch does not add an OS-builder page to Setup Centre. It supplies the Framework capability and explicit command-line workflow that such a page can consume later. The existing installer, maintenance, VM and boot-media pages remain unchanged.
