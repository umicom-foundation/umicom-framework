Store coding events and history safely

A coding runtime exposes two different kinds of observations. An event queue holds notifications until a consumer removes them. A history store retains snapshots so a user can inspect previous states without consuming them. Framework keeps these policies separate while sharing bounded text validation.

1. Choose the retention policy

ServiceOrderingWhen fullReading
Event queueFirst in, first outRefuse a group that does not fit; existing events remainPop removes only the copied records
Snapshot historyOldest retained record firstEvict the oldest records after the entire new group is admittedCopy leaves history intact

Neither service is a durable audit log. Their contents live in memory and disappear when the owner is destroyed. Both require serialized access; they do not create a worker thread or provide a mutex.

2. Admit text without rewriting evidence

UmiAiCodingEventValidateText checks the event task label and message. UmiAiCodingAgentSnapshotValidateText checks the task, request, provider, model and patch labels. Every array must contain a zero terminator within its own capacity. Empty labels remain valid.

These operations deliberately preserve scalar evidence such as status codes, state values, counts, flags, sequence values and revisions. They do not certify that a transition was valid or that a recorded operation succeeded. Unknown state values may be displayed as unknown; never use a stored snapshot as permission to execute a task.

Text termination is also separate from UTF-8 decoding and presentation escaping. A web viewer must escape HTML, and a terminal viewer should apply its control-character policy before displaying untrusted messages.

3. Deliver event groups without partial insertion

#include "umicom/ai_coding_runtime/event_queue.h"
#include <string.h>

int main(void)
{
    UmiAiCodingEventQueue *queue = NULL;
    UmiAiCodingEvent events[2] = {0}, output[2];
    size_t copied = 0U;
    int exit_status = 1;
    events[0].kind = UMI_AI_CODING_EVENT_STATE;
    events[0].state = UMI_AI_CODING_RUNTIME_PREPARING;
    events[0].sequence = 10U;
    strcpy(events[0].message, "Preparing the request");
    events[1].kind = UMI_AI_CODING_EVENT_MESSAGE;
    events[1].sequence = 11U;
    strcpy(events[1].message, "Waiting for review");
    if (umi_ai_coding_event_queue_create(&queue) != UMI_STATUS_OK) return 1;
    if (UmiAiCodingEventQueuePushBatch(queue, events, 2U) != UMI_STATUS_OK) goto done;
    if (UmiAiCodingEventQueuePopBatch(queue, output, 1U, &copied) != UMI_STATUS_OK) goto done;
    if (copied != 1U || output[0].sequence != 10U) goto done;
    if (umi_ai_coding_event_queue_count(queue) != 1U) goto done;
    exit_status = 0;
done:
    umi_ai_coding_event_queue_destroy(queue);
    return exit_status;
}

Build this C23 program against the installed SDK's Umicom::developer target. Expected exit status is zero. The producer supplies sequence values, and the event queue preserves them. Unlike the coding task queue, it does not assign new identities.

A batch pop copies at most the supplied output capacity. Empty queues return OK with zero copied. A zero-capacity call may use a null output pointer and removes nothing. The existing single-event pop retains its NOT_FOUND result for an empty queue.

4. Retain the newest snapshots

UmiAiCodingHistoryRecordBatch accepts up to UMI_AI_CODING_RUNTIME_HISTORY_CAPACITY snapshots in one group. It checks every incoming text field before evicting any older record. A malformed final snapshot therefore cannot erase valid history.

For a capacity of 64, a history containing 61 records has room for three. Adding seven snapshots drops four old records, retains 57 old records and appends all seven new ones. If a complete group of 64 is accepted, it replaces the retained window.

UmiAiCodingAgentSnapshot page[8];
size_t copied = 0U;
UmiStatus status = UmiAiCodingHistoryCopyRange(
    history, 0U, page, 8U, &copied);
/* On OK, page[0..copied) contains the oldest retained observations. */

The offset is an index in the current retained window. An offset equal to its count returns OK with zero copied; a larger offset returns NOT_FOUND. Retention can shift offsets when older records are evicted, so serialize a read with mutations and do not treat an offset as a permanent snapshot identity.

5. Keep prior state when a call is refused

  • Malformed incoming text returns INVALID_ARGUMENT before a batch changes storage.
  • Event batches that exceed remaining space and history groups larger than the entire retention capacity return CAPACITY_EXCEEDED before traversing their records.
  • Invalid private owner bounds return INVALID_STATE before indexing storage. This indicates an ownership or memory-integrity problem, not a reason to increase a capacity argument.
  • Failed batch reads preserve the output records and the caller's prior copied-count value.
  • Input and output records must be separate from owner storage. The copied-count result must also be separate from record arrays.

Provide real readable input extents and writable output allocations. A numeric count cannot make an invalid pointer safe. Keep all records stable for the duration of the call.

6. Qualify admission, eviction and draining

Expected result: all selected cases pass. Execute and inspect native qualification before claiming that result. This storage contract does not establish producer sequence continuity, valid state transitions, successful provider calls or durable audit persistence.
