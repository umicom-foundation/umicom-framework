Boot Kernel and Linux images with Umicom

A virtual machine runs a guest operating system inside an emulator. The host is your computer; the guest can use a different processor architecture. Framework builds QEMU arguments, checks selected files and owns the emulator process. Applications can reuse these services without creating their own process launcher.

This workflow provides a serial text console. It does not embed a graphical guest desktop. Use trusted native QEMU installations and guest assets you are permitted to use. The command neither downloads nor installs them. A successful process start or QMP response is not evidence that an operating system booted.

Choose a boot target

Run umicom qemu targets to list the shared catalogue. umicom-vm qemu accepts the same subcommands in the standalone VM tools.

TargetRequired assetMachine and console
umicom-kernel--firmware umicom-system.elfRV64 virt, ACLINT disabled, one CPU, at least 128 MiB
linux-x86_64--kernel Linux boot imagex86-64 q35, console=ttyS0
linux-riscv64--kernel Linux ImageRV64 virt, OpenSBI, console=ttyS0
linux-aarch64--kernel Linux ImageARM virt, Cortex-A57, console=ttyAMA0
pc-iso--iso BIOS-compatible imagex86-64 q35 with SATA CD-ROM; guest needs serial interaction
pc-disk--disk BIOS-compatible raw imagex86-64 q35 with VirtIO disk

Linux targets accept an optional initramfs using --initrd and an explicit guest command line using --append. Linux RV64 uses QEMU's default OpenSBI unless an absolute --firmware path is supplied. ARM direct Linux boot does not accept a separate firmware image in this workflow. Guest kernels need the drivers for the selected virtual devices.

Review an Umicom Kernel boot

  1. Prepare your built umicom-system.elf, a matching native QEMU executable and an existing working directory. Use complete paths. For example:

    New-Item -ItemType Directory -Force "C:\VMs\Umicom"

  2. Preview the argument vector. This step opens no guest file and starts nothing.

    umicom qemu plan --target umicom-kernel `
    --qemu "C:\msys64\ucrt64\bin\qemu-system-riscv64.exe" `
    --directory "C:\VMs\Umicom" `
    --firmware "C:\umicom\umicom-kernel\build\riscv64-clang-debug\bin\umicom-system.elf"

    The output lists -machine virt,aclint=off, -S, -m 128 and -smp 1. Each numbered line is one argument, not a shell command.

  3. Repeat with review in place of plan. Review reads the executable and selected input files, then prints a fingerprint. That fingerprint describes those bytes and arguments; it is not a signature or trust certificate. QEMU's shared libraries and automatically located firmware are outside this check. Keep the trusted installation and inputs unchanged while running.

  4. Repeat with run and add --expect followed by the fingerprint you just reviewed. The command checks the inputs again and connects to QEMU while paused. It refuses a stale fingerprint.

  5. At the VM prompt, type resume, then console. Use send help to send a line to the guest and console to retrieve its response. Output is a bounded ring buffer; poll it regularly. The terminal escapes non-printable bytes instead of interpreting guest escape sequences.

  6. For Umicom Kernel, use send poweroff. Other operating systems may use a different shutdown command. powerdown sends a QEMU power request which the guest may ignore. quit-qemu and force-stop stop the emulator and are not evidence of clean guest shutdown.

Save several local configurations

Profiles live in a local SQLite database through Framework's Data Server. They store paths and settings, not running processes or reusable launch approvals. Keep the database outside your source repositories. Do not put credentials in a guest command line: configuration values are not an encrypted secret store.

umicom qemu profiles save --database "C:\VMs\profiles.sqlite" `
    --id umicom --name "Umicom system" --target umicom-kernel `
    --qemu "C:\msys64\ucrt64\bin\qemu-system-riscv64.exe" `
    --directory "C:\VMs\Umicom" `
    --firmware "C:\umicom\umicom-kernel\build\riscv64-clang-debug\bin\umicom-system.elf"

umicom qemu profiles list --database "C:\VMs\profiles.sqlite"
umicom qemu profiles show --database "C:\VMs\profiles.sqlite" --id umicom
umicom qemu profiles review --database "C:\VMs\profiles.sqlite" --id umicom

To run that configuration, use profiles run with the same database and ID and an --expect fingerprint from the latest review. To update a saved profile, repeat save with its current --expected revision. To remove only its settings, use profiles remove --database FILE --id ID --expected REVISION. Guest files are retained. There is a maximum of 64 standalone profiles; the earlier packaged-image catalogue is separate.

Try Linux or a disk image

A direct Linux boot needs an architecture-compatible kernel and a usable root filesystem. An initramfs can contain that filesystem; otherwise provide a raw disk and the matching root= parameter. The command does not guess a root partition or promise that an arbitrary distribution image works.

umicom qemu plan --target linux-riscv64 `
    --qemu "C:\msys64\ucrt64\bin\qemu-system-riscv64.exe" `
    --directory "C:\VMs\Linux" --kernel "C:\VMs\assets\Image" `
    --initrd "C:\VMs\assets\initramfs.cpio.gz" `
    --append "console=ttyS0 rdinit=/init" --memory 1024

Replace plan with review, then use the returned fingerprint with run. For AArch64 select linux-aarch64, qemu-system-aarch64 and an ARM64 kernel, and use console=ttyAMA0. For an x86-64 ISO select pc-iso and supply --iso. A graphical-only installer will not be usable in this serial interface.

An optional --disk must name a regular RAW image, not QCOW2 or a host device. QEMU writes guest changes to a temporary overlay and discards them when it exits. This is useful for experiments but not for persistent installation. No monitor command is provided to commit those writes back to the source.

Troubleshooting and extension points

  • Invalid option: check spelling, duplicates and the target's allowed assets. An unused initramfs or command line in Kernel mode is rejected.
  • Review failed: check that paths are absolute, input files are nonempty regular files and the working directory already exists. Links and device paths are not accepted by the checked file layer.
  • Inputs changed: review again and inspect the new plan. Do not reuse a fingerprint from an older build.
  • QMP negotiation failed: confirm that the selected executable is a compatible QEMU system emulator. Unsupported machine options, missing firmware and missing host libraries can prevent startup.
  • No console output: the guest starts paused. Resume it, poll the console and check its serial configuration. Paused QMP state does not prove a valid guest image.
  • Database capacity: SQLite profiles support the bounded record format. The memory-only Data Server has a smaller value limit and can reject very long configurations without replacing their prior values.

Application developers use UmiVmBootPlanCreate, UmiVmBootReview and UmiVmBootStart, followed by existing UmiVmControl operations. Keep blocking review and process work on a persistent worker, because Linux child ownership is tied to the creating thread. Saving a profile does not open its guest paths. Additional architectures belong in the shared target table with explicit firmware, device and test coverage.

See QEMU invocation, RV64 virt and ARM virt for the underlying emulator behaviour. Hardware acceleration, graphics embedding, networking, writable base disks, migration and guest agents require separate integration.
