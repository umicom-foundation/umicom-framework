Connect to Paper or Live without enabling orders

A connection and a trade are different actions. In this lesson you will choose a broker environment, open a read-only connection, identify the accounts that the provider reports, and inspect one account's values and positions. Nothing in this connection tool places, changes or cancels an order.

Begin with the offline example. Then use a Paper login to check the real connection on your computer. The same controls also offer Live read-only access when you deliberately select it.

Development scope. This is a native C23 implementation of a limited TWS framed-field protocol, negotiated from version 151 to 176. It is not the official IBKR SDK and does not decode the newer protobuf protocol. The delivery tests use an inert local peer, not an authenticated TWS session. Actual provider compatibility, Windows execution and the graphical interface still require local acceptance. Do not treat the guide as evidence that those checks have already passed.

1. Understand the two choices

Paper means that you intend to connect to a paper-account session. Live means that you intend to inspect a live-account session. The selection does not change the login in TWS or IB Gateway. That login is made in the provider's own application, with its own authentication. Keep passwords and two-factor codes there; Umicom has no field for them.

Both Umicom choices are read-only. Live selection additionally requires an acknowledgement. This is a reminder about the account you intend to access, not an execution permission.

IBKR documents separate default socket ports for its two programs and two environments. They can be changed in the provider's settings. Use the configured port, not a guess. Provider setup instructions

Provider program Paper default Live default
Trader Workstation (TWS) 7497 7496
IB Gateway 4002 4001

The connection window always reports Server mode attested: NO. Neither a familiar port nor a particular account prefix proves which environment is behind a local socket. Confirm the login in TWS/Gateway and compare the account identifier before reading its data.

2. Build the tools and run the offline example

Merge the accompanying full files into the matching directories. Use the delivered Build-and-Git instructions for the complete application build and tests. The smaller build below isolates this component; it does not replace the full suite.

Open PowerShell and run:

Set-Location "C:\umicom\Umicom-Applications"
$ErrorActionPreference = "Stop"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\examples\ibkr_connection" `
    -B ".\build\broker-connection-lab" `
    -G Ninja -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "Configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build ".\build\broker-connection-lab" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\broker-connection-lab" `
    --parallel 2 --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Tests failed." }

& ".\build\broker-connection-lab\bin\umicom-broker-profile-example.exe"
if ($LASTEXITCODE -ne 0) { throw "The example failed." }

Expected output:

Paper TWS default: 7497; Live TWS default: 7496
Both profiles are read-only. A port number does not prove the account mode.
Practice complete. No socket, file, order or network request was created.

The example validates two configurations in memory. Passing it proves neither a network connection nor a broker login. Linux/WSL developers can build the same source with CMake and Ninja; the source package's host-tool entry is umicomOS/tools/broker-connect.

3. Prepare the provider application

Open TWS or IB Gateway yourself. For the first connection exercise, choose the Paper login, finish authentication and wait for the application to finish loading.

In the provider's API settings, enable socket clients and keep Read-Only API enabled. The provider's read-only setting blocks API orders; coordinate that setting with any other API clients using the same session. Record the configured socket port. These controls are described in the IBKR setup lesson.

Umicom connects only to 127.0.0.1, which means the same operating-system network host. It does not use DNS, ask for a remote server, create a tunnel or change the provider's settings. For the Windows exercise, run both programs on Windows. Do not assume that a program running inside WSL or a VM shares the Windows loopback endpoint.

Each concurrently connected API client needs its own identifier. This component defaults to 35 and refuses zero. Choose another positive identifier when a different program or connection already uses 35. Opening a second Umicom window does not automatically allocate a new identifier.

4. Open the connection window

In a GUI-enabled full build, open Trader and choose Open Paper / Live broker connections. The existing simulation and linked market tape remain separate. This button does not turn their values into broker observations.

You can also open the standalone graphical program:

C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-broker-workbench.exe

For the smaller laboratory build, the program is under build\broker-connection-lab\bin instead. Its GTK libraries must be available; the smaller SDK build does not create a redistributable GTK runtime bundle. When GTK development files are unavailable, CMake says so and builds only the native tools and applicable tests.

The window starts disconnected. Choose Paper, choose TWS or IB Gateway, check the port and choose a unique client ID. Changing program or environment resets the suggested port and clears the Live acknowledgement. A custom port can then be entered explicitly.

Choose Connect read-only. The profile fields are locked while this connection is active. The program opens the local socket, negotiates its protocol, waits for the account list and API-ready identifier, then checks the provider clock. The official API describes the readiness callback as the point after which client requests should be sent. Connection sequence

The state should eventually read Read-only API ready. A successful TCP connection alone is insufficient. An unsupported protocol, timeout or provider error ends the attempt and leaves a readable explanation.

5. Inspect one account

The account selector is populated only from the list received on this connection. IBKR describes this list as the accounts available to the logged-in user. Managed accounts

Compare the identifier with the provider application. Select the intended account and choose Read selected account once. The component requests four summary tags: NetLiquidation, TotalCashValue, BuyingPower and AvailableFunds, together with position observations. The provider requests may cover all accounts authorised to the login; only rows for your exact selected identifier are retained in the displayed snapshot.

Summary and positions arrive separately. Each has its own completion indicator and reception time. A partial response remains INCOMPLETE, even when some rows have arrived. Zero positions is a complete empty result only after the provider's end marker has arrived. Missing information is never filled with practice values or a made-up zero.

Values stay in the provider's textual representation. This preserves decimal quantity strings and avoids turning an unset or display-only value into booked money. Position rows carry contract identity and contract details alongside quantity and average cost. They are observations, not a replacement for the Framework financial position/ledger authority.

The tool cancels the two read subscriptions after their initial end markers. Those are subscription cancellations, not order cancellations. Captured responses do not continue updating. Their displayed ages continue to increase while the connection is healthy. A heartbeat checks transport responsiveness; it does not refresh account balances.

IBKR's documentation separates account-summary and position requests and describes their subscription/end-marker behaviour. Large adviser and broker account structures need separate qualification and may require different requests. Account summary · Positions

6. Refresh, disconnect and switch environment

Each connection permits one selected-account read. To refresh, inspect another account or change the environment, choose Disconnect and then explicitly connect again. A new connection owns new input buffers, a new account list and new readiness state. An old response cannot silently become part of the new session.

Disconnecting retains the last rows with a stale indication so you can see what was received. Connecting again clears that old display. There is no automatic reconnect, automatic Paper fallback or automatic Live promotion.

For Live inspection, first confirm the Live login in the provider, select Live in Umicom, check the endpoint and acknowledge the read-only access. Then connect and verify the returned account identifier. This still cannot send an order. Closing the connection window closes its socket, including when another owner has retained a reference to a closed widget.

7. Use the command-line tool

These commands open a real local connection when you run them. Run the offline --self-test first. The path below is for the full Applications build.

Set-Location "C:\umicom\Umicom-Applications"
$Broker = ".\build\windows-ucrt64-all-debug\bin\umicom-broker-connect.exe"

& $Broker --self-test
if ($LASTEXITCODE -ne 0) { throw "Policy self-test failed." }

# Explicit read-only connection: list available accounts, then disconnect.
& $Broker connect --mode paper --program tws
if ($LASTEXITCODE -ne 0) { throw "Paper connection inspection failed." }

Live is equally explicit:

& $Broker connect --mode live --program tws --acknowledge-live
if ($LASTEXITCODE -ne 0) { throw "Live connection inspection failed." }

For Gateway, use --program gateway. To match a deliberately changed endpoint, add --port followed by the configured port. Use --client-id to choose another positive client identifier.

To inspect data, copy an exact identifier returned by the account-list command. Do not use the placeholder as an account:

$Account = "REPLACE_WITH_AN_EXACT_RETURNED_ACCOUNT_ID"
& $Broker connect --mode paper --program tws --account $Account
if ($LASTEXITCODE -ne 0) { throw "The selected-account response did not complete." }

Successful output includes the requested mode, the explicit absence of environment attestation, the protocol version and actual returned identifiers. Account rows depend on your account; there is deliberately no fixed “successful balance” in this lesson. The command exits with failure if validation, transport or completion fails. It never switches to simulated output to make the command appear successful.

8. Follow the C ownership boundary

The complete example is framework/examples/ibkr_connection/lesson.c. It starts from UmiIbkrConnectionOptionsDefault, constructs the Live alternative, and demonstrates that validation refuses Live until it is acknowledged. Its policy labels are separate from the provider environment.

The full command-line client in main.c then shows the complete lifecycle:

Validate → Create → Open → Pump → Read account → Copy → Close / Destroy

Create allocates owned state but opens no socket. Open is the explicit external action. Pump performs bounded nonblocking work, using a monotonic timestamp supplied by the host. Copy returns an independent snapshot. Destroy closes and releases the owned state.

All calls for one connection must run on one owner at a time. Do not pump on one thread while destroying the same object on another. The GTK adapter uses its main context; the CLI uses one polling loop. Applications should compose this service instead of implementing another broker socket inside a chart.

The separate client directory contains an installable-SDK consumer. It constructs Paper and Live objects and releases them without opening either. After installing the focused SDK to a separate prefix, build it with:

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --install ".\build\broker-connection-lab" `
    --prefix "C:\umicom\Practice\BrokerSDK"
if ($LASTEXITCODE -ne 0) { throw "SDK installation failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\examples\ibkr_connection\client" `
    -B ".\build\broker-sdk-client" -G Ninja `
    -DCMAKE_PREFIX_PATH="C:/umicom/Practice/BrokerSDK"
if ($LASTEXITCODE -ne 0) { throw "Client configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\broker-sdk-client"
if ($LASTEXITCODE -ne 0) { throw "Client build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\broker-sdk-client" --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Client test failed." }

Do not install this dependency-subset SDK over a complete Framework SDK.

9. Troubleshoot the right layer

What you see What to check
Local socket refused Provider running and fully logged in; configured port; socket access enabled; both programs on the same host.
Waiting for readiness, then timeout Provider approval prompt, API settings, protocol compatibility and unique client identifier. Do not call it connected merely because TCP opened.
Requested Live access refused locally Confirm your intended provider login and select the explicit Live acknowledgement. No order setting needs enabling.
Duplicate-client error Disconnect the older client or choose another positive client ID. Do not automatically reuse zero.
Unsupported or malformed response Retain the error and provider version privately. The bounded native field protocol may need an adapter update; do not disable validation.
Summary or positions incomplete The response failed, timed out or exceeded capacity. Reconnect after resolving the cause. Do not use the partial rows as a complete portfolio.
Another-account selection refused Choose an exact identifier supplied on this connection, not a guessed prefix or an identifier from a different login.
Old rows after disconnect They are retained and labelled stale, not continuing to update.

No provider credentials or observations are written to a database by this component. However, console output, screenshots, terminal history and process dumps can reveal account information. Share only the minimum redacted diagnostic needed for support.

10. Limits and acceptance

This profile supports 32 account identifiers, 64 retained summary rows and 64 retained positions for the selected account. Frame bodies are capped at 64 KiB. Each pump processes at most 64 frames and reads at most 64 KiB. Default handshake/request deadlines are ten seconds; the public options permit 100–60,000 ms. The UI and CLI use the default. Excess capacity or malformed input stops the observation rather than silently cropping a portfolio.

Connection success does not qualify trading. The window can inspect subscribed bid, ask and last observations for an explicit contract ID and exchange. It has no order transmission, order cancellation, modification, fills reconciliation, saved profile database or reconnect recovery. Existing simulation, replay, chart and order services are not replaced or armed by this window.

Inspect subscribed market quotes

  1. Connect read-only and wait for API readiness.
  2. Copy the contract ID and exchange from TWS Contract Description into the quote fields.
  3. Choose Subscribe to quote. API data permissions are decided by the provider; no regulatory snapshot is requested.
  4. Read each field's type and receipt age. Delayed and frozen data stay labelled. Missing, failed, cancelled, disconnected, type-mismatched or older-than-15-second values are stale.
  5. Choose Cancel quote stream before selecting another contract. A quote-specific refusal is retained in the quote panel without destroying independent account observations.

This native inspector displays one contract at a time. Framework's umicom/broker_connectivity/quotes.h contract owns up to 16 subscriptions, provides copied snapshots and guards late callbacks with non-reused request IDs. The inspector does not search contracts, load candles or submit orders. See IBKR's market-data workflow. Provider and GUI acceptance remain separate from authored source and fixture coverage.

A useful local acceptance record identifies the built Umicom commit, operating system, provider version, requested mode, configured endpoint, readiness result, selected-account response markers and clean disconnect. Check Paper first. Live read-only acceptance is a separate deliberate exercise. Never include passwords, authentication codes or unredacted account values in the source repository.

11. Exercises and answers

Exercise A. Run the profile example without TWS open. Why does it still succeed?
Answer: it validates memory-only options. It does not call the socket-opening operation.

Exercise B. Change the Paper port to the usual Live port in a practice configuration. Has that proved the environment?
Answer: no. Port defaults are editable routing choices. The requested mode remains intent; the provider login must be checked separately.

Exercise C. Receive three position rows but no end marker. Is this a three-position portfolio?
Answer: it is a partial observation. The response may still be missing records.

Exercise D. Read a completed snapshot, wait one minute and receive a successful heartbeat. Are the account values now one minute newer?
Answer: no. The heartbeat checks the connection. The snapshot retains its original reception time.

Exercise E. Select Live and leave the acknowledgement clear. Choose Connect.
Answer: the local validation refuses to open the connection. No test order is needed.

Exercise F. Explain which component owns the socket.
Answer: the Framework connection owns it. Trader attaches the view; closing that view releases its connection through the shared lifecycle.
