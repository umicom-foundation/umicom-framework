Plan AI context within explicit limits

An AI request can include a project description, selected source, diagnostics or retrieved documents. Each item consumes part of the model's input budget and may carry a different privacy classification. Framework's context broker selects metadata deterministically before an adapter reads or sends the underlying text. The broker itself opens no URI and calls no model.

This lesson uses context_broker.h and privacy_policy.h. It assumes basic C structures and status checks. A token estimate is a planning input supplied by the application; this service does not tokenize the final prompt or guarantee that an external model will accept its length.

1. Register bounded provenance

A context source contains an ID, label, URI, classification, estimated token count, priority and two flags. The URI describes where the source came from. Actual source text remains owned by its adapter. UmiAiContextSourceValidate checks that all fixed text fields terminate within their arrays, required fields are nonempty, enum values are known and the token estimate is positive.

UmiAiContextSource source = {0};
strcpy(source.source_id, "context.readme");
strcpy(source.label, "Project overview");
strcpy(source.uri, "workspace://project/README.md");
source.kind = UMI_AI_CONTEXT_DOCUMENT;
source.classification = UMI_AI_DATA_PUBLIC;
source.estimated_tokens = 600U;
source.priority = 50U;
source.mandatory = 1;
source.enabled = 1;
UmiStatus status = umi_ai_context_broker_upsert(broker, &source);

Use bounded copying for values obtained from a form or file. A first-byte check alone cannot make an unterminated array safe for later comparison. The Framework validator performs the bounded scan; applications supply meaningful metadata and must not misclassify private content as public.

2. Calculate the usable budget

Reserve room for the model's output before selecting context. A context limit of 8,192 tokens with 2,048 reserved leaves 6,144 tokens for selected sources. The caller also supplies a maximum source count. The limit must be positive, the reserve must be smaller than the limit, and the count must fit the fixed plan capacity.

Enabled sources are considered in this order: mandatory before optional, then higher priority, then source ID in lexical order. Every nonzero mandatory/enabled flag means true, including a negative value. Consistent boolean interpretation prevents a negative true value from accidentally sorting behind optional sources.

3. Distinguish a drop from a failed plan

Source outcomePlan result
Optional source does not fit or policy refuses itSkip it, increment the dropped count and mark the successful plan truncated.
Mandatory source does not fitReturn a capacity error and preserve the previous complete output.
Mandatory source is refused by privacy policyReturn the policy error and preserve the previous complete output.
Invalid policy, unknown provider kind or corrupt broker stateRefuse before selecting any source, even when the broker is empty.

The planner builds a private candidate through Framework's shared value-construction helper. A failure near the end cannot expose the already selected prefix as a new plan. An older plan remaining in memory does not authorize its use after a failed refresh: inspect the return status and keep the request stopped.

4. Validate policy before applying it

UmiAiPrivacyPolicyValidate requires both local and remote classification limits to be known values, from public through restricted. Sharing checks also require a known provider kind. An unknown numeric kind must not fall through to the local-policy branch. Valid local, AuthorEngine and test providers retain their existing local-policy treatment; a remote provider uses the remote limit.

The default policy permits public remote context and requires approval for sensitive local material within its local classification limit. Approval cannot override a classification above that limit. Persistence has its separate session/text switches and sensitive-approval rule; it does not inherit the sharing ceiling. A valid policy is still a caller-supplied decision, not a security label inferred from the text or an authentication of the transport.

Installing a malformed policy through the AuthorEngine service now fails before changing its policy, the runtime policy or the service revision. Boolean switches retain their established nonzero-is-true meaning. Initialize from umi_ai_privacy_policy_default() and alter explicit fields, rather than passing an incomplete zero-initialized policy.

5. Track the owner that produced a plan

UmiAiContextBrokerCapture returns the current count and revision. The plan records the broker revision it observed. Accepted upserts, removals and clears advance that owner; an imported source's historical revision is replaced by the assigned stored revision. A plan owns copies of its metadata and does not change automatically when the broker changes.

Revisions belong to their particular broker. Comparing two numbers from different owners proves nothing. Serialize broker access and recheck relevant owner, workspace and provider state before executing a request. The plan revision does not describe later edits to underlying files or prove that the final prompt still matches its token estimate.

Mutation refuses an exhausted revision before changing anything. UmiAiContextBrokerClearChecked reports that refusal. The older void clear remains available, delegates to the checked function and leaves state intact if it cannot complete. A successful clear advances the revision even when already empty. Use the checked form whenever the caller must distinguish completion from refusal.

6. Exercise the native implementation

From a configured Framework checkout, stop on a failed command:

cmake --preset windows-ucrt64-debug
cmake --build --preset windows-ucrt64-debug --target umicom-ai-context-admission-test umicom-ai-context-planning-test umicom-ai-privacy-admission-test
ctest --test-dir build/windows-ucrt64-debug -R '^framework[.]ai[.](context|privacy)[.]' --output-on-failure --no-tests=error

The owner cases cover bounded fields, full-registry replacement, corrupt state and exact revision limits. The planning cases distinguish optional drops from mandatory refusal, check deterministic order and preserve old output on failure. The policy cases cover the full default sharing matrix and unchanged service state after invalid installation.

  1. Register two mandatory sources whose combined estimate exceeds the budget. Keep a copy of a previous valid plan.
  2. Request a plan and expect a capacity error with the previous output unchanged.
  3. Mark the lower-priority source optional and retry. Expect success with a reported drop.
  4. Change the provider to remote and classify a mandatory source confidential. Expect policy refusal despite an approval flag.
  5. Correct the inputs, prepare a new complete plan, and compare its captured broker revision before any separately approved execution.

The installed SDK example uses the public context and policy symbols offline. Configuration, registration and source review do not prove these native tests or the installed consumer passed. No model training, retrieval indexing, text loading or remote request is performed by these metadata exercises.
