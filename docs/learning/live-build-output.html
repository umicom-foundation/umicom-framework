Reading build output while a job runs

A build phase is one step in a project workflow, such as configuration, compilation, testing or running a program. Framework can publish output during each step. Applications read an owned copy, so their interface does not borrow a buffer that the worker is changing.

Connect a frontend

  1. Create a project session with umi_build_project_session_create. The built-in executor streams output automatically. Keep the session alive until the worker has finished or session destruction has joined it.
  2. Submit a validated profile with the owner's current workspace trust decision. Merely reading output never starts a compiler or grants permission to execute project code.
  3. Allocate a UmiBuildOutputSnapshot on the heap. It contains a fixed-size byte buffer and is too large to be a routine local variable in a small UI thread stack.
  4. On the frontend's owning thread, call UmiBuildProjectSessionReadOutput. An operation identifier of zero means that no job has been submitted. A nonzero identifier and changing revision mean new evidence is available.
  5. For a GTK frontend, create UmiBuildOutputGtk4Create() once and pass each successful snapshot to UmiBuildOutputGtk4Update. GTK remains on its owning thread; process callbacks never touch widgets.
  6. Continue collecting completed results with umi_build_project_session_result_at. Use the final status to determine success. Receiving text is not proof that a build or test passed.

This polling helper illustrates the ownership boundary. The caller supplies a live session and presenter;

#include <stdlib.h>
#include "umicom/build/live_output_gtk4.h"

UmiStatus RefreshBuildOutput(UmiBuildProjectSession *session, GtkWidget *panel)
{
    /* The caller owns this copy; the worker never borrows it. */
    UmiBuildOutputSnapshot *output = calloc(1U, sizeof(*output));
    if (output == NULL) return UMI_STATUS_OUT_OF_MEMORY;
    UmiStatus status = UmiBuildProjectSessionReadOutput(session, output);
    if (status == UMI_STATUS_OK) status = UmiBuildOutputGtk4Update(panel, output);
    free(output);
    return status;
}

Choose the appropriate execution interface

UmiBuildRunnerRunObserved supplies raw process chunks to a synchronous observer. The ordinary umi_build_runner_run uses the same path with no observer. Both preserve cancellation, child-process-tree ownership, diagnostic parsing and completed history. The callback borrows its bytes only until it returns; copy what you need promptly and do not destroy or re-enter the runner from that callback.

Hosts with their own transport can use UmiBuildProjectSessionCreateObserved. Provide an observed executor and leave config.execute empty. The executor must emit chunks synchronously before returning, honour the cancellation token, and release no session-owned objects. Existing custom executors remain supported: their output appears when the phase finishes, with streamed set to false.

Understand the limits

  • The snapshot retains the latest 65,535 raw bytes of the current phase. At the next phase its byte count starts again. Slow polling can miss an entire phase; completed-result history remains the place to review earlier phases.
  • length is the number of bytes retained; total_bytes counts received bytes in this phase. truncated means earlier bytes were omitted. A legacy executor reports only its already-bounded final buffer.
  • Standard output and standard error are merged. Chunks are not necessarily lines or complete UTF-8 characters. Embedded NUL bytes are valid evidence, so use the supplied length instead of strlen.
  • The GTK display makes NUL visible as ␀ and replaces invalid UTF-8 for readability. This does not change the raw snapshot.
  • Follow output scrolls to new evidence. Turning it off preserves the displayed text and selection. Refresh output shows the latest copy once; Copy displayed output copies the visible transcript even when newer evidence is waiting.
  • The transcript does not interpret terminal escape commands, accept program input, or save a complete log file. The existing completed diagnostic parser still operates on its own bounded final result buffer.

Troubleshoot missing output

  1. Check whether the phase is still running or has failed to launch. A tool can buffer its own output until it flushes.
  2. Check Follow output. If paused, choose Refresh output or turn following back on.
  3. For a custom executor, inspect streamed. Final-output-only executors cannot provide progress they never emitted.
  4. If an operation or revision is stale, obtain a fresh snapshot. Do not overwrite a newer display with an earlier job's data.
  5. If counters_saturated is set, refresh on every poll; revision equality is no longer sufficient.
