Keep completed test evidence across restarts

A test archive stores what a completed run observed. It keeps the original selection, repeat settings, outcomes and source context so a later viewer can explain which tests ran and which never started. Reading history does not mark the current checkout as tested and never executes a saved selection.

Choose the storage owner

Link Umicom::test_archive and include umicom/testing/archive.h. The archive uses the shared Data Server. Basic CTest execution still links through Umicom::testing without requiring this archive library. A memory Data Server is useful for transient sessions; SQLite retains records when the application restarts.

  1. Create a Data Server at an explicitly selected private location. The caller owns that server.
  2. Call UmiTestArchiveCreate with a scope such as studio.tests. Scopes contain at most 64 ASCII letters, digits, dots, dashes or underscores. Each scope holds at most 32 saved runs.
  3. Keep the completed UmiCtestJob alive. Its immutable request copies contain the original test IDs, build directories, configurations, enabled flags and timeouts.
  4. Fill UmiTestArchiveOrigin from the context accepted when that run started. A caller-supplied revision description is optional. Neither a description nor a workspace generation proves that the checkout was clean or identifies every byte in a test executable.
  5. Choose whether to retain diagnostic output. The default zero-initialized value omits it. Names, paths and result metadata are still stored. SQLite storage here is not encrypted.
  6. Save only a terminal job. The archive copies its complete intended selection and completed results within one transaction. The difference between planned and completed attempts records work that never started; it is never treated as a pass.

Keep an interactive application responsive

Include umicom/testing/archive_write.h to create and submit an UmiTestArchiveWrite on an existing task queue. Keep its archive, Data Server and source job alive. Do not replace the source job while saving. Poll UmiTestArchiveWriteRead on the UI thread; it copies memory and does not read the database.

  1. Create the writer from a terminal job and a copied origin.
  2. Submit it once. A queue rejection leaves a created writer that can be retried or destroyed.
  3. Continue normal UI refresh. Stop calls UmiTestArchiveWriteCancel and returns promptly.
  4. Wait through polling until the writer is terminal. A nonzero saved.id means a database commit succeeded, even if cancellation arrived immediately afterward.
  5. Destroy the writer on its creating thread, then release the source job and archive when no longer needed.

Cancellation checked before commit rolls back the save. A failure to save is a storage result, not a new test verdict. Applications should show both outcomes independently.

Read, inspect and retain evidence

UmiTestArchiveList returns metadata ordered by durable ID. UmiTestArchiveRequestAt addresses the original selection; UmiTestArchiveResultAt addresses completed invocations in execution order and returns a one-based repeat number. These are different indices when a selection repeats. Public errors leave output objects unchanged.

Each save owns a new ID. IDs are not reused after removal. Remove a particular run with UmiTestArchiveRemove; its rows and metadata are removed atomically. There is no automatic eviction. The memory backend has a shared record limit and can fill before the archive reaches 32 runs. A capacity failure rolls back and preserves earlier evidence.

Retained text is the adapter's bounded diagnostic tail, not a complete process log. Long records are split into values small enough for Data Server's existing 4 KiB limit. The archive validates chunk lengths and result identities; missing chunks are reported as corruption. A catalogue read validates metadata, not every stored result body. Archives are local records, not signed attestations: a user with database write access can modify them.

Handle common errors

ResultWhat to do
BUSYThe job is still running, a save owns the archive, or the Data Server is already in a transaction. Poll later. Do not commit or roll back a transaction you did not acquire.
CAPACITY_EXCEEDEDKeep the original job available. Remove a specifically reviewed old run or select another private database, then save again.
PARSE_ERRORKeep the database for diagnosis. A saved record is incomplete or unsupported. Do not replace it with an empty archive or present its unreadable results as passed.
IO_ERRORCheck the selected location, space and permissions. The original run remains unchanged. A rollback failure must be resolved through the Data Server's recovery contract. An I/O error can leave the commit outcome uncertain; inspect the database before retrying rather than assuming no write occurred.
UNAVAILABLEPersistent SQLite support is absent from this build. Memory storage is transient.

Compare completed runs

Include umicom/testing/archive_compare.h and call UmiTestArchiveCompare with the baseline and candidate IDs. It reads both runs in one transaction and returns an owned comparison. Release it with UmiTestArchiveComparisonDestroy. The comparison stays readable after the archive closes; it does not contain diagnostic output.

  1. Choose two saved runs from the same private archive.
  2. Read UmiTestArchiveComparisonRead for the total number of rows and each outcome category.
  3. Read rows with UmiTestArchiveComparisonRowAt. Each row includes the selected request and aggregate repeated-attempt counts on both sides.
  4. Inspect changed conditions and incomplete evidence before treating a result as a regression. Never use comparison rows as permission to run a test command.

Matching uses the exact build-directory, configuration and test name. Discovery IDs may change without changing identity. Paths are compared as bytes; aliases and case differences are not guessed. Duplicate matching keys are ambiguous and return a parse error.

CategoryMeaning
New failure after a complete passEvery baseline attempt passed; the candidate has a failure, timeout or reporting error under the same recorded conditions.
Complete pass after a failureThe baseline had a failure and every candidate attempt passed.
Failure remainsBoth runs contain failure evidence. Inspect the original attempts for details.
Execution conditions changedThe source root, repeat count, early-stop policy, timeout or enabled flag changed. Counts are still shown, but no regression claim is made.
Incomplete evidenceAt least one side contains cancelled, not-run or never-started attempts without a stronger observed failure/recovery classification.
Added or removedThe named test and execution location occur in only one selection.
Unchanged or changed outcomeThe recorded outcome counts agree or differ. A skipped test can have an unchanged outcome; that does not mean it passed.

Duration changes alone do not change classification. Equal caller-supplied revision labels do not prove that source files or executables are identical. Comparisons report observed evidence, not the cause of a failure or release readiness.

Keep native interfaces responsive

For interactive hosts, include umicom/testing/archive_review.h. Create a review, submit it to a Framework task queue and poll UmiTestArchiveReviewRead. The worker reads storage while the UI copies only memory. ready identifies a fully captured comparison, even if cancellation arrived just after capture.

Keep the archive and queue alive until the review is terminal. Request cancellation before closing, continue polling, then destroy the review. A pending destroy returns BUSY. Do not wait for a worker inside a GTK callback. Present results in bounded pages for large suites.

If storage is busy, retry after the current transaction finishes. Missing or corrupt rows fail the entire comparison; no partial result is published. A comparison failure leaves the caller's existing comparison pointer unchanged. Preserve the database for diagnosis rather than removing individual storage keys.
