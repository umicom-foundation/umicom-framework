Read historical bars and explore a candlestick chart

A candle summarizes the opening, highest, lowest and closing price within an interval. The shared broker window can request a finite set of intraday bars from TWS or IB Gateway, then display them using Framework's chart renderer. Trader uses this same window through its broker connection action.

This is a captured historical view. It does not stream new candles, submit orders or establish whether the most recent candle has finished. Data availability depends on the selected contract, route and the permissions of the account logged into TWS.

Capture a chart

  1. Open the broker connection window and connect to your intended Paper or Live session. Keep Read-Only API enabled in TWS. Confirm the actual login there; a port number alone does not identify an account's environment.
  2. Use symbol discovery or TWS Contract Description to find the instrument's positive Contract ID. Enter that ID and its Exchange in the existing contract fields. A historical request does not require a quote subscription.
  3. Expand Historical candlestick chart. Choose Trades, Midpoint, Bid or Ask, a bar size, and a duration in seconds. Start with one-minute bars and a duration of 14400 seconds (four hours).
  4. Leave the end field empty for the latest available window. To request an earlier window, enter a UTC value such as 20261007 13:00:00 UTC. UTC is a common time reference that does not change with the computer's local time zone.
  5. Select whether to restrict data to regular trading hours, then choose Read historical bars. The display changes only after the complete response has passed validation. A valid response can contain no bars.
  6. Adjust Visible bars (zoom) to change how many candles appear. Increase Older bars offset (pan) to move backward through the capture. These controls use the existing data and do not send another broker request.
  7. Read the contract, route, interval, capture status and last visible candle below the chart. Unavailable volume is labelled explicitly. A finished response can still include an unfinished final candle.

Bounds and recovery

SettingSupported behaviour
Bar intervals1, 5, 15 and 30 minutes; 1 hour.
Capture sizeAt most 512 bars and 64 KiB per broker response. The duration reserves space for an edge bar.
DurationUp to one day, also limited by bar size. For one-minute bars the maximum is 30660 seconds.
Request pacingOne pending capture per connection; at least 15 seconds between accepted requests. This local throttle does not replace broker-wide limits.
CancellationCancel historical request stops accepting its response. It never cancels a trading order.
Timeout and ageA pending capture times out after 60 seconds. The native view clears captures older than five minutes after receipt, or after disconnect.

If a request is refused, check the contract and route, reduce the duration, verify the UTC format and wait before retrying. A broker rejection appears in the capture message; resolve the reported entitlement or contract issue before trying again. A full transmit queue leaves the previous capture intact. A newly accepted request replaces it.

A precision warning means a reported price cannot be represented exactly by the current decimal owner. The original numeric text remains available to code that inspects retained bars, but the chart refuses to draw that series. A build without the optional chart renderer still shows the capture summary.

Save a capture for offline review

  1. In the historical chart section, enter a new absolute CSV file path in a private folder.
  2. Choose Write new historical-bar report and wait for the saved status. The export takes an independent copy before the file worker starts; changing the chart or reconnecting does not alter that copy.
  3. Import provider price and volume columns as text to retain their spelling. Text cells use the shared protection against spreadsheet formula prefixes, including negative-number text.
  4. Keep the capture-state columns with the bar rows. A pending, cancelled or failed request produces metadata, not fabricated bars. Stale captures remain exportable with their state attached.

Existing files are never replaced. If writing fails, inspect any partial new file and choose another path. Closing the window after the write starts does not undo the requested write. Developers can use UmiIbkrHistoricalExportCsv without opening a native window.

Reuse the implementation

  1. Link Umicom::ibkr_connection and include umicom/broker_connectivity/historical_bars.h. Fill a UmiIbkrHistoricalQuery using a resolved contract and validate it before requesting.
  2. Call UmiIbkrHistoricalRequest with the connection's monotonic clock and keep its returned request ID. Continue pumping the connection. Each accepted request owns a distinct identity, including after cancellation.
  3. Use UmiIbkrHistoricalCopy to inspect completion and freshness, then UmiIbkrHistoricalBarCopy to obtain independent values. Check numeric exact flags before decimal calculations, and the availability flags before using volume, weighted-average price or trade count.
  4. For graphics, link the optional Umicom::ibkr_historical_chart target and include umicom/broker_connectivity/historical_chart.h. Create a scene for a contiguous bar range, render it with the existing chart adapter, and destroy it with umi_chart_render_scene_destroy.
  5. Keep exact broker numbers separate from floating-point presentation values. The candle projection exposes a volume-availability flag; its zero placeholder is not a measured volume. A scene owns its commands, but the application must still check the capture's status before showing it as current.

The decoder supports the connection's negotiated legacy protocol range. Daily bars, historical ticks, streaming historical updates, combination contracts, expired-contract options and protobuf messages need separate implementations. Add their ownership and protocol coverage before extending this contract.
