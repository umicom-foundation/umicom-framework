Capture local assets

An asset is a file you want to use as input: for example, a picture, video clip, recording, document or lyrics. The shared Assets page captures its complete bytes in memory. The capture stays unchanged if the original file changes later.

1. Select and capture

  1. Open the Creative workbench and select Assets.
  2. Choose Choose source file..., select a local file, and confirm. You can also enter its absolute path. Choosing a file does not read its contents.
  3. Enter a meaningful name and select its purpose. Purpose is a label; it does not prove that a file is a valid image, video or audio recording.
  4. Choose Capture local file. The read runs in a worker while the controls show that it is pending. A successful result displays the name, source and complete byte count.

Only one asset is captured in this page at a time. Capturing another replaces it after success. A failed or cancelled load keeps the previous capture. The size limit is 64 MiB; larger files are refused as a whole. Empty files are allowed. A filename alone does not upload data, run a decoder or contact an AI provider.

Preview a captured PNG image

  1. Capture a PNG file, or reopen an asset archive containing one.
  2. Choose Preview captured PNG. Decoding runs in a worker; neither the original bytes nor a saved file is changed.
  3. When complete, the page displays the image fitted to the available space and reports its pixel dimensions.

The decoder validates file content, not the filename or declared purpose. It supports static, noninterlaced PNG images, including palette, grayscale and transparency. Limits are 64 MiB of encoded input, 8192 pixels on either side and 16,777,216 pixels in total. Sixteen-bit samples are reduced to their high eight bits. Colour-profile conversion, EXIF orientation, animation, JPEG and video playback are not provided by this action.

Choosing or capturing a file does not decode it automatically. A refused preview retains its capture for inspection or copying. Replacing or releasing a capture clears the old image. Cancel requests are checked during decoding and pixel packing; large images can temporarily require several full pixel buffers. If the decoder is absent, the page explains that PNG preview is unavailable.

Crop, rotate and export a PNG

  1. Capture a supported PNG and enter its crop rectangle. Crop left and Crop top count pixels from the original top-left corner, starting at zero. Width or height zero means use the remaining image in that direction.
  2. Select an orientation. The crop is applied first, followed by a quarter turn, half turn or horizontal/vertical flip.
  3. Choose Preview captured PNG to inspect the result. Changing an edit clears the old view, so it cannot be mistaken for the new result. Invalid bounds keep the original capture.
  4. Enter a new absolute destination filename ending in .png, in an existing folder.
  5. Choose Export edited PNG to new file. The operation captures the current form, decodes the original again, applies the edits and writes a new PNG. Read its final status and byte count.
  6. Choose Reset image edits and preview again to return to the original pixels.

The original captured bytes and saved archive remain unchanged. Write captured bytes to new file still writes the original file exactly; PNG export writes a newly encoded image. Cropping and orientation preserve the decoded RGBA channels without resampling. Export stores RGBA pixels without copying original text, colour profiles, EXIF or animation metadata. It is not a byte-for-byte re-save of the original PNG.

Existing files are never replaced. Failed or cancelled exports may leave a partial or complete new file for inspection. The original capture remains available. Edits currently belong to the form and are not saved into an asset archive or scene project; export the result to retain them. No Undo history or timeline placement is provided by these controls.

2. Save a separate copy

  1. Review the captured asset details.
  2. Enter a new absolute destination filename in an existing folder.
  3. Choose Write captured bytes to new file. The copy uses the retained bytes, even if the source has changed.
  4. Read the reported status and byte count. Existing destinations are never overwritten.

If copying fails or is cancelled, a new partial file may remain. Inspect it before deciding what to do; it is never deleted automatically. Choose another destination for a new attempt. Cancel is cooperative: a blocking filesystem operation can finish before the worker observes it. A complete file may already have been written when cancellation is reported.

3. Save and reopen an asset archive

A raw copy contains only the original file bytes. An asset archive keeps those bytes together with the name and declared purpose you chose. It is a separate file, not a scene-project attachment.

  1. Capture the asset and review its details.
  2. Enter a new absolute archive filename in an existing folder, for example C:\Users\YourName\Documents\cover.umiasset on Windows or /home/yourname/Documents/cover.umiasset on Linux.
  3. Choose Save new archive and wait for the status to report success. The saved archive is plaintext, so select a folder you control.
  4. You can now close the page. Later, open Assets again, choose Choose saved archive... and select that file. Selection alone does not open it.
  5. Choose Open archive. The complete envelope and checksum are checked before the capture changes. The original source file is not needed.

Opening a damaged, truncated, oversized or unsupported archive keeps the previous capture. A checksum detects corruption; it does not prove who created a file or make media safe to decode. The original source path is deliberately omitted, so restored captures show supplied bytes as their source. To recover the original binary file, reopen the archive and use Write captured bytes to new file.

Saving never overwrites an existing archive. If a save fails or is cancelled, its new file may be partial or complete. Retain it for inspection and select a different filename for another attempt. Archive loading may temporarily hold both the encoded file and restored bytes in memory. The payload limit remains 64 MiB.

4. Manage the capture

Release capture frees the in-memory copy. It does not delete source or copied files. Closing the page releases its capture and requests cancellation of pending work. Captures are not yet saved as project attachments, added to a timeline, embedded in RAG, or included in generation requests. Use the existing Audio clip page for supported PCM-WAVE inspection and editing.

5. Reuse the Framework service

UmiCreativeAssetCapture copies supplied bytes; UmiCreativeAssetLoadFile reads a selected local file. Inspect metadata with UmiCreativeAssetInspect and borrow the immutable byte view with UmiCreativeAssetBytes. Keep the asset alive while readers use that view, then release it with UmiCreativeAssetDestroy. A host that writes a copy calls UmiCreativeAssetWriteNew and inspects both its returned status and write result.

The byte service has no GUI dependency. Native file operations reuse Platform input/output ownership; other hosts can supply bytes from their own file picker. A decoder must validate content before rendering it. A provider adapter must explicitly prepare and review an upload before sending it. This service supplies neither operation automatically.

Include umicom/creative_workspace/asset_archive.h for archive operations. UmiCreativeAssetArchiveSaveNew streams the existing capture to a new native file. UmiCreativeAssetArchiveLoad restores one owned capture. Initialise output asset pointers to NULL; failed operations do not replace a live output. Inspect the returned status and write receipt before reporting success.

For hosts with their own file access, UmiCreativeAssetArchiveEncode returns an owned portable byte buffer and UmiCreativeAssetArchiveDecode restores it. Release an encoded buffer with UmiCreativeAssetArchiveFree. Keep each input asset alive for the entire call. These APIs have no GTK dependency and do not start remote requests.

Image hosts can link Umicom::png_image and include umicom/media/png_image.h. Check UmiMediaPngAvailable, then call UmiMediaPngDecode with a NULL output surface. A successful result uses the existing owned Media image surface; destroy it with umi_media_image_surface_destroy. The decoder performs no native window, file or network operations. Framework uses an installed libpng when available and exports that dependency to SDK consumers. A build without it reports an unavailable capability.

Reusable editing is in umicom/media/image_edit.h. UmiMediaImageSurfaceApplyEdit accepts an exact nonempty crop rectangle and orientation, then returns a separate owned surface. The input remains stable throughout the operation. UmiMediaPngEncode creates a complete owned PNG buffer; release it with UmiMediaPngFree. UmiMediaPngWriteNew composes encoding with native new-file creation and a write receipt. Encoding availability is independent of decoding and is reported by UmiMediaPngEncoderAvailable.

Limits and privacy

Captures and copies are ordinary local data, not encrypted secret storage. Do not use the asset page as an API-key vault. Local reads require ordinary absolute regular files and refuse final links and devices. Parent aliases are trusted, so choose folders you control. The page holds one complete file in memory and provides no streaming, thumbnails, project attachment persistence, general media decoding or mobile/browser packaging. The optional PNG action provides only the image subset described above.
