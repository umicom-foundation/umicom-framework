Build the application, keep every test

An application is assembled from several pieces. Each piece may compile by itself, yet the combined application can still fail before the compiler starts. This guide shows how to recognise that difference and check the complete arrangement without removing tests.

You will rebuild the shared components, run their existing checks together and compile a small C program that uses a market tape, a historical replay and read-only Paper/Live settings. The observations are fictional. The program does not connect to a broker.

Before you begin

Keep a separate copy of any important work. Use a practice build directory, close running Umicom applications and review file replacements before merging them. The steps here do not require deleting your source or build cache.

1. Know which stage failed

Configure
Describe the build→Build
Compile and link→Test
Exercise behaviour

Configuration is CMake reading the project descriptions. A target is an item it should build, such as a library or executable. A dependency is another target that item needs. CMake writes instructions for Ninja only after this description is valid.

Compilation turns C source into object files. Linking joins those objects with the required libraries. CTest then runs registered checks; a successful compilation does not establish that those checks passed.

When a log says Subdirectories may not be created during deferred execution, CMake has not completed its description. The later Ninja message about rebuilding build.ninja is a consequence of that failure. It is not evidence that hundreds of application source files are individually broken.

2. Understand the late integration step

Framework needs some components to wait until their canonical dependency targets have been declared. Its integration functions therefore run at the end of the parent CMake directory. This is a deferred call.

The faulty route tried to create test subdirectories at that late point. The corrected route reads the same test definitions with include(). Every test source is identified relative to the file containing its definition, rather than relative to whichever application happens to be calling it.

# A test source belongs beside this CMake list file.
add_executable(umicom-market-tape-test
    "${CMAKE_CURRENT_LIST_DIR}/test_tape.c")

The library, test names, test logic and arguments remain. The earlier registration commands are kept in explained if(FALSE) blocks for source review. Do not reactivate those blocks in a deferred integration path.

Do not use BUILD_TESTING=OFF as the repair. That can hide the failing test-registration route while also hiding the checks you need.

3. Merge the update into matching folders

Extract the source package into a staging folder. Match Umicom-Applications to C:\umicom\Umicom-Applications, and umicomOS to C:\umicom\umicomOS. Merge Framework first. The OS additions are a small host entry into the same Framework laboratory, not a second implementation.

Use the manifest when reviewing replacements. Keep Build-and-Git.md, Manifest.json and Validation.txt outside the repositories. Do not replace whole folders or delete files that exist only in your checkout.

Open PowerShell in your normal account, then configure:

Set-Location "C:\umicom\Umicom-Applications"

$ErrorActionPreference = "Stop"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --preset windows-ucrt64-all-debug `
    -DBUILD_TESTING=ON `
    -DUMICOM_BUILD_NATIVE_TOOL=ON `
    -DUMICOM_BOOT_MEDIA_ENABLE_DEVICE_WRITES=OFF

if ($LASTEXITCODE -ne 0) {
    throw "Configuration failed. Stop here."
}

Stop at the first failed stage. Successful configuration should reach both Configuring done and Generating done. A new error from another source location needs its own investigation; it should not be hidden with a warning-suppression flag.

4. Build, then run the tests

After configuration succeeds, build the complete application tree:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build `
    --preset windows-ucrt64-all-debug `
    --parallel 2 `
    -- -k 0

if ($LASTEXITCODE -ne 0) {
    throw "Full build failed. Do not proceed to tests or commits."
}

Only after the full build succeeds, run the complete suite:

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --preset windows-ucrt64-all-debug `
    --parallel 2 `
    --no-tests=error `
    --output-on-failure

if ($LASTEXITCODE -ne 0) {
    throw "The full test suite failed. Review the failures before committing."
}

The focused selection below is useful when investigating these components, but it does not replace the complete suite.

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --preset windows-ucrt64-all-debug `
    -R '^framework\.(component_integration|market_tape|research_replay|ibkr_connection)\.' `
    --parallel 2 `
    --no-tests=error `
    --output-on-failure

if ($LASTEXITCODE -ne 0) {
    throw "Component integration or retained regression tests failed."
}

--no-tests=error stops an empty selection from looking successful. The integration checks go further: they compare the actual test names with an expected inventory. A matching total is not enough if one test was accidentally replaced by another.

Platform-specific checks are registered only on their supported platform. A Linux socket test does not become a Windows socket test because both builds use CMake.

5. Run one program that uses all three components

The complete source is framework/examples/component_integration/main.c. The example has no network or file-write call. It creates its own fictional tape and historical replay, then validates separate Paper and Live settings without connecting.

& ".\build\windows-ucrt64-all-debug\bin\umicom-component-integration-example.exe"
if ($LASTEXITCODE -ne 0) {
    throw "The memory-only component example failed."
}

The expected output is:

WORKSHOP bar: open 100.00, high 101.00, low 99.00, close 100.50, volume 8
Historical replay: 4 observations; final equity 9998.50; no open position.
Paper and Live configuration: read-only; Live acknowledgement required.
Practice complete. No broker connection, file write or real order was made.

The tape combines four trades into one bar. The replay requests a long position, fills it on a later quote and closes it on another later quote. The result is 9,998.50 from an initial 10,000.00, because the example crosses the quoted spread. This is an explanation of the supplied fictional calculation, not a performance forecast.

The final policy check confirms that Live configuration needs an acknowledgement and that both configurations remain read-only. A successful configuration check is not a provider login or permission to trade.

6. Follow the C ownership

The tape and replay handles each belong to the example until their corresponding destroy call. The tape snapshot has its own allocation. The final cleanup path releases all three, including after a failed check.

The strategy callback receives a borrowed view: it may read that view during the callback but must not free it. The Framework, not the callback, decides when a simulated request becomes eligible for a fill. These ownership rules remain useful when the same components are later used by a graphical application.

Read the complete, compiled C example
/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/component_integration/main.c
 *
 * PURPOSE:
 *   Use three public Framework components in one native consumer. A fictional
 *   tape and historical strategy share instrument records. Paper/Live options
 *   are validated separately; neither mode opens a socket or enables orders.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/
#include "umicom/trading/market_tape.h"
#include "umicom/strategy_research/research_replay.h"
#include "umicom/broker_connectivity/connection.h"
#include <math.h>
#include <stdio.h>
#include <stdlib.h>

/* The callback requests simulated positions, not broker orders. The replay
 * service decides whether an instruction is eligible on a later observation. */
static UmiStatus PracticeStrategy(const UmiResearchView *view, void *context,
    UmiResearchDirection *target)
{
    (void)context;
    if (view == NULL || target == NULL) return UMI_STATUS_INVALID_ARGUMENT;
    *target = view->observationIndex == 0U ? UMI_RESEARCH_LONG :
        view->observationIndex == 2U ? UMI_RESEARCH_FLAT : UMI_RESEARCH_HOLD;
    return UMI_STATUS_OK;
}

int main(void)
{
    UmiMarketTape *tape = NULL;
    UmiResearchReplay *replay = NULL;
    UmiMarketTapeSnapshot *tapeView = calloc(1U, sizeof(*tapeView));
    UmiMarketTapeConfig tapeConfig = UmiMarketTapeConfigDefault();
    UmiResearchConfig researchConfig = UmiResearchConfigDefault();
    UmiResearchSnapshot result = {0};
    UmiResearchObservation observations[4] = {0};
    const double prices[4] = {100.0, 101.0, 99.0, 100.5};
    UmiInstrument instrument = {.instrument_id = {"WORKSHOP"}, .symbol = "WORKSHOP",
        .venue = "PRACTICE", .currency = {"GBP"}, .multiplier = 1.0};
    UmiStatus status = UMI_STATUS_OK;
    size_t processed = 0U;
    int exitCode = 1;
    if (tapeView == NULL) {
        fputs("Cannot allocate the owned tape snapshot.\n", stderr);
        return 1;
    }
    status = UmiMarketTapeCreate(&tapeConfig, &tape);
    if (status == UMI_STATUS_OK) status = UmiMarketTapeRegister(tape, &instrument);
    if (status == UMI_STATUS_OK) status = UmiMarketTapeBegin(tape, &instrument.instrument_id, 1U, 1U);
    for (size_t i = 0U; i < 4U && status == UMI_STATUS_OK; ++i) {
        UmiMarketTapePacket packet = {0};
        int64_t timestamp = 1000 + (int64_t)i * 200;
        packet.kind = UMI_MARKET_TAPE_TRADE;
        packet.generation = 1U;
        packet.sequence = (uint64_t)i + 1U;
        packet.receivedTimeMs = timestamp;
        packet.value.trade = (UmiTradeTick){instrument, prices[i], 2.0, timestamp};
        status = UmiMarketTapeApply(tape, &packet, NULL);
        observations[i].sequence = (uint64_t)i + 1U;
        observations[i].quote.instrument = instrument;
        observations[i].quote.bid = prices[i] - 0.5;
        observations[i].quote.ask = prices[i] + 0.5;
        observations[i].quote.bid_size = 10.0;
        observations[i].quote.ask_size = 10.0;
        observations[i].quote.event_time_ms = timestamp;
    }
    if (status == UMI_STATUS_OK) status = UmiMarketTapeRead(tape, 1800, tapeView);
    if (status != UMI_STATUS_OK || tapeView->barCount != 1U) {
        if (status == UMI_STATUS_OK) status = UMI_STATUS_INTERNAL_ERROR;
        goto finished;
    }
    researchConfig.initialEquity = 10000.0;
    researchConfig.units = 1.0;
    researchConfig.commissionPerUnit = 0.0;
    researchConfig.slippageBps = 0.0;
    researchConfig.latencyMilliseconds = 0U;
    status = UmiResearchReplayCreate(&researchConfig, observations, 4U,
        PracticeStrategy, NULL, &replay);
    if (status == UMI_STATUS_OK) status = UmiResearchReplayRun(replay, 4U, &processed);
    if (status == UMI_STATUS_OK) status = UmiResearchReplaySnapshot(replay, &result);
    if (status != UMI_STATUS_OK || processed != 4U || result.state != UMI_RESEARCH_COMPLETED ||
        result.position != 0 || result.fills != 2U || fabs(result.equity - 9998.5) > 0.000001) {
        if (status == UMI_STATUS_OK) status = UMI_STATUS_INTERNAL_ERROR;
        goto finished;
    }
    UmiIbkrConnectionOptions paper = UmiIbkrConnectionOptionsDefault();
    UmiIbkrConnectionOptions live = paper;
    live.environment = UMI_TRADING_LIVE;
    live.adapter.paperOnly = 0;
    live.adapter.port = UmiIbkrDefaultPort(UMI_IBKR_TWS, UMI_TRADING_LIVE);
    if (UmiIbkrConnectionValidate(&paper) != UMI_STATUS_OK ||
        UmiIbkrConnectionValidate(&live) != UMI_STATUS_PERMISSION_DENIED) {
        status = UMI_STATUS_INTERNAL_ERROR;
        goto finished;
    }
    live.acknowledgeLive = true;
    if (UmiIbkrConnectionValidate(&live) != UMI_STATUS_OK ||
        !paper.adapter.readOnly || !live.adapter.readOnly) {
        status = UMI_STATUS_INTERNAL_ERROR;
        goto finished;
    }
    printf("WORKSHOP bar: open %.2f, high %.2f, low %.2f, close %.2f, volume %.0f\n",
        tapeView->bars[0].open, tapeView->bars[0].high, tapeView->bars[0].low,
        tapeView->bars[0].close, tapeView->bars[0].volume);
    printf("Historical replay: %zu observations; final equity %.2f; no open position.\n",
        processed, result.equity);
    puts("Paper and Live configuration: read-only; Live acknowledgement required.");
    puts("Practice complete. No broker connection, file write or real order was made.");
    exitCode = 0;
finished:
    if (exitCode != 0) fprintf(stderr, "Component check failed (status %d).\n", (int)status);
    UmiResearchReplayDestroy(replay);
    UmiMarketTapeDestroy(tape);
    free(tapeView);
    return exitCode;
}

7. Practise with the smaller integration laboratory

This is useful for learning and focused investigation. It builds real canonical source subsets, not substitute trading services. It is smaller than the complete Framework and does not qualify the installed applications.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& "C:\msys64\ucrt64\bin\cmake.exe" `
    -S ".\framework\examples\component_integration" `
    -B ".\build\component-integration" `
    -G Ninja `
    -DCMAKE_BUILD_TYPE=Release
if ($LASTEXITCODE -ne 0) { throw "Laboratory configuration failed." }

& "C:\msys64\ucrt64\bin\cmake.exe" `
    --build ".\build\component-integration" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Laboratory build failed." }

& "C:\msys64\ucrt64\bin\ctest.exe" `
    --test-dir ".\build\component-integration" `
    --parallel 2 --no-tests=error --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Laboratory tests failed." }

& ".\build\component-integration\bin\umicom-component-integration-example.exe"
if ($LASTEXITCODE -ne 0) { throw "Laboratory example failed." }

The laboratory requests integration in a child directory before its owner targets exist, just as the failing route did. It then verifies that the deferred callbacks construct the expected libraries and register the tests.

CheckQuestion it answers
Deferred / immediate / mixedDo late, direct and mixed integration paths retain the same checks?
Repeated / reconfigureDo repeated requests and reused build directories avoid missing or duplicate registrations?
Missing / partial ownersDoes an unrelated host avoid acquiring fabricated dependencies?
Tests offDoes the explicit no-tests product configuration still build its tools?
RegenerateCan a private copied project rebuild its Ninja description automatically?
InstalledCan another C project consume the exported SDK targets?

Each probe receives a new directory below the build tree. Logs and failed attempts remain available for inspection. The regeneration case edits only its own private copy of the fixture, never your repository source.

8. Read failures without discarding evidence

Configuration still fails

Check that both the component CMake file and its matching test CMakeLists.txt were merged. Replacing only add_subdirectory with include is not sufficient when the test source paths remain relative to the caller.

No tests matched

Keep BUILD_TESTING=ON, rerun configuration and inspect the test names. ctest -N lists registrations; it does not run them. An empty list is not a pass.

A probe failed

Its error reports the retained directory. Read the configure, build and test logs in that order. Preserve the first substantive message as well as the final exit status.

Native checks pass but a window fails

A headless source check does not test GTK ownership, Windows DLL loading, display scaling or account authentication. Record that application failure separately. This update does not change the broker's read-only boundary or the physical-media write policy.

9. Check your understanding

Questions

1. Why does a failed configuration prevent Ninja from compiling the application?

2. Why would disabling tests conceal this particular defect?

3. Two configurations each list 186 checks. What must you compare before concluding they kept the same coverage?

4. Does the example's Live configuration prove the provider is logged in to a Live account?

5. Who releases the tape snapshot, and why is there one cleanup path?

Answers and explanations

1. Ninja needs a valid generated build description. CMake has not produced one when configuration fails.

2. The faulty call was inside test registration. Removing that route avoids the symptom but removes the checks as well.

3. Compare identities, arguments and supported-platform conditions, then actually execute the checks. The new matrix compares the exact identities and runs the retained suites.

4. No. It validates local settings only. This example opens no connection, and a port or selected mode cannot attest a provider login.

5. The caller owns its allocated snapshot and frees it. A common cleanup path prevents successful and failed paths from forgetting an owned object.

Reference and next steps

The CMake reference explains deferred calls, directory processing and list-file locations. The engineering contract for this repair is docs/development/component-integration.md.
