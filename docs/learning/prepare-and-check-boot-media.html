Umicom · A practical starting point

Prepare a boot image, then check what you are copying

Learn the workflow with an ordinary file before working near a physical device.

You will use Umicom’s native tools to inspect a practice image, review a destination, create a checked copy and understand what the result does—and does not—prove.

No USB is needed for the practice lesson. Physical writing remains disabled in the default build. This guide describes the delivered source workflow, not a hardware-qualified release.

1. Know what you are preparing

A boot device starts a computer before its usual operating system loads. Creating one is therefore different from copying a document onto an ordinary USB drive. A disk image describes sectors, partition tables and, sometimes, the files a boot loader needs. Writing that image directly to a device replaces what was there.

Start with a file-to-file exercise. You will create a small practice image, inspect it, review a new destination, make a verified copy and check the result again. You do not need to plug in a USB drive, change the computer’s startup settings or run as administrator.

What is available in this delivery?

The native tools inspect supported image structures and create checked, new-file copies. The Windows Boot Media Centre adds a graphical view of those operations. Physical USB writing has an experimental backend, but it is disabled in the default build and has not been device-qualified. Optical-disc burning and safe eject are not included.

The existing Setup Centre still provides its earlier boot-file preparation and GRUB ISO path. This new tool does not replace those features. It does not include a ready-to-boot Umicom OS image.

Inspect the image→Review the destination→Confirm the plan→Copy and read back

Three objects that are easy to confuse

An image file is an ordinary file such as practice.img or a qualified umicom.iso. A new-file copy is another ordinary file, useful for checking the workflow. A physical disk is a hardware device with its own identity, capacity and sector size. A drive letter is not enough to identify that whole device safely.

A kernel and umicom-rootfs.cpio.gz from the native OS builder form a direct-kernel boot bundle. They are not, by themselves, a complete USB disk image. Renaming the archive to .iso or .img does not change its contents.

2. Find the tools and run the first checks

Build the applications using the accompanying Build-and-Git.md first. On the standard Windows checkout, open PowerShell and set the build location below. These commands run already-built native programs; they do not install a compiler.

$ErrorActionPreference = "Stop"
$Bin = "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

& (Join-Path $Bin "umicom-media.exe") --self-test
if ($LASTEXITCODE -ne 0) { throw "The media self-test failed." }

& (Join-Path $Bin "umicom-media-review-example.exe")
if ($LASTEXITCODE -ne 0) { throw "The review example failed." }

The first program checks its CRC calculation without opening a file or device. The second uses a fictional image and fictional USB record to show why a protected disk is refused. The fictional record is not a real hardware observation and cannot authorise a physical write.

Native media CRC self-check passed. No file or device was opened.

In this guide, a command followed by an error check is one step. Stop when that check reports a failure. Continuing with old output can make a later result refer to the wrong input.

3. Create a practice image, not a bootable operating system

The supplied example can create a new, two-mebibyte ordinary file. It has a small synthetic partition table so the inspector has something meaningful to read. It contains no filesystem and no operating system. Do not write this practice file to a physical device.

Create a new folder under your own user profile. The unique suffix avoids mixing today’s exercise with an older one. The native example refuses to replace an existing file.

$Practice = Join-Path $env:USERPROFILE ("Umicom Media Practice-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $Practice | Out-Null
$Image = Join-Path $Practice "practice.img"
$Copy = Join-Path $Practice "verified-copy.img"
$Media = Join-Path $Bin "umicom-media.exe"

& (Join-Path $Bin "umicom-media-image-example.exe") --output $Image
if ($LASTEXITCODE -ne 0) { throw "Practice-image creation failed." }

Write-Host "Source image: $Image"
Write-Host "New copy:     $Copy"
Created a new 2 MiB regular-file practice image.
Not bootable: no filesystem or operating system. Do not write it to a physical device.

Without --output, the example keeps the image in memory and releases it before returning. With the explicit output argument, it creates only the named new regular file. It does not create a device node, partition a disk or change the boot loader.

4. Inspect the file and interpret the result

& $Media inspect --image $Image
if ($LASTEXITCODE -ne 0) { throw "The image was not accepted by the inspector." }

The practice image should report 2,097,152 bytes, an SHA-256 value and MBR: yes. GPT, ISO9660 and El Torito should be no. Your output describes the file, not the machine you are using.

MBR and GPT are partition-table formats. ISO9660 identifies an optical-image structure. El Torito is the boot-catalogue structure inspected inside supported optical images. A BIOS or EFI catalogue-entry flag means that such an entry was found and bounded; it does not prove that its code will run on a particular computer.

A useful counterexample

This exercise intentionally produces a file whose MBR structure can be recognised even though it cannot start Umicom OS. A valid table and a matching hash are necessary checks for some workflows, not a complete boot test.

An SHA-256 value identifies the bytes captured during the check. It is not a password, publisher signature or antivirus result. Keep the image in a private folder and do not edit it while inspecting or transferring it. Windows file-sharing rules reject conventional concurrent writers; Linux file locks require other programs to cooperate.

5. Review before creating the destination

& $Media review --image $Image --output $Copy
if ($LASTEXITCODE -ne 0) { throw "The new-file plan could not be reviewed." }

Read the destination path. It must end in verified-copy.img inside the practice folder. At this point that file has not been created.

The output includes a full Fingerprint and a Confirmation beginning with CREATE. The fingerprint binds the image contents and the destination used in the review. For a physical-device plan, the service also binds the observed identity, model, serial, capacity and sector size.

Copy the values from your own result when the next two prompts appear. Do not copy an example fingerprint from a manual; it would refer to a different plan.

$Fingerprint = Read-Host "Paste the full Fingerprint from this review"
$Confirmation = Read-Host "Paste the complete Confirmation, including CREATE"

& $Media copy --image $Image --output $Copy --expect $Fingerprint --confirm $Confirmation
if ($LASTEXITCODE -ne 0) { throw "The copy was not completed and verified." }

The command reviews the current inputs again and requires the same fingerprint. A changed source, changed destination or conflicting existing file stops it. The library’s in-memory plan is consumed when an apply attempt begins; the CLI reconstructs a fresh plan and compares it with the fingerprint you supplied.

The copy operation reads and writes bounded chunks, flushes the target, reads it back and compares its digest. Success means the bytes returned by that read agree with the captured image. It is not a sudden-power-loss test or proof that every hardware cache honoured a flush.

6. Verify independently and test a refusal

& $Media verify --image $Image --output $Copy
if ($LASTEXITCODE -ne 0) { throw "The full-file comparison failed." }

This command compares two regular files of equal length. It is not a command for verifying a physical disk. A changed byte or an extra trailing byte prevents a whole-file match.

Now run the same copy command again. It should refuse the existing destination. That refusal is the intended result; the first verified copy remains intact. Choose a different new filename to practise another transfer rather than deleting output automatically.

A cancelled or failed attempt can leave a partial new file. Keep it for investigation. The program does not label it verified, resume it automatically or remove it behind your back.

7. Use the Windows Boot Media Centre

After the Windows build succeeds, open this executable:

C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-media-centre.exe

Choose Browse beside Complete raw image or ISO and select your practice image. Choose Inspect image and read the observations in the result panel.

Use Choose beside the practice-file destination to enter a new filename. The dialog selects a name; the service still refuses an existing file. Choose Review copy, check the destination and type the exact confirmation into its field. Then choose Create verified copy. Verify file again performs the later full-file comparison.

Changing the image, destination or selected USB record discards the previous review. During work, input controls are disabled. Cancel requests a stop at the next progress boundary. Closing the window while work is active requests cancellation and waits for the owned worker; a native filesystem or device call may take time to return.

The form has native scrollbars for smaller windows and stores its layout in logical coordinates for DPI changes. These Windows controls and their hidden construction test are delivered as source; they have not been executed in the Linux delivery environment. Test the actual window before treating it as a Windows release.

Why is Write reviewed USB disabled?

The default build sets UMICOM_BOOT_MEDIA_ENABLE_DEVICE_WRITES=OFF. This is deliberate. The file exercise remains usable, but a physical write is unavailable until the experimental backend has been deliberately enabled in an engineering qualification build. Do not change that setting merely to finish this lesson.

8. Read a device record without writing it

Discover USB disks, or the command below, requests a read-only inventory. It does not format a drive, mount a filesystem, unmount a volume or request elevation.

& $Media list

The inventory shows an exact device path, model, serial, identity, byte capacity, logical sector size and a reason when writing is blocked. Unknown devices are not guessed into the list. A USB SSD that reports itself as fixed media is not accepted merely because it has a USB cable.

On Linux, the adapter checks the whole disk, its partitions, mounts, swap and kernel holders, then checks the kernel disk-sequence identity again during acquisition. On Windows, it inspects native storage identity and volume extents, excludes the running Windows volume and requires locks on target volumes before a write. Missing or ambiguous observations cause refusal. These are implementation checks, not completed hardware qualification.

Always rediscover after unplugging or reconnecting a device. Compare the physical label, capacity and serial yourself. Never infer a target from a familiar drive letter or assume that yesterday’s device number still belongs to the same disk.

The current physical-image profile

The image limit is 64 GiB and the target limit is 256 GiB. Physical transfers accept only identified removable USB whole disks with 512-byte logical sectors. GPT images require an exactly sized target; GPT relocation and partition expansion are not provided. Optical-only ISO files are refused as USB disk images.

For a larger MBR target, the backend also clears up to the final 1 MiB beyond the image to retire stale trailing partition signatures. Space between the copied image and that final area is left alone. This is not secure erasure. Device contents can be destroyed as soon as the first write occurs; neither cancellation nor a checksum can restore the old files.

9. Move from a practice file to a real boot image

Keep image construction, inspection, transfer and actual boot testing as separate stages. The practice file is deliberately not a substitute for a real Umicom OS image.

The earlier Setup Centre workflow can stage an x86-64 kernel, root filesystem and GRUB menu. Its native Linux ISO command invokes an explicitly selected GRUB tool. The command forms are:

umicom-setup media-stage --kernel ABSOLUTE_KERNEL --initrd ABSOLUTE_ROOTFS --output NEW_PREPARATION_DIRECTORY
umicom-setup media-iso --prepared PREPARATION_DIRECTORY --grub ABSOLUTE_GRUB_PROGRAM --output NEW_ISO_FILE

Replace those capitalised labels with paths from a qualified build, following the Setup Centre guide. These commands are included here to show the existing integration boundary, not as proof that a particular ISO has been built or booted.

Inspect the resulting complete image, then perform a disposable file-copy exercise. A real BIOS boot, UEFI boot and USB-device boot each require their own test. Passing one does not imply the others passed. The native OS builder’s direct-kernel QEMU test is another distinct test: it bypasses a disk boot loader.

This delivery does not burn a CD/DVD, eject hardware, download an operating system, repair firmware, sign a publisher release or qualify a real removable device. Its GUI and native tools provide the next checks and transfer components without pretending those remaining steps are complete.

10. Read the C behind the exercise

Open examples/boot_media/practice_image.c in Studio. The program allocates a two-mebibyte buffer, writes a small synthetic table, optionally creates a named new file and releases the buffer. Ownership is visible: the function that allocates the buffer also frees it on every exit path.

This helper writes a 32-bit value in little-endian byte order:

static void Little32(unsigned char *out, unsigned value)
{
    for (unsigned i = 0; i < 4U; ++i)
        out[i] = (unsigned char)(value >> (i * 8U));
}

Each iteration moves the next group of eight bits into the low position. Converting to unsigned char keeps that byte. The least significant byte is written first. File formats specify byte order; it must not depend on which processor happens to run the tool.

Two mebibytes contain 4,096 sectors of 512 bytes. The example reserves the first sector for its table and describes the remaining 4,095 sectors as a synthetic partition. There is still no filesystem inside that partition. This is why interpreting a table is different from proving that the medium can boot.

Follow the service boundary

Next open include/umicom/boot_media/media.h. UmiBootMediaInspect returns observations. UmiBootMediaReviewFile creates an owned plan. The plan getters return borrowed pointers that remain valid only while the plan exists. UmiBootMediaApply consumes an attempt, and UmiBootMediaPlanDestroy releases the allocation.

The progress callback runs on the invoking thread. It can request cancellation, but it must not free or change the plan, input files or handles. In the Windows adapter, an owned worker invokes the service and posts presentation messages back to the window. The service itself does not manipulate GUI controls.

review_lesson.c demonstrates a pure policy decision. tests/boot_media/test_media.c demonstrates actual new-file copies, tampering, cancellation and stale-review refusals. Its synthetic structures are test inputs, not guest-boot results.

11. Understand the repaired Windows build errors

A compiler needs declarations before it can type-check a call. The Windows System Centre uses the modern network-interface table so it can retain 64-bit byte counters. With the affected MinGW include order, the IPv6 socket definitions were not visible when the interface-table declarations were processed.

The repaired source includes <ws2ipdef.h> after <winsock2.h>, before IP Helper consumes the network declarations. It does not replace the modern counters with an older 32-bit API or suppress the diagnostics.

A different failure came from the private name Folder. The Windows Shell SDK already contributes a type with that name to C’s ordinary identifier namespace. The active private helper is now BrowseExistingFolder. The folder picker, return behaviour and allocated Shell-item cleanup remain the same. The earlier function and call are retained in explained disabled blocks.

The temporary-directory warning has a different cause: formatting a long prefix plus a suffix into one fixed array can truncate the result. The repair builds and checks a bounded filename first, then uses the existing Framework path join to check total capacity. It also retains the separator when the temporary location is a Windows drive root.

After merging, configure and build the repaired targets before running tests. A source-level diagnosis is not a substitute for the actual Windows compiler and SDK; the accompanying instructions include that local check and the full suite.

12. Troubleshooting and review questions

The image is rejected.
Check that it is a complete sector-addressable image rather than a ZIP, kernel or compressed root filesystem. The reader intentionally supports bounded profiles, not every valid disk or optical format.
The copy refuses an existing file.
Choose a new destination. This protects both a previous successful copy and an incomplete one being investigated.
The reviewed fingerprint no longer matches.
Inspect the source, review the current destination and obtain a fresh confirmation. Do not try to force the old plan to execute.
No USB device is offered.
The adapter may lack a complete identity, supported geometry, permission or volume information. Do not change device classification or bypass a refusal to make it appear eligible.
Verification fails.
The read-back did not agree, an input changed, or the operation was cancelled. Keep the source and result for investigation. A partially written device must not be treated as a working boot device.
The command returns 77.
The requested capability is unavailable in this build or environment. That is not a completed transfer or a passed hardware test.

Finally, explain why undoing a source-code change and recovering overwritten USB data are entirely different operations.

Compare your answers

A table describes byte ranges; it does not supply a filesystem or a working boot loader. A digest identifies captured bytes, whereas authenticity needs a separate trusted signing process. An existing destination is refused. In UmiBootMediaApply, p->consumed = 1 marks the attempt before side effects. Source history retains earlier code; a raw-device write replaces data and has no rollback in this implementation.

Keep the useful result

Retain the practice folder and your notes about each refusal. The goal is not to make every button turn green. It is to know what was checked, which inputs were used and what a successful result actually establishes.
