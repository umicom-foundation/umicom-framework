Review a replacement for selected code

Studio can show how a proposed replacement changes the complete source draft before you apply it. The proposal may be your own edit or code you deliberately copy from a chat reply. The form treats it as plain text: it does not run commands, parse patch instructions or extract code from a model response automatically.

Prepare and inspect an edit

  1. If you are using a chat reply, read it first and copy only the code you intend to propose. The chat follow-up guide explains how to discuss earlier text. Copying a reply does not approve a source edit.
  2. In the source editor, select the code to replace. Open AI Coding and choose Review selected-code replacement…. The selection must be nonempty and belong to a writable source document.
  3. Check the document name, captured selection and byte position. The capture includes unsaved source changes and remains attached to this document throughout the review.
  4. Type or explicitly paste into Proposed replacement. It initially contains the captured selection, so opening the form does not propose a deletion. Emptying this field deliberately proposes removing the selection. Remove Markdown fences or explanation paragraphs if they are not intended source code.
  5. Choose Preview complete draft. Read both full texts, including the surrounding code. Use the comparison's difference navigation when available. Long files can exceed the line-alignment limits while both complete texts remain visible; follow the comparison's message.
  6. Select I approve replacing this captured selection with the reviewed text, then choose Apply reviewed replacement. The form closes after a successful change. Changing proposed text clears the preview and approval, so you must preview it again.
  7. Inspect the changed draft in the editor. Undo restores the captured draft. Save remains a separate action; applying the proposal never writes the source file to disk.

Cancel or closing the form leaves the source unchanged. The captured target is fixed: switching tabs or moving the caret does not redirect the edit. If the target's text, saved state, path, permissions or external-change state changes, Apply refuses the old proposal. Close it and capture the intended source again.

Recover without losing later work

  • No selection or read-only target: select text in an editable source file before opening the action. The form does not choose a complete file for you.
  • Proposal is stale: keep any proposed text you still need, cancel the form and reopen it from the current source. A fresh capture prevents an old suggestion from overwriting newer typing.
  • Another document operation is active: finish or cancel that operation before opening or applying a proposal. Save All, reviewed Close and pending clipboard operations are checked at the relevant boundaries.
  • Unsupported text or size: use complete UTF-8 text without embedded zero bytes. The complete resulting document must fit Framework's eight-megabyte document limit and the comparison viewer's supported limit. No truncated replacement is applied.
  • Identical proposal: the comparison says that the text is unchanged. Applying closes the review without adding a new Undo step.

Privacy and ownership

This review uses window memory and the existing document service. It does not fetch provider text, automatically read the clipboard, write a transcript or save the source. Typing or pasting into the form is an explicit local action. The source, proposed input and comparison subtree are marked private for Framework's recording and screenshot policy.

Closing the form releases its captured proposal and clears its input views. The application must unbind document editing before destroying its document coordinator; retained controls cannot call a retired owner. The operating system and clipboard may hold separate copies of text you copied or pasted.

Extend the shared workflow

UmiDocumentProposalCreate captures a nonempty selection and the complete original draft. UmiDocumentProposalSetText prepares a full proposed draft without changing the source. The proposal has its own revision, so callers can reject approval for an older proposed text as well as changes to the source.

Display the complete before-and-after texts, obtain explicit approval, then call UmiDocumentProposalApply with the revision shown to the user. The implementation reuses the replacement owner's identity, save-state and exact-byte checks and its existing Undo transaction. It does not introduce another document store. Use the coordinator's owner thread and keep its dependencies alive through checking and applying.

GTK applications call UmiGtk4AdapterReviewSelectedCode after binding their existing document coordinator. The form owns the capture; the binding's invalidatable token protects application lifetime. A model response should remain untrusted text until the user chooses a replacement and reviews its effect. Add other proposal producers through this same boundary rather than granting them direct file-writing authority.
