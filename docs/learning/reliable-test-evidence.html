Build reliable test reports

A test result describes one observation: what ran, what happened and how long it took. A report puts that observation into a form another program can read. This lesson uses the same Framework services available to Umicom Studio IDE and other applications. It teaches how to keep a failed export from damaging a previous report and how to avoid misleading coverage percentages.

You will use examples/test_evidence/main.c. Its data is invented for a small exercise; it does not claim that any Umicom product passed qualification. You need an installed Framework SDK with the test_platform component, a matching C compiler, CMake and Ninja. If these tools are unfamiliar, start with headers and tests.

1. Understand the three owners

An owner is the part of a program responsible for keeping something alive and releasing it. A snapshot is a copied set of values describing one moment. In this example, the application owns the input snapshot and output buffer. The formatter creates temporary storage, validates the input, and copies a complete report to the output only when everything succeeds.

This is atomic replacement at the API boundary: callers never receive half of a successful report. It is not a lock, a database transaction or a promise of safe concurrent calls. The caller must serialize access and keep the input and output memory separate.

2. Copy and build the installed example

Use a new exercise folder so an earlier edited example is not overwritten. The commands below assume the SDK is installed at C:\umicom\installed\framework. Stop after any command reports an error. This small consumer links installed libraries; it does not build the Framework source tree.

New-Item -ItemType Directory "C:\umicom\examples\test-evidence"
Copy-Item "C:\umicom\installed\framework\share\umicom\framework\examples\test_evidence\*" "C:\umicom\examples\test-evidence"
Set-Location "C:\umicom\examples\test-evidence"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\test-evidence"
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DUMICOM_EXPECTED_SDK_PREFIX="C:/umicom/installed/framework" -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\configure.log"
$LASTEXITCODE
cmake --build build --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\build.log"
$LASTEXITCODE
ctest --test-dir build --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\test-evidence\tests.log"
$LASTEXITCODE

Configuration checks that the selected package comes from the requested SDK directory. A missing component or environment-contract error means the SDK needs attention. Do not point the consumer at a random source build to conceal a missing installation. Use a fresh log folder for a later exercise if you want to retain these logs.

3. Export one result

& ".\build\umicom-test-evidence.exe" result 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\result.log"
$LASTEXITCODE

JSON is a text format made of named fields. For example, "outcome":"failed" pairs a field name with a string. A JSON string cannot contain a literal line break. The formatter writes \n for that break and \" for a quote inside the string. It also escapes other control characters and rejects invalid UTF-8, the encoding used for international text.

The output includes "durationMs":12.500 and an outcome of failed. The program exits with zero when the exercise behaves as designed. That zero means the example's checks succeeded; it does not turn the invented failed result into a pass.

UmiStatus status = umi_test_platform_report_result_json(
    &result, json, UMI_TEST_PLATFORM_RESULT_JSON_CAPACITY);
if (status == UMI_STATUS_OK) {
    puts(json);
}

UmiStatus tells the caller whether the operation succeeded. The capacity is the number of bytes available, including space for the terminating zero byte that ends a C string. Use the published capacity constant rather than guessing a buffer size. Escaping can make output longer than the original text.

4. Refuse a short output without losing prior work

& ".\build\umicom-test-evidence.exe" short-output 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\short-output.log"
$LASTEXITCODE

The example first writes previous complete report into its output buffer. It then deliberately offers only eight bytes to the formatter. The expected message is Short output refused; previous report retained. The caller can now show the error and keep the previous report visible. It must not claim that the old report belongs to the newly refused input.

The formatter also refuses unterminated fixed fields, unknown outcomes, negative durations and nonfinite values such as infinity. It does not silently shorten messages. JSON numbers use a dot as their decimal separator; export does not change the process locale. Do not change the numeric locale concurrently with formatting.

5. Read coverage without confusing it with test success

& ".\build\umicom-test-evidence.exe" coverage 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\coverage.log"
$LASTEXITCODE

Coverage counts which instrumented lines or branches were exercised. A branch is one possible route through a decision. The example reports 90 of 100 lines and eight of ten branches. With the default policy it prints Line coverage: 90.00% | gate: Passed. A gate is a rule that compares measurements with thresholds. A passing coverage gate does not prove the assertions are good or the application is correct.

The API stores percentages as basis points: one point is one hundredth of a percent. Thus 9000 points means 90.00%. Integer arithmetic keeps threshold comparisons stable. The ratio calculation avoids multiplying a large counter by 10,000, which could exceed the largest value an unsigned 64-bit integer can hold.

EvidenceInterpretation
Covered lines exceed total linesInvalid input. The new analysis is refused.
No measured linesUnknown by default. A caller may explicitly allow empty coverage, but should explain that policy.
Skipped testThe test did not exercise its intended behavior. This is separate from a coverage percentage.
Repeated fragmentsFragments are added. Replace a prior revision using its stable registry ID; do not append it as new data.

6. Try a counter overflow

& ".\build\umicom-test-evidence.exe" overflow 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\overflow.log"
$LASTEXITCODE

The expected message is Overflow refused; previous analysis retained. The exercise first publishes a report whose line total is the maximum 64-bit unsigned value. It then adds another fragment with one line. The second total cannot be represented. The analyzer refuses it before publication, preserving the earlier report and its revision.

A revision is a number identifying a retained state. Here it belongs to the registry or analysis, not to Git. Keep source revisions, configuration, host identity and original logs separately when recording real qualification evidence. Do not combine reports from unrelated sessions merely because their file names match.

Read history without turning skips into success

The Framework history analyzer keeps every selected observation in sample_count. Passed, failed and timed-out results supply completed sample counts and duration statistics. Skipped, cancelled and unrun observations remain visible, but they do not satisfy the minimum completed-sample rule. If the latest observation is one of those incomplete outcomes, stability remains Unknown even when earlier executions passed.

Timing means and trends use completed observations. A long skipped setup therefore cannot make a later execution appear dramatically faster. Durations and numeric policy thresholds must be finite and nonnegative. An unrepresentable derived trend refuses the candidate and preserves the previous analysis. The default near-zero baseline rule does not calculate a percentage against times at or below one billionth of a millisecond.

Include umicom/test_platform/history_analysis.h, create a UmiTestHistoryAnalysis, and call umi_test_history_analysis_build with the item and result registries. Read the copied snapshot and item rows after success, then destroy the analysis when finished. Stable is a classification of retained observations under a policy, not proof of complete product qualification.

Compare benchmark measurements

A benchmark measures a property such as latency, the time required to finish an operation. Run the example with benchmark to analyze three invented measurements: 11, 12 and 13 milliseconds against a baseline of 10. A baseline is the reference measurement used for comparison.

& ".\build\umicom-test-evidence.exe" benchmark 2>&1 | Tee-Object "C:\umicom\_local\logs\test-evidence\benchmark.log"
$LASTEXITCODE

The expected mean is 12 milliseconds, population standard deviation is approximately 0.816497 milliseconds, and change is 20%. The mean is the arithmetic average. Standard deviation describes how far measurements spread around that average. Because lower latency is better, this increase exceeds the default tolerance and the example reports a regression. The example itself still returns zero when this expected behavior is observed.

The analyzer scales finite measurements before calculating statistics, so large sums and unscaled squared differences do not overflow. Signed measurements are supported. A zero baseline means absent evidence; nonzero baselines that cancel to a zero mean also leave the comparison unknown. An explicitly honored provider regression remains visible even without a baseline. Invalid numbers or unrepresentable percentage changes refuse the new report while retaining the previous one.

On systems that use a separate standard math library, the SDK exports that link dependency. Use its CMake target rather than listing archive files by hand. Floating-point results can round differently between compiler and hardware combinations; compare measurements with suitable tolerances and record the environment.

Extend the exercise

  1. Change the result outcome to UMI_TEST_PLATFORM_OUTCOME_SKIPPED. The serialized outcome should remain skipped.
  2. Change covered lines from 90 to 50. Inspect the gate and explain why the default line threshold is no longer met.
  3. Set both line counters to zero. Inspect Unknown without enabling allow_empty.
  4. Read src/test_platform/structured_report.c and src/test_platform/coverage_analysis.c. Follow the validation, temporary storage, publication and cleanup paths.
