Retain complete CodeGuard results

1. Separate a completed report from a failed attempt

A quality panel may already display a useful report when the next scan fails. Clearing that report before traversal starts makes a disk error look like a new empty result. Scanning directly into the displayed object can leave only the first few findings from an incomplete attempt. Framework now owns a separate candidate result and publishes it only when scanning returns OK.

Open src/codeguard/service.c. Follow the candidate from result creation through umi_codeguard_scan, result swap and destruction. On failure the candidate is destroyed and the retained report remains unchanged. On success the arrays are swapped; destroying the candidate then releases the former report. A successful scan with zero findings really replaces the previous findings. A failed scan with zero collected findings does not.

2. Keep ownership stable without pretending nothing changed

The service returns a borrowed result object. Its address stays stable until service destruction. Each finding is borrowed from an owned array. Successful replacement invalidates old finding pointers, while a failed scan preserves them. The allocation-free swap transfers array ownership between the retained and candidate objects; it does not copy a second unbounded report. Peak memory still includes both reports during scanning.

/* service is an existing caller-owned UmiCodeGuardService. */
UmiStatus status = umi_codeguard_service_scan(service, &profile);
if (status == UMI_STATUS_OK) {
    /* Read the newly completed report, then apply the chosen severity gate. */
    const UmiCodeGuardResult *current = umi_codeguard_service_result(service);
    /* Render or copy findings while this owner remains stable. */
    (void)current;
} else {
    /* Show the failed attempt separately. Retained findings describe the
     * previous completed scan, not a passing result for this attempt. */
}

This fragment assumes a configured profile and an existing service. Calls must be serialized. The swap is a logical commit point, not a thread-safety primitive or a filesystem transaction. It does not stop other software from changing files during a scan. The ordinary entry point remains synchronous. The optional cancellable service observes a shared token during traversal and analysis boundaries; it creates no asynchronous worker.

3. Preserve the requested workspace

A fixed array can store only a bounded root path. Silently truncating a longer input changes the scan scope. Creation now rejects empty roots and roots longer than 1023 bytes, clears a valid output pointer on refusal and copies an accepted root exactly. Allocation does not prove that the path exists. Relative paths retain their earlier semantics and resolve when scanning occurs; use an absolute path when the workspace identity must not depend on a later current-directory change.

4. Own a finding before growing its array

A caller can borrow a finding from a result and append that same value. If append first reallocates the array, the borrowed input pointer may refer to retired storage. The corrected append copies the finding value before growth, then publishes it only after allocation succeeds. Count, capacity and the array remain unchanged on allocation failure.

The maximum representable item count is SIZE_MAX divided by the size of one finding. Initial allocation and growth respect that bound. Growth near the limit caps at the maximum rather than wrapping a multiplication into a small allocation. Tests isolate the arithmetic with temporary internal metadata instead of attempting an enormous allocation.

5. Read the deterministic regression boundary

  1. Open tests/codeguard/test_transactional_results.c. It includes the production ownership sources once and substitutes only allocator and scanner boundaries.
  2. Read partial-failure: the scanner writes candidate findings before returning an error. The retained object, findings and summary must still describe the prior successful scan.
  3. Compare first-failure, replace and empty. They distinguish an incomplete initial attempt, a complete replacement and a complete empty report.
  4. Read candidate-object and candidate-items. They inject allocation failures before scanning and check that the scanner was not called.
  5. Read result-alias-growth. Its allocator always moves the array and poisons retired storage, so the test does not depend on whether the system realloc happens to keep an address.
  6. Compare result-swap, result-swap-empty and result-swap-invalid. Check ownership after exchange and verify that all allocations are released.

The scanner double controls failure timing; it does not validate source rules or directory traversal. Keep the existing CodeGuard rule and scanner tests as well. The focused fixture compares finding fields rather than unspecified C structure padding. Quarantined storage is released at the end of each test.

6. Run the focused qualification

Use an already configured Framework build with BUILD_TESTING enabled. Replace the build path consistently with your own configured directory. Run each command separately and stop on an error. These commands are a qualification workflow, not a claim that they have run on your machine.

cmake --build build/windows-ucrt64-debug --target umicom-codeguard-ownership-tests --parallel 2
ctest --test-dir build/windows-ucrt64-debug -R "^framework[.]codeguard_ownership[.]" --output-on-failure --no-tests=error

Expect 30 focused ownership cases with no failures or skips, including cancellation and analysis capacity exhaustion. If an ownership case fails, inspect the failed boundary before widening the expected result. If the test target is absent, configure the current source with BUILD_TESTING enabled. A successful configuration registers checks; it does not compile or execute them. Existing scanner and product suites require their own build and run.

7. Build an independent application

The complete [installed SDK example](../../examples/sdk_codeguard/README.md) links the exported CodeGuard component without a Framework source checkout. It checks scanning, report writing and the severity gate separately. Read its main.c and follow the README with your installed package. A failed output stream is not a successful report, and an OK scan status does not mean no high-severity findings were found.

Exercise

Design a panel state with two fields: the last completed report and the latest attempt status. Walk through success, partial failure, allocation failure and successful empty replacement. State when each borrowed finding pointer becomes invalid. Then extend the fixture with a timeout outcome and predict which state should remain visible. Keep source scanning, UI presentation and policy decisions at separate boundaries.
