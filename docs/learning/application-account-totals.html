Calculate a training account balance

A banking screen needs more than a number with a currency symbol. The program must know what currency the amount belongs to, how its units are represented and whether an operation can be completed safely. We will use a small training account to practise these decisions. No bank connection or real payment is involved.

Choose a clear representation

For this GBP example, an amount is stored in pence. 10000 means £100.00. The scale is 2, meaning that two decimal places are used when displaying the amount. This keeps our example calculations in whole-number arithmetic; we do not use a floating-point approximation for settled cash.

UmiMoney is a Framework structure. A structure groups related fields: here, the minor-unit amount, scale and currency. The currency array contains G, B, P and a terminating zero byte. The terminator marks the end of a C string; it is not another displayed character.

Follow the deposits

The array deposits contains three amounts: £25.00, £5.00 and £12.50. The loop visits each array element once. sizeof(deposits) / sizeof(deposits[0]) calculates the number of elements in this array. Indexing starts at zero, so a three-element array has positions zero, one and two.

For each deposit, we create a matching UmiMoney value and call umi_money_add. The function checks currency compatibility and whether the result fits in its integer representation. The expression &balance passes the address of the balance object, allowing the function to write the accepted result back to it.

Separate arithmetic from banking policy

The example next requests a £32.50 payment. Before subtracting, it checks that this payment does not exceed the training balance. This is an application rule. It is separate from checking that integer subtraction is representable. Correct arithmetic alone does not prove that a payment is authorised.

Framework owns the reusable money operation. A real account service would also own permissions, limits, reservations, ledger entries and persistence. A button should request a payment through that service; it should not write a new account balance directly.

Work out the expected result

Starting balance: 10000 pence
Deposits:          2500 + 500 + 1250 pence
Payment:           3250 pence
Final balance:    11000 pence = GBP 110.00

The program prints GBP 110.00 and returns success only when the calculated balance is 11000 pence. That final comparison gives us a small executable check. In a larger test suite, we would also check rejected inputs and boundary values.

Bad code and a safer approach

/* Do not use this as the account update. */
balance.minor_units += deposit.minor_units;

This line has no currency check and can overflow a signed integer. Use the shared checked operation and handle its result. A failure must leave the previous account value intact. Do not display “payment complete” merely because a button callback ran.

Extend the exercise

Add a fourth deposit of 200 pence and predict the new output. Then change the payment to more than the available amount and trace the rejection. Keep each experiment separate so that a changed result has an understandable cause.

Build and run the supplied example

Configure the learning targets once using the course setup. Run the commands below one at a time. Stop when a command reports a failure; do not continue to run an older executable.

Windows · PowerShell

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --build --preset windows-ucrt64-all-debug --target umicom-learning-account-totals --parallel 2
& ".\build\windows-ucrt64-all-debug\bin\umicom-learning-account-totals.exe"

Linux · terminal

cd "$HOME/umicom/Umicom-Applications"
cmake --build --preset linux-gcc-all-headless-debug --target umicom-learning-account-totals --parallel 2
./build/linux-gcc-all-headless-debug/bin/umicom-learning-account-totals

account_totals.c

framework/examples/learning/projects/account_totals.c

/*-----------------------------------------------------------------------------
 * Umicom Framework — application development lessons
 * File: examples/learning/projects/account_totals.c
 * PURPOSE: Use shared money operations for a GBP training account, without real payments.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/

#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include "umicom/finance/money.h"

/* This is training data, not an account connected to a bank. */
int main(void)
{
    UmiMoney balance = {10000, 2U, {{'G', 'B', 'P', '\0'}}};
    const int64_t deposits[] = {2500, 500, 1250};
    UmiMoney payment = {3250, 2U, {{'G', 'B', 'P', '\0'}}};

    for (size_t index = 0U; index < sizeof(deposits) / sizeof(deposits[0]); ++index) {
        UmiMoney deposit = {deposits[index], 2U, {{'G', 'B', 'P', '\0'}}};
        if (umi_money_add(&balance, &deposit, &balance) != UMI_STATUS_OK) {
            fputs("Deposit cannot be represented. Balance was not changed.\n", stderr);
            return EXIT_FAILURE;
        }
    }
    /* Application policy is checked before the shared arithmetic. */
    if (payment.minor_units > balance.minor_units) {
        fputs("Payment rejected: insufficient training balance.\n", stderr);
        return EXIT_FAILURE;
    }
    if (umi_money_subtract(&balance, &payment, &balance) != UMI_STATUS_OK)
        return EXIT_FAILURE;
    printf("Umicom training account: GBP %" PRId64 ".%02" PRId64 "\n",
        balance.minor_units / 100, balance.minor_units % 100);
    return balance.minor_units == 11000 ? EXIT_SUCCESS : EXIT_FAILURE;
}
