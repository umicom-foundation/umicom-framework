Working with reviewed project files

Studio's coding adapter and Framework's local coding workspace use the same file service. The service reads complete files and writes a complete replacement before publishing it. Reviewing and approving a proposed change remains the coding service's responsibility.

Apply a reviewed change

  1. Open the project you intend to edit. Keep source files in ordinary folders beneath its root. Create required parent folders with the project's file tools before applying a patch.
  2. Read the proposed before and after text, including every affected filename. Preparing or recording a patch does not approve it and does not write source files.
  3. Approve the reviewed patch explicitly. If its before text no longer matches the file, review the newer contents and prepare a fresh change instead of bypassing the conflict.
  4. Apply the approved change. Framework opens existing parent folders, writes a temporary sibling file, flushes and closes it, then publishes the selected file. Unicode names use explicit UTF-8 conversion on Windows.
  5. Inspect the resulting source. Revert through the coding service if needed; reversion also checks the current contents before restoring the previous text.

Use the service from C

A workspace adapter captures an absolute root when it is initialized. A later change to the process's current directory therefore does not redirect its file operations. Keep the adapter's workspace alive until all calls have finished.

#include "umicom/ai_coding_runtime/local_workspace.h"

UmiAiCodingLocalWorkspace *workspace = NULL;
UmiAiCodingWorkspaceAdapter adapter;
UmiStatus status = umi_ai_coding_local_workspace_create(projectRoot, &workspace);
if (status == UMI_STATUS_OK) {
    status = umi_ai_coding_local_workspace_adapter(workspace, &adapter);
    if (status == UMI_STATUS_OK) {
        /* Pass the adapter to your approved patch workflow.
         * The workflow still owns approval and conflict review. */
    }
}
umi_ai_coding_local_workspace_destroy(workspace);

The lower-level UmiRootedFileRead, UmiRootedFileWrite, UmiRootedFileRemove and UmiRootedFileExists functions are declared in umicom/platform/rooted_files.h. They accept an absolute root and a portable relative filename. They grant no workspace trust or editing permission.

Handle failures without losing source

  • Missing parent: create the intended folder separately. The file service does not invent a directory tree from a proposed patch.
  • Capacity exceeded: a bounded read refused the entire file. No partial text is returned. Choose an appropriate supported limit before requesting another read.
  • Binary text: the coding adapter refuses embedded NUL bytes. Use the binary platform reader for binary data instead of presenting it as editable patch text.
  • Permission denied: inspect file permissions, Windows read-only state, open handles and links. Do not automatically retry with broader privileges.
  • Invalid path: use an ordinary filename. Traversal, repository metadata paths, Windows device aliases, alternate streams and ambiguous names are refused.

Understand the limits

This is single-file publication, not a transaction across several files and not an operating-system sandbox. Serialize edits within your application. An external program can still change a file between the coding service's review and its later write.

The selected root and its descendants must not be symbolic links or Windows reparse points. Ancestors above that root are trusted. POSIX operations use opened directory descriptors; Windows retains parent handles during the call. A root containing a literal backslash on POSIX is refused because portable Framework paths treat that character as a separator.

Replacement copies ordinary POSIX permission bits, but not ownership, access-control lists or other extended metadata. Windows read-only files are refused. Hard-linked aliases keep the previous file contents when a new file replaces the selected directory entry. If you depend on special file metadata, review that requirement before using this adapter.

Flush and close errors are reported, and a failed publication keeps the prior destination. A failed temporary-file cleanup may leave a sibling named .umicom-write-.... Do not treat that file as an applied patch. Power-loss durability of the parent directory is not guaranteed. The synchronous APIs belong on an application worker when used by a GUI.

For general filesystem operations, see Unicode project paths.

Create an export without replacing an existing file

Saving an edited document and creating a new practice copy have different requirements. UmiRootedFileWrite deliberately supports replacement. Use UmiRootedFileCreate when a selected destination must be new, such as a lesson example, an export or a separate evidence file.

#include "umicom/platform/rooted_files.h"

UmiRootedFileCreation report;
UmiStatus status = UmiRootedFileCreate(
    selected_root, "practice/example.c", verified_bytes, byte_count, &report);
if (status == UMI_STATUS_OK) {
    /* The new file was written, flushed and closed. */
} else if (report.created) {
    /* A partial new file remains. Show its path and report.bytes_written. */
} else {
    /* Creation was refused or failed before a new leaf was opened. */
}

This fragment assumes that the application already owns a selected absolute root and the input bytes. The practice directory must exist. The service checks relative path syntax and opens checked parent directories. The native create operation refuses an existing leaf, including a symbolic link. There is no earlier existence check followed by an overwrite, no shell invocation and no automatic parent creation.

The report is initialized on every call. created records a successful exclusive open; it does not promise a complete file. bytes_written counts bytes accepted by native writes. complete becomes true only after writing, flushing and closing succeed. A later failure leaves the new file in place for inspection. Unlike the replacement writer's staged publication, exclusive creation may expose an incomplete new file to other readers on some platforms. Use the reported status rather than file existence to decide whether copying succeeded.

New POSIX files start with mode 0600, restricted further by the process umask. Windows uses the parent directory's inherited access policy. No original permissions or extended metadata are copied. Ancestors above the chosen root remain trusted. Concurrent callers can compete for one destination; only one may create it, and refused callers must choose a different name. A successful flush and close still cannot guarantee survival of every power failure or later external edit.

For a complete learning example, read examples/learning_pack_inspector/practice.c. Its UmiLearningPracticeCopy service verifies a manifest-declared example's bytes before calling rooted exclusive creation. The application previews the choice and requests copying explicitly; neither operation grants permission to build or execute the copied code.
