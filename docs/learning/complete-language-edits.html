Review complete language edits

Choose how diagnostic context arrives

Some fixes need the server's diagnostic data. Select Include fresh diagnostics for fixes to obtain that data within the action request's own connection. The default waits for a notification. Select Use pull diagnostics for fixes as well when the server offers explicit diagnostic requests.

  1. Choose the source scope and both diagnostic options before requesting actions. The pull option has no effect while diagnostic context is unchecked.
  2. Choose Request code actions. All selected drafts are sent first. Framework requests a complete diagnostic report for the primary draft, validates its ranges and includes the relevant original diagnostic objects in the action context.
  3. Select a returned edit-only action and use the normal complete comparison and approval workflow. Diagnostics themselves do not grant permission to edit.

Missing providers, refused or unchanged reports, invalid ranges and unsupported related-document reports stop the action request. Studio does not replace a failed diagnostic capture with an empty context. Changing either diagnostic option retires pending choices and approvals, even if changed back afterward. Captures shown in a separate Problems window are not reused across server connections.

SDK hosts can use UmiLanguageCodeActionQueryNativeWithContext or UmiLanguageCodeActionQueryOnServerWithContext with optional additional sources. Select UMI_LANGUAGE_ACTION_DIAGNOSTICS_NONE, UMI_LANGUAGE_ACTION_DIAGNOSTICS_NOTIFICATION or UMI_LANGUAGE_ACTION_DIAGNOSTICS_PULL. Existing APIs keep their previous contracts. Pull context requires both diagnostic and code-action capabilities, shares one read budget, and preserves opaque diagnostic data only within that connection.

A rename can affect several open documents, and the server may use other drafts to understand the symbol. Framework keeps a copy of every supplied source dependency, builds every proposed result, and requires a complete review before changing any document. A dependency is a document used to produce the answer, even when the answer does not edit that document.

Capture before making the request

  1. On the document coordinator's owning thread, collect the explicit document IDs that the chosen server should receive. Call UmiDocumentSourceWorkspaceCreate from umicom/document/source_workspace.h. The capture accepts read-only dependencies and owns their complete UTF-8 text.
  2. Read metadata with UmiDocumentSourceWorkspaceAt and text with UmiDocumentSourceWorkspaceRead. Copy the values before dispatching a worker. Keep the document capture on its owning thread; workers must not follow live document or native widget pointers.
  3. For a temporary rename query, put the primary source in UmiLanguageRenameRequest and other sources in UmiLanguageQuerySource rows. Call UmiLanguageRenameQueryNativeWithSources. Each exact URI must be distinct. The request sends every supplied draft before asking for the rename, and closes every successfully opened draft before publishing a result.
  4. Wait for the worker to finish and return the owned catalogue. No document has been edited by this query. Failed source messages, invalid returned ranges and failed cleanup do not publish a usable result.

Prepare the complete review

  1. Link Umicom::source_review and include umicom/source_review/workspace_edit.h. This composition sits above the document and language services, so neither lower-level service depends on the other.
  2. Back on the document owner's thread, call UmiSourceWorkspaceEditReviewCreate with the original capture, complete catalogue and the protocol version actually sent. Temporary native queries use version 1 for all synchronized sources. Editor revisions and protocol versions are separate values.
  3. On success the function takes ownership of the capture and catalogue and clears both input pointers. On failure both remain yours to destroy. It resolves every target by exact URI, validates all previews, and stages a complete transaction. An unknown target, read-only target or invalid range refuses the whole proposal.
  4. Use Inspect, At and Texts to present every changed document's complete comparison. Call AcceptDocument only after showing that comparison. The revision comes from the review summary.
  5. Borrow the catalogue with Catalogue to show edit ranges and complete annotation labels and descriptions. An annotation is an explanation supplied with an edit. AnnotationState identifies which explanations require confirmation; call ConfirmAnnotation for each explicit decision. Unused annotations remain visible but do not require confirmation.
  6. After every changed document and required explanation is reviewed, collect final approval and call Apply. Framework rechecks every captured dependency, including untouched documents, before publishing the complete draft transaction.
  7. Destroy the review when finished. Saving is a separate operation. Undo restores each changed draft separately; this workflow does not create one project-wide Undo command.

Use the native panel

GTK hosts can call UmiGtk4AdapterReviewWorkspaceEdits instead of implementing the presentation above. The panel displays complete comparisons, literal edit details, individual confirmation controls and a final approval. It must use the same coordinator as the adapter's document binding. Preflight failures leave the model with the caller. Once native construction begins, the panel takes ownership and clears the input pointer, including if parent closure cancels construction.

The window participates in the existing replacement busy and cancel commands. Closing the parent, unbinding documents or closing the review invalidates retained controls. The panel is private in interaction recordings. A server description cannot execute markup or become an editor command.

Use the same review for code actions

  1. Capture the intended source set on the owner thread as above. Use UmiLanguageCodeActionQueryNativeWithSources from umicom/language_runtime/code_action_query.h with the primary range and copied additional sources.
  2. Pass 1 for include_diagnostics to obtain fresh primary diagnostics within that connection, or 0 for an empty diagnostic context. Other values fail preflight. Each synchronized source uses protocol version 1.
  3. Present action titles, disabled reasons and command requirements from the owned action catalogue. Keep the source capture while the user chooses among these actions; changing selection alone does not change the captured source inputs.
  4. For the selected action, call UmiLanguageCodeActionCatalogueReadEdits. It returns a separately owned workspace-edit catalogue. It refuses disabled, unresolved and command-dependent actions rather than applying an incomplete part.
  5. Pass that complete edit catalogue and the original source capture to UmiSourceWorkspaceEditReviewCreate. The action catalogue remains yours; only the selected decoded edits and source capture transfer on success. The complete review checks all dependencies and targets, including required annotation confirmations, before applying.

The GTK Actions form exposes additional-source inclusion independently of diagnostic context. Its source capture transfers to the complete review when a selected action opens successfully. To review a different action afterward, close the complete review and request again. This avoids keeping a second mutable owner of the same capture.

Limits and recovery

Capture and document application are bounded to 64 documents, 8 MiB per draft and separate 64 MiB source, proposal and history preparation budgets. The native query has a smaller 65536-byte limit for each complete JSON message, including escaping and its protocol envelope. A source that fits the document owner may still exceed the native message limit. Preview accepts at most 256 edits per target. The query uses one shared protocol version; mixed document versions require a separate capture policy.

Targets outside the captured set return NOT_FOUND. Open the necessary drafts and request again; do not discard the missing targets and apply a subset. File creation, renaming and deletion remain unsupported. Exact URI comparison does not resolve filesystem aliases. Hosts must prevent aliases from representing one document twice.

A changed source, saved revision, identity, caret, selection, permission or conflict marker requires a new capture. Opening an unrelated document does not extend an existing capture. Read-only dependencies can contribute source; a returned edit targeting one is refused. No source is saved or loaded from disk by the review service.

Preparation runs on the document owner thread and may take time for large source sets. It does not dispatch native events or call external providers while preparing or applying. The shared store and view publication relies on that owning-thread rule; it is not a cross-service snapshot for arbitrary concurrent observers. Native startup and synchronous writes retain their existing cancellation limitations.
