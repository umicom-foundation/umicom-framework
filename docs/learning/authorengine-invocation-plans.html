Prepare complete native tool plans

A desktop application often needs an external tool to build a document, inspect a provider or generate a result. The application should first describe the intended operation as data that can be reviewed. Framework's AuthorEngine integration creates a native invocation containing an executable, separate arguments and a working directory. Preparing this value does not run the tool.

Prerequisites: C structures, arrays, pointers and status returns. Follow the declarations in authorengine.h and the implementation in authorengine.c. AuthorEngine itself is an independently installed program; a plan is not evidence that the program is installed or that its version supports every operation.

1. Keep arguments separate

A shell command string mixes program structure with input text. A native argument vector keeps each value separate, so a path containing spaces remains one argument. Framework does not quote or concatenate the values into a shell command. The process adapter must retain this distinction when launching and must select the plan's working directory explicitly.

#include <string.h>
#include "umicom/ai/authorengine.h"

UmiStatus prepare_book_build(UmiAiAuthorEngineInvocation *plan)
{
    UmiAiAuthorEngineConfig config = {0};
    strcpy(config.executable, "uaengine");
    strcpy(config.workspace, "C:/Projects/My Book");
    /* Publication commands do not require an AI provider. */
    return umi_ai_authorengine_plan_publication_invocation(
        &config, UMI_AI_AUTHOR_ENGINE_BUILD, NULL, plan);
}

A successful value contains the command argument build and the configured working directory. It does not check whether the directory exists, resolve a trusted executable, create output folders or publish content. Those decisions belong to the later approved execution boundary. A relative executable name still needs deliberate resolution by the launcher.

2. Validate fixed configuration fields before reading strings

A field such as char workspace[UMI_AI_TEXT_CAPACITY] may contain no terminating zero byte. Checking only its first byte does not make snprintf(..., "%s", workspace) safe. Publication planning now uses Framework's bounded text-field validator before copying executable and workspace.

AI planning already validates all three configuration fields and requires a provider. Publication planning uses only executable and workspace; provider metadata is unused and remains optional. Neither validator checks path existence, credentials, encoding validity or executable trust. A field that is correctly terminated can still be unsuitable for execution.

3. Publish only a complete plan

Consider a preview plan that accepts a site folder, or an AI generation plan whose final output-path argument is too long. A direct writer could clear the old plan, copy the executable and several arguments, then return an error. The caller would receive a failed status alongside a partially changed value.

The public planners now use the shared value-construction helper:

  1. Allocate a temporary candidate for the inline invocation fields.
  2. Build and validate every argument in that candidate.
  3. Copy the complete candidate into the destination only after success.
  4. Free the candidate on every return path.

A failed request, including allocation failure, leaves the previous destination unchanged. This is useful for an editable launch form: the last complete value stays available while the draft is corrected. The caller must still stop execution after a failed planning call. Keeping an older valid plan does not mean the user approved executing that older plan.

4. Understand the two command families

PlannerCommand familyInput requirements
umi_ai_authorengine_plan_invocationHealth, provider catalogue and generationExecutable, workspace and provider; generation also requires session, model, input and output values.
umi_ai_authorengine_plan_publication_invocationProject initialization, ingestion, build, export, preview serving/opening, rendering, doctor and publicationExecutable and workspace; a nonempty site override is accepted only for preview serving.

The external command spellings and argument order are preserved. A site override on a build or export request returns UMI_STATUS_INVALID_ARGUMENT. An argument at or above its destination capacity returns UMI_STATUS_CAPACITY_EXCEEDED; truncation would change the selected path and is refused. The configuration workspace field is larger than one argument slot, so an AI plan can refuse a workspace that a publication working-directory field can hold.

5. Borrow text from a previous plan carefully

An editor may pass a path already stored in the destination plan back into the planner. Staging keeps that old storage readable until every input has been consumed. The resulting invocation owns copies of its text, so it does not retain caller pointers after success.

/* draft_site points into the previous plan. Both objects remain alive
 * and access is serialized until the planner returns. */
const char *draft_site = plan.arguments[4];
UmiStatus status = umi_ai_authorengine_plan_publication_invocation(
    &config, UMI_AI_AUTHOR_ENGINE_SERVE_PREVIEW, draft_site, &plan);
if (status != UMI_STATUS_OK) {
    /* Show the failure and keep editing. Do not launch the retained plan. */
}

Borrowing does not make dangling pointers valid. Non-configuration string inputs must still be readable, zero-terminated strings. Keep all inputs stable for the call. The helper adds no lock and no ownership of threads, processes or provider handles.

6. Run the boundary exercises

From the Framework repository with its configured toolchain, stop after any failed command:

cmake --preset windows-ucrt64-debug
cmake --build --preset windows-ucrt64-debug --target umicom-ai-authorengine-planning-test umicom-ai-authorengine-boundary-tests
ctest --test-dir build/windows-ucrt64-debug -R '^framework[.]ai[.]authorengine[.]planning[.]|^framework[.]ai_authorengine_boundary$' --output-on-failure --no-tests=error

The planning scenarios check the publication command mappings, required fields, unterminated arrays, exact argument limits, late refusal, borrowed input and literal punctuation. They create plans only. A semicolon or a dollar sign in these fixtures is data, never a shell instruction. The installed consumer checks the same exported boundary without invoking AuthorEngine.

  1. Build one valid plan and copy its complete bytes.
  2. Request a site override for a non-preview command. Expect an invalid-argument result and unchanged destination bytes.
  3. Supply an overlong final output argument. Expect a capacity error with the original plan intact.
  4. Pass a site pointer borrowed from the old plan into preview planning. Confirm the exact new argument survives.
  5. Keep process execution as a separate exercise with reviewed tool identity, working directory, authorization and actual exit/log evidence.

Configuration or test registration does not establish that these executables ran. No real AuthorEngine process, installed SDK execution, filesystem side effect or GUI workflow is qualified by a source review of the planner.
