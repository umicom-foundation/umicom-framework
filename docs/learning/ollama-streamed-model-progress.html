Native AI application learning path

Read streamed model progress with the Umicom Framework SDK

Build a C23 client that understands model-download progress without performing a download. This course uses the Umicom Framework SDK, synthetic messages and an ordinary console program. You need pointers, structures, callbacks and basic CMake experience. No Python environment or provider account is required.

Lesson 1: understand the response contract

Ollama documents POST /api/pull with a model name and streamed status responses by default. Events can include a status, digest and byte counters. The stream: false option selects a single response. See the official pull API. Umicom's code here reads supplied response bytes; it does not send that request.

A streamed response uses newline-delimited JSON: each line contains a separate JSON value. Network reads may split anywhere, including inside a string or a multibyte character. A read is therefore not a record. See Ollama streaming. The native owner accumulates bounded lines and sends complete objects to the existing Framework JSON decoder.

Lesson 2: separate progress, completion and installation

ObservationWhat it establishesWhat remains separate
A progress objectThe provider supplied that messageSuccessful HTTP completion and local file contents
Exact status successA provider terminal claimEnd of input without a later error
Successful FinishA complete admitted protocol sequenceServer identity, downloaded bytes and inference readiness
A digest stringCopied provider metadataA locally verified cryptographic hash

Ollama can send an error object after streaming has begun, without changing the already-sent HTTP status. See streaming errors. A client that trusts only HTTP 200 can show false success. The Umicom decoder gives error text precedence if an event also contains a status.

When transport integration is added, check the reviewed endpoint, permission, HTTP outcome and transport EOF independently. Call Finish only after a successful transport outcome. Release the owner on a transport error. A loopback endpoint can still contact an external registry; locality of the address does not authorize a download.

Lesson 3: build a project using the installed SDK

  1. Install a qualified Framework SDK into a separate prefix such as C:SDKsUmicom, using its documented compiler and architecture.
  2. Copy the complete directory share/umicom/framework/examples/ollama_pull to C:Projectsmodel-progress. It contains main.c and CMakeLists.txt.
  3. Use the matching toolchain. The project verifies the selected installed package and environment contract, links Umicom::ai and stages the approved Umicom identity through the SDK helper.
  4. Run each command separately and stop on an error:
cmake -S C:/Projects/model-progress -B C:/Projects/model-progress/build -G Ninja -DUMICOM_SDK_ROOT=C:/SDKs/Umicom -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DBUILD_TESTING=ON
cmake --build C:/Projects/model-progress/build
ctest --test-dir C:/Projects/model-progress/build --output-on-failure

Expected behavior: the example reads two synthetic events in seven-byte chunks, reports that no model was downloaded or verified, and checks that a response missing its terminal record is refused. The test is named sdk.ollama-pull.progress. These are instructions and expected results, not a claim that your installed package has passed.

Lesson 4: own a stream and its copied observations

UmiOllamaPullStream *stream = NULL;
UmiStatus status = UmiOllamaPullStreamCreate(NULL, NULL, &stream);
if (status == UMI_STATUS_OK)
    status = UmiOllamaPullStreamFeed(stream, bytes, length, NULL);
/* Call only at independently successful transport EOF. */
if (status == UMI_STATUS_OK)
    status = UmiOllamaPullStreamFinish(stream, NULL);
UmiOllamaPullSnapshot observation = {0};
if (stream != NULL)
    UmiOllamaPullStreamRead(stream, &observation);
UmiStatus released = UmiOllamaPullStreamRelease(&stream);

This fragment assumes bytes and length describe the complete input; a transport adapter calls Feed for every chunk. The complete example shows repeated calls and checks release. Read copies the last event, counts and failure state even after a parse error. Earlier callbacks are not rolled back. Do not retry a failed feed on the same owner: release it and begin a separately authorized operation.

An optional observer receives a borrowed event valid only during that callback. Copy it before retaining it. Calls are serialized by the application. The observer may read a snapshot, but feeding, finishing or releasing the same owner returns BUSY. This guard prevents re-entry; it does not make concurrent thread access safe. A graphical product should marshal copied observations to its existing UI owner.

Lesson 5: keep values and limits honest

Check known before using total or completed. Missing is different from zero. Counters retain exact integers through INT64_MAX, including values that cannot be represented exactly by a JavaScript number. The reader refuses fractions, exponents, negative values and completed counts above a simultaneously reported total. Never sum repeated progress events: counters can refer to the current layer and are not an incremental byte delta.

The limits are 16 KiB per line, 16 MiB admitted input, 65,536 events, 512 JSON nodes per event and 16 nested containers. A possible trailing CR counts toward the line bound. Empty LF/CRLF lines are ignored; whitespace-only records are refused. The final object may omit LF. All object keys, including unknown extensions, must be unique. Status, digest and error fields hold at most 256, 128 and 1,024 UTF-8 bytes respectively. Nothing is silently truncated.

A failure latches and clears pending text. Earlier events remain visible for diagnosis. A successful feed is never a completed pull, and a provider error record is delivered before Finish returns IO_ERROR. Treat provider text as untrusted display data: use a fixed format string, escape it for HTML and avoid publishing private errors.

Lesson 6: diagnose and extend deliberately

  1. Remove the success record. Expect PARSE_ERROR at finish while the earlier progress remains observable.
  2. Split the UTF-8 input at each byte boundary. The decoded event must stay identical.
  3. Append a record after success. Expect refusal instead of a completed stream.
  4. Return UNAVAILABLE from an observer. Confirm that the delivered event remains counted and later calls retain the failure.
  5. Request cancellation after the terminal record but before finish. The result must be cancelled, not successful.
  6. For a future transport adapter, separately test non-200 status, dropped connections and endpoint changes. The offline parser tests do not establish those behaviors.

If configuration cannot find Framework, select the installed prefix rather than a source folder or one DLL. If SDK identity or toolchain checks fail, correct the package/toolchain pairing. Do not bypass them. A successful configure does not establish compilation, linkage or runtime availability.

The producer registers framework.ai.ollama_pull.event.*, framework.ai.ollama_pull.stream.* and the offline example. Submit actual compiler and SDK identity, commands and pass/fail results. This service adds progress decoding; it does not implement Ollama model execution, model pulling, automatic registration or full feature parity.

Lesson 7: inspect a captured transcript without trusting it

A progress file can be truncated, edited or copied from another machine. Its SHA-256 identifies the observed bytes; it cannot authenticate the server or prove that a model is installed. The shared file service reports those limitations explicitly and omits provider status and error messages from its JSON.

  1. Create a small UTF-8 fixture with two JSON records. Use an absolute filename in a directory you control.
  2. Run the installed SDK example built in lesson 3, with its existing build directory.
  3. Read the exit code and metadata together. Exit 0 means a complete transcript reporting success; exit 3 means a complete transcript reporting a provider error. Exit 2 means incorrect arguments; exit 1 means read, parse or output failure.
$capture = Join-Path $env:TEMP 'umicom-pull-sample.ndjson'
[System.IO.File]::WriteAllText($capture, "{`"status`":`"pulling`",`"total`":8,`"completed`":4}`n{`"status`":`"success`"}`n", [System.Text.UTF8Encoding]::new($false))
& '.\build\bin\umicom-sdk-ollama-pull.exe' models inspect-pull $capture
$LASTEXITCODE

Expected fields include scope: offline-pull-progress-file, two events, the file byte count and its SHA-256, provider_outcome: success, and both verification flags set to false. The example remains useful without arguments: it runs the earlier synthetic stream exercise. The main native CLI accepts umicom models inspect-pull ABSOLUTE_NDJSON; the standalone model tool accepts umicom-models inspect-pull ABSOLUTE_NDJSON. Media's console accepts the same models inspect-pull route.

For an application, include umicom/ai/ollama_pull_file.h and link Umicom::ai. Call UmiOllamaPullFileInspect, then serialize with UmiOllamaPullFileJson. Failed inspection preserves the previous report. A valid provider error is a successfully read observation whose provider_outcome is UMI_OLLAMA_PULL_ERROR. File I/O and protocol failures remain separate status values. Graphical clients should call the blocking file reader on a worker and marshal the copied report to their existing UI owner.

The file must be a regular absolute UTF-8 path, at most 16 MiB. Final symlinks, reparse points, devices and directories are refused; parent aliases may be followed, so choose trusted parents. The same opened handle is checked before and after reading and must close successfully. This is not an immutable filesystem snapshot. Cancellation is cooperative between reads and records. No provider message, model name or filesystem path appears in the serialized report.

  1. Remove the final success record: expect exit 1 and no JSON report.
  2. Replace it with {"error":"example failure"}: expect exit 3, an error outcome and no copied error text.
  3. Append a record after success: expect refusal.
  4. Try a relative path or directory: expect refusal, then retry with the actual absolute regular filename.
  5. Run ctest --test-dir build --output-on-failure after building the installed SDK example. Its sample and file cases are registered separately. A configuration pass alone is not execution evidence.

Test names are contracts too: set_tests_properties must name the test registered by add_test. Producer configuration does not configure every shipped standalone example. Qualify the installed project independently to catch missing helpers, mismatched test names and unavailable runtime dependencies.
