Bound native memory without losing data

A program can ask for more memory than it can use safely. This lesson builds a small C program that puts a limit on its own buffer requests. It refuses a request before making the allocation, keeps the old data, and explains the refusal. The same ownership rules matter when building a text editor, an image pipeline or a local model application.

This allocator limits only buffers explicitly allocated through it. It does not limit the whole process, another library, model weights allocated elsewhere, GPU memory or the operating system. Native code still needs correct ownership and measured results.

1. Prepare one small learning project

If this is your first program, begin with files and folders, PowerShell commands, development tools and your first C program. Next read pointers and allocation. You do not need a model, GPU or network service for this exercise.

An SDK, or software development kit, contains the headers, compiled libraries and build information another program needs to use Framework. A header declares functions; a library supplies their compiled implementation. Use an installed Framework SDK containing umicom/base/budget_allocator.h and the matching base library. A new header beside an older library is insufficient. Follow the installed SDK setup first. The SDK and your program must use compatible compilers, architecture and runtime libraries.

2. Understand the quantities before the code

TermMeaning in this lesson
ByteA unit of memory. These examples use small byte counts so you can calculate every result.
BufferA contiguous region of memory holding data, such as letters or image pixels.
OwnerThe object responsible for tracking a buffer and eventually releasing it.
Live bytesThe sum of requested sizes of buffers that this owner has not released.
Peak bytesThe largest live payload observed by this owner, including both old and replacement buffers during copying.
Byte limitThe maximum live requested payload this owner allows.
Block limitThe maximum number of independently owned live buffers.
MetadataThe allocator's own bounded table of pointers and sizes. Its size is reported separately from payload.
RefusalA failed request with a specific status. It is a normal result that the caller must handle.

Requesting 16 bytes does not imply that the operating system commits exactly 16 bytes. The parent allocator may use bookkeeping and larger regions. Likewise, releasing a buffer need not immediately lower the process's resident memory. Use these counters for the contract they measure, and use process measurements separately.

3. Create an owner and allocate a buffer

The complete example includes umicom/base/budget_allocator.h. Read these lines in its main function:

UmiBudgetAllocator *owner = NULL;
void *buffer = NULL;
void *replacement = NULL;

if (umi_budget_allocator_create(NULL, 32U, 2U, &owner) != UMI_STATUS_OK)
    return 3;
if (umi_budget_allocator_allocate(owner, 16U, &buffer) != UMI_STATUS_OK)
    goto cleanup;
memcpy(buffer, "Umicom", 7U);

NULL means no pointer is stored yet. The first NULL argument chooses Framework's system allocator as the parent. 32U is the byte limit; 2U is the live block limit. The U suffix denotes an unsigned integer constant. &owner passes the address of the pointer variable so a successful call can write its result there.

void * stores an address without specifying the payload's type. Use an actual void * output variable rather than casting the address of a differently typed pointer to void **. The output begins as NULL; allocation leaves it unchanged on failure. memcpy copies seven bytes: six letters and the terminating zero byte of the C string. The remaining nine bytes are not part of that string and must not be read as initialized data.

Each function returns a UmiStatus. UMI_STATUS_OK means this operation succeeded. goto cleanup jumps to the one cleanup section in this function when an operation fails. It does not retry, exit the whole application, or release anything by itself.

4. Calculate the temporary peak

This allocator resizes by allocating a replacement, copying the bytes that fit, then releasing the original. That makes failure ownership explicit. It also means both buffers coexist briefly. The limit applies to that peak, not just the eventual size.

OperationOld payloadNew allocationTemporary totalResult with a 32-byte limit
Allocate the first buffer01616Allowed; live 16, peak 16
Try to grow it to 24162440Refused before parent allocation; live 16, peak 16
Shrink it to 816824Allowed; after copying, live 8, peak 24
Grow the 8-byte buffer to 2482432Allowed; after copying, live 24, peak 32

Even shrinking can be refused when the replacement cannot coexist with the old buffer. A same-size request returns the existing pointer without allocation. A zero-size resize is invalid and never frees the original. These rules are deliberately explicit; do not assume they match every system's realloc behavior.

UmiStatus status = umi_budget_allocator_resize(owner, buffer, 24U, &replacement);
if (status == UMI_STATUS_OK) {
    buffer = replacement;
    replacement = NULL;
}

This fragment shows the ownership pattern, not a complete program. On success, the old pointer and any views into it are invalid. Assign the replacement only after checking success. On refusal, retain the original pointer and data. Do not write buffer = umi_realloc(...) without retaining the old pointer: a failed request could erase your only reference to live memory.

5. Read counters and release ownership

The example copies a snapshot into UmiBudgetAllocatorSnapshot. Changing that copy does not change the allocator. capacity_refusals counts requests rejected by the byte or block limit. allocation_failures counts failed parent allocations after admission. The second case can still happen below the configured limit.

Destroying the owner while a buffer remains live returns UMI_STATUS_BUSY. The owner stays available so the caller can release its buffers. This makes lost ownership visible instead of silently discarding it. The normal cleanup order is:

umi_budget_allocator_release(owner, buffer);
buffer = NULL;
umi_budget_allocator_destroy(&owner);

The complete example checks both statuses. A successful release ends the buffer's lifetime; clearing one pointer does not clear other aliases. Never call free() on a buffer owned here, and never continue using it after release. An interior pointer, such as (unsigned char *)buffer + 1, is not the allocation's starting address and is refused. Exact-address checks cannot detect a stale pointer whose address has later been reused.

For an existing component accepting UmiAllocator, umi_budget_allocator_adapter supplies compatible callbacks. The budget owner must outlive that component and all its buffers. Adapter allocation failure returns NULL; use the explicit status API when the caller needs to distinguish the reason. Serialize all operations on one owner: this service does not provide internal locking.

6. Configure, build and test your copy

Configure asks CMake to locate the compiler and SDK and prepare build instructions. Build compiles and links the program. Test executes the registered checks. One successful stage does not establish success of the next.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S . -B .\build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DUMICOM_EXPECTED_SDK_PREFIX=C:/umicom-sdk -DBUILD_TESTING=ON
cmake --build .\build --target umicom-budgeted-buffer
ctest --test-dir .\build --no-tests=error --output-on-failure -R '^sdk[.]budgeted_buffer([.]refusal)?$'
& .\build\umicom-budgeted-buffer.exe
& .\build\umicom-budgeted-buffer.exe --reject-only

-S . chooses the source directory and -B .\build keeps generated build files separate. -G Ninja chooses the build tool. -D sets a named CMake option. The explicit SDK prefix prevents accidental discovery of a different installation. The example also checks that the selected package belongs inside that prefix.

Expected output from the ordinary run, after the program's internal checks succeed:

Umicom bounded buffer: live=24 peak=32 refusals=1

Expected output with --reject-only:

Umicom bounded buffer: live=16 peak=16 refusals=1

The printed live value is captured before cleanup. Successful completion then releases the buffer and destroys the owner. CTest should select exactly two tests; no matching tests is an error. Record the actual output and exit code, SDK identity and compiler version. Expected text in this guide is not a record of your run.

7. Diagnose a result before changing the code

SymptomNext check
Header or SDK package missingCheck the prefix and installed files. Reinstall the matching SDK; do not mix a copied new header with an older library.
Compiler or Ninja not foundRevisit development-tools setup and inspect the command search path.
Undefined reference at link timeConfirm the base library contains the new allocator and the target links Umicom::base.
Capacity exceededAdd every live buffer and the proposed replacement. Check the block limit too. Do not treat this as an unexpected process crash.
Out of memory below the limitThe parent allocator refused storage. Preserve current data and report failure; do not retry indefinitely.
Busy on destroyFind the still-owned buffers. Release them through the same allocator before destroying it.
Process memory stays high after releaseMeasure allocator retention, other owners and device allocations separately. A requested-byte counter is not resident memory.

8. Practice with a prediction and evidence

  1. Before editing, calculate whether 12 live bytes plus a 20-byte replacement fits a 32-byte limit. Predict both the peak and final live counts.
  2. In a separate copy, change the example and its expected checks to exercise that boundary. Rebuild and record the actual result.
  3. Try a 21-byte replacement. Confirm refusal preserves every initialized byte and does not consume another live block.
  4. Explain why two 8-byte buffers can reach a block limit even when the byte limit still has room.
  5. Read tests/base/test_budget_allocator.c in the Framework source. Its parent allocator deliberately fails a selected allocation. Explain how that differs from relying on a machine to run out of memory.
  6. For a real component, list all allocations that bypass the adapter before claiming its memory is bounded. Measure repeated load, work, cancellation and unload cycles with the same input.
Check the first answer

12 + 20 = 32, so the temporary payload fits. The peak is 32 and the final live payload is 20. Metadata and parent allocator overhead are separate.
