Own a reviewed image request

Framework keeps provider requests independent of the native widget toolkit. The portable Umicom::seedream owner prepares a request, sends it through a trusted transport and returns an owned RGBA image. Media composes the shared GTK page; other hosts can use the same request owner.

Follow the ownership sequence

  1. Zero-initialize UmiSeedreamDraft. Set its model and prompt to terminated UTF-8 strings. Call UmiSeedreamPrepare with a NULL plan pointer. Preparation copies the fields, validates the complete JSON and performs no I/O.
  2. Call UmiSeedreamReview and show the borrowed destination and body to the user, together with the local key alias and possible provider charge. Destroy and rebuild the plan if the user changes any request field or account selection.
  3. After approval, run UmiSeedreamExecuteWithProfile on a worker. Keep the profile store and cancellation token alive for the whole call. The plan is used by one worker at a time; it must not be destroyed concurrently.
  4. Start with a zero-initialized UmiSeedreamResult. Inspect the status and request_may_have_run even after errors. Once transport starts, the plan cannot be reused. A failure is not evidence that the provider performed no work.
  5. On success, the result owns its image. Read dimensions and rows through the image-surface API, or call UmiMediaPngWriteNew on a worker to save a new PNG. Keep the image alive until readers finish.
  6. Call UmiSeedreamResultClear to release the image, and UmiSeedreamDestroy to release the plan. Never overwrite a live result with a structure assignment unless its old image has first been released.

Extend the workflow safely

The native page uses a weak widget reference for worker completion. Workers own their plans, password copies and cancellation tokens. Export temporarily moves the image into the worker and returns it even on failure. A retained child control becomes inert when its panel is destroyed.

Additional frontends can supply UmiSeedreamExecuteWithTransport. Its callback is trusted application code: it must enforce TLS certificate verification, the fixed destination, response bounds, no redirects and no secret logging. Test fixtures replace this boundary without contacting any provider.

Reference images should be added as owned, reviewed captures, with explicit upload approval. Do not add arbitrary download URLs or reread a mutable source file after approval. Additional output modes need their own complete response validation and memory limits before being exposed in the form.

Limits and troubleshooting

The request is text-only, single-image, PNG and non-streaming. It retains watermarking and asks the provider for 2K dimensions. Use a compatible enabled ModelArk model. JSON replies are limited to 32 MiB, decoded PNG files to 16 MiB and decoded image surfaces to the PNG owner's limits. The parser validates the whole JSON, refuses duplicate required fields and checks the PNG framing and integrity before publishing an image.

Missing optional HTTP or PNG support returns unavailable. Authentication errors, unavailable models, rate limits and malformed replies do not expose raw provider error bodies. There is no automatic retry or persistent job history. Cancellation only stops local work; users must reconcile an uncertain request with their provider account.

The protocol fields follow the BytePlus image generation API. Request and response fixtures cover ownership, approval, malformed data and native transport restrictions; those fixtures do not establish account entitlement or live service availability.
