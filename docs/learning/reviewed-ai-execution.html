Keep reviewed AI execution durable

A model can finish answering while the application fails to save the answer. Those are two different outcomes. Framework's reviewed AI workspace records approval before execution, records RUNNING before calling a provider, and stores the final result afterwards. An execution owner now carries that contract through one shared implementation.

1. Prepare and review a fixed request

A job identifies the provider, model, prompt and reviewer. A grounded job also retains its selected source passages. Preparing a job performs no generation. Review is a separate operation; stale evidence or changed provider bindings must not silently reuse an earlier decision.

UmiStatus status = UmiAiWorkspacePrepare(
    workspace, "draft.one", UMI_AI_WORKSPACE_DRAFT,
    "example.local", "selected-model", NULL,
    "Draft a short introduction.", "author", 256);
if (status == UMI_STATUS_OK) {
    status = UmiAiWorkspaceReview(workspace, "draft.one", "reviewer", true);
}

The provider must already be registered and allowed by runtime policy. These local author/reviewer labels are records, not authenticated identities. A real application obtains its review decision from the appropriate user workflow.

2. Retain storage while execution is active

The workspace borrows a Data Server connection and an AI runtime. Both must outlive it. The execution owner retains the workspace until it is released, including the period after a result is settled but its controller still needs to read copied state.

The private owner has three phases: prepared, running and settled. Prepared owns a busy lease but has not written RUNNING or contacted a provider. Running begins only after that record is durably published. Settled means final publication has been attempted and its outcome retained; it does not necessarily mean the answer was saved.

PhaseProvider may have run?Release behavior
PreparedNoAbandoning the owner restores availability without changing the approved job.
RunningYes, or dispatch is about to beginRefuse owner release until the outcome is settled.
SettledThe operation has returnedKeep copied outcome and workspace storage until explicit release.

This is an ownership contract, not a new thread lock. Workspace operations still belong to one serialized owner. Only the cancellation token may be set from another thread.

3. Keep the existing synchronous workflow

status = UmiAiWorkspaceRun(workspace, "draft.one", cancellation);
if (status != UMI_STATUS_OK) {
    /* Inspect the stored job and recovery state before deciding what is safe. */
}

The public Run function now delegates preparation, durable start and final settlement to the shared execution owner. Provider dispatch still uses current runtime policy. Tool dispatch still requires the existing tool permission and workspace allowlist. Result identity, finish reason, token usage and grounded citations still pass through the same response validator.

The request and reviewed job are copied into the execution owner. A provider callback receives the prepared request, not mutable GUI state. A second run of an already successful immutable job returns without invoking the provider again.

4. Handle failures at their actual boundary

  1. Before preparation completes: allocation or admission failure leaves the approved job untouched and calls no provider.
  2. Before RUNNING is published: allocation, current-policy or storage refusal prevents external work. Release the prepared owner; it has not consumed the approved request.
  3. After external work: validate the response and attempt final publication exactly once.
  4. If final publication fails: retain the successful or failed operation status separately from the publication error, require recovery, and refuse another run.
  5. On reload: treat a persisted RUNNING record as interrupted. Do not automatically repeat the provider call.

A failure to save a successful answer does not prove that the provider failed or never ran. Retrying automatically could duplicate a tool side effect. The private execution interface exposes both statuses so a future background controller can report this distinction without creating another persistence implementation.

A cancelled generation has no published successful answer. A cancelled tool operation is marked interrupted because cancellation does not prove that its external effect was undone.

5. Use checked workspace release

status = UmiAiWorkspaceRelease(&workspace);
if (status == UMI_STATUS_BUSY) {
    /* Keep the owner alive until its work and retained controllers are released. */
} else if (status == UMI_STATUS_OK) {
    /* workspace is NULL; borrowed runtime and Data Server still belong to us. */
}

Release refuses busy storage and storage retained by an execution. It leaves the pointer unchanged on refusal. The legacy void Destroy function also refuses active storage, but cannot return the reason. A provider callback that reenters destruction therefore cannot free the workspace beneath the active operation through either supported entry point.

Checking a flag does not make concurrent destruction safe. Serialize access, confirm native worker joining in background hosts, and retain the borrowed runtime and storage connection until workspace release succeeds.

The public raw local-stream job owns copied requests, partial text, cancellation and joining. The reviewed stream controller now composes that owner with workspace approval and durable settlement. It obtains canonical provider configuration, prepares transport without sending a request, publishes RUNNING and then starts network work. GTK application wiring remains a separate integration step.
