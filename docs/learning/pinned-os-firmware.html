Identify firmware in a native OS boot run

The explicit firmware workflow records the exact RISC-V firmware bytes used by a direct-kernel QEMU run. It reuses native image verification, process ownership and ordered boot-report checks.

Prepare the inputs

  1. Build a verified RISC-V bundle with the native image workflow.
  2. Select a compatible OpenSBI binary for QEMU's virt machine. Retain its source, version, licence and build provenance with the reviewed pin. This interface does not approve a firmware release.
  3. Record the lower-case SHA-256 digest and exact nonzero byte count. Select an absolute regular-file path.
  4. Select a native QEMU executable and a new result directory outside the bundle. Its parent must already exist.

Check without execution

umicom-os-image firmware --file /absolute/fw_jump.bin --sha256 REVIEWED_LOWERCASE_SHA256 --bytes EXACT_BYTE_COUNT

Replace the uppercase placeholders. Exit zero confirms byte identity only. This check does not start a guest, prove compatibility or authenticate a publisher.

Run normal and recovery separately

umicom-os-image boot --bundle /absolute/riscv-bundle --qemu /usr/bin/qemu-system-riscv64 --firmware /absolute/fw_jump.bin --sha256 REVIEWED_LOWERCASE_SHA256 --bytes EXACT_BYTE_COUNT --mode normal --result /absolute/results/normal --timeout 90
umicom-os-image boot --bundle /absolute/riscv-bundle --qemu /usr/bin/qemu-system-riscv64 --firmware /absolute/fw_jump.bin --sha256 REVIEWED_LOWERCASE_SHA256 --bytes EXACT_BYTE_COUNT --mode recovery --result /absolute/results/recovery --timeout 90

Stop on failure. Each run captures accepted firmware as firmware.bin in its new result directory and passes that absolute path to QEMU. Existing output directories are refused. Successful transcript assessment is followed by bundle, QEMU and firmware-capture rechecks.

Read all three records

request.umi version 2 identifies source, architecture, mode, QEMU, deadline and firmware. console.log contains bounded process output. result.umi version 2 records completion, launch, exit, timeout, cancellation and the transcript and firmware hashes. Preserve partial output for diagnosis. An output directory by itself does not prove a process launched.

A changed capture fails qualification even when the transcript looks correct. Missing tools are not a pass. Synthetic transport fixtures can emit these markers and must remain labeled as fixtures rather than real guest execution.

Compatibility

The original UmiOsImageBoot and unpinned CLI retain their behavior and version-one evidence. The new UmiOsImageBootWithFirmware API is declared in umicom/os_image/boot_firmware.h. All three CLI pin fields are required together; partial pins cannot silently select default firmware.

The explicit contract currently supports RISC-V direct-kernel runs only. It does not qualify x86 BIOS/UEFI, physical installation, signed boot or a hostile-host sandbox. A digest identifies bytes without certifying them.
