Inspect an OS source profile

An image profile lists source files and pins the Buildroot revision, Linux version and kernel archive digest. Framework can inspect that declaration without preparing output, downloading dependencies or launching build tools.

Read the declaration

  1. Build the native umicom-os-image tool through your configured Framework or Applications build.
  2. Choose the OS checkout whose declaration you want to inspect. The usual file is image/native/profile.umi.
  3. Run the command with an absolute file path:
& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom-os-image.exe" profile --file "C:\umicom\umicomOS\image\native\profile.umi"

Expected output starts with UMICOM_OS_PROFILE_INSPECTION 1, followed by declared pins, the profile-text SHA-256 digest, the file count and each source name. The final operation summary says process-launched=0. Your configured build may place the tool elsewhere; use its actual output path.

Interpret rejection

The parser requires its supported format, canonical lowercase digests, a three-part numeric Linux version, a sorted unique source list, and the profile itself in that list. It rejects unsupported owners, traversal paths, unknown fields, control characters and truncated input. Source names begin with framework/ or umicomOS/. Fix the declaration itself and inspect it again; do not suppress an error by removing the validation.

The file reader requires a bounded regular file at an absolute path and rejects symbolic links or reparse-point paths through the native image I/O adapter. A missing file, rejected path or malformed profile returns a nonzero exit status and does not print an accepted inventory.

Use the same service in an application

Include umicom/os_image/profile.h and link Umicom::os_image. Open a buffer with UmiOsImageProfileOpen, or read a file with UmiOsImageProfileRead. Read a copied summary with UmiOsImageProfileInfoRead and enumerate borrowed names through UmiOsImageProfileFileAt. Destroy the owner when finished. A failed operation leaves the caller's output unchanged.

Understand the evidence boundary

This checks declarations. It does not verify that listed files exist, that a Git checkout matches the pin, that dependencies have an approved licence, or that an image boots. The profile-text digest differs from the frozen input-manifest digest created by preparation: changing source contents can change the latter without changing the former.

Use the normal preparation, build, bundle-verification and guest-boot stages for those additional checks. Keep the resulting evidence with the source identity and tool versions used in that run.
