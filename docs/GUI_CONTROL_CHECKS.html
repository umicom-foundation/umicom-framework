Find and check the controls in an Umicom window

A window may contain a document editor, a Save button, a menu and several panels. Each has a different job. When an operation does not work, a useful first question is: which control received the request?

The control map lists the controls currently built inside an application window. It shows their types, their test identifiers and their current state. You can attach this map to an interaction report so another developer can find the same control without guessing from its position on the screen.

Begin with an Umicom Notes project

Use a practice workspace containing no passwords, customer records or live financial connections. Open one Notes document and make a small change, such as adding a comment that explains what a function returns. Leave a second document open so you can check that an operation affects only the intended one.

Open Report problem from the application's shared titlebar. This opens the recording panel beside the application. Opening this panel does not start recording, save a document or change a project.

1. Make a control map

Choose Inspect controls. The map includes the application window and its related GTK dialogs, but excludes the recorder itself and unrelated application windows. It does not click the listed controls.

When the status says Control map saved, choose Open folder. Each inspection has its own number. Open controls-000001.html in your browser. Beside it, controls-000001.json contains the same map in a format that tools can read. The companion controls-000001-session.json identifies the recording session and retains the observations already collected, if any.

You do not have to start recording to inspect controls. The map is useful on its own, and the recorder remains paused. To collect a sequence of actions as well, choose Start and follow the recording guide.

Opening the reporting window can move keyboard focus away from the application. The map reports the state at inspection time; it does not reconstruct focus from an earlier screenshot.

3. Distinguish a missing ID from a broken feature

An untagged button may still work when clicked. It needs a test identifier so an automated scenario can locate it reliably. Conversely, a perfectly tagged button may be connected to an empty handler. A test identifier tells us where to act, not whether the requested work was completed.

Some controls contain internal widgets. The Notes editor might have an outer component named notes.editor and an unnamed text input inside it. The map records that the input can use its parent's ID. It does not count every internal GTK widget as another missing application feature.

If two controls in the same window have the same ID, the map retains both rows and counts both as ambiguous target records. Correct the identifiers in the source rather than selecting whichever row happens to appear first. Separate windows may use the same IDs; tests must still choose an unambiguous window scope when both are in the driver's search area.

4. Record the problem and the result you expected

Choose Start, return to the Notes editor and repeat the smallest sequence that demonstrates the problem. For example, use Save after changing the first document. Check the saved file as well as its modified marker. The second document must remain unchanged.

Return to Report problem and add a note: “Save returned, but notes.c still contains the old text. The second document was not changed.” State what you actually observed. A repeated ID or missing tag is a testability finding; a file that was not saved is a separate behaviour finding.

Add a screenshot when the visual state matters, with screenshot consent enabled. Then export the interaction report and share the relevant control map, session file and interaction report together. Inspect the files before sharing. Notes, screenshots and explicitly assigned IDs may disclose project information.

5. Turn the finding into a repeatable test

A test needs a starting state, an action and an expected result. For a Notes Save test, the starting state is a known edited document. The action is Save. The result is that the correct file contains the new text and the other draft remains unchanged.

State checks answer smaller questions: has a dialog become visible; is an action enabled; does an input hold the expected text; is the saved-note checkbox selected? These checks help locate the failure, but they do not replace the file or application-model check.

The Framework test driver can assign text through entry and text-editor APIs, activate controls and inspect their state. Operating-system keyboard and pointer tests are also needed for shortcuts, hit testing, focus and window placement. Calling a widget API is not the same as moving a mouse or typing through the desktop.

Private controls and report limits

The map does not collect captions, document contents, typed text or clipboard data. A built-in password field or a component marked private appears as private-control, without its ID or child rows. This cannot discover every kind of sensitive business information automatically.

Each map contains at most 4,096 rows, with a maximum nesting depth of 256. A larger tree is rejected rather than presented as a complete map with its last rows missing. A report panel allows 20 inspection attempts; close it and open a new report panel when another session is needed. Previous exports are not overwritten.

Inspection and export run on the application's GUI thread. They cannot operate while that thread is frozen. In that situation, preserve the existing live log and capture the window with your operating system's screenshot tool. Independent windows, native system dialogs and applications outside the selected window family need their own inspection or an external desktop testing tool.

Troubleshooting

SituationNext step
Report problem is not present.Check that the application uses Framework's shared titlebar and has been rebuilt with the recording support. A different window host must connect the same public recording component.
A menu's controls are absent.Some controls are created only when their menu or panel opens. Inspect the relevant state, or make a test fixture that creates that state before taking the map.
The map contains duplicate IDs.Identify the owning component and give separate controls distinct IDs. Keep IDs stable when changing captions or layout.
Export fails.Check the reported status and available storage. Do not treat a file left by an unsuccessful multi-file export as proof that the whole export completed.
A control is disabled.Check its prerequisites: an open document, a selected project, required permissions or a ready service. Record unexplained disabled states rather than enabling every action blindly.
