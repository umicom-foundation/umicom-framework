Working copies, search and safe document changes

A note-taking application and a source-code editor have much in common. Both display text, keep changes while the user works, save named files and ask before discarding unsaved work. Umicom Framework provides shared services for these tasks so that applications do not need to invent their own file-saving rules.

This guide explains how the editor view and document store work together. It includes two complete programs: a small search preview and an in-memory Notes editor that works with source text beyond the first 64 KiB.

Understand the three versions of a document

The file on disk is the saved version. The document store holds an in-memory record with a stable document ID, path, text and revision. The editor view holds the text currently displayed by the simple editor adapter, along with its caret, selection and modified marker.

These are not three independent owners that may overwrite each other freely. UmiDocumentCoordinator connects the store and view. It synchronises edits, maintains document-level history, checks external file changes and performs saves through the existing document provider.

The distinction matters while a person is typing. A visible draft can differ from the store before the next synchronisation. Code deciding whether it is safe to close a document must inspect the coordinator's working-copy snapshot, not just the store's saved state.

A snapshot is a description of current state. Reading one does not save or commit the draft. Its text length and dirty state include the visible draft, while its revision identifies the store record. A client must not interpret that revision alone as a fingerprint of every unsynchronised keystroke.

Follow one editing operation

Suppose a developer opens notes.c, changes noteCount to savedCount, then saves.

  1. The coordinator opens a document and returns its view ID. Opening the same normalised path again selects the existing working copy rather than creating another record.
  2. The editor publishes the accepted draft through the view model. A modified working-copy snapshot can now warn about unsaved work even before synchronisation.
  3. A replacement operation prepares its complete result before updating the store. The previous text is retained for Undo.
  4. Save synchronises the working copy and checks the destination. If another process changed the file, the caller receives a conflict rather than silently overwriting it.
  5. After a successful write, the stored and displayed state describe the saved version.

Applications should call these services rather than writing the file directly behind the coordinator. Otherwise, the baseline used for external-change detection can become inconsistent with the file.

Keep identity separate from selection

The active tab is a selection, not a permanent identity. It can change while a file dialog, confirmation or background action is pending.

Capture a UmiDocumentId when an action begins. Use UmiDocumentCoordinatorSaveAs to save that document to a selected path, or UmiDocumentCoordinatorClose to close it after an explicit discard decision. A document that has already closed returns UMI_STATUS_NOT_FOUND. It must not be replaced by whichever tab is now active.

Use the existing active-document convenience functions for operations that genuinely mean “the active document now”. Captured asynchronous requests need the targeted functions instead. The coordinator is used on its owner's thread; worker threads should deliver results back to that thread rather than modifying its tables concurrently.

Search without saving

UmiDocumentCoordinatorFindNext searches the visible draft. Pass zero for the backwards argument to find the next occurrence, or a nonzero value to find the previous occurrence. Both directions wrap once. The operation changes caret and selection, but not document history or the file on disk.

The original umi_document_coordinator_find function remains available with its first-occurrence behaviour. Existing callers do not need to change simply because a graphical editor now provides next/previous navigation.

For a tool that works directly with a text buffer, use UmiEditorSearchNavigate. Its offsets and lengths are byte offsets, not displayed character positions. The GTK adapter is responsible for converting between these byte positions and the positions used by its text widget.

The shared literal search supports case-sensitive, ASCII-insensitive and smart ASCII-case modes. Smart case becomes case-sensitive when the search text contains an uppercase ASCII letter. Whole-word matching treats letters, digits, underscore and non-ASCII bytes as word bytes. It is useful for straightforward source-text searches, but it is not a parser or a full Unicode word-segmentation service.

Replace only after checking the complete result

UmiDocumentCoordinatorReplaceNext replaces a matching selection, or the next occurrence when no matching selection exists. Its caret advances past the replacement, so repeatedly replacing note with NOTE does not stay on the same occurrence.

UmiDocumentCoordinatorReplaceAll changes every original, non-overlapping match in one document-level operation. The new text is not searched again during that operation. Replacing a with aa, for example, finishes after considering the original text; it does not keep expanding its own output.

An empty replacement string deletes a match. A null replacement pointer is rejected by the coordinator. Read-only views reject editing. An oversized result is rejected before changing the draft, store or replacement history.

Undo and Redo use the coordinator's existing bounded history. Replace All adds one replacement step. If the user had typed a pending draft beforehand, synchronising that draft is a separate earlier history step. This is document-level history, not a claim that every toolkit's keystroke-level Undo stack has been unified.

Build a search preview with Framework

The complete example is in framework/examples/editor_workflow. It previews a rename in source text without writing a file. That makes it useful for understanding search and replacement before adding a Save command to an application.

The program borrows its input strings. It writes the result into a separate array that it owns. The array's capacity includes room for a final zero byte, which marks the end of a C string.

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/editor_workflow/main.c
 * PURPOSE: Preview a literal rename in a small Umicom Notes source document.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/
#include "umicom/editor/search_engine.h"
#include <stdio.h>
#include <string.h>

/* All input is borrowed; replacement is written into separate caller storage.
 * This example previews text only. It does not modify a file on disk. */
int main(void)
{
    const char *source = "int noteCount = 3;\nint total = noteCount;\n";
    const char *needle = "noteCount";
    const char *replacement = "savedCount";
    UmiEditorSearchOptions options = {UMI_EDITOR_SEARCH_CASE_SENSITIVE, 1, 0, 0U};
    UmiEditorSearchMatch match;
    char preview[256];
    size_t replacements = 0U;
    UmiStatus status = UmiEditorSearchNavigate(source, strlen(source),
        needle, strlen(needle), &options, 0U, 0, 0, &match, NULL);
    if (status != UMI_STATUS_OK) {
        fputs("The requested name was not found.\n", stderr);
        return 1;
    }
    printf("First name begins at byte %zu.\n", match.offset);
    status = UmiEditorSearchReplaceAll(source, strlen(source), needle,
        strlen(needle), replacement, strlen(replacement), &options,
        preview, sizeof preview, &replacements);
    if (status != UMI_STATUS_OK) {
        fputs("The complete preview could not be prepared.\n", stderr);
        return 1;
    }
    printf("Replaced %zu occurrences. Preview:\n%s", replacements, preview);
    /* A deterministic check also makes the example suitable for CTest. */
    return replacements == 2U && strcmp(preview,
        "int savedCount = 3;\nint total = savedCount;\n") == 0 ? 0 : 1;
}

The first function locates an occurrence. The second prepares the replacement preview. Both return a UmiStatus; a non-success result is handled before the program uses their outputs.

The example deliberately uses whole-word, case-sensitive matching. The maximum_matches field limits collected result lists in the older list API. It does not limit navigation or Replace All, so a document with more than 4,096 occurrences can still be searched and fully processed.

The program checks its expected result before returning zero. This gives CTest a useful success or failure signal without relying on an assert that a Release build may remove.

Configure and run the example on Windows

First build and install the updated Framework SDK using the Applications build guide. In this example it has been installed at C:\umicom\installed\studio-source-files. Use your actual installation directory if it is different.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S ".\framework\examples\editor_workflow" -B ".\build\notes-search" -G Ninja -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_MAKE_PROGRAM="C:/msys64/ucrt64/bin/ninja.exe" -DCMAKE_PREFIX_PATH="C:/umicom/installed/studio-source-files"
cmake --build ".\build\notes-search" --parallel 2
ctest --test-dir ".\build\notes-search" --no-tests=error --output-on-failure
& ".\build\notes-search\umicom-notes-search.exe"

Run one command at a time. If configuration cannot find UmicomFramework, check the installation prefix and confirm that it contains the exported CMake package. Pointing at the source directory is not the same as providing an installed SDK.

Try a controlled failure

Change char preview[256] to char preview[8] in your practice copy and rebuild. The new text will not fit. The program should report that it could not prepare the complete preview and return a failure status. Restore the original capacity afterwards.

Now change the replacement string to numberOfSavedNotes. Predict how many replacements there will be and whether the complete result still fits. Update the deterministic expected string and rerun the test. This connects a capacity rule to a real editing operation rather than treating bounds checking as an unrelated exercise.

Do not pass overlapping input and output storage to UmiEditorSearchReplaceAll. It needs an unchanged original input for both passes. The public header documents this ownership requirement.

Work with complete source documents

As a project grows, a source file may contain hundreds or thousands of lines. Its tab still needs only a title, a path and a few display settings. Copying the entire file whenever the tab changes would mix two different jobs.

UmiUiDocumentViewSnapshot therefore keeps its small source_text field as a preview. The view model owns the complete draft separately when it no longer fits that field. A preview is useful for inspection; it is not the content to save, search or compile.

TaskFramework operation
Read the complete byte count and text revisionUmiUiDocumentViewModelTextInfo
Take an independent copy of the draftUmiUiDocumentViewModelCopyText
Release that copyUmiUiDocumentViewModelFreeText
Publish a complete edited draftUmiUiDocumentViewModelUpsertText
Save, search or undo a document operationThe existing UmiDocumentCoordinator functions

The full-text setter borrows your input for the duration of the call and copies accepted bytes into the model. You can then release your input. The full-text getter gives you a separate allocation; do not keep a pointer into private model storage. This ownership rule allows the model to resize its draft without invalidating a caller's copy.

Use the metadata getter and ordinary upsert when only the caret, title or another tab property changes. For a large document, the ordinary upsert rejects an edited preview instead of interpreting that shortened text as a complete replacement. To intentionally replace the whole document, including making it empty, use the full-text setter.

Read the length before choosing a representation

This fragment assumes views is the document view model and viewId identifies an open tab. It reports the full size without making another complete text copy:

UmiUiDocumentTextInfo info;
UmiStatus status = UmiUiDocumentViewModelTextInfo(views, viewId, &info);
if (status == UMI_STATUS_OK) {
    printf("Complete draft: %zu bytes\n", info.byte_count);
}

By contrast, strlen(view.source_text) measures only the snapshot's preview. It must not be used as the full length of a larger document. preview_complete says whether that preview happens to contain all of the text.

Try the complete Notes document example

The second program in examples/editor_workflow creates an unsaved Notes source document, finds a name after the first 64 KiB, replaces both occurrences and uses Undo to restore the original text. Blank lines represent the earlier part of the source file, making it easy to see whether the operation reaches the end. It does not write files or execute the source being edited.

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/editor_workflow/complete_document.c
 *
 * PURPOSE:
 *   Edit an in-memory Notes source document beyond its metadata preview.
 *
 * AUTHOR AND ORGANISATION:
 * Sammy Hegab
 * Umicom Foundation
 *
 * LICENCE:
 * MIT
 *---------------------------------------------------------------------------*/
#include "umicom/document/document.h"
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* This programme changes an unsaved document only. It never overwrites files. */
int main(void)
{
    UmiCommandRegistry *commands = NULL;
    UmiUiWorkbench *workbench = NULL;
    UmiDocumentStore *store = NULL;
    UmiDocumentCoordinator *documents = NULL;
    UmiUiDocumentViewSnapshot view = {0};
    char viewId[UMI_UI_ID_CAPACITY];
    char *source = NULL;
    char *restored = NULL;
    size_t restoredLength = 0U;
    size_t foundAt = 0U;
    int result = 1;
    const size_t prefixLength = 65536U;
    const char *body = "int noteCount = 3;\nint total = noteCount;\n";
    const size_t sourceLength = prefixLength + strlen(body);

    /* Give each service an explicit owner. Cleanup below reverses this order. */
    if (umi_command_registry_create(&commands) != UMI_STATUS_OK ||
        umi_ui_workbench_create("umicom.notes.editor", commands, &workbench) != UMI_STATUS_OK ||
        umi_document_store_create(&store) != UMI_STATUS_OK ||
        umi_document_coordinator_create(store, workbench, NULL, &documents) != UMI_STATUS_OK ||
        umi_document_coordinator_new(documents, "notes.c", viewId, sizeof viewId) != UMI_STATUS_OK)
        goto cleanup;

    /* Blank lines stand in for the earlier part of a larger source file.
     * The names we will edit are deliberately after the first 64 KiB. */
    source = malloc(sourceLength + 1U);
    if (source == NULL) goto cleanup;
    memset(source, ' ', prefixLength);
    for (size_t index = 63U; index < prefixLength; index += 64U) source[index] = '\n';
    memcpy(source + prefixLength, body, strlen(body) + 1U);

    UmiUiDocumentViewModel *views = umi_ui_workbench_documents(workbench);
    if (umi_ui_document_view_model_find(views, viewId, &view) != UMI_STATUS_OK) goto cleanup;
    view.dirty = 1;
    if (UmiUiDocumentViewModelUpsertText(views, &view, source, sourceLength) != UMI_STATUS_OK)
        goto cleanup;

    /* Metadata tells us whether its small text preview is complete. */
    UmiUiDocumentTextInfo info;
    if (UmiUiDocumentViewModelTextInfo(views, viewId, &info) != UMI_STATUS_OK) goto cleanup;
    printf("Notes source: %zu bytes. Full text fits the preview: %s.\n",
        info.byte_count, info.preview_complete ? "yes" : "no");

    if (umi_document_coordinator_find(documents, "noteCount", &foundAt) != UMI_STATUS_OK)
        goto cleanup;
    printf("Found noteCount at byte %zu.\n", foundAt);
    size_t replacements = 0U;
    if (UmiDocumentCoordinatorReplaceAll(documents, "noteCount", "savedCount", &replacements) != UMI_STATUS_OK ||
        replacements != 2U || umi_document_coordinator_undo(documents) != UMI_STATUS_OK)
        goto cleanup;

    /* CopyText returns our own allocation, which stays valid independently
     * of the model. Always release it with the matching Framework function. */
    if (UmiUiDocumentViewModelCopyText(views, viewId, &restored, &restoredLength) != UMI_STATUS_OK)
        goto cleanup;
    if (foundAt != prefixLength + 4U || restoredLength != sourceLength ||
        memcmp(restored, source, sourceLength) != 0) goto cleanup;
    puts("Replaced two names, then restored the complete source with Undo.");
    result = 0;

cleanup:
    if (result != 0) fputs("The Notes editing example could not complete.\n", stderr);
    UmiUiDocumentViewModelFreeText(restored);
    free(source);
    umi_document_coordinator_destroy(documents);
    umi_document_store_destroy(store);
    umi_ui_workbench_destroy(workbench);
    umi_command_registry_destroy(commands);
    return result;
}

Follow the services from top to bottom. The command registry and workbench provide the presentation model. The store owns the document record. The coordinator connects them. The cleanup label releases each resource in reverse ownership order, including when an earlier operation fails.

The program's own source allocation and the model's draft are different allocations. After replacement, restored is a third, independent copy used to check Undo. Matching each allocation with the correct release operation is an important part of memory management in C.

Build the examples with the Windows or Linux commands earlier in this guide. Then run the second executable:

& ".\build\notes-search\umicom-notes-document.exe"
./build/notes-search/umicom-notes-document

It should report that the full text does not fit the preview, find noteCount at byte 65540, and confirm that Undo restored the complete source. The example links Umicom::document, so it uses the same coordinator as an application rather than a second editing implementation.

Understand the memory limits

The supported complete draft is at most 8 MiB (8,388,608 bytes) of UTF-8 text. The view model permits at most 64 MiB of dynamically allocated draft capacity across its tabs; small inline previews, temporary copies, the document store and native widgets use additional memory. Closing a tab releases its draft allocation. These are deliberately bounded in-memory documents, not a virtualised editor for files of arbitrary size.

Each coordinator Undo or Redo stack retains at most 32 entries and 16 MiB of stored text, including terminating zero bytes. When a successful edit needs room, the oldest entries are released. An unsuccessful edit does not evict history. The working-copy snapshot reports the number of steps still available. Native keystroke history and coordinator history remain separate mechanisms.

The coordinator also limits raw input files to 8 MiB and checks the decoded size. UTF-16 input can become larger when decoded to UTF-8. An oversized file is rejected, not shortened. A provider that supports file information is asked for its size before the whole-file read; the returned bytes are checked again afterwards because a file may have changed. This check is not a streaming-read guarantee for a provider without size information.

The view model protects individual publications and copies with its mutex. The coordinator still belongs to one owner thread. A worker may return data for that owner to apply; it must not race a Save, Undo or document-close operation.

Extend the exercise

Change the name to archivedCount, adjust the expected result, and rerun CTest. Next, make the draft shorter with the full-text setter and undo that edit. Finally, publish a change at the end while leaving the initial preview unchanged. The text revision and the complete content should change together.

Check before closing a window

umi_studio_close_guard_evaluate checks documents and the existing Test, Debug and AI activity snapshots. A host with an additional background operation can use UmiStudioCloseGuardEvaluateWithActivity. A running build is then included in the decision without being misreported as a running test or changing existing public structure layouts.

A failed state query is not evidence that there is no unsaved work. The graphical host should leave the window open, explain the problem and let the user return to their work. Only an explicit, successful close decision should proceed.
