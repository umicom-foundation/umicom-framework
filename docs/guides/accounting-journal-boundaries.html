Checked journal arithmetic

The finance component stores journal amounts as signed 64-bit integer minor units. A journal line contains one positive debit or credit. It has no currency field, so the surrounding accounting service must establish account currency and scale before combining lines. Equality of integer totals is not proof that currencies, periods or permissions match.

1. Construct complete values

  1. Include umicom/finance/accounting/journal_entry.h and link to Umicom::finance.
  2. Create the entry with umi_accounting_journal_entry_init, supplying an ID and a valid Gregorian date. The new entry is a draft.
  3. Create each line with umi_accounting_journal_line_init, supplying a line ID, account ID and nonnegative debit and credit amounts. Exactly one side must be positive.
  4. Call umi_accounting_journal_entry_add_line and check its result. The maximum is 32 lines. Invalid input, an overflowing total or a non-draft entry leaves the entry unchanged.

Initialization stages a complete value before replacing the destination. Invalid identifiers, dates or amounts preserve the existing destination. Callers must serialize access and respect the ownership requirements documented in the public headers.

2. Inspect totals with a status result

Use umi_accounting_journal_entry_totals(entry, &debit, &credit). Both outputs must be distinct and outside the entry. On failure, neither output changes. The function validates the public line count before traversal and checks each addition before performing it. A malformed structure returns UMI_STATUS_INVALID_ARGUMENT; an unrepresentable total returns UMI_STATUS_CAPACITY_EXCEEDED.

The older scalar debit and credit accessors remain available. They return zero for invalid or overflowing input, which cannot distinguish refusal from an empty total. Use the checked operation for financial decisions. umi_accounting_journal_entry_balanced also uses checked totals and returns false for invalid, overflowing or empty entries.

3. Generate from an accounting event

umi_accounting_posting_engine_generate builds the whole journal before publishing it. Malformed event or rule fields, inactive rules, mismatched event types and invalid journal IDs leave the output unchanged. Refused requests increment the rejection counter once when both counters have room; exhausted counters refuse without changing state.

The minimum signed integer has no representable positive signed magnitude. The checked event-magnitude API and posting engine refuse it instead of silently saturating. The legacy scalar event-magnitude function keeps its compatibility saturation and must not drive new posting logic. Negative events retain the existing absolute-magnitude mapping; the caller must choose appropriate reversal rules and accounts.

4. Store an accepted journal locally

umi_accounting_journal_book_post copies a balanced journal into a bounded in-memory book and marks the copy posted. It rejects duplicate journal IDs and invalid existing book state. The maximum is 64 entries. umi_accounting_journal_book_validate checks the count, every stored entry and duplicate IDs before later operations rely on the book.

This book does not authorize an operator, validate account currencies, close a financial period or persist a ledger transaction. Compose those controls explicitly through the relevant Framework services before using the local journal result.

5. Review accounts, periods and the current book together

The local journal posting review captures the candidate, chart, calendar and book before a user decision. It checks account eligibility, inclusive period boundaries, exact totals and duplicate journal IDs. Apply refuses changes to active captured fields and succeeds at most once. These checks remain local and require the surrounding owner to establish currency, authorization and durable posting policy.

Recover from a refusal

  1. Keep the previous entry, book and output values. A failed request is not a partial success.
  2. Inspect the returned status and the original fields. Do not clamp an amount or replace it with zero.
  3. Correct the input under an explicit accounting rule, then prepare a new request.
  4. If a restored record is invalid, retain it for diagnosis outside the active book.

For double-valued local practice and CSV capture, see Reviewing a local accounting batch. That compatibility workflow is separate from these integer journal contracts.
