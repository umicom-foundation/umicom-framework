Search saved form answers

The shared native form editor provides two searches. Find records looks at record metadata such as its key and revision reason. Search saved answers also verifies each selected record and compares its stored answers with your conditions.

Find and open an answer match

  1. Open or create an explicitly selected local database. Use an application whose record editor supplies a form schema and a record namespace.
  2. Expand Saved answer conditions. Choose Add condition, select a field and comparison, then enter a value. The unit beside the input comes from the schema. Add more conditions when every one must match.
  3. Optionally enter metadata text in the record search box. That text narrows which records are examined before answer comparisons.
  4. Choose Search saved answers. Wait until the operation completes. The list contains matches for the editor's active form version, in record-key order.
  5. Select a result explicitly and choose Open selected listed record. The editor checks that its stored revision still matches the result. Opening also requires a clean draft; save or explicitly discard your changes first.
  6. Choose Next answer matches to continue the same search. If the conditions or database changed, start a new search instead.

What happens to current edits?

Search does not save, discard or replace the current form. It searches saved answers, so a value you have typed but not saved will not affect matches. Incomplete condition text stays in its field and blocks a search until corrected. Changing a condition while a search or selected-record read is running makes that result obsolete; the editor refuses to replace your view with it.

For application developers

Link to Umicom::form_record_editor_gtk4. Existing editor composition automatically includes the query controls. Use UmiFormRecordEditorGtk4SetFilter to replace conditions explicitly and UmiFormRecordEditorGtk4FindTyped to search with metadata text and a first-page or next-page flag. The latter returns asynchronous acceptance; wait for Busy to become false, then inspect LastStatus.

Register historical schemas with SetHistoryCatalogue before connecting if the namespace contains older form versions. The service checks those records with their original schema but excludes them from current-version answer matches. Unknown versions or malformed selected records fail the search instead of producing an incomplete success. Applications own access control and the lifetime of immutable schemas while workers are active.

Troubleshooting and limits

A stale-result refusal means the filter, metadata text, selected revision or namespace heads changed. Start a first-page search again. Do not retry a next page from a metadata-only search as an answer-search continuation. The two modes have different result identities.

Search is bounded to 256 namespace heads, 32,768 storage rows per catalogue scan and 16 results per page. It may inspect several records on a worker and is not an indexed large-database search. Ordinary metadata discovery remains available for schemas that cannot expose answer filters. See native typed filters and typed record search for value, unit and consistency rules.
