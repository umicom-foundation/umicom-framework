Recover a build that keeps re-running CMake

This guide uses Windows PowerShell, MSYS2 UCRT64, CMake and Ninja. CMake prepares a build plan. Ninja executes it. CTest runs registered tests. These commands keep the existing Umicom Applications build directory and its compiled files.

1. Recognise the symptom

One Re-running CMake after a source or configuration change is normal. A loop shows repeated Configuring done, Generating done and Build files have been written, immediately followed by another configuration. A changing step counter, such as [1/4] becoming [1/6], does not prove that C files are being compiled.

Studio's generated wiki manifest was rewritten on every configuration. Framework watches that manifest for genuine updates. Writing identical bytes changed its modification time and could keep Ninja regenerating. The correction compares contents before writing and retains all existing checksum checks.

2. Stop the loop and integrate the complete correction

  1. Press Ctrl+C once in the terminal running the loop. Wait for the PowerShell prompt.
  2. Keep the build folder. Do not delete CMakeCache.txt, edit build.ninja manually or disable regeneration.
  3. Integrate framework/cmake/UmicomLearningModuleBundle.cmake, applications/studio/cmake/UmicomStudioLearningModules.cmake and the accompanying applications/studio/tests/cmake/learning_regeneration directory. The caller and shared helper must be updated together.
  4. Finish copying or merging before restarting. Do not run two configure/build operations against the same build directory.

3. Configure the existing build directory

The first command selects the project. The second places UCRT64 tools on this terminal's search path. Run each block in order and stop on errors.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --preset windows-ucrt64-all-debug
if ($LASTEXITCODE -ne 0) { throw "Configuration failed. Read the first CMake error." }

Expected result: configuration and generation finish once. A large project can take minutes. A successful configuration is not a successful compilation or test run.

4. Check whether the build plan is stable

& "C:\msys64\ucrt64\bin\ninja.exe" -C ".\build\windows-ucrt64-all-debug" -d explain build.ninja
if ($LASTEXITCODE -ne 0) { throw "Build-plan check failed." }

-C selects the folder. -d explain prints why a target is considered out of date. This command executes the build-plan check and may rerun CMake to write generated build files. Selecting build.ninja requests the plan rather than compiling applications. Do not add -n for this check: a dry run can report a pending glob check and simulated regeneration without executing the check that would establish whether anything really changed.

With unchanged inputs, expect a prompt return with no Re-running CMake. Ninja may print ninja: no work to do. or just its normal glob checks. One regeneration can be legitimate if a source changed after configuration. If complete cycles repeat, cancel and preserve the explanation output. Look for a named input newer than an output, a missing file, or a changed glob. A glob is a filename pattern such as *.h; checking one is not itself an error.

5. Run the focused regression, then resume compilation

ctest --test-dir ".\build\windows-ucrt64-all-debug" -R "^studio[.]cmake[.]learning_regeneration$" --output-on-failure --no-tests=error
if ($LASTEXITCODE -ne 0) { throw "Learning regeneration regression failed." }
cmake --build --preset windows-ucrt64-all-debug --parallel 2
if ($LASTEXITCODE -ne 0) { throw "Build failed. Do not install stale artifacts." }

The regression configures a small fixture, checks stable timestamps, edits a lesson, checks the new manifest and stages its files. It does not compile the full IDE. The final command resumes the incremental application build. Two parallel jobs limit simultaneous compiler processes; they do not guarantee a particular memory requirement.

After the build succeeds, run normal qualification:

ctest --preset windows-ucrt64-all-debug --output-on-failure
if ($LASTEXITCODE -ne 0) { throw "Tests failed. Review the report before installation." }

Read failures, skips and not-run cases separately. Install or launch only after the checks required for the product have passed.

6. Treat the GTK warning separately

GTK provides native windows and text controls. An input method handles composed text and language switching. The Win32 defect leaves a callback registered after its input context is destroyed; later input can access an object whose lifetime ended.

The correction is GTK commit 30727f8a524dbaa69118a60d6bbef4b3447245b1. A package must include that change or a reviewed equivalent. A patch beside a recipe has no effect unless the recipe lists it, verifies its checksum and applies it before compilation. GTK 4.24.1 alone does not establish the repair.

The advisory does not cause the regeneration loop or stop configuration. Do not suppress it to claim the runtime is repaired. Follow Checking the GTK runtime on Windows for package verification, staging and native lifetime tests. Close applications and finish or stop other builds before replacing GTK.

7. Report the right evidence

ObservationEvidence and next investigation
Repeated CMake cyclesFull -d explain output, source revisions and the named input's timestamp and content hash.
GTK advisoryPackage version, reviewed recipe/patch, built package digest, staged DLL identity and native tests.
LLDB 0xc0000135The debugger probe log. A Windows loader dependency may be missing; investigate separately.
Compiler/linker errorThe first actual error and target, rather than an earlier optional-tool warning.
No matching testCheck that all regression files were integrated and CMake completed. --no-tests=error prevents an empty selection being mistaken for success.

Include the command, exit code, complete log and source revisions. State whether files were changing during the run. Keep credentials and private project content out of shared reports.
