Keep and recover a record draft

A draft is text you are still editing. A record revision is text committed to the database. A recovery copy keeps the draft and the exact earlier revision you reviewed, so you can resume editing later without pretending that the draft has been committed.

Use the native editor

  1. Open the same local record database you used for the note. Open a record or create a new draft, then type your changes.
  2. Expand Keep or recover unsaved work. Enter an absolute filename in an existing directory you control, for example C:/umicom/_local/recovery/review-note-1.umird. Use a different filename for each copy.
  3. Choose Keep draft copy. Wait for the completion message. You can continue typing while the captured copy is written; that later typing is not included in the earlier capture.
  4. The editor still shows unsaved changes. Keeping a copy does not save a record revision. To close, save the record normally or explicitly discard the local edits after checking that the copy completed.
  5. To recover, open the appropriate database and save or discard any currently dirty draft. Enter the recovery file's absolute path and choose Recover draft copy.
  6. Review the recovered text, supply the reviewer and reason for the next revision, then choose Save revision. If someone has saved a newer revision, compare it before explicitly adopting its baseline.

Recovery copies contain plaintext, including the earlier baseline. Keep them in private storage. They are bounded to the record editor's 16,384-byte content limit and are not encrypted. Healthcare exercise notes must remain fictional. There is no automatic timer, remote upload or automatic deletion of old copies.

Use the shared C23 API

Include umicom/data/record_draft_snapshot.h and link Umicom::data for capture, validation, encoding and restoration. For filesystem operations, include umicom/data/record_draft_files.h and link Umicom::record_recovery. This separate library reuses the platform file services without adding filesystem dependencies to every data consumer.

  1. Allocate a UmiRecordDraftSnapshot on the heap and call umi_record_draft_snapshot_capture on the draft's owning thread. A pending database save returns BUSY; finish that save before capturing.
  2. Pass the copied snapshot to a worker. Call umi_record_draft_snapshot_write_new with an absolute path. No live editor object is needed by this worker.
  3. Read a selected copy with umi_record_draft_snapshot_read(directory, relative_path, output). The directory must be explicit and absolute. Rooted-file checks refuse traversal and links beneath the selected root.
  4. Before restoring against a database, call umi_record_draft_snapshot_check_store. It compares the complete historical baseline, including its canonical metadata and content. It allows a later stored head because the next save checks the head again.
  5. On the draft's owning thread, call umi_record_draft_snapshot_restore. It refuses to replace dirty text or a pending request. Native hosts must also reject replies for closed windows or text changed since the read began.

Portable snapshots support arbitrary bytes. The GTK editor accepts UTF-8 text without embedded NUL and checks the application's record namespace. The codec verifies an explicit version, exact lengths, canonical metadata and a SHA-256 digest before publishing output. These checks detect accidental damage; they do not authenticate authors or protect a file from someone who can replace its contents and digest.

Try the installed example

Use the installed examples/data_history project and its existing SDK configuration. Build the umicom-record-draft-recovery-example target and run its executable. It captures, encodes, decodes and restores a new draft in memory. The expected message is Recovered 24 unsaved bytes; no record was committed.

Understand a refusal

  • File already exists: choose a new filename. Recovery never overwrites the previous copy.
  • Invalid or partial file: retain it for diagnosis and choose a complete copy. The current draft remains unchanged.
  • Different or missing baseline: select the original database. Recovery does not silently import another database's revision history.
  • Current draft has changes: save or explicitly discard them before restoring. A recovery read cannot take their place.
  • Stored revision changed: the recovered text remains available. Compare the latest stored text and make an explicit reconciliation decision.
  • Write failure: keep the editor open. A partial new file may remain, so retry under a new name after resolving storage access or space.

An accepted file write continues if the widget retires. Hosts must keep its owning main context and process alive until UmiRecordEditorGtk4Busy becomes false. Forced termination cannot guarantee completion. Recovery does not restore cursor position, reviewer form fields, an in-flight save or a whole database backup.
