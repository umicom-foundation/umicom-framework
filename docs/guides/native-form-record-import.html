Import a form record in a native application

The shared GTK4 importer reads a history file, displays the complete typed history and restores it only after explicit confirmation and host authorization. Link Umicom::form_record_import_gtk4 and include umicom/ui/gtk4/form_record_import.h.

Use the widget

  1. Choose the history bundle with Browse, or type its absolute path.
  2. Choose an existing SQLite database with Browse, or type an absolute path for a new database in a directory you control. Choose the destination before reviewing; changing either path invalidates the review.
  3. Press Review history file. File reading, integrity checks and schema decoding run on a worker. A failed or outdated result does not become an importable review.
  4. Inspect the revision pages and select the confirmation box only for the record you intend to import.
  5. Press Import confirmed history. The host must authorize that exact destination and record. The worker restores all revisions in one transaction and refuses existing records.

Integrate with a host

Provide a trusted immutable schema catalogue, the expected form identifier, a record namespace ending in a dot and a required authorize_restore callback. The callback runs on the GTK thread and returns a Framework status. It must apply your access policy; returning OK unconditionally is appropriate only in an explicitly unrestricted local demonstration. A pure optional key check runs on a worker.

Keep borrowed schemas and callback contexts alive until the widget and all accepted work are finished. StateRead returns the captured operation path, status, reviewed identity and committed revision. The operation-finished signal reports completion with two integer arguments: operation and status. Admission returning OK is not completion.

Closing and retrying

CanClose remains false while work is admitted. Retirement discards pending read results but cannot undo an accepted write. Keep the main loop alive until the completion arrives, then release borrowed data. Later path edits never redirect an admitted write; its result identifies the original captured database.

A collision retains existing rows. A storage error requires inspecting the database and recovery state before retrying. Creating a new destination can leave an empty SQLite file after failure; the importer does not delete it. Paths must be local absolute filenames in locations the host trusts. Filename validation alone is not a confinement boundary for parent directory links.

Limits

Imports are bounded to one complete entity history. This does not provide authentication, encryption, a whole-database backup or schema migration. An optional separate local receipt is described below; plain imports do not create one. Original labels are not authenticated people. Application authorization and clinical or financial decisions remain separate.

Keep an atomic import receipt

A host can set the optional receipt_source label to require a separate receipt. Fill the unique receipt ID, operator label and reason before reviewing the file. Changing them invalidates the review. The visible Restore action captures UTC time and imports history and receipt in one transaction. The original author labels stay unchanged.

Programmatic hosts can use UmiFormRecordImportGtk4RestoreWithReceipt with their own complete request. Inputs are copied before authorization; changing the caller object later cannot change the admitted receipt. A configured source must match. On completion, has_receipt and receipt identify the committed provenance. Read or verify it with the portable receipt service. Without a configured source or explicit request, the original plain-import route remains available.

Inspect the last completed receipt

A receipted import shows its copied receipt below the history preview. The import operator and original author appear separately with UTC timestamps and the reviewed checksum. The heading identifies the last completed import; changing inputs or starting another operation does not turn that historical receipt into a receipt for the new operation. A display error does not change a successful database result. Hosts can inspect receipt_display_status independently from status.
