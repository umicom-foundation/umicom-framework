Review workbench values before applying edits

A panel may show one selection while a worker or another panel produces a newer one. Copying an older edited value back without checking its revision can overwrite the newer selection. The Framework's reviewed replacement functions make that decision explicit for selection-provider, selection, context-source and context-event records that contain inline text and scalar fields.

Prepare and apply a draft

  1. Read the live value and its revision while holding the owner's normal access boundary. A revision is a counter identifying a published value; it is not a timestamp.
  2. Copy the value into a separate draft. Change its fields using the existing domain setters and present the result for review.
  3. Call the type's replace_if_current function with the live value, the originally observed revision and the draft.
  4. If the live revision has changed, stop and show the newer value. Do not retry automatically with a newly read token: that would turn a rejected stale review into an unreviewed overwrite.
uint64_t observed = selection.revision;
UmiWorkbenchSelectionAccountItem draft = selection;
UmiStatus status =
    umi_workbench_selection_account_item_set_label(&draft, "Selected account");
if (status == UMI_STATUS_OK) {
    status = umi_workbench_selection_account_item_replace_if_current(
        &selection, observed, &draft);
}
/* Handle INVALID_STATE by reviewing the current selection again. */

The example requires an already initialized, valid UmiWorkbenchSelectionAccountItem and serialized owner access. Use umicom/workbench_selection/account_item.h for its declarations. The replacement validates both values, requires the same record identity and publishes all fields with exactly one new live revision. A draft's own revision does not determine the live token.

Understand refusal and ownership

INVALID_STATE means the observation is stale. CAPACITY_EXCEEDED means the revision counter cannot advance. Invalid identities or fields are refused through the existing domain validator. Every refusal leaves the live record unchanged. Self-replacement is permitted and advances once; partially overlapping records are not supported.

Text setters now preserve accepted text and its revision when input is null, too large or the counter is exhausted. A setter can accept a suffix of its own field as input. A successful setter still advances once when the text is identical. The existing void touch functions preserve sequence, timestamp and revision at exhaustion; they cannot return an error. Use reviewed replacement when the caller needs a status.

These are value operations. They do not emit a context event, update a registry, activate a provider, perform a trade, or authorize an action. Continue using the owning service's publication API for those operations. They do not supply locks, cross-thread synchronization, storage transactions or durable recovery.

Keep constructors for new records. Reinitializing an actively observed record resets its revision and would invalidate the meaning of outstanding tokens. Resource-owning structures need their own lifetime rules and are not candidates for a plain struct-copy replacement.

Extend a record safely

  1. Add validation for every new field, including termination checks for fixed text arrays.
  2. Update the portable archive reader, writer and schema when the saved representation changes.
  3. Extend the fixture's field-by-field equality function. Successful replacement must copy the complete semantic value without relying on struct padding.
  4. Exercise stale reviews, invalid drafts, self-replacement, aliasing, capacity refusal and the final usable revision. Existing constructors, setters and public interfaces remain available.
