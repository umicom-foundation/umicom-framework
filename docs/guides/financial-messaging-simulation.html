Try financial messaging without moving money

Umicom Framework provides a native C23 foundation for logical financial messages. Bank, Accountant, TMS and Trader can run the same synthetic example. It shows why receiving a message, accepting a payment, settling between institutions and crediting a beneficiary are different events.

This is a development foundation. It does not connect to banks, authenticate institutions, sign or transmit UFMP messages, execute payments or establish legal settlement finality. The logical message catalogue and local storage format are not a published interoperable wire protocol.

1. Build and run the console example

Use a Windows UCRT64 development environment with the configured Umicom Applications checkout. The commands below are qualification steps for your checkout; availability in source does not establish that your build has passed them. Stop at the first failed command.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --preset windows-ucrt64-all-debug -DBUILD_TESTING=ON
cmake --build --preset windows-ucrt64-all-debug --parallel 2 --target umicom-bank-console umicom-accountant-console umicom-tms-console umicom-trader-console
& ".\build\windows-ucrt64-all-debug\bin\umicom-bank-console.exe" --ufmp-simulate
& ".\build\windows-ucrt64-all-debug\bin\umicom-accountant-console.exe" --ufmp-simulate
& ".\build\windows-ucrt64-all-debug\bin\umicom-tms-console.exe" --ufmp-simulate
& ".\build\windows-ucrt64-all-debug\bin\umicom-trader-console.exe" --ufmp-simulate

The expected report has five delivery attempts, one accepted logical operation, four identical retries and a refused changed payload. Receipt alone leaves settlement pending. Beneficiary credit can precede interbank settlement; completion requires both observations. These counts describe synthetic in-memory comparisons, not a production exactly-once execution guarantee.

2. Understand the reusable services

ServiceWhat it doesWhat the caller must still provide
Envelope validationChecks bounded identifiers, known types, schema token, payload size, revision and time limits. Verifies the SHA-256 digest of exact body bytes.Identity, authorisation, payload schema validation and signature verification.
Replay comparisonDistinguishes the same delivery, a fresh delivery of the same operation and conflicting reuse of an ID or key.Atomic persistence and recovery of effects and results.
Payment progressProjects trusted delivery, acceptance, settlement and credit evidence independently. Checks issuer role, payment identity and expected revision.Verified evidence, institution policy and durable event storage. An issuer string is not authentication.
Local inbox journalCommits an exact envelope/body with message and operation indexes in one Data Server transaction. Returns the same receipt on retry and reloads records after reopening SQLite.Authenticated admission, appropriate SQLite durability and backup policy, processing workers, an outbox and atomic business-effect handling.

Operation keys are scoped by exact sender ID, across recipients. Reusing a key for a different recipient, type, schema or payload is refused. Retry with a new message ID while retaining the same operation key and business content. Delivery timestamps and tracing fields can change for that retry. Expired incoming envelopes are refused; historical records remain readable.

Preview a scoped clearing position

Each financial console also accepts --clearing-preview. The shared Framework example produces a gross pay of 12,500 GBP minor units, gross receive of 4,000 and net receive of -8,500. It refuses duplicate obligation IDs, mixed currencies/scales, mismatched counterparties, settlement accounts, schemes or value dates, and overflowing gross totals. Amounts are integers throughout. The result is an analytical preview; it grants no netting or settlement authority.

& ".\build\windows-ucrt64-all-debug\bin\umicom-tms-console.exe" --clearing-preview

3. Link an SDK consumer

Use Umicom::finance for pure message validation and progress. Link Umicom::financial_inbox when the consumer needs Data Server persistence. This second library depends on finance and Data Server; the low-level finance library does not acquire database dependencies.

find_package(UmicomFramework CONFIG REQUIRED)
add_executable(financial-inbox-example inbox.c)
target_compile_features(financial-inbox-example PRIVATE c_std_23)
target_link_libraries(financial-inbox-example PRIVATE Umicom::financial_inbox)

The examples/financial_messaging directory contains a complete installed-SDK consumer. Build it against your SDK installation, then supply a new disposable SQLite path:

cmake -S ".\framework\examples\financial_messaging" -B ".\build\financial-messaging-example" -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_PREFIX_PATH=C:/umicom/installed/applications
cmake --build ".\build\financial-messaging-example" --parallel 2
& ".\build\financial-messaging-example\financial-inbox-example.exe" "C:\umicom\_local\ufmp-example.sqlite3"

Run it twice. The first run should record one synthetic message. The second should return the same receipt with no second operation record. The example uses fixed synthetic times and fixture bytes; it is not a network listener. Keep the example database outside public repositories.

4. Journal ownership and limits

  1. Authenticate the sender and validate signatures, permission and the payload schema before journal admission. A body digest alone cannot establish identity.
  2. Call UmiUfmpInboxReceive outside any existing Data Server transaction. The service owns begin, commit and rollback and leaves the caller's output unchanged on error.
  3. Only a successful return establishes a committed local receipt. Read the returned backend: a memory Data Server loses all records on shutdown.
  4. Use UmiUfmpInboxLoad to retrieve the original envelope and exact body by receipt ID. Records have a 1,024-byte payload limit in this bounded foundation.
  5. Reserve keys beginning ufmp.inbox.v1/ for this service. Do not delete replay records when a message expires or edit these keys through a second writer.
  6. Implement business processing separately. A receipt is not a payment acceptance, ledger posting or settlement instruction. Exactly-once financial effects require their own transactional effect/result design.

The journal writes explicit fields rather than C structure bytes, so compiler padding and native integer layout are not persisted. Its local text representation is not CBOR and must not be used as COSE signing input. Database digests detect accidental corruption; a malicious writer able to replace both content and digests is outside this check.

5. Run focused checks

cmake --build --preset windows-ucrt64-all-debug --parallel 2 --target umicom-ufmp-envelope-test umicom-ufmp-replay-test umicom-ufmp-progress-test umicom-ufmp-catalogue-test umicom-ufmp-simulation-test umicom-ufmp-inbox-store-test umicom-ufmp-inbox-codec-test umicom-ufmp-inbox-sqlite-test umicom-ufmp-clearing-test umicom-ufmp-legacy_netting-test umicom-ufmp-binding_vector-test
ctest --preset windows-ucrt64-all-debug -R "^framework\.ufmp\." --output-on-failure --no-tests=error

The SQLite test target is registered only when Data Server has SQLite enabled. Its absence means restart and multiple-connection coverage is unavailable; it is not a pass. Tests use synthetic participants and disposable build-directory databases. Configure first so newly added test targets are visible.

Troubleshooting

  • Unknown target or symbol: check that the application uses the updated Framework checkout or SDK, then configure again. A thin host built against an older SDK reports that UFMP simulation is unavailable.
  • ALREADY_EXISTS: an existing message ID or operation key was reused for different content. Inspect the original record; do not bypass the guard by silently inventing a new payment identity.
  • BUSY: another transaction owns the Data Server or SQLite writer. Finish your own transaction or retry later; do not roll back another owner's work.
  • PARSE_ERROR: the payload digest or stored record/index is inconsistent. Preserve the database for investigation. Do not overwrite evidence to force admission.
  • TIMEOUT: the incoming envelope expired. A new delivery can retain its operation identity with fresh timestamps.
  • CAPACITY_EXCEEDED: the caller's policy or the 1,024-byte inbox bound was exceeded. Larger payload support requires a storage design change.
