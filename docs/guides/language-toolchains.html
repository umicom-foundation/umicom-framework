Choose and qualify language toolchains

Native game, media and web services · Check an SDK environment · Repeated CMake configuration

A toolchain is the set of programs that turns source files into a running program: compiler, assembler, linker, libraries and sometimes a virtual machine. Studio coordinates these tools. Installing an editor, or recognising a filename, does not install the compiler or its libraries.

Current scope. Framework provides language records and installed-tool inspection for the selection below. D and FreeBASIC have CMake console starters; Umicom C has a bounded preview starter. The other rows describe prerequisites and the current project route. They are a practical selection of twenty languages, not a performance or popularity ranking. Language-specific debugger sessions and compilers must be qualified on the target machine. Studio does not silently download or install them.

1. Understand the steps

Write source→ Configure tools→ Build artifacts→ Test results→ Run applicationDebug: inspect a paused program

Configure checks paths and prepares build rules. Compile translates a source language. Link combines compiled objects and libraries. Run executes a program; test compares its behaviour with an expected result. A debugger lets you stop at a source line, inspect variables and advance through execution. Successful configuration alone does not prove any of the later steps.

2. Choose the language and its complete tools

All rows use open-source language implementations. Obtain tools from the named project's official distribution and follow its platform instructions. Record the release, architecture, licence and installation directory. Standard libraries are not interchangeable between compilers merely because the source language is the same.

3. Make one toolchain discoverable

  1. Choose the architecture of your development computer and intended executable, for example x86-64 Windows. Choose a complete distribution for that platform.
  2. Install or unpack it according to its official instructions. Keep dependencies separate from project source. Preserve the licence notices if you redistribute tools.
  3. Open a new PowerShell window. Use the following pattern, replacing the example compiler folder with the real folder containing your compiler. This changes only this terminal and its future child processes.
$env:Path = "C:\Tools\ldc\bin;C:\msys64\ucrt64\bin;$env:Path"
Get-Command cmake, ninja, ldc2
ldc2 --version
cmake --version
ninja --version

Expected result: each command resolves to the intended installation. If Get-Command fails, stop and correct the folder. If --version fails with a missing DLL, the installation or its runtime search path is incomplete. A file existing on disk is not sufficient. Restart Studio from this terminal so it inherits this environment; a previously running Studio process keeps its earlier environment.

In Project Settings, use Inspect tools to review resolved and missing files. Optional language tools may be missing without preventing a C project. This inspection does not execute or validate every discovered tool. On Windows, Kotlin and TypeScript often provide script launchers; a process API that only launches executable images cannot run those scripts directly. Use a reviewed build recipe or an explicitly configured command interpreter for them, keeping arguments separated and avoiding string-built commands from untrusted input.

4. Build the D console starter

  1. In Studio choose New Project, then D Console Application. Use a new empty project directory and a simple target name such as d_notes.
  2. Review the generated source, CMake files and README. Apply Project Settings with your chosen paths. Trust the project only after reviewing its build scripts.
  3. Choose Configure. It must find ldc2; the recipe does not substitute DMD or GDC because their options differ.
  4. Choose Build, Test and Run in that order. The starter should print Result: 42. The CTest case checks that exact output and a zero exit code.
  5. If a control produces no feedback, inspect Output and the actual application version. Use the equivalent terminal commands below to separate a compiler problem from a Studio interaction problem.
Set-Location "C:\Dev\d_notes"
cmake --preset windows-ucrt64-debug
cmake --build --preset windows-ucrt64-debug --parallel 2
ctest --preset windows-ucrt64-debug --output-on-failure --no-tests=error
& ".\build\windows-ucrt64-debug\bin\d_notes.exe"

Run commands separately and stop on a failure. The source contains unittest { assert(add(19, 23) == 42); }; -unittest enables that check. Change an operand in the printed expression and observe a failing output test. Restore it and rerun the same checks. This teaches the difference between a test detecting a defect and a process merely finishing.

5. Build the FreeBASIC starter

Choose FreeBASIC Console Application, name the target basic_notes and use another empty directory. Check Get-Command fbc and fbc -version. Use the same three CMake/CTest commands in that directory, then run its bin/basic_notes.exe. The expected output is again Result: 42.

The generated Function AddNumbers(... As Integer) As Integer declares the inputs and result as integers. Return sends a value back to its caller. Print writes text. End 1 signals failure if the internal check fails. The -g -exx flags request debug information and runtime checks supported by FreeBASIC. They do not make all pointer operations safe.

If the compiler lives outside PATH, configure with -DUMICOM_D_COMPILER="C:/real/path/ldc2.exe" or -DUMICOM_BASIC_COMPILER="C:/real/path/fbc.exe" as appropriate. The complete compiler distribution must still be usable. On Linux use linux-debug instead of windows-ucrt64-debug and run the executable without .exe.

Build and test a Pascal console project

  1. Install a complete Free Pascal distribution for your operating system. In PowerShell, check Get-Command fpc and fpc -iV.
  2. In Studio choose New Project and Pascal Console Application. For a terminal workflow, use umicom project templates to find developer.template.pascal-console and follow the project plan and creation steps.
  3. Open the generated folder, review src/main.pas and the CMake files, then configure, build and test with Studio or run the commands below. The executable is in the build directory's bin folder and should print Result: 42.
umicom configure --preset windows-ucrt64-debug
umicom build --preset windows-ucrt64-debug --jobs 2
umicom test --preset windows-ucrt64-debug

Use linux-debug on Linux. If discovery fails, run CMake directly with -DUMICOM_PASCAL_COMPILER="C:/path/to/fpc.exe". If the compiler starts but reports missing units, check its installation and runtime search paths. Keep compiler output in the build tree.

The generated README gives the Runtime staging command, which copies the built executable to a folder you select. A staged host program still needs deployment and debugger checks on the intended platform. Free Pascal compiler options.

Build and test a Java console project

  1. Select Java Console Application when creating a project in Studio or choose developer.template.java-console in Umicom Command.
  2. Set JAVA_HOME to your JDK folder. The Development Kit supplies both the compiler and the Java runtime. Run the commands below from the generated folder. Use the linux-debug preset on Linux.
umicom make --source . --preset windows-ucrt64-debug
umicom build --source . --preset windows-ucrt64-debug --target run-program

The configure step selects javac, jar and java. The build writes the selected application's JAR under build/windows-ucrt64-debug/bin. A JAR is an archive with compiled Java classes and entry-point metadata. The test launches the actual archive and checks the printed application name. If tool selection is wrong, correct JAVA_HOME and configure a fresh build directory.

To inspect source locally, run jdb -classpath followed by the archive path and Main. Enter stop in Main.main, then run. Expect a stop inside src/Main.java. A JVM runs the archive and provides the debug session. The Runtime install component stages the archive for a compatible JVM.

6. Use Umicom C in Studio and PowerShell

The Umicom C preview is a bounded virtual machine: a program executes using Umicom instructions and explicit limits. Its starter is a small arithmetic example, not a full C23 compiler. Language tags and interoperability plans do not mean arbitrary Java, BASIC or D source can already be mixed and executed in one file.

  1. Build or obtain the matching Umicom C command-line tool. Confirm Get-Command umicom-c finds the desired executable.
  2. Create the Umicom C preview project in Studio. Its preset is preview, and its build directory is build/preview.
  3. Configure, Build and Test. Run routes through the configured CMake preview target, using the selected compiler and Studio's existing output runner.
  4. For terminal debugging, enter the commands below from the generated project folder. VM debugging is separate from Studio's native debugger.
cmake --preset preview
cmake --build build/preview --target preview
ctest --test-dir build/preview --output-on-failure --no-tests=error
umicom-c debug src/main.uc --max-steps 256

The generated example should report a result of 42. Keep the source unchanged for the first run; its README lists the available preview tasks. The step budget bounds execution, not the memory requirements of unrelated native tools. Review each command's help before extending the program.

7. Share Umicom Framework through a C interface

An ABI is the binary agreement between compiled modules: calling convention, symbol names, type sizes and memory ownership. Use an installed Framework SDK of matching architecture and runtime. D uses extern(C) declarations; FreeBASIC can declare functions in an Extern "C" block. A declaration alone does not provide the library implementation.

  1. Start with a narrow C wrapper around the actual SDK header, using fixed-width values and explicit buffer sizes.
  2. Compile the C wrapper with the SDK's supported C toolchain. Link its import/static library from the other language.
  3. Match all argument sizes and calling conventions. Avoid passing C++ classes, garbage-collected references or language strings through an undocumented C boundary.
  4. Let the allocator that creates an object release it through its documented function. Do not mix free, a D garbage collector and BASIC runtime ownership.
  5. Test success, invalid input, short buffers and repeated create/destroy cycles before adding UI or network work.

The D and BASIC console starters intentionally require only their standard runtimes; they do not already link every Framework library. See the SDK environment guide for installed-package discovery and the native service lesson for a complete C consumer.

8. Separate hosted OS and bare-metal Kernel targets

TargetWhat is required
Windows or Linux terminalCompiler/runtime built for that host, matching libraries and executable format.
Umicom desktop shell running on an existing OSThe host OS still supplies process, filesystem and runtime services. A desktop shell is not a new machine ABI.
A future Umicom OS distributionQualify its actual loader, libc/runtime, system calls, libraries, toolchain and debugger. A Linux build is compatible only if those contracts really match.
Umicom Kernel, bare metalFreestanding compiler target, linker script, startup code, supported hardware, memory model and Kernel APIs. Hosted D/BASIC/Java/.NET programs cannot be assumed to work.

A VM interpreter could be ported into a Kernel service, but it needs explicit allocation, I/O, scheduling and isolation contracts plus execution tests. The hosted Umicom C preview does not establish that port. Likewise, C server-rendered websites can avoid WebAssembly for their server logic; browser-native execution requires a separately implemented and qualified target.

9. Diagnose a failed first run

Read the first native debugger stop from Umicom Command

  1. Compile a local C or C++ console project in Debug mode, with source symbols enabled. Keep the source and executable from that build together.
  2. With a DAP-capable GDB on PATH, run the command below from the generated project. Replace the executable name and preset directory with the output of your build. To select a particular GDB, add --adapter followed by its executable path. To use an installed LLDB DAP adapter, specify --kind lldb.
umicom debug --program "build/windows-ucrt64-debug/bin/c_notes.exe" --timeout-ms 8000

Expect a JSON record with event set to stopped, the first frame name and its source location when the debugger supplies one. The command then terminates the debug session. It applies the timeout separately to launch, observation and termination. If launch fails, check the selected executable, adapter and its runtime dependencies. If the reported frame has no source location, check that the executable includes symbols. Use Studio for an interactive session.

  • Compiler not found: inspect the first configure error, PATH and explicit compiler setting. Do not keep pressing Run.
  • Linker error: inspect architecture and runtime libraries; installing one executable is insufficient.
  • No tests found: enable testing and configure the intended directory. Do not treat an empty test run as a pass.
  • Executable missing: fix the build first; confirm the configured target and output folder.
  • Debugger cannot start: check the debugger's own dependencies and executable format before examining project source.
  • Studio has old templates: rebuild and integrate the matching Framework and Studio package. New source in a comparison folder does not update an installed application.
