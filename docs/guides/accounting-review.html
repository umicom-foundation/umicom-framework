Reviewing a local accounting batch

An accounting batch groups debit and credit lines for review. The compatibility UmiOpenTmsAccountingBook stores up to 256 lines in memory. Framework checks each currency separately and can capture an immutable review before changing the batch's local approval or posting flags. No function in this interface sends a payment, connects to a bank, writes a journal to disk or authenticates an approver.

1. Create a valid batch

  1. Allocate a book and initialise it with umi_open_tms_accounting_book_init. Keep one owner responsible for access; concurrent writes are not supported.
  2. Fill each UmiOpenTmsAccountingLine with an account ID, reference, currency and either a debit or credit. Call umi_open_tms_accounting_book_add and check its result before updating the display.
  3. Use exactly three uppercase ASCII currency letters. This checks syntax only; it does not consult a currency registry. IDs and references must fit their arrays, end in a zero byte, contain a non-space character and have no control bytes.
  4. Amounts must be finite and nonnegative, with exactly one positive side. A successful addition revokes earlier approval. A locally posted book refuses additions.

The compatibility model uses double and an absolute balance tolerance of 0.000001 for each currency. It is suitable for a local preview, not exact-money posting. Converting a preview into the separate accounting ledger needs explicit currency, rounding, account, permission and idempotency policies. Do not silently cast these amounts to integer minor units.

2. Show the actual review

  1. Call umi_open_tms_accounting_review_create with UMI_OPEN_TMS_ACCOUNTING_APPROVE. Creation validates every active line, checks currency balances and copies the complete batch without changing it.
  2. Read metadata using umi_open_tms_accounting_review_read. Show the source revision, action, line count and proposed flags.
  3. Read each line using umi_open_tms_accounting_review_line. Display these owned copies, rather than rereading a live book that may have changed.
  4. After the user's decision and your application's current permission checks, call umi_open_tms_accounting_review_apply. Success advances the revision once. A changed revision, flag, line count, order, account, reference, currency or amount refuses the old review without changing the book.
  5. Destroy the review when finished. Prepare a separate UMI_OPEN_TMS_ACCOUNTING_POST review for an already approved batch if the workflow needs its local posted flag. That flag is only in-memory workflow state.

The review owns its copy and can outlive the source object. Reusing a successfully applied review fails. On stale-state refusal, show the current batch and request a new decision; never retry by replacing the stored revision. Padding and unused array tails are not user data and do not invalidate a semantically identical batch.

Use the TMS practice window

In Umicom TMS, choose Accounting batch practice. Enter a line and select Add line to local batch. For a balanced example, add GBP 100 debit to a practice cash account, then GBP 100 credit to a practice receivable account. Enter 0 on the unused side.

Select Approve local batch, then Prepare complete batch review. Inspect every displayed line and the proposed state. Tick the acknowledgement and select Apply reviewed local action. Setting the local posted flag requires a second, separate review. Editing any entry or changing the action revokes the prepared review. Adding a line after approval also revokes that approval. Decimal inputs use a full stop with no grouping, exponent or whitespace. Each new window has an empty batch; closing discards unsaved edits.

Older SDKs show that the optional surface is unavailable. The acknowledgement is not an authenticated second approver. For the original in-memory workflow, closing without an explicit save discards the batch; the file workflow below adds controlled persistence.

Save a capture or review an imported batch

  1. Enter an absolute archive path in a directory you control, then select Save captured batch to new file. The file must not already exist. The worker saves the batch as it was when requested; later edits are not included. Wait for the result before closing if you need to see the save receipt. An accepted write may finish after the window closes.
  2. To import, enter an existing archive path and select Open archive for review. Read both CURRENT and LOADED sections, including every line, currency and local approval/posting flag. Nothing in the live batch changes during this preview. An invalid file leaves it untouched.
  3. Tick I reviewed the current and loaded batches and choose Replace with reviewed local batch. Changing an entry or action revokes this review. Open again after any such edit; older action reviews are also invalidated.

Existing files are never overwritten. A failed write can leave a partial new file for inspection; choose another path for a retry. Archives are neither encrypted nor authenticated, and imported flags do not authorise a payment, journal entry or separate approval.

3. Keep currencies separate

umi_open_tms_accounting_book_currency_totals returns one currency's debit and credit totals. An unknown currency returns UMI_STATUS_NOT_FOUND. Overflow refuses the calculation and leaves both outputs unchanged. The older aggregate umi_open_tms_accounting_book_totals accepts only empty or single-currency books; a mixed-currency book returns UMI_STATUS_INVALID_STATE. GBP 100 debit and USD 100 credit do not balance each other.

Save and restore portable batch values

Include umicom/open_tms/accounting_archive.h and link to Umicom::finance. This interface encodes values into caller-owned memory; it does not open files. The separate Umicom::treasury_files component exposes umi_open_tms_accounting_book_save_new and umi_open_tms_accounting_book_load for blocking file work on a worker. The native window composes these services asynchronously.

  1. Call umi_open_tms_accounting_book_archive_encode(book, NULL, 0, &size) to measure the required storage, allocate it, then encode and check the result. A short output buffer remains untouched and reports the required size.
  2. On import, enforce umi_open_tms_accounting_book_archive_limit() before allocating input storage. Decode into a separate draft. Small-stack callers should use umi_open_tms_accounting_book_archive_decode_with_workspace with two distinct heap-allocated books: one scratch value and one output. Neither may overlap the input.
  3. Show every draft line, currency, revision and imported lifecycle flag. An unfinished draft may be unbalanced. An archive claiming approved or posted state must balance per currency. Bad envelopes, fields or flags leave the destination unchanged.
  4. Capture a separate expected copy of the current local book before review. After the user's decision, call umi_open_tms_accounting_book_archive_decode_if_unchanged on the owning thread. A changed active line, revision or flag refuses replacement. Destroy any earlier action review and create a new one for the restored batch.

The archive contains only active fields, not structure padding or unused text tails. Its checksum detects accidental corruption; it supplies neither authentication nor encryption. Imported approvals are historical local values and never establish the identity or permission of an approver. Restoring an older revision is allowed; applications requiring monotonic history must impose that policy before replacing local state.

4. Try the installed SDK example

Install a Framework SDK containing the finance component first. From the Framework source directory, substitute your installed prefix in this example. Stop if any command fails; a successful configuration alone does not establish SDK usability.

cmake -S examples/accounting_review -B build/accounting-review -G Ninja -DUMICOM_SDK_PREFIX=C:/umicom/installed/framework
cmake --build build/accounting-review
ctest --test-dir build/accounting-review --output-on-failure --no-tests=error

The scenarios exercise normal local application, stale-review refusal, separate GBP/USD totals, archive round trips and stale replacement refusal. Each should return success after checking its expected outcome. The example links only to exported Framework targets and rejects a package found outside the requested installed prefix.

Export a captured spreadsheet report

  1. In the accounting practice window, select Open captured CSV report. The new window captures the current batch and shows its revision. Later edits in the practice window do not change this report. Open another report to capture newer values.
  2. Review the CSV rows. The batch row records local flags, line rows retain entry order, and currency-total rows are sorted by currency. A blank amount means it does not apply to that row. There is no total combining GBP, USD or other currencies.
  3. Expand Save displayed text, choose a new absolute filename ending in .csv, then save. Existing files are kept. An accepted write may finish after the report closes; wait for the result if you need to inspect its receipt.

The export uses a full stop as the decimal separator and quotes every field. Formula-like account and reference text receives a leading apostrophe. Spreadsheet import settings can still affect display, so import identifiers as text. These double-valued amounts are local practice data, not an exact ledger. The CSV is for inspection, not restoration; use the archive workflow to reopen the original values.

Applications without GTK can include umicom/open_tms/accounting_report.h and call umi_open_tms_accounting_book_report. On success it returns an owned UmiCsvDocument; release it with UmiCsvDocumentDestroy. On failure the output pointer is null and the source book is unchanged. Draft imbalance can be reported, but a claimed approval that does not balance is rejected. Invalid UTF-8 or an overflowing total also rejects the complete report.

Try file persistence with an installed SDK

The accounting_files example requires the optional treasury_files component. It links only to the installed package you select. Create a private output directory first and substitute a new archive filename on each round-trip run. Stop on any failed command.

cmake -S examples/accounting_files -B build/accounting-files -G Ninja -DUMICOM_SDK_PREFIX=C:/umicom/installed/framework
cmake --build build/accounting-files
New-Item -ItemType Directory -Force C:\umicom\_local\examples
& .\build\accounting-files\accounting-files.exe roundtrip C:/umicom/_local/examples/accounting-example.umiv
& .\build\accounting-files\accounting-files.exe inspect C:/umicom/_local/examples/accounting-example.umiv

A successful round trip saves a synthetic balanced GBP batch, reloads it, compares all serialized values and prints its CSV report. inspect reads the existing archive without writing it. An existing destination is a refusal, not a request to replace it. This example does not register an automatic file-writing CTest: the archive destination is always an explicit user choice.

Troubleshooting

ResultWhat to inspect
Invalid argumentCheck bounded text, currency syntax, non-finite amounts and whether both sides or neither side are positive.
Invalid stateCheck each currency balance, lifecycle flags and whether the batch changed after preview creation. Make a fresh review after an edit.
Capacity exceededCheck the 256-line limit, an overflowing total or an exhausted revision. Do not wrap revisions or truncate lines.
Already existsThe batch is already approved; approval is not a way to create another revision.
Package configuration missingInstall the finance component and confirm the prefix contains the Framework package and its exported libraries.

Native hosts must additionally validate text encoding before displaying portable byte strings. Public book fields are caller-owned and can be overwritten; they are not tamper-proof approval evidence. Retain a separate authenticated ledger workflow for real posting.
