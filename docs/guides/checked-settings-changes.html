Apply related settings together

A settings form often edits several values that belong together. Framework can validate them all and compare them with the values the user reviewed before publishing any change.

  1. Include umicom/platform/settings_changes.h and link Umicom::platform.
  2. Pass distinct keys to UmiSettingsReadValues. The returned values come from one locked read. Keep these copied values with the form.
  3. Create one UmiSettingChange per key, with its reviewed value and proposed value.
  4. Call UmiSettingsApplyChanges. All candidates must satisfy the existing schema. An outdated expected value returns UMI_STATUS_INVALID_STATE; nothing is changed.
  5. On success, refresh the relevant presentation. Saving settings to disk is a separate action.
const char *keys[] = {"editor.width", "editor.spaces"};
UmiSettingValue reviewed[2];
UmiStatus status = UmiSettingsReadValues(settings, keys, 2, reviewed);
if (status == UMI_STATUS_OK) {
    const UmiSettingChange changes[] = {
        {keys[0], reviewed[0].text, "2"},
        {keys[1], reviewed[1].text, "true"}
    };
    status = UmiSettingsApplyChanges(settings, changes, 2);
}

The example assumes both keys exist in your schema. Expected and proposed values are normalized by that schema, so boolean synonyms compare consistently. Comparison concerns current values, not their history: a value changed away and back matches its original review.

Use between one and 256 distinct keys. Unknown keys, invalid values, duplicates or allocation failure leave the settings unchanged. Failed reads leave output untouched. Callers own stable, non-overlapping input and output storage. Destruction must not race an operation.

Native indentation controls

UmiGtk4IndentationPreferencesCreate returns an ordinary floating GTK box with a width entry and spaces checkbox. Parent it normally, then read the draft with UmiGtk4IndentationPreferencesRead. These controls do not retain an application or save files. Run them on the GTK owner thread.
