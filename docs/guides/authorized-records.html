Authorize record operations with identity and purpose

The authorized-record service checks who is using a record, which operation they need, and why they need it. It combines Framework's identity registry, session registry, policy engine and atomic record storage. An identity is a registered person or service. A session is a private handle issued by a trusted host after authentication. A policy is a set of explicit allow and deny rules.

Set up a trusted host

  1. Include umicom/data/authorized_records.h and link Umicom::authorized_records. Keep the identity, session and policy services alive until the authority is destroyed. Keep the Data Server and authority alive until the record adapter is destroyed.
  2. Authenticate the user through your application's trusted login system. Register an enabled identity and issue its session. The session registry itself does not check passwords or perform external login. Never accept a caller-supplied actor label as proof of identity.
  3. Create an authority with a fixed source label and an entity prefix ending in a dot, such as example.. The prefix bounds the records this authority can address. Identifiers and purpose names use ASCII letters, digits, dots, underscores and hyphens. A bare prefix is not a record.
  4. Add a policy for the operation and a policy for its purpose. These are separate checks. A read rule alone does not permit a read. For example:
UmiPolicyRule read = {
    "example.editor", "record.read", "example.note", UMI_POLICY_ALLOW
};
UmiPolicyRule purpose = {
    "example.editor", "record.purpose",
    "purpose/review/record/example.note", UMI_POLICY_ALLOW
};

The existing policy engine uses the last matching rule. Keep rule ordering explicit. Missing rules deny access. Operation capabilities are record.read, record.history, record.create and record.amend. Purpose rules use purpose/<purpose>/record/<entity>.

Read and save

  1. Build a request containing the private session handle, record identifier, declared purpose, operation and trusted current clock value. The host supplies time; a remote client must not choose a time that extends its session.
  2. Use umi_authorized_record_latest for the current document. Use umi_authorized_record_load with a nonzero revision and READ_HISTORY permission for an older version. Use umi_authorized_record_open_reviewed to require that the current head still matches a previously reviewed metadata snapshot.
  3. Create a record with CREATE and expected revision zero. Amend with AMEND and the last reviewed revision. The service derives actor from the current identity, source from the authority, and recorded time from the trusted request. Supply the reason, optional observation time and document bytes.
  4. Inspect the returned status before using any output. On denial or storage failure the output remains unchanged. Successful results contain a copied access receipt. It describes the completed check; it is not a permission token and must not authorize a later operation.

Run the fictional example

From a configured Framework build with testing enabled:

cmake --build build --target umicom-authorized-record-example-test
ctest --test-dir build -R "^framework\.authorized_records\." --output-on-failure --no-tests=error

The example stores and reads a fictional note. Memory backend cases are always registered when the target is available. SQLite cases are registered when SQLite is found. The service does not require a graphical display.

Handle refusal without losing work

PERMISSION_DENIED means the current session, identity, scope, operation or purpose is not allowed. Preserve the user's unsaved draft and ask the trusted host to resolve access. INVALID_STATE means a reviewed record changed; reload and review before amending. BUSY means the storage transaction is already owned by another operation. Do not commit or roll back that other operation. Invalid or oversized input must be corrected before retrying.

Ownership and limits

One trusted owner must serialize policy, identity and session changes with protected record operations. The authority checks several existing services; it does not hold a lock across those services. Keep request buffers stable until the call returns. Do not expose raw Data Server writes, policy mutation, session issuance or lower-level record APIs to untrusted code. Those APIs remain available for trusted internal use and can bypass this adapter.

This is an in-process access boundary, not a network authentication system or process sandbox. It does not encrypt storage, validate clinical decisions, authorize payments, or supply a durable security audit. Purpose appears in the returned access receipt; the historical document metadata format is unchanged. Applications needing a durable purpose trail must use a separately qualified audit sink. Existing application editors require explicit integration with the authority before their record operations gain these checks.
