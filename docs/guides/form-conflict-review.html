Review concurrent form edits

Two people can begin with the same saved record and change it independently. A three-way comparison uses that common baseline to distinguish a new change from an old value. It never writes a database by itself.

Understand the choices

BaselineLocalIncomingAutomatic result
2 kg3 kg2 kg3 kg: local change
2 kg2 kg8 kg8 kg: incoming change
2 kg3 kg3 kg3 kg: identical changes
2 kg3 kg8 kgUnresolved: an explicit decision is required

An answer includes its value, unit, missing-state marker and missing reason. Unknown and Not applicable are distinct from Unanswered. Choosing an incoming answer does not establish that it is factually correct or authorized.

Use the portable comparison

  1. Link Umicom::application and include umicom/application/experience/structured_form_merge.h.
  2. Establish that baseline, local and incoming describe the same record and schema. Form IDs and increasing counters alone do not prove shared ancestry.
  3. Call umi_structured_form_merge_create. It copies the three forms. Keep the immutable schema alive until the review is destroyed.
  4. Read umi_structured_form_merge_state and each umi_structured_form_merge_field. Show all three answers and their units to the reviewer.
  5. Use umi_structured_form_merge_select with the current review revision to choose a branch. Use umi_structured_form_merge_custom for a separately entered, validated answer.
  6. Call umi_structured_form_merge_finish to produce a proposed form. Unresolved conflicts, stale review tokens and invalid required answers leave the output unchanged.
  7. Destroy the review when finished. This portable service does not authenticate a reviewer or update storage.

Bind review to a saved form session

  1. Link Umicom::form_records and include umicom/data/structured_form_conflict.h.
  2. Capture the current session and verify its saved baseline against the selected database with umi_record_draft_snapshot_check_store. Load the current record document from that same database. Run database work away from the GUI thread.
  3. On the session's serialized owner, call umi_structured_form_session_review with the captured generation. Preparation verifies document integrity, identity and schema. A never-saved key collision is refused.
  4. Read fields, choose answers and preview through the conflict APIs. Keep the originating session and schema alive throughout the review.
  5. Call umi_structured_form_session_accept_review. It checks that the baseline, local bytes, answers and selection generation still match. Adoption changes the draft and its baseline together, or changes neither.
  6. Prepare and commit a normal session save. The storage revision is checked again. If a third writer changed the record during review, retain the draft and start a fresh comparison.

Expected results and recovery

Taking every incoming answer leaves a clean draft using the exact incoming bytes. Keeping a different local or custom answer leaves a dirty draft ready for an explicitly requested save. Adoption advances the session generation; an old review cannot be applied twice.

If review returns Busy, complete the pending save first. If it reports an invalid state, inspect whether local typing, record selection, schema or stored ancestry changed. Do not bypass the check by reusing counters. A required-answer refusal may still permit draft review with submitting set to zero, but it never turns an incomplete answer into a known value.

The native form record editor exposes the same workflow through Review stored version and Apply reviewed answers. Its asynchronous result is invalidated by later visible typing. Secret schemas require a different protected editor. These services provide revision handling, not encryption, permissions or domain approval.
