Save record content and its history together

A transaction groups several database writes into one operation. Either all writes are committed, or the earlier state is retained after rollback. The record-document service uses a transaction for the content, amendment metadata and current-revision pointer, so an application does not need to coordinate separate saves.

Include umicom/data/record_document.h and link Umicom::data. The service supports the Framework memory and optional SQLite Data Server backends. A record can contain up to 16,384 bytes, including binary zeroes. It is intended for bounded notes or structured records; large documents and media attachments need another storage service.

Actor and source fields are descriptive labels. They do not authenticate a user. Content is not encrypted. Access control, authenticated identity, record schemas and decisions about care or payments belong to the consuming services. The example uses fictional administrative and statement-review notes.

Create a record

  1. Create a Data Server with umi_data_server_create_memory, or open a database with umi_data_server_create_sqlite. Check its returned status before proceeding.
  2. Choose a stable entity ID, at most 63 bytes. Use a product namespace, such as bank.review.example, to keep unrelated records separate.
  3. Supply the amendment source, actor, reason and a nonzero recorded time. Metadata arrays must be terminated and contain no control characters.
  4. Pass the content and its byte length to umi_record_document_append, using expected revision zero for a new record. Do not include a text terminator unless it is part of the intended content.
  5. Keep the returned revision only when the call succeeds. The service calculates SHA-256 from the submitted bytes and replaces the copied metadata's digest; it does not change your input metadata.
UmiRecordAmendment metadata = {
    .entity_id = "bank.review.example",
    .source = "fictional-statement",
    .actor = "fictional-reviewer",
    .reason = "Record a review note",
    .recorded_at_nanoseconds = 100
};
const char note[] = "Reference requires review.";
UmiRecordRevision saved;
UmiStatus status = umi_record_document_append(server, &metadata,
    note, sizeof note - 1, 0, &saved);
if (status != UMI_STATUS_OK) {
    /* Keep the editor draft and report the failure. */
}

Read and amend without losing another edit

  1. Read umi_record_document_latest into a caller-owned UmiRecordDocument. Its length gives the valid content size. Binary content is not a C string; use its length when displaying or exporting it.
  2. Keep document.record.revision while the user edits their copy.
  3. Submit the new bytes with that reviewed revision. A stale revision returns UMI_STATUS_INVALID_STATE. Keep the draft, reload the current record separately, and let the user compare the changes.
  4. Use umi_record_document_load to read a particular earlier revision. The original content remains available after an amendment.
  5. Use umi_record_document_verify to check every revision through the recorded head. This checks required rows, encoding, byte counts, digests and recorded-time order.

All public document operations own their transactions, including reads. Calls inside an existing transaction return BUSY; they do not complete the caller's transaction. SQLite reads currently use Data Server's immediate transaction mode and can contend with other database writers. Run database operations on the application's managed worker when blocking storage would affect the interface.

Keep the storage format consistent

The older metadata-only history API remains available. Choose one append API for each entity. A metadata-only revision has no content rows, so it cannot silently be amended as a document. An explicit migration would need to supply and verify the missing historical content. The document service does not invent that content.

Content is stored as bounded hexadecimal chunks with a versioned manifest. Applications must not write keys beginning with repo.record-history. or repo.record-content.. Each revision consumes several Data Server records; the memory backend's total record limit still applies. Failed saves do not delete earlier revisions to make room.

Run the installed example

After installing an SDK that includes the data component, copy share/umicom-framework/examples/data_history into your own example workspace. From that copied folder, use the installed prefix appropriate to your system:

cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH="C:/umicom/installed/applications"
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure --no-tests=error

Stop on a failed command. The consumer project links the installed Umicom::data target. The document example should report two intact revisions for each fictional entity, with the original retained and a stale edit refused. The example uses memory storage and does not demonstrate restart persistence; the SQLite reopen regression covers that separate behavior.

Recover from an error

StatusAction
INVALID_STATEKeep the draft. Inspect whether the reviewed revision is stale or a supposedly unused storage key is occupied. Do not overwrite existing rows.
BUSYLet the active transaction finish. Retry through the application's normal worker after reviewing its current state.
INVALID_ARGUMENTCheck metadata, nonzero recorded time, entity ID, pointers and content length.
NOT_FOUND / PARSE_ERRORA required row is absent or malformed, or its content digest differs. Preserve the database for inspection. Do not treat missing content as an empty record or silently recreate it.
CAPACITY_EXCEEDEDCheck the 16 KiB document limit and the backend's record capacity. Keep the unsaved draft.
IO_ERRORRead Data Server diagnostics. A failed rollback can require further recovery on the same server. Do not assume the database is ready for a retry until its recovery contract is satisfied.

Output snapshots remain unchanged on failure. Hash verification detects accidental content changes, not a malicious rewrite of the complete store, a deleted history tail, or a trusted signer. Store backups and retention policies remain separate responsibilities.
