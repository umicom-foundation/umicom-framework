Build and test a changed component

A compiler turns source files into object files. A linker joins those objects and libraries into a program. Ninja remembers the inputs needed for each output, so an ordinary build in an existing build folder reuses work that is still current. You do not need a different compiler to get incremental builds.

Tests are separate. Running CTest without a selection asks for the whole configured suite, even when the build had nothing to compile. Use a component build and a reviewed test selection while developing; run broader integration and release qualification at agreed checkpoints.

1. Keep one configured build folder

  1. Open PowerShell in the Applications checkout and make the compiler tools available.
  2. Configure once for the chosen compiler and options. Configure again after adding targets, changing options, or merging files whose original timestamps were preserved. An ordinary Ninja build can also regenerate changed CMake inputs.
  3. Keep this build folder between edits. A different folder starts with no reusable objects. Changing the compiler, compiler flags or shared headers may legitimately invalidate many outputs.
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\repository-publication"

cmake --preset windows-ucrt64-all-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\repository-publication\incremental-configure-01.log"
Run each step separately and stop on an error. PowerShell pipelines do not automatically stop later commands when a compiler fails. Use new log names for subsequent runs. Do not run concurrent builds or configuration operations in the same build directory.

2. Build a selected target and its dependencies

A target is a named output or group of outputs in the build configuration. For a document fingerprint change, this target builds its test executable and the libraries needed by it:

cmake --build --preset windows-ucrt64-all-debug --target umicom-document-fingerprint-tests --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\repository-publication\document-build-01.log"

After a source edit, expect only the affected objects and dependent link steps. When everything is current, Ninja normally reports no work. A shared public header can affect more than one source file. The selected target is a build boundary, not a claim that one test covers every consequence of a change.

3. Run the matching tests

Run this only after the selected build succeeds:

ctest --preset windows-ucrt64-all-debug -R "^framework[.]document[.]fingerprint$" --parallel 2 --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\repository-publication\document-tests-01.log"

-R selects test names using a regular expression. Here, ^ means the beginning of the name, [.] means a literal dot, and $ means its end. --no-tests=error catches an empty selection. Review failed, skipped and disabled tests separately; an exit code of zero does not prove every configured check executed.

4. Work on a whole application

The Applications build provides product and test groups. For Studio, build both groups, then select Studio-owned checks:

cmake --build --preset windows-ucrt64-all-debug --target umicom-product-studio umicom-tests-studio --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\repository-publication\studio-build-01.log"

ctest --preset windows-ucrt64-all-debug -R "^studio[.]" --parallel 2 --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\repository-publication\studio-tests-01.log"

These groups depend on the enabled application configuration. Shared application-integration tests are a separate scope. They may need additional application binaries or fixtures. Build those dependencies when the selected tests require them. A shared Framework change can affect other products, so add their checks or use the full suite; the name filter alone does not discover dependency impact.

To inspect which test names a filter selects without running them, add -N to the CTest command. To retry failures from the previous run, use ctest --preset windows-ucrt64-all-debug --rerun-failed --output-on-failure --no-tests=error. That uses the previous failure list and ignores name-selection filters. It is a recovery step, not complete regression coverage.

5. Use the native Umicom command

A CLI containing the build-test command performs the two phases in order and stops if the build fails. Framework owns argument validation, execution, cancellation and output capture, so native applications can use the same service. The target and test expression are explicit; this command does not automatically determine affected tests.

Run the CLI from a separate tools installation when rebuilding Umicom itself. Windows cannot replace a running executable. The command must not be inside a build or installation destination that it will overwrite. First use umicom build-test --help to check that the installed CLI supports the command.

umicom build-test --source C:\umicom\Umicom-Applications --build build\windows-ucrt64-all-debug --target umicom-document-fingerprint-tests --tests "^framework[.]document[.]fingerprint$" --jobs 2 --dry-run

umicom build-test --source C:\umicom\Umicom-Applications --build build\windows-ucrt64-all-debug --target umicom-document-fingerprint-tests --tests "^framework[.]document[.]fingerprint$" --jobs 2 --log C:\umicom\_local\logs\repository-publication\document-cycle-01.log

The command requires an existing configured --build directory, one --target and a non-empty --tests expression. An aggregate target can group several outputs. Choose a target that builds the selected tests and their fixtures. --preset, --clean, --define and installation/launch options are rejected. Configure separately when changing the build configuration. CMake/Ninja can still regenerate their own graph during a build.

A preview starts no tools and writes no log. An execution log needs an existing parent directory and a fresh filename; an existing log is not overwritten. The log captures child output. The CLI displays command descriptions and discovery diagnostics separately. The older make command still configures, builds and tests, and check still performs toolchain diagnosis.

6. Understand automatic selection

The impact inventory guide describes umicom impact. It previews target/test relationships from configured source ownership. Inventory capture must be enabled for that build. Missing ownership, configuration changes or changed submodules can require a full selection. Do not discard that fallback simply to shorten a run.

Git working-tree changes disappear after a commit. A reliable selection must compare against a known, successfully qualified immutable revision as well as current staged, unstaged and untracked changes. Use the documented --since option or explicit changed paths when appropriate. An impact preview does not itself compile or test, and build-test does not yet consume that preview automatically.

7. Investigate a surprisingly large build

ObservationCheck
Many objects rebuild after one header changeInspect the header's consumers and compiler definitions. Framework currently carries a shared public-contract fingerprint through its base target; a changed fingerprint can invalidate many compile commands. This also protects content changes copied with preserved timestamps. Disabling that protection can leave stale objects.
A source-only edit rebuilds unrelated objectsCheck compiler/options changes, generated inputs, timestamps and command-line differences. Ask Ninja to explain a pending target: cmake --build --preset windows-ucrt64-all-debug --target umicom-document-fingerprint-tests -- -n -d explain. This is a dry-run diagnostic and does not compile the target.
Build is short but tests take hoursCheck the selected test names, durations and nested configure/build tests. Use a reviewed component filter during development. A small number of slow tests can dominate total time.
The same Framework compiles in several foldersApplications includes Framework. Reuse that build for integrated development. Keep separate standalone SDK, OS and release configurations when those distinct environments need qualification.
More parallel jobs make the machine slowerMemory, storage and nested compiler work may be saturated. Start with two jobs and measure before increasing. CTest observes declared resource locks; undeclared shared state still needs review.
Tests report missing executablesBuild the test targets first and resolve compiler or quarantine errors. Do not accept an old binary or skip the failing coverage.

8. Run broader qualification before a release

cmake --build --preset windows-ucrt64-all-debug --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\repository-publication\full-build-01.log"

ctest --preset windows-ucrt64-all-debug --parallel 2 --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\repository-publication\full-tests-01.log"

A focused run provides evidence for its selected scope. Shared interfaces, configuration changes, packaging, installation and platform-specific behavior need their corresponding integration checks. Keep successful qualification records with source revisions, configuration and selected tests so later changes can be compared with a meaningful baseline.
