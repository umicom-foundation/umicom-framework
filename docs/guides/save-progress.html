Understanding Save All progress and library links

When you choose Save All in Umicom Studio, the document service saves your work and the interface explains what happened. Those are separate responsibilities. The service decides which files were saved; the status area displays a copy of that result.

This lesson follows a Notes project with three source files. You will read its save progress, check that the numbers agree, and build a small programme that uses the same public functions as Studio. You will also learn why a function can compile successfully at its call site but still be missing when an executable is linked.

1. Read the save result

Imagine that notes.c was saved by the current Save All run. You saved notes.h separately before its turn arrived. The test source still needs saving. There are three documents in the original sequence:

FieldValueMeaning
total3The number of pending documents captured when this sequence began.
saved1Documents whose save operation succeeded in this sequence.
unchanged1Documents already saved by another action before their turn.
remaining1Documents not successfully processed, including a current failed item.

The counts must agree: saved + unchanged + remaining = total. Framework checks the parts without first adding them, because adding extremely large unsigned counts could overflow.

The phase describes what happens next. READY means another step can run. NEEDS_PATH means an untitled document needs a filename. COMPLETE, FAILED and CANCELLED end the sequence. An empty sequence is complete; it is not waiting to save a nonexistent document.

Cancellation does not undo an earlier save. A failed interface refresh can also occur after all files were saved. Keep the successful counts in that situation rather than telling the user that their saved work disappeared.

2. Use the shared functions

UmiDocumentSaveProgressValidate()

Pass a pointer to a copied UmiDocumentSaveProgress. The function checks the declared phase and status, the terminated document name, and the count partition. It returns UMI_STATUS_OK when those fields agree, or UMI_STATUS_INVALID_ARGUMENT otherwise. It neither modifies nor retains the snapshot.

Validation checks consistency, not authenticity. Someone could construct a consistent set of invented counts. To know what a real save did, obtain the snapshot from its session and independently inspect the files in an acceptance test.

UmiDocumentSaveProgressFormat()

Give this function the snapshot, an output character array and that array’s capacity. It validates the snapshot and creates a complete message. A malformed snapshot leaves the output unchanged. A valid message that cannot fit returns UMI_STATUS_CAPACITY_EXCEEDED without publishing half a sentence. The capacity includes the terminating zero byte.

Ready, filename-request and failure messages include the already-saved count, so the displayed information accounts for the whole original sequence. Names are plain text. A GUI host should not interpret them as markup.

UmiGtk4AdapterDocumentSaveAllProgress()

A GTK application calls this accessor on its UI owner thread to copy progress from the currently attached save run. It does not advance the run, open a chooser or write a file. The adapter must remain alive. NOT_FOUND means there is no active run, and INVALID_STATE means its ownership is no longer valid. Output is unchanged on failure.

The adapter clears a finished run before notifying the host. Copy final progress from the completion callback; do not expect the active-run accessor to retain a history of completed sequences.

3. Run a complete Notes progress example

The following programme deliberately uses sample progress. It writes no project files. First it displays a consistent result, then a cancelled result, then verifies that contradictory counts cannot replace an existing message. The separate save_all.c example in the same directory demonstrates real temporary-file saving and read-back checks.

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/editor_workflow/save_progress.c
 * PURPOSE:
 *   Read and explain a copied Notes Save All result through the public library.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/
#include "umicom/document/save_session.h"
#include <stdio.h>
#include <string.h>

/* Print only a result whose counters and state agree. The caller owns both
 * the snapshot and output buffer; neither function retains their addresses. */
static int ShowProgress(const UmiDocumentSaveProgress *progress)
{
    char message[UMI_DOCUMENT_NAME_CAPACITY + 384U];
    UmiStatus status = UmiDocumentSaveProgressValidate(progress);
    if (status == UMI_STATUS_OK)
        status = UmiDocumentSaveProgressFormat(progress, message, sizeof(message));
    if (status != UMI_STATUS_OK) {
        fprintf(stderr, "Cannot display save progress: %s\n", umi_status_text(status));
        return 1;
    }
    return puts(message) == EOF ? 1 : 0;
}

int main(void)
{
    /* This is sample progress for teaching, not an instruction to save files.
     * notes.c was saved by this run, notes.h was saved separately, and the test
     * source remains pending. Production values come from the save session. */
    UmiDocumentSaveProgress progress = {0};
    progress.phase = UMI_DOCUMENT_SAVE_READY;
    progress.last_status = UMI_STATUS_OK;
    progress.total = 3U;
    progress.saved = 1U;
    progress.unchanged = 1U;
    progress.remaining = 1U;
    if (ShowProgress(&progress) != 0) return 1;

    progress.phase = UMI_DOCUMENT_SAVE_CANCELLED;
    progress.last_status = UMI_STATUS_CANCELLED;
    if (ShowProgress(&progress) != 0) return 1;

    /* A contradictory result must not replace an existing status message. */
    char message[128] = "Keep the previous status";
    progress.remaining = 0U;
    if (UmiDocumentSaveProgressFormat(&progress, message, sizeof(message)) !=
            UMI_STATUS_INVALID_ARGUMENT ||
        strcmp(message, "Keep the previous status") != 0) return 1;
    puts("Invalid progress was rejected; the previous status was preserved.");
    return 0;
}

Configure the corresponding preset first. The expected output is:

Save All: 1 saved, 1 remaining. 1 already saved separately.
Save All cancelled: 1 saved, 1 already saved, 1 remaining.
Invalid progress was rejected; the previous status was preserved.

Try changing remaining in the first snapshot to two. The numbers would then describe four documents rather than three, so validation must reject them. Restore the correct value afterwards.

4. Understand a missing function at link time

A header declares a function’s name, parameters and result. A C implementation supplies its body. The compiler turns that implementation into an object file. A static library groups object files into an archive. The linker connects calls in an executable to the definitions supplied by its libraries.

save_session.h          Declaration used by a caller
        ↓
save_session.c          Function body owned by Framework
        ↓
save_session.c.obj      Compiled implementation
        ↓
libumicom_document.a    Static archive
        ↓
Studio / example       Linked executable

An undefined reference means a required definition could not be resolved. A successful archive build does not establish that it contains every function declared by a header. An older object file can still be a valid object file while lacking a newer function.

Likewise, a C _Generic signature check examines a declaration without necessarily emitting a call. A real link check must contain an executable reference to the function. Keep type checks and add linked consumers; neither replaces the other.

5. Check the actual libraries

umicom-save-link-readiness builds the core consumer, GTK-library consumer, Save All example and native save tests. Studio’s existing umicom-studio-build-readiness also depends on it. A configuration without GTK support cannot satisfy the full save-link target.

The core consumer runs the example above. The GTK-library consumer makes real calls to the accessor’s null-argument boundary and the formatter. It does not initialise GTK or open a window. It checks linking and argument handling; use the separate graphical tests to check interaction with a real window.

& "C:\msys64\ucrt64\bin\cmake.exe" --build --preset windows-ucrt64-all-debug --target umicom-save-link-readiness --parallel 2
& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --no-tests=error --output-on-failure -R '^framework\.document_saving\.link\.'

GNU nm can list definitions in an archive. A capital T identifies a global code symbol; U identifies an unresolved reference. The following commands select definitions only:

& "C:\msys64\ucrt64\bin\nm.exe" --defined-only --extern-only ".\build\windows-ucrt64-all-debug\lib\libumicom_document.a" | Select-String 'UmiDocumentSaveProgressFormat$'
& "C:\msys64\ucrt64\bin\nm.exe" --defined-only --extern-only ".\build\windows-ucrt64-all-debug\lib\libumicom_ui_gtk4.a" | Select-String 'UmiGtk4AdapterDocumentSaveAllProgress$'

Each command should show its named definition. This is a useful diagnosis, but a successful real consumer link remains the stronger check because it also resolves that consumer’s dependencies.

7. Test the user’s outcome

Open a disposable Notes project, modify a named source file and an untitled header, then choose Save All. Cancel when asked for the header’s name. Read the named file back: its successful save should remain. The header should remain open with its draft. Start a fresh sequence to save the remaining work.

Use Report problem to retain a note, the relevant interaction log and an optional screenshot when the result differs from what you expected. Avoid sharing private document contents or credentials. A responding control alone does not establish that the intended file was saved.
