Adopt project indentation for one document

An .editorconfig file describes editor preferences for matching files in a project. Umicom can inspect those preferences and propose indentation for an open saved document. Adoption is explicit and affects that working copy only.

Review and apply

  1. Open a project folder and a saved source file inside it.
  2. Choose Use project indentation in the editor actions. The window identifies the captured source file and project boundary.
  3. Choose Inspect. Reads run in the background. The report shows the previous and proposed indentation, source file names and their SHA-256 digests. A digest identifies observed bytes; it does not lock a file.
  4. Review the proposal, then choose Apply indentation. Umicom re-reads the configuration and compares it with the reviewed evidence before changing that document's override.
  5. Use Document indentation and Use session defaults to remove the override later.

Changing tabs does not change the captured target. Editing source text during a review is allowed. Changing the target's saved path, its indentation settings, session defaults or configuration evidence rejects the pending proposal. Inspect again after reviewing the change.

What changes

Only the document indentation pair is adopted: a width from 1 to 16 and spaces or tabs. Missing properties keep the document's current effective values. Distinct indentation and tab widths cannot currently be represented. Invalid indentation values are rejected instead of silently replaced with defaults.

Encoding, line endings, trailing whitespace and final-newline properties are reported but not applied. No source text, Undo history, file, project settings file or persisted session default is rewritten. The override expires when the working copy closes.

Configuration example

root = true
[*.c]
indent_style = space
indent_size = 4

The search stops at root = true or the chosen project boundary. Umicom does not search ancestors above that boundary. The inspector uses bounded UTF-8 parsing, refuses links below the admitted root and never executes project commands. See the configuration inspector guide for parser limits.

Recovery

  • Configuration changed: Inspect again. Even changed comments produce different source evidence and require a fresh review.
  • No applicable settings: check matching sections and indentation property names. A configuration containing only encoding or newline preferences offers no indentation proposal.
  • Unsupported widths: use matching indentation and tab widths from 1 to 16, or keep the existing document policy.
  • Operation cancelled: no pending worker is allowed to apply after cancellation or editor retirement.
  • Applied, refresh interrupted: the policy mutation completed before a native display callback interrupted refresh. Refresh the editor display; this message does not mean the setting was rolled back.

Embed the C23 service

Load an inspection on a worker. On the document owner thread, create UmiDocumentEditorConfigPlan; success transfers inspection ownership to the plan. Show its summary. Before approval, re-read the same scope and call UmiDocumentEditorConfigPlanApplyObserved on the owner thread. Destroy the plan and the reinspection independently.

The service compares supplied observations and performs no file I/O during application. Files can change after a re-read; there is no filesystem-wide transaction. Applications must keep the coordinator alive and serialize its document operations. A successfully applied plan is consumed and cannot be applied twice.
