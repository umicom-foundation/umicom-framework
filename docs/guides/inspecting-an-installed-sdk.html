Choose an installed Framework SDK

An SDK is the installed set of headers, libraries and package files that another project uses to compile and link. Choosing its installation folder should not accidentally select a different SDK, or confuse the version of an inspection tool with the version installed there.

Inspect an installation

  1. Install the Framework development files into a folder you control. A current installation with relative include and library directories provides share/umicom/framework/sdk.properties.
  2. Use the native command with that installation folder: 
    umicom sdk inspect "C:/SDKs/Umicom"
    The command accepts a relative folder and resolves it at invocation time. Framework worker APIs require an absolute folder.
  3. Review the declared version, ABI and paths. ABI means the binary interface expected by compiled code. The receipt describes these values; it does not prove that an archive was built for your machine or compiler.
  4. Check the five presence results: package configuration, exported targets, package version, public umbrella header and base library. An empty directory is not a library file. Exit code zero means these files were found. Exit code one means inspection failed or required files were missing; two means incorrect command usage.

Inspection does not evaluate CMake, execute a package script, invoke a compiler or linker, load a library, or connect to a remote service. Compile and link your consumer to establish whether the selected installation can actually be used.

Select the SDK in Studio Build Settings

  1. Open a project, then Build Settings.
  2. Enter the full installation folder in Framework SDK installation folder and select Inspect SDK. The read runs off the UI thread.
  3. Review the installed paths and missing-file messages. Editing the location, even back to its original text, invalidates the review. Closing or hiding the form also invalidates it.
  4. Select Use inspected SDK in this profile. This inserts or replaces -DUmicomFramework_DIR:PATH=... in the current CMake definitions. Other definitions retain their values. The exact package folder is used, including custom relative library folders such as lib64.
  5. Review the complete form, select Apply Settings, and configure when ready. Neither inspection nor selecting the package grants workspace trust or starts a build. Use a fresh build folder when changing compiler or target architecture.

The installation may change after inspection. CMake and the compiler remain responsible for checking the files at actual use. A saved package location remains a local project setting; it is not a portable promise that another computer has the same SDK.

Use the services from C

UmiSdkInstallationInspect reads a bounded receipt and reports owned paths and presence flags. umi_sdk_validate_prefix compares its declared version and ABI with the caller's requirement. It no longer substitutes the inspecting process's own Framework identity. A successful comparison is still metadata evidence.

UmiBuildConfigureDefinitionSet and UmiBuildConfigureDefinitionRemove edit a private build-profile draft. They validate the complete definition list, preserve the profile on failure and do not execute a shell. Dedicated settings such as the compiler and installation prefix remain owned by their existing profile fields. Removing a definition does not clear a value already cached in a build directory.

Understand older and custom installations

SituationWhat to do
No receiptInstall the updated SDK into a separate prefix. The legacy presence probe can inspect conventional include/lib layouts, but version validation, the native inspection command and Studio's SDK selector require metadata.
Malformed receiptReinstall from a known build. The service refuses malformed, duplicate, unknown, oversized or unsafe relative paths instead of falling back to another SDK.
Missing archive or package fileCheck that the development installation completed. A partial installation cannot satisfy inspection merely because its directories exist.
Absolute install directories or unsupported layout charactersCMake may still support your layout, but no relocatable receipt is emitted. Use the package's explicit CMake location. Do not reuse an old receipt from a different layout; choose a clean prefix.

The receipt is bounded to 16 KiB and contains exactly one schema, Framework version, ABI, include directory, library directory and base-library path. Versions have three numeric components. Relative paths reject traversal and executable expressions. Trusted parent-directory aliases may still be followed; this is not a filesystem sandbox. Presence inspection does not qualify optional SDK components, dependencies or every exported target.

When adding SDK metadata fields, update the producer, bounded parser, inspection consumer and regression fixtures together. Keep executable package logic out of the receipt.

Check the complete Framework dependency chain

A component can depend on another Framework library. This is called a transitive dependency: your program requests the first component, and the linker also needs the libraries that component uses. A broker connection component, for example, uses shared platform services to read and replace local settings files.

  1. Configure your consumer against the intended installation, using the exact UmicomFramework_DIR package folder.
  2. After find_package, request the installed-SDK contract check: 
    umicom_require_installed_sdk("C:/SDKs/Umicom"
    Umicom::market_tape
    Umicom::research_replay
    Umicom::ibkr_connection)
    The package exposes this helper. It checks the selected prefix, imported Framework targets, their include folders, library files for every advertised configuration, and the complete public-header identity.
  3. Read the first refusal before building. A transitive Framework library outside the prefix can indicate a mixed installation. Install the matching SDK into a fresh folder rather than borrowing that archive from a source build.
  4. Build and run the independent consumer after configuration succeeds. Path and header checks cannot establish binary compatibility or runtime correctness.

The traversal follows Framework target names in link interfaces, including static-library link-only dependencies. A visited set prevents repeated visits and handles dependency cycles. All advertised Framework references are checked, including conditional references. Third-party packages and system libraries have separate locations and are not required to live inside the Framework prefix.

A library can inherit its public include directory from another Framework component. Such a library does not need to repeat that directory in its own exported properties. The contract follows its Framework dependencies and checks every header path they publish. The base component must still identify the installed base headers. Interface aggregates may have no archive, while an ordinary library must identify an existing archive or shared-library file.

The smaller component-integration laboratory installs a deliberate subset of Framework. Its consumer uses UMICOM_EXPECTED_SDK_PREFIX to restrict package discovery and umicom_require_installed_sdk_layout to check component paths. Its sdk-origin.txt records the selected package. That subset check does not replace the full SDK public-header identity check.

If a native window fails after linking

An SDK origin check identifies headers and link libraries. It does not prove which shared toolkit a process loads or that the toolkit has no defects. Follow Diagnose GTK runtime failures on Windows to separate compiler metadata, loaded versions and known input-method lifetime issues.
