Review linked context changes

A context group is a named value that related panels can share. For example, two trading panels might follow the same selected instrument, while two education panels follow the same course. Framework owns the values and the rules for changing them. Application modules supply their own identity and presentation.

The context review API lets a host prepare several edits, display the proposal, and accept it later. Preparation copies the input and leaves the live workspace alone. Acceptance checks that the workspace still matches what was reviewed.

This is a C API for application hosts. It does not add a graphical review dialog, connect a provider, save a workspace, load a project, or execute an order, payment or command. A context value describes presentation state; it is not an authority to perform an operation.

1. Choose the correct owner

Use umicom/application/runtime/context_review.h and link the existing Umicom::application target. A product host includes its own workspace_commands.h and uses that product's review and apply wrappers. They refuse a runtime belonging to another product. Keep the experience catalogue immutable for the runtime's lifetime.

Operate on the runtime's owning thread. Keep the runtime and any bound workbench alive, and do not reinitialise either while reviews exist. A workbench is borrowed: destroying a review never destroys the workbench. Coordinate related host writes on the same thread; the underlying typed UI store also has its own mutex.

2. Describe the edit

Use a zero-initialised array of UmiApplicationContextChange values. Each name may occur once. Text must end with a null character inside its fixed array. Names must be nonempty; a SET value may be empty. The example names below are illustrative; choose names understood by your own panel consumers.

UmiApplicationContextChange changes[] = {
    { UMI_APPLICATION_CONTEXT_SET, "linked.primary", "sample-project" },
    { UMI_APPLICATION_CONTEXT_SET, "linked.secondary", "sample-document" }
};
UmiApplicationContextReview *review = NULL;
UmiStatus status = umi_application_context_review_prepare(
    runtime, changes, sizeof(changes) / sizeof(changes[0]), &review);

Proceed only if status == UMI_STATUS_OK. A failed preparation leaves the output pointer unchanged. A successful review owns its input text, so the host may reuse the original input array. Never overwrite an existing owned review pointer with a second preparation; destroy the old review first.

3. Display copied review rows

Read umi_application_context_review_summary to obtain the number of added, updated and removed groups. Read each row with umi_application_context_review_row. The row includes the proposal, whether the group existed, and its previous application-cache value. This value is not an independently captured view of UI state. An empty prior value is distinct from an absent group; inspect existed to tell them apart.

When a workbench is bound, each row also contains a copied typed UI value. The summary's ui_difference_count reports affected groups whose UI value differs from the application cache, including a missing value or another type. Show both values before acceptance. Applying the reviewed edit deliberately replaces the affected UI value; it does not silently treat the cache as current UI evidence. Choose application-owned key names to avoid unrelated services.

Rows and summaries are copies. Editing a returned row cannot change the review. Treat the summary as a display model, not an instruction to execute a command. The group names in a removal are meaningful; its unused value is returned empty.

4. Accept or cancel

/* Run after the host has obtained the user's choice. */
if (accepted) {
    status = umi_application_context_review_apply(runtime, review);
}
umi_application_context_review_destroy(review);
review = NULL;

Acceptance requires the original runtime, the same session and workbench, unchanged context entries, and the observed UI revision. A successful nonempty edit advances the application context revision once. The bound UI store also publishes the complete change under one lock and advances once. The application cache is assigned only after that publication succeeds. A failed acceptance leaves both context stores unchanged. An accepted review cannot be applied again.

On UMI_STATUS_INVALID_STATE, discard the review, refresh the displayed state and prepare a new proposal. Do not retry with an invented revision. Another UI context change, including one to an unrelated key, can invalidate a review. Cancelling simply destroys the review and leaves live context values alone.

5. Clear a group or replace one at capacity

Use UMI_APPLICATION_CONTEXT_REMOVE and the existing group name. A removal needs no value. The group must exist in the application store; if a workbench is bound, it must still exist there when accepted. Missing groups return UMI_STATUS_NOT_FOUND. The convenience function umi_application_workspace_runtime_clear_context uses the same transaction.

A transaction may contain up to UMI_APPLICATION_RUNTIME_MAX_CONTEXT_BINDINGS distinct changes. All removals free capacity before additions, regardless of their order in the input. This allows a full workspace to replace one group with another. Keys outside the proposal remain untouched. Context revisions and per-entry revisions never wrap; counter exhaustion refuses the edit.

Typed UI context transactions

Services that own typed UI keys can use UmiUiContextApplyChanges from umicom/ui/context_changes.h, linked through Umicom::ui. It accepts Boolean, integer and string SET operations and key-only removals. Boolean inputs are exactly zero or one. The complete candidate is held on the heap and published only if every operation succeeds. It invokes no callbacks.

Use UmiUiContextReadKeys to capture selected typed values and one revision under the same lock. Missing keys are explicit, repeated requested keys are allowed, and returned values are independent copies. This read supports coherent confirmation views without exposing pointers into the live store.

Read the current UI revision, then submit that value as expected_revision. A zero-length request only checks the revision; it does not advance it. This transaction does not make several independent getter calls into a single read snapshot. Coordinate the surrounding host workflow when a reader needs a consistent multi-key view.

Recover from a refused edit

StatusWhat to check
INVALID_ARGUMENTCheck runtime identity, structure size, string terminators and operation kinds. Do not shorten a group name silently.
ALREADY_EXISTSEach proposal may mention a group only once. Combine repeated edits into one intended result before preparation.
INVALID_STATEThe review is stale, already applied, or belongs to another runtime. Capture a fresh proposal.
CAPACITY_EXCEEDEDCheck application and UI capacity, text length and exhausted revisions. A capacity failure does not partially update earlier groups.
NOT_FOUNDThe removed group is absent. Refresh the presentation before deciding whether a new removal is needed.
OUT_OF_MEMORYNo candidate was published. Keep existing state and let the caller retry when resources are available.

The operation log records a durable context-links scope label. Individual before/after values are available in review rows. The bounded log is diagnostic information, not durable audit storage, and a full log does not undo a successful context edit. Use a separate persistence service when durable evidence is required.

Future frontend contributors can render the copied rows in a native view and pass the accepted review to Framework. Keep validation and state publication here; avoid adding another application-owned context store.
