Inspect an existing Umicom data store

An inspection connection can read an existing SQLite Data Server without obtaining permission to change its records. Use it for history viewers, import receipt readers and diagnostic screens. It does not create a missing database or install a missing table.

Open, read and close

  1. Let the user select the database. Authorize access in your application. Supply an explicit absolute local path.
  2. Open the inspection connection on your storage worker. Keep the complete operation on that worker when a service owns a transaction.
  3. Read records through the normal Data Server and record APIs, then destroy the connection after all users have finished.
#include "umicom/data/record_transfer.h"

UmiDataServer *server = NULL;
UmiStatus status = umi_data_server_open_sqlite_readonly(database_path, &server);
if (status == UMI_STATUS_OK) {
    UmiRecordTransferReceipt receipt;
    status = umi_record_transfer_receipt_verify(server, receipt_id, &receipt);
    /* Publish a copied result to the UI only when status is OK. */
}
umi_data_server_destroy(server);

Link your program to Umicom::data. SQLite support must be enabled in the Framework build. The opener returns UNAVAILABLE when that support is absent, and clears the output pointer on failure.

What inspection permits

Get, visit, count, snapshot, history, document and receipt reads remain available. Begin, commit and rollback use the existing transaction ownership rules. A nested transaction reports BUSY. Read transactions do not request a writer reservation.

Set, delete and every arbitrary SQL execute call return PERMISSION_DENIED, including SQL that appears to be a SELECT. Use the bounded read APIs instead. The access mode is immutable; changing data requires a separately authorized writable connection. Ordinary memory and writable SQLite connections retain their existing behavior.

Expected failures

  • A missing or corrupt file produces a storage error; inspection does not repair or create it.
  • An unrelated database, missing key/value table, incompatible columns or view substituted for the table is refused.
  • Empty names, SQLite special names beginning with a colon and file: URIs are rejected. URI options must not redefine the selected destination.
  • Lock contention can report BUSY. Retry explicitly after the other operation finishes.
  • Receipt verification checks the imported history and its checksum. It does not authenticate authors or protect against replacement of the entire store.

SQLite may perform its normal journal and WAL coordination. This API prevents record changes through its connection; it is not a forensic guarantee that no filesystem metadata or coordination files are touched. Choose a dedicated copy for forensic analysis.

SQLite background

The implementation uses SQLite's read-only connection flag and deferred read transactions. Application permissions, file selection and worker lifetime remain responsibilities of the host.
