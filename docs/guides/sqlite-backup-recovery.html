Back up and recover a SQLite Data Server

Umicom copies a consistent SQLite snapshot into a new selected file. It uses the SQLite backup engine, including committed content still held in a write-ahead log. It does not copy the live database file with an ordinary filesystem copy.

Create a backup

  1. Choose an absolute filename in an existing directory that you control. The filename must not already exist.
  2. Finish any transaction on the source Data Server.
  3. Call the checked backup operation on a storage worker and inspect its returned status.
  4. Retain the successful report with your application's private operational records. It describes the destination, SQLite page count and key/value row count.
#include "umicom/data/backup.h"

UmiDataBackupReport report;
UmiStatus status = umi_data_backup_create_checked(server, backup_path, &report);
/* Use report only after status == UMI_STATUS_OK. */

The complete main database is copied, including application tables beyond umicom_kv. Temporary and attached databases are outside this operation. The report's record count refers only to key/value rows. Both the source and copied database must pass SQLite quick_check before success is reported; this does not verify application meanings, foreign keys or identities.

Recover without replacing the current database

  1. Select the backup file and a different, new destination filename.
  2. Call umi_data_backup_restore_checked. It opens the backup read-only and creates a verified snapshot at the new destination.
  3. Open the recovered database separately. Check the records and workflows you need.
  4. Only after your application's own review, switch it to the recovered path. Keep the previous database for comparison.
UmiDataBackupReport recovered;
UmiStatus status = umi_data_backup_restore_checked(backup_path, new_database_path, &recovered);

The original store is never replaced, deleted or renamed. Recovery does not close other applications or switch their configuration. Record histories and import receipts are copied intact; use the record verification services to check those application-level contracts.

Failures and limits

  • ALREADY_EXISTS: choose a new filename. Do not delete the existing file merely to retry.
  • BUSY: finish the current transaction or wait for conflicting database activity, then explicitly retry.
  • INVALID_STATE: SQLite reported structural diagnostics or the selected source is incompatible. Preserve it for investigation.
  • A filesystem or engine error after exclusive creation may leave an empty or partial new file. It is retained as evidence and must not be treated as a successful backup.
  • Relative paths, URI destinations, missing parent directories and oversized paths are refused.

This operation is synchronous on its caller's worker. It performs no automatic retries, encryption, signature generation, cloud upload or backup rotation. The directory must be trusted against concurrent replacement. A successful close is not a power-loss durability guarantee.

Compatibility

The existing umi_data_backup_create and umi_data_backup_restore entry points delegate to the checked services. They now require new absolute destination filenames and refuse overwriting an existing database. Their earlier file-copy bodies remain disabled in the source for review.

See the SQLite backup API for snapshot semantics, and Umicom SQLite health for the precise scope of quick_check.
