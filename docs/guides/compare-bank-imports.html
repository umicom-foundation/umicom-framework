Compare two imported bank reports

Use this review to see how two saved transaction imports differ. Both imports remain unchanged. The comparison matches an exact account ID and a nonempty transaction ID. It does not merge imports, connect to a bank, change a ledger or calculate money to transfer.

Bank, Trader and TMS expose the shared Bank transaction reports window. The Framework supplies the comparison so these applications use the same matching rules.

Try two invented reports

  1. Use examples/bank_feed/comparison-before.csv and examples/bank_feed/comparison-after.csv in the Framework checkout. Installed examples are under share/umicom/examples/bank_feed within your installation prefix.
  2. Open Bank transaction reports. Select Statement CSV, choose comparison-before.csv, and select Import for review. Wait for Imported locally.
  3. Select Retain current import as before. The message confirms the retained row count and the original source digest. A digest identifies bytes; it does not authenticate a bank. All accounts in that import are retained, regardless of the account dropdown.
  4. Choose comparison-after.csv and select Import for review again. Changing the file clears the current view while leaving the explicitly retained import available.
  5. Select Compare retained import. A separate window shows both imported sides. For these examples, expect two changed pairs, one after-only row and one unidentified observation on each side. Identical unidentified rows stay separate.
  6. Choose a row to inspect its original index, ID, amount, currency, status, reference and description. Hide identical pairs filters only the view; it does not remove data.
  7. To save the comparison, choose a new private CSV filename in the export control and explicitly save. The CSV includes every comparison, even pairs hidden by the filter. Existing files are not overwritten.
  8. Return to the import window and select Forget retained import when finished. An already open comparison keeps its own copies. Closing the import window also closes its comparison windows and releases the retained data.

Clear report clears the current import. The separate Forget retained import action clears the before side. Retained data is held only in memory; it is not saved automatically and will not reappear after restarting the window.

Read the result correctly

ResultMeaning
sameMatching identifiers and all retained fields agree.
changedMatching identifiers exist, but at least one retained field differs. For example, a pending debit becomes booked. Amount spelling is separate from exact numeric value: 12.50 and 12.50000 are numerically equal but their spelling differs.
before-only / after-onlyA known identifier occurs only on that imported side. This is not evidence of deletion, a newly created bank transaction or a missing payment.
before-unidentified / after-unidentifiedThe transaction ID was absent. Descriptions, dates and amounts are not used to guess its identity.

The first side's original order is retained, followed by unmatched observations from the second side. The words before and after describe the sides you chose; the application does not prove chronology. IDs and timestamps compare exactly, including case and timestamp spelling. Currencies are not converted.

An import may contain only one page or an incomplete period. Previous/next page flags remain visible, but absent flags do not prove completeness. The review covers the selected fields retained by the importer; discarded provider extensions cannot be compared. Restored archive metadata is an unverified claim.

Understand the CSV

The first data row contains scope metadata. Each comparison then has a row for each present side. comparison_index links the pair; before_index and after_index refer to zero-based positions in the respective imports. A blank index means that side is absent. Both imports' page flags and the scope warning repeat on every data row.

changed_fields_mask adds these independent values when fields differ:

ValueField
1Exact decimal amount
2Amount spelling
4Currency
8Credit/debit direction
16Booked/pending status
32Mutability
64Booking time text
128Reference
256Information/description

For example, 48 is status plus mutability. A one-sided observation has mask zero because no pair exists to compare. Text that could be interpreted as a spreadsheet formula is escaped by the shared CSV writer. This report is a review export, not a statement CSV that can be re-imported.

Limits and recovery

  • Each import accepts at most 1,024 rows. The comparison can contain at most 2,048 entries.
  • Failed replacement imports do not replace the retained before side. Correct the file or mapping, import again, then compare explicitly.
  • Comparison and retention are unavailable while an import is still loading. Wait for its result.
  • Core CSV output is bounded to 4 MiB. The native exporter also limits text to 2,097,152 characters. An oversized export is refused as a whole; the native observation review stays available.
  • If a host changes a selection during display publication, choose the filter or row again. Closing a window retires its controls. An export already accepted may finish its immutable write.
  • Keep reports and snapshots in a private location. Account IDs, references and descriptions are included.

Use the C23 service

Include umicom/bank_feed/comparison.h and link Umicom::bank_feed. Call UmiBankFeedComparisonCreate with two accepted feeds, then read its summary and rows. The result owns copies, so the input feeds can be released after creation. Destroy the result with UmiBankFeedComparisonDestroy. The API performs no file or network operations.
