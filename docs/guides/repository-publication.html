Publish a workspace with Umicom

The native umicom repo publish-all command finds Git repositories in a workspace, publishes changed children, and then records those child revisions in their parents. The Framework owns discovery, ordering and publication policy; the command presents its results. Git and working authentication for each remote are required.

1. Prepare the workspace

Finish editing and review the files that belong in the public repository. Keep local notes, credentials and generated output outside source repositories or properly ignored. The command uses git add -A, which includes additions, modifications and deletions. Ignore rules do not protect files already tracked by Git.

Ordinary publication requires every managed checkout to be on main. A narrow, explicit recovery option described below can attach a clean detached leaf checkout that already contains exactly the published revision. Every checkout needs one origin whose fetch and push destinations identify the same repository. Use a credential-free HTTPS URL or the usual git@host:organisation/repository.git spelling and configure credentials through Git's credential helper. Registered submodules must already be checked out; publication does not initialise missing checkouts.

Choose a root that contains all related repositories and their Git metadata. Repositories are discovered immediately below that root and through their registered Git submodules. If the root is itself a repository, only that repository and its registered children are selected. Arbitrary nested source folders are not searched. Third-party submodules under third_party/, third-party/ or vendor/ retain their parent pins; the third_party/umicom/ namespace remains managed.

2. Preview

umicom repo publish-all "C:\umicom"

The preview fetches current origin/main metadata and lists changed paths and commits ahead of or behind the remote. It does not stage, commit, push, or change working files. A blocked checkout stops publication for the workspace before source changes are staged. Review every blocker before applying.

3. Publish

umicom repo publish-all "C:\umicom" --apply

The command displays a preview and performs a fresh preflight before applying. Keep editors and other Git processes idle until it finishes. Its sequence is:

  1. Acquire exclusive publisher markers in Git metadata. Fast-forward clean older checkouts and inspect the resulting repository graph again.
  2. Select one publishing copy for each remote. Publish dependencies before repositories that refer to them.
  3. Run the existing Framework submodule lock service for each parent after its children have been published.
  4. Stage with git add -A, check staged whitespace and known private paths, and commit only when the index differs from the current commit.
  5. Push the local main branch to remote main, using Git's submodule publication check. A previously committed change is pushed even when no new commit is needed.
  6. Fast-forward other clean copies of that remote and continue with their parents.
  7. Check the final working trees, child revisions and remote branches. Report completed actions and release publisher markers.

The default commit message is chore: update source, tests and public documentation. Supply a more specific message for a focused change:

umicom repo publish-all "C:\umicom" --apply --message "fix: repair archive regressions and bank test dependencies"

Repeating a successful invocation does not create empty commits. Publication is sequential across remotes, not an all-or-nothing transaction. If a later push fails, earlier successful pushes remain published and local commits remain available. The command never resets, cleans, stashes, rebases, force-pushes or creates a merge commit.

4. Monitor without publishing

umicom repo watch "C:\umicom" --interval 30

The foreground monitor prints a new report when the local snapshot changes. It uses cached remote references and does not fetch, stage, commit, lock or push. Press Ctrl+C to stop; a running bounded Git probe may finish first. Monitoring does not automatically upload edits while they are being written. Use publish-all --apply when the changes are ready.

Attach an already-published detached checkout

A submodule can show a detached HEAD: its current commit is selected directly instead of through a local branch. If its files are clean and that commit equals freshly fetched origin/main, preview the bounded recovery option:

umicom repo publish-all "C:\umicom" --attach-published-main

The report shows the branch and both revisions. Eligible leaf repositories have no managed children, an existing local main branch whose commits are all contained in the published commit, and no other worktree using main. A worktree is another checkout sharing the same Git repository. Dirty files, unpublished commits, an old detached revision, divergent history, a missing local main branch or a different named branch stop recovery.

After reviewing the complete workspace preview, apply recovery and the normal publication sequence together:

umicom repo publish-all "C:\umicom" --attach-published-main --apply

This command can publish other reviewed changes in the selected workspace. Attachment alone updates Git references and their reflogs, which record their previous values; it does not rewrite working files or the index. If main was an ancestor, its advance remains recorded even if the later attachment fails. Read the completed-action report and preview again. Keep other Git processes idle: the publisher marker coordinates Umicom publishers, not every external editor or Git process.

Use one authoring checkout for shared Framework source. Commit and publish there, then let clean copies receive that revision through checked fast-forward pulls. The parent lock records the resulting child commits. Recovery never chooses between independent edits or invents a resolution for a source conflict. The foreground watch command does not accept this option.

Resolve a blocked run

Message or conditionAction
Detached checkout or branch other than mainInspect git status and preserve any local commits. Decide which main history should contain them before changing branches. Publication does not choose that history for you.
Divergence, or local edits behind origin/mainReview the incoming and local changes together. The command stops rather than resolving a conflict or replacing files.
Several copies contain independent editsCompare the copies and integrate the intended source into one publishing copy. Clean copies can then advance to its published commit.
Private or generated pathReview the named file and move private material outside the repository. Previously committed material also needs review: deleting it in a later unpublished commit does not remove it from the earlier commit.
Missing submodule or changed .gitmodulesReview and complete repository registration separately before running workspace publication.
Authentication or push rejectionFix credentials or review the updated remote. Completed local commits are retained. Run a new preview before retrying.
Publisher marker already existsCheck whether another publisher is active. After a process interruption, inspect its output and Git state before manually removing only the stale umicom-publication.lock marker. Never remove an active Git lock.
A commit hook changed the reviewed treeInspect the local commit and hook output. The commit is retained without being pushed by this invocation.

Scope and limits

The filename policy blocks known working records such as Batch/Update documents, private tool folders, environment files and generated build output, including files found in unpublished commit trees. It is not a content or secret scanner and cannot identify every private sentence in an otherwise ordinary source file. Review remains necessary. It does not rewrite existing public history.

The bounded service supports 128 checkouts, 512 child relationships, 32 levels of nesting and inspection of up to 256 unpublished commits per checkout. Git output capture is bounded at 16 MiB per command. Paths through links or Git metadata outside the selected workspace are rejected. Git hooks and credential helpers execute normally; use trusted repositories. Filesystem edits by other processes are not a transaction with this service.

Applications can use umicom/repository/publication.h to present the same workflow on a worker thread. Allocate the report on the heap and keep borrowed request strings and cancellation state alive until the call returns. Existing single-repository commands retain their behavior.

Consistent updates and development commands

Automatic alignment uses explicit fast-forward-only pulls from origin main with rebase, autostash and recursive submodule checkout disabled. It checks the resulting commit against the reviewed revision and stops if the remote changes. Use umicom pull for a clean individual checkout; update commands leave nested checkouts untouched by default. See the development command guide for configure, build, test, installation, packaging, launch and complete output logs.
