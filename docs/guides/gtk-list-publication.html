Publishing a native file list

A file list displays a snapshot: the project, filter and file-index revision that were current when its rows were prepared. A native widget notification can run application code while rows are being removed or added. That code can close the window or select another project. Framework's UmiGtk4ListBoxPublish stops publication when the host reports that its captured snapshot is no longer current.

1. Prepare rows before changing the visible list

Include umicom/ui/gtk4/list_publication.h and link the GTK4 Framework target, Umicom::ui_gtk4. Create up to UMI_GTK4_LIST_PUBLICATION_LIMIT distinct widgets, taking a strong nonfloating reference to each with g_object_ref_sink. Leave them unparented. Ordinary labels or buttons are wrapped by GTK in list rows; explicit GtkListBoxRow widgets are also accepted.

Use an unbound list without native sorting. Filter and order the source records before creating widgets. Do not supply a native root, an ancestor of the list or the same widget twice. Invalid input is rejected before Framework removes existing rows.

2. Capture the host identity

Keep an independent context alive until publication returns. Its current-state callback should resolve a live host and compare the project session, query, page offset and data revision with the captured values. A strong reference to a window keeps its allocation alive; it does not prove that the window is still open. Check both lifetime and the application's current ownership.

/* The host owns capture and every row through this call.
 * CheckCapturedPage resolves its live host instead of retaining a raw owner. */
UmiStatus status = UmiGtk4ListBoxPublish(
    list, rows, rowCount, CheckCapturedPage, &capture);

The callback returns UMI_STATUS_OK only while the original page remains valid. Return UMI_STATUS_CANCELLED for a retired host or an appropriate non-OK status for a changed source. Do not mutate the same native list from this callback. Nested publication is refused with UMI_STATUS_BUSY.

3. Invalidate old row actions before publishing

Give each page an action identity owned independently of the application window. A row click must compare that identity and the captured workspace session before opening a file. Replace the list's action identity before publication starts. Do not treat a copied filename as authority to act on the currently selected project.

After the helper returns, resolve the host again before updating summary text or navigation buttons. Those setters can also emit notifications, so repeat the check between host-dependent operations. Mark the page rendered only when all required publication steps succeed.

4. Recover from cancellation

Preflight failures leave existing rows in place. Cancellation after removal begins can leave an empty or partial page. Framework does not roll back, retry, activate a row, move focus or restore selection. Invalidate the cancelled page's action identity and let the host take a fresh snapshot on its next refresh. Keep the last successful data snapshot separately from the native widgets.

The helper retains the list, the old rows and copies of the input widget references while observers run. The caller still owns its references and must release them. Unexpected row insertion or reordering returns UMI_STATUS_INVALID_STATE; it is not treated as a successful display.

5. Review the regression examples

tests/gui_control_checks/test_list_publication.c demonstrates preflight rejection, cancellation from real parent notifications, reentry, release of the caller's array, unexpected row changes and capacity limits. Its CTest names begin with framework.ui.list_publication.. A missing graphical display produces the explicit skip status 77; that is not evidence that native publication passed.

Studio's Explorer uses this service to keep workspace changes and page actions consistent. Applications remain responsible for their own source snapshots, authorization rules, refresh scheduling and visible recovery messages.
