Understanding verified CTest execution

Learn how to select the intended test, preserve its build context and distinguish a genuine pass from a skipped or unexecuted check.

1. A test process is not a test result

Suppose Umicom Notes has a test called notes.save. It checks that saving a note creates the expected file. CTest is the programme that finds and runs this test. CTest can also prepare a test environment, skip a test, run cleanup work and produce a report.

A successful exit from CTest is useful, but it does not by itself prove that the selected test ran and passed. A deliberately skipped test may not make CTest fail. Conversely, a test body can pass while required cleanup fails. The Framework therefore checks both the process result and a fresh report containing the selected test’s result.

Selected test → Framework CTest adapter → CTest → Fresh JUnit report → Verified Framework result
StateMeaning for an application
PassedThe exact selected test is reported as having run successfully, with no run-level failure.
FailedThe test, its surrounding run, or a required result-handling step failed.
SkippedThe test was deliberately skipped or disabled. It is not evidence of a pass.
Not runNo usable execution result exists, for example because an executable, selection or required fixture was unavailable.
Cancelled / timed outThe operation was interrupted or exceeded a time limit. Partial output is not a passing result.
Use the pass gate for acceptance decisions. UmiCtestResultRequirePassed checks the state, Framework status and process exit code together. Returning UMI_STATUS_OK from a run is not enough when the reported state is skipped.

2. Keep identity, build location and working location separate

A test name is literal text

Names such as notes.save[1]+ contain characters that have special meanings inside a regular expression. The Framework escapes those characters before passing an anchored selection to CTest. Selecting this name must not run a similarly spelt neighbour such as notesXsave1. Arguments are passed through the existing process API as separate values, not assembled into a shell command.

The build root owns the catalogue

The CTest build directory contains the generated test catalogue. A test’s WORKING_DIRECTORY is the location in which its executable should operate. These directories can be different. The adapter passes the build root to CTest and leaves the executable’s working directory, properties and fixture lifecycle under CTest’s control.

Framework metadata discovery already records the build root in the test item’s uri. Studio uses that value and the associated discovery record. It does not substitute another project’s most recently active build directory. The same discovery record supplies the selected configuration, such as Debug.

Identifiers are not display names

A short stable identifier connects a result to its catalogue record. The display name is the literal name CTest knows. Pass options.test_id when a display name does not fit the older identifier field. Names are bounded to 255 UTF-8 bytes; the identifier must fit the existing 160-byte field including its terminating zero.

3. Run an Umicom Notes test from C

Include the existing public CTest adapter header. The configuration and identity strings below are borrowed only during the synchronous call. The caller owns the result. Keep the build directory valid for the duration of the call.

#include "umicom/testing/ctest_adapter.h"
#include <stdio.h>

static int VerifyNotesSave(const char *buildDirectory)
{
    UmiCtestRunOptions options = {0};
    UmiTestResult result;
    options.configuration = "Debug";
    options.test_id = "umicom.notes.save";

    UmiStatus status = UmiCtestRunConfigured(
        buildDirectory, "notes.save[1]+", &options, &result);

    if (status != UMI_STATUS_OK ||
        UmiCtestResultRequirePassed(&result) != UMI_STATUS_OK) {
        fprintf(stderr, "The save check was not accepted.\n%s\n", result.output);
        return 1;
    }
    return 0;
}

The older umi_ctest_run entry point remains available and delegates to the same execution policy. The general-purpose test runner is also retained; applications should use the CTest-specific entry point for CTest suites.

Run an owned suite

UmiCtestRunSuite accepts an existing UmiTestSuite, caller-owned result storage and a summary. It preserves catalogue order and stable identifiers. Each selected test uses the same verified path as an individual run. A disabled catalogue record does not launch a process. A cancelled token prevents subsequent launches while preserving result slots.

Each enabled suite item uses its own CTest invocation. Required fixtures may consequently run again for another item. This is an integrity-first sequential suite API, not a new parallel CTest scheduler. The existing summary structure has no “not run” counter, so unusable execution results count as failed in this suite summary.

Choose timeout semantics deliberately

A CTest test property controls that test’s own timeout. The optional Framework timeout_ms limits the entire CTest invocation, including preparation and cleanup. Those limits are different. An enabled suite item’s nonzero Framework timeout overrides the suite-wide option.

4. Build and run the focused checks

Use an existing Framework checkout with CMake, Ninja and a C23-capable compiler. The runtime report option requires CTest 3.21 or later; the measured Linux checks accompanying this delivery used CTest 3.31.6. The focused CMake project compiles the real Framework adapter, process implementation, cancellation token and catalogue implementation.

In Windows PowerShell, run the following from the Umicom Applications workspace. These commands create a separate build directory and do not change the main application build.

Set-Location "C:\umicom\umicom-applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

cmake -S ".\framework\tests\ctest_execution" `
    -B ".\build\ctest-execution-checks" -G Ninja `
    -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw "CTest checks configuration failed." }

cmake --build ".\build\ctest-execution-checks" --parallel 2
if ($LASTEXITCODE -ne 0) { throw "CTest checks build failed." }

ctest --test-dir ".\build\ctest-execution-checks" `
    --output-on-failure --parallel 2 --no-tests=error
if ($LASTEXITCODE -ne 0) { throw "CTest execution checks failed." }

The tests create an inner disposable CTest catalogue under their own build directory. Some inner tests intentionally fail, time out or skip. The outer regression test passes only when the Framework recognises the intended outcome. The outer fixture lock prevents concurrently running checks from sharing inner CTest logs or sentinel files unsafely.

The standalone project is deliberately separate from the main workspace test catalogue. Run it explicitly; do not assume the normal workspace preset registers these new checks automatically.

What the checks exercise

The catalogue includes literal metacharacters, quotes, backslashes, spaces in build paths, configurations, a separate working directory, missing tests, missing executables, skips, timeouts and failing fixture setup or cleanup. A separate failure-injection executable replaces only the process boundary to test missing, malformed, oversized, duplicate and interrupted reports. A deterministic mutation test checks bounded parsing and preservation of caller output on errors.

5. Diagnose the first useful failure

SymptomWhat to check
No exact selected resultRefresh discovery. Check the literal name, configuration and CTest build root. Do not replace the root with the executable’s working directory.

Not run after setup failedRead the fixture’s failure. The selected body was blocked; correcting its body is not necessarily the solution.

6. Understand the boundaries

The report reader accepts a bounded CTest JUnit vocabulary, not arbitrary XML or every JUnit dialect. It rejects DTDs, unsupported processing instructions, invalid UTF-8, duplicate selected records and inconsistent structure. Reports larger than 8 MiB are rejected rather than partially interpreted. A separate temporary directory is created exclusively for each call; an old report is never reused. Cleanup removes only the report and directory it owns, not an unexpected directory tree.

Running a project’s tests executes its code with your privileges. A private report directory is not a security sandbox. Only run projects and toolchains you trust.

The current Windows process implementation uses CreateProcessA. The private report path is converted without best-fit substitution to its active code page, but this update does not provide general Unicode command-line support. The native Unicode-name execution case is explicitly disabled on Windows; UTF-8 parser tests remain enabled. ASCII build paths are the safest first validation path for the existing Windows adapter.

Framework cancellation targets the existing child-process boundary; complete descendant-process termination is not guaranteed. This update does not rework Studio’s GUI scheduling or wire a new mid-test Stop mechanism. Keep synchronous calls off a GUI owner thread through the application’s existing scheduling architecture.

Legacy text discovery and the metadata registry’s existing capacity limits are unchanged. This execution update does not claim to solve large-catalogue discovery, metadata streaming, or every Test Explorer presentation issue.
