Compare statement balances

Reconciliation compares recorded activity with a statement balance. The review does not move money, authenticate a bank account or change the practice ledger.

  1. In Trader, Bank or TMS, open Bank transaction reports.
  2. Choose a saved Open Banking transaction JSON response and select Import for review. This reader accepts the documented Open Banking transaction fields; arbitrary bank CSV and PDF statements need a separate converter. Select the required account and currency.
  3. Select Reconcile selected account. The new window owns a snapshot. Importing a different file later does not change it. Close and reopen the comparison to use fresh data.
  4. Enter the first and last booking dates as YYYY-MM-DD. Both dates are included. Use the calendar dates printed by the provider; timestamps are not converted to your computer's timezone.
  5. Enter the balance immediately before the first date and the reported balance after the last date. Use a dot decimal separator, with no currency symbol, thousands separator or exponent.
  6. Select Compare balances. Expected closing equals opening plus booked credits minus booked debits. Difference equals reported closing minus expected closing.
  7. Review pending entries, missing identifiers, mutable booked entries and previous/next-page flags. An arithmetic match alone does not establish a complete or authentic statement.
  8. Save the CSV to a private folder you choose. It includes the assumptions, comparison and selected period's transactions. Editing a date or balance disables the previous export until you compare again.

Work through an example

Choose the invented response at C:\umicom\Umicom-Applications\framework\examples\bank_feed\statement.json, select lesson-account | GBP and enter 2026-10-12 for both dates.

An opening balance of 100.00, a booked credit of 12.50 and a booked debit of 2.25 give an expected closing balance of 110.25. A pending debit of 999.00 is counted but excluded. If the statement closes at 110.26, the reported difference is 0.01.

When a comparison is unavailable

Check date spelling, account selection and amount precision. The reader allows at most 1,024 transactions in one saved response. Arithmetic uses checked decimal coefficients, not floating point. Very large totals are refused rather than rounded. Reports are never partially exported after a calculation failure.

Data and ownership

Each account and currency is compared separately. There is no foreign-exchange conversion, automatic pagination or bank login. The local file is the evidence source; no provider URL in that file is followed. Closing the source window closes its comparison windows. Closing a window prevents new exports but does not undo a file write already accepted.

Import a prepared CSV statement

The same window also accepts an explicitly formatted CSV. Select Statement CSV before importing. Follow Import a statement CSV for its nine columns, signed amounts, invented example and error recovery. The JSON instructions above remain supported. Arbitrary provider CSV and PDF layouts still need a separate converter.

For contributors

The portable contract is umicom/bank_feed/statement.h. Applications call the common GTK report launcher. Extend the shared selector and report together so arithmetic and exported rows always use the same account, currency and booking-date rules. Regression cases live in tests/bank_feed/test_statement.c and tests/bank_feed/test_statement_native.c.

For provider CSV layouts that need explicit column choices, select CSV with custom columns and follow Match statement CSV columns. Daily review uses the same imported observations for JSON, prepared CSV and mapped CSV.

Inspect daily balances

  1. Import examples/bank_feed/daily-statement.csv using Statement CSV. Select practice-account | GBP and open Reconcile selected account.
  2. Enter 2026-10-10 through 2026-10-13, opening 10.00 and reported closing 3.00. Select Compare balances.
  3. Read Daily balance trace and CSV. The days appear in date order, even if the source rows arrived in another order. Pending entries are counted but their amounts are excluded.
  4. Use the export below the daily view to save statement-daily-balances.csv. The original export above the view remains the transaction comparison report.
  5. After editing any date or balance, compare again. Both exports are disabled and the daily view is cleared until the new assumptions have been reviewed.

The minimum is -5.00 on 11 October. The supplied opening participates in the minimum and first-negative calculation. A negative result describes these assumptions and imported entries; it is not a bank-confirmed balance or an overdraft decision.

Only dates with selected observations have rows. A missing date carries the preceding calculated balance; it does not mean zero or prove that the source is complete. Daily grouping uses the provider's written date. Credits and debits within a day are combined, so the report does not describe intraday lows, transaction ordering or future cash movements.

Read the daily CSV

The export contains an opening row, one row per observed date and a closing row. Daily counts and movements describe that date; the closing row carries the period totals. Every row repeats the account, currency, selected period, supplied balances, arithmetic difference, pagination flags and report limitations. Keep this file private: it contains account data.

Amounts are exact decimal text. Import amount columns as text to retain their written precision. The common CSV writer adds an apostrophe to formula-like text, including negative text amounts, to prevent spreadsheet formula execution. Do not treat this report as a ready-to-post bank import.

If a daily intermediate balance exceeds the decimal range, no partial daily report is offered. A valid aggregate comparison can remain available: a final total may fit even when an earlier daily balance cannot. Narrow the period and supply its correct opening balance, or review the source amounts. The program does not round or silently omit entries to force a result.

Extend the daily report

umicom/bank_feed/statement_timeline.h provides an immutable snapshot owned by the caller. It reuses the existing statement selection and aggregate rules. Release it with UmiBankStatementTimelineDestroy; creating or exporting it performs no file or network operation. The native review uses the same API and revokes exports on edits and close. Portable and GTK regressions are in tests/bank_feed/test_statement_timeline.c and tests/bank_feed/test_statement_timeline_native.c.

Save a comparison you can reopen

A transaction CSV is useful for inspecting rows. A reusable statement review also retains the account, currency, dates and supplied opening/closing balances used in a comparison.

  1. Import your statement and select Reconcile selected account.
  2. Enter the period and balances, then select Compare balances. A mismatch can be saved too; it is an observation to investigate.
  3. At the bottom of the comparison window, use the reusable review export. Choose an absolute, new private filename such as C:\umicom\_local\statements\review.json. Create the containing folder first. Select its save action and wait for the result.
  4. In Bank transaction reports, choose Umicom statement review archive, select that saved file and choose Import for review.
  5. The imported observations appear in the report and a separate comparison opens with the saved dates and balances. Its totals are calculated again. Changing the source-file selection later does not change this independent comparison.
  6. Edit any date or balance to explore another assumption, then compare again before saving. Use another filename to retain both reviews: existing files are not overwritten.

The archive contains all accounts in the original import, including rows outside the selected period. Keep it private. It preserves known source format and a claimed source SHA-256 digest, but neither the archive nor that digest authenticates a provider. Mapping settings, source paths and discarded provider extensions cannot be recovered. Decimal scales are retained; spacing, redundant signs and leading zeros in entered balances are replaced by canonical decimal text.

Recovery and limits

  • A malformed or unsupported review is refused. No partial comparison opens and no ledger posting occurs. Select the correct file format and retain the original file for inspection.
  • A changed path, changed format or closed import window invalidates an outstanding load. Wait for the worker to finish before starting another import.
  • Editing a comparison revokes all three exports: aggregate CSV, daily CSV and reusable review. A save already accepted by the export service contains the earlier immutable snapshot and may finish.
  • The observation archive remains bounded at 4 MiB and 1,024 rows. The review envelope permits another 4,096 bytes for scope. Native export additionally limits text to 2,097,152 characters. If an archive cannot fit, an otherwise valid arithmetic comparison remains visible.
  • Reopening is a calculation over retained observations. It does not prove statement completeness, source integrity, settlement, permission to transact or reconciliation with a ledger.

Reuse the C23 service

Include umicom/bank_feed/statement_archive.h and link Umicom::bank_feed. Create an owned review with UmiBankStatementArchiveCreate, read copied fields with UmiBankStatementArchiveRead, and release it with UmiBankStatementArchiveDestroy. Encode/decode do no file I/O. Free encoded bytes with UmiBankFeedArchiveFree. Decode calculates totals from the stored observations; the file does not carry a trusted success flag.

examples/statement_review is a complete installed-SDK consumer. Its roundtrip case expects a zero difference; mismatch expects 0.01. Both retain a pending debit while excluding it from booked movement. The native importer and comparison window use these same shared services.
