Why the metadata catalogue is different

A test catalogue is the list of tests that CTest knows about in one configured build. It is not the record of which tests passed. Umicom Notes may have a few tests; the Framework workspace can have thousands. Losing entries during discovery makes later results misleading even when individual test execution is correct.

This provider extends the existing test_platform/ctest.c implementation. The legacy text-listing adapter remains separate and bounded. Studio’s existing metadata command calls the JSON provider through Framework services.

Trusted configured build→CTest JSON output→Bounded byte capture→Validated staged registries→One successful publication

The caller keeps input strings, registries and cancellation token alive for the call. Supply an absolute configured build root when the application may later change working directory; this provider preserves the supplied root and does not introduce another path-normalisation implementation. The owner must serialise access to all three registries. The final swaps cannot fail or allocate, but this is failure-atomic under owner serialisation, not a lock-free or concurrent-reader transaction.

No new process runner, application-level JSON model or persistence authority is introduced. New API names are additive; existing process and test snapshot layouts remain unchanged. Private implementation includes are compiled only through their owning C source.

What is preserved and rejected

Each imported test retains its name, enabled/disabled state, labels, timeout, display command, working directory and CTest build root. Source file and line are additionally obtained from the test’s direct backtrace node. CTest keeps authority over executing the actual argv, environment, fixtures and other runtime properties.

Short IDs keep the existing suite.name spelling. A longer representable name receives a bounded deterministic identifier. Duplicate names or ID collisions are rejected rather than overwriting another record. The hash is an identifier, not a cryptographic signature.

The command string remains a display projection, not an executable shell command or lossless argv serialisation. Labels keep the established semicolon display format. Other property values are checked for valid JSON syntax but are not stored in these snapshots. The provider does not claim complete validation of every unused backtrace edge.

JSON Unicode escapes and raw UTF-8 are validated. Embedded NULs in represented fields, overlong names, unrepresentable labels/commands/paths, duplicate known fields, unsupported versions and inconsistent configuration are errors. Timeouts use decimal-to-millisecond conversion with positive fractional milliseconds rounded up and overflow rejected.

Refreshing without destroying the previous catalogue

Parsing and capacity checks precede publication. Framework clones the item, suite and discovery registries, removes the selected suite in the copies and imports its new records. Only after every new record and provenance field succeeds are the copies swapped into the live registries.

A complete empty catalogue is a valid refresh: it removes obsolete tests while keeping a suite record. An unconfigured directory is not an empty catalogue; the live entry point requires a readable CTestTestfile.cmake. Refreshing another project cannot take over a suite ID already owned by a different project.

A failed allocation, malformed later record, truncated output, timeout, cancellation, process error or configured limit leaves all three original registries and their revisions unchanged. The failure summary is zeroed. This does not clear or migrate historical execution records in the separate result store.

Explicit limits

BoundaryCurrent limit / meaning
Item registry65,536 records including roots and all projects; grows on demand. This is the coded hard bound, not a claim that every frontend can display it.
Live JSON capture32 MiB default; caller may select up to 128 MiB. Entire JSON is retained for the bounded span parser.
Process duration120 seconds default; configurable. Existing runner timeout/cancellation polling remains in use.
Stored names255 UTF-8 bytes, not necessarily 255 characters. Larger names fail rather than truncate.
Labels / display command511 / 1,023 bytes respectively.
Paths / configuration1,023-byte paths and 127-byte configuration. Suite IDs are at most 117 bytes so the existing discovery prefix fits.
Legacy text discoveryUnchanged 1,024-case limit; this is not the scalable entry point.
Other consumersHistory, selection, result storage, UI hierarchy and rendering have separate existing limits.

If a capture allocation or byte limit fails, the sink records failure and discards later bytes while the existing runner reaches exit, cancellation or timeout. It does not claim immediate process-tree termination. Combined stderr/stdout contamination is rejected, not silently stripped.

CTest reads scripts in the configured build root even in list-only mode; discover trusted projects. This is not an untrusted-build sandbox.

Use the configured discovery API

UmiTestPlatformItemRegistry *items = NULL;
UmiTestPlatformSuiteRegistry *suites = NULL;
UmiTestPlatformDiscoveryRegistry *discoveries = NULL;
UmiTestPlatformCtestImportOptions options = {
    .project_id = "notes",
    .suite_id = "notes.ctest",
    .configuration = "Debug",
    .build_directory = "C:/umicom/notes/build"
};
UmiTestPlatformCtestDiscoveryOptions limits = {0};
UmiTestPlatformCtestImportSummary summary = {0};
char diagnostics[2048];
UmiStatus status = umi_test_platform_item_registry_create(&items);
if (status == UMI_STATUS_OK)
    status = umi_test_platform_suite_registry_create(&suites);
if (status == UMI_STATUS_OK)
    status = umi_test_platform_discovery_registry_create(&discoveries);
if (status == UMI_STATUS_OK) {
    limits.maximum_tests = 20000U;
    limits.maximum_output_bytes = 32U * 1024U * 1024U;
    limits.timeout_ms = 120000U;
    status = UmiTestPlatformCtestDiscoverConfigured(&options, &limits,
        items, suites, discoveries, &summary, diagnostics, sizeof(diagnostics));
    /* Use summary only when status is OK. Otherwise show diagnostics and
       retain the caller's previous catalogue. Do not translate failure to PASS. */
}
umi_test_platform_discovery_registry_destroy(discoveries);
umi_test_platform_suite_registry_destroy(suites);
umi_test_platform_item_registry_destroy(items);

This is a call-site fragment inside a C function. Include umicom/test_platform/ctest.h. In a long-lived application the registry owner keeps the registries between refreshes instead of destroying them at the end of each call. Use the existing Master Controller / Slave Controller ownership and task services; do not call a blocking discovery on the GUI event loop and then describe it as asynchronous.

Qualification boundaries

The delivery’s focused Linux tests exercise a real 10,000-test CTest catalogue and independently compare every imported name, disabled state, timeout, source file/line, labels and working directory against CTest JSON. The previous 81 checks remain.

Native Windows/UCRT64 execution, complete Studio compilation/linking, GUI refresh/selection/cancellation, complete workspace regression, clean-machine installation and process-tree termination are not qualified by these tests.

Protocol basis: CMake’s CTest JSON object model. The exercised CMake/CTest version is 3.31.6; unsupported protocol versions fail explicitly.
