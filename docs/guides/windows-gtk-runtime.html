Diagnose GTK runtime failures on Windows

Umicom's native windows use GTK. GTK is a toolkit: it supplies controls such as text entries, menus and windows. A successful C compilation does not prove that the toolkit loaded by a running program has no defects. Investigate the application's source and its runtime dependencies together.

Understand the three identities

Build configuration        Application process              Test evidence
package metadata     →     executable + loaded GTK DLL  →   version, backend, result
headers and libraries      selected when the process starts  actual behavior

A DLL is a shared library loaded into a Windows process. Package metadata describes the libraries the build discovered. A copied application can load a different DLL from its own directory, so changing the toolchain's package does not automatically replace every installed application's runtime.

  1. Save the complete failing test or application output, including the exception and the action immediately before it.
  2. Read the GTK runtime version printed by native qualification tests. The TMS host tests also print their header version and display backend. The header version describes compilation; the runtime version comes from the loaded toolkit.
  3. Inspect the runtime copies beside the executable and compare their origins with the toolchain package. Retain file hashes when comparing two deployments.
  4. Rebuild or reinstall through the repository's normal workflow after selecting a verified dependency package. Re-run the failing workflow with the intended runtime.

Windows input-method disposal advisory

An input method helps turn keyboard input into text, including composition and language-specific input. GTK's Windows implementation registers a callback for native input messages. A callback is a function the operating system can invoke later. If its associated input context has already been destroyed, invoking that callback can access an object that is no longer valid.

The GTK 4.24.0 and 4.24.1 release sources lack an upstream correction that removes this callback during context disposal. A matching diagnostic can mention gtk_im_context_ime_message_filter and GTK_IS_IM_CONTEXT_IME when a native window is closed or another window becomes active. This diagnostic supports investigation of the toolkit defect; it does not prove that every similar crash has the same cause.

EvidenceWhat it establishes
GTK package version 4.24.0 or 4.24.1The upstream release source needs review. A distributor may have backported a fix without changing this version.
Stable-branch commit 30727f8a524dbaa69118a60d6bbef4b3447245b1The upstream correction tracks the display that owns the message filter and removes the filter during disposal.
A vendor package containing that correctionThe package includes the source repair. Its loaded runtime and the application workflow still need qualification.
A successful rerun with identified runtime filesThe observed workflow passed in that environment. Other workflows remain separate coverage.

Review the upstream stable-branch correction and the vendor package's source or backport record. Upgrading to version 4.24.1 alone does not establish that this correction is included.

Framework reports the known-version advisory when its GTK adapter is configured for Windows. The check uses package metadata and leaves all tests enabled. An unlisted version receives no matching advisory; that is not a certification of safety.

Recheck the affected host workflow

From a configured Umicom Applications checkout, after building the changed targets and installing the intended runtime, run the focused host checks:

ctest --test-dir build/windows-ucrt64-all-debug --output-on-failure --no-tests=error -R "tms[.](forward_host|accounting_host)[.]independent$"

Both tests open independent native child windows, dispose one and inspect the surviving host. Preserve the printed toolkit version, backend and disposal-stage messages with the result. A missing display is a skipped test, not a successful host check.

If the exception remains, retain the new output and obtain a native debugger stack with the exact executable and DLL identities. Do not suppress GTK critical diagnostics or change the crash into a skip. Framework's early focus-release safeguard remains useful defensive behavior, but it does not replace the toolkit's responsibility to unregister its own callbacks.
