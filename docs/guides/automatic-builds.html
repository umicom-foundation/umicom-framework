Automatic builds and test selection

An incremental build keeps previously compiled work. The configured build generator follows source and header dependencies, recompiles the parts that need updating, and links the programs that depend on them. Keep the same build folder between runs so that this information remains available.

Automatic qualification adds a second decision: which tests need to execute. Framework retains an individual result for each supported self-contained test. A passing result can be reused while its built executable and recorded execution context remain unchanged. Reused evidence is reported separately from newly executed tests.

Use a configured project

  1. Configure and build the project once with testing enabled. The initial build creates the native command and test-receipt helper. A first qualification has no passing receipts to reuse.
  2. Use an installed Umicom command outside the build folder you are updating. On Windows, a running executable cannot overwrite its own program file. This also applies when using Studio to build Studio itself.
  3. Run verification for the existing project build folder. You select the project configuration, not individual targets or test names:
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\umicom\installed\applications\bin\umicom.exe" verify --source . --build ".\build\windows-ucrt64-all-debug" --config Debug

The installed command must include the automatic verification implementation. Stop on an error and read the reported log. The command uses the existing cache, refreshes configuration in supported Umicom build trees, builds incrementally, and runs the automatically selected tests. It never cleans the build directory.

Use Studio

  1. Open the project and select its existing build profile. The source and build folders belong to that project.
  2. Enable testing in the profile when you want Build to include test qualification.
  3. Choose Build or Test. Framework performs the work on Studio's existing worker, so Output, Problems, cancellation and operation history keep their existing behaviour.

Building a separate application against an installed SDK uses its installed libraries. Building a project that includes Framework source lets the generator follow those source dependencies. Automatic testing does not itself make every Framework source dirty.

First build and later builds

Studio fixes the execution plan when you start a request. If the build folder does not yet contain an automatic test driver, Framework runs Configure, Build and ordinary CTest in that order. A driver created by Configure becomes available for the next request; it does not start another build inside the current Test stage. If a driver is already available, that driver owns the complete automatic verification sequence.

A failed Configure or Build stops its later stages. Test failures remain failures in Output and operation history. Turning off testing in the profile requests Configure and Build only; it does not retain the previous request's test policy.

How a previous result is treated

Previous evidenceNext verification
Passing self-contained test; matching executable and execution contextReuse the historical result.
Failure, timeout, cancellation, skip, disabled or missing resultKeep the test selected; a skip is not a pass.
Changed executable, runtime dependency, CTest catalogue, environment or configured cacheInvalidate affected receipts; shared context changes conservatively invalidate all cached receipts.
New test, unknown inputs, external service, fixture or dependency groupExecute normally through CTest.
Interrupted run or invalid reportSelected tests remain due. Older passing receipts cannot silently replace an incomplete attempt.

Each test has its own outcome. One failing case does not discard unrelated unchanged passing receipts. The driver also consults CTest's latest failure lists so a failure seen outside the automatic workflow can override an older cached pass.

What is supported first

The in-memory snapshot contract cases are registered as self-contained tests. Their executable and linked runtime libraries contain their test inputs. The driver resolves and hashes those runtime dependencies; incomplete runtime information disables reuse. Most other suites retain ordinary execution until their complete inputs have been reviewed and declared. You do not need to maintain a list of changed files.

CMake and CTest 3.29 or newer are required for the generated automatic driver. Native Windows and Linux builds with an available runtime dependency scanner support receipt reuse. Other configurations preserve ordinary testing. Profiles with explicit presets retain their existing CTest preset semantics; automatic reuse is currently available through a resolved build-directory profile.

Projects using an installed SDK without a generated automatic driver also retain full CTest execution. Package, deploy and ordinary test commands keep their established full-qualification path. A full release test run remains useful for environmental and integration problems that cannot safely be cached.

Find the records

The command prints its verification log path. Automatic driver records live below BUILD/.umicom/qualification/CONFIG/. Every run keeps configuration and incremental-build logs, CTest discovery and the list of reused tests. When tests execute, it also saves their transcript and JUnit results. A run that reuses every result does not invent a new test report. receipts.tsv is a versioned table of test names, input digests and outcomes. The native parser rejects malformed or duplicate rows; an unreadable previous table widens selection instead of assuming success.

Records describe the executable tested, not subsequent edits to source files. Continue development in a separate checkout while qualification is running, or run verification again after editing the tested project. Before-and-after checks reject observable changes to the built artifacts and execution context.

Understand a full-test fallback

A test result is reusable only when its complete runtime inputs are known. A dependency scanner may report an unresolved library even though the operating system can launch the program. Windows API-set names, for example, are loader contracts rather than ordinary DLL files. Framework keeps every test selected when dependency resolution is incomplete; it does not ignore unknown libraries to obtain a smaller test count.

  1. Open the run folder printed by umicom verify.
  2. Read before.tsv.policy.txt. eligible permits comparison with previous receipts; it does not mean that every test is reusable. full keeps the complete suite selected.
  3. Read before.tsv.runtime.txt for the reason and the resolved, unresolved or conflicting dependencies. The file contains local paths, so keep it with private build logs.
  4. Resolve a missing runtime installation or dependency declaration, then verify again. Do not delete exclusions from the dependency scanner or label unknown inputs as self-contained.

The native receipt reader accepts LF and Windows CRLF line endings and exports canonical LF. It still rejects duplicate test names, damaged digests, embedded zero bytes and incomplete records. A rejected current manifest stops verification; damaged previous receipts cannot grant a test exclusion.

A successful fallback run qualifies the tests that actually executed. It does not demonstrate that acceleration is available on that host. Keep the transcript and report alongside the policy record when comparing build times.

Verify the executable behind a test

A test name and its declared target are different facts. The declaration says which executable a contributor believes owns the inputs. CTest discovery says which program will actually run. Framework compares those facts before it can reuse a pass. If a test has been redirected to a wrapper, renamed executable or different target, the complete run remains selected.

  1. Find discovery.json.owners.log in the automatic run folder.
  2. A successful check reports the number of closed-input executable bindings examined. This validates command identity only; runtime dependencies and previous outcomes still have to qualify.
  3. If an identity or program differs, inspect the test's add_test command and its umicom_test_closed_inputs declaration together. Correct the declaration or remove eligibility when the command now depends on a wrapper or external inputs.
  4. Run verification again. Do not edit the generated registry or old receipt files to make a mismatch disappear.

The native catalogue parser builds one owned catalogue from the complete JSON document, retains decoded test names and executable paths, and uses sorted identities for lookup rather than reparsing the document for each registration. Missing commands, duplicate names and malformed records cannot authorize exclusions. Paths must be absolute and match the discovered spelling; Windows slash spelling is normalized, but letter case is not folded because individual directories can be case-sensitive. Equivalent aliases can conservatively cause a full run.

Recover from an incompatible receipt helper

The driver and native helper share a command protocol. Protocol 3 includes executable ownership verification and process-aware result recording. Before reading previous results, the driver asks the executable for its protocol version. A usage message or an older version stops automatic verification before any saved pass can exclude a test.

  1. Read receipt-helper-protocol.stdout.txt, .stderr.txt and .result.txt in the reported run folder. The current helper must report UMICOM-TEST-RECEIPTS 3 and exit successfully.
  2. Finish integrating the complete source update before starting qualification. Do not replace source files during the build being measured.
  3. Configure the existing build folder again, then build umicom-test-receipts. Its content fingerprint covers the adapter and local includes even when copied files retain older timestamps.
  4. Retry verification after that build succeeds. Keep the earlier logs so the executable that failed compatibility remains identifiable.

The legacy record STATE JUNIT interface remains available for callers that have already checked successful runner completion and stable inputs. Automatic verification uses record-result STATE JUNIT success|failure explicitly. A protocol match is a prerequisite, not a passing test result.

Read individual results after a failed runner

CTest's process result describes the invocation as a whole. A JUnit report describes individual test observations. A report can contain passing rows while CTest returns an error. The automatic driver keeps the original report and its failure details, but conservatively leaves fresh passes from that unsuccessful invocation due for another run.

ObservationSaved reuse state
Runner succeeds; inputs stay stable; reported test passesThe pass can be compared with unchanged inputs on the next run.
Runner fails or its completion is unknown; reported test passesKeep the test due. The report still shows the individual observation.
Reported failure, timeout, skip, disabled or not-run resultRetain a nonpassing outcome. No test exclusion is granted.
Older eligible pass was excluded and is absent from this reportKeep that historical receipt independently.
Report is malformed or input identity changes during executionStop without admitting fresh passes. Keep the logs for investigation.
  1. Read the CTest exit result and results.xml together. A passing row alone cannot make the whole invocation successful.
  2. Fix the reported failure, or investigate why the runner stopped. Do not manually change receipt outcomes to obtain a smaller selection.
  3. Run verification again against stable files. Tests selected during an unsuccessful invocation can run again even when their individual rows previously passed. Older excluded passes can still be reused if their inputs remain valid.

This policy favours a conservative retry over maximal reuse after an unsuccessful invocation. It does not erase the previous report or describe an observed individual pass as an assertion failure.

Why a build can still be large

A shared header or compiler-option change may affect many source files. Framework currently also exports a public-header fingerprint to protect against timestamp-preserving file copies. Changing a public header can therefore cause broad recompilation. The automatic test driver preserves this safeguard. Replacing it requires dependency-complete content tracking, not simply disabling freshness checks.

A new compiler is not required for incremental builds. Framework coordinates the existing compiler, generator and CTest while retaining evidence. Compiler development is a separate project; it would still need correct dependency tracking and test-input contracts.

Declare another eligible test

Contributors may register a test only after checking that it reads no external files, plugins, network services, clocks, mutable fixtures or undeclared state. Runtime-linked libraries are fingerprinted automatically. Tests with fixture, environment, resource or ordering requirements are excluded from reuse by the final registration check.

add_test(NAME example.value-rules COMMAND example-value-tests)
if(COMMAND umicom_test_closed_inputs)
    umicom_test_closed_inputs(example.value-rules example-value-tests)
endif()

Do not apply this declaration to an entire directory merely to reduce test counts. Missing knowledge must result in execution. Adding a new input to a previously self-contained test requires removing or extending its reuse contract before accepting cached results.
