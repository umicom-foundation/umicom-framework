Open and edit local record notes

The Framework record editor provides a native GTK4 text surface over the shared draft service. A product supplies its title, description and record namespace. Framework owns database access, revision checks, the editable draft and background storage work. Healthcare composes this editor in its Review notes tab beside its existing Access exercise.

This is a local notes workflow for fictional exercises. It is not a clinical record system, a banking ledger, a sign-in service or encrypted storage. Reviewer names are attribution labels. Applications must provide their own authenticated access policy before using the service with restricted information.

Save and reopen a fictional note

  1. Open the Healthcare application and choose Review notes, or launch the SDK example below.
  2. Enter an absolute database filename in a directory you control, such as C:/umicom/_local/record-notes.sqlite3. The directory must already exist. The file can be new or an existing compatible Umicom Data Server database. Use a dedicated file for the exercise.
  3. Select Open or create database. Choosing a filename alone does not create a file. Wait for the database-ready message. This editor keeps that database until it closes.
  4. Enter practice-one as the record key and select New draft. The application namespace is added automatically. New draft does not query storage; attempting to save an already-used key is refused by the revision check.
  5. Enter fictional text, a reviewer name and a reason for the revision. Select Save revision. A saved message means the captured text was committed. You can continue typing during the write; newer text remains marked as unsaved.
  6. Close after all saves complete and the draft is clean. Reopen the application, choose the same database and key, then select Open record. Expect the last saved text and revision to appear.

The editor accepts UTF-8 text up to 16,384 bytes. Some characters use multiple bytes. Larger visible text remains available to shorten or copy; it cannot be saved or silently treated as clean. Stored binary records and invalid UTF-8 are refused without replacing the current draft.

Review another writer's changes

  1. If Save reports a changed stored revision, keep your draft. Select Compare stored text. The lower read-only pane shows a separate stored snapshot and its attribution; your draft stays editable above it.
  2. Read both versions and edit your draft to include the text you intend to retain. Comparing alone does not change which revision the next save expects.
  3. Select Keep my draft against this revision only after review. This chooses the shown snapshot as the baseline and leaves your draft text unchanged. It does not merge text or write to storage.
  4. Select Save revision to append your reviewed draft. If storage changes again, the save is refused and you can compare again. Earlier stored revisions remain available through the record-document API.

Discard local edits restores the chosen saved baseline, including an explicitly adopted comparison snapshot. For a new unsaved record it closes the draft. Opening another record refuses unsaved changes. The host's close guard asks you to save or discard and waits for active storage work. There is no crash recovery for unsaved drafts.

Browse earlier amendments

  1. Expand Amendment history and select Refresh history. Each page shows at most 16 revisions, newest first, with reviewer, source, reason and recorded timestamp.
  2. Select Older revisions to continue. If another writer advances history, refresh from the new head rather than silently mixing pages from different heads.
  3. Enter a positive revision number from the history and select View historical text. Its content appears in the read-only review pane. Your editable draft and save baseline stay unchanged.
  4. Use Compare stored text again when preparing a save against the current stored revision. Historical viewing cannot choose an older save baseline.

History pages inspect metadata, not the entire payload chain. Reading a selected document verifies that document's content. See the shared paging API for head checks and transaction guarantees.

Compose the editor in a native application

  1. Link Umicom::record_editor_gtk4 and include umicom/ui/gtk4/record_editor.h. Build with GTK4 and the SQLite Data Server provider for local persistence.
  2. Call UmiRecordEditorGtk4New on the GTK thread with a title, description, nonempty namespace prefix and source label. It copies the strings and returns a floating widget on success; parent it in a window or container.
  3. Connect the window's close-request signal and return the inverse of UmiRecordEditorGtk4RequestClose. The installed example demonstrates retaining the editor for that signal connection and releasing the reference with the closure.
  4. Keep the process and owning GLib main context alive while UmiRecordEditorGtk4Busy is true. Removal, disposal or explicit retirement prevents new actions and late reads from updating the closed surface. It does not cancel a database write already accepted.
  5. Create a new widget when changing database or attaching to another root. Unrooting permanently retires its action authority, including controls another object retained.

The implementation dispatches owned snapshots to GTask workers. Workers never read widgets or a mutable draft. Completion returns to the owning main context; observer callbacks may remove the host, so subsequent widget access checks retirement. Forced process termination can interrupt work and is not equivalent to an orderly close.

Build the installed SDK example

Install a GTK-enabled Framework SDK containing record_editor_gtk4, its data and UI dependencies, and SQLite support. Copy share/umicom-framework/examples/record_editor into your own example workspace. From that copied directory run the following, stopping if a command fails:

cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH="C:/umicom/installed/applications" -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe"
cmake --build build --target umicom-record-editor --parallel 2
& ".\build\umicom-record-editor.exe"

Keep the UCRT64 GTK runtime directory on PATH when launching on Windows. The example opens the Local record notes window; use the fictional workflow above. It has no automatic connection and does not create a database until you choose the action.

Troubleshooting

SymptomNext step
Database unavailableUse an absolute file path in an existing writable directory. Confirm SQLite support is built. Do not select an unrelated application's database.
Save refusedCheck reviewer and reason fields, text size and the status message. For a changed revision, use the comparison workflow. For an I/O error, keep the draft and inspect storage before retrying; a missing reply does not prove a write never committed.
Comparison failsThe key may not yet exist, storage may be unavailable, or the stored content may be binary. Your draft remains available. Comparing a new unused key normally reports not found.
Cannot close or open another recordWait for active storage work, then save or explicitly discard local edits. Oversized visible text also counts as unsaved.
Native tests report skippedGTK could not initialize a display. Run the GUI coverage in a desktop session. A skipped case has not validated the workflow.
