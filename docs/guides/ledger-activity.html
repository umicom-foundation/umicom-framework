Calculate posted account activity

Account activity is the movement recorded by posted journals during a chosen date range. The Framework calculates it from a complete local journal book and chart of accounts, using integer minor units. Bank, Accountant and TMS hosts can call the same service instead of writing separate arithmetic and date filters.

This result describes the supplied book. It does not prove that the book contains every external transaction. It also does not add an opening balance or convert currencies.

1. Check the inputs

  1. Use a book containing complete, balanced journals marked as posted. Drafts, duplicate journal identifiers and malformed counts are refused.
  2. Supply the chart that identifies every account referenced anywhere in the book. A missing account is refused even if its journal is outside the requested dates.
  3. Establish one currency and minor-unit convention for the entire book. These journal containers do not store that metadata.
  4. Choose two valid financial dates, with the first no later than the last. Both endpoints are included.

An account can disallow new posting while retaining historical activity. The service validates the account, but does not discard its past entries because its current posting permission is false.

2. Capture the calculation

#include "umicom/finance/accounting/ledger_activity.h"

UmiAccountingLedgerActivity *activity = NULL;
UmiStatus status = umi_accounting_ledger_activity_create(
    book, chart,
    (UmiFinancialDate){2026, 10U, 1U},
    (UmiFinancialDate){2026, 10U, 31U},
    &activity);
if (status == UMI_STATUS_OK) {
    const UmiAccountingLedgerActivitySummary *summary =
        umi_accounting_ledger_activity_summary(activity);
    for (size_t i = 0U; i < summary->account_count; ++i) {
        const UmiAccountingLedgerActivityRow *row =
            umi_accounting_ledger_activity_at(activity, i);
        /* Present row->account, totals and normal_net_minor here. */
        (void)row;
    }
}
umi_accounting_ledger_activity_destroy(activity);

Call while your application owns serialized access to the inputs. The successful result contains its own copies: later edits to the book or chart do not change it, and the inputs can be released after the call. Rows and the summary are borrowed from this result and remain valid until it is destroyed.

3. Interpret the result

ValueMeaning
scanned_journalsAll journals validated in the supplied book.
selected_journals, line_countWhole journals and their lines selected by the inclusive date range.
account_count, active_accountsAll chart accounts, and accounts with at least one selected line. A zero net does not necessarily mean no activity.
debit_minor, credit_minorSeparate exact nonnegative totals for each row and the whole selected range.
normal_net_minorDebit minus credit for a debit-normal account; credit minus debit for a credit-normal account. Opposite-side movements can make this negative.

Rows retain chart order, including accounts with no selected lines. Use umi_accounting_ledger_activity_find for exact account-ID lookup. Unknown, empty or malformed IDs return null; matching is case-sensitive.

If you need a closing account balance, supply a separate, verified opening balance and the correct historical coverage in a higher-level financial service. Do not rename an activity total as a closing balance.

4. Try the installed example

The journal batch example posts two local practice journals. After installing the finance SDK and learning examples, use an absolute SDK prefix and a separate build directory:

cmake -S "C:/umicom/installed/finance/share/umicom/examples/journal_batch" -B "C:/umicom-build/journal-batch" -G Ninja -DUMICOM_SDK_PREFIX="C:/umicom/installed/finance"
cmake --build "C:/umicom-build/journal-batch"
ctest --test-dir "C:/umicom-build/journal-batch" --output-on-failure --no-tests=error
& "C:/umicom-build/journal-batch/journal-batch.exe" activity
& "C:/umicom-build/journal-batch/journal-batch.exe" activity-range

Stop on any failed command. The activity mode prints 2000 GBP minor units for both accounts' normal-side activity. The activity-range mode excludes the posted date and prints zero for both accounts. Both retain the accounts in their output.

Recover from a refusal

  • INVALID_ARGUMENT: check input pointers and both dates.
  • INVALID_STATE: inspect the whole chart and book for malformed, duplicate, unbalanced or non-posted records.
  • NOT_FOUND: an account referenced by a stored line is absent from the chart. Restore the account identity; hiding the journal with a date filter does not repair the reference.
  • CAPACITY_EXCEEDED: a public count is invalid or a debit/credit total exceeds signed 64-bit capacity. A small net does not make an overflowing gross total safe. Do not clamp or silently drop rows.
  • OUT_OF_MEMORY: no result was published. Release unused application state and retry when resources permit.

Every refusal leaves inputs unchanged and returns a null activity pointer. No file, provider call, payment, approval or new posting is performed.
