Share argument boundaries across program launches

Framework's base argument parser lets build runners, debugger adapters and language servers agree on where each argument begins and ends. It never invokes a shell. Applications collect settings and use the shared resolver instead of carrying their own parsing rules.

Use a build profile

  1. Initialise UmiBuildProfile with umi_build_profile_init.
  2. Set run_program and either run_argument or run_arguments. The first is a single literal value; the second uses the quoted grammar. Do not fill both.
  3. Validate the complete profile. Use UmiBuildProfileArguments to obtain its effective vector. A failed resolution clears the argument output.
  4. The CMake Run provider copies that vector into its owned command record. A debugger host passes it to UmiDebugRuntimePlatformLaunchArguments. The native launcher formats the vector losslessly before using the existing adapter and DAP lifecycle.
  5. Keep execution permission and project lifetime checks in the owning workflow. Resolving an argument list grants no permission to run it.

Grammar and ownership

--file "notes for review.txt" "" 'literal $HOME'

The result contains four arguments. Quotes group text, and an empty quoted string preserves an empty value. A backslash escapes quotes, backslashes and whitespace; otherwise it stays literal. No wildcard, environment-variable or command expansion occurs.

UmiArguments owns bounded text cells and pointers into those cells. Do not copy the pointers and then discard the record. Copy strings into the receiving owner's storage, or parse directly into its record. Input and output storage must not overlap. The language-server wrapper retains its established public structure and rebinds all copied pointers before returning.

UmiArgumentsFormat turns a vector into reversible quoted text. It measures the complete result before writing and clears the output on failure. This representation is intended for saved settings and review, not for a shell command.

Persistence and limits

Build profiles retain all previous member offsets and append the list field. Rebuild consumers against the matching header; the public structure is larger. The existing Data Server transaction saves the complete profile and its revision together. Earlier records without a list are loaded with their literal argument intact. A current record missing the list field is rejected as incomplete.

The base parser accepts at most 32 arguments of 1,023 bytes each. Build profiles apply their narrower command-cell limit of 511 bytes per argument and a 1,023-byte list field. Native debugger launch evidence also has a 1,023-byte text limit after quoting. Overflow is reported before starting an adapter.

Extend the workflow

A new frontend should bind its fields to the profile, preserve the legacy literal field, and surface validation errors beside the inputs. A new debugger should accept a vector rather than parse an application-specific string. Extend the shared grammar only with regression coverage for spaces, quotes, empty values, Unicode, Windows paths, capacity failures and pointer ownership.

The examples and regression source use production Framework APIs. Their presence is not a compiler, GUI or installed-debugger qualification result.
