Rename a project file or folder

Explorer can change the name of an existing file or folder within its current parent. The operation keeps file contents and refuses to replace a destination. It uses Framework workspace services, so other native applications can adopt the same rules.

  1. Open your project and enable its local editing trust only when you control the project files.
  2. Finish any running Studio build. Close source tabs for the entry you want to rename, including tabs beneath a folder. Save or discard each draft deliberately when closing; Rename does not make that decision.
  3. In Explorer, choose Rename…. Enter the current path relative to the project root, such as src/parser.c.
  4. Enter just the new name, such as reader.c. Do not enter a different folder. Select Rename once.
  5. Read the result. A successful rename requests an Explorer refresh. If refresh could not start, use Refresh after the current refresh completes. Do not repeat the rename.
  6. Open the renamed source and update references yourself. For example, change src/parser.c to src/reader.c in your CMake source list. Include directives and imports are not rewritten automatically.

When a rename is refused

An existing destination remains unchanged. Choose a different name. A busy result can mean an affected tab is still open, a build is active, or the workspace changed. Close the form and reopen it after resolving the cause. An old form cannot act on a newly opened project.

Parent traversal, repository metadata such as .git, device names and invalid portable filenames are refused. Registered project roots and folders containing them need a separate project relocation workflow. Source links and linked parent folders are not followed.

Framework integration

Call UmiWorkspaceRenamePreview with the current graph revision to obtain the two absolute paths. Use UmiDocumentCoordinatorPathInUse to check both paths against all open documents. On the owner thread, exclude active builds and call UmiWorkspaceRenameEntry. Its renamed result remains authoritative if closing an operating-system handle or a later index refresh fails. Neither function saves, closes or retargets documents.

Windows uses a held source handle and FILE_RENAME_INFO with replacement disabled. Linux uses descriptor-relative renameat2 with RENAME_NOREPLACE. Other hosts or unsupported filesystems return NOT_IMPLEMENTED; there is no copy-and-delete fallback.

This is a local editing operation, not a filesystem sandbox. Keep project directories under your control and avoid external source or parent renames at the same time. Linux checks the source name before the rename; it does not lock that name to an inode against a competing process. Path checks do not discover every hard-link alias. No Git staging, commits, pushes or build execution occurs.
