Inspect affected builds and tests

An incremental build reuses outputs whose inputs have not changed. Selecting tests is a different job: a change to a shared library can affect applications and tests that depend on it. Umicom's impact command previews this relationship using a configured build inventory.

This command is a preview. It reads selected metadata and, when requested, Git status. It does not configure, compile, run tests, install software, change branches or publish commits. A preview is not qualification evidence. The source tree and build metadata must describe the same configuration.

For a practical component build and test cycle, see Build and test a changed component. That explicit execution workflow is separate from this impact preview.

1. Capture the configured inventory

From a Framework source checkout, configure the desired preset with inventory capture enabled. Keep build output separate from source and do not reconfigure the same build directory concurrently.

cmake --preset windows-ucrt64-debug -DUMICOM_RELEASE_INVENTORY_CAPTURE=ON

The generated file is normally build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv. Use the actual build directory and configuration shown by CMake. A parent Applications build has its own inventory under that parent's build directory; its paths are relative to that parent's source root.

2. Preview working changes

Run the newly built native command with an absolute inventory path. Replace the example root with your checkout. The command observes staged, unstaged and untracked changes. Renames contribute both old and new paths. A changed submodule requests a full selection; the child repository must also be qualified separately.

umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --working-tree

Git status describes current uncommitted changes. To include committed changes, add --since COMMIT, replacing COMMIT with the full commit ID recorded by your last accepted qualification run. Umicom compares that immutable ID with the observed HEAD and includes current working changes. It prints both commit IDs. A short ID, branch name, missing object or conflicted working tree is refused. The commit comparison requires Git support for --no-lazy-fetch; unsupported Git versions fail rather than downloading missing objects. Replacement refs are disabled for this comparison so they cannot substitute different content for the recorded IDs.

A baseline identifies which source differences to consider; it does not prove that the baseline passed, that the inventory is current, or that the source stayed unchanged during discovery. Keep the qualification evidence for that baseline. Without one, supply affected paths explicitly or request --full. --since implies working-tree discovery and cannot be combined with --changed.

umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --changed src/example.c --changed include/umicom/example.h --expression

Paths supplied with --changed are relative to the inventory's source root. For a rename, supply both names. Do not combine explicit paths with --working-tree. --git PROGRAM selects the Git executable for working-tree discovery.

3. Read the selection

ReasonMeaning
changed-sourceA changed file belongs to this target.
dependentThis target depends on an affected target.
test-ownerA selected target is a declared prerequisite of this test.
test-prerequisiteThis target must be built for a selected test, even when its own source did not change.
related-testThis test belongs to the selected setup, cleanup or ordering group. Its own declared build targets are included too.
alwaysThe test is explicitly required whenever there is selected work.
full-selectionKnowledge is incomplete or broader coverage was requested.

Missing test owners, unresolved source paths or dependency expressions, imported interfaces with unrepresented dependencies, unknown test dependencies, unrecognised changed files and CMake configuration changes widen the selection. Older inventories without impact metadata also widen coverage. Full selection is an honest fallback; adding precise declarations can make later previews narrower.

--expression emits an anchored regular expression for the exact selected test names when a narrow expression can be represented within the limit. It escapes regular-expression characters. This output is data, not shell-quoted command text. Full selections, empty test sets, control characters and excessive size do not emit a narrow filter. Never substitute an empty filter and call it a focused check.

4. Declare test prerequisites

Include the shared helper before declaring ownership. Register a test first, then list every build target it needs, including fixture programs that are not linked into its executable:

include(path/to/framework/cmake/UmicomImpactInventory.cmake)
add_test(NAME example.edit COMMAND example-edit-test)
umicom_test_impact_owners(example.edit TARGETS example-edit-test fixture-writer)

A test that must run for every source change can add ALWAYS. File-only checks may use ALWAYS without targets. The declaration does not change the test command. Undeclared ownership remains visible rather than being guessed from a filename. Cross-directory ownership capture requires CMake 3.28; older versions retain registration and use broader selection.

Keep setup and cleanup with their tests

A fixture is a named setup and cleanup requirement. Declare its programs as normal CTest tests, give each test its own build prerequisites, and set the usual CTest properties. For example:

add_test(NAME storage.prepare COMMAND storage-prepare)
add_test(NAME storage.read COMMAND storage-read-test)
add_test(NAME storage.cleanup COMMAND storage-cleanup)
umicom_test_impact_owners(storage.prepare TARGETS storage-prepare)
umicom_test_impact_owners(storage.read TARGETS storage-read-test)
umicom_test_impact_owners(storage.cleanup TARGETS storage-cleanup)
set_tests_properties(storage.prepare PROPERTIES FIXTURES_SETUP storage)
set_tests_properties(storage.read PROPERTIES FIXTURES_REQUIRED storage)
set_tests_properties(storage.cleanup PROPERTIES FIXTURES_CLEANUP storage)

During inventory capture, Framework collects the completed test registrations across configured directories. Selecting any member of a declared fixture or ordering relationship includes the whole connected group and every member's build prerequisites. A shared fixture can therefore select several consumers, even if only one consumer's source changed. Unrelated tests remain outside the group unless another reason selects them. Multiple setup tests, cleanup-only fixtures and overlapping fixtures are supported.

This grouping chooses coverage; CTest still schedules execution. A DEPENDS relationship specifies order and does not require the earlier test to pass. Fixture setup failures prevent dependent tests from running, while cleanup remains scheduled. Resource locks are separate and remain under CTest's control. See the official DEPENDS reference and fixture reference.

The collector requires CMake 3.28 or newer for cross-directory test properties. Missing or ambiguous names, fixture requirements with no registered setup or cleanup, unresolved expressions and missing executable ownership widen coverage. Selection terminates even for cycles, but it does not make an invalid CTest execution cycle valid. Inventory rows with related-test edges use version-two impact metadata; older Umicom readers safely widen to full selection. Recapture the inventory after changing test registrations.

5. Execute separately and retain evidence

Build the selected executable and library targets using the existing umicom build --target NAME workflow. Interface libraries in the inventory may have no standalone build rule; build their concrete consumers. Run selected tests with umicom test --tests REGEX. Do not run tests against missing or stale binaries. Preserve each log outside public source directories and identify the source files, toolchain and configuration actually used.

The preview does not compare current source bytes with capture-time hashes, monitor files, schedule background workers or prove that runtime-loaded resources have complete ownership. Commit comparison disables external diff drivers and text conversion, and keeps both sides of a rename as deleted and added paths. Reconfigure after build-system changes, review custom commands and runtime fixtures, and use a stable source snapshot for background qualification. Full integration and installed-consumer checks remain necessary at release milestones.

6. Compare source observations

A source observation records the current contents of every source file and public header listed in the inventory. The command reads those files without changing them and prints one SHA-256 fingerprint. SHA-256 is a content digest: a different fingerprint means the observed data or its inventory context changed.

  1. Finish configuration, review the inventory and keep the qualification checkout stable. Work on other changes in a separate checkout.
  2. Before building, request an observation and keep the output with your private build log:
umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --full --observe-sources
  1. Build and test the reviewed selection separately. Preserve the commands, exit codes and logs.
  2. Afterward, repeat the observation with the previous 64-character lowercase fingerprint. Replace the placeholder below with the value printed in step 2:
umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --full --expect-sources PREVIOUS_FINGERPRINT

A match prints Listed source bytes and inventory match. A mismatch exits with code 3 and does not emit another usable selection. Review the changed files and configure again when necessary, then obtain a new observation and repeat affected qualification. Do not replace the expected fingerprint merely to make the check succeed.

The fingerprint includes the inventory generation, checkout and build roots, configuration, ownership records, exact listed paths, file lengths and current content digests. Shared source paths are read once. Missing files, unresolved generated inputs, unreadable files, directories and invalid header-path metadata refuse observation with code 2. The error names the failing inventory input or file so you can correct that input before retrying. The native reader rejects a link at the final path component; parent-directory aliases are not a confinement boundary. Use an inventory you trust.

The command limits each file to 16 MiB and the whole observation to 512 MiB. No partial fingerprint is reported when a limit or read fails. Framework hosts can use umicom/distribution/runtime/source_observation.h for immutable results, tighter limits, cancellation and an injected storage reader. The caller owns the result and releases it with UmiReleaseSourceObservationDestroy.

Scope of this check: observations cover listed sources and public headers. They do not automatically cover private headers, unlisted resources, configuration-file bytes, toolchains, environment variables or network dependencies. They also cannot detect an edit that is reversed between reads. Matching before/after observations are not an atomic filesystem snapshot and cannot prove which bytes a compiler consumed. Keep the qualification checkout stable. A matching fingerprint never substitutes for build results, test results or complete release qualification.

Recovery and exit codes

  • 0: preview completed; this is not a passing build or test run.
  • 1: work was selected but no registered tests cover it.
  • 2: invalid arguments, malformed metadata, a discovery failure or an output error. Correct the reported cause; no partial plan should be used.
  • 3: the supplied source-observation fingerprint no longer matches. Reassess the changed inputs before accepting qualification.

If a commit comparison is unavailable, check the full baseline ID and local object availability, and use a Git version supporting --no-lazy-fetch. See the Git global-option reference. If the preview widens unexpectedly, read the printed reason. Add missing ownership to CMake rather than suppressing the fallback. If the inventory belongs to another checkout, recapture it locally. If metadata changed while reviewing a selection, discard that selection and preview again.

For the Git format used by the revision reader, see the official raw diff format documentation.

Inspect input coverage and retain results

Add --list-inputs to the normal impact command to observe and list every inventory input. Each row contains its digest, byte count and escaped path. This remains a read-only preview. Targets can declare private headers and resources with umicom_target_qualification_inputs(target FILES ...). Missing inputs remain unresolved rather than being silently omitted.

Record scoped qualification evidence explains how hosts bind a selection to source observations, preserve exact outcomes, and retain a private report and database history. These APIs do not automatically run builds or tests.
