Inspect affected builds and tests

An incremental build reuses outputs whose inputs have not changed. Selecting tests is a different job: a change to a shared library can affect applications and tests that depend on it. Umicom's impact command previews this relationship using a configured build inventory.

This command is a preview. It reads selected metadata and, when requested, Git status. It does not configure, compile, run tests, install software, change branches or publish commits. A preview is not qualification evidence. The source tree and build metadata must describe the same configuration.

1. Capture the configured inventory

From a Framework source checkout, configure the desired preset with inventory capture enabled. Keep build output separate from source and do not reconfigure the same build directory concurrently.

cmake --preset windows-ucrt64-debug -DUMICOM_RELEASE_INVENTORY_CAPTURE=ON

The generated file is normally build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv. Use the actual build directory and configuration shown by CMake. A parent Applications build has its own inventory under that parent's build directory; its paths are relative to that parent's source root.

2. Preview working changes

Run the newly built native command with an absolute inventory path. Replace the example root with your checkout. The command observes staged, unstaged and untracked changes. Renames contribute both old and new paths. A changed submodule requests a full selection; the child repository must also be qualified separately.

umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --working-tree

Git status describes current uncommitted changes. To include committed changes, add --since COMMIT, replacing COMMIT with the full commit ID recorded by your last accepted qualification run. Umicom compares that immutable ID with the observed HEAD and includes current working changes. It prints both commit IDs. A short ID, branch name, missing object or conflicted working tree is refused. The commit comparison requires Git support for --no-lazy-fetch; unsupported Git versions fail rather than downloading missing objects. Replacement refs are disabled for this comparison so they cannot substitute different content for the recorded IDs.

A baseline identifies which source differences to consider; it does not prove that the baseline passed, that the inventory is current, or that the source stayed unchanged during discovery. Keep the qualification evidence for that baseline. Without one, supply affected paths explicitly or request --full. --since implies working-tree discovery and cannot be combined with --changed.

umicom impact --inventory "C:/work/framework/build/windows-ucrt64-debug/release-inventory/inventory-Debug.tsv" --changed src/example.c --changed include/umicom/example.h --expression

Paths supplied with --changed are relative to the inventory's source root. For a rename, supply both names. Do not combine explicit paths with --working-tree. --git PROGRAM selects the Git executable for working-tree discovery.

3. Read the selection

ReasonMeaning
changed-sourceA changed file belongs to this target.
dependentThis target depends on an affected target.
test-ownerA selected target is a declared prerequisite of this test.
test-prerequisiteThis target must be built for a selected test, even when its own source did not change.
alwaysThe test is explicitly required whenever there is selected work.
full-selectionKnowledge is incomplete or broader coverage was requested.

Missing test owners, unresolved source paths or dependency expressions, imported interfaces with unrepresented dependencies, CTest fixture or dependency edges, unrecognised changed files and CMake configuration changes widen the selection. Older inventories without impact metadata also widen coverage. Full selection is an honest fallback; adding precise declarations can make later previews narrower.

--expression emits an anchored regular expression for the exact selected test names when a narrow expression can be represented within the limit. It escapes regular-expression characters. This output is data, not shell-quoted command text. Full selections, empty test sets, control characters and excessive size do not emit a narrow filter. Never substitute an empty filter and call it a focused check.

4. Declare test prerequisites

Include the shared helper before declaring ownership. Register a test first, then list every build target it needs, including fixture programs that are not linked into its executable:

include(path/to/framework/cmake/UmicomImpactInventory.cmake)
add_test(NAME example.edit COMMAND example-edit-test)
umicom_test_impact_owners(example.edit TARGETS example-edit-test fixture-writer)

A test that must run for every source change can add ALWAYS. File-only checks may use ALWAYS without targets. The declaration does not change the test command. Undeclared ownership remains visible rather than being guessed from a filename. Cross-directory ownership capture requires CMake 3.28; older versions retain registration and use broader selection.

5. Execute separately and retain evidence

Build the selected executable and library targets using the existing umicom build --target NAME workflow. Interface libraries in the inventory may have no standalone build rule; build their concrete consumers. Run selected tests with umicom test --tests REGEX. Do not run tests against missing or stale binaries. Preserve each log outside public source directories and identify the source files, toolchain and configuration actually used.

The preview does not compare current source bytes with capture-time hashes, monitor files, schedule background workers or prove that runtime-loaded resources have complete ownership. Commit comparison disables external diff drivers and text conversion, and keeps both sides of a rename as deleted and added paths. Reconfigure after build-system changes, review custom commands and runtime fixtures, and use a stable source snapshot for background qualification. Full integration and installed-consumer checks remain necessary at release milestones.

Recovery and exit codes

  • 0: preview completed; this is not a passing build or test run.
  • 1: work was selected but no registered tests cover it.
  • 2: invalid arguments, malformed metadata, a discovery failure or an output error. Correct the reported cause; no partial plan should be used.

If a commit comparison is unavailable, check the full baseline ID and local object availability, and use a Git version supporting --no-lazy-fetch. See the Git global-option reference. If the preview widens unexpectedly, read the printed reason. Add missing ownership to CMake rather than suppressing the fallback. If the inventory belongs to another checkout, recapture it locally. If metadata changed while reviewing a selection, discard that selection and preview again.

For the Git format used by the revision reader, see the official raw diff format documentation.
