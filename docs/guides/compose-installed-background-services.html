Compose background services from an installed SDK

This small C23 application combines three services used by Studio: a task queue, a file watcher and a process supervisor. Its purpose is to check the installed public API and ownership boundaries together. It builds against installed headers and libraries rather than compiling Framework sources.

The watcher uses its deterministic fake backend. The example delivers one explicit file event and does not monitor or modify your project. The process supervisor launches the example executable itself in child mode; that child prints a fixed message and exits. No shell, broker connection or network service is involved.

Follow the service graph

main controller owns ExampleServices
  ├─ task queue retains the submitted task
  │    └─ task borrows ExampleServices and emits one file event
  ├─ watcher borrows ExampleServices as its sink payload
  │    └─ sink requests stop; it cannot release its own active watcher
  └─ process supervisor owns one child job
       └─ child output and terminal result are copied into a snapshot

controller waits for results → stops owners → checks releases → frees payload

Borrowing means temporary use without taking ownership. The queue retains a reference to the task object, but it does not own the example's separate heap payload. That payload must stay alive until the callback returns and its worker has been joined. Joining waits for native thread completion; reading an ordinary result counter is not a replacement for it.

The callback deliberately tries checked release on a borrowed watcher pointer. The expected result is UMI_STATUS_INVALID_STATE, with the pointer unchanged. It then requests cancellation and returns. The main controller owns the later blocking stop and release operations.

Prepare one installed package

First build and install the updated Framework platform SDK using your normal repository workflow. This example is installed at share/umicom-framework/examples/background_services. A previous SDK lacking the new lifecycle APIs will not satisfy the example. Reinstall matching headers, libraries and package metadata together.

The following PowerShell commands use C:\umicom\installed\framework as the SDK prefix. Replace that prefix if your chosen installation lives elsewhere. Run each step separately, inspect $LASTEXITCODE and stop after an error. Keep a consumer build directory dedicated to this compiler and SDK.

  1. Make log storage and select the same compiler environment used for the SDK: 
    New-Item -ItemType Directory -Force "C:\umicom\_local\logs\sdk-background-services"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
  2. Configure the independent project: 
    cmake -S "C:/umicom/installed/framework/share/umicom-framework/examples/background_services" -B "C:/umicom/_local/build/sdk-background-services" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_EXPECTED_SDK_PREFIX=C:/umicom/installed/framework -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-background-services\configure.log"
  3. Build just the example: 
    cmake --build "C:/umicom/_local/build/sdk-background-services" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-background-services\build.log"
  4. Run its single registered contract check and capture the output: 
    ctest --test-dir "C:/umicom/_local/build/sdk-background-services" -V --no-tests=error --output-log "C:/umicom/_local/logs/sdk-background-services/tests.log"

This consumer build does not rebuild Framework. Its CMake project imports Umicom::platform from the chosen prefix and rejects a cached Framework configuration outside that prefix. Environment metadata checks the declared ABI, operating system, compiler family and pointer size; native build and execution still need to succeed.

Read the result

A successful program prints Installed watcher, queue and process lifecycle completed.. The CTest name is sdk.background_services.consumer. A timeout, failed native process start, unexpected child result, callback error or incomplete release produces failure. There is no skip code for this example.

The supervisor result must have a successful terminal state, exit code zero and the expected child text. The completed job is explicitly released before the supervisor closes. This demonstrates consuming one result and returning its slot, rather than keeping every job until application exit.

The owner remains allocated if a native stop or release fails. The example then exits unsuccessfully; it never frees callback data beneath a retained worker. In a long-running application, retain that owner for investigation and retry. Do not hide a cleanup failure by changing it into a successful exit.

Troubleshoot without replacing the package boundary

  • Configuration comes from another prefix: choose a fresh consumer build directory. Do not add source-tree include paths to make the check pass.
  • A lifecycle function is undeclared or missing during linking: check that both the installed headers and platform archive came from the updated SDK. Reinstall them together rather than copying only a header.
  • The child cannot start: inspect the operating system's reported loader or security event and the executable path in the verbose CTest log. Do not disable protection or treat a missing executable as a test pass.
  • Release fails: keep the operation name and status from standard error. The source retains owners intentionally so this error cannot silently become a use-after-free.
