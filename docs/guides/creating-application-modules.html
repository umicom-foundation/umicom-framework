Create an Umicom application module

An application module is a source repository with its own manifest, build rules, tests and installation rules. The native project creator can prepare this source for an independent SDK build or for registration as an Umicom Applications submodule. It uses shared C23 Framework services; no Python or PowerShell generator is involved.

Choose a source folder and preview the files

  1. Use a built or installed umicom command that includes module creation. Choose an existing folder for your projects. The tool never chooses a hidden user folder.
  2. Choose a lower-case folder name, an application title and a dotted application ID. Use the same ID throughout the life of the application. The example below assumes C:\Projects already exists.
  3. Run the preview. It reads templates and prints the destination, build option and file list. It creates no application directory.
umicom repo create "Weather" --module --parent "C:\Projects" --slug weather --id org.example.weather

The expected option is UMICOM_APPLICATIONS_BUILD_WEATHER. Use --console-only for a project whose manifest advertises only the console. Otherwise the generated project includes console and GTK4 frontends.

Preview an individual file before applying:

umicom repo create "Weather" --module --parent "C:\Projects" --slug weather --id org.example.weather --show CMakeLists.txt

The file argument is one of the relative paths in the preview. It cannot read arbitrary files. --dry-run explicitly selects the default preview behaviour. --show and --dry-run cannot be combined with --apply.

Create and use the project

  1. Keep the destination absent. An existing directory is rejected even when empty.
  2. Repeat the request with --apply. Each invocation reads the templates again; if you edited them since your earlier preview, review them again first.
  3. Open the generated README and follow its configure, build, test and installation steps. Install the Framework SDK before an independent build. GTK4 development packages are also required for the graphical frontend.
umicom repo create "Weather" --module --parent "C:\Projects" --slug weather --id org.example.weather --apply

The generated model formats a greeting and validates the name. The console accepts a name argument. The GTK4 window lets you enter a name and create the same greeting. The model is independent of GTK, so contributors can add and test business rules once.

Register the module with a suite

The creator writes source only. Review it, create its Git repository and publish it using your normal repository workflow. Register that repository as applications/weather with Git submodule add. The suite reads registered Git membership; a copied folder alone is not registered. See application module discovery for the manifest contract and existing native registration commands.

Enable the printed suite option during configuration. The module supplies its own tests and installer rules. The generated GTK frontend owns its window and is recognised by the shared host integration. Keep GTK enabled when using a GUI-declaring module in the shared native suite; disabling it does not create a generic replacement window. A console-only module does not declare a GUI.

Separate wrapper repositories, automatic remote creation and automatic submodule registration are not performed by this mode. It does not add a launcher catalogue entry or a product-specific shared workstation controller. The existing umicom repo create workflow without --module remains available with its established Git options.

Use the creator from a native application

Link Umicom::scaffold and include umicom/scaffold/application_module.h. These interfaces can serve a Studio wizard without duplicating file generation:

  1. Collect explicit source and template folders, a slug, name and ID.
  2. Call umi_application_scaffold_plan on a worker. The returned plan owns all rendered bytes and validates the generated manifest.
  3. Read the summary and file views to present the preview. File views remain valid until the plan is destroyed. Keep access on one owner thread.
  4. After the user chooses to create the source, call umi_application_scaffold_apply with that same plan.
  5. Show the result and release the plan. An apply attempt consumes it even when creation fails. The native form described below uses this same service.

Create from Studio

  1. Open Studio's welcome page and choose New Umicom Application. The ordinary Create New Project recipes remain available.
  2. Enter the name, dotted application identifier and module slug. Select an existing parent folder with Choose Parent Folder, or enter its absolute path. The creator makes a new child folder named after the slug.
  3. Leave the template folder blank to use the resources shipped with Framework, or select trusted templates explicitly. Choose whether to include the GTK frontend.
  4. Choose Preview Source. Select each file in the list to inspect its rendered contents. No destination directory exists yet. Editing any field, including changing it back, invalidates that preview.
  5. Choose Create Source after reviewing it. The form writes the same bytes it displayed. It does not reread templates during this step.
  6. When creation succeeds, choose Open Project. Studio opens the source and applies the generated build settings. If another operation prevents opening, finish that operation and retry; the generated source remains in place.
  7. Review Build Settings and workspace trust before configuring. For an independent build, provide the installed Framework SDK prefix in the CMake definitions, for example -DCMAKE_PREFIX_PATH="C:/umicom/installed/applications". Install GTK development packages if the graphical frontend is enabled.
  8. Configure, build and run tests using Studio's existing build actions. Read the build target catalogue and explicitly choose the program for Run or Debug. The creator leaves the run path empty because generators place binaries differently.

Template reads and source writes use workers. Closing a preview discards its authority; creating files requires another preview after reopening. Normal close and Cancel wait while an accepted write finishes. Destroying the host does not undo a write already started, and a background completion never opens another workspace automatically.

Embedding applications can call UmiGtk4ApplicationModuleDialogCreate from umicom/ui/gtk4/developer_dialog.h. Keep its owned handle until UmiGtk4DeveloperDialogDestroy, and destroy it before freeing callback context. Headless clients can use UmiDeveloperApplicationScaffoldProject to prepare the same untrusted project model and build profile from a reviewed plan. An identifier may fit a manifest but exceed the IDE model's capacity; preview rejects that case before writing any files. The graphical preview also requires UTF-8 templates.

Limits and recovery

Creation is exclusive: it never overwrites a pre-existing file or folder. If a write or close fails, the command reports the last path and completed file count, and retains partial source for inspection. It does not delete that work or claim a project-wide transaction. Choose a fresh destination after inspecting a failed attempt. Do not let another process replace the selected parent or generated directories during creation. Parent aliases are trusted; this service is not a filesystem security sandbox.

Template files are limited to 32 KiB each and to the fixed catalogue. Unknown replacement tokens, embedded NUL bytes, missing files and invalid manifests fail before any destination is created. Custom templates are source you must review before building; the size and token checks do not make arbitrary CMake or C code safe to run.

Names use a portable subset: slugs contain lower-case letters, digits and hyphens, start with a letter and do not end in a hyphen; titles contain letters, digits, spaces and hyphens and start with a letter. IDs have nonempty dotted segments that start with letters. Windows device names are refused on every platform. Internationalised project identities are outside this template contract; a generated application can later provide translated user-facing text.

If templates are missing, reinstall the Framework component or pass --template-root with the absolute path to templates/application_module in a trusted Framework checkout. Installed templates are found relative to the executable and configured data directory; a source build also has its configured source location as a fallback. No compiler, Git credentials, remote account or GUI session is required just to preview or write the source.

Choose the installed SDK

After creating a standalone project, use the installed SDK inspection workflow to select its Framework package in Build Settings. A chosen package location does not grant workspace trust or replace compiler and linker qualification.
