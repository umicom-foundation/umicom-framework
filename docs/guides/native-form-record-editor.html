Save typed forms locally

The native form record editor combines a schema (the definition of each field) with a local SQLite database. It stores a new revision for each successful save. It does not authenticate users, encrypt records or send data to a remote service.

Use an editor

  1. Enter the full path to a local database in an existing directory. Choose Open or create database. Wait for the connection result.
  2. Enter a record key and choose New record, or choose Open record to load an existing key. A missing key is reported; opening it never creates a record.
  3. For each answer, select Known, Unknown, Not applicable or Unanswered. Supply a value for Known and a reason for permitted missing states. A required boolean needs an explicit true or false answer.
  4. Enter an attribution label and a reason for the revision. Choose Save draft to retain an incomplete form, or Check required answers and save to require all mandatory answers.
  5. Wait for the save result. Typing may continue while saving; the result acknowledges only the captured answers. Later typing remains unsaved.
  6. Before closing, save changes or choose Discard unsaved answers and confirm. Discard restores the last saved baseline or closes a never-saved record.

Compose an application

Link Umicom::form_record_editor_gtk4 and include umicom/ui/gtk4/form_record_editor.h. Keep the immutable schema alive for the widget's lifetime and any outstanding work. Products supply a namespace, source label and optional pure key validator. The returned widget has a floating GTK reference; attach it to a parent or sink that reference.

The Connect, Open and Save APIs return whether work was accepted. Wait until UmiFormRecordEditorGtk4Busy is false and inspect UmiFormRecordEditorGtk4LastStatus for the result. Keep GTK's main context running. Check UmiFormRecordEditorGtk4CanClose before permitting window closure. Unrooting permanently retires this editor, so create a new widget when moving to a new host.

Recover from a refusal

Review concurrent changes

A stale save means another writer changed the stored revision. Your local answers remain. After an I/O failure, inspect storage before retrying because a storage interruption can have an ambiguous outcome.

  1. Choose Review stored changes. The editor reads the current stored record and verifies your saved baseline. It shows changed fields with baseline, local and incoming answers, including units and reasons for missing answers.
  2. For a field changed differently by both writers, choose Keep baseline, Keep local or Take incoming. Automatic accepts changes made by only one writer and identical changes made by both; a conflicting field remains unresolved.
  3. Choose Apply reviewed answers locally. This updates your local draft and its baseline together. It does not write the database. If you typed after starting the review, start a fresh review instead of applying stale choices.
  4. Review the resulting form and save when ready. The save checks the stored revision again. If another writer changed it during your review, repeat the comparison.

A never-saved key collision cannot establish a shared baseline. Keep a recovery copy and choose a different key or review the existing record separately. Review does not authenticate another writer or grant authority to change a domain record.

Oversized, malformed or incompatible forms are refused without truncation. The record payload limit is 16,384 bytes. A schema may permit more answers than this storage limit can hold, so size the product's schema accordingly. Secret fields and sensitive records require a separate protection design. This editor is not a credential vault or a clinically qualified records system.

Keep a recovery copy

  1. Enter a full private recovery-file path in an existing directory.
  2. Choose Keep a new recovery copy. Visible answers must be valid as a draft. Incomplete required answers are allowed; invalid numbers or dates are refused without changing your text.
  3. Use a new filename each time. Existing files are never overwritten. A copy is ordinary plaintext data and does not mark the database record saved.
  4. To restore, connect the intended database, explicitly resolve any current edits, enter the recovery-file path and choose Recover a checked draft. The editor checks the namespace, schema and stored baseline before replacing the visible form.

A newer database head does not rewrite the recovered draft. The next save still checks its original revision and may refuse a stale save. Recovery is an explicit user action, not automatic background saving. Find saved records with the catalogue and inspect earlier revisions without replacing your draft. See Find and inspect typed records for the complete workflow.

Export saved history

  1. Open a saved record and resolve any unsaved answers. Export refuses a new or dirty record.
  2. Enter a full new filename in an existing private directory, or use Browse. Choosing a filename does not write it.
  3. Choose Export saved history and wait for the result. The worker checks that the saved head still matches the editor before creating the file. If another writer changed it, review the stored changes and retry only after reviewing the new baseline.
  4. Use the shared importer to review the file and restore an unoccupied record in a chosen destination. Original attribution labels are retained but are not authenticated.

Export contains complete saved history for one record, limited to 16 revisions. It is plaintext, does not export drafts, and never overwrites a file. A failed write may leave a partial new file; inspect it and choose another filename. Later typing remains unsaved. Keep the main loop alive until accepted writes finish, including after window retirement.
