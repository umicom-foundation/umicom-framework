Editing authorized records in a native application

The Framework native form editor connects a typed form to an owned record host. The host checks the current session, user, purpose and policy whenever it reads or writes a record. Applications supply authentication and their schema; the editor does not provide a login service.

Compose an editor

  1. Link your native application with Umicom::authorized_form_editor_gtk4 and include umicom/ui/gtk4/authorized_form_editor.h.
  2. Create an owned record host, register the authenticated identity, and install explicit operation and purpose rules. A new host denies access by default. Issue a current-time session through the host.
  3. Pass the host, immutable schema, private session handle and purpose to UmiAuthorizedFormEditorGtk4New. The widget retains the host. Keep schema data and any borrowed clock state alive until all widgets and background operations finish.
  4. Place the returned floating widget in a GTK container. Perform widget operations on the GTK owner thread. Do not put session handles in logs or visible fields.
  5. Use UmiAuthorizedFormEditorGtk4ReadState to inspect state. Use UmiAuthorizedFormEditorGtk4CanClose before routine closing. Prompt for explicit discard if there are unsaved values, or wait for a pending operation.

Try the fictional example

When examples and GTK dependencies are enabled, the umicom-authorized-form-native-example target opens a parcel form. It uses in-memory storage and fictional identities; it is not a production authentication example.

  1. Enter example.parcel in Record ID and choose New.
  2. Enter a mass and an amendment reason, then choose Save. Wait until the operation completes.
  3. Change the mass and save again. The editor checks the previously reviewed record revision before appending an amendment.
  4. Choose Discard to abandon unsaved edits. A saved form returns to its last saved values; a never-saved draft closes.

Understand asynchronous ownership

Save captures an immutable form snapshot. You can continue editing while storage runs. A successful save advances the stored baseline but does not overwrite later input or mark later edits as saved. Open refuses to replace unsaved input, including input entered while a read was pending.

Current-time host methods sample the trusted clock after admission, so a queued operation cannot reuse an old timestamp to bypass session expiry. The default clock is monotonic: its values describe elapsed time, not UTC dates.

Retiring or disposing the editor prevents further UI mutation. It does not cancel or undo a write already admitted by the host. Completion state retains the actual storage result. Keep processing the main context until pending work completes before releasing borrowed schema or clock data.

Recover from rejected operations

  • Access denied: inspect the current identity, session and both operation and purpose rules. The editor intentionally does not ask the user to type an actor name.
  • Stale record: preserve your edits and review the current head separately before deciding how to reconcile them. The editor never silently overwrites another amendment.
  • Invalid value: correct the field and apply it again. Required values are checked when the caller requests submission validation.
  • Busy: wait for the pending operation before opening another record, discarding or saving again.

A clean saved form rejects a duplicate amendment. This component does not yet provide automatic draft recovery, a record browser, session renewal or a product approval workflow. Passing submission validation only validates answers; it does not approve a medical or financial operation.
