Check the SDK environment

Check background work through an installed SDK

A background task continues while another part of an application handles input. Closing its window must not release memory that the task still uses. Framework provides task references, cooperative cancellation and queue shutdown as separate operations. This consumer exercises those public contracts through installed libraries.

The existing queue-shutdown laboratory builds a small subset of the actual Framework sources. Its independent client now also has an explicit mode for a complete installed Framework SDK. The two modes answer different packaging questions; neither requires a replacement queue implementation.

Choose the package

For the full SDK, use the client installed at share/umicom-framework/examples/queue_shutdown/client. Replace C:/SDKs/Umicom below with your actual SDK prefix. Use the matching compiler and target environment. The SDK must contain the platform library and the environment checks described in the SDK environment guide.

  1. Prepare separate output and log locations: 
    New-Item -ItemType Directory -Force "C:\umicom\_local\logs\sdk-shutdown"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
  2. Configure the independent client: 
    cmake -S "C:/SDKs/Umicom/share/umicom-framework/examples/queue_shutdown/client" -B "C:/umicom/_local/build/sdk-shutdown" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_SHUTDOWN_USE_FRAMEWORK_SDK=ON -DUMICOM_EXPECTED_SDK_PREFIX=C:/SDKs/Umicom -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-shutdown\configure.log"
    The package configuration, Framework headers and imported libraries must belong to that prefix. Metadata agreement is not a substitute for the following build and execution.
  3. Build only this client: 
    cmake --build "C:/umicom/_local/build/sdk-shutdown" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-shutdown\build.log"
  4. Run its registered checks: 
    ctest --test-dir "C:/umicom/_local/build/sdk-shutdown" --output-on-failure --no-tests=error --output-log "C:/umicom/_local/logs/sdk-shutdown/tests.log"
    Run each command separately and stop on an error. Check $LASTEXITCODE; PowerShell does not automatically stop after a failed native command.

For the original focused laboratory package, keep UMICOM_SHUTDOWN_USE_FRAMEWORK_SDK=OFF and select its UmicomQueueShutdown_DIR. Install that subset into a separate prefix; do not overlay it on a complete Framework SDK.

Read each result separately

CTest nameContract exercised
installed.shutdown.clientThe original nonblocking demonstration drains one task, observes joined workers and releases the stopped queue. Return code 77 means nonblocking join is unsupported; it is a skip, not a pass.
installed.shutdown.drainA portable blocking controller finishes accepted work and checks stopped-queue counters.
installed.shutdown.cancel-running-and-pendingOne callback has entered before a second task is queued. Cancellation reaches the running task and prevents the queued callback from starting.
installed.shutdown.rejected-reusableA queue that closed admission refuses a new task without consuming or cancelling it. The caller can still run its own task.
installed.shutdown.caller-releaseThe queue retains an accepted task after the caller releases its reference. The callback payload remains alive until join.
installed.shutdown.callback-errorThe callback's error remains visible after successful shutdown. A stopped queue does not mean all jobs succeeded.
installed.shutdown.worker-selfA callback cannot join or wait for idleness of its own queue.

The six named cases use blocking shutdown on their command-line controller. They do not claim that blocking the graphical event thread is safe. GUI code should use the existing polling lifecycle where supported, or an explicitly owned lifecycle worker. Never silently replace a nonblocking operation with a blocking join.

Understand the memory boundary

caller owns task reference ---- submit ----> queue retains another reference
caller owns callback payload -----------------------> keep alive
request cancellation ----> callback observes it ----> callback returns
request stop ----> workers finish native teardown ----> join succeeds
release stopped queue ----> release caller task references ----> free payload

A reference keeps the task object alive. It does not automatically retain user_data, the application's payload pointer. The client allocates its payload independently and frees it only after the queue is joined and released. Counters shared with the worker are atomic, so reading them does not create a data race.

Each gated fixture has a finite escape path and CTest has a process timeout. A timeout is failure evidence, not permission to free data still borrowed by a worker. If native cleanup fails, this failed client retains its heap owners until process exit; it does not report success or use forced thread termination as a repair.

Extend the qualification

Start with examples/queue_shutdown/client/lifecycle_cases.c. Follow the public declarations in platform/task.h, platform/task_queue.h and platform/threading.h. Keep all scenarios independent of private structure layouts and source-tree include paths.

Run the consumer for every supported compiler, target architecture and runtime combination you intend to release. Sanitizer and GUI lifecycle runs provide additional evidence. These small cases do not certify every public ABI, every application shutdown path, or malicious/uncooperative callback behaviour.

The expected outcomes above describe the authored checks. Record the actual configuration, compiler, SDK revision and test results when you run them.

File-watcher callbacks have a similar ownership boundary. See Watch files without releasing live callbacks for checked release and retry behaviour.
