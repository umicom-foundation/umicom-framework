Review evidence before completing Kanban cards

A Done card is a planning decision. It does not prove that software passed its tests. The Framework completion-plan service lets a host record who reviewed a card, which source and configuration they reviewed, and which evidence they accepted before moving cards to Done.

What is available

This is a synchronous C23 service in Umicom::kanban, declared in umicom/kanban/completion_plan.h. It creates an owned review plan, checks whether that plan still applies, applies its reviewed card moves atomically, and encodes or decodes private review records. Existing boards and their normal editing API retain their behavior. The shared GTK4 board now includes a private completion-review section, also available to Studio hosts using that board. Automatic test-result verification and mandatory review enforcement are separate host responsibilities.

Review and complete cards

  1. Keep the board under one serialized owner. Finish the work and retain the relevant build, test, installation or manual-review evidence. Keep private logs outside public repositories.
  2. Inspect each card's acceptance criteria against that evidence. Read failures and skipped coverage explicitly. A report with unchanged failures or removed tests is not proof of a repair.
  3. Choose the target Done column and a local reviewer identifier. Record the source/build identity and configuration you actually reviewed. These values are declared context, not authentication.
  4. Prepare one UmiKanbanCompletionRecord per selected card. Use UMI_KANBAN_COMPLETION_REVIEWED with a 64-character lowercase SHA-256 evidence digest and a rationale describing what was accepted. For several files, retain a manifest and identify that manifest. A digest identifies bytes; it does not validate their contents.
  5. If accepting an explicit review exception, use UMI_KANBAN_COMPLETION_EXCEPTION and describe why. A digest is optional for an exception. An exception still cannot bypass incomplete checklists, unresolved dependencies, an explicit blocker, work-in-progress limits or disallowed transitions.
  6. Call UmiKanbanCompletionPlanCreate with the observed board revision. It checks every record and previews the complete transaction on an independent board copy. Creation changes neither the live board nor its activity.
  7. Retain the private plan, then explicitly call UmiKanbanCompletionPlanApply. It rechecks the exact board content and revision before applying all moves in one existing board transaction. A failure changes no cards. Successful completion advances the board revision once.
  8. Save the board through its normal document owner. Keep the review plan as historical evidence. Board saving and plan retention are separate storage operations, not one disk transaction.

Use the native board

  1. Select the card to review. For the development workflow it must be ready to leave Testing. Open Review evidence before completing cards below the board.
  2. Enter your reviewer identifier, the source and configuration you reviewed, the evidence file's lowercase SHA-256 digest, and an acceptance rationale. Review the evidence yourself. Typing a digest does not verify the evidence or run any tests.
  3. For a deliberate exception, select Record an explicit review exception and state the reason. The digest may then be empty, but normal board completion rules still apply.
  4. Enter an absolute path ending in .umicompletion inside an existing private directory. Choose a new filename, then click Save selected card review. The file operation runs in the background using the selected card and fields captured at the click. Editing the fields during the save does not change that saved decision.
  5. Inspect the retained preview: card ID, destination, board revision, source, configuration, evidence and rationale. A successful save has not moved the card. Check the approval box and click Apply reviewed completion to request the move.
  6. Save the board through its host. The review file remains historical evidence, even if a later board save fails. Changing selection after saving does not retarget the retained decision to another card.

To inspect an earlier decision, enter its path and click Load retained review. Loading never changes a board. A separate approval and Apply are required, and stale or different board content is refused. The host chooses the first configured Done-stage column when capturing a new review; its identifier appears in the preview.

Discard removes the displayed review without deleting its file. A refused load or save retains the earlier accepted preview. Existing files are never overwritten. Closing, hiding or retiring the control during a request suppresses its late preview; an already dispatched file write can still finish. If a preview is interrupted, load or save it again before approval.

This optional control does not replace ordinary drag-and-drop or board editing. It provides a review record rather than authentication or a mandatory approval policy. The private fields and files are separate from the public website export.

Reuse a saved test report as evidence

When the shared saved-report browser is included in the native build, open Inspect saved CTest evidence inside completion review. Choose a completed CTest JUnit XML file, click Open report, and inspect its results. The browser identifies the exact bytes it parsed and displays complete outcome counts even when the visible test list is filtered.

  1. Review the report's scope, failures, timeouts, skipped tests, disabled tests and tests that did not run. Confirm separately which source and configuration produced it; the XML digest cannot establish this.
  2. Click Use displayed report digest. This copies the accepted report's digest into the draft without rereading its filename. It leaves source identity, configuration and rationale for your explicit review.
  3. Save a new completion review, inspect its retained preview, then approve it separately. Choosing another report revokes readiness of the older displayed decision, even if its preview remains available for inspection.

A missing or still-loading report cannot supply evidence. A failed or empty report can be inspected and referenced, but is never labeled a successful qualification automatically. Using its digest alone moves no cards, approves no review, saves no board and publishes nothing.

Why a plan can become stale

The plan captures the board's complete portable archive digest, board ID and live revision. A different board with the same ID and revision is refused if its content differs. Any subsequent board edit, including an unrelated assignment, requires a fresh explicit review. This conservative rule avoids silently applying acceptance to different criteria. No automatic rebase is provided.

Opening a board archive creates a new live revision starting at 1. A plan from the previous session remains historical evidence and normally needs fresh review. Reapplying a successfully used plan is refused because the live revision has advanced.

Keep review records private

Use UmiKanbanCompletionPlanEncode to measure and encode the plan. First pass a null buffer and zero capacity, allocate the returned size, then encode. Archives are limited to 256 KiB and at most 128 card decisions. Short buffers remain unchanged. Decode owns its strings independently and refuses damaged or malformed input.

The archive contains reviewer attribution, private rationale, source context and evidence identifiers. It is plaintext with a corruption checksum; it is neither encrypted nor signed. Store it in a private directory with appropriate permissions. The board archive and reviewed public-roadmap projection do not automatically include these records. Publish only separately reviewed public fields.

Retain review files without replacing earlier evidence

The optional native adapter in Umicom::kanban_storage declares UmiKanbanCompletionPlanWriteNew and UmiKanbanCompletionPlanLoadFile in umicom/kanban/completion_storage.h. Supply an absolute path ending in .umicompletion inside an existing private directory you control. In an interactive host, call file operations on a worker.

  1. Write the fully reviewed plan to a new filename. Existing files are refused, including an earlier review. A failed write can leave a partial new file; retain it for diagnosis and choose a new name.
  2. After a successful write, explicitly apply the plan on the board owner thread and save the board separately. A saved review is evidence of the decision, not proof that the board save succeeded.
  3. Load a retained plan into an independent candidate. Loading performs no board edits. Call UmiKanbanCompletionPlanCheck against the current board before offering application.

The file adapter uses the shared bounded input and exclusive output services. It does not create directories, overwrite earlier decisions, authenticate reviewers or publish any data. The complete portable board archive and the separate review file have independent lifetimes.

Recover from refusal

  1. For a stale plan, reread the current board and review the changed content. Create a fresh plan rather than changing the old plan's identity.
  2. For a policy refusal, inspect the card's checklist, blocker, dependencies, current column and destination limits. Resolve the actual condition; an exception is not a bypass.
  3. For malformed evidence fields, use a complete lowercase digest, bounded UTF-8 rationale, a valid reviewer ID, and nonempty source/configuration context. Missing evidence must remain explicit.
  4. For an archive error, retain the original bytes for diagnosis. A successfully decoded plan still needs a current-board check before application.

All accepted evidence and review exceptions are supplied by the caller. The core planning service performs no file reads, test execution, signature validation, authentication or network publication. It cannot establish that a report belongs to the declared source without the host's independent evidence.
