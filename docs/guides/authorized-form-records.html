Save typed forms through record permissions

A typed form keeps each answer's meaning: its field, value type, unit and whether the answer is known or deliberately missing. The authorized-form adapter stores these answers through the record access service. It preserves the existing snapshot format and uses the same identity, session and purpose policy.

Connect the adapter

  1. Set up an authorized-record service as described in the linked guide. Keep its dependencies alive and serialize protected operations with security changes on one trusted owner.
  2. Link Umicom::authorized_form_records and include umicom/data/authorized_form_records.h. Keep the form schema and request inputs stable until each operation returns.
  3. Load revision zero with READ_HEAD for the current form. Load a positive record revision with READ_HISTORY. The output contains the storage revision, typed answers and access receipt together. A permission denial does not expose decoded answers.
  4. Create with CREATE and expected record revision zero. Amend with AMEND and the last reviewed storage revision. Amendments also require READ_HEAD for the same entity and purpose: the adapter checks that the previous document is a form using the same schema before writing.
  5. Handle success before marking a live draft saved. A form's editing revision and its storage revision are different counters. The adapter does not change the caller's draft. A saved marker must match the exact editing revision whose bytes were stored.

Drafts and submission

Saving a draft allows unanswered required fields. Submission is a separate product action: call umi_structured_form_validate with submitting enabled, inspect its field report, then follow the application's reviewed workflow. A successful draft save does not mean that the form was submitted, approved or suitable for a clinical or financial decision.

Recover from refusal

Keep unsaved answers when access is denied. Reauthenticate or correct the host policy through the trusted host. Do not replace an actor label to bypass a denied session. INVALID_STATE during an amendment can mean the storage head or schema differs from the reviewed form. Reload and review the difference; a schema change requires a deliberate migration. PARSE_ERROR means stored content is not a valid typed snapshot. Do not overwrite it as a repair. BUSY means another transaction owns the store; retry after that owner finishes.

Qualify the service

From a configured Framework build with testing enabled:

cmake --build build --target umicom-authorized-form-load-test umicom-authorized-form-save-test
ctest --test-dir build -R "^framework\.authorized_forms\." --output-on-failure --no-tests=error

These cases exercise fictional parcel forms against memory storage and, when available, SQLite. They cover denied reads, incompatible snapshots, preserved drafts, stale amendments and trusted authorship. They do not qualify a product login, a network endpoint or a native editor.

Limits

The existing unguarded form and record APIs remain available for trusted internal services. Applications must explicitly adopt this adapter and keep those lower-level services out of untrusted reach. The adapter supplies no passwords, encryption or durable purpose audit. Access receipts describe completed checks and never authorize later operations. Stored snapshots must fit the bounded record document size.
