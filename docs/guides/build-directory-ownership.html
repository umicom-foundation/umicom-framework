Owning a build directory

Two jobs can corrupt one another's outputs if they configure or build in the same directory at the same time. Framework supplies a cooperative guard: every participating job opens the same persistent guard file and holds exclusive ownership until its work ends.

Use it in a native build session

  1. Choose an absolute build directory and create it before submitting work. Keep separate directories for independent configurations. The guard never creates a directory or selects a location in your user profile.
  2. Include umicom/build/directory_guard.h and link Umicom::build.
  3. On the session owner's thread, enable the guard while the session is idle.
  4. Submit the normal workflow. The worker acquires ownership before its first phase and releases it after its final phase, failure or cancellation.
  5. Read the guard snapshot to distinguish an unavailable directory, a busy owner and an acquired lease. If acquisition fails, no executor phase starts.
UmiStatus status = UmiBuildProjectSessionSetDirectoryGuard(session, true);
if (status == UMI_STATUS_OK)
    status = umi_build_project_session_submit(
        session, profile, UMI_BUILD_PHASE_TEST, trusted);

/* Poll on the frontend; the copied snapshot performs no disk I/O. */
UmiBuildDirectoryGuardSnapshot guard;
status = UmiBuildProjectSessionReadDirectoryGuard(session, &guard);

Read acquisition_status only when attempted is true. A successful submission means the worker was queued, not that it acquired ownership or passed its tests. The session's terminal status remains authoritative for workflow completion.

Existing sessions default to disabled. Enabling a guard does not protect earlier jobs, unguarded sessions or direct CMake, Ninja and CTest commands. CMake preset profiles currently refuse guarded execution with UNAVAILABLE, because preset inheritance can select a different binary directory. Use an explicit directory profile or resolve that workflow in the host before adopting a guard. Do not silently lock a different directory.

Coordinate another host

UmiBuildDirectoryGuardAcquire(directory, &lease) uses the same .umicom-build.lock filename. The output pointer must initially be null. Keep the lease alive for the complete protected workflow and call UmiFileLeaseRelease(&lease) on every exit path. A custom executor must return only after its children stop using the directory. The native build runner owns its process tree.

The lower-level UmiFileLeaseTryAcquire in umicom/platform/file_lease.h accepts a caller-chosen absolute regular-file path. It leaves existing bytes intact and creates a missing empty file. An incompatible owner returns BUSY immediately. The operating system releases native ownership when the handle closes or its process exits.

Keep the guard file

File existence does not indicate an active owner. Do not delete a guard file to recover from a busy result: another process may already hold its original file object, and a replacement would permit two owners. Wait for the owning job to finish or choose another build directory. Ordinary release leaves the empty file in place.

Use a trusted, stable local directory. Final symlinks, reparse points and special files are refused, but ancestor directories are not secured against replacement. POSIX locks are advisory; Windows uses an exclusive sharing mode. Network filesystems, hostile directory changes and raw forked children that retain descriptors are outside this coordination guarantee. The guard does not freeze source files, prove compiler inputs, or authorize publication.

Native support covers Windows, Linux and macOS. Other hosts report UNAVAILABLE. Regression coverage includes independent processes, process exit without cleanup, preserved file bytes, all-phase ownership, failed acquisition, cancellation, disabled compatibility and preset refusal. These checks must be executed for the host being qualified.

Native reference contracts: Windows CreateFileW and Linux flock.
