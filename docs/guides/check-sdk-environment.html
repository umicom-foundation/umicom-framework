Choose an installed SDK

Check a Framework SDK with an independent application

A header tells a compiler how to call a library. The library contains the compiled implementation. An SDK packages these files together. Finding both files is necessary, but it does not establish that they describe the same binary interface or were built for your target computer.

This guide uses the small sdk_environment example shipped with Framework. It asks CMake to check the package declarations, compiles assertions against the installed headers, links one real base-library function, and provides a runnable test. Each step answers a different question.

Understand the three checks

CheckWhat it establishesWhat remains to check
Package originThe selected configuration and Framework library paths belong to the requested installation.The contents may still be incomplete or incompatible.
Environment declarationsThe required ABI number, operating-system identifier, pointer size and C compiler family agree.Instruction set, runtime-library model, packing, calling conventions and compiler options need separate qualification.
Independent consumerIf compilation, linking and execution succeed, this consumer can use the selected base API.Other components, public structures, application shutdown and every supported target still need their own tests.

ABI means application binary interface: the agreement compiled pieces use when calling each other. Two processors can both use eight-byte pointers and still execute different instructions. Equal metadata is an early check, not proof that arbitrary binaries can be combined. Compiler versions are reported for review; equal family names alone do not certify compatibility between versions.

Prepare the example

  1. Install a current Framework SDK with its base library, public headers and CMake package. The example is installed at share/umicom-framework/examples/sdk_environment under that SDK. It is also available in the source tree at examples/sdk_environment.
  2. Use the compiler and target environment for which that SDK was built. The commands below use a Windows UCRT64 GNU toolchain. Replace C:/SDKs/Umicom with your actual installation prefix. A prefix is the common root folder of the SDK.
  3. Use a new consumer build directory when changing compiler, target or SDK. This keeps cached settings from a previous configuration out of the comparison. Keep the SDK installation itself unchanged while the consumer is being qualified.
  4. Create a directory for the command logs: 
    New-Item -ItemType Directory -Force "C:\umicom\_local\logs\sdk-environment"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

Configure, build and run

Run one command at a time and stop if it fails. PowerShell does not automatically stop after every failed native command. $LASTEXITCODE reports that command's exit code; zero means success. A log records output, but its existence does not prove success.

  1. Configure the independent application: 
    cmake -S "C:/SDKs/Umicom/share/umicom-framework/examples/sdk_environment" -B "C:/umicom/_local/build/sdk-environment" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_EXPECTED_SDK_PREFIX=C:/SDKs/Umicom -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\configure.log"
    CMake should report the agreeing environment identifiers and the producer and consumer compiler versions. It must finish configuration and generation successfully before you continue.
  2. Compile and link: 
    cmake --build "C:/umicom/_local/build/sdk-environment" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\build.log"
    This builds the small consumer. It does not rebuild Framework source.
  3. Run the registered test: 
    ctest --test-dir "C:/umicom/_local/build/sdk-environment" --output-on-failure --no-tests=error --output-log "C:/umicom/_local/logs/sdk-environment/tests.log"
    The expected test name is sdk.environment.consumer.
  4. Run the program directly when you want to read its output: 
    & "C:\umicom\_local\build\sdk-environment\umicom-sdk-environment-example.exe" 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\run.log"
    It prints the header version, required ABI, actual pointer size and the status text returned by the linked base library. These are expected behaviours of the example, not evidence that your installation has already passed.

Use the checks in your own CMake project

project(MyFrameworkApplication LANGUAGES C)
find_package(UmicomFramework CONFIG REQUIRED COMPONENTS base)
umicom_require_sdk_environment(2)
umicom_require_installed_sdk_layout("C:/SDKs/Umicom" sdk_headers Umicom::base)

Declare the ABI your application was written against; do not copy the installed package's value into that requirement. Otherwise the comparison would always agree. Call the environment helper after project(... LANGUAGES C), when CMake knows the consumer compiler and pointer size. Use umicom_require_installed_sdk when you also require the complete SDK's public-header contract rather than this example's component layout check.

The example uses C23 static_assert to compare the installed header ABI with its independent requirement and sizeof(void *) with the package's declared pointer size. It then calls umi_status_text(UMI_STATUS_OK). The real symbol makes a successful link more informative than printing only header constants.

Recover from a refusal

DiagnosticNext action
Package outside the expected prefixInspect the cached UmicomFramework_DIR. Use a fresh consumer build directory and the intended prefix. Do not borrow archives from another SDK.
Environment metadata unavailableInstall the current package files together with their matching headers and libraries.
ABI or header assertion differsReview the API and ABI changes, then select a compatible SDK or adapt the application. Changing only the number hides the disagreement.
System, pointer size or compiler family differsBuild/select an SDK for the intended consumer toolchain and target. This conservative helper does not approve cross-family combinations.
Compile, link or runtime failure after metadata agreesKeep the first diagnostic and compiler versions. Investigate the actual archive, target architecture, options and runtime dependencies. Metadata agreement is not a repair.

Maintain one Framework identity

Framework's numeric version fields, version string and ABI identifier are published in include/umicom/base/version.h. The package generator and passive sdk.properties receipt now read that same source. The package generator refuses duplicate definitions, unsupported numeric forms, out-of-range values, a conflicting version string, or a project version that disagrees with the header.

The parser expects the canonical plain decimal definitions used by that header; it is deliberately not a C preprocessor. The version components fit the public UmiVersion fields. An ABI number is a release-maintained contract identifier, not a computed proof that every exported function remains compatible.

Metadata regressions are registered as framework.sdk.identity.* and framework.sdk.environment.*. Their synthetic fixtures exercise refusals without compiling libraries. Keep those results separate from this real installed consumer and from the product's complete runtime qualification.
