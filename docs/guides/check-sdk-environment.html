Choose an installed SDK

Check a Framework SDK with an independent application

A header tells a compiler how to call a library. The library contains the compiled implementation. An SDK packages these files together. Finding both files is necessary, but it does not establish that they describe the same binary interface or were built for your target computer.

This guide uses the small sdk_environment example shipped with Framework. It asks CMake to check the package declarations, compiles assertions against the installed headers, links one real base-library function, and provides a runnable test. Each step answers a different question.

Understand the three checks

CheckWhat it establishesWhat remains to check
Package originThe selected configuration and Framework library paths belong to the requested installation.The contents may still be incomplete or incompatible.
Environment declarationsThe required ABI number, operating-system identifier, pointer size and C compiler family agree.Instruction set, runtime-library model, packing, calling conventions and compiler options need separate qualification.
Independent consumerIf compilation, linking and execution succeed, this consumer can use the selected base API.Other components, public structures, application shutdown and every supported target still need their own tests.

ABI means application binary interface: the agreement compiled pieces use when calling each other. Two processors can both use eight-byte pointers and still execute different instructions. Equal metadata is an early check, not proof that arbitrary binaries can be combined. Compiler versions are reported for review; equal family names alone do not certify compatibility between versions.

Prepare the example

  1. Install a current Framework SDK with its base library, public headers and CMake package. The example is installed at share/umicom-framework/examples/sdk_environment under that SDK. It is also available in the source tree at examples/sdk_environment.
  2. Use the compiler and target environment for which that SDK was built. The commands below use a Windows UCRT64 GNU toolchain. Replace C:/SDKs/Umicom with your actual installation prefix. A prefix is the common root folder of the SDK.
  3. Use a new consumer build directory when changing compiler, target or SDK. This keeps cached settings from a previous configuration out of the comparison. Keep the SDK installation itself unchanged while the consumer is being qualified.
  4. Create a directory for the command logs: 
    New-Item -ItemType Directory -Force "C:\umicom\_local\logs\sdk-environment"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

Configure, build and run

Run one command at a time and stop if it fails. PowerShell does not automatically stop after every failed native command. $LASTEXITCODE reports that command's exit code; zero means success. A log records output, but its existence does not prove success.

  1. Configure the independent application: 
    cmake -S "C:/SDKs/Umicom/share/umicom-framework/examples/sdk_environment" -B "C:/umicom/_local/build/sdk-environment" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_EXPECTED_SDK_PREFIX=C:/SDKs/Umicom -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\configure.log"
    CMake should report the agreeing environment identifiers and the producer and consumer compiler versions. It must finish configuration and generation successfully before you continue.
  2. Compile and link: 
    cmake --build "C:/umicom/_local/build/sdk-environment" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\build.log"
    This builds the small consumer. It does not rebuild Framework source.
  3. Run the registered test: 
    ctest --test-dir "C:/umicom/_local/build/sdk-environment" --output-on-failure --no-tests=error --output-log "C:/umicom/_local/logs/sdk-environment/tests.log"
    The expected test name is sdk.environment.consumer.
  4. Run the program directly when you want to read its output: 
    & "C:\umicom\_local\build\sdk-environment\umicom-sdk-environment-example.exe" 2>&1 | Tee-Object "C:\umicom\_local\logs\sdk-environment\run.log"
    It prints the header version, required ABI, actual pointer size and the status text returned by the linked base library. These are expected behaviours of the example, not evidence that your installation has already passed.

Use the checks in your own CMake project

project(MyFrameworkApplication LANGUAGES C)
find_package(UmicomFramework CONFIG REQUIRED COMPONENTS base)
umicom_require_sdk_environment(2)
umicom_require_installed_sdk_layout("C:/SDKs/Umicom" sdk_headers Umicom::base)

Declare the ABI your application was written against; do not copy the installed package's value into that requirement. Otherwise the comparison would always agree. Call the environment helper after project(... LANGUAGES C), when CMake knows the consumer compiler and pointer size. Use umicom_require_installed_sdk when you also require the complete SDK's public-header contract rather than this example's component layout check.

The example uses C23 static_assert to compare the installed header ABI with its independent requirement and sizeof(void *) with the package's declared pointer size. It then calls umi_status_text(UMI_STATUS_OK). The real symbol makes a successful link more informative than printing only header constants.

Recover from a refusal

DiagnosticNext action
Package outside the expected prefixInspect the cached UmicomFramework_DIR. Use a fresh consumer build directory and the intended prefix. Do not borrow archives from another SDK.
Environment metadata unavailableInstall the current package files together with their matching headers and libraries.
ABI or header assertion differsReview the API and ABI changes, then select a compatible SDK or adapt the application. Changing only the number hides the disagreement.
System, pointer size or compiler family differsBuild/select an SDK for the intended consumer toolchain and target. This conservative helper does not approve cross-family combinations.
Compile, link or runtime failure after metadata agreesKeep the first diagnostic and compiler versions. Investigate the actual archive, target architecture, options and runtime dependencies. Metadata agreement is not a repair.

Maintain one Framework identity

Framework's numeric version fields, version string and ABI identifier are published in include/umicom/base/version.h. The package generator and passive sdk.properties receipt now read that same source. The package generator refuses duplicate definitions, unsupported numeric forms, out-of-range values, a conflicting version string, or a project version that disagrees with the header.

The parser expects the canonical plain decimal definitions used by that header; it is deliberately not a C preprocessor. The version components fit the public UmiVersion fields. An ABI number is a release-maintained contract identifier, not a computed proof that every exported function remains compatible.

Metadata regressions are registered as framework.sdk.identity.* and framework.sdk.environment.*. Their synthetic fixtures exercise refusals without compiling libraries. Keep those results separate from this real installed consumer and from the product's complete runtime qualification.

Continue with background-task ownership and shutdown through the installed SDK to exercise lifecycle contracts beyond the base-library call.

Record checks without manufacturing a passing result

UmiSdkConformance stores three caller-reported counts: checks run, passed and failed. Start with a zero-initialized value. Empty evidence is valid data, but it is not a passing result. Every completed check must contribute to exactly one outcome, so checks_run == checks_passed + checks_failed.

Use the checked recording function when writing a consumer. It validates that invariant and refuses an exhausted counter before modifying the summary. Always inspect the returned status before using the summary's verdict:

#include "umicom/sdk/conformance.h"

static UmiStatus record_consumer_result(UmiSdkConformance *checks,
                                        UmiStatus observed_status,
                                        int *out_all_passed)
{
    if (out_all_passed == NULL) return UMI_STATUS_INVALID_ARGUMENT;
    UmiStatus recorded = umi_sdk_conformance_record_checked(
        checks, observed_status == UMI_STATUS_OK);
    if (recorded != UMI_STATUS_OK) {
        /* The previous summary is not evidence for this refused observation. */
        return recorded;
    }
    *out_all_passed = umi_sdk_conformance_passed(checks);
    return UMI_STATUS_OK;
}

The caller initializes UmiSdkConformance checks = {0}; once for a collection and passes its address. The output verdict is written only when recording succeeds. observed_status above is the actual result produced by your check. The recorder does not run a compiler, inspect a library or determine whether that check was sufficient. Keep skipped and unexecuted work separate; do not turn either into a passed observation. A complete release needs the identified checks required by its qualification plan.

Validation uses subtraction after checking the passed count against the total. Adding two untrusted size_t counts could overflow and make inconsistent data appear valid. Checked recording returns INVALID_STATE for inconsistent summaries and CAPACITY_EXCEEDED when no further total can be represented. Every refusal preserves the checked API's input bytes.

The older umi_sdk_conformance_record function remains available. Because it cannot return an error, a refused recording sets its failed count to SIZE_MAX. This latch prevents a dropped observation from leaving a passing verdict and retains the other counts for diagnosis. Reinitialize the entire structure to start a new collection; do not edit only the failure field to hide an error.

umi_sdk_conformance_passed now requires a consistent, nonempty summary with no failures. umi_sdk_report_format refuses inconsistent evidence and stages complete text before writing the caller's buffer. If the output buffer is too small, its previous contents remain unchanged; check the status before displaying them. These operations require serialized ownership and supply no thread lock.

Compare toolchain declarations in native C

UmiSdkToolchainEvidence is a record supplied by its caller. Its compiler name, version and architecture must now be nonempty C strings, and its pointer size must be nonzero. Validation does not discover a compiler, parse a version range or inspect machine code. An unrecognized nonempty architecture remains an explicit declaration, not a verified capability.

umi_sdk_toolchain_compare compares two valid records and returns flags for each differing field. A successful return means comparison completed, even when fields differ. The result contains values only and retains no input pointers; keep the input strings readable and unchanged until the synchronous call returns. Invalid input leaves the result bytes unchanged.

This complete metadata-only example deliberately supplies different version strings. It performs no compiler discovery or SDK file access:

#include "umicom/sdk/toolchain.h"
#include <stdio.h>

int main(void)
{
    UmiSdkToolchainEvidence producer = {"GNU", "14.1", "x86_64", 8};
    UmiSdkToolchainEvidence consumer = {"GNU", "14.2", "x86_64", 8};
    UmiSdkToolchainComparison compared;
    UmiStatus status = umi_sdk_toolchain_compare(&producer, &consumer, &compared);
    if (status != UMI_STATUS_OK) return 2;
    int written = printf("Declared fields differing: %u\n",
                         (unsigned)compared.differing_fields);
    if (written < 0 || fflush(stdout) != 0 || ferror(stdout)) return 2;
    return compared.declarations_match ? 0 : 1;
}

Link this program with Umicom::sdk. For these explicit inputs the version-difference flag is set and the program returns 1. The expected result describes the example; compile, link and run it against your selected SDK before recording actual qualification evidence.

FlagDeclaration compared
UMI_SDK_TOOLCHAIN_DIFFERENT_COMPILERCompiler identifier
UMI_SDK_TOOLCHAIN_DIFFERENT_VERSIONComplete version string
UMI_SDK_TOOLCHAIN_DIFFERENT_ARCHITECTUREArchitecture identifier
UMI_SDK_TOOLCHAIN_DIFFERENT_POINTER_SIZEDeclared pointer bytes

Strings compare exactly and case matters. amd64 and x86_64 therefore differ, as do 14.1 and 14.1.0. Normalize records through an explicitly chosen discovery policy if that is your application's requirement. The comparison itself does not silently substitute aliases, infer instruction sets or approve a compiler-version change. Equal declarations still need the independent consumer, runtime and lifecycle checks described above.

Check what an application requires from a declared SDK

A consumer is an application using the SDK. Its requirement record names a minimum Framework version, a nonzero ABI number and the targets it expects. An ABI describes the binary calling contract. A manifest supplies a declared version, ABI and component inventory. These records are ordinary data: constructing one does not inspect an installation or load a library.

  1. Keep arrays and counts together. A nonzero target count requires a readable target-pointer array, and a nonzero component count requires readable component records. Validators now reject null arrays and counts whose byte extent cannot be represented before indexing. C pointers do not encode allocation length, so callers must still supply the full declared storage and NUL-terminated strings.
  2. Validate the complete inputs. umi_sdk_requirement_validate rejects a zero ABI requirement, matching the existing consumer contract. An empty target or component inventory is valid. The same-major minimum-version and minimum-ABI-number comparison policy is retained; neither rule replaces binary qualification.
  3. Separate comparison completion from satisfaction. umi_sdk_consumer_check returns UMI_STATUS_OK after comparing valid declarations. Read declarations_satisfied for the policy result and the missing-target fields for diagnosis. Invalid declarations leave every output byte unchanged, so do not display an old result after a failed call.

This complete C example uses deliberately illustrative version and ABI values. Its supplied manifest lacks the media target; it does not describe your installed SDK:

#include "umicom/sdk/consumer.h"
#include <stdio.h>

int main(void)
{
    const char *required[] = {"Umicom::base", "Umicom::media"};
    const UmiSdkComponent components[] = {{"base", "Umicom::base", 1}};
    UmiSdkConsumer consumer = {
        "example.application", {{3, 4, 5}, 7}, required, 2
    };
    UmiSdkManifest manifest = {{3, 4, 5}, 7, components, 1};
    UmiSdkConsumerCheck result;
    if (umi_sdk_consumer_check(&consumer, &manifest, &result) != UMI_STATUS_OK)
        return 2;
    int written = printf("Missing target entries: %zu\n", result.targets_missing);
    if (written < 0 || fflush(stdout) != 0 || ferror(stdout)) return 2;
    return result.declarations_satisfied ? 0 : 1;
}

Link with Umicom::sdk. For these declarations, the expected missing count is 1, the first missing index is 1 and the program returns 1. The output status is an expected example result, not execution evidence. Change the declared inventory to include the second target and compare again; then separately configure and link a real consumer against an explicitly selected SDK.

Result fieldMeaning
targets_checkedNumber of required entries examined, including duplicates.
targets_missingRequired entries with no exact target-name match in the supplied inventory.
first_missing_indexFirst absent required entry, or SIZE_MAX when none are absent.
version_abi_compatibleDeclared version and ABI satisfy the existing metadata policy.
declarations_satisfiedVersion/ABI policy matches and no required entry is missing.

Names compare exactly and case matters. An optional component still belongs to the supplied inventory. Extra targets are allowed, and duplicated required entries are counted separately rather than silently deduplicated. The result contains no borrowed pointers and remains readable after inputs are released. During the call, keep inputs stable and use separate output storage. There is no internal lock. Work can grow with the product of the two inventory counts; bound untrusted lists before submitting them.

umi_sdk_manifest_current describes the linked Framework, not an arbitrary SDK on disk. Use the installed-SDK inspection workflow when you need evidence about a selected prefix, then perform independent compile, link and runtime checks. A matching declared target name is not proof that its library exists or exports the required functions.
