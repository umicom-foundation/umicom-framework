Read amendment history in bounded pages

Include umicom/data/record_history_page.h and link Umicom::data. The query returns up to 16 amendment rows, newest first, for one entity. It works with metadata-only history and the metadata of atomic record documents. It does not require GTK or create a worker.

Read the first and following pages

  1. Allocate a UmiRecordHistoryPage. Call umi_record_history_page with the Data Server, entity ID, expected head zero, before revision zero and a page size from 1 to 16.
  2. Check the returned status before reading the output. count gives the number of rows. head_revision identifies the latest revision observed in this transaction.
  3. If next_before_revision is nonzero, pass it as the next exclusive cursor and pass the returned head_revision as the expected head. The next page starts immediately before that revision. Reuse the same entity.
  4. Stop when the returned cursor is zero. Do not pass zero again as a continuation; zero requests the first page.
  5. If a continuation returns INVALID_STATE, storage has advanced or the requested cursor is outside the current range. Retain the existing visible page and ask for a fresh first page. Do not append stale output as though the request succeeded.
UmiRecordHistoryPage page;
UmiStatus status = umi_record_history_page(server, "fictional-review",
    0, 0, UMI_RECORD_HISTORY_PAGE_CAPACITY, &page);
/* Display only after status == UMI_STATUS_OK. */
if (status == UMI_STATUS_OK && page.next_before_revision != 0) {
    status = umi_record_history_page(server, page.entity_id,
        page.head_revision, page.next_before_revision,
        UMI_RECORD_HISTORY_PAGE_CAPACITY, &page);
}

Understand consistency and limits

Each query owns one Data Server transaction, covering the head, page rows and preceding boundary. It validates metadata identity, canonical revision numbers and timestamp order within that range. It publishes the output only after the transaction commits. An existing caller transaction returns BUSY and remains owned by the caller. Other failures roll back the query; rollback failure reports IO_ERROR.

The head check detects normal appends between requests. It is not a cryptographic snapshot token and does not detect a malicious replacement of an entire store under the same head. Pages do not verify every earlier link or payload. Use umi_record_document_load for selected content and umi_record_document_verify for the complete content history. Provenance labels are not authentication.

A missing entity returns NOT_FOUND. A missing row inside a requested range also returns NOT_FOUND, while malformed metadata or reversed timestamps return PARSE_ERROR. Neither case means an empty successful history. The caller output stays unchanged on every error. A cursor of one returns an empty successful page because there is no revision zero.

Try the installed example

Copy the installed share/umicom-framework/examples/data_history directory to a writable example workspace and run these commands there. Stop if a command fails.

cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH="C:/umicom/installed/applications"
cmake --build build --target umicom-record-history-page-example --parallel 2
ctest --test-dir build -R "^consumer.record-history-pages$" --output-on-failure --no-tests=error

The example uses only fictional in-memory metadata. Expected program output is History head 19: 19 revisions across 2 pages. Native hosts can use the record editor's history pane, which dispatches reads on a storage worker and keeps historical content read-only.
