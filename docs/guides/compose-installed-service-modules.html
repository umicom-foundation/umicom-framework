Compose application modules with the Framework SDK

An application often has one part that supplies data and another that uses it. A document editor supplies text to a search panel; a market-data connection supplies prices to a chart. Each part needs to know when its dependency is available and when it is safe to stop using it. Framework's module controller and service registry keep these responsibilities explicit.

This example uses a small counter instead of files or a financial account. One module creates the counter and publishes it as a shared service. A second module borrows it and changes its value. The example needs no graphical session, credentials or network. It demonstrates ownership and lifecycle contracts, not a complete editor or trading application.

Understand the two kinds of registration

A capability names something a module can provide. A service is the actual object another module can use. The provider declares the capability example.counter when its module is registered. Its configure callback allocates and registers the real counter. The consumer declares the same capability as a requirement. Framework therefore starts the provider before configuring the consumer.

Registration order is deliberately reversed in services.c: the consumer is registered first. This lets the example check that declared dependencies, rather than incidental registration order, control startup.

The example also copies provider metadata before stopping. The names remain readable after the owned counter is destroyed, while a fresh lookup reports that the service was removed. This separates a diagnostic observation from a live dependency.

Read the four source files

FileResponsibility
composition.hDeclares the application-owned state and its two borrowed module descriptors.
services.cDefines provider and consumer callbacks, ownership transfer and capability admission.
main.cSelects a scenario, checks observable results and always attempts checked release.
CMakeLists.txtSelects one installed SDK and registers five focused checks.

The provider passes UMI_SERVICE_OWNED when registering the counter. If registration succeeds, the registry calls DestroyCounter when the service is removed. If registration fails, ownership never transferred, so the provider frees its allocation itself. The descriptor strings are copied by the service registry; the counter and callback payload have separate lifetimes.

The consumer stores a borrowed counter pointer. Its successful stop clears that pointer before the provider removes the service. A failed stop leaves the pointer and provider alive so the owner can retry. Do not free the application state merely because a stop call returned an error.

Build against an installed SDK

Install an updated Framework SDK containing the runtime component using the repository's build and install instructions. The example is installed under share/umicom-framework/examples/service_composition. An older SDK without the checked release and registration contracts cannot run this example.

The following PowerShell commands assume the SDK is installed at C:\umicom\installed\framework. Replace that path consistently if your installation is elsewhere. These commands compile the small consumer and link installed libraries; they do not add Framework's source directory to the build. Run each command separately and stop if it reports an error.

New-Item -ItemType Directory -Force "C:\umicom\_local\logs\service-composition"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

cmake -S "C:\umicom\installed\framework\share\umicom-framework\examples\service_composition" -B "C:\umicom\_local\build\service-composition" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DUMICOM_EXPECTED_SDK_PREFIX="C:/umicom/installed/framework" -DBUILD_TESTING=ON 2>&1 | Tee-Object "C:\umicom\_local\logs\service-composition\configure.log"

cmake --build "C:\umicom\_local\build\service-composition" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\service-composition\build.log"

ctest --test-dir "C:\umicom\_local\build\service-composition" --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\service-composition\tests.log"

& "C:\umicom\_local\build\service-composition\umicom-service-composition-example.exe" stop-retry 2>&1 | Tee-Object "C:\umicom\_local\logs\service-composition\run.log"

A successful configure must use the requested installation. The example checks the resolved package configuration, installed header layout and SDK environment metadata. A cached package from another prefix is refused. Use a separate build directory when changing SDK installations or compiler families; do not bypass an environment mismatch by adding unrelated include paths.

Understand each check

ScenarioExpected behaviour
normalThe provider starts first, the consumer changes its counter to one, and shutdown releases everything in dependency order.
corrected-registrationA duplicate capability rejects the whole module admission. No partial marker remains. Corrected input can register the same module identity.
startup-failureA deliberate consumer start error causes rollback. The configured consumer releases its borrowed pointer before the counter is destroyed. A later start can succeed.
stop-retryThe first consumer stop returns an error. Its counter remains alive, restart is refused, and a second stop completes cleanup.
restartTwo start/stop cycles create separate counter lifetimes. Stopping does not destroy reusable module descriptors.

Successful runs print Service composition passed: followed by the scenario name and exit with code zero. CTest should report five passing checks. This is an expected result to verify on your installation, not a claim about an unexecuted build. Checks use explicit conditions rather than assert, so release-build settings do not remove them.

Investigate a failure

  1. Read the first reported configure or link error. A missing checked-release symbol usually means the selected archive predates the header used by the consumer. Confirm that the SDK's headers and libraries came from the same build.
  2. For a scenario failure, read its named condition. Compare the provider's registration and destruction counters before changing callback order.
  3. For a retained controller, keep application state alive and investigate the failed phase. Real applications should expose a retry or a controlled shutdown error. Do not repeatedly call a void destroy function and assume cleanup happened.
  4. For new modules, declare real requirements, make failed configure unwind its own partial work, and make stop support configured but not fully started state. Keep successfully registered descriptors and capability arrays unchanged until the controller has been released.

This example uses serial callbacks which return normally. It does not prove thread safety, force a blocked callback to return, or provide concurrent service snapshots. Applications with workers must first stop and join those workers. Continue with background service composition, module lifecycle retries and shared service ownership.
