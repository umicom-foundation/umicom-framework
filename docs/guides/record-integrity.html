Checking transaction history

A record chain links each record to the digest of its predecessor. A digest is a fixed-size summary of bytes. Umicom Framework uses the existing SHA-256 service to detect changes relative to a checkpoint that you saved separately.

This C23 component performs no file or network operations. It does not transfer money, authenticate people, encrypt records, run smart contracts or agree a blockchain history with other computers. An attacker who can replace both your records and your expected checkpoint can create a different internally consistent history. Retain the expected checkpoint through a separately trusted process.

1. Build an installed SDK consumer

The example requires an installed Framework SDK containing Umicom::record_chain and its base dependency. From the Framework source directory, configure the example with your SDK installation prefix:

cmake -S examples/record_chain -B build/record-chain-example -G Ninja -DCMAKE_PREFIX_PATH=C:/umicom/installed/applications
cmake --build build/record-chain-example --parallel 2
ctest --test-dir build/record-chain-example --output-on-failure --no-tests=error

The example creates a synthetic receipt, encodes and decodes it, then verifies its payload against a retained endpoint. A successful run prints Verified one synthetic record and exits with zero. A missing component means the selected SDK predates this capability or was installed incompletely; do not substitute headers from an unrelated source checkout.

2. Choose a source identity and payload schema

Supply a stable, nonzero 32-byte chain identity for each history. Keep different databases and incompatible payload schemas separate. A kind is a nonzero 32-bit application-defined schema identifier. Define exact payload bytes, including integer encoding and text normalization, before appending records. Never hash C structures directly: compiler padding and machine byte order are not a portable format.

UmiRecordChainCheckpoint checkpoint;
UmiRecordChainRecord receipt;
/* chain_id contains the host's stable source identity. */
UmiStatus status = umi_record_chain_start(chain_id, &checkpoint);
if (status == UMI_STATUS_OK)
    status = umi_record_chain_append(&checkpoint, kind,
        canonical_bytes, byte_count, &receipt);

Serialize access to each checkpoint. Inputs and output objects must not overlap; the checkpoint itself is updated in place. Failed operations leave outputs and the checkpoint unchanged. Empty payloads are supported. Each payload is limited to 16 MiB, and each verification batch to 4,096 records.

3. Verify the complete intended history

Start from a previously trusted checkpoint. Each UmiRecordChainInput borrows a receipt and the exact corresponding payload bytes. Pass the separately retained endpoint to umi_record_chain_verify. Verification checks identity, sequence, predecessor, payload digest, record digest and final endpoint before updating the checkpoint.

Reordered, duplicated or removed records fail. A valid prefix also fails when the expected endpoint represents a longer history. umi_record_chain_accept checks one next record only; callers using that lower-level function must still compare their final checkpoint themselves.

4. Store and exchange portable values

Use archive.h to encode an 80-byte checkpoint or a 156-byte receipt. Decoders require the exact size and reject trailing bytes and unknown schema markers. Decoding a receipt checks its own digest but does not verify its payload or its position in a history; call acceptance or batch verification afterward. Decoding a checkpoint does not establish its trust.

EnvelopeFields in order
Checkpoint, 80 bytes8-byte URCP marker (version 1), 32-byte identity, 8-byte sequence, 32-byte digest.
Receipt, 156 bytes8-byte URCR marker (version 1), 32-byte identity, 8-byte sequence, 4-byte kind, 8-byte payload size, 32-byte predecessor, 32-byte payload digest, 32-byte receipt digest.

Integers use big-endian byte order. Markers are the four ASCII letters followed by bytes 0, 0, 0, 1. Genesis hashes the ASCII bytes UMICOM-RECORD-CHAIN-GENESIS:1, one LF byte and the identity. The receipt digest hashes UMICOM-RECORD-CHAIN-RECORD:1, one LF byte and the 116 field bytes after its marker and before its final digest. No NUL terminator is included. The payload digest hashes only the payload bytes.

5. Inspect Bank and Exchange event histories

UmiBankOperationsCheckpoint commits to retained UBO1 event text using kind 0x55424f31. UmiFinanceOperationsCheckpoint commits to UFIN1 commands using kind 0x55464931. Both reuse their existing canonical persistence codecs without the text terminator. They cover complete command histories, including approvals and reversals, rather than only current balances.

Pass the revision you observed. BUSY means the local view changed: inspect it again before capturing a new anchor. These calls inspect cached state and do not reload storage. A poisoned service is refused; financial operations also refuse a view left behind by a failed reload. Explicitly reload or reopen the underlying service through its normal API to observe external changes.

Capture, independently retain, and later compare checkpoints with the same source identity. Changing actor, payload or order changes the commitment. An identical idempotent request adds no event, so it does not change the checkpoint. The adapter does not establish a real bank balance or external trade settlement.

Privacy and application integration

Keep raw events and integrity anchors within their existing access policy. A digest of predictable private data can be guessed, so hashing is not anonymization. No checkpoint is automatically posted to a public chain or website. Native GTK4 hosts, C23 web services and other SDK consumers can share this library; authentication, durable anchor retention and any later signing service belong to explicit host boundaries.

Focused qualification

Developers can build the production receipt sources and base hash without compiling every application:

cmake -S tests/record_chain -B build/record-chain -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/record-chain --parallel 2
ctest --test-dir build/record-chain --output-on-failure --no-tests=error

The focused suite includes a real installed-consumer exercise that relocates a new SDK prefix and builds the independent example. Its stage logs remain below the build directory. Financial integration cases are part of the full Framework build and have names beginning framework.record_chain.bank. and framework.record_chain.finance.. These checks do not qualify network consensus, signing, payment-provider connections or a graphical workflow.
