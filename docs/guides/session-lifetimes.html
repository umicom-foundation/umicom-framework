Own an application session

A session records which principal signed in and when that access expires. A principal is a stable identifier for a person or service. The session registry stores active sessions in memory; it does not verify a password, grant permissions, encrypt traffic or persist sign-ins across a restart.

Issue and use a session

  1. Authenticate the principal with the application's trusted identity provider. Verify that the identity is currently enabled.
  2. Create a registry with umi_session_registry_create, then call umi_session_registry_issue with the principal ID, a trusted nanosecond clock value and a nonzero lifetime.
  3. Keep the returned handle private and opaque. Do not derive another handle, parse its suffix or write it to application logs. The registry uses the operating system's random source and fails issuance if that source is unavailable.
  4. Before an operation, call umi_session_registry_validate with a current trusted clock value. Then check current identity enablement and the requested resource policy. A valid session alone does not authorize access to a record.
  5. Revoke the handle when the user signs out. Use cleanup to remove revoked or expired records. Destroy the registry only after all callers have stopped using it.

Clock and failure behavior

Expiry is exclusive: a session is invalid when the supplied time reaches its expiration. Issuance refuses an expiration that would overflow the 64-bit clock value. Validation also refuses timestamps before issuance or before the last accepted activity time. A clock rollback does not move activity backwards; wait for trusted time to catch up or require a fresh authenticated session according to application policy.

Expired sessions are deactivated and cannot be revived by submitting an earlier time. Other clock refusals preserve the stored session. Failed issue and validate calls leave the output record unchanged. A full registry requires explicit cleanup or a deliberate application limit; it never silently evicts an active session.

Scope of protection

Handles contain random bytes obtained through Framework's platform service. This is not a complete web login implementation. Applications still need a secure transport, protected credential handling, request validation, revocation policy and current authorization checks. Do not expose internal registries or issuance APIs to untrusted callers. There is no automatic refresh or extension of expiration.

Focused checks

cmake --build build/windows-ucrt64-debug --target umicom-session-lifetime-test umicom-session-entropy-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework[.]security[.]session[.]" --output-on-failure --no-tests=error

The lifetime target uses the platform random service. The entropy target links the production registry to a deterministic test double to exercise failure, collision retry and capacity without weakening the public API.
