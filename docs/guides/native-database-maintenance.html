Native database health and recovery

The shared GTK4 panel inspects an existing SQLite Data Server and creates independent database copies. Applications supply authorization and decide which database to use. The panel does not replace an application's open store.

Use the panel

  1. Choose an existing SQLite database in the first row. Selecting a filename does not open it yet.
  2. Select Check database. The worker runs SQLite quick_check. A completed check may report problems; absence of diagnostics does not authenticate data or validate application rules.
  3. For a backup, choose a new filename in the second row and select Create backup. The destination must not exist. SQLite copies its committed snapshot, including WAL changes.
  4. To recover a saved database into a separate file, choose that saved file as the source and another new filename as the destination. Select Recover to new database.
  5. Inspect the newly created database before configuring your application to use it. The original file and active database stay available.

Integrate with an application

Link Umicom::database_maintenance_gtk4 and include umicom/ui/gtk4/database_maintenance.h. Create UmiDatabaseMaintenanceGtk4Options with a required authorization callback. That callback runs on the GTK thread with copied operation, source and destination values before any storage work starts. Authorize each selected path under your application's access policy; do not use an unconditional success callback for protected records.

GtkWidget *panel = NULL;
UmiDatabaseMaintenanceGtk4Options options = {
    .authorize = authorize_database_operation,
    .authorize_context = application
};
UmiStatus status = UmiDatabaseMaintenanceGtk4New(&options, &panel);
if (status == UMI_STATUS_OK)
    gtk_box_append(GTK_BOX(container), panel);

Connect operation-finished to receive an integer UmiStatus, then read UmiDatabaseMaintenanceGtk4State. The method return value describes admission, not completion. For a health check, inspect health.sound. For a successful copy, inspect the captured destination, page count and key/value record count.

Closing and editing

CanClose is false while admission or a worker operation is in progress. Retire the panel when abandoning its UI, and keep the main context alive until completion. A read is discarded after the selection changes. An accepted copy can still finish and its real outcome remains in the copied state even after retirement. There is no mid-operation cancellation and no automatic undo of file creation. A rejected new call preserves any earlier completed result; use its return value to diagnose the rejection.

Recovery guidance

If the destination exists, choose a different filename. If SQLite is busy, finish the other transaction and explicitly try again. A failure after exclusive destination creation may retain an empty or partial new file for inspection. No existing file is deleted. Run these operations beneath trusted directories; the service is not a sandbox against concurrent filesystem replacement. Backups are not encrypted and quick_check does not prove application-level correctness or power-loss durability.
