Editing saved searches in GTK4

A saved search stores a title, conditions and the record namespace it searches. The reusable search-draft widget keeps incomplete text visible while a portable session tracks the last valid definition. It performs no file or database access.

Add an editor to a native application

  1. Link Umicom::structured_form_search_draft_gtk4 and include umicom/ui/gtk4/structured_form_search_draft.h. Initialize GTK on its owner thread.
  2. Keep the form schema immutable and alive. Call UmiStructuredFormSearchDraftGtk4New with that schema and a fixed record prefix. Parent the returned floating widget or take a reference.
  3. Use Begin for a new form.search. identifier or Open with a verified record document. A new search is unsaved. Opening a stored search establishes its baseline.
  4. Let the user edit the title, metadata text and typed conditions. State reports the last accepted model. Accept validates current controls. An incomplete number or empty title remains visible and does not replace that model.
  5. Call CanClose from the application's close decision. It accepts valid visible text, then returns false for unsaved changes, incomplete values or a pending save. Offer Save, explicit Discard, or return to editing.

Save without losing later typing

  1. Authorize the write and obtain attribution from the application's identity service.
  2. Call PrepareSave. Copy the request to a serialized storage worker and retain the widget until completion. The request is an immutable snapshot.
  3. Run umi_record_save_request_commit on the selected Data Server. Return the status and saved revision to the GTK owner thread.
  4. Always call FinishSave, including when dispatch fails. A failure leaves the draft available for retry. Completion after retirement or disposal still records the real save outcome; it does not overwrite text typed after preparation.

CanClose may accept later valid text into the model. A successful save only advances the captured baseline. If the user typed again, those edits remain unsaved. Keep processing worker completion before releasing the last widget reference.

Recover an interrupted draft

  1. Call Capture when no save is pending. It accepts valid native values and returns a snapshot of the baseline and current definition. Invalid visible text cannot be captured by this typed interface; leave the editor open so the user can correct it.
  2. Use the record draft snapshot codec and the application's private file-storage policy to persist the snapshot. This format is plaintext and does not supply encryption or access control.
  3. When reopening, choose and authorize the database first, then call umi_record_draft_snapshot_check_store. It checks the baseline against that database but cannot prove database identity.
  4. Create a matching widget and call Restore. Both baseline and current content must match the exact form schema and fixed record namespace. A later save still checks the stored revision.

Recovery and integration limits

Opening, beginning or restoring another search refuses unsaved valid native edits. Invalid current text also blocks replacement. Explicit Discard restores stored controls or closes a new search. Controls retained from a replaced body cannot modify the active draft.

A GTK observer can retire the widget while controls are replaced. In that case the operation reports cancellation even though its portable transition was accepted; inspect State before disposing the host. Do not retry blindly. All widget calls belong on the GTK thread.

This component supplies a reusable editing surface. Applications must connect their own file chooser, close prompt, storage worker and authorization. Existing record-browser search controls do not automatically acquire this close/recovery workflow merely by linking the component.

Focused regression commands

After configuring a GTK-enabled Framework build:

cmake --build build/windows-ucrt64-debug --target umicom-search-draft-gtk-test
ctest --test-dir build/windows-ucrt64-debug -R "^framework[.]structured_forms[.]search-draft[.]gtk[.]" --output-on-failure --no-tests=error

These tests require a display. A missing display is reported as skipped, not passed. The cases cover dirty-close decisions, stale controls, recovery scope and worker completion after disposal.
