A useful Problems panel connects compiler feedback to an editable document. This guide explains the shared services behind that connection and builds a small reader that you can run before adding any graphical controls.

From output text to a source location

A compiler produces text. An IDE needs structured information: severity, source path, line, column and message. Framework's compiler parser supplies these fields, and its existing build adapter converts them to UmiBuildDiagnostic. The Problems model and the build result therefore use the same compiler grammar.

Windows paths contain a colon after the drive letter. Splitting at the first colon would turn C:/Umicom Notes/main.c into the wrong path. Framework reads recognised numeric location suffixes from the right, retaining the drive letter and directory names.

Supported text includes common GCC/Clang path:line:column messages, MSVC path(line,column) messages, and CMake location headers. Ordinary source excerpts and progress messages are not automatically errors merely because they contain the word “error”. ANSI colour and erase-to-end sequences are ignored; the parser is not a terminal emulator or a universal parser for every compiler locale and output format.

Build a diagnostic reader

The complete example is at framework/examples/build_diagnostics. It reads an example diagnostic without opening or changing a source file. The caller owns both the input string and the output record.

/*-----------------------------------------------------------------------------
 * Umicom Framework
 * File: examples/build_diagnostics/main.c
 * PURPOSE: Read a compiler message for an Umicom Notes source file.
 * AUTHOR AND ORGANISATION: Sammy Hegab, Umicom Foundation
 * LICENCE: MIT
 *---------------------------------------------------------------------------*/
#include "umicom/build/parser.h"
#include <stdio.h>
#include <string.h>

int main(int argc, char **argv)
{
    const char *line = argc > 1 ? argv[1] :
        "C:/Umicom Notes/src/main.c:8:5: error: expected ';' before return";
    UmiBuildDiagnostic problem;
    UmiStatus status = umi_build_parse_diagnostic_line(line, &problem);
    if (status != UMI_STATUS_OK) {
        fprintf(stderr, "No complete compiler diagnostic: %s\n", umi_status_text(status));
        return 1;
    }
    printf("Source: %s\nLine: %zu\nColumn: %zu\nMessage: %s\n",
        problem.file, problem.line, problem.column, problem.message);
    /* The default invocation is also a useful check for CTest. */
    if (argc == 1 && (strcmp(problem.file, "C:/Umicom Notes/src/main.c") != 0 ||
        problem.line != 8U || problem.column != 5U)) return 1;
    return 0;
}

The return status matters. Use the record only when parsing returns UMI_STATUS_OK. NOT_FOUND means that the line was not recognised. CAPACITY_EXCEEDED means that retaining it would require shortening a field; the parser does not invent a navigable cropped path.

The default test input names an Umicom Notes file on Windows. You can pass another quoted compiler message as the first argument. This program tests message parsing, not compilation of that named file.

Compile the example on Windows

First build and install the updated Framework SDK into a fresh development directory. The example below assumes C:\umicom\installed\studio-diagnostics. Use your actual installation path.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S ".\framework\examples\build_diagnostics" -B ".\build\notes-diagnostics" -G Ninja -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_PREFIX_PATH="C:/umicom/installed/studio-diagnostics"
cmake --build ".\build\notes-diagnostics" --parallel 2
ctest --test-dir ".\build\notes-diagnostics" --no-tests=error --output-on-failure
& ".\build\notes-diagnostics\umicom-notes-diagnostics.exe"

Each command has a separate purpose: configure the build, compile the example, run its test, then start it directly. Stop when a command reports a failure.

Compile the example on Linux

With the Framework SDK installed under your home directory:

cd "$HOME/umicom/Umicom-Applications"
cmake -S framework/examples/build_diagnostics -B build/notes-diagnostics -G Ninja -DCMAKE_PREFIX_PATH="$HOME/umicom/installed/studio-diagnostics"
cmake --build build/notes-diagnostics --parallel 2
ctest --test-dir build/notes-diagnostics --no-tests=error --output-on-failure
./build/notes-diagnostics/umicom-notes-diagnostics

The example links Umicom::build. It does not include private implementation files or compile a second copy of the parser.

Connect a source viewer

The diagnostic pipeline owns retained problem records. UmiDiagnosticNavigationSource selects the next or previous unresolved local source problem through a caller-owned navigation cursor. It scans the entire retained model rather than stopping at a query page boundary. A stable diagnostic ID is suitable for a visible row; an index can point elsewhere after insertion or removal.

UmiDiagnosticOpenSource passes the chosen local path to the existing document coordinator. An open file selects its existing draft. A relative path requires an explicit absolute base directory. The operation does not execute a tool, save a file or discard another tab.

UmiDocumentCoordinatorGoToPosition places the caret using a one-based line and UTF-8 byte column. It clamps an excessive column to the line end and avoids placing the caret in the middle of a UTF-8 sequence. A missing line reports NOT_FOUND; the open source is still available for inspection.

Keep messages complete and bounded

The build record supports paths up to 2,047 bytes. The existing Problems snapshot supports a smaller URI field. A path that cannot fit is retained in build evidence, but the projected row has no cropped navigation target and explains why Output is needed.

Build results keep a bounded diagnostic list and a dropped count. Oversized lines and fields are counted instead of being silently shortened into an apparently complete problem. The build transcript also has its existing capture limit; a complete external build log is still valuable for unusually large failures.

Positions remain those reported by the compiler. For GCC, display columns and byte columns can differ around tabs and non-ASCII characters. See the official formatting options before selecting a column policy for your own project.

Practise with real messages

Copy the first compiler error from a disposable Notes build and pass it to the example. Check its path and numbers against the saved source. Next try a warning, an MSVC-style message, an ordinary progress line, and a message containing an unusually long path.

For a GUI, keep the model and coordinator on their owning thread. Transfer completed build results to that thread before publishing rows. Do not keep a borrowed pointer to a temporary diagnostic inside a widget callback; copy its stable ID.
