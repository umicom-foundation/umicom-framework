Browser forms with the native Framework

The Umicom::form_web library renders an HTML form and converts a browser submission into a reviewed edit. The implementation is C23. It uses the same typed answers, units, schema versions and validation as the native structured-form editor.

This adapter supplies controls and validation. Your application owns the HTTP server, user authorization, sessions and storage. The example runs offline and does not start a website.

1. Define one shared schema

Create an immutable UmiStructuredFormSchema over your existing field descriptors. Give it a semantic version and one rule per field. Use exact unit identifiers: a submitted value in mass.lb cannot replace a field declared as mass.kg. For financial amounts, use your exact-money service or integer minor units; binary floating point is not an exact monetary representation.

2. Render the reviewed state

umi_web_structured_form_render(schema, form, "/forms/review", session_token,
                               html, html_capacity, &html_length);

Allocate the large form and HTML buffers on the heap. The renderer emits an HTML fragment with associated labels, explicit answer-state selectors and two actions: Apply draft and Validate for submission. It escapes text and attributes, uses a local action path and emits no script. Add your document shell, stylesheet and HTTP headers around this fragment.

Read-only fields are disabled and stay server-owned. Known secret fields are refused rather than reflected into HTML; passwords need a dedicated non-reflecting workflow. A small output buffer returns a capacity error and leaves the old output intact. The maximum HTML buffer is larger than the basic Framework response body: check your chosen response/streaming API before serving large forms.

3. Authenticate before interpreting a POST

  1. Require the expected HTTP method and application/x-www-form-urlencoded content type.
  2. Authenticate the session and authorize access to the requested record. Validate the request origin using your host's policy.
  3. Supply the expected session-bound CSRF token. A token must contain 1–127 ASCII letters, digits, underscores or hyphens. Generate it with a secure token service, never from the example's constant.
  4. Enforce body-size limits before reading the complete request. Do not log raw form bodies, tokens or secret answers.

4. Prepare and apply one edit

umi_web_structured_form_prepare(schema, current, body, body_length,
                                session_token, edit, &submitting);
/* Only after a successful preparation: */
umi_structured_form_edit_apply(schema, current, edit);

Keep these operations within the application's ownership or synchronization boundary. Preparation does not mutate the form. Application checks the revision and old answers again, so another writer cannot redirect an older edit. Only persist after both operations succeed. Use Umicom::form_records for the shared record adapter; edit revision and storage revision are separate values.

A submission must include every editable field. Missing, duplicate, unknown and read-only controls are refused. Form identity, schema version and revision must match the current model. The submit action also checks required answers; draft application permits unanswered required fields. Unknown and not-applicable answers need an allowed policy and a reason.

Input conventions

InputAccepted spelling
Booleantrue or false
IntegerDecimal digits with an optional sign, within signed 64-bit range.
DecimalDot separator, optional exponent; no whitespace, hex, NaN, infinity or suffix.
TimestampInclude Z or an explicit offset, such as 2024-02-29T12:00:00+01:00.
ChoiceThe schema's option identifier, not its translated label.

Numeric parsing is independent of the process locale. Windows UCRT and POSIX locale APIs are supported. Other hosts refuse unsupported decimal conversion. Finite subnormal values can round-trip; overflow and underflow to zero are refused.

The browser keeps inactive value and reason controls so a user can change the state selector without immediately losing their draft. Preparation discards those inactive controls when constructing the accepted answer. That distinction is explicit: unknown is not a stale numeric value with a flag.

Browser submissions normalize line endings. This adapter stores LF text, converts submitted CRLF pairs back to LF, and refuses bare CR. Rendering refuses existing CR-bearing answers so a browser round trip cannot silently change their representation. See the HTML textarea specification and WHATWG explanation of submission normalization.

Troubleshooting

  • Invalid state: reload the current record, compare the user's draft, and prepare a new edit. Never overwrite a newer record to bypass a stale revision.
  • Missing control or parse error: preserve the user's draft in the host view and explain the rejected field or malformed request. Do not apply a partial form.
  • Capacity exceeded: check decoded field limits and request limits. Refuse oversized input rather than truncate it.
  • Permission denied: check host authorization/token handling and whether a secret field is being reflected.
