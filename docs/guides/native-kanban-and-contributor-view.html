Use a native Kanban board and publish a contributor view

A Kanban board groups cards into lists that describe the work's current state. Umicom keeps the board rules, named assignments, saved files and website generation in C23 Framework services. GTK4 presents the native editor. A browser displays the generated HTML and CSS; this first contributor website has no script, editing form or server account.

1. Open the native editor

  1. Use a Framework build containing Umicom::kanban_gtk4. The native tool option also provides umicom-kanban.
  2. Launch umicom-kanban.exe on Windows, or umicom-kanban on a system where it is installed. Studio builds linked to this adapter show Plan development → Open Kanban board on the welcome page.
  3. Choose an existing absolute folder for private board files. For example, create C:\umicom\_local\boards with your file manager, then select it with Browse.
  4. Enter a filename such as development.umikb. Click Create board for a new file or Open board for an existing saved board.

Expected result: five lists appear—To do, Doing, Testing, Blocked and Done. Create refuses an existing filename. Open validates the saved contents. A sibling .lock file coordinates local writers; leave it in place. The editor does not choose a hidden AppData directory or silently overwrite another board.

2. Add, assign and move cards

  1. Type a title and click Add card. The new card appears in To do and becomes selected.
  2. Click an existing card to select it. Edit its title and click Rename selected.
  3. Type a developer's display name and click Assign name, or press Enter in the developer field. Matching names appear below the field. An exact match, ignoring letter case, reuses an existing person. A new name creates a directory entry with a stable internal identifier.
  4. Clear the developer field and assign it to remove an assignment. Names are planning labels, not authenticated accounts or repository permissions.
  5. Drag a card onto another list. Alternatively, choose a destination beside Move selected and click that button.
  6. Click Save board to persist the board and its developer directory.

Expected result: moves and assignments either succeed together with a new board revision, or leave the previous state intact. Moving a card does not execute a build or certify tests. Existing checklist, dependency and work-limit rules still apply. A refused stale edit requires selecting the current card again and reviewing the change.

Edit private card details

  1. Select the card, then expand Edit private card details.
  2. Click Load selected card details. The status identifies the card and board revision that the form belongs to.
  3. Edit its title, description, priority and blocker reason. An empty blocker means the card has no explicit blocker; it does not move the card between lists.
  4. Click Apply card details. Expected result: the card changes once while assignments, acceptance checks, dependencies, labels and due date remain intact.
  5. Click Save board in its host to persist the change. Applying a form alone does not write a board file.

If the board changes, a different card is selected, the form is hidden or the host starts file work, load the selected card again before applying. A refused edit keeps the typed draft so you can review it. Loading explicitly replaces that draft; copy text you need to retain first. Titles and blocker reasons allow 255 UTF-8 bytes and descriptions allow 2047. A long multibyte entry is refused without truncating the board.

Private detail fields are never substituted for the separate public website fields. Review and include public text explicitly. Checklists, dependency editing, labels, deadlines and list limits remain available through the C23 board API; this form does not expose them yet.

3. Save safely and recover from an external change

  1. Save board updates the file opened by the document, even if you have changed the filename field for a later operation.
  2. If another program changes that file, saving refuses the replacement and retains your in-memory edits.
  3. Choose an unused filename in the folder fields and click Save copy to new file. This writes the current board to a new file. It does not overwrite an existing destination or change the original document binding.
  4. After inspecting the copy, explicitly enable Discard unsaved board edits on this close attempt and close the original document. Open the recovered copy to continue working there.

Closing a board or its window refuses unsaved edits unless discard is explicitly selected. File work runs on a worker while editing controls are frozen. A board window opened by Studio owns its document independently: closing Studio's editor window does not discard the board. Forced process termination can still lose unsaved memory.

4. Prepare a public contributor page

  1. Expand Review a public website snapshot.
  2. Enter a public board title. This is separate from the private board title.
  3. Select a card. Enter the title and optional summary you want contributors to see. Enter a developer name only when you intend that name to be public.
  4. Click Include reviewed card. Repeat for every card to publish. Including the same card again replaces its reviewed fields.
  5. Click Generate website. Review the displayed HTML source. Use Save displayed text to save a new HTML file, for example C:\umicom\_local\public-preview\index.html, inside a folder you created.
  6. Open the saved file in a browser and inspect the titles, summaries, assignments and list positions before uploading it.

Only your explicit public fields and each selected card's current list are rendered. Private descriptions, local IDs, developer-directory names, activity, dependency data and storage paths are not copied into the page. All public fields are validated as UTF-8 and escaped as text. An empty selection produces an empty board, not an export of all private cards.

Use Save or reopen a private public-selection plan to retain reviewed public fields. This private plan is separate from the board archive and generated HTML. See saving reviewed publication plans. Regenerate and upload the contributor snapshot after changes; an existing website does not update automatically.

5. Host the contributor view

  1. Create a clean website folder containing only the reviewed index.html.
  2. Upload that file to your chosen static website host. Set it as the site's index document.
  3. Visit the hosted URL in a normal browser and verify the visible cards. Contributors can view the board on desktop and mobile widths without installing GTK.

Keep the private board, its guard file, development logs and internal planning directory out of the upload. This Framework component does not deploy files or provide authentication. Hosting credentials, HTTPS and access policy belong to your chosen host. The page has embedded styling and does not load external assets or trackers.

6. Reuse the feature in a C23 application

find_package(UmicomFramework CONFIG REQUIRED COMPONENTS kanban_gtk4)
target_link_libraries(my_application PRIVATE Umicom::kanban_gtk4)
set_target_properties(my_application PROPERTIES
    C_STANDARD 23 C_STANDARD_REQUIRED YES C_EXTENSIONS NO)

Call the shared window from the GTK owner thread:

#include "umicom/ui/gtk4/kanban_window.h"

GtkWindow *board = UmiKanbanGtk4CreateWindow(application);
if (board != NULL) gtk_window_present(board);

For a host that already owns a board document, use UmiKanbanGtk4Create from umicom/ui/gtk4/kanban.h. That panel borrows the board. Freeze it before a worker accesses the document, refresh it after external edits, and retire it before releasing the document. The window helper manages these steps for ordinary hosts. Use gtk_window_close rather than forcibly destroying an open document window.

Headless applications can link Umicom::kanban alone and call umi_kanban_publication_html with an explicitly reviewed array of UmiKanbanPublicCard. Measure output first with a null buffer and zero capacity; the returned size includes the terminating NUL byte. Allocate that size, render at the same board revision, and write exactly one byte fewer to the HTML file. The renderer performs no file or network operations.

7. Compatibility and limits

  • Saved developer directories use a distinct archive schema. The updated reader accepts older four-list and five-list archives. Older readers refuse named-directory archives; update Framework before opening them.
  • Display names can repeat in the C23 directory. The first native assignment form refuses ambiguous matches; it does not guess which person was intended.
  • The board supports at most 1,024 cards and 128 named developers. Native title and name limits are byte limits, so long multibyte names may be refused without truncation.
  • Drag-and-drop is local to one native board panel. A drag from another application or another board cannot submit a move.
  • The contributor site is a snapshot. Registration, permissions, shared editing and a C23 web service are not supplied by this static export. Private selection plans can be retained separately.

Embedding hosts and forced window removal

Use gtk_window_close for ordinary closure. It keeps the existing checks for pending work and unsaved edits. A host that forcibly calls gtk_window_destroy removes the editor immediately and discards its unsaved in-memory changes; it does not automatically save them.

An already accepted file operation may still finish after forced removal. Its result is not attached to the removed window. The document lease is then released on a worker, even when the host retains a reference to the window. A create or save that already succeeded remains on disk.

  1. Keep a reference to the window while coordinating shutdown.
  2. After removal, use UmiKanbanGtk4WindowBusy(window) on the GTK owner thread to observe pending work and lease cleanup.
  3. Continue processing the main loop until it returns false, then release the retained window reference. Do not block the owner thread in a polling loop that prevents completion callbacks.
  4. Reopen the saved board normally to review its contents. A guard file is not permission to bypass the storage service or delete another editor's lease.

The busy query is a lifetime aid, not proof that a save succeeded. Normal file results appear in the window status. Forced removal has no remaining status surface, and process termination can prevent cleanup callbacks from running.
