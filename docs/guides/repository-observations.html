Repository observations and repair proposals

A repository observation describes what Git reported during a read. It is useful for a source-control panel, a project health view, or a proposal to repair missing repository configuration. It is not a lock on the checkout, proof of a successful build, or confirmation that commits have reached a remote server.

1. Choose the information your application needs

Link your application to Umicom::repository for inspection and repair proposals. This target also provides the shared Umicom::vcs dependency. Use UmiVcsWorkingTreeRead when you need individual paths, rename sources, staged changes, conflicts, or separate child-repository flags. Use umi_repository_inspection_service_refresh for the existing maintenance and structural reports.

The inspection status probe uses the same immutable working-tree observation as Source Control. A filename containing spaces, tabs, or a newline remains one path. Renames carry both the original and destination path. A staged gitlink is an index entry that records a child repository commit; a child with uncommitted files is separate evidence.

2. Give the service an explicit directory

#include <umicom/repository/inspection_service.h>
#include <stdlib.h>

UmiRepositoryInspectionService *service = malloc(sizeof *service);
if (service != NULL) {
    umi_repository_inspection_service_init(service);
    UmiRepositoryInspectionContext context;
    umi_repository_inspection_context_init(&context, project_directory);
    UmiStatus status = umi_repository_inspection_service_refresh(service, &context);
    /* Present status before interpreting the retained observation. */
    present_repository_result(service, status);
    free(service);
}

project_directory and present_repository_result belong to your application. Keep the service alive if you want to retain the last complete report between refreshes. The context borrows its directory and executable strings for the call. Run refreshes on a worker, with one owner and no simultaneous access to the same service. Large report arrays belong on the heap rather than a small UI worker stack.

3. Show whether evidence is available

StateMeaningWhat to show
No successful observationNo refresh has completed.Offer Refresh and explain any failure. Zero counts do not mean a clean checkout.
Last refresh succeededThe accepted snapshot and reports belong to a completed refresh.Show findings and their accepted revision. Files may have changed afterwards.
Stale retained observationA refresh failed or the snapshot revision no longer matches.Keep the older report visible with a stale label and the latest error.

UmiRepositoryInspectionEvidenceRead supplies these states. umi_repository_inspection_text_format includes the state, revision, and last refresh result. Successfully formatting a stale report does not make its evidence current. Health and audit helpers also require collected evidence.

4. Keep a proposal beside its evidence

umi_repository_remediation_service_plan collects inspection evidence, builds a proposal, and evaluates its policy report before publishing the new value. If a later stage fails, the older observation and proposal remain together and last_status records the failed attempt. Check UmiRepositoryRemediationEvidenceCurrent before presenting a proposal as current. This check does not authorize any Git mutation.

These services do not stage, commit, fetch, merge, push, or automatically apply repair commands. A separate workflow must review the proposed actions and obtain the application's required user authorization. Recheck the repository before applying a proposal because other programs can edit it after observation.

5. Handle limits and errors

  1. On a malformed record or incomplete output, retain the prior report and show the error. Do not reinterpret the missing data as zero changes.
  2. On a timeout, confirm the selected directory and Git executable, then offer a retry. A retry is a new observation.
  3. On a capacity error, explain that the observation exceeded a bound. The shared VCS reader limits input to 32 MiB, paths to its fixed path capacity, and entries to its shared change-list bound. The aggregate byte-parser compatibility entry point additionally limits its input to 4 MiB.
  4. Do not retry a mutation to repair a read failure. Inspection does not grant permission to change repository contents.
The publication guarantee concerns the service's in-memory value. Independent Git queries and optional metadata probes do not form a filesystem transaction. A successful inspection does not claim remote freshness, atomic disk recovery, or release qualification.

Extending the integration

Add status grammar support to the shared VCS parser and then project it into the maintenance model. Avoid teaching each UI its own Git text parser. Keep exact paths in the observation; escape them only when creating a display label or serialized document. The lower-level UmiRepositoryGitCapture API captures bounded binary output for other Git protocols, such as module registration. Its caller owns the returned bytes and releases them with UmiRepositoryGitCaptureRelease. It is an execution primitive, not an authorization policy.

See application module discovery for registered-module validation and Git's porcelain status format for the protocol specification.
