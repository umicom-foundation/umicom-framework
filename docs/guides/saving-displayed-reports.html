Save a displayed report

Saving a displayed report creates a plain UTF-8 text file that you can read in a text editor or include in a review.

Where this is available

WorkspaceText saved
Bank statementThe displayed account statement and captured range.
Bank audit investigationThe captured summary. Command and journal CSV actions remain separate.
Cash planning in TMS, Trader and BankThe displayed assumptions and projection. JSON saves the editable plan; CSV exports its table.
Media and Music creative workspaceThe project summary. This does not render video or export the project database.
AI Drafts and reviewThe displayed request, source references and returned draft. Saving does not run a model or approve an action.
Studio and Education teaching inspectorThe labelled report for the last successfully inspected file.

Save the text

  1. Open the report and check its account, project, job or teaching-file identity.
  2. Expand Save displayed text. Enter a new absolute filename, or use the folder button to choose one. For example, choose C:\Umicom Reports\cash-projection.txt in a folder you have already created.
  3. Select Save displayed text. Choosing a filename alone does not save anything.
  4. Wait for the saved byte count and destination. Open the file in a text editor and check that it contains the report you intended to share.

The text is captured when you press Save. Later report or filename edits do not change that accepted write. Only one write runs per export control. Changing Bank audit filters does not change its earlier capture; choose Capture audit before saving a new summary.

If a save fails

  • Existing file: choose a new filename. The exporter never overwrites it.
  • Missing folder or denied access: choose an existing folder you control.
  • Empty or oversized text: display a useful report first. The control accepts at most 2,097,152 characters and 8,388,608 UTF-8 bytes; larger reports are refused.
  • Interrupted write: a partial new file can remain. The message shows its destination and bytes written. Inspect it before retrying with a different filename.

An accepted write may finish after its window closes. Closing prevents new captures; it does not undo an accepted write. Successful close does not guarantee survival of a later power failure.

For contributors

Use UmiTextExportGtk4Create for a GtkLabel or GtkTextView, or UmiTextExportGtk4CreateForBuffer for a report buffer. Both return a floating widget. The source is weakly observed; no worker borrows it. Retain the control if host disposal can precede service cleanup, call UmiTextExportGtk4Retire when closing, then release your reference. Keep report formatting in its existing owner.

This is a text snapshot, not a signed audit record, accounting backup or broker instruction. Share it only with the intended recipient; reports can contain private information.

Export only a current generated report

A generated website may depend on both a model revision and reviewed public fields. Use UmiTextExportGtk4CreateGuardedBuffer when an old buffer must not be saved after either changes. Its admission callback runs on the GTK owner thread before a text copy is accepted. Return UMI_STATUS_OK only while the report still represents the reviewed source; otherwise return a refusal status.

The callback must be short and must not perform blocking file or network work. Keep external owners weakly bound and retire the control before releasing them. The constructor takes callback-context ownership only on success. The context destructor runs when the export control is finalized.

The existing label and buffer constructors retain their original behavior. Every accepted export still writes an immutable copy to a new filename. A later source change does not rewrite or cancel that accepted file. A refusal creates no file; regenerate and review the report before trying again.
