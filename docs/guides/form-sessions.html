Editing and saving typed form records

A structured form session joins typed answers to the Framework's durable draft protocol. It keeps the selected record, current edit, saved baseline and outstanding save separate. Link Umicom::form_records and include umicom/data/structured_form_session.h.

1. Create the editing owner

Call umi_structured_form_session_create with an immutable schema. Keep that schema alive until the session is destroyed. Serialize calls on one owner, normally the native UI thread or an application request owner. The service starts no threads and opens no database.

2. Start or open a record

session_begin creates an unsaved typed draft under an entity identifier. It does not check whether that identifier already exists in a store; the first save checks. To open an existing record, use umi_record_document_open_reviewed to retrieve the exact catalogue selection, then pass the document to session_open. Opening verifies the payload digest and matching schema.

Both operations refuse to replace unsaved edits or an outstanding save. Every accepted replacement advances a session generation. A generation identifies the selected editing context; a form revision identifies changes within that context. Capture both from session_snapshot.

3. Apply a reviewed edit

umi_structured_form_session_snapshot(session, view);
/* Prepare an edit against view->form with the shared form service. */
umi_structured_form_session_apply(session, view->generation, edit);

A successful edit changes all captured fields atomically. An old generation, old form revision, changed previous answer, incompatible unit or oversized serialized form refuses the operation. The accepted model and its draft bytes stay together. A true no-op does not make a loaded record dirty.

4. Save without losing later typing

  1. Call session_prepare_save with the reviewed generation and attribution. Use submitting=0 to save a valid draft, or 1 to also require the submission rules.
  2. Copy the returned UmiRecordSaveRequest to your worker. Keep it unchanged and call umi_record_save_request_commit there using an owned, live Data Server.
  3. Return the result and committed metadata to session_finish_save on the originating session owner. Use the exact request identifier.

Editing remains available while saving. A second save is busy. Successful completion advances the saved baseline to the captured content; newer edits remain dirty. Wrong request identifiers and mismatched success metadata leave the outstanding request intact. A failed write clears only the matching pending request and preserves the draft.

If dispatch fails before a worker starts, finish the request with that failure. If storage reports an ambiguous I/O failure, inspect the store before retrying. Closing a window does not prove that a running write was cancelled. Complete workers and disconnect their replies before destroying their session.

5. Discard or recover explicitly

session_discard requires an explicit user decision and the current generation. It restores the saved answers, or closes a never-saved new record. It advances generation so delayed edits for the discarded view are refused. It cannot run during a save.

session_capture returns a recovery snapshot when no save is pending. Use the existing record draft snapshot codec and rooted recovery-file service to retain it locally. Before restoring against a selected store, verify its baseline with umi_record_draft_snapshot_check_store. Then call session_restore on an empty or clean session. A newer stored head is not silently merged; the next save performs the normal predecessor check.

Limits and integration

Serialized forms must fit the bounded record document limit. Sessions do not encrypt data, authenticate actors, authorize records, schedule autosave or decide which database to use. Your application supplies those policies and retains the session across view refreshes. These services are shared foundations for product workflows; applications must still connect selection, editing, persistence and visible error handling.
