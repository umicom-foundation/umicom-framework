Umicom Framework · Project files

Narrow a file search

A project can contain source code, generated files, notes and third-party libraries. Include and exclude patterns help focus a saved-file text search on the files you need. Framework applies the patterns before opening files, so excluded files do not consume the result limit or fail the search because their contents are unreadable.

Try the controls in Studio

  1. Open a project, refresh Explorer if its file list has changed, then open the Search panel.
  2. Enter the literal text to find, such as savedCount.
  3. In Files to include, enter *.c;*.h to search C sources and headers.
  4. In Files to exclude, enter generated/* to skip that folder and its descendants. Change this to the actual generated folder in your project.
  5. Choose Find in Files. Read the captured scope beside the results. Editing the fields prepares another query; it does not change a search already running or relabel existing results.
  6. Clear both fields and search again to return to all indexed files.

Search reads saved bytes. It does not save drafts, execute project tools or change the index's own exclusion rules. Opening a result preserves an existing working copy. If an unsaved edit moved the match, search navigation reports that the saved location is no longer present rather than selecting unrelated text.

Read the pattern rules

PatternMeaning
*.c;*.hEither basename pattern matches at any folder depth.
src/*.cA workspace-relative path starting with src/ and ending with .c, including nested folders.
generated/*Everything below the workspace's generated folder.
note?.cA basename with exactly one byte between note and .c.
Blank IncludeAll indexed files are initially eligible.
Blank ExcludeNo additional exclusion is applied.

A pattern without a slash applies to the filename; one with a slash applies to the whole workspace-relative path. * matches zero or more bytes, including slashes. ? matches one byte, which may be only part of a multibyte UTF-8 character. Matching is case-sensitive on every platform: *.C differs from *.c. The text query's Match case checkbox does not change path matching.

Separate alternatives with semicolons. Exclude wins when both lists match. Backslashes become forward slashes, and spaces around each pattern are trimmed. Spaces inside a name remain literal. Each field permits 511 bytes and up to 16 patterns. Brackets, braces, control characters, absolute paths and empty list items are rejected. This syntax has no regular expressions, escape sequences, brace expansion or special double-star operator; consecutive stars behave like one star.

Recover from an input error

  1. Remove a trailing semicolon or empty item, such as the middle item in *.c;;*.h.
  2. Replace a brace expression such as *.{c,h} with *.c;*.h.
  3. Use a workspace-relative pattern instead of an absolute drive path.
  4. Shorten an overlong list or reduce it to at most 16 patterns. Your previous results remain available when a new request is rejected.

If the workspace or index changes, rerun the search. Results remain tied to their original request and index revision; changing scope cannot make an old result belong to a new request. Cancellation keeps files unchanged and does not cancel a separate build or Explorer refresh.

Use the shared C API

Include umicom/platform/search_session.h and link Umicom::platform. The session must already own an index whose root is absolute:

UmiSearchPathFilter filter;
UmiStatus status = UmiSearchPathFilterInit("*.c;*.h", "generated/*", &filter);
if (status == UMI_STATUS_OK) {
    status = UmiFileSearchStartFiltered(session, "savedCount", 1, 0U, &filter);
}

An OK start result means the request was accepted, not that the search finished. Poll UmiFileSearchRead on the owner thread, and use matches only when ready is true. Keep the index alive until the session is destroyed. The filter and query are copied before the worker is submitted; the caller can then reuse its input storage.

Use UmiFileSearchFilterRead with the request ID to label the captured scope, and UmiFileSearchMatchAt to copy an individual result. A different or stale request is rejected. The original UmiFileSearchStart remains available and clears the extra filter for that request.

A synchronous tool can call UmiSearchFileIndexScoped with the existing request, progress and result callbacks. It copies the filter and retains the normal bounded reads, cancellation and revision checks. Its streaming sink can receive earlier matches before a later error; discard partial results when the workflow requires a complete set. files_considered includes candidates rejected by the filter; rejected candidates are not counted as searched, binary or oversized files.

These filters express search intent. They do not grant access, create a filesystem sandbox or stop another service from reading a path. The normal index, filesystem and operating-system rules still apply.

Extend the implementation

Keep syntax and matching in src/platform/search_filter.c, and file reads in src/platform/search.c. New frontends should call the shared session rather than removing rows after a broad search: filtering rows afterwards would still read excluded files and spend the match limit on them. Add focused scenarios to tests/test_search_filter.c when changing syntax or worker ownership.
