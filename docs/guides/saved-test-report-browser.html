Review saved CTest reports

A saved report records an earlier test run. The report browser reads CTest JUnit XML and lets you review test names, durations and recorded outcomes. It does not build software, run tests, or establish that the report belongs to your current source files.

Create and open a report

  1. Finish building the test executables you intend to run.
  2. Run CTest from your configured build directory. Choose a private output folder that already exists: 
    ctest --output-on-failure --no-tests=error --output-junit "C:/work/private/tests.xml" --output-log "C:/work/private/tests.log"
    Keep the console log too: it contains diagnostic output that the short result messages may not include.
  3. In an application containing the Framework saved-report panel, choose the XML file with Browse or enter its absolute filename. Select Open report.
  4. Wait for the read to finish. The loaded filename appears separately from the editable filename field. Changing that field does not load another report.
  5. Choose an outcome, name filter and order, then select Apply filters. The default lists every non-passed result. Next and Previous show 64 matching records at a time.
  6. Select Copy page to copy the displayed page. Select Close report to release the loaded report. Neither operation changes the source XML.

Interpret the results

Passed, failed, timed out, skipped, disabled and not run are distinct outcomes. Skipped and disabled tests did not supply passing coverage. A not-run test often needs a completed build or corrected test environment; inspect its log before diagnosing application code. An empty report is not evidence that tests passed.

The summary describes all records in the loaded report, while the page contains only the filtered selection. Name matching folds ASCII letters only; other UTF-8 characters are matched exactly. Names and messages are plain text. Control characters are escaped so report content cannot inject extra displayed records.

Loading and cancellation

The native panel reads and parses on a worker thread. A load accepts a complete, local, absolute filename and at most 64 MiB. The path and filter choices are captured when you select Open report. Later edits remain drafts until you select Apply filters or open another report. While loading, Cancel load prevents publication of its results; the bounded read finishes before its resources are released. Hiding or closing the panel also cancels publication. Showing it again does not revive the older load.

If a filter is invalid, the accepted page stays visible. Correct the choices and Apply again. A missing or malformed replacement report also leaves the accepted report, page position and loaded filename unchanged. Cancelled replacements do the same. Only a successful replacement or Close report releases that view. If loading fails, check that you selected JUnit XML rather than the console log, that the report finished writing, and that its declared counts and encoding are valid. Keep the original report and log for diagnosis.

Embed the reusable service

Link the testing SDK and include umicom/testing/ctest_report_file.h and umicom/testing/ctest_report_view.h. Call UmiCtestReportReadFile, initialise a filter with UmiCtestReportFilterInit, then create a view. The view borrows its immutable report: destroy all views before destroying the report. It owns its filter and index. Formatting is measured before writing and supports pages of 1 through 128 records.

The GTK host uses UmiGtk4CtestReportCreate from umicom/ui/gtk4/ctest_report.h. Create and use this widget on the GTK thread. The shared testing service does not depend on the editor or a Studio project. The existing umicom test-report command uses the same bounded file reader.

Compare two saved runs

The comparison panel answers which exact test names changed outcome between two completed CTest reports. It does not certify that either report belongs to the current source tree. Keep the source revision, build configuration and console log with each report.

  1. Finish both test runs and retain each JUnit XML file under a different absolute filename. Do not select a file that another process is still writing.
  2. In the comparison panel, choose the baseline file and the current file, then select Compare reports. Both filenames are captured together; changing the entries while loading affects only the next request.
  3. Read the accepted filenames and counts. Recovered means the same name changed from a non-passing outcome to passed. Regressed means it changed from passed to another outcome. Disabled and skipped remain separate outcomes.
  4. Check added and removed records before drawing conclusions. Removing a failing test is not a repair. Unchanged outcomes can still be failures; open the current report in the report browser to inspect them.
  5. Use Next and Previous for 64-record pages or Copy page to copy the displayed text. Close comparison clears the view without modifying either source file.

Missing, malformed or cancelled replacements retain the previously accepted pair and page. Cancel load stops a pending result from being accepted; it does not interrupt local file reads. Once text has been accepted, its filename labels finish updating together even if a synchronous interface callback hides the panel.

Each input has the report reader's 64 MiB limit. Files are read sequentially, so the pair is not an atomic filesystem snapshot. Compare immutable completed files. Matching uses decoded names exactly, including letter case. Changed names therefore appear as removed and added records. Empty or unchanged reports never establish that everything passed.

Embed saved comparisons

Include umicom/testing/ctest_comparison_file.h and link Umicom::testing. UmiCtestReportCompareFiles returns an owned comparison, independent of the two input filenames and temporary report objects. Release it with UmiCtestReportComparisonDestroy. This synchronous file operation belongs on a worker when used by an interactive application.

UmiCtestReportComparisonFormat accepts a page limit from 1 through 128. First pass a null output and zero capacity to obtain the required byte count, then allocate that count plus one for the terminator. Short buffers remain unchanged. The GTK adapter, UmiGtk4CtestComparisonCreate in umicom/ui/gtk4/ctest_comparison.h, owns the worker and publication lifecycle.

Identify the bytes in an accepted comparison

Each comparison page and clipboard copy begins with the baseline and current byte counts and SHA-256 digests. A digest is a fixed-length content identifier. The reader computes it from the exact bytes sent to the parser. Changing line endings or whitespace changes the digest even when test outcomes remain identical.

  1. Keep completed reports under distinct filenames and open the pair.
  2. Copy the displayed page to your private run notes. Retain both original XML files and their console logs.
  3. When comparing another copy later, compare its byte digest as well as its filename. A matching filename alone is insufficient.

Paging uses accepted memory, so later path changes do not alter its digests. Failed and cancelled replacements retain the previous identities. A digest is not a signature and does not prove who produced a report, which checkout it tested, or whether either test run succeeded. Files must remain stable while initially read.

Native and command-line hosts can call UmiCtestReportReadFileWithIdentity or UmiCtestReportCompareFilesWithIdentity. Pass an optional identity output alongside the owned report or comparison. Failure leaves that identity unchanged and the report output null. Paired identities are published together only after both reports and their comparison succeed. Destroying the report does not invalidate the caller-owned identity.

Retain the accepted report identity

The native browser displays the byte count, SHA-256 digest and complete outcome counts for its accepted report. Filters and paging change the visible selection, not those whole-report counts. Editing the filename or replacing its file later does not change the accepted evidence; explicitly open the new file to replace it.

Native hosts can call UmiGtk4CtestReportReadEvidence on the GTK owner thread after loading finishes. It copies the captured path, exact parsed-byte identity and summary into caller-owned storage. Busy publication returns UMI_STATUS_BUSY; no accepted report returns UMI_STATUS_NOT_FOUND. Failures leave the caller output unchanged. The value remains valid after the panel closes.

This is saved evidence, not proof of the current source, a trusted author or process success. A filename can be reused and a report can be incomplete for the feature being reviewed. Keep source identity and required coverage explicit.
