Review saved CTest reports

A saved report records an earlier test run. The report browser reads CTest JUnit XML and lets you review test names, durations and recorded outcomes. It does not build software, run tests, or establish that the report belongs to your current source files.

Create and open a report

  1. Finish building the test executables you intend to run.
  2. Run CTest from your configured build directory. Choose a private output folder that already exists: 
    ctest --output-on-failure --no-tests=error --output-junit "C:/work/private/tests.xml" --output-log "C:/work/private/tests.log"
    Keep the console log too: it contains diagnostic output that the short result messages may not include.
  3. In an application containing the Framework saved-report panel, choose the XML file with Browse or enter its absolute filename. Select Open report.
  4. Wait for the read to finish. The loaded filename appears separately from the editable filename field. Changing that field does not load another report.
  5. Choose an outcome, name filter and order, then select Apply filters. The default lists every non-passed result. Next and Previous show 64 matching records at a time.
  6. Select Copy page to copy the displayed page. Select Close report to release the loaded report. Neither operation changes the source XML.

Interpret the results

Passed, failed, timed out, skipped, disabled and not run are distinct outcomes. Skipped and disabled tests did not supply passing coverage. A not-run test often needs a completed build or corrected test environment; inspect its log before diagnosing application code. An empty report is not evidence that tests passed.

The summary describes all records in the loaded report, while the page contains only the filtered selection. Name matching folds ASCII letters only; other UTF-8 characters are matched exactly. Names and messages are plain text. Control characters are escaped so report content cannot inject extra displayed records.

Loading and cancellation

The native panel reads and parses on a worker thread. A load accepts a complete, local, absolute filename and at most 64 MiB. Current filter choices are applied when the load finishes. While loading, Cancel load prevents publication of its results; the bounded read finishes before its resources are released. Hiding or closing the panel also cancels publication. Showing it again does not revive the older load.

If a filter is invalid, the old page is cleared. Correct the choices and Apply again. If loading fails, check that you selected JUnit XML rather than the console log, that the report finished writing, and that its declared counts and encoding are valid. Keep the original report and log for diagnosis.

Embed the reusable service

Link the testing SDK and include umicom/testing/ctest_report_file.h and umicom/testing/ctest_report_view.h. Call UmiCtestReportReadFile, initialise a filter with UmiCtestReportFilterInit, then create a view. The view borrows its immutable report: destroy all views before destroying the report. It owns its filter and index. Formatting is measured before writing and supports pages of 1 through 128 records.

The GTK host uses UmiGtk4CtestReportCreate from umicom/ui/gtk4/ctest_report.h. Create and use this widget on the GTK thread. The shared testing service does not depend on the editor or a Studio project. The existing umicom test-report command uses the same bounded file reader.
