Review a local journal

A journal records the debit and credit lines of an accounting event. A chart of accounts identifies the accounts that may receive those lines. An accounting calendar identifies the period containing the journal date. The Framework review service combines these local checks and captures the values before an application asks an operator to apply the journal.

This service changes a bounded in-memory book. It does not connect to a bank, authorize a payment, authenticate an approver or persist a ledger transaction. Journals do not contain currency or scale metadata: the surrounding service must establish compatible account currencies and minor units before using these APIs.

1. Prepare and inspect

  1. Include umicom/finance/accounting/posting_review.h and link Umicom::finance.
  2. Construct the journal, chart, calendar and book with their existing initialization APIs. Check each insertion result. Keep one owner responsible for serializing changes.
  3. Call umi_accounting_posting_inspect. Its return value describes whether inspection produced a preview. A return of UMI_STATUS_OK does not alone mean posting is permitted: read preview.refusal and preview.blocker.
  4. Display totals, the resolved period and any refused line. A line index of SIZE_MAX means the refusal concerns the whole entry or its context.

Inspection requires a valid, balanced draft or validated entry; complete valid containers; a matching open period; known postable accounts; available book capacity; and a new journal ID. It does not change its inputs or allocate a review.

2. Capture the decision

Call umi_accounting_posting_review_create only when a fresh review is needed. It repeats inspection and owns a heap copy of all active context. On failure it sets the output review pointer to NULL. On success, use umi_accounting_posting_review_preview and umi_accounting_posting_review_entry to display the immutable capture. These borrowed pointers remain valid until review destruction.

UmiAccountingPostingReview *review = NULL;
UmiStatus status = umi_accounting_posting_review_create(
    &entry, &chart, &calendar, &book, &review);
if (status != UMI_STATUS_OK) {
    /* Present the refusal; keep the existing owner values. */
    return status;
}
/* Present the capture and obtain the application's explicit local decision. */
status = umi_accounting_posting_review_apply(
    review, &entry, &chart, &calendar, &book);
umi_accounting_posting_review_destroy(review);
return status;

3. Apply once to unchanged owners

Apply requires the same live owner addresses and their captured active fields. A changed line amount, account name, posting flag, date range, calendar order or existing journal requires a fresh review. Padding, unused rows and bytes after text terminators are ignored. A successful apply appends one posted copy; it does not change the candidate journal. Repeating apply is refused.

The caller must serialize access for the entire operation and keep the owners alive. Address and content comparison is a local stale-decision check. It is not a security boundary, a persisted replay defense or a generation counter that detects change-and-restore history. Applications with asynchronous dialogs must also use their owner-lifetime controls.

4. Handle refusal without losing edits

ObservationNext action
Invalid record, count or amount overflowPreserve the source for diagnosis. Correct the input through its owner; never clamp an amount to make it fit.
Missing or closed periodSelect a permitted accounting date or resolve the period policy through an authorized workflow. Do not bypass the check.
Missing or blocked accountReview the chart and the indicated journal line. Account flags are local data, not operator authorization.
Duplicate journal or full bookInspect existing entries. A duplicate refusal must not be retried under an invented ID to conceal a repeated event.
Apply returns INVALID_STATEKeep all current data, discard the stale review and inspect again. Refusal does not partially append an entry.

5. Exercise the installed SDK example

After installing Framework and its Learning component, the following PowerShell commands build the example entirely against that installed SDK. Change the prefix if your installation is elsewhere. Stop if a command reports an error.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S "C:\umicom\installed\applications\share\umicom\examples\journal_posting" -B "C:\umicom\_local\build\journal-posting" -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_SDK_PREFIX=C:/umicom/installed/applications -DBUILD_TESTING=ON
cmake --build "C:\umicom\_local\build\journal-posting" --parallel 2
ctest --test-dir "C:\umicom\_local\build\journal-posting" --output-on-failure --no-tests=error
& "C:\umicom\_local\build\journal-posting\journal-posting.exe" apply

The example covers apply, a changed account, a closed period, an unrepresentable signed magnitude and a changed book. Expected successful execution reports the appropriate refusal or one locally stored journal and exits with code zero. The example explicitly uses synthetic GBP pennies; it performs no filesystem persistence or provider communication.

If a new declaration or symbol is missing, build and install the same Framework revision before configuring the example. Do not add source-tree include or library paths to hide an incomplete installation. The installed SDK guard checks that the requested prefix supplies the imported targets.
