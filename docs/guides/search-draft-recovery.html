Own and recover search drafts

A query draft contains the title, text search and typed conditions being edited. UmiStructuredFormSearchSession owns those edits separately from a stored definition. The service performs no database or user-interface work; a native, web or command-line host can use the same ownership rules.

Create and edit

  1. Create a session with an immutable form schema and a fixed searched-record namespace. Keep the schema alive until session destruction.
  2. Begin a new form.search. entity with a valid definition, or open a verified stored document. Dirty content is never silently replaced.
  3. Read a session snapshot. It contains the definition, dirty state, stored baseline revision, generation and edit revision.
  4. Pass both generation and edit revision with an edit. Generation identifies the open draft context; edit revision identifies the observed content. An old command cannot apply to a reopened draft.
  5. Use explicit discard to restore a stored baseline or close a never-saved definition. Discard does not write the database.

Save while editing continues

  1. Prepare a save using the current tokens and valid attribution. This creates an immutable UmiRecordSaveRequest.
  2. Send only that copied request to your storage worker. The worker calls umi_record_save_request_commit.
  3. Return its status and committed revision to umi_structured_form_search_session_finish_save on the session's owner thread.
  4. Read the session snapshot again. The baseline advances to the captured bytes. Any edits made after preparation remain current and dirty.

If dispatch fails, finish the request with that failure status. A wrong completion token or mismatched success receipt leaves the pending request intact. A window closing does not cancel an admitted database write; complete workers before destroying their session.

Recovery

  1. Capture a UmiRecordDraftSnapshot while no save is pending. It includes both the reviewed baseline and unsaved definition.
  2. Use the existing draft snapshot codec or explicit new-file recovery service to retain it. Recovery is plaintext and does not clear dirty state.
  3. Before restoring against a database, call umi_record_draft_snapshot_check_store to compare its historical baseline.
  4. Restore only into an empty or clean session. Both baseline and draft must decode with the exact schema and fixed namespace.
  5. Save explicitly after review. A newer database head can still refuse that save; recovery does not bypass revision checks.

The installed SDK example form_search_recovery.c demonstrates capture, codec round-trip, restore and immutable save. Link to Umicom::form_records.

Limits

The service accepts complete valid definitions. A host must retain incomplete native text separately and include it in close protection. It does not merge conflicting definitions, change schemas, authenticate a database, encrypt recovery files or authorize query execution.
