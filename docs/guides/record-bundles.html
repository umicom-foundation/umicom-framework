Transferring a record with its history

A record bundle contains the original metadata and content for every revision of one small record. It can be decoded and restored into a store where that record does not exist. The Framework preserves original identifiers and revisions; it never merges a bundle into occupied history.

Link with Umicom::data and include umicom/data/record_bundle.h. A bundle holds at most 16 revisions, each within the normal 16 KiB content limit. A longer history is refused in full. This bounded transfer does not back up an entire database, attachments or application settings.

Capture and review

  1. Call umi_record_bundle_capture with the selected entity identifier. It reads and validates the complete history within one transaction.
  2. Use umi_record_bundle_count and umi_record_bundle_at to inspect copied metadata and bytes before export. Show the entity, source, actor labels and revision count to the user.
  3. Call umi_record_bundle_encode to obtain an allocated, versioned byte sequence. The format includes canonical metadata, content lengths, individual content digests and a whole-frame checksum. Release the returned bytes with umi_record_bundle_bytes_free.

Restore into a new entity location

  1. Read an explicitly selected input under UMI_RECORD_BUNDLE_MAX_BYTES. This API does not choose filenames or perform filesystem I/O.
  2. Decode with umi_record_bundle_decode. Review the result before permitting a restore. Keep the returned immutable bundle alive while the operation runs.
  3. Call umi_record_bundle_restore_new on the destination worker. All revisions are staged in one transaction. A conflicting head or occupied row refuses the restore and rolls back staged data.
  4. Read the restored historical revisions and compare their contents. Existing unrelated entities are retained. Free the bundle with umi_record_bundle_destroy after readers finish.

Failure handling

BUSY means the operation could not own a transaction; a caller's existing transaction remains theirs. CAPACITY_EXCEEDED during capture means the whole history is outside this bundle's bounds. INVALID_STATE during restore commonly means occupied history; choose a genuinely separate destination after review rather than deleting data to make the restore succeed.

Malformed framing, changed checksums or inconsistent history refuse decoding. Outputs remain unchanged on errors. A rollback failure reports IO_ERROR; inspect the store before retrying. A checksum detects accidental alteration but is not a signature. Bundles are plaintext and include original actor labels and content, so the application must authorize export and select suitable storage.

Try the installed example

The SDK data-history examples include record_bundles.c. Build the umicom-record-bundle-example target in that installed example project. It uses two memory stores and should print: Restored two revisions; original note retained; duplicate restore refused. It performs no external service or file access.

Explicit file export and import

For filesystem support, link Umicom::record_bundle_files and include umicom/data/record_bundle_files.h. Call umi_record_bundle_write_new with an absolute path in an existing directory you control. It encodes first, then creates the file exclusively. An existing file is refused and retained. A write failure can leave a partial new file for diagnosis; do not report it as a completed export.

Call umi_record_bundle_read with an explicit absolute directory and a portable relative filename. The rooted reader bounds file size and refuses traversal and links. The decoded bundle must still be reviewed and authorized before the separate restore operation. Neither file operation derives a path from record metadata or touches a database. Run file operations on a worker to keep native interfaces responsive.

Destination occupancy

A missing current record does not prove its storage is empty. Restore checks reserved history and content keys for that identity, including orphan revisions outside the incoming range. Any such row blocks import and remains unchanged. The occupancy scan is limited to 32,768 total destination rows; a larger store returns a capacity error before staging anything. Use a separately reviewed recovery procedure for orphan rows; this service never deletes them.
