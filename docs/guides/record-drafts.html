Edit records without losing unsaved work

A draft is the local copy a person is editing. The saved baseline is the version they opened or last saved. A save request is a separate copy captured when they choose Save. Keeping these three values separate allows an application to keep accepting edits while storage is busy.

Include umicom/data/record_draft.h and link Umicom::data. The draft service works with atomic record documents, which store content and amendment history together. Each draft holds up to 16,384 bytes. Content can be text or binary; the service does not parse a product's record schema.

Draft-handle operations do no database I/O and create no threads or widgets. The separate save-request commit function is called by the host on its storage worker. It supplies shared editing behavior for application hosts. Attribution labels do not grant access; the application remains responsible for permissions and authenticated identity. Draft memory and stored documents are not encrypted by this service.

Open a record or start a new one

  1. Create a handle with umi_record_draft_create. Check the status before using the returned pointer.
  2. For a saved record, read umi_record_document_latest on the application's storage worker. On the draft's owning thread, pass the resulting snapshot to umi_record_draft_open. Open validates the metadata and content digest before copying it.
  3. For a new record, call umi_record_draft_begin with a stable entity ID of at most 63 bytes. A new empty record is dirty and can be saved. Begin does not query storage; saving expected revision zero will reject an existing record.
  4. Read umi_record_draft_state to obtain the content length, dirty flag, saving flag and reviewed revision. Copy bytes with umi_record_draft_copy_content. It does not append a text terminator; allocate and add one separately when displaying text.
  5. When content changes, call umi_record_draft_set_content with its byte length. Invalid or oversized input leaves the existing draft intact.

Open and Begin refuse to replace a dirty draft. Offer the user Save, Discard or Cancel before opening another record. Call umi_record_draft_discard only after their decision: it restores a saved baseline, or closes an unsaved new record. Open, Begin and Discard return BUSY while a save is outstanding.

Capture and complete a save

  1. Supply UmiRecordDraftAttribution with source, actor, reason and a nonzero recorded time. Fields must be terminated and contain no control characters. Observed time can be zero when it is unknown.
  2. Call umi_record_draft_prepare_save. It captures the current content, derives the entity and predecessor revision, and calculates the content digest. Check its status before dispatching anything.
  3. Copy the returned UmiRecordSaveRequest into a managed worker's owned job data. Its approximately 17 KiB payload should not be passed as a pointer to a temporary stack variable. The worker receives the copy and its storage handle, never the mutable draft.
  4. Let the worker call umi_record_save_request_commit. It verifies that the captured content still matches its digest before the atomic document append. Do not replace the captured content with whatever is currently in the editor.
  5. When the worker finishes, route its result back to the same draft on its owning thread. Use umi_record_draft_finish_save with the captured request ID and the committed revision returned by storage. On failure, pass the failed status and NULL.
  6. Refresh the visible status from umi_record_draft_state. A successful save can leave dirty true because a newer edit remains unsaved.
/* Worker: request is its own copy; it never accesses the editor draft. */
UmiRecordRevision saved;
UmiStatus result = umi_record_save_request_commit(server, &request, &saved);

/* Owning thread, after the worker has finished: */
UmiStatus acknowledged = umi_record_draft_finish_save(draft,
    request.request_id, result, result == UMI_STATUS_OK ? &saved : NULL);
/* Check acknowledged and refresh the displayed state. */

For example, a user saves “review pending” and then types “review completed”. When the first write finishes, the saved baseline becomes “review pending” and the editor still contains “review completed”. Its next save uses the new baseline revision. Returning the editor to its older baseline while a save is running also keeps those bytes; the completed write does not silently replace them.

Request IDs are unique within one draft handle's lifetime. A second preparation returns BUSY. A wrong ID or mismatched successful revision leaves the pending request intact so the host can diagnose the wrong reply. Route completions to their original handle; IDs are not global authorization tokens.

Keep workers and handles alive correctly

Serialize all calls on a draft, normally on the UI thread. The service is not a lock around widgets or a thread-safe shared editor. A worker uses its copied request while the owning thread may continue changing the draft.

If dispatch fails before a job starts, finish the prepared request with an appropriate failure such as CANCELLED. If I/O is already running, wait for its actual completion. Closing a window does not prove the write was cancelled. Complete or disconnect replies before destroying the draft, and keep the Data Server alive until its workers finish.

A non-OK completion clears the pending flag and returns the worker's status. It retains the baseline and current bytes. This is different from an invalid completion ID, which does not change pending state. Destroy releases ordinary memory; it does not cancel work, remove persisted history or securely erase secrets.

Review a changed stored revision without losing the draft

  1. Keep the current draft and load the latest stored document on the storage worker. Capture the current draft entity and expected_revision when starting that read.
  2. Show the stored snapshot separately from the editable draft. Let the user compare both versions and decide which text they want to keep.
  3. After their explicit decision, call umi_record_draft_adopt_reviewed with the validated stored document and the baseline revision captured before the read. A different entity, an older revision, a changed baseline or a pending save is refused. Reusing the same revision with different content or attribution is refused too.
  4. The call changes only the saved reference point. Every current draft byte remains in place. If the draft already equals the reviewed content it becomes clean; otherwise Save prepares a new revision against the reviewed baseline.
  5. Another writer may change storage after review. The next save still checks the stored revision and may require another comparison. Adopting a snapshot is not permission to overwrite an unseen version.

Prefer this single checked operation over a sequence that discards and reopens the draft. The native GTK4 editor provides this comparison and adoption flow for application hosts.

Recover from a stale save

  1. Keep the draft. A rejected write must not be reported as a successful save.
  2. Copy the local bytes for a comparison view or an explicit draft export. Keep this copy until the user accepts the resolved content.
  3. Load the latest stored document separately. Show both versions and explain that another writer advanced the revision.
  4. After the user's decision, explicitly discard the old baseline, open the latest document, and set the reviewed combined content as a new edit.
  5. Prepare a fresh save. The new request uses the reviewed latest revision. Another concurrent write can still reject it; handle that result the same way.

The service does not automatically merge free text or approve changes. After IO_ERROR, persistence may need recovery and verification before another save: losing a reply does not prove that a write failed to commit.

Run the installed example

Install an SDK containing the data component, then copy share/umicom-framework/examples/data_history into your own example workspace. From that copied directory, use your installed SDK prefix:

cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH="C:/umicom/installed/applications"
cmake --build build --target umicom-record-draft-example --parallel 2
ctest --test-dir build -R "^consumer.record-drafts$" --output-on-failure --no-tests=error

Stop on a failed command. Expected example output:

synthetic-care-review: later edit retained; both captured revisions readable
synthetic-bank-review: later edit retained; both captured revisions readable

The console example executes storage inline to make the sequence easy to read. It uses fictional records in memory; it does not provide a clinical editor, a bank transaction service, crash recovery for unsaved drafts or a background worker. Native application hosts must supply those integrations separately.

Common statuses

StatusWhat to inspect
INVALID_STATEA closed or clean draft cannot prepare a save. A dirty draft cannot be replaced. A stale storage revision or wrong completion also uses this status; keep the operation context when reporting the error.
BUSYA save is pending, or the storage transaction is busy. Complete the active operation before preparing another save or replacing its document.
INVALID_ARGUMENTCheck pointers, metadata fields, identity, nonzero recorded time and returned completion metadata.
PARSE_ERRORThe supplied document's digest does not match its bytes. Preserve the original evidence and reload through the document service.
CAPACITY_EXCEEDEDThe content or output buffer is too small or large for the operation, or a revision/request counter is exhausted. No revision wraps back to zero.
IO_ERRORKeep the draft and inspect Data Server recovery diagnostics before retrying. Re-read persisted state when the write outcome is uncertain.
