Review test coverage across hosts

A test skipped on Windows may still need a passing Linux observation. A saved pass from older source must not close that gap. Framework's coverage review connects exact test names to required hosts, configurations and a requested source identity.

Prepare the observations

  1. Build the intended source on each required host. Record the source fingerprint, toolchain, configuration, command and exit status alongside the test evidence. A branch name such as main is not a stable fingerprint.
  2. Capture a complete CTest JUnit report and import it with UmiCtestReportImport or the existing saved-report file service. Keep runtime skips, disabled tests and missing executables separate.
  3. Describe each required test, host and configuration. The capability description explains why that host is required, such as a GTK display or a Linux filesystem operation.
  4. Create a coverage review. Inspect every outstanding row before deciding which environment or test needs attention.

Turn a skipped result into a qualification task

A prerequisite is something a test needs before it can exercise its intended behaviour. A symbolic-link test needs permission to create a link. A playback test needs a decoder. Returning the configured skip code records that the test could not perform its check; it does not prove that the application behaviour is correct.

  1. Find the exact test name in the CTest summary or JUnit report. Read its captured output for the missing prerequisite.
  2. Keep the result as skipped. A phrase such as “Test Passed” in the low-level temporary log can describe process acceptance under a skip rule; use the reported test outcome, including the JUnit skipped element, when counting coverage.
  3. Assign that exact test to a host and configuration capable of exercising it. Record why, rather than deleting the requirement or changing its expected return code.
  4. Repair the prerequisite or use the appropriate host, then rebuild only what that change requires and rerun the affected cases. Keep the original observation and the new result.
  5. Accept the requirement only when the new report identifies the intended source and records a real pass. A missing capability on one host cannot be replaced by an unrelated passing test.

The capability text in a coverage manifest is a description, not a machine probe. “Windows with link permission” does not enable that permission, and “media plugins” does not install anything. Keep setup and result evidence alongside the manifest.

CTest defines skip return codes separately from failing assertions and timeouts. Keep a JUnit result report when saving observations for the coverage service.

Use the shared C23 service

The following fragment assumes report is an already imported report owned by the caller. The identity is illustrative; supply the real fingerprint captured with the run.

#include <umicom/testing/ctest_coverage.h>

UmiCtestCoverageRequirement required[] = {{
    .name = "application.editor.open",
    .host = "windows-desktop",
    .configuration = "Debug",
    .capability = "GTK display"
}};
UmiCtestCoverageHost hosts[] = {{
    .host = "windows-desktop",
    .configuration = "Debug",
    .source_identity = "source-fingerprint-from-the-run",
    .report = report
}};
UmiCtestCoverageReview *review = NULL;
UmiStatus status = UmiCtestCoverageReviewCreate(
    "source-fingerprint-from-the-run",
    required, 1, hosts, 1, &review);
if (status == UMI_STATUS_OK) {
    UmiCtestCoverageSummary summary;
    status = UmiCtestCoverageReviewRead(review, &summary);
    if (status == UMI_STATUS_OK) {
        for (size_t i = 0; i < summary.requirements; ++i) {
            const UmiCtestCoverageRow *row =
                UmiCtestCoverageReviewAt(review, i);
            /* Present the requirement and outcome as plain text.
             * Read observation only when has_observation is true. */
            (void)row;
        }
    }
    /* This gate covers only the explicitly required rows. */
    status = UmiCtestCoverageRequirePassed(review);
}
UmiCtestCoverageReviewDestroy(review);

The review copies its rows and the requested identity. After creation, it does not borrow the input arrays or reports. Rows remain valid until the review is destroyed. It keeps requirement order so a board or checklist can retain its planned ordering.

Read the saved result message

Each observed row includes its saved duration and Saved result message. The same Framework formatter supplies these fields to the native coverage panel, copied pages, the SDK consumer and the command-line coverage command. If the report supplied no message, the page says not recorded. A missing host, missing test or mismatched source has no matching observation, so no message is borrowed from another result.

Saved messageWhat it establishesWhat to investigate next
SKIP_RETURN_CODE=77The configured skip code was observed.Read the testcase output or run log for the missing prerequisite. The code alone does not identify that prerequisite.
SKIP_REGULAR_EXPRESSION_MATCHEDA configured output rule caused a skip.Inspect that rule and the captured output; retain the skipped outcome.
Unable to find executableThe test did not run.Check the build result and executable path before rerunning.
TimeoutThe recorded test exceeded its timeout.Inspect progress and teardown evidence. This message does not identify the blocked operation.
Test is disabled.The test was disabled in that report.Review the configuration and the required host plan.

Messages are bounded saved metadata, not a diagnosis or the complete process output. Control bytes and backslashes are displayed as hexadecimal escapes; for example a line feed appears as \x0A. This keeps imported text from creating a second apparent result row. Printable text is displayed as text, not executed or interpreted as a command.

Filtering changes only the visible rows. A page containing no matching failures cannot certify the whole required set. Keep the original JUnit report and run log so you can trace the exact test and source identity when investigating a message.

Interpret outstanding coverage

OutcomeNext step
Failed or timed outInspect the saved diagnostic and repair the failure. A timeout remains a failure even when some work completed.

Missing hostSupply the exact host/configuration observation. A Release result does not satisfy a Debug requirement.

Duplicate host/configuration observations and duplicate test/host/configuration requirements are rejected. Choose the intended observation explicitly instead of relying on whichever report appears first. Empty requirements can be reviewed but never satisfy the passing gate.

Review a saved plan with the native command

  1. Keep the complete JUnit reports in one evidence directory, for example C:\umicom\_local\logs\testing. Save the source fingerprint and host configuration with each run. Do not rename old metadata to make it match a new build.
  2. Create coverage.csv in that directory. Use the exact header below. A host row identifies one report. A require row identifies one test that must pass on that host and configuration. This example uses illustrative names and fingerprints; replace them with values from your own runs.
kind,host,configuration,source_identity,test,capability,report
host,windows-desktop,Debug,source-fingerprint-from-the-run,,,windows.xml
host,linux-desktop,Debug,source-fingerprint-from-the-run,,,linux.xml
require,windows-desktop,Debug,,application.editor.open,GTK display,
require,linux-desktop,Debug,,filesystem.exchange,Linux filesystem operation,

Every record has seven fields. Empty fields still need their commas. Quote a field containing a comma, and double a quote inside a quoted field. Names are case-sensitive and whitespace is significant. UTF-8 with or without a byte-order mark, LF and CRLF are accepted. Blank records, extra columns, unknown row kinds, control characters and duplicate identities are rejected.

  1. Run the installed native command, or the executable from your Applications build:
& "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom.exe" test-report --coverage "source-fingerprint-from-the-run" "C:\umicom\_local\logs\testing\coverage.csv"
$LASTEXITCODE

Exit 0 means every listed requirement has a passing saved result for the exact host, configuration and requested source identity. Exit 1 means a requirement remains outstanding, or the plan has no requirements. Exit 2 means an input could not be admitted. The command prints each requirement and outcome; it does not run tests or write files.

Report paths are relative to the manifest directory, even when the command runs from another directory. Child folders are supported with either slash. Absolute paths, drive prefixes, empty path components, . and .. components are refused. A missing declared report is an input error. A requirement whose host has no declared report row produces missing host.

Reuse the manifest in an application

Include umicom/testing/ctest_coverage_manifest.h. Call UmiCtestCoverageManifestImport with the complete CSV byte span, then inspect its host and requirement accessors. Import copies input and performs no file reads. Call UmiCtestCoverageManifestReviewFiles with an explicit absolute evidence directory and requested source identity to obtain the same immutable review used by the CLI. Destroy the manifest and review separately.

CSV input is limited to 4 MiB, with up to 256 host reports and 100,000 requirements. The aggregate report input limit is 64 MiB; the existing XML parser limits also apply. Parsed records and copied review rows require additional memory. File reading can block, so native applications should perform it on a worker and present results as plain text.

Use a trusted evidence directory. Final report files must be ordinary local files; parent directory aliases may still be followed. This service is not filesystem confinement and does not authenticate a report. Resolve input errors before using its review to make a release decision.

Review coverage in a native application

Applications can embed the same review with UmiGtk4CtestCoverageCreate from umicom/ui/gtk4/ctest_coverage.h and link against Umicom::ui_gtk4. The panel owns its accepted review and reads files on a worker. Create and use its widgets on the GTK thread.

  1. Open the application's coverage panel. In Studio, open Test Explorer and expand Review required host coverage.
  2. Choose the absolute filename of the CSV plan described above. Enter the expected source/build fingerprint captured with the intended run.
  3. Click Open coverage. Review the captured filename, requested identity and counts. The panel displays up to 64 requirements per page, in manifest order.
  4. Use Next and Previous to inspect outstanding rows. Copy page copies the displayed page as plain text, including its source and scope.
  5. Use Close review to clear the accepted view without deleting any evidence files.

Editing the filename or identity does not change the accepted review. Click Open coverage to submit the new values. Cancellation, hiding the panel, or a refused replacement leaves the last accepted review available; a pending file read finishes releasing resources before another load can begin. Cancelling does not interrupt an operating-system file read.

If input is refused, check the seven-column CSV header, absolute manifest filename, relative report paths, source identity, limits and complete JUnit reports. The status explains that the accepted review is unchanged. An empty plan can be displayed but cannot establish passing coverage. A skipped requirement remains outstanding even when another host reports a pass for a different row.

Reuse file admission and plain-text pages

UmiCtestCoverageReviewReadFile accepts an absolute manifest filename and expected source identity. It reads the manifest and reports relative to that file's directory, returning an owned review or a null result on failure. It has the same input limits as separate manifest import and review. It can block while reading files; call it from your application's worker.

UmiCtestCoverageReviewFormat formats between 1 and 128 requirements as plain text. Pass a null output and zero capacity to obtain the required byte count, allocate one additional byte for the terminator, then call again with the same review, offset and limit. A short output buffer is unchanged and reports its required size. The formatter does not read files, run tests or change observations.

Find outstanding requirements

  1. After opening coverage in Studio, choose Outstanding requirements to focus on failures, timeouts, skips, disabled or missing tests, missing hosts and source mismatches.
  2. Optionally type part of a test name or capability, a host, and a configuration. The test/capability field matches either of those two columns. The other fields must also match. ASCII letters ignore case; punctuation is literal, so .* is not a wildcard.
  3. Choose requirement, test name, host/configuration or outcome order, then click Apply filter. Equal sort keys retain the original manifest order.
  4. Review the applied filter printed above the rows. Draft entry changes do not change that page until Apply filter succeeds. Next, Previous and Copy page use the accepted filtered view.

A filtered page retains the whole-review counts. Choosing only Passed, or choosing a filter with no matches, cannot turn outstanding coverage into a passing result. Loading a different plan keeps the accepted filter; choose All requirements and clear its text fields to see every row again. Invalid or oversized input leaves the previous page intact.

Reuse coverage filters

Include umicom/testing/ctest_coverage_view.h and link against Umicom::testing. Initialise UmiCtestCoverageFilter with UmiCtestCoverageFilterInit; its default selects outstanding rows. Set its bounded UTF-8 fields and outcome bitmask, then call UmiCtestCoverageViewCreate. The view copies the filter but borrows the immutable review. Destroy every view before its review.

Use UmiCtestCoverageViewRead for the accepted filter, matching counts and original summary; UmiCtestCoverageViewAt returns a borrowed row. UmiCtestCoverageViewFormat creates an escaped page of 1 to 128 rows through the same size-query pattern as the full-review formatter. Filtering never changes UmiCtestCoverageRequirePassed, which always evaluates the entire required set.

Limits

This service compares supplied metadata and saved results. It does not execute tests, discover host capabilities, authenticate identities, verify timestamps, inspect logs or prove that a report was built from the claimed source. Keep that provenance in the calling application's evidence workflow. A passing coverage gate does not imply that unlisted tests passed; use UmiCtestReportRequirePassed when the complete report must pass.

Requirements and observations are bounded by the public capacity constants. Allocation, malformed text and capacity failures return an error with a null review. Summary reads leave their output unchanged on invalid arguments. Link consumers against Umicom::testing.
