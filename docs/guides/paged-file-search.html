Paged saved-file search

A search page is a copy of a small part of a completed search. It lets a native application display results without building a widget for every match. The original search still owns file reading, cancellation and result limits.

  1. Create and start a UmiFileSearchSession. In a graphical application, inspect progress from the owner thread; do not wait inside an event handler.
  2. After successful completion, call UmiFileSearchPageCreate(session, offset, 0, &page). Zero selects 64 rows. A caller may choose up to 128 rows.
  3. Read the copied summary and rows. The summary includes the captured query, include/exclude patterns, result count and adjacent offsets.
  4. Before activating a result, call UmiFileSearchPageValidate with the original live session. Keep the application's workspace generation check as well.
  5. Destroy the page when its display is retired. It does not own the session.
UmiFileSearchPage *page = NULL;
UmiStatus status = UmiFileSearchPageCreate(session, 0U, 64U, &page);
if (status == UMI_STATUS_OK) {
    UmiFileSearchPageSummary summary;
    UmiFileSearchPageRead(page, &summary);
    /* Copy rows into presentation widgets; preserve summary.offset. */
}
UmiFileSearchPageDestroy(page);

What to expect

Offsets align to a page boundary and clamp to the last available page. An empty successful search has zero pages. A stale, running or cancelled request cannot produce a successful page. Rejected calls leave output arguments unchanged.

Recovering from stale results

Search again when the workspace, file index or accepted query changes. A page can still be read after its original session is destroyed, but it can no longer authorise navigation. Result validation does not inspect current disk bytes: source opening must separately confirm the literal match and preserve unsaved editor drafts.

Search supports saved files and the existing 1000-result limit. Paging does not increase that limit, search unsaved drafts or start another worker.
