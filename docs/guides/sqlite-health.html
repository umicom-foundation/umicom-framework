Read SQLite health and checkpoint results

A SQLite diagnostic statement can execute successfully while returning rows describing a problem. Umicom reads those rows before reporting database health.

Check a store

  1. Open a Data Server. Use a read-only connection when you only need inspection.
  2. Run the health check on a storage worker outside an existing transaction.
  3. Check both the returned status and the report's sound field.
UmiSqliteHealthReport report;
UmiStatus status = umi_sqlite_health_read(server, &report);
if (status == UMI_STATUS_OK && report.sound) {
    /* SQLite quick_check completed and returned exactly one "ok" row. */
} else if (status == UMI_STATUS_OK) {
    /* Show report.first_diagnostic as plain text; preserve the database. */
}

The report contains up to 100 diagnostic rows. Reaching that limit does not mean all problems were found. An unusually long first diagnostic is replaced by an explanation and first_diagnostic_omitted is set. A failure to run the check leaves the caller's report unchanged.

This is SQLite's quick_check, not a foreign-key, application-record, authentication or backup audit. In particular, a sound structural report does not establish that financial or clinical data is correct. The scan can take time even though the result count is bounded.

Read-only inspection

SQLite can omit CHECK expressions when it loads a read-only database schema. Framework therefore checks the original file and, if that scan is sound, checks a private writable snapshot. The source connection remains read-only. A private read transaction keeps both checks on the same committed contents; an existing application transaction is refused.

SQLite owns the unnamed temporary snapshot and removes it when its connection closes. Allow temporary storage roughly proportional to the database size and run the operation on a worker. A copy, scan or cleanup error leaves the report unchanged. This is an inspection aid, not a saved backup.

  1. If the check returns BUSY, finish the existing transaction or let the competing operation finish, then retry explicitly.
  2. If it returns INVALID_STATE because CHECK constraints were disabled, restore PRAGMA ignore_check_constraints=OFF on the writable connection before checking it.
  3. If temporary storage or copying fails, report the returned error. Do not display a previously successful health report as the new result.

Complete a WAL checkpoint

A write-ahead log (WAL) can hold committed pages that have not yet been copied into the main database file. umi_sqlite_checkpoint_full requests a full checkpoint and reports the frame counts on success. It returns BUSY when another reader or writer prevents completion. Retry explicitly after that activity finishes.

UmiSqliteCheckpointReport report;
UmiStatus status = umi_sqlite_checkpoint_full(server, &report);
/* On OK, report.wal_mode distinguishes a WAL store from an ordinary one.
 * On failure, report is unchanged; do not interpret its old frame counts. */

An ordinary non-WAL store succeeds with frame counts of -1. Read-only handles refuse checkpointing with PERMISSION_DENIED. Existing transactions are refused with BUSY; these helpers never silently commit or roll back caller work.

Existing entry points

umi_sqlite_integrity_check remains available and now returns INVALID_STATE when the completed check reports structural diagnostics. umi_sqlite_checkpoint retains its full-checkpoint purpose and propagates contention. Use the report APIs when a screen needs details.

A completed checkpoint is not a safe live-file-copy protocol. Use a SQLite-consistent backup operation; another connection can write again after the checkpoint returns. See SQLite's checkpoint contract for the engine behavior.
