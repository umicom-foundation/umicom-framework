Review and publish a journal batch

A journal records matching debit and credit entries in integer minor units. A batch is an ordered set of journals that should enter the same local book together. If its last journal is invalid, none of its earlier journals should be posted.

The Framework batch service prepares a private book, captures the inputs used for review, and checks that the live inputs still match before publishing. It uses the same eligibility rules as single-journal review.

1. Establish the account and amount convention

Choose one currency and scale for the relevant accounts before creating journals. The example uses GBP pennies. These journal structures contain integer amounts but no currency or scale metadata; they do not perform currency conversion or infer an account's currency. Keep the live journals, account catalogue, period calendar and book alive and serialize access to them.

2. Inspect the complete batch

#include "umicom/finance/accounting/posting_batch.h"

UmiAccountingPostingBatchPreview preview;
UmiStatus status = umi_accounting_posting_batch_inspect(
    entries, count, &chart, &calendar, &book, &preview);

If status is OK, inspection produced a preview. Check preview.refusal separately. A refused preview identifies failed_index, the first refused journal, and detail, its posting reason. ready_count and line_count describe the inspected eligible prefix, not journals already posted. The live book remains unchanged.

The count must be between one and UMI_ACCOUNTING_MAX_ITEMS. Inspection allocates bounded temporary storage and can return OUT_OF_MEMORY. Invalid arguments leave the output preview unchanged.

3. Capture what the user will review

UmiAccountingPostingBatchReview *review = NULL;
status = umi_accounting_posting_batch_create(
    entries, count, &chart, &calendar, &book, &preview, &review);

Only an eligible complete batch produces a review. Display entries from umi_accounting_posting_batch_entry(review, index) and their eligibility from umi_accounting_posting_batch_entry_preview. These borrowed pointers remain valid until the review is destroyed. They describe the captured values even if an editor changes the live journals later.

Do not sum amounts across journals without establishing currency and scale agreement. The batch preview supplies counts rather than a misleading cross-currency money total.

4. Apply the captured decision

status = umi_accounting_posting_batch_apply(
    review, entries, count, &chart, &calendar, &book);

umi_accounting_posting_batch_destroy(review);
review = NULL;

A successful apply appends all journals as POSTED and consumes the review. It leaves the original input journal states unchanged. Repeating Apply is refused. A changed active field, different owner address, changed order or count, closed period, edited account, or modified live book makes the review stale. A refused apply does not change the live book.

If a review is stale, show the new live state and capture a new review. Do not silently replace the user's captured decision. There is no allocation, provider call, file write or callback during apply.

ResultMeaning and next action
INVALID_ARGUMENTCheck required pointers and the bounded entry count. Output memory must not overlap an input.
ALREADY_EXISTS during captureA journal ID already exists in the book or appears earlier in this batch. Correct the duplicate before recapturing.
CAPACITY_EXCEEDEDThe full set cannot fit or an entry total overflows. No prefix is posted.
INVALID_STATE during applyThe review is stale, already consumed, or supplied with different owners. Review the current values again.

5. Explore the installed example

The SDK installs share/umicom/examples/journal_batch. Copy that directory to a writable example folder and replace the prefix below with your actual installed SDK location:

cmake -S . -B build -DUMICOM_SDK_PREFIX="/absolute/path/to/sdk"
cmake --build build
ctest --test-dir build --output-on-failure

The example uses only exported SDK targets. Its scenarios demonstrate successful publication, stale drafts, changed account permission, duplicate IDs and a refusal in the second journal. On a multi-configuration generator, add the appropriate configuration to build and CTest commands.

What this service does not establish

This is serialized, all-or-nothing in-memory publication. A struct assignment is not a concurrent atomic operation or a database transaction. The surrounding service still owns authenticated approval, currency agreement, persistence, crash recovery, reconciliation and external posting receipts. Local pointer identity and field equality do not protect against malicious memory writers, address reuse or replay after persistence.
