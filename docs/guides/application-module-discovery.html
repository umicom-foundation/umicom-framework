Registering an Umicom application module

An application module is a repository containing a CMake project and an application.umicom.yaml manifest. The manifest describes the application. The Applications suite discovers registered modules from its .gitmodules file. Adding an initialised module no longer requires three matching declarations in UmicomExtendedApplicationModules.cmake.

Discovery reads source metadata. It does not clone repositories, commit files, prove that an application works, or grant permission to run arbitrary CMake code. Review the module before configuring it. Configure-time support requires CMake 3.24 or later and Git.

1. Prepare a module

Start with the complete examples/application_module directory. Keep the project, manifest and application source at the root of the module repository. Give your module unique application and executable identities. Build identity values use plain ASCII identifiers, and display names may additionally contain spaces, parentheses, dots and hyphens. Quoted YAML, expressions and multiline build identities are deliberately unsupported.

schema: umicom.application.v1

application:
  id: org.example.notes
  name: Example Notes
  version: 0.1.0
  executable: example-notes
  console_executable: example-notes

frontends:
  - console

installation:
  component: ExampleNotes

Keep docs/application-features.md in the module, with sections named Supported features, Getting started and Limitations. Describe real behaviour and recovery steps. The suite accepts this guide or an existing entry in its central application coverage document.

2. Inspect the manifest

From a terminal where the native Umicom command is available:

umicom repo inspect-module "C:\Projects\example-notes\application.umicom.yaml"

Expect the identity, build option, installer component and declared frontend names. The command reads only the chosen manifest. Native inspection also uses the existing runtime manifest validator. A successful inspection does not replace compilation or workflow testing.

3. Register the repository

From the Applications suite, add your reviewed module using ordinary Git or the existing native repository command. Replace the example repository address with yours:

git submodule add https://example.org/team/example-notes.git applications/example-notes

Use a direct path under applications/ containing lowercase letters, digits and hyphens. Initialised modules must have a manifest and CMakeLists.txt within their directory. Discovery checks all available identities, including disabled modules, for collisions. It rejects paths and metadata that resolve outside their permitted source directory.

4. Select and build the module

The option comes from native_executable, when present, otherwise executable. Discovery removes a leading umicom-, changes dots and hyphens to underscores, and uppercases the result. Existing core products keep their specialised options and setup. New module options default to off.

ExecutableBuild option
umicom-weatherUMICOM_APPLICATIONS_BUILD_WEATHER
example-notesUMICOM_APPLICATIONS_BUILD_EXAMPLE_NOTES
cmake --preset windows-ucrt64-all-debug -DUMICOM_APPLICATIONS_BUILD_EXAMPLE_NOTES=ON
cmake --build --preset windows-ucrt64-all-debug --target example-notes --parallel 2
ctest --preset windows-ucrt64-all-debug -R "^example-notes\." --output-on-failure --no-tests=error

Use the actual CTest names registered by your module. Stop when configure fails; a later build cannot repair a missing manifest or an uninitialised repository. The all-module option enables every registered module and fails if any checkout is missing. After initialising a missing checkout, explicitly configure again.

5. Keep installation and tests with the application

The Framework registration helper calls the module's existing add_subdirectory integration. It sets CMAKE_INSTALL_DEFAULT_COMPONENT_NAME before entering the module, so ordinary install() rules inherit that component. An explicit installation.component is preferred; otherwise the component comes from the display name with non-alphanumeric characters removed. Module add_test() rules remain active when testing is enabled.

cmake --install build/windows-ucrt64-all-debug --component ExampleNotes --prefix "C:/Projects/installed"

Rules that explicitly name another install component remain explicit. Discovery does not rewrite them. Install the required Framework runtime and resources too.

6. Compose a graphical frontend

Declare native_executable separately from console_executable and list gtk under frontends. If your module defines its own non-imported executable with that native name, the suite adds it to umicom-desktop-products and retains its own install rules. An unrelated target, alias or library with that name is rejected. The existing shared host remains available to applications with an implemented Framework product experience. A new manifest alone does not create controllers, panels, a product experience or a launcher-catalogue entry.

Standalone SDK use

The example also supports an independent build against an installed SDK:

cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH="C:/Projects/installed" -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure --no-tests=error

The installed package exports the C23 descriptor API through Umicom::runtime and the CMake helpers through UmicomApplicationModules.cmake.

Troubleshooting and limits

  • Missing checkout: initialise the named submodule, then configure again. Discovery never fetches or resets a checkout. The suite's existing governance audit may also require all registered checkouts even when building selected modules.
  • Identity or option collision: choose distinct identities and executable names; changing only letter case is insufficient on Windows.
  • Metadata rejected: use the nested schema first, direct two-space application fields and ordinary scalar identities. Keep manifests within 64 KiB. Older flat manifests remain supported by the runtime API but must be converted for automatic build discovery.
  • Frontend unavailable: declaring a native executable does not implement its product UI. Supply the executable or implement the corresponding Framework experience.
  • Scope: discovery supports at most 128 direct application modules. Native inspection accepts a normal local file and does not follow a final symlink. Parent directories must be trusted. These checks are not a sandbox for a malicious build script.

The native source creator and Studio form can create a standalone application whose build also works as a registered suite module. Coordinated creation of separate remote repositories and automatic publication are not supplied. Repository changes remain an explicit workflow after source review.

Inspect registrations before configuring

The native command reads registered direct children of applications and their manifests without configuring, building, fetching or changing Git state:

umicom repo modules "C:\umicom\Umicom-Applications"

It prints the number of registered applications, ready manifests and unavailable manifests. Each ready row names its build option, installer component and advertised frontends. An uninitialised checkout or invalid manifest remains in the report with its status; it is not silently treated as an application that can build.

An absent registration file produces an empty catalogue. A copied directory that is not registered in .gitmodules is not included. Duplicate paths or colliding application IDs, build options, installer components and executable names reject the catalogue and identify the conflicting paths. Comparisons ignore ASCII letter case to keep names portable across supported filesystems.

This is local source evidence. It does not prove that a submodule commit is pushed, that the parent records its current commit, or that the application compiles. Git include files are disabled during this inspection. The service rereads the registration file to detect an observable edit during collection; it does not lock the repository or provide a transaction across all manifests. Paths must use the portable applications/lower-case-slug layout. Resolve reported missing manifests or collisions before registering another module or enabling its build option.

Native hosts can link Umicom::scaffold and use UmiApplicationCatalogueLoad from umicom/scaffold/application_catalogue.h on a worker. Entry pointers are borrowed until UmiApplicationCatalogueDestroy. Do not use this read-only catalogue as authority to overwrite source, alter a Git index or execute an application.

For the source creator and Studio form, see creating application modules. Those workflows are separate from discovery and do not publish repositories.

Check a proposed module before registration

  1. Create the application source in a folder you selected, then inspect its manifest.
  2. Run the registration preflight against the suite and the proposed direct application path: 
    umicom repo check-module "C:\umicom\Umicom-Applications" "C:\projects\weather\application.umicom.yaml" applications/weather
  3. Read the reported application ID, build option and installer component. Success prints No registration conflict observed and returns exit code 0. No submodule, Git index, commit or remote is changed.
  4. If the command identifies an existing registration, choose a distinct identity, executable or installer component in the proposed manifest and repeat the check. Names that differ only by letter case still conflict. If an existing manifest is unavailable, restore that checkout or repair its manifest before treating the review as complete.
  5. Review source and repository ownership before using your usual explicit submodule registration procedure. Configure after registration so the suite discovers the manifest. Repeat the preflight if any existing manifest or registration changes.

The preflight checks metadata in a local snapshot. It does not verify Git history, remote ownership, the parent gitlink, build-script safety or executable readiness. It is not a lock and does not reserve names. The catalogue has a 128-application bound; a full catalogue reports capacity rather than silently omitting an application.

Native clients can call UmiApplicationCatalogueCheckCandidate with a descriptor produced by the manifest parser or source creator. The function checks the bounds of all copied fields, validates the derived option and returns a copied reason and conflicting path. It performs no I/O. Keep the catalogue alive for the call, then reload it when the user changes the suite or its manifests.
