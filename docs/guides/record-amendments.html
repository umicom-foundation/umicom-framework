Keep the history of a record amendment

An amendment is a new revision explaining a change to a record. The original revision remains available. The Framework Data Server supplies shared storage and transactions; application code supplies the identity, source, actor and reason.

Include umicom/data/record_history.h and link Umicom::data. The same API can describe a synthetic care observation, a reviewed bank import or an edited document.

What is retained

FieldMeaning
Entity IDA stable application identifier, at most 63 bytes.
Revision and previous revisionA numbered chain starting with revision 1 and predecessor 0.
Source, actor and reasonRequired metadata describing this amendment. Earlier revisions keep their own values.
Observed and recorded timesCaller-supplied nanoseconds. Observed time can be zero when unknown. Recorded time must be nonzero and cannot move backwards within the entity history.
Content SHA-256Exactly 64 lowercase hexadecimal characters supplied by the application to identify separately retained content.

This service stores metadata, not document contents. It does not authenticate actors, check the supplied content digest, authorize changes or make clinical decisions. A hash does not prove who made a change. Applications remain responsible for access control, content storage and the relationship between the saved content and this history.

Create and amend a record

  1. Create or open a Data Server. Memory storage lasts until that server is destroyed; SQLite storage uses a database file when SQLite support is available.
  2. Populate a UmiRecordAmendment. All text arrays must be terminated and contain no control characters. Source, actor and reason are required; free-text documents belong in separate storage.
  3. Call umi_record_history_append(server, &amendment, 0, &saved) for a new entity.
  4. Read and review the latest revision. Submit a later amendment with that reviewed number as expected_revision.
  5. Use umi_record_history_load to display an earlier revision, umi_record_history_latest for the current one, and umi_record_history_verify to check the recorded chain.

The service owns a transaction around the new row and current-revision pointer. It rejects nested transactions and competing owners. A failed operation leaves the caller's output unchanged. History verification checks missing or malformed links and time regressions; it cannot detect a malicious rewrite of the whole store or validate external content.

Try the fictional examples

From an Applications checkout with the Windows UCRT64 toolchain and its existing prerequisites installed:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --preset windows-ucrt64-all-debug -DBUILD_TESTING=ON
cmake --build --preset windows-ucrt64-all-debug --target umicom-lineage-history-test umicom-record-history-test umicom-record-history-example --parallel 2
ctest --preset windows-ucrt64-all-debug -R '^framework\.data\.(lineage|history)\.' --output-on-failure --no-tests=error
& ".\build\windows-ucrt64-all-debug\bin\umicom-record-history-example.exe"

Stop if any command reports an error. The example prints two fictional entity IDs, each at revision 2, with the original source still available. SQLite-specific cases are registered only when SQLite is enabled; their absence does not establish SQLite coverage. The example and tests contain no real care or financial records.

The installed SDK includes this guide and share/umicom-framework/examples/data_history. Its separate CMake project uses find_package(UmicomFramework CONFIG REQUIRED) and has no source-tree fallback.

Handle a rejected amendment

ResultRecovery
INVALID_STATERe-read the latest revision and let the user review the difference. Do not silently retry using the new number. An occupied orphan row also requires inspection.
BUSYFinish the caller-owned transaction or wait for the other operation, then review and retry. The service does not commit somebody else's transaction.
INVALID_ARGUMENTCheck required metadata, digest format and recorded time.
PARSE_ERROR / NOT_FOUNDInspect the stored history and restore from a trusted backup if appropriate. Do not overwrite a damaged history to make it appear complete.
IO_ERRORInspect Data Server diagnostics. If rollback could not complete, retain the server and follow its rollback recovery contract before another operation.
CAPACITY_EXCEEDEDCheck storage and field limits. The memory backend has a bounded number of records. Do not discard earlier amendments to free space.

Existing lineage clients

The older umi_lineage_* API remains available with its original public structures and valid six-field text format. Reopened handles now skip occupied keys; failed saves do not change the caller's sequence; empty optional fields remain readable. Because its provider-neutral store has no atomic compare-and-insert operation, callers must serialize legacy appenders and must not delete history keys. Use the transaction-owned amendment API for new expected-revision workflows.

Reserve repo.record-history.* and legacy lineage keys for their services. Direct database edits bypass these contracts. Presentation, authenticated identity, payload persistence and migration tools must be supplied by the consuming application or additional Framework services.
