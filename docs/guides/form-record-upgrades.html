Reviewing stored form upgrades

A schema describes the fields and rules in a form. Changing that description must not silently change an older record's meaning. The Framework upgrade service creates a reviewable proposal and saves it as a new historical revision. Link your C23 application with Umicom::form_records and include umicom/data/structured_form_upgrade.h.

Before you begin

Keep the original schema available for reading old records. The new schema must have the same form identifier and a greater version. The conservative migration accepts added fields with valid defaults and removed unanswered fields. It refuses removing answered fields or changing an existing field's value type, unit or date/time format. Conversion between units needs a separately reviewed application workflow.

Review and save a proposal

  1. Load the original document with umi_record_document_latest. Identify its original schema from your application's trusted schema catalogue. Do not choose a schema from an untrusted file path.
  2. Call umi_structured_form_upgrade_create with that schema, the document and the new schema. This checks the stored digest and decodes the original form before migration. No storage is written.
  3. Read umi_structured_form_upgrade_snapshot. Show the original and target versions, retained/added/removed field counts and proposed values to the reviewer. The review has its own revision token, separate from form edits and stored record revisions.
  4. To adjust the proposal, capture an edit with umi_structured_form_edit_capture and apply it with umi_structured_form_upgrade_apply, passing the reviewed token. Invalid or stale edits leave the proposal unchanged.
  5. Collect source, actor and reason. Prepare an owned request with umi_structured_form_upgrade_prepare_save. Pass submitting=1 when all mandatory answers are required; zero permits an incomplete draft. Preparation marks a save pending but performs no I/O.
  6. Pass the copied request to umi_structured_form_upgrade_request_commit on the chosen storage worker. It checks that the exact original historical document exists there, then appends only if the current stored head is still the reviewed revision. Keep the request unchanged while the worker uses it.
  7. Return the result and saved metadata to umi_structured_form_upgrade_finish_save on the owning thread. A successful matching reply closes the review. Read the new revision using the new schema, and the old revision using its original schema.

Ownership and recovery

The immutable target schema must outlive the upgrade handle. Source documents and original schema data are copied or consumed during creation and may be released afterward. Allocate the large bounded view and request structures on the heap. Serialize operations on the handle and keep storage work off the GTK main thread.

Pending saves block proposal edits. An unrelated completion does not clear the pending operation. A failed completion retains the proposal. If the storage result is uncertain, inspect the actual stored head before retrying; a lost response is not evidence that nothing was saved. Destroying the review does not cancel a worker.

Expected refusals

  • INVALID_STATE during creation: check schema identity/version, units, changed field types and removed answers.
  • INVALID_STATE on commit: the historical baseline differs or another writer appended a revision. Reload and review a new proposal; do not overwrite the newer head.
  • BUSY: finish the pending operation before starting another edit or save.
  • Validation errors when submitting: display the new schema's required fields and let the reviewer provide answers.

Attribution labels do not authenticate a reviewer. The caller owns access control, permitted schema selection and authorization. This local review service does not provide encrypted storage, electronic signatures or protection against an administrator rewriting raw history.
