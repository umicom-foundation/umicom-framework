Develop projects with the Umicom command

The native umicom program coordinates Git, CMake, CTest and application processes through Framework services. Install a build of the CLI that includes these commands, and make its executable available on your PATH. The selected development tools must already be installed; the CLI does not install compilers or create packaging targets.

Run the CLI from a separate tools installation when rebuilding Umicom itself. On Windows, an executable cannot be replaced while it is running. Keep the running CLI outside both the build folder and the installation destination; keep its required runtime libraries available as well. A project build or install must not overwrite the command supervising it.

Publish a workspace consistently

  1. Keep each development checkout on its intended main branch. Edit shared source in one primary checkout. Other copies should be clean.
  2. Review changes before publication. Keep private notes, logs and credentials outside public repositories. Filename checks cannot determine whether every document is appropriate for publication.
  3. Preview the workspace. This discovers repositories and fetches remote metadata; it does not stage source, commit, push or switch branches.
umicom repo publish-all C:\work
umicom repo publish-all C:\work --apply

--apply performs a fresh preflight. Framework publishes each changed child repository once using git add -A, a non-empty commit and a normal push to main. It pulls clean duplicate copies with fast-forward-only, nonrecursive updates, locks parent child revisions, then commits and pushes parents. A dependency is published before the parent that records its revision. Existing vendor pins are retained.

Detached checkouts, independent work in duplicate copies, divergence and changed registrations stop the workflow for review. It never uses force-push, reset, clean, automatic stash or rebase to make publication succeed. A later failure can leave earlier repositories successfully published; inspect the completed-action report and rerun after resolving the cause. Publication across independent remotes is not a transaction.

umicom repo watch C:\work --interval 30
umicom add -A
umicom commit -m "Improve application commands and regression coverage"
umicom push
umicom pull
umicom repo lock .

watch observes local changes without publishing. pull and repo update require a clean checkout on the requested branch and default to leaving nested checkouts untouched. The advanced --with-submodules update option explicitly checks out registered child pins and may detach those children; it is not part of the main-branch development routine. repo lock records checked-out child commits; it does not download newer code. Prefer publish-all when publishing an ecosystem with duplicate copies and parent repositories. Individual commands do not automatically coordinate other checkouts.

See repository publication for the discovery rules and limits.

Preview before running development tools

Use --dry-run on configure, build, test, install, package, make, deliver or launch. It shows the working directory and literal process arguments without discovering tools, launching them or creating a log. Printed arguments are an inspection view, not a shell script. A successful preview is not compiler or test evidence.

umicom build --source C:\work\my-project --build build\debug --jobs 2 --dry-run
umicom build --help

Configure, build and test

A preset is a named configuration defined by the project's CMake files. Choose a preset that exists in that project. The following preset name is an example; replace it when working on a different project. Unknown or duplicate CLI options fail before tool discovery.

umicom configure --source C:\work\my-project --preset windows-ucrt64-all-debug --log C:\work\logs\configure-01.log
umicom build --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\build-01.log
umicom test --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\test-01.log

Choose an existing, private log directory and a new filename for each invocation. Existing files are never overwritten. Output appears live and the log retains raw merged stdout/stderr, including output longer than the diagnostic tail. A failed log open prevents execution. A later write failure stops subsequent phases after the active child finishes. A flush error is reported even if the child succeeds. Tool-discovery diagnostics and the CLI's command descriptions are displayed separately from the raw child-output log.

test always supplies --output-on-failure and --no-tests=error. No matching tests is a failure. CTest still defines how disabled/skipped tests and compiler warnings affect its exit status: inspect the log rather than interpreting zero as proof that every test ran or every warning disappeared.

umicom make --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\make-01.log
umicom test --source C:\work\my-project --build build\debug --tests "^framework[.]toolchain" --jobs 2
umicom configure --source C:\work\my-project --build build\debug --define BUILD_TESTING=ON --define CMAKE_BUILD_TYPE=Debug

make runs configure, build and test in sequence, stopping on the first failure. Up to sixteen --define NAME=VALUE options can be passed to configure/make/deliver. Values are literal arguments; they are not interpreted by a shell.

Select binary folders explicitly

Some presets use a binaryDir outside build/preset-name. Umicom does not infer that directory for installation or launch. Use the actual binary folder with --build. Relative paths, including executable, install and log paths, are resolved against --source; the source is resolved against the invocation directory.

If both --preset and --build are supplied, configure uses that configure preset with an explicit -B override. Build, test and package then operate directly on that directory. In this mode build/test preset-specific arguments and environment settings are not applied; supply the corresponding CLI selectors explicitly. Use preset-only commands when those preset settings are needed.

Install and package

umicom install --source C:\work\my-project --build build\debug --prefix C:\work\installed\my-project --config Debug --log C:\work\logs\install-01.log
umicom package --source C:\work\my-project --build build\debug --config Debug --jobs 2 --log C:\work\logs\package-01.log

Installation requires both --build and --prefix. Add --component Framework to install only a configured component. Packaging builds the project's package target, or a target selected with --package-target. A project without that target reports an error; Umicom does not invent an installer.

umicom deliver --source C:\work\my-project --preset windows-ucrt64-all-debug --build build\delivery --prefix C:\work\installed\my-project --config Debug --jobs 2 --log C:\work\logs\delivery-01.log

deliver runs configure, build, test, install and package. It performs no Git publication. A failed package step does not undo a completed installation. Use separate commands when publishing source before qualification, or when a project has no package target.

Launch applications

umicom launch studio --source C:\work\my-project --build build\debug
umicom launch --source C:\work\my-project --executable C:\work\installed\my-project\bin\my-app.exe -- --workspace "C:\work\examples with spaces"
umicom qemu --help

launch and run share the same execution service. Application aliases select bin/umicom-NAME under the explicit binary directory, with the native executable suffix. Studio and Desk have their established executable names. Use --executable for a different layout, including multi-configuration output folders. Arguments after -- go to the application unchanged. A run is supervised until the application exits. Use the separate QEMU commands for supported virtual machines and kernel boot workflows.

Recover from a failed step

  1. Read the named failing phase, child exit code and log path. Later phases were not attempted.
  2. Correct the reported source, tool, configuration or permission problem. Do not delete a log to disguise a failure.
  3. Rerun the failed command with a new log filename. A per-process limit can be set with --timeout-ms.
  4. For an explicitly requested clean, use a separate binary directory containing a CMake cache for the selected source. Source directories, ancestors and unrelated folders are refused. Keep the directory and its parents under your control; this check is not an adversarial filesystem sandbox.

The original Framework request and report layouts remain available to native callers. The extended execution contract adds optional observers and an injectable process transport; Studio can share the same orchestration without implementing shell commands.
