Develop projects with the Umicom command

The native umicom program coordinates Git, CMake, CTest and application processes through Framework services. Install a build of the CLI that includes these commands, and make its executable available on your PATH. The selected development tools must already be installed; the CLI does not install compilers or create packaging targets.

Run the CLI from a separate tools installation when rebuilding Umicom itself. On Windows, an executable cannot be replaced while it is running. Keep the running CLI outside both the build folder and the installation destination; keep its required runtime libraries available as well. A project build or install must not overwrite the command supervising it.

Publish a workspace consistently

  1. Keep each development checkout on its intended main branch. Edit shared source in one primary checkout. Other copies should be clean.
  2. Review changes before publication. Keep private notes, logs and credentials outside public repositories. Filename checks cannot determine whether every document is appropriate for publication.
  3. Preview the workspace. This discovers repositories and fetches remote metadata; it does not stage source, commit, push or switch branches.
umicom repo publish-all C:\work
umicom repo publish-all C:\work --apply

--apply performs a fresh preflight. Framework publishes each changed child repository once using git add -A, a non-empty commit and a normal push to main. It pulls clean duplicate copies with fast-forward-only, nonrecursive updates, locks parent child revisions, then commits and pushes parents. A dependency is published before the parent that records its revision. Existing vendor pins are retained.

Detached checkouts, independent work in duplicate copies, divergence and changed registrations stop the workflow for review. It never uses force-push, reset, clean, automatic stash or rebase to make publication succeed. A later failure can leave earlier repositories successfully published; inspect the completed-action report and rerun after resolving the cause. Publication across independent remotes is not a transaction.

umicom repo watch C:\work --interval 30
umicom add -A
umicom commit -m "Improve application commands and regression coverage"
umicom push
umicom pull
umicom repo lock .

watch observes local changes without publishing. pull and repo update require a clean checkout on the requested branch and default to leaving nested checkouts untouched. The advanced --with-submodules update option explicitly checks out registered child pins and may detach those children; it is not part of the main-branch development routine. repo lock records checked-out child commits; it does not download newer code. Prefer publish-all when publishing an ecosystem with duplicate copies and parent repositories. Individual commands do not automatically coordinate other checkouts.

See repository publication for the discovery rules and limits.

Compose a single-project lifecycle

umicom workflow combines verification, configuration, build, test and repository actions through the shared Framework executor. Complete requests are admitted before execution, duplicate options are refused, and failures stop later actions. See execute a reviewed lifecycle for goal selection, preview, option scope and partial-progress interpretation. Workflow is a bounded single-project composition; use the individual commands below for logs, JUnit, definitions and delivery options, and publish-all for ecosystem publication.

Preview before running development tools

Use --dry-run on configure, build, test, install, package, make, deliver or launch. It shows the working directory and literal process arguments without discovering tools, launching them or creating a log. Printed arguments are an inspection view, not a shell script. A successful preview is not compiler or test evidence.

umicom build --source C:\work\my-project --build build\debug --jobs 2 --dry-run
umicom build --help

Configure, build and test

A preset is a named configuration defined by the project's CMake files. Choose a preset that exists in that project. The following preset name is an example; replace it when working on a different project. Unknown or duplicate CLI options fail before tool discovery.

umicom configure --source C:\work\my-project --preset windows-ucrt64-all-debug --log C:\work\logs\configure-01.log
umicom build --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\build-01.log
umicom test --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\test-01.log

Choose an existing, private log directory and a new filename for each invocation. Existing files are never overwritten. Output appears live and the log retains raw merged stdout/stderr, including output longer than the diagnostic tail. A failed log open prevents execution. A later write failure stops subsequent phases after the active child finishes. A flush error is reported even if the child succeeds. Tool-discovery diagnostics and the CLI's command descriptions are displayed separately from the raw child-output log.

test always supplies --output-on-failure and --no-tests=error. No matching tests is a failure. CTest still defines how disabled/skipped tests and compiler warnings affect its exit status: inspect the log rather than interpreting zero as proof that every test ran or every warning disappeared.

umicom make --source C:\work\my-project --preset windows-ucrt64-all-debug --jobs 2 --log C:\work\logs\make-01.log
umicom test --source C:\work\my-project --build build\debug --tests "^framework[.]toolchain" --jobs 2
umicom configure --source C:\work\my-project --build build\debug --define BUILD_TESTING=ON --define CMAKE_BUILD_TYPE=Debug

make runs configure, build and test in sequence, stopping on the first failure. Up to sixteen --define NAME=VALUE options can be passed to configure/make/deliver. Values are literal arguments; they are not interpreted by a shell.

Keep test transcripts and structured results

Three output files serve different purposes. --log records the child's raw merged output through Framework and refuses an existing filename. --output-log asks CTest to write its own transcript. --output-junit asks CTest to write an XML result file that other tools can read. XML is a structured text format; it is not a separate test run.

  1. Choose an existing private directory for this qualification attempt. Use a new directory for a rerun to retain earlier results.
  2. Check umicom test --help lists the artifact options. CTest 3.21 or later is required for JUnit output.
  3. Preview the exact paths, then run the same request without --dry-run.
  4. Inspect the command's exit status and both reports. A skipped test remains a skip, and an interrupted run may leave incomplete files.
umicom test --source C:\work\my-project --build build\debug --output-log C:\work\logs\attempt-01\ctest.log --output-junit C:\work\logs\attempt-01\results.xml --log C:\work\logs\attempt-01\stream.log --dry-run
umicom test --source C:\work\my-project --build build\debug --output-log C:\work\logs\attempt-01\ctest.log --output-junit C:\work\logs\attempt-01\results.xml --log C:\work\logs\attempt-01\stream.log

The three paths must be distinct. CTest owns its files and may replace existing content, whereas Framework creates the raw stream log exclusively. Do not point two output options at the same file. Relative artifact paths resolve against --source, just like the other CLI paths. Native callers set absolute test_output_log and test_output_junit paths in a zero-initialized UmiBuildExecutionOptions.

The equivalent direct test command is:

ctest --test-dir C:\work\my-project\build\debug --output-on-failure --no-tests=error --output-log C:\work\logs\attempt-01\ctest.log --output-junit C:\work\logs\attempt-01\results.xml

These direct commands use the same project build tree. Choose either the Umicom invocation or the direct invocation for an attempt; running both with identical output paths replaces CTest's first reports. See the CTest JUnit documentation for the tool's output contract.

Pass an option to the configured build tool

CMake delegates compilation to the generator selected during configuration. For a Ninja build, the following request keeps compiling independent work after an error. It still returns a failed build result when any required command fails, so a combined workflow stops before tests or installation.

umicom build --source C:\work\my-project --build build\debug --jobs 2 --build-argument -k --build-argument 0
cmake --build C:\work\my-project\build\debug --parallel 2 -- -k 0

Use one of these equivalent commands. Each --build-argument supplies one literal value after CMake's -- separator, with at most sixteen values. Values containing spaces need PowerShell quotes. The CLI does not interpret shell expressions. The values are passed to build and package phases only, including those phases inside make or deliver; they do not become configure definitions or test options. A different generator may need different native arguments. Consult CMake's build command and your chosen generator before using them.

If the CLI refuses an output option on a build-only command, move it to umicom test or a workflow containing a test phase. If a native argument is rejected by Ninja, correct that argument and rerun the failed phase; changing a CTest option cannot repair a compiler failure.

Understand validation before execution

A build request describes the action and paths. Execution options describe how it is observed: preview, output callbacks, configure definitions and the chosen binary directory. Native integrations call UmiBuildExecutionValidate to check these together. Both UmiBuildExecuteWithOptions and UmiBuildExecuteLogged use the same validation before invoking callbacks or creating an output log.

  1. Prepare the request and its options. Configure definitions belong to configure, make or deliver; passing them to a build-only action is an error.
  2. Inspect the returned status and diagnostic. Correct missing paths, invalid argument storage or malformed definitions before trying again. A rejected request does not reserve the requested log filename.
  3. Retry with the corrected request. If a previous accepted invocation already created the log, choose a new filename; it is never overwritten.

For example, a native caller that marks the build directory as explicit but supplies no path receives an invalid-argument result before log creation. This ordering keeps a typo from consuming the filename needed by the corrected run. Validation checks the invocation contract; it does not prove a compiler is installed, a target exists or a project can build. The regression sources in tests/toolchain_lifecycle/test_build_logging.c and test_build_execution.c exercise these boundaries with a controlled process transport. Running them is a separate qualification step.

Build and test a changed component

Use umicom build-test with an explicit configured build folder, target and test expression to compile then test without requesting configure or clean. It stops before tests if the build fails. See Build and test a changed component for a complete example, selection limits and incremental-build troubleshooting.

Select binary folders explicitly

Some presets use a binaryDir outside build/preset-name. Umicom does not infer that directory for installation or launch. Use the actual binary folder with --build. Relative paths, including executable, install and log paths, are resolved against --source; the source is resolved against the invocation directory.

If both --preset and --build are supplied, configure uses that configure preset with an explicit -B override. Build, test and package then operate directly on that directory. In this mode build/test preset-specific arguments and environment settings are not applied; supply the corresponding CLI selectors explicitly. Use preset-only commands when those preset settings are needed.

Install and package

umicom install --source C:\work\my-project --build build\debug --prefix C:\work\installed\my-project --config Debug --log C:\work\logs\install-01.log
umicom package --source C:\work\my-project --build build\debug --config Debug --jobs 2 --log C:\work\logs\package-01.log

Installation requires both --build and --prefix. Add --component Framework to install only a configured component. Packaging builds the project's package target, or a target selected with --package-target. A project without that target reports an error; Umicom does not invent an installer.

umicom deliver --source C:\work\my-project --preset windows-ucrt64-all-debug --build build\delivery --prefix C:\work\installed\my-project --config Debug --jobs 2 --log C:\work\logs\delivery-01.log

deliver runs configure, build, test, install and package. It performs no Git publication. A failed package step does not undo a completed installation. Use separate commands when publishing source before qualification, or when a project has no package target.

Launch applications

umicom launch studio --source C:\work\my-project --build build\debug
umicom launch --source C:\work\my-project --executable C:\work\installed\my-project\bin\my-app.exe -- --workspace "C:\work\examples with spaces"
umicom qemu --help

launch and run share the same execution service. Application aliases select bin/umicom-NAME under the explicit binary directory, with the native executable suffix. Studio and Desk have their established executable names. Use --executable for a different layout, including multi-configuration output folders. Arguments after -- go to the application unchanged. A run is supervised until the application exits. Use the separate QEMU commands for supported virtual machines and kernel boot workflows.

Recover from a failed step

  1. Read the named failing phase, child exit code and log path. Later phases were not attempted.
  2. Correct the reported source, tool, configuration or permission problem. Do not delete a log to disguise a failure.
  3. Rerun the failed command with a new log filename. A per-process limit can be set with --timeout-ms.
  4. For an explicitly requested clean, use a separate binary directory containing a CMake cache for the selected source. Source directories, ancestors and unrelated folders are refused. Keep the directory and its parents under your control; this check is not an adversarial filesystem sandbox.

The original Framework request and report layouts remain available to native callers. The extended execution contract adds optional observers and an injectable process transport; Studio can share the same orchestration without implementing shell commands.

Record tool versions before qualification

umicom doctor --versions-only uses Framework tool discovery to report executable paths and version results. It runs the discovered tools' version commands and captures the selected compiler target. It does not compile, link or run a generated probe program. Use --versions-only with an optional --report destination; options such as --all still belong to a separate full doctor check.

umicom doctor --versions-only

The report explicitly prints Compile, link, runtime and C23 probes: NOT RUN. A zero exit status means the required discovery checks completed, not that your project can build. A missing required tool produces a nonzero result. Correct the installation or discovery environment and repeat the inventory before requesting a build.

  1. Record the inventory alongside the source revision, selected preset and complete configure command.
  2. Check that the reported compiler family and paths match the SDK and build tree you intend to use. The inventory does not inspect a previously configured CMake cache.
  3. Run configure, build and tests as separate qualification steps. Preserve their results even when inventory succeeded.

On PowerShell, an outer Start-Transcript/Stop-Transcript session can still capture the commands you typed and their surrounding output. Umicom's --log records a supervised child stream; it does not replace that whole-session record. The shorter inventory command also does not replace a full umicom doctor --all check, which may compile and run probes.

Save a tool inventory file

  1. Create a private attempt directory before running the command. Use a fresh filename; the writer never replaces an earlier inventory.
  2. Check umicom doctor --help lists --report. Use a CLI executable outside any build/install tree you are about to replace.
  3. Run the inventory command below, then inspect its exit status before continuing.
umicom doctor --versions-only --report C:\work\evidence\attempt-01\tools.json

The JSON file includes the discovered profile, target, selected compiler names, every known tool's state/path/version and the discovery result. Missing tools are explicit. The compile, link, runtime and C23 probe states are not-run, and qualificationPassed is false even when discovery succeeds. A version string describes the tool's reported text; this file does not hash executable bytes or record every dependency.

CLI exitMeaningNext step
0Discovery completed and a requested report was saved.Compare paths with the intended build cache, then qualify separately.
1Discovery was incomplete. A requested valid report was still saved.Inspect missing/failed tools; correct the environment and use a new report path.
2Invalid invocation, evidence write failure or console-output failure.Read the diagnostic. Retain a partial file after storage failure; a saved file may already exist if console output failed later.

Recovery: an already-existing filename remains unchanged. A relative path is refused before discovery. The parent directory must exist. Windows output paths must be ordinary UTF-8 drive paths; device names, alternate streams and UNC paths are refused. Invalid UTF-8 in a captured field is rejected instead of silently changing evidence. For a write/flush failure, preserve the incomplete file and choose a new name after fixing storage.

Use the shared service from C

#include "umicom/toolchain/version_inventory.h"

/* Discovery is a separate, explicit operation. Keep its status beside its
 * report. This helper only validates and writes the already captured data. */
UmiStatus SaveVersionInventory(const UmiToolchainDiscoveryReport *report,
    UmiStatus discovery_status, const char *new_absolute_path)
{
    return umi_toolchain_version_inventory_save(report, discovery_status,
        new_absolute_path);
}

Callers must capture with skip_compile_probe = 1 and serialize access to the report until formatting or saving returns. The service rejects reports whose probe-pass flags are set. Zero flags alone cannot prove that a caller actually skipped probes, so this is an API precondition as well as an input check. CLI and Studio integrations can share this service. The native CLI is wired; a dedicated Studio evidence-export control is not supplied by this guide.

Keep three identities separate

  1. Tool inventory: describes discovered paths and version responses. It does not inspect the selected CMake cache or authenticate executable bytes.
  2. Source observation: the existing umicom source-observation command hashes files declared in a generated release inventory. It does not discover every unlisted file or create an atomic filesystem snapshot.
  3. Qualification report: the existing umicom qualification-report command reads a saved report; reading it does not rerun its tests.

Follow scoped qualification for source-observation, report and retry-plan commands. Keep the outer PowerShell transcript when you need the typed commands and surrounding shell output. A new inventory report complements that record; it does not capture a whole session, Git history, installed dependencies or deployment.

Record selected file bytes

A version string describes what a program reports. A SHA-256 digest identifies the bytes read from a file. Use observe-files to compare a compiler executable, runtime library or explicit source selection between qualification runs. The command reads the paths you list without executing them.

  1. Install a CLI containing observe-files. Check umicom observe-files --help. Keep the supervising CLI outside any build or installation destination.
  2. Create a private evidence directory and choose a new report filename.
  3. Pass absolute paths, quoted when they contain spaces.
umicom observe-files --file "C:\tools\bin\gcc.exe" --file "C:\tools\bin\libgtk-4-1.dll" --report "C:\work\evidence\tools-before.json"

Replace these example paths with actual files. A successful save prints a confirmation. Omit --report to print JSON. The report lists each path, byte count and lowercase SHA-256 digest. Files are read in selection order; no directory traversal occurs.

The default limit is 64 MiB per file, at most 64 files and 256 MiB combined. Use --max-bytes 1048576 for a one-MiB per-file limit. Empty files are valid. A missing file, directory, final-component link, invalid UTF-8 path, exact duplicate path or oversized file refuses the whole observation.

Compare without overstating the result

  1. Capture a before report, keep the inputs stable, run separate qualification commands, then capture an after report under a different filename.
  2. Compare the selection and each digest. Matching values support a claim about the bytes observed at those two reads. An edit followed by a reversal between captures can go undetected.
  3. Record test results separately. Equal hashes do not mean tests passed. A DLL path does not prove that a particular process loaded it.
  4. For a vendor repair, compare with trusted source/package records. A digest without a trusted reference cannot establish patch identity.
$before = Get-Content -Raw "C:\work\evidence\tools-before.json" | ConvertFrom-Json
$after = Get-Content -Raw "C:\work\evidence\tools-after.json" | ConvertFrom-Json
Compare-Object $before.files $after.files -Property path,bytes,sha256

No comparison output means those selected properties match. Keep both original reports. Local paths may disclose private directory names.

Recover from a refusal

Exit code 2 indicates invalid command arguments or selection syntax. Exit code 1 indicates a capture or output failure. Fix the input or storage problem before retrying. Existing destinations remain unchanged: choose a new name. After a write or flush failure, preserve the partial file; it is not deleted automatically. Trusted parent-directory aliases may be followed. This service is not an adversarial filesystem sandbox.

The C API is UmiFileObservationCapture in umicom/toolchain/file_observation.h. It owns copied paths and digests until UmiFileObservationDestroy. Formatting and saving do not reread source files. GUI clients should capture on a worker because filesystem reads can block.
