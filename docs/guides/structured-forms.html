Versioned structured forms

A form answer can be known, explicitly unknown, not applicable, or still unanswered. Keeping these states separate avoids treating a missing measurement as zero. The C23 structured-form service adds these distinctions to the existing application experience fields. Existing form APIs remain available.

Describe the form

  1. Define ordinary UmiApplicationExperienceField descriptors with stable identifiers, value types and constraints.
  2. Wrap the base schema in UmiStructuredFormSchema. Give it a nonzero semantic version and one rule for every field in the same order.
  3. Set the rule's unit to an exact identifier such as mass.kg or an empty string for unitless values. Units are application-defined tokens. This service neither infers nor converts them.
  4. Permit unknown or not-applicable answers only where the product workflow supports them. These answers require a reason and carry no typed value or unit.

The base descriptor's api_version describes its C interface. The new schema version describes answer meaning. Keep the borrowed schema and rules immutable throughout an editing session.

Edit and validate

  1. Allocate a UmiStructuredForm and call umi_structured_form_init. Initialization checks default values and leaves the output untouched if a default is invalid.
  2. Copy the displayed model revision when preparing an edit. Call umi_structured_form_set with that revision, the field ID and the complete answer. A stale revision refuses the edit without replacing the current model.
  3. Call umi_structured_form_validate with submitting set to zero while editing. Required unanswered fields may remain in a draft.
  4. Before submission, validate with submitting set to one and inspect the report's error count. An explicitly permitted unknown answer satisfies the answer requirement; a product can forbid it by policy.
  5. After persistence acknowledges the exact revision, call umi_structured_form_mark_saved. An older acknowledgement cannot mark newer edits clean.

Typed values and range/choice validation reuse the existing field service. An empty text value remains different from an unanswered field. Known answers cannot carry a missing-value reason. Read-only fields cannot be changed through edit commands.

Dates and instants

Offset timestamp2024-02-29T09:30:00.123+01:00 or a Z suffix

Dates use the Gregorian calendar, years 0001–9999. Timestamps require seconds and an explicit offset; fractions allow one to nine digits. Offset magnitude cannot exceed 14:00. Unknown -00:00, leap seconds, named timezones and local timestamps without offsets are unsupported. Original text is retained. No host timezone or daylight-saving guess participates in validation.

Apply several changes together

Keep an immutable before model while editing a private candidate. Capture a UmiStructuredFormEdit, then apply it to the reviewed model. Every old answer, new answer, permission and field ID is checked before any mutation. One batch advances the revision once. Prepare an inverse immediately after applying a batch to implement reviewed undo; applying the inverse advances the revision again.

Move to a newer schema

umi_structured_form_migrate matches stable field IDs within the same form and requires a higher semantic version. It refuses removed answered fields, changed unit/type/format declarations and answers that violate new constraints. It creates a dirty candidate for review and never modifies the source on refusal. Renaming fields and converting units require a separately reviewed workflow.

Try the installed SDK example

From the installed share/umicom-framework/examples/structured_forms directory, run these commands after installing a Framework SDK that includes the application component:

cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/framework-sdk
cmake --build build
ctest --test-dir build --output-on-failure

Expected output: Mass: Unknown (Not measured). Stale edit refused. If CMake cannot find the package, point the prefix at the SDK installation, not its source checkout. If a schema change refuses an old answer, retain the original and review the unit, field type, version and missing-value policy.

Use the GTK4 editor

  1. Link Umicom::structured_form_gtk4 and construct the widget with UmiStructuredFormGtk4New. Keep the immutable schema alive for the entire widget lifetime. Initial answers are copied.
  2. Select an answer state, type its value and provide a reason when unknown or not applicable. Numeric entries use a decimal point regardless of desktop locale; boolean entries use true or false.
  3. Choose Apply draft or Validate for submission. A rejected field preserves the previously accepted model. Inactive value/reason controls retain their draft text on screen, but only information belonging to the selected answer state enters the model.
  4. Read the accepted model through UmiStructuredFormGtk4Snapshot. Persist through the application and acknowledge that exact revision with UmiStructuredFormGtk4MarkSaved.
  5. Check UmiStructuredFormGtk4CanClose before changing records or closing. Unapplied inputs and unsaved accepted answers require the host to ask for an explicit discard. Removing the editor from its root permanently retires it; create a new instance when reopening.

The installed example also builds structured-form-native when the GTK4 component is present. It is an unsaved fictional demonstration. Choice values currently use their option identifiers, and multiline values use a single entry. No web transport or product workflow is added by this widget.

Save typed answers with revision history

  1. Link Umicom::form_records and choose a record entity ID plus source, actor and reason metadata. A label is not authentication; the host must authorize access.
  2. Call umi_structured_form_record_save with zero for a new storage record or the last reviewed record revision for an amendment. The form editing revision and storage revision are separate counters.
  3. On success, acknowledge the exact captured form editing revision in the model or native editor. A newer draft stays dirty.
  4. Use umi_structured_form_record_load with zero to load the latest stored revision, or a specific number for history. Supply the original semantic schema. Use umi_structured_form_record_open_reviewed when opening a catalogue selection so a changed head cannot silently replace the selected version.

Saving accepts valid drafts with unanswered required fields. Submission validation remains explicit. Snapshot bytes and amendment metadata are committed together through the existing record document service. Hash checks detect damaged content; they do not authenticate authors or encrypt data. The current record limit is 16 KiB. Oversized forms are refused without creating a partial revision.

The standalone snapshot codec permits up to 128 KiB, preserves active typed values and all semantic metadata, and rejects extra bytes or an incompatible schema. Decimal encoding requires IEEE binary64 support. The snapshot alone has no checksum or authentication. Use the record adapter when you need atomic storage and content verification.

Integration limits

This service owns validation and in-memory editing. The optional record adapter provides local persistence; the form editor does not save automatically. Authorization, clinical decisions, monetary conversion and product-specific submission remain host responsibilities. GTK4 and native web hosts can share these C23 APIs; transport decoding and product-specific submission remain adapter responsibilities. Never trust a client-supplied revision as authorization.
