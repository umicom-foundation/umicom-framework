Recording scoped qualification evidence

A scoped check builds and tests the part of a project affected by a change. Framework can keep its selection, source observations and exact test outcomes together. The recording service does not run CMake, CTest or Git.

Link Umicom::distribution for planning, observation, run recording and report formatting. Link the separate Umicom::qualification_history bridge when the host also uses Data Server job history. Pure assessment needs no database. Missing, not run, disabled, skipped, cancelled, timed out, failed and passed outcomes remain different. A rerun needs a new attempt; it cannot replace an earlier failure.

1. Declare additional inputs

Private headers, templates and runtime resources can affect a feature without being in compiler sources. Associate them with their real local target:

include("${framework_root}/cmake/UmicomImpactInventory.cmake")
umicom_target_qualification_inputs(my_library FILES
    src/private_state.h
    resources/defaults.ini)

Call after creating the target. Relative paths use the calling directory; duplicates are removed per owner. A file can belong to several targets. Aliases, imported targets, directories and generator expressions are rejected. Missing or generated files stay unresolved and prevent a complete source observation. This declaration does not change compiler inputs or custom-command dependencies; maintain those build recipes separately. Undeclared inputs remain outside coverage.

2. Create a run before executing work

  1. Capture a fresh configured inventory and create an affected-work plan.
  2. Observe its listed bytes with UmiReleaseSourceObserve. Add --list-inputs to the normal umicom impact command to see every deduplicated input digest, byte count and escaped path.
  3. Generate a new attempt identity, expressed as lowercase SHA-256. Also supply a digest of the compiler, configuration, commands and relevant environment.
  4. Call UmiReleaseQualificationCreate. The plan and observation must describe the same inventory. Names and digests are copied; input objects may then be destroyed.

Keep inputs stable during execution. Matching observations do not prove that files stayed unchanged between reads, or that the compiler used those bytes. The service does not inspect unlisted inputs, authenticate supplied evidence, or create an isolated build snapshot.

3. Record outcomes and seal the attempt

UmiReleaseQualificationIdentity identity;
UmiReleaseQualificationGetIdentity(run, &identity);
/* Use the host's authorized executor for selected work. */
UmiReleaseQualificationRecordBuild(run, &identity, &build_result);
UmiReleaseQualificationRecordTest(run, &identity, exact_test_name, &test_result);
/* Repeat for every selected test; check every returned status. */
UmiReleaseQualificationClose(run, &identity, after_observation, toolchain_after);
UmiReleaseQualificationDescribe(run, &summary);

Each result includes outcome, Framework status, exit code, duration and captured log digest. PASSED requires OK. A passing build requires a known zero exit code. Individual test exits may be unknown when an aggregate runner result covers them; unknown values are never asserted as zero. Exact selected names are required. Evidence from another attempt or plan is rejected. Build evidence must exist before test results. Tests after a failed build stay visible but cannot make the run ready: their executables might be stale.

Close failed and interrupted attempts too. Supply null after-observation or toolchain when unavailable; explicit blockers remain. Closed runs cannot accept new results. Open attempts, no-test selections, missing results, non-passing outcomes or changed identities cannot become ready for review. Readiness covers this selection only; it is not product release approval.

Import a complete saved CTest report

Link Umicom::qualification_ctest and call UmiReleaseQualificationImportCtest with the identified run, original JUnit bytes and the actual test-process result. The existing strict parser validates the XML. Every selected name must appear exactly once; missing, unexpected or duplicate names prevent the entire import. No partial results remain. Disabled and runtime skipped tests stay separate. The report parser retains its limits of 64 MiB, 100,000 tests and 255 bytes per test name; oversized names are refused rather than truncated.

JUnit does not provide each executable exit code. Imported records mark those codes unknown and identify the XML bytes by SHA-256. The aggregate runner outcome and captured-log digest are stored separately. A failed runner still blocks review even if every testcase row says passed. The caller must establish that the saved report came from this attempt; parsing alone cannot prove freshness.

4. Save evidence privately

Call UmiReleaseQualificationFormatReport with null output and zero capacity to measure its buffer, allocate that size, then call again. Use the host's checked file-saving service to save it in a user-chosen private location outside public repositories. The formatter opens no files. It includes every selected target and test, missing results, before/after identities and log digests. Names are hex-encoded so tabs and newlines cannot create false records. Keep full logs separately with their matching digests.

For database history, call UmiReleaseQualificationHistoryBegin on a pristine run and immediately call UmiReleaseQualificationHistoryPublish to record RUNNING before execution. Publish progress and closure with the returned entry ID and revision. Its three steps mean build evidence recorded, every test accounted for, and observations sealed; they are not a test count. Only a closed ready run becomes SUCCEEDED. Stale revisions are refused. Inspect the stored entry before retrying; never replay work because a history entry appears unfinished. The small history entry stores digests and progress, not detailed per-test results.

Report format

Version-one TSV starts with UMICOM-QUALIFICATION and version 1. Identity and observation rows contain lowercase digests. The selection row contains changed-path count and fallback mask. Summary fields are targets, tests, recorded, missing, passed, failed, skipped, not-run, cancelled, timed-out, disabled, blockers, closed, build-recorded, ready-for-review and test-process-recorded, in that order. Booleans use 0 or 1. Target rows contain a hex name and reason mask. Test rows add a result or missing. Results contain outcome, status, exit code, duration in milliseconds and log digest. The build and test-process rows use the same result fields. A dash in the exit-code field means unknown. The final row is end. An empty after-observation means unavailable, never unchanged. This is an audit record, not an authenticated certificate or executable replay format.

Troubleshooting

  • INVALID_STATE: inspect attempt/plan identity, closed state, build-before-tests ordering or stale history revision.
  • ALREADY_EXISTS: preserve the recorded outcome and create a new attempt for a retry.
  • NOT_FOUND: the name is not selected or has no recorded result. Do not substitute a passing default.
  • CAPACITY_EXCEEDED: retain the error. Truncating names or result sets would hide unchecked work.

Existing CLI and Studio workflows retain their behavior. Hosts must explicitly integrate these APIs; adding the recording service does not automatically attach evidence to every execution.

Planning affected builds and tests

Present a run safely in Studio or another frontend

Include umicom/distribution/runtime/qualification_view.h to capture an immutable view on the ledger's owning thread. The view copies the complete selection, exact names, outcomes and summary. Later run mutations or destruction cannot change the captured view. Transfer the view between threads only after capture completes; stop all readers before destroying it.

  1. Call UmiQualificationViewCapture(run, &view) while run mutations are serialized.
  2. Read the summary even when a filtered page is empty. Source and toolchain blockers can remain when every recorded test passed.
  3. Use UmiQualificationViewPage for bounded pages of tests, selected targets, missing required evidence or non-passing outcomes. Page offsets refer to the filtered list; each row also carries its stable unfiltered index.
  4. For GTK4, link Umicom::qualification_gtk4, include umicom/ui/gtk4/qualification_review.h, and create a panel on the GTK thread.
  5. Marshal the completed snapshot to that thread, then transfer it with UmiGtk4QualificationReviewSetView(panel, &view). Success clears the caller's pointer; the panel releases the old snapshot. Passing a null view clears the panel.

The GTK panel provides 64-row pages, evidence counters, full attempt/plan/source digests and persistent blockers. It treats names as plain text and visibly marks shortened display names. The immutable model and report retain exact names. Target rows mean selected work; aggregate build success does not provide separate per-target execution records. An optional absent test-process result is displayed as not supplied, while required missing build/test evidence remains a blocker.

The adapter does not launch jobs, import files, infer success from an empty filter, or authorize Git publication. A host still needs to connect its actual executor and capture snapshots at meaningful progress points. This library does not automatically connect every existing Studio workflow to qualification records.

Sequence an attempt through a host executor

Umicom::qualification_workflow combines the existing ledger, source observations, strict CTest import and optional build-directory guard. Include umicom/distribution/runtime/qualification_workflow.h. Call the synchronous service on a worker thread.

  1. Supply the configured inventory, its impact plan, a new execution digest and source-read options.
  2. Provide build and test callbacks that execute the exact selection and return complete outcome evidence. A callback returns OK when its evidence is available; the recorded build or test process can still have failed. A callback error means the result is unavailable and cannot be recorded as a pass.
  3. Provide a toolchain observation callback. It runs before execution and during closure; it must hash the actual reviewed tools, commands and relevant environment.
  4. Optionally request cooperative ownership of the inventory's existing build directory. The host must resolve presets to that same directory before execution.
  5. Use the progress observer to capture immutable presentation views. This is an observation callback, not an asynchronous job, publication action or authority to mutate the ledger.
  6. Inspect both the returned status and any returned run. Before ledger creation a failure leaves the output null. After creation the caller receives the sealed attempt even when execution, import or final observation failed.

A failed or invalid build prevents the test callback from running. Incomplete or mismatched test reports change no test records. Cancellation prevents later executors; late cancellation remains an explicit interruption even when every test already passed. The first execution failure is retained, and a native lease-release failure also blocks review. A complete but non-passing assessment returns INVALID_STATE; OK requires a ready scoped summary.

Hosts retain tool trust, command construction, process-tree lifetime, cancellation, private raw logs and report ownership. The service does not invent a compiler, run shell strings, automatically retry, or publish repository changes. Before/after observation cannot detect a change followed by a reversal; stable source snapshots and end-to-end CLI/Studio adoption remain separate integration work.

The report's execution-status row retains a terminal orchestration status independently of individual outcomes. Interrupted attempts refuse later result writes. A closed interrupted attempt remains blocked; durable history records cancellation as cancelled and other execution failures with their original status.

Save a qualification result and reopen it later

A qualification archive keeps one attempt's exact selection, identities, outcomes and closing observations. The file is historical evidence. Opening it does not check today's source, run tests or resume an unfinished job. Store reports and their logs in a private directory you choose, outside source repositories.

  1. Let the qualification workflow finish and return its sealed run, including when the run failed or was cancelled. Call UmiQualificationArchiveSave(run, absolutePath, &receipt) from a worker thread. Choose a new filename below an existing trusted directory. The service does not overwrite an existing file or choose a hidden profile directory.
  2. Keep the returned reportSha256, byte count and attempt identity with your private job history. The receipt is returned only after writing and closing succeeds. Keep the detailed build/test logs too: the report records their digests and does not contain their contents.
  3. Reopen the file using UmiQualificationArchiveLoad(path, expectedDigest, &view, &receipt). The reader checks the expected digest when supplied, exact report structure, unique names, the recomputed plan identity and all derived totals and blockers. A malformed or inconsistent report returns an error with no partial view.
  4. Pass the owned view to the GTK qualification panel, or inspect it from the command line. A saved view remains explicitly marked historical. It cannot be converted into a mutable run or used to restart execution.
umicom qualification-report "C:\umicom\_local\qualification\attempt.tsv"
umicom qualification-report "C:\umicom\_local\qualification\attempt.tsv" --all
umicom qualification-report "C:\umicom\_local\qualification\attempt.tsv" --expect-report YOUR_RETAINED_SHA256

Replace the path with a report created by a host using the archive service, and replace the digest placeholder with the 64 lowercase hexadecimal characters from its retained receipt. The command does not create a report itself. Without --all, it shows missing and non-passing rows plus every summary blocker. Exit 0 means that the saved scoped result was ready for review; exit 1 means incomplete or blocked evidence; exit 2 means invalid input, a read failure or an output failure.

If saving fails, the partial file is retained for diagnosis. Choose a different filename for another attempt; do not treat an existing file as proof that saving succeeded. A digest mismatch means the supplied receipt and file differ: retain both and investigate their provenance. A matching digest is not a signature and does not prove the recorded commands actually ran. Only separately trusted execution and logs can support that claim.

The strict version-one parser accepts the canonical LF/tab report format, with hexadecimal name fields and bounded allocations. It rejects unknown versions, extra or missing rows, duplicate names, invalid numbers, contradictory outcomes and altered plan fingerprints. It can inspect an explicitly exported open report as a saved incomplete attempt, but the archive writer accepts only sealed runs. Report parsing and file I/O use the same Framework services from CLI and GTK hosts.

Check the evidence core without rebuilding every application

The independent project in tests/scoped_qualification compiles the real inventory, impact, source observation, qualification ledger, view and archive implementations. It reuses the normal core regression registrations and fixtures. It does not install a second Framework or replace the normal Framework build. Use a separate build directory so it cannot interfere with an application build already running.

  1. Open a terminal with a C23 compiler, CMake and Ninja available. The Windows example below uses the UCRT64 toolchain.
  2. Configure the focused source directory into a separate short binary directory. Keep logs outside the source repository.
  3. Build the focused project and inspect its build log. Stop if the build fails; test results from an incomplete build are not qualification.
  4. Run its registered tests. A successful focused run supports these core services only. The normal Framework build still needs to check optional CTest orchestration, persistent history, GTK presentation, CLI dispatch and installed SDK consumers.
Set-Location "C:\umicom\Umicom-Applications\framework"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
New-Item -ItemType Directory -Force "C:\umicom\_local\logs\qualification-core"
cmake -S ".\tests\scoped_qualification" -B "C:\umicom\_local\build\qualification-core" -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DCMAKE_BUILD_TYPE=Debug 2>&1 | Tee-Object "C:\umicom\_local\logs\qualification-core\configure.log"
cmake --build "C:\umicom\_local\build\qualification-core" --parallel 2 2>&1 | Tee-Object "C:\umicom\_local\logs\qualification-core\build.log"
ctest --test-dir "C:\umicom\_local\build\qualification-core" --output-on-failure --no-tests=error --output-log "C:\umicom\_local\logs\qualification-core\tests.log"

Run each command separately and stop on an error. PowerShell does not automatically stop a pasted sequence after a native program fails. The private build directory keeps fixture files and logs accessible without placing them in a user profile or public source tree. CTest registers file-I/O fixtures below its own working directory; it does not remove existing evidence.

This small project has no installation or launch step. Application launch and full SDK qualification belong to their normal configured projects. Passing its selected tests does not imply that every Framework test or every product passed.

Compare closed attempts without hiding lost coverage

UmiQualificationCompare compares two closed immutable views and owns its result independently of them. It pairs the aggregate build, optional test-process record and exact test names. It reports added or removed test coverage, previously passing evidence that is now missing or non-passing, recovered passes and other outcome/status/exit changes. Timing and log-digest changes remain available in each row without being labelled failures by themselves.

umicom qualification-report "C:\umicom\_local\qualification\after.tsv" --compare "C:\umicom\_local\qualification\before.tsv"

The first file is the later result; --compare names the earlier file. Both must contain closed attempts. Add --all to include unchanged rows. Comparison returns exit 1 when previously passing evidence becomes missing or non-passing, or when test coverage was removed, even if the later selection itself passed. Invalid files or open attempts return exit 2.

Different recorded plan identities mean that selection, source, inventory or toolchain inputs differ. An outcome transition can still help review, but it does not establish its cause. Two reports with the same execution identity do not establish independent runs. Summary blockers and saved-report provenance remain visible; comparison does not run commands, accept a release or update issue records automatically.

Derive affected work from source observations before recording a new execution. Retain earlier failed or missing qualification separately.

Plan the next attempt from recorded outcomes

Include umicom/distribution/runtime/qualification_retry.h and link Umicom::distribution to use UmiReleaseQualificationPlanNext. The service combines an earlier identified attempt, its source baseline, a current source observation and the current toolchain identity. It derives required retry names itself, then uses the shared affected-work graph.

  1. Keep the source observation that was used to create the previous attempt. Keep its closed qualification record separately. A report filename or branch name is not a substitute for these identities.
  2. Capture the current observation from the current configured inventory. Reconfigure after registration, file membership or build configuration changes.
  3. Determine the current compiler, commands, options and relevant environment fingerprint through the host's established toolchain policy. Pass a null toolchain when it is unknown; do not reuse an old value simply to obtain fewer tests.
  4. Call the service with a null output plan pointer and a summary. Check the returned status before reading either output.
  5. Review the source comparison, historical compatibility reasons and selection. Execute through the host, using a new attempt identity and new logs.
UmiReleaseImpactPlan *next = NULL;
UmiQualificationRetrySummary explanation;
UmiStatus status = UmiReleaseQualificationPlanNext(
    inventory, previousSource, currentSource, previousAttempt,
    currentToolchain, &next, &explanation);
/* Use next only after success. It is a selection, not completed execution. */
UmiReleaseImpactDestroy(next);
Earlier evidenceNext selection
Closed, stable, compatible attempt with successful buildConsider its individual passes while retaining failures, skips, missing results and newly affected work.
Test absent from that earlier scoped attemptKeep the test due; absence is not a pass.
Open or interrupted attempt, unsuccessful build/runner, unknown or changed toolchain, mismatched baseline or inventorySelect the full configured graph, including targets without test ownership.
Outstanding earlier name absent from current registrationKeep the unknown name as a reason for full selection; investigate whether its issue has really been retired.
No registered testsReturn UNAVAILABLE without publishing a plan.

historicalPasses counts compatible individual observations considered during planning. It is not the number skipped: a source edit or fixture relationship can select those same tests again. historyReasons explains why earlier evidence could not narrow the work. The source observation summary remains separate from the full-plan request, which need not enumerate changed paths.

The earlier record is never modified. An unsuccessful attempt cannot be overwritten by a successful retry. This service does not search a database, reconstruct an old source snapshot, start a compiler, execute CTest or authenticate supplied evidence. If the old source observation is unavailable after an application restart, keep it unavailable and accept broader selection. Hosts still need complete declared input and environment policies; before/after file reads are not an atomic snapshot.

The installed examples/observed_impact consumer includes history-pass, history-failed and history-unknown-tools modes. These create clearly labelled synthetic records to demonstrate selection; they do not certify an actual product build.

Plan from saved report bytes

UmiReleaseQualificationPlanFromReport uses the same selection rules after strict parsing of an earlier report. It requires a separately retained report digest, current metadata, current observed inputs and toolchain identity. The old baseline remains a separate input. A missing baseline selects the full graph.

The reader validates framing, supported flags, exact names, result invariants, derived counters and the recorded plan identity before planning. It reconstructs a private temporary record, destroys it after selection and never exposes it as a resumed job. Corrupt or mismatched bytes return an error and leave both outputs unchanged.

Use the owner-selected private archive and receipt policy of your host. Hash equality detects changed bytes relative to a retained receipt; it does not authenticate the report or establish actual test execution. The API reads no file paths and executes no commands. Report bytes must already be bounded and length excludes a terminating null byte.

The installed example provides saved-pass, saved-failed and saved-unknown-tools. These destroy the original synthetic attempt before deriving the next selection. They retain source observations in memory, so they are not a durable baseline storage implementation.

Retain the source baseline across restarts

source_observation_archive.h provides UmiReleaseSourceObservationEncode and UmiReleaseSourceObservationDecode. Encoding produces owned bytes, a byte length excluding the string terminator, and a digest. Store this historical data and its receipt privately through the host. Decoding validates the receipt, exact inventory identity, canonical expected path membership, file and total-byte bounds, and the reconstructed source fingerprint.

The decoder reads no source files. Its independently supplied inventory owns the expected file list; data rows cannot redirect it to arbitrary files. Returned observations own their paths independently of the encoded buffer and inventory. Free encoded storage with UmiReleaseSourceObservationFreeEncoded and observations with UmiReleaseSourceObservationDestroy.

A reopened baseline is historical. Capture a separate current observation before planning. The archive does not retain source contents, make an atomic snapshot or authenticate execution. Paths may contain private machine details. Changed inventory or a damaged archive must remain a visible refusal; retain the old evidence rather than editing its fields to obtain a match.

The installed example adds restored-pass, restored-failed and restored-edited. It destroys the earlier baseline and attempt before selecting work from their encoded data. The corresponding selections are 0/0, 1/1 and 2/1 targets/tests. The last mode demonstrates that fresh edits remain due even when earlier synthetic results passed. Memory-buffer demonstrations do not provide host persistence or unattended scheduling.

Capture a baseline and preview the next attempt

The native umicom command now exposes the same Framework archive and selection services. Enable inventory capture during normal configuration with -DUMICOM_RELEASE_INVENTORY_CAPTURE=ON. Use the inventory from that exact build directory and configuration. Finish an active build before reconfiguring its directory.

  1. Create an owner-controlled private evidence directory outside the public repository.
  2. Before an attempt, capture declared source inputs with source-observation. Choose a new filename and retain its printed archive SHA-256 separately. An existing destination is refused.
  3. Keep the qualification report exported by the execution host and its separate report receipt. Raw CTest text or JUnit XML is not the qualification TSV report format.
  4. After a source change, use qualification-plan to inspect the next selection. It reads current inputs itself and derives retries from the earlier report. It does not start execution.
umicom source-observation --inventory "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\release-inventory\inventory-Debug.tsv" --output "C:\umicom\_local\qualification\before.tsv"

umicom qualification-plan --inventory "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\release-inventory\inventory-Debug.tsv"

The second command deliberately has no earlier report and selects the full registered graph. To narrow selection using trusted historical evidence, supply all paired arguments:

umicom qualification-plan --inventory "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\release-inventory\inventory-Debug.tsv" --baseline "C:\umicom\_local\qualification\before.tsv" --baseline-sha256 BASELINE_RECEIPT --report "C:\umicom\_local\qualification\attempt.tsv" --report-sha256 REPORT_RECEIPT --toolchain CURRENT_TOOLCHAIN_SHA256

Replace the three uppercase placeholders with their actual 64-character lowercase SHA-256 values. The toolchain value must describe the current compiler, commands, options and relevant environment under the host policy. If it is unknown, omit --toolchain and accept full selection. Copying the old value simply to avoid work is invalid. Add --summary to omit rows without changing selection.

Both commands return 0 when their own operation succeeds and 2 when input, file access or output fails. A successful preview, even an empty selection, is not a new passing execution. No Git operation, compiler or test process is started. A corrupt archive or report returns an error; it is not silently replaced by an empty history.

Application hosts can use UmiReleaseSourceObservationSave and UmiReleaseSourceObservationLoad for the same explicit file boundary. Save uses exclusive creation, publishes its receipt only after successful close and retains a partial new file on failure. Load checks a separately supplied receipt before decoding. These APIs require absolute paths beneath trusted parent directories; the input adapter rejects final symbolic links and non-regular files, but does not make every parent directory immune to aliasing or replacement.

This is a planning and evidence-storage interface. Unattended scheduling, database selection of historical attempts, stable before/after execution identity and acceptance remain host responsibilities. See automatic builds for the separate existing execution workflow.
