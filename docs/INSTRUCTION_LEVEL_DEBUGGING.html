Instruction-level debugging in Umicom Framework

Use the shared debugger runtime to move through native machine instructions and manage instruction breakpoints from C.

Source steps and instruction steps

A source-level step follows statements described by debug information. One source statement can correspond to several machine instructions. An instruction-level step asks the active Debug Adapter Protocol provider to execute exactly one machine-code step before stopping again.

C or Assembly source→compiler / assembler→machine instructions→debug adapter→Framework models

Framework keeps these concepts separate. Existing source stepping remains available while low-level stepping uses the same persistent debugger session, selected thread and inspection models.

Step one machine instruction

umi_debug_workbench_step_instruction() operates on a paused Framework debug runtime. Pass 0 for an instruction-level Step Over or a non-zero value for instruction-level Step Into.

UmiStatus status = umi_debug_workbench_step_instruction(
    platform,
    0,      /* Step Over one machine instruction. */
    1500U);

The request uses DAP's granularity: "instruction". After the request is accepted, Framework marks the adapter and inspection session as running and clears the old disassembly window. The normal debugger event pump remains responsible for publishing the next stopped event.

Issue another instruction step only after the runtime reports a paused adapter again. A successful request means the adapter accepted the step; the later stopped event identifies where execution actually paused.

Choose an instruction breakpoint

The disassembly model owns the selected and current instruction. umi_debug_workbench_instruction_reference() copies the selected instruction's adapter reference and falls back to the current instruction when no row is selected.

char reference[UMI_DEBUG_INSTRUCTION_MEMORY_REFERENCE_CAPACITY];
UmiStatus status = umi_debug_workbench_instruction_reference(
    disassembly,
    reference,
    sizeof(reference));

This reference is adapter data, not a shell command and not a pointer for the application to dereference.

Toggle an instruction breakpoint

umi_debug_workbench_toggle_instruction_breakpoint() synchronises the Framework advanced-breakpoint registry with DAP setInstructionBreakpoints. Existing enabled instruction breakpoints are preserved when a new one is added or an existing one is removed.

int enabled = 0;
UmiStatus status = umi_debug_workbench_toggle_instruction_breakpoint(
    platform,
    1500U,
    &enabled);
ResultMeaning
UMI_STATUS_OKThe adapter accepted the complete replacement set and Framework updated its models.
UMI_STATUS_NOT_IMPLEMENTEDThe adapter does not advertise instruction-breakpoint support, or the selected instruction cannot be used as a breakpoint target.
UMI_STATUS_INVALID_STATEThe debuggee is not in a paused state suitable for changing machine-level inspection state.

The registry is changed only after a successful adapter response. This keeps the visible breakpoint decoration aligned with the debugger's accepted breakpoint set.

Use the C and Assembly Notes example

Build framework/examples/development/c_assembly_notes with debug symbols. Pause before UmiNotesCountByte(), inspect registers and disassembly, then step into the Assembly routine one instruction at a time. Toggle a breakpoint on a later instruction and continue to it.

Compare the program counter and argument registers with count_byte.S. The C declaration remains the stable ABI boundary; the Assembly implementation follows the calling convention for the selected target.
