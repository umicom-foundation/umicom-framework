Choose project tools and read build output

A project needs a compiler and build tools. Studio stores the chosen tool folder with that project's build settings. This lets you open Studio normally and use the same tools without changing your computer's global PATH. PATH is the list of folders an operating system searches for programs.

Choose where a new project lives

  1. Open Create New Project. The destination starts empty.
  2. Enter the new folder name and choose its parent folder. For example, choosing C:\Projects and naming the folder notes prepares C:\Projects\notes. You can also type the complete destination directly.
  3. Review the complete destination and template before creating the project. Choosing a folder alone creates no files. Creating the project does not build or execute it.
  4. Keep personal projects in a folder you chose. The lesson library is a separate location: selecting lessons does not move your project or authorise its scripts.

Select the build tools

  1. Open Project Build Settings for the current project.
  2. Set Build tools folder to the absolute folder containing CMake, CTest, CPack and Ninja. With an MSYS2 UCRT64 installation this is commonly C:\msys64\ucrt64\bin. Use your actual installation path.
  3. Leave the field empty to use the PATH inherited when Studio started. Enter one folder, not a command or a list of folders. Spaces in a path do not need surrounding quotes.
  4. Review the compiler, generator, build folder, presets, program and working folder. Apply the settings. Only trust a project after reviewing its source and build scripts.
  5. Start the desired build workflow. The selected tool uses an absolute program path; its child processes receive the chosen folder at the front of PATH. Another project and the parent process keep their own environment.

The setting reaches configure, build, clean, test, install and package commands, as well as background Test Explorer discovery and selected test runs. Run also receives the child PATH so that native runtime dependencies can be found. A missing program in an explicitly selected folder is an error: Studio does not silently substitute a different installation.

Inspect tool locations before running them

  1. In Project Build Settings, enter the tools folder and optional C compiler, then choose Inspect developer tool files. This checks the draft choices; it does not apply or save them.
  2. Read the result for CMake, CTest, CPack, Ninja, the selected C compiler, GDB, LLDB and Clangd. An explicit tools folder is searched on its own. A missing file is not replaced by a different installation from PATH.
  3. A blank compiler appears as CMake chooses the compiler during configuration. Presets, an existing CMake cache and generator choices can affect that selection. The inventory does not guess the compiler CMake will use.
  4. A result saying that a file exists confirms its location only. It does not run the file or verify its architecture, dependencies, executable permissions or supported protocols. Not every project requires every listed tool.
  5. If you edit the tools folder or compiler while inspection runs, inspect again. Closing or hiding the form retires the pending result. Apply the settings separately when you are ready.

Choose variables for Run and Debug

An environment variable gives a program a named setting without adding another command-line argument. Use project settings for ordinary values such as a data folder or development mode.

  1. Open Project Build Settings and find Run / Debug environment.
  2. Enter assignments such as APP_MODE=development DATA_FOLDER="C:/Project Data". Names start with an ASCII letter or underscore, followed by letters, digits or underscores. Quote values containing spaces.
  3. Apply the settings and review project trust. Run uses a copied set of values; native Debug supplies the same values to its adapter process for the target to inherit.
  4. Use the program's output or debugger to confirm that it reads the intended setting. Changing the saved values does not modify an already running process; stop and launch again.

The list permits 16 assignments within 1,023 bytes. Duplicate names, including case variants, are refused. NAME= sets an empty value; it does not remove the variable. Values are literal: dollar signs, percent signs and shell expressions are not expanded. Unspecified variables remain inherited. An explicit PATH value replaces its inherited suffix; the selected build-tools folder is still prepended for runtime dependencies.

These settings apply to Run and native Debug only. Configure, Build, Test, Install, Package and Terminal keep their own environment. Studio's process environment is unchanged. Saved settings and debugger configuration records are ordinary local data, so keep passwords and API keys out of this field.

The debugger adapter and its target both receive the launch settings. Adapter policy and shell startup files can subsequently change target values. Framework deliberately avoids supplying a partial DAP env object, because GDB defines that object as the complete inferior environment. See also the LLDB DAP launch reference.

Start the native debugger

  1. Build the project with debug information and review the program and working folder in Project Build Settings.
  2. Choose GDB or LLDB in the debugger settings. With a selected tools folder, Studio looks for gdb or lldb-dap in that folder; Windows adds .exe. Install a debugger that supports the Debug Adapter Protocol (DAP), the messages an IDE uses to control a debugger.
  3. If your adapter lives elsewhere, enter its absolute executable path. That path takes precedence; the project's selected tools folder still reaches the adapter's child PATH for runtime dependencies.
  4. Review the launch and start debugging. The accepted project settings are copied for the pending launch. A later settings change invalidates that request instead of silently changing the program or tools.
  5. Use the debugger's threads, call stack and variables after it stops. A successful build alone does not confirm that an installed adapter supports DAP or that a breakpoint can be resolved.

Missing adapters and protocol failures remain visible errors. Studio does not download a debugger, select another installation or report a debugging session as ready merely because the executable exists.

Check a language server

  1. Open Outline and find the language-server connection form. It starts with a copy of the current project's tools folder; you can edit that draft.
  2. Enter a trusted absolute server path. With a tools folder selected, you may enter a simple name such as clangd instead. Review the arguments and project folder.
  3. Choose Check language server. The check starts a child, reads its advertised capabilities and closes it. It does not send an editor draft, although the server can inspect the project folder.
  4. Wait for the result. Editing the inputs, hiding the panel or closing it cancels the earlier check; an old result cannot establish readiness for new inputs.

This form checks a connection only. It does not activate persistent editor completion, save language-server preferences or change the settings of separate source-query dialogs.

Read a running build

In Output, expand Compiler messages for the current phase. It shows complete retained records while the process runs, with Previous and Next controls for pages of 16 messages. You can select and copy the text. Switching to another build phase returns to its first page; records from the earlier phase remain in its completed result.

The live view retains the first 256 representable records in a phase. Its retention-loss count reports records that could not fit, and parser losses report malformed or oversized records. Use the complete log for additional details. When polling finds no changed text, your text selection is preserved. A phase ending is not itself a success result.

The build panel displays error, warning and note counts for the current phase while output arrives. Counts reset at the next phase. Complete compiler records are recognised from the stream before the bounded console preview drops older text. A CMake message may span several lines and is counted when its message finishes.

The completed Problems list holds at most 256 diagnostics. The live counters can count beyond that list. An unrepresented count means a record exceeded a storage bound or could not be retained; inspect the saved full output when available. Ordinary program output is not a diagnostic. Zero recognised errors does not mean success: process exit status, cancellation and each required workflow stage still determine the result.

Custom executors that supply only final output remain supported. Their counts describe the final bounded preview and are labelled accordingly; they are not described as a complete stream.

Open a source location from a running build

  1. Expand Compiler messages for the current phase in Output.
  2. Click inside the compiler message you want to inspect, then choose Open source at cursor. Use Previous or Next to reach another page.
  3. Studio opens the file through the same document owner as the editor. An already open draft keeps its text, history and unsaved state; this action does not save or reload it.
  4. If the build has moved to another phase, use the refreshed message. A record from an earlier operation cannot silently open a different operation's location.
  5. If the location is ambiguous, inspect the full log and open the correct file yourself. A relative filename is checked under both the captured source and build folders. Two different existing files with that name are refused rather than guessed.

A message needs a real file and a source line. Tool banners, pseudo-files, missing files and external URL handlers are not source locations. Columns are treated as one-based UTF-8 byte positions; a position inside a multibyte character moves to that character's start. A changed draft may no longer contain the reported line; its contents stay intact.

If a tool or test does not start

  1. Check the chosen folder and verify that the expected executable exists there. Studio does not install a tool merely because you enter its folder.
  2. Check whether the project was configured with a different compiler or generator. Review CMake's cache and diagnostic message before changing an existing build directory.
  3. For Test Explorer, configure the project with testing enabled first. Its build folder needs a readable CTestTestfile.cmake.
  4. If you change the tool folder while discovery or a selected run is active, the completed result cannot be published under the new selection. Let the operation stop, then discover or run again.
  5. Read the final process status and saved output. A skipped, cancelled or unstarted test is not a passing test.

For contributors

Use the Framework process search-path helpers to prepare child-only overrides. Do not call a global environment setter from a settings form or worker. Jobs must copy the reviewed tool directory before dispatch and compare current settings before publishing results. The streamed compiler parser owns bounded line and message buffers; consumers own their result lists and must report capacity losses.

Set an SDK path or project build option

CMake cache definitions let a project select dependencies and optional features. They are project settings, so Studio saves them with the same profile as the build folder.

  1. Open Project Build Settings and find CMake definitions.
  2. For an installed Framework SDK, enter -DCMAKE_PREFIX_PATH="C:/SDKs/Umicom", replacing the path with your actual installation root. Forward slashes keep Windows paths easy to read.
  3. Add a project option as another argument, for example -DUMICOM_LESSON_WITH_GTK:BOOL=ON. Quote a whole value when it contains spaces. Several SDK prefixes can share one quoted, semicolon-separated value.
  4. Apply Settings, review project trust, then Configure. The definitions appear as individual literal arguments in the build command and are passed after a selected configure preset.
  5. Read the configure output. An accepted setting does not prove the SDK exists or that the project uses that option. CMake may report an unknown option or missing dependency.

Each argument must have the form -DNAME[:TYPE]=VALUE. Supported optional types are BOOL, PATH, FILEPATH, STRING and INTERNAL. Empty values are allowed. The field accepts up to 1,023 bytes, at most 32 arguments, and fewer than 512 bytes per argument. Names start with a letter or underscore and may then include letters, digits, underscores, dots or hyphens. Duplicate names are refused.

Use the dedicated profile fields for compiler, configuration, testing, warning policy and installation directory. Internal generator and build-tree identities cannot be changed through this field. Toolchain files and other project options can still affect executed build scripts: review them before granting trust.

Clearing an entry stops passing that override on later configure commands. It does not erase a value already cached by CMake. Review the build cache or choose a new build directory when you need a fresh configuration; do not delete a working build tree merely to change an option. Definitions and tool output are not secret storage. Keep credentials out of this field.

See the CMake command reference for cache definitions and the CMAKE_PREFIX_PATH reference for dependency search prefixes.

Run an executable you already built

  1. Open Project Build Settings. Select the existing executable and its working folder. A relative program such as ./build/debug/bin/example.exe is resolved from the project folder. A bare name such as example.exe is refused for this action.
  2. Review the program arguments and Run / Debug environment settings. Grant workspace trust only after reviewing the project and the program you intend to launch.
  3. Search Studio commands for Run current executable. It queues one Run phase and shows output through the normal Output panel.
  4. Use the existing Stop Build control to request cancellation. Read the final status before starting another program or closing the workspace.
  5. Use Build and Run when you want saved sources compiled first. Run current executable leaves editor drafts and source files untouched; it does not check whether the binary is newer than your source.

The file and folders must exist before the job is accepted. This check does not validate executable format or prevent another process replacing the file before launch. The operating system reports launch failures. An accepted job is queued work, not a successful run. Optional output logs retain the same exclusive-file rules as builds, and job history records this action as one launch step.

Keep named build and launch configurations

  1. Open Project Build Settings and expand Saved configurations. Choose Refresh saved configurations. Names belong to this project and the currently selected local settings database.
  2. Edit the build and launch fields. For example, use a separate build folder for a Release configuration, or choose a different program working folder for sample data.
  3. Enter a name such as Debug with sample data, then choose Save form as named configuration. Saving stores a copy; it does not change the active settings or run a tool.
  4. To reuse a saved copy, select its name and choose Load selected configuration into form. This replaces edits in the settings form. Review the fields, then use Apply Settings when you want to activate them.
  5. To replace a saved copy, enter its existing name and explicitly check Replace an existing configuration with this name. The choice resets after a successful save.

The library holds up to 32 configurations per project and host platform. Names are case-sensitive and use 1 to 63 ASCII letters, digits, spaces, dots, dashes or underscores, with no leading or trailing space. The stored profile values still support the same Unicode paths and arguments as ordinary project settings.

If another window saves first, refresh the names and review your selection again. If the workspace, its trust state or the local storage binding changed while the form was open, reopen Project Build Settings. These checks prevent old selections from being applied to a different context. A configuration never contains a workspace trust decision.

Configurations use the same Data Server field encoding as the current project profile. With a SQLite-backed settings connection they survive application restart; memory-only hosts retain them only during the current session. Passwords and API keys do not belong in these settings. Exporting named configurations is not provided by these controls.

Rename or remove a saved configuration

  1. Select the saved configuration. To rename it, enter the new name above and choose Rename selected configuration to the name above. An existing destination name is refused.
  2. To remove it, check Remove the selected saved configuration; keep current form settings, then choose Remove selected saved configuration. Read the result message before continuing.
  3. Names refresh after a successful change. Removal frees a library slot but leaves the current form and active project settings intact. It does not remove project files or build output.
  4. If the library changed elsewhere, refresh the names and choose again. Changing the selection or refreshing the library clears removal confirmation. A failed refresh does not undo a successful operation; inspect the refreshed library before retrying.

Removal cannot be undone by the library. A profile still present in the form can be saved again under a new name. Damaged records and unknown stored fields prevent removal, so a newer extension's settings cannot be silently erased. Keep a backup of the settings database before repairing damaged records. Contributors should extend the shared profile field tables when adding persisted settings; the transaction either publishes the complete library change or reports failure.

Use the real compiler settings in source tools

Build Settings can prepare compiler database export and inspect generated commands. C-family source review forms can use a reviewed database folder for clangd. Follow Use compiler settings with Studio source tools for the complete workflow and supported limits.
