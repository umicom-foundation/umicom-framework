Saving and restoring Framework values

A value archive is a bounded sequence of bytes that represents a record or an ordered registry. It lets storage services retain a value without copying a C structure's padding, unused text or machine-specific integer layout. The existing domain still decides whether the restored fields are valid.

The public APIs live beside their records. For example, bookmarks provide umi_platform_bookmarks_snapshot_archive_encode and umi_platform_bookmarks_snapshot_archive_decode. The bookmark registry adds umi_platform_bookmarks_registry_archive_encode and umi_platform_bookmarks_registry_archive_restore. SDK, testing, desktop, editor, language, project, debug, source-control, UI, designer and chart value families use the same ownership rules.

Save a complete collection

  1. On the registry's owner thread, read its current revision. A revision is an observation token for that particular owner, not a timestamp or an authorization.
  2. Call the registry encoder with that revision, a null buffer and zero capacity. Check the returned status and required byte count before allocating.
  3. Allocate the reported space and encode using the same revision. If the owner changed, discard the old measurement and start again. An undersized buffer receives no partial bytes.
  4. Give the completed bytes to the existing storage service. Use a Data Server transaction when saving related state together. Check both storage and commit results, and retain the previous accepted save after a failure.
  5. Free your buffer after the storage operation has completed. The codecs never retain it.
uint64_t observed = umi_platform_bookmarks_registry_revision(registry);
size_t bytes_needed = 0;
UmiStatus status = umi_platform_bookmarks_registry_archive_encode(
    registry, observed, NULL, 0, &bytes_needed);
/* Check status, allocate bytes_needed bytes, then call again with the
   same observed revision and the allocated buffer. */

The complete, compilable storage lesson includes allocation, transaction errors, recovery and cleanup. It reuses UmiBlobStore over an in-memory Data Server. The same codec can supply another supported storage adapter; file durability and cross-process conflict handling remain that adapter's responsibility.

Restore after review

  1. Read the saved bytes into owned, bounded storage. Apply a product-specific size limit before accepting a large input.
  2. Decide which saved collection the user wants to restore. Restoration replaces the complete collection; an empty archive clears it.
  3. Observe the destination registry's current revision immediately before preparing the restore. Pass that observation to archive_restore.
  4. Inspect the returned status. The decoder verifies the envelope, field layout, checksum, text bounds and each domain value before the existing replacement operation checks duplicate identities and publishes everything together.
  5. Refresh the UI only after successful publication. A refused restore keeps all previous rows and their revision. Successful publication uses the destination's next revision; it never adopts a saved counter as current authority.
Restored values are evidence. A saved command, debugger state, account observation or order draft must be reviewed and revalidated by its live service. Decoding does not connect a broker, run a command, restore credentials, acquire a permission or submit an order.

Use the installed SDK lesson

Copy the installed examples/value_archive directory into a writable working directory. Replace the installation path below with your Framework SDK location, and use a shell containing your C compiler and CMake.

  1. Configure the lesson against the installed SDK:
    cmake -S . -B build -DCMAKE_PREFIX_PATH="C:/UmicomSDK" -DBUILD_TESTING=ON
  2. Build the independent consumer:
    cmake --build build
  3. Run the lesson's check:
    ctest --test-dir build --output-on-failure

The expected console message is Recovered bookmark: Notes project (file:///workspace/notes.c). This lesson demonstrates storage handoff and recovery into a new registry within one process. It uses no real project files and does not prove disk-crash recovery or installed-product readiness.

Understand refusals

StatusMeaning and next step
INVALID_ARGUMENTCheck pointers, buffer rules and the domain fields. No output value is published.
INVALID_STATEThe owner changed after observation. Obtain a new observation and review again; do not force an old revision.
CAPACITY_EXCEEDEDFor encoding, allocate the required output size when reported. For restoration, reduce the collection or investigate exhausted owner counters. Do not reset a live counter.
PARSE_ERRORThe bytes are damaged, truncated, noncanonical or outside the typed numeric/text bounds. Retain the previous state and recover another saved copy.
UNAVAILABLEThe field layout is incompatible, or the host cannot represent a required floating value. Use an explicit migration; never reinterpret raw struct bytes.
ALREADY_EXISTSThe saved collection contains duplicate identities. Examine the rejected row; do not silently discard it.
OUT_OF_MEMORYTemporary restoration storage could not be allocated. The live collection remains intact.

Limits and extension points

Archives are limited to 16 MiB. Individual types have tighter bounds. Restoration also bounds its decoded row storage and uses the existing owner's replacement scratch allocation. The in-memory Data Server's single text value is smaller: the lesson's hexadecimal blob adapter can store at most 2,047 binary bytes through that backend. Larger workspaces need a suitable storage adapter or a separately designed transactional chunk store; do not assume the archive limit is a storage guarantee.

Text ends at its first null terminator. Unused text space and C padding are excluded; text bytes otherwise follow the domain's existing validation and are not automatically normalized. Integer fields have explicit byte order and range checks. Floating fields require finite binary64 values and retain signed zero. A record's structure-size field is rebuilt locally, while other compatibility fields remain subject to its validator.

The checksum detects accidental damage, not a malicious sender. Archives are neither encrypted nor authenticated. Choose deliberately which values may be saved or exported; keep secrets in their established credential storage. A successful envelope inspection alone does not establish valid domain state.

To extend a record, add its new field to the encoder, decoder, schema identity, size bound, validator and member-by-member regression fixture. Schema identity includes the record name, ordered field types and text capacities. Changes to that identity require an explicit migration decision. Keep resource-owning pointers, callbacks and operating-system handles out of these value archives.
