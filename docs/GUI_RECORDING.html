Recording and reporting GUI problems

A useful problem report shows what you tried, what you expected and what happened instead. A screenshot shows one moment. An interaction log adds the order of the actions that led to it.

Consider the Save button in Umicom Notes. You change a document and press Save, but the saved file still contains the old text. A report should show which document was open, how you requested Save, and how you checked the file afterwards. It should not assume that the button worked just because it was clicked.

1. Open the recorder

Open your Umicom application and choose Report problem in its shared titlebar. The recording panel belongs to that application window. Start with a disposable project or training account; do not use a real payment or live order to practise a test.

Recording starts off. Opening the panel does not begin collecting your input. The main window and its related GTK dialogs are the recording scope. Other applications, independent windows and operating-system file choosers are outside that scope.

2. Record a short reproduction

Choose Start, return to the application and repeat the smallest sequence that shows the problem. A short sequence is easier to understand than several minutes of unrelated work. The recorder observes pointer-button releases, keyboard activity and scrolling without taking control of the application.

While recording is active, enter a short note in the recording panel and choose Add note. For example: “Expected Save to update notes.c. The modified marker stayed visible and the file did not change.” Notes are limited to 120 characters; add another short note when needed.

Choose Pause before switching to private work. Start resumes the same session; it does not erase earlier entries. Closing the recording panel stops it. A new panel creates a new session. After 4,096 entries the recorder stops rather than replacing earlier evidence.

3. Add a screenshot

Return to Start when the session is paused. Tick Allow screenshots of visible application content, choose the application window or dialog, and press Take screenshot. The image is saved as a PNG next to the log. Each image captures the selected GTK content, not a video of the desktop or the mouse pointer.

A visible built-in password field, or a component marked private by its developer, blocks the whole image. Other visible information may still be sensitive: source code, account numbers, names and file paths can appear in screenshots. Close private views first and inspect every image before sharing it.

The session permits up to 20 capture attempts and 64 MiB of saved images. Each image is limited to 4,096 × 4,096 pixels and 16 MiB. A very large window or a high display scale can exceed the limit; reduce the window size before trying again.

4. Export and inspect the report

Choose Export report. This pauses collection and writes a JSON data file and an HTML page. Choose Open folder to inspect them. Files are stored in a unique folder inside the operating system’s user-data location under umicom/gui-recordings. The panel displays the exact path.

FilePurpose
session.jsonApplication identifier and the available runtime information, saved when recording starts.
events-live.jsonlOne observation per line, flushed as it is recorded. Earlier lines can help after an unexpected application exit.
events-000001.jsonA complete export of the retained observations. Later exports use another filename.
report-000001.htmlA readable table you can open in a browser. Screenshot links refer to files beside it.
frame-000001.pngAn image you explicitly chose to capture.

Keep the files together so the image links work. A report is local: the application does not upload it or create a GitHub issue automatically. Review its contents, remove anything unnecessary from the copy you intend to share, and compress that reviewed copy into a ZIP.

If the application stops before Export, look for session.json and events-live.jsonl. A final line may be incomplete after a crash. Flushing the log does not guarantee survival of a power loss or storage failure.

5. Explain the outcome

An entry marked Not asserted means the recorder saw an input but did not check the operation’s result. This is normal for a human recording. Add what you observed and how you checked it.

A control without an existing stable identifier is labelled unidentified followed by its GTK type. This helps identify gaps in test coverage, but it is not a unique location. A screenshot and your reproduction steps help the developer find it. Not every menu or popup exposes a useful target through the same event route.

Practise with Umicom Notes

Open two source documents in a practice Notes project. Change one line in the first document and add a comment to the second. Start the recorder, select the first document and use the Save menu. Check the first file on disk and confirm that the second draft is still unsaved. Add a note describing the result, capture a screenshot when useful, then export.

Repeat the exercise using the keyboard shortcut. These are separate routes to the same operation; one can be connected correctly while the other is not. Never reset or discard real work to make a test easier.

What to include when reporting a defect

Give the report a clear title, such as “Save toolbar does not update the active document”. Include the application and Framework revisions, operating system, display scale, starting state, steps, expected result and actual result. Explain whether it happens every time. Attach only the reviewed logs and images needed to understand it.

The recorder stores the application ID, GTK version, available OS name/version and process bitness. It does not infer Git commits from a potentially different source checkout. Developers should record the revisions used to build the executable separately.

Recording a video

On Windows, Windows + Shift + S opens image capture and Windows + Shift + R opens video capture in Snipping Tool. Select only the relevant area, reproduce the problem, stop and review the recording. A video can show menus, pointer movement and operating-system dialogs that are not part of the GTK recording scope. Microsoft’s Snipping Tool guide explains both modes.

Privacy and limits

Typed characters, clipboard contents and widget text are not collected by the input recorder. Explicit notes and screenshots are different: they contain the information you chose to include. Do not type credentials into notes or share screenshots of confidential records.

The recorder is a problem-reporting tool, not a global keylogger, a video encoder or a general macro player. It does not replay a recorded session, inspect every command handler or discover every defect automatically. Automated scenarios add explicit checks for the expected application state.

Related dialogs are discovered periodically, so a very short-lived window can close before it is observed. Screenshot rendering and local export currently use the GUI thread. If that thread freezes, use an external screenshot/video tool and retain the available log. Do not interpret missing observations as proof that no input occurred.
