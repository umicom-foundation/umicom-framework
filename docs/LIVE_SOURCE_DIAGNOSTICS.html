Live source diagnostics

A language server is a separate program that analyses source code. Framework can keep one selected server running for one document while an editor sends updated drafts. Diagnostics are the warnings and errors returned by that program. They do not mean the project has been built or tested.

Use the native panel

  1. Open a named source file in a trusted project. Choose Live diagnostics… in Studio's code tools.
  2. Check the language-server program and its arguments. For C and C++, use an installed clangd executable. A selected tool folder controls local executable lookup; it is not a download or installation step.
  3. For clangd, inspect the project's compile_commands.json and use its folder in the arguments. See compiler database setup. Do not pass clangd-specific arguments to another server.
  4. Choose Start live diagnostics. The selected local process receives a copy of the open draft. No source file is saved by this operation.
  5. Edit the document. The panel samples the draft approximately every 350 milliseconds while mapped. A changed draft clears the previous display; a report appears when the server publishes diagnostics for the new source version.
  6. Use Previous diagnostics and Next diagnostics for further pages. Each page shows up to 32 entries; very long messages are visibly shortened.
  7. To visit a reported location, choose its Diagnostic number and select Open source. The complete current draft must still match the report. Moving the caret or switching tabs is allowed; changed text is refused without moving to a different location.
  8. Choose Stop before changing the server settings. Closing or hiding the panel requests cancellation. Reopening a panel requires a fresh Start.

Connect another editor

  1. Create a UmiLanguageDiagnosticMonitorConfig with explicit project directory, root URI, document URI, language and initial source. Creation copies this data and starts no process.
  2. Run UmiLanguageDiagnosticMonitorRun once on a dedicated worker. Keep GTK widgets and document models on the editor thread. The worker alone owns the protocol session.
  3. Call UmiLanguageDiagnosticMonitorSubmit with complete UTF-8 snapshots. Keep the returned source sequence with the current draft. New pending text replaces older unsent text, so rapid typing does not create an unlimited queue.
  4. Read publications with UmiLanguageDiagnosticMonitorTake. Display only a catalogue whose returned sequence still matches your captured source. Destroy the catalogue after use. Clear any displayed catalogue immediately when your editor changes the draft or rejects a new submission.
  5. Call UmiLanguageDiagnosticMonitorStop when trust, document identity or workspace ownership changes. Join the worker before destroying the monitor. A completed flag does not replace joining the thread.

The lower-level session API supports an exclusive caller-owned transport for other hosts. Once initialization begins, the session owns protocol sequencing and stops the transport when closing. The caller still destroys a borrowed server object; native sessions own their server object.

Protocol and ownership limits

The server must support opening documents and full or incremental text synchronization using UTF-16 positions. Incremental synchronization sends one range replacing the entire preceding document; this is valid incremental protocol, not an optimized edit differ. Each session tracks one document and increases its protocol version only when text changes.

A publication must match the document URI and current version. An unversioned publication is accepted only before the first source change. After that, an unversioned report cannot prove which draft it describes and is ignored. Servers may skip intermediate drafts or publish nothing; an empty display is not proof that compilation would succeed.

Source text and encoded protocol messages have bounded capacity below 64 KiB. JSON escaping adds bytes, so a source draft can exceed the wire limit before reaching the text limit. Invalid UTF-8, embedded NUL, unsupported synchronization, malformed ranges and unexpected server requests are reported rather than silently accepted. Dynamic registration, configuration requests, server-initiated edits and alternative position encodings are not implemented in this session.

Cancellation is cooperative and uses the existing native process transport. The panel samples host authorization with the draft; it is not an instantaneous security boundary or a process sandbox. A language server can read files and run other programs with the user's permissions. Use a trusted executable and project. The transport's direct-child shutdown does not promise termination of every independently created descendant process.

Troubleshooting

  1. If startup reports a missing executable, choose its full path or the correct project tool directory.
  2. If C include files are unresolved, regenerate the compiler database and check its source-file entry and selected build directory.
  3. If changed drafts produce no output, check the status for unversioned reports and inspect the server's synchronization support. Stop, correct the settings and start a new session.
  4. If a draft exceeds capacity, stop this panel and use the project's compiler diagnostics. Source text is never truncated for analysis.
  5. If the document is renamed, closed or the project changes, reopen Live diagnostics from the intended document. A panel never silently follows a different tab.
