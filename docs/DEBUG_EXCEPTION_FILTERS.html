Pause on exceptions

A debugger can pause when a running program encounters an exception. Each adapter decides which exception filters it supports. Studio displays the adapter's own labels instead of assuming that every language has the same exception categories.

Choose filters in Studio

  1. Open a trusted project and start a native debug session, or attach to an application you are authorised to debug.
  2. Open the Debug surface and expand Pause on exceptions.
  3. Choose Refresh exception filters. If the adapter advertises no filters, Studio explains that there are no choices for this session.
  4. Select the filters you want and choose Apply exception filters. This replaces the complete selected set. Clearing every checkbox and applying sends an empty set.
  5. Read the result beneath each selected filter. Verified by adapter means that the adapter supplied positive per-filter verification. Not verified by adapter includes its explanation when available. Accepted; individual verification not supplied means that the request succeeded but the adapter omitted individual results.

Changing a checkbox alone sends no request. Refresh discards unapplied checkbox changes. Choices are held for this connection and are not saved as a global debugger preference.

What happens when connecting

During native initialization, Framework reads the advertised catalogue. After the adapter signals that configuration can begin, Framework sends its advertised default selection before completing configuration. If no filters were advertised, it sends no exception-filter request. Existing source breakpoints still use their normal configuration sequence.

Stale selections and failed requests

A selection belongs to one session and one configuration revision. An older panel cannot silently reapply choices after another edit or a new session. Refresh and review the current choices when Studio reports that the state changed.

An adapter refusal, malformed response or timeout leaves acknowledgement unavailable. The target may already have received the change, so Studio rereads its local request state without automatically resending it. The controls do not resume the target, evaluate an expression or terminate a process.

Framework integration

UmiDebugRuntimeExceptionFiltersRead returns an owned copy of the catalogue, selection and acknowledgement. Modify only the selection's checkbox values, then pass it to UmiDebugRuntimeExceptionFiltersApply on the platform's owner thread. The platform checks session identity, revision, entry count and boolean values before sending anything. Hosts must also check their current workspace authority.

The GTK panel accepts host Read and Apply callbacks. It owns the callback context until destruction, keeps callbacks on the GTK thread and refuses Apply from a hidden panel. Applications supply their own trust and lifecycle checks without duplicating the protocol layer.

Supported scope

The catalogue is bounded to 32 filters, with bounded UTF-8 text. Malformed, duplicate or oversized advertised entries are rejected rather than silently truncated. This implementation supports basic filter selection from the initialization catalogue. Filter conditions, exception path options and dynamic replacement of that catalogue are not exposed here. Reconnect after changing adapter configuration. Requests wait synchronously for bounded replies.

The protocol mapping follows the official Debug Adapter Protocol specification: the advertised exceptionBreakpointFilters supply the IDs for setExceptionBreakpoints. Per-filter breakpoint verification is optional, which is why the interface reports missing verification separately from success or refusal.
