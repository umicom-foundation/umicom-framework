# Native decoder inference and text generation

**Sammy Hegab · Umicom Foundation · MIT**  
**Canonical implementation:** Umicom Framework (C23)

## Purpose

This learning laboratory demonstrates that a decoder trained using the native
Framework can be loaded from an approved local checkpoint and used for
**autoregressive next-token generation**. It does not introduce a second model
implementation under the application. The decoder, checkpoint codec, byte
tokeniser and deterministic PRNG are the existing Framework implementations.
The new generation service composes those existing capabilities.

A generated token is not a proof of correctness. The present model is a small
single-block educational transformer with a 260-token byte vocabulary. Its
training examples are limited; generated output will often be nonsensical,
contain NUL bytes, or fail UTF-8 validation.

## Generate from an explicitly approved checkpoint

The steps below assume the repositories are at their established local paths.
Do not run a checkpoint downloaded from an untrusted source. The checkpoint
checksum detects accidental corruption, not malicious replacement.

```powershell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

cmake -S ".\framework\learning\native-llm" `
    -B ".\build\windows-ucrt64-native-llm-debug" `
    -G Ninja -DBUILD_TESTING=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build ".\build\windows-ucrt64-native-llm-debug" --parallel 2
ctest --test-dir ".\build\windows-ucrt64-native-llm-debug" `
    --output-on-failure --no-tests=error
```

Create a *new* checkpoint using the existing native experiment tool. Adjust
the filename if you have already used it: the training program intentionally
refuses to overwrite an existing checkpoint.

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-experiment.exe" `
    ".\framework\learning\native-llm\fixtures\experiment.conf" `
    "C:\umicom\_local\umicom-decoder-example.umi"
```

Generate 24 bytes greedily from a short C source prompt:

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-generate.exe" `
    "C:\umicom\_local\umicom-decoder-example.umi" `
    "int account" 24 1 1.0 42
```

Try stochastic top-K sampling using the same checkpoint and prompt:

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-generate.exe" `
    "C:\umicom\_local\umicom-decoder-example.umi" `
    "int account" 24 8 0.8 42
```

The positional arguments are: approved checkpoint, quoted prompt, maximum
new-byte count, top-K, temperature and random seed. Only the first two are
required. Output is escaped (`\n`, `\t`, `\xHH`) so raw generated control
characters cannot modify the terminal or execute any action.

## Why generated bytes cannot always be shown directly

The byte vocabulary reserves IDs 0–3 for special purposes. ID `4+byte` stores
every byte value exactly, including zero. The model has not been trained with
reliable end-of-sequence targets, so the generator produces exactly the
requested number of bytes. The native sampling service excludes special IDs
from its output distribution.

The generated bytes may include isolated UTF-8 continuation bytes or NUL.
Therefore the Framework returns a byte buffer and its *explicit length*, not
a NUL-terminated string. A host application must validate, escape, or otherwise
handle binary output before rendering it as text.

## How inference works

For each new position, the generator constructs the most recent
`contextLength` token IDs, left-padding a short prompt with the reserved
beginning-of-sequence ID. It asks the canonical decoder for logits, reads only
the final row, excludes the four reserved IDs, selects a token, and appends it
to its private generation history. The next iteration includes the new token.
When all steps succeed, the caller receives the entire generated sequence.
Rejected input leaves the supplied output buffer and count unchanged.

**Greedy selection** chooses the highest logit (tie: smallest token ID). It does
not consume random state. **Top-K selection** chooses from only the K largest
eligible logits; the seeded Framework PRNG selects among these using stable
softmax probabilities at the requested positive temperature.

For logits `2, 1, 0` and temperature `1`, the corresponding probabilities are
approximately `0.6652, 0.2447, 0.0900` after normalising the exponentials.
Restricting to top-K=2 discards the third token, producing approximately
`0.7311, 0.2689` between the remaining candidates. Lower temperatures
concentrate the distribution; higher temperatures flatten it.

## Verifiable engineering boundaries

- Training and inference reuse the same decoder implementation and checkpoint
  encoding. All service APIs are exposed from the Framework's stable C ABI.
- The current implementation recomputes the entire rolling context at every
  step; it does **not** yet implement a KV cache or streaming output.
- Output is limited to 256 newly generated tokens per call and at most 4,096
  prompt bytes. The decoder itself supports at most 32 context tokens.
- Neither model parameters nor optimiser step counts change during inference.
- There is no content-safety classifier, command execution, external network
  request or authority to alter application state.
- The supplied seed is for *reproducibility*, not secrecy. Do not use this PRNG
  for cryptographic or security-sensitive decisions.
- The service does not certify generalisation, coding skill, correctness or
  Calypso integration knowledge. Such claims require independent evaluation.

## Verification

The CTest inventory includes deterministic and stochastic sampling, rejected
numeric settings, byte/token roundtrips, greedy generation, prompt context,
checkpoint reload equivalence, and proof that generation leaves saved model
weights unchanged. Execute the complete isolated native training laboratory
before incorporating it into any application. The optional root Framework
CMake registration is described in the merge instructions; the complete
Umicom Applications build is not implied by a successful isolated run.

## Exercises

1. Run identical prompts with the same seed and verify identical output.
2. Keep the seed constant but change top-K from 1 to 8. Explain the difference
   between deterministic and stochastic prediction.
3. Train a larger, reviewed corpus and compare independently measured held-out
   cross-entropy before judging whether generation has improved.
4. Explain why the interface returns bytes with a length rather than `char *`
   treated as a C string.
5. Describe what additional state a future KV-cache implementation will need
   to preserve and verify, especially when the model uses learned positions.
